## 1. 一句话定位

本节先把论文压缩成一个可以在半分钟内讲清楚的结论。

**SchGen 把“自然语言描述 PCB 功能”转成可执行的 Python 原理图代码，再由 KiCad API 生成可编辑原理图：它用带相对坐标和引脚名连线的 Code-L1 表示，对 GPT-oss-20B 做 LoRA 监督微调，训练数据由 1390 种设计扩成 8420 个请求-代码样本，得到 82.00% 的有效电路率和 60.5% 的专家功能正确率，并在同一表示下超过 GPT-5.2、GPT-o4mini 和 Grok-4。**

这句话里的六个承重点，后文按同样顺序展开。

1. **任务从自然语言开始，而不是从网表开始。**
   用户只需描述电源、LED、USB、连接器或微控制器等功能需求。
   模型的目标是输出能被执行、能在 KiCad 中打开和继续编辑的 PCB schematic，而不是一张不可编辑的图片。
   这也是论文定义的新学习任务：natural-language-to-PCB-schematic generation。

2. **表示设计是主要瓶颈。**
   原始 KiCad 文件虽然是文本，却包含大量版本相关元数据和绝对几何坐标，LLM 很容易产生格式错误。
   图片表示不能直接编辑，也不便于机器检查。
   SchGen 将设计动作抽象成添加符号、放置标签、查询引脚位置和按引脚名连线等 Python API。

3. **Code-L1 把几何预测改成语义匹配。**
   符号相对于局部锚点用偏移量放置，导线通过 `symbol_ref` 与 `pin_name` 连接。
   因而模型不必同时精确回归整张图的绝对坐标和每一段折线，只需理解“哪个元件的哪个功能引脚连接到哪里”。
   论文的消融结果显示，相对坐标和引脚名连线缺一不可。

4. **数据由 agent-human 协作构造。**
   论文从开放硬件设计和 SparkFun 资源获取参考图像，先让多模态 LLM 生成草图代码，再执行代码收集错误反馈，并由人工修正复杂连接。
   对齐后的 KiCad 文件再被解析为 Code-L1/L2/L3，并由多模态 LLM 生成简洁或详细的用户请求。
   这样把原本只有图片的开放设计转成可监督训练的“请求-代码-思考”样本。

5. **训练的是专门化生成模型。**
   SchGen 以 Apache-2.0 许可的 GPT-oss-20B 为底座，使用 SFT（Supervised Fine-Tuning，监督微调）和 LoRA（Low-Rank Adaptation，低秩适配）。
   数据中还加入由 GPT-oss-120B 和 GPT-oss-20B 蒸馏出的 CoT（Chain of Thought，思维链）过程。
   论文报告的配置是 1 张 NVIDIA A100 80GB、3 个 epoch、约 21 GPU-hours。

6. **“有效”不等于“可以直接制造”。**
   82.00% 只表示 Python 能执行且 KiCad ERC 没有 critical error；60.5% 是两位专家对 100 个测试设计评估的功能正确率。
   论文没有把完整 PCB 送入制造，也没有完成板级信号完整性、热、EMI 或可制造性签核。
   这条边界在第 9 节和第 10 节会单独拆开。

### 1.1 论文回答的核心问题

论文真正要解决的不是“LLM 会不会写 Python”，而是三个相互耦合的问题。

- **怎样表示 schematic。**
  表示必须短、可读、可执行，还要保留组件语义、引脚语义和布局关系。

- **怎样获得成规模的配对数据。**
  公开 PCB 资源常以图片发布，图片缺少可直接训练的编辑操作序列。

- **怎样判断生成结果是否真的可用。**
  单看字符串相似度不够，必须同时检查代码可执行性、ERC、空间重叠、netlist 和专家功能判断。

### 1.2 端到端直觉

可以把 SchGen 看成一个三层编译器。

- 第一层把人类意图编译成语义化 Python 操作。
- 第二层把这些操作执行成 KiCad 原理图和组件引脚网络。
- 第三层把原理图导出为 PCB layout 所需的 netlist。

它没有替代 PCB layout、铜线 routing 或制造工艺；它把自动化的起点从“手工画 schematic”提前到了自然语言。

## 2. EDA 阶段映射（①-⑰）

本节要解决的问题是：把一个 PCB 论文放进资料包统一的 17 阶段数字芯片流程时，哪些是直接覆盖，哪些只是最接近的类比。

标准芯片流程见 [芯片流程.md](../芯片流程.md)。该流程针对数字 IC；SchGen 的对象是板级组件、原理图符号和电气网络，所以表中的“覆盖”不能被解读为它完成了对应芯片工具链。

| 阶段 | 覆盖 | PCB 对应与边界 |
|---|:---:|---|
| **① RTL 设计** | ⚠️ 最接近的核心 | PCB schematic 的系统架构、器件选择、功能模块和连接关系在抽象层面最像 RTL 设计；但 SchGen 不输入或生成 Verilog/VHDL，也不描述触发器和组合逻辑。 |
| **② RTL 功能仿真** | ❌ | 没有数字 RTL testbench 仿真。模型只生成原理图代码，代码执行成功不是电气功能仿真。 |
| **③ 逻辑综合** | ⚠️ 类比交接 | `write_out_all_wires()` 将语义化操作编译为 KiCad schematic，并可导出 netlist；这类似“把高层描述变成下一阶段结构”，但不是标准单元映射、逻辑优化或门级网表综合。 |
| **④ 门级仿真** | ❌ | 不生成门级网表，不用 SDF 反标延迟，也不跑门级 testbench。 |
| **⑤ STA** | ❌ | 不做时钟路径、setup/hold、WNS/TNS 或工艺角静态时序分析；PCB 原理图中通常也没有统一的芯片时钟约束。 |
| **⑥ 形式验证** | ❌ | 没有 SAT/SMT 等价证明。KiCad ERC 是规则检查，不等价于 RTL 与门级网表的形式等价验证。 |
| **⑦ 布局规划（Floorplan）** | ⚠️ 仅有视觉相邻概念 | SchGen 在 schematic 画布上选择中心符号并相对放置外围符号；这改善原理图可读性，但不决定 PCB 板框、层叠、宏器件和电源网络。 |
| **⑧ 标准单元摆放（Placement）** | ❌ | 没有把芯片标准单元放到硅片坐标，也没有 PCB layout 中的封装摆放；原理图符号坐标不是实物元件坐标。 |
| **⑨ 时钟树综合（CTS）** | ❌ | 不插时钟缓冲器、不平衡时钟 skew，也没有芯片 CTS 阶段。 |
| **⑩ 布线（Routing）** | ⚠️ 只涉及 schematic wire | `connect_pins()` 和 `write_out_all_wires()` 连接符号引脚并做基础自动走线；它画的是原理图连线，不是带宽度、阻抗、层和过孔约束的 PCB 铜线 routing。 |
| **⑪ 后仿真** | ❌ | 论文明确不采用 SPICE 作为整体评估；没有 SDF 加 SPEF 的版图后仿真，也没有寄生 RC。 |
| **⑫ 物理验证（DRC/LVS）** | ⚠️ 只做 ERC 级别前置检查 | 有效电路率要求 KiCad ERC 无 critical error；没有 PCB DRC 的线宽/间距检查，也没有版图与原理图的 LVS。 |
| **⑬ 签核（Signoff）** | ❌ | 专家验证和 netlist 指标是研究评估，不是 STA、功耗、IR drop、EMI、DRC 全通过后的制造签核。 |
| **⑭ 流片（Tape-out）** | ❌ | 输出不是 GDSII，未向晶圆厂提交版图。PCB 设计也有制造文件，但论文没有走到该阶段。 |
| **⑮ 制造（Fabrication）** | ❌ | 没有光刻、刻蚀、掺杂或 PCB 打样结果的实验。 |
| **⑯ 封装 + 测试** | ❌ | 组件封装名称可能出现在符号/元件值中，但没有成品板组装、ATE 或实验室电气测试。 |
| **⑰ 芯片到手** | ❌ | 论文交付的是可编辑 KiCad schematic 和 netlist 前置产物，不是流片后的芯片。 |

**覆盖率：2/17（阶段 ① 和 ③ 为方法核心的 PCB 类比阶段；PCB 原理图不在芯片 17 阶段框架内，其余标注仅供跨域参考）。**

表里的两个核心相邻阶段需要这样理解。

- ① 对应“设计意图落到器件和连接”这一层，不对应寄存器传输。
- ③ 对应“从可读的高层操作得到结构化网络”这一层，不对应综合器的 Boolean optimization 和 technology mapping。

> **最容易被误读的边界：** SchGen 的“功能正确”由 ERC、netlist 对比和专家检查近似衡量；它不代表板子在真实电压、电流、温度、噪声、时序或制造条件下工作，更不代表数字芯片 RTL-to-GDSII 流程已经完成。

### 2.1 为什么把 ① 作为最接近阶段

数字芯片的 ① RTL 设计描述模块、数据通路和控制关系。

PCB schematic 的对应工作是选择 MCU、稳压器、电阻、电容、连接器、电源符号和标签，并规定它们的 pin-to-pin connectivity。

两者都在物理实现之前确定系统架构，但抽象对象不同。

RTL 的节点通常会在综合后变成标准单元；PCB schematic 的节点通常是带有封装信息的器件符号，随后交给 PCB layout。

因此这里使用“最接近”而不是“等同”。

### 2.2 为什么 ③ 只能标为类比

芯片逻辑综合有明确的输入 RTL、标准单元库和约束文件，并输出 gate-level netlist、SDF 与 SDC。

SchGen 的代码执行器则读取 API 调用，查找 KiCad symbol library 中的器件，解析 pin location，最后写出 `.kicad_sch` 和 wires。

它完成了表示转换，却没有把 Boolean function 优化成 AND、OR、DFF 等 cell，也没有优化 PPA。

“有一个从高级描述到结构化电路的编译动作”是共同点；“输出是什么电路、由什么工具优化”是根本差异。

### 2.3 ⑦、⑧、⑩ 的三个空间层次

原理图上的 `pos_x` 和 `pos_y` 主要服务于人类阅读。

PCB layout 的 placement 使用 footprint、板框、层、机械禁布区和热/电气规则。

PCB routing 还要处理铜箔宽度、差分对、阻抗、过孔和回流路径。

所以 SchGen 的 relative coordinate 只解决“符号在 schematic 页面上怎样排得可读”，不能替代 ⑧ 的封装 placement 或 ⑩ 的铜线 routing。

## 3. 输入 / 输出

本节要解决的问题是：一个自然语言请求经过哪些可观察的中间产物，最后到底得到什么文件和什么质量信号。

### 3.1 输入：用户请求

SchGen 的直接输入是用户对板级功能的自然语言描述。

论文用两种风格扩充请求分布。

- **Concise request。** 面向不了解 PCB 细节、只给功能摘要的用户。
- **Detailed request。** 指定元件、数值、引脚关系、电源网络和预期行为。

论文附录给出的简洁请求如下。

```json
{"messages": [{"role": "user", "content": "I want a 1.8V regulated supply from VIN using an AP2112K LDO, with a test point on the 1.8V rail and a solder-jumper-selectable LED indicator.\n"}]}
```

同一任务的详细请求指定了更多工程意图。

```text
I am looking to add a small 1.8 V power block to a larger board, mainly to step
 down a VIN rail and provide a clean +1V8 output. I would also like a simple
 visual indicator to show when the rail is active, with a solder jumper to disable
 it. Use an AP2112K-1.8 in SOT-23-5. Tie EN to VIN, leave NC unconnected, and
 place a 1 uF capacitor between VIN and GND. Put an LED on +1V8 through a 220 Ohm
 resistor and a solder jumper to GND. Add a test point on +1V8, and keep VIN,
 +1V8, and GND as the main net labels.
```

这两个输入表达的是相同的电路意图，但对模型的检索和规划难度不同。

详细请求给出器件值和连接约束，简洁请求要求模型从功能描述中补全器件选择。

### 3.2 输入中的领域上下文

模型还需要由代码提示提供 schematic API 说明、符号库上下文和示例代码。

论文的公平比较会给不同 LLM 相同的 Python APIs 和 example code。

实际仓库 README 还要求扫描 KiCad 库，生成 `organized_fp.json` 和 `organized_lib.json` 等上下文文件。

因此输入不是单独一段自然语言；完整推理上下文可以抽象为下面三部分。

```text
用户请求
  + API 函数签名与语义
  + 可用 KiCad symbol library / pin context
  = 模型生成条件
```

如果缺少符号库上下文，模型即使理解“稳压器”也可能写出不存在的库名、器件名或 pin name。

如果缺少 API 示例，模型可能退回到原始 KiCad s-expression 或绝对坐标 wire。

### 3.3 Code-L1 的最小可执行输出

下面是根据论文 Listing 1 清理排版后的最小化输出片段。

它保留一个 AP2112K-1.8 稳压器、输入去耦电容、输入/输出电源符号、测试点和 LED 支路的关键操作。

```python
import os
import sys

PROJECT_PATH = os.environ["PROJECT_PATH"]
sys.path.append(PROJECT_PATH)
from modules.kicad_sch_interface import *

center_x_1, center_y_1 = 120, 105
add_schematic_symbol(
    symbol_lib="Regulator_Linear",
    symbol_name="AP2112K-1.8",
    pos_x=center_x_1,
    pos_y=center_y_1,
    reference="U1",
    value="AP2112K-1.8",
    rotation=0,
    mirror="None",
)
add_schematic_symbol(
    symbol_lib="power",
    symbol_name="VAA",
    pos_x=center_x_1 - 20,
    pos_y=center_y_1 + 5,
    reference="#PWR1",
    value="VIN",
    rotation=0,
    mirror="None",
)
add_schematic_symbol(
    symbol_lib="Device",
    symbol_name="C",
    pos_x=center_x_1 - 20,
    pos_y=center_y_1 - 5,
    reference="C1",
    value="1uF",
    rotation=0,
    mirror="None",
)
add_schematic_symbol(
    symbol_lib="power",
    symbol_name="GND",
    pos_x=center_x_1 - 20,
    pos_y=center_y_1 - 24,
    reference="#PWR_C1",
    value="GND",
    rotation=0,
    mirror="None",
)
add_schematic_symbol(
    symbol_lib="power",
    symbol_name="+1V8",
    pos_x=center_x_1 + 13,
    pos_y=center_y_1 + 5,
    reference="#PWR_1V1",
    value="+1V8",
    rotation=0,
    mirror="None",
)
add_schematic_symbol(
    symbol_lib="Connector",
    symbol_name="TestPoint",
    pos_x=center_x_1 + 16,
    pos_y=center_y_1 + 2,
    reference="TP1",
    value="TP1",
    rotation=270,
    mirror="x",
)
connect_pins("#PWR_1V1", "+1V8", "TP1", "TP1")
connect_pins("#PWR1", "VIN", "C1", "1")
connect_pins("U1", "VOUT", "#PWR_1V1", "+1V8")
connect_pins("#PWR1", "VIN", "U1", "VIN")
connect_pins("U1", "VIN", "U1", "EN")
connect_pins("C1", "2", "#PWR_C1", "1")
connect_pins("C1", "2", "U1", "2")
write_out_all_wires()
```

这段代码不是直接写出每一段绝对坐标 wire。

`center_x_1` 和 `center_y_1` 是局部锚点，外围器件使用相对偏移。

连接操作引用 `U1`、`C1`、`TP1` 和引脚名，而不是依赖脆弱的线段端点。

### 3.4 API 输入与输出契约

论文给出的 API 抽象可以整理为下表。

| API | 主要输入 | 主要作用 | 产生的语义 |
|---|---|---|---|
| `add_schematic_symbol` | symbol library、symbol name、坐标、reference、value、rotation、mirror | 在 KiCad 页面放置组件符号 | “有哪个器件、放在哪、如何朝向” |
| `add_label` | label position、文本、label reference、类型、方向 | 放置电源/网络标签 | “这个局部网络叫什么、怎样作为接口” |
| `get_pin_location` | symbol reference、pin name | 查询具体引脚位置 | 把语义引脚解析成几何端点 |
| `connect_pins` | 两个 symbol reference 和两个 pin name | 连接两个引脚 | “哪两个电气端点属于同一连接” |
| `write_out_all_wires` | 当前已注册的符号和连接 | 写出 KiCad 文件并进行基础自动走线 | 可打开、可编辑的 schematic |

论文在 API 原型处使用 `x, y, ref` 形式的短参数名，而 Listing 1 使用 `pos_x, pos_y, reference` 关键字。

本文的代码示例沿用附录 listing 中实际出现的关键字写法；二者表达的是同一层 API 抽象，具体关键字应以仓库当前实现为准。

对于 power symbol 和 net label，论文规定它们通常只有一个 pin，默认 pin name 为 `1`。

实际示例中，电源符号也可能使用可读的名字如 `VIN` 或 `+1V8` 作为连接语义。

### 3.5 中间产物一：语义化操作序列

模型首先输出一段 Python 程序，而不是最终的 KiCad s-expression。

这段程序包含几个逻辑区块。

```text
导入 API
  ▼
选择中心器件并设置 anchor
  ▼
以相对坐标放置外围器件与标签
  ▼
按 reference + pin name 建立连接
  ▼
调用 write_out_all_wires
```

这一步的关键中间表示是“可执行编辑操作序列”。

它同时承载组件清单、布局关系和连接关系，因而可以被 LLM 阅读，也可以被解释器验证。

### 3.6 中间产物二：KiCad schematic

API 执行后生成可在 KiCad 中打开的 schematic 文件。

文件中会包含组件符号、power symbols、net labels、引脚和 wire 几何。

它是可编辑的工程中间产物，而非模型输出的不可修改渲染图片。

```text
Python Code-L1
      │ 执行
      ▼
KiCad .kicad_sch
      │ 打开与 ERC
      ├──────────────▼
      │          ERC 报告
      ▼
组件与网络图
```

### 3.7 中间产物三：网络图与 netlist

论文把 netlist 表示成一组网络，每个网络是若干 `(symbol, pin)` 节点的集合。

例如，一个简化的稳压器网络可以写成：

```text
N_VIN = {(#PWR1, VIN), (U1, VIN), (U1, EN), (C1, 1)}
N_VOUT = {(U1, VOUT), (#PWR_1V1, +1V8), (TP1, TP1)}
N_GND = {(C1, 2), (#PWR_C1, 1)}
```

这里的 `N_VIN`、`N_VOUT` 和 `N_GND` 不是芯片门级网表中的 gate net。

它们是 PCB 原理图中的电气网络，之后可作为 PCB layout 和 footprint wiring 的输入。

### 3.8 输出：四个层次

SchGen 的“输出”应分四层报告，而不是只说“生成了一个电路”。

1. **代码输出。** 一段 Python API 调用，可以审阅、重跑和定位错误。
2. **文件输出。** 由 API 写出的可编辑 KiCad schematic。
3. **电气结构输出。** 从 schematic 提取的 component-pin netlist。
4. **质量信号。** Python 执行状态、KiCad ERC、空间重叠、netlist 指标和专家评估。

### 3.9 一个端到端 walkthrough

以“VIN 输入、AP2112K 输出 +1V8、测试点和可跳线 LED”为例，端到端过程如下。

```text
自然语言请求
  │
  ▼
模型识别：稳压器、去耦电容、测试点、LED、220 Ohm、电源网
  │
  ▼
选择 U1/C1/D1/R1/JP1 与 power symbols
  │
  ▼
设定 U1 和 LED 支路两个局部 anchor
  │
  ▼
用相对偏移放置器件
  │
  ▼
用 VIN、+1V8、GND、VOUT 等 pin name 连接
  │
  ▼
执行并写出 KiCad schematic
  │
  ├── Python 异常？
  ├── ERC critical error？
  ├── 组件/导线重叠？
  └── netlist 是否与目标连接一致？
```

如果模型把 `U1.VOUT` 误接到 `GND`，代码可能仍然能够执行，但 ERC、netlist 或专家检查会暴露问题。

这正是论文不只报告字符串损失，而要报告多层验证指标的原因。

## 4. 方法与架构

本节要解决的问题是：SchGen 怎样把表示、数据、模型和验证串成一个可运行的系统。

### 4.1 整体 Pipeline

论文 Figure 1 给出的产品路径是“请求到 schematic，再到 netlist、PCB layout、Gerber 和 fabrication”。

```text
┌─────────────────────────────────────────────────────────────────┐

│ 例如：I want a 1.8V regulated supply from VIN ...              │

                               ▼
┌─────────────────────────────────────────────────────────────────┐

│ connect_pins / write_out_all_wires                              │
└──────────────────────────────┬──────────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────────┐
│ GPT-oss-20B + LoRA 生成 Code-L1 Python                         │
│ 选择器件、建立局部 anchor、相对放置、按 pin name 连线           │
└──────────────────────────────┬──────────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────────┐
│ Code-to-Schematic APIs 执行                                    │
│ 解析 symbol、查询 pin location、生成 wires                     │
└──────────────────────────────┬──────────────────────────────────┘

```

框图中的最后一行是论文 Figure 1 的工作流延伸，不是 SchGen 模型的训练输出。

模型直接控制的是第三个框到第五个框；netlist 之后的 PCB layout、Gerber 和 fabrication 只是下游交接目标。

### 4.2 为什么不能直接生成原始 KiCad 文本

原始 KiCad 文件带有版本、generator、paper、lib_symbols、pin display 和大量几何元数据。

这些字段对人类使用 KiCad 必要，但对“根据功能要求决定电路连接”的模型来说包含大量冗余。

模型还必须同时满足括号层级、版本格式、引用编号、坐标精度和线段端点一致性。

任何一个格式错误都可能让 EDA 工具无法解析整个文件。

因此论文把 raw KiCad file 作为 baseline，而不是默认的理想监督目标。

### 4.3 为什么图片也不是答案

图像可以让人看到符号和线路，却不能直接作为可编辑工程文件。

图像生成模型还容易扭曲符号形状、文字和线交点。

即使视觉上看起来像 LED 电路，也很难从像素可靠恢复“D1 的 A pin 是否与 +1V8 同网”。

SchGen 的目标不是生成漂亮的 raster image，而是生成可执行的、可检查的编辑操作。

### 4.4 模块一：语义 API 集合

#### 4.4.1 添加符号

`add_schematic_symbol` 是把器件类型和版面位置绑定起来的原语。

它需要知道 symbol library 和 symbol name，因为相同的功能名称可能对应不同 KiCad 库或封装变体。

它还写入 reference、value、rotation 和 mirror，保证输出 schematic 可继续编辑。

```python
add_schematic_symbol(
    symbol_lib="Device",
    symbol_name="LED",
    pos_x=center_x_2,
    pos_y=center_y_2,
    reference="D1",
    value="LED",
    rotation=90,
    mirror="None",
)
```

`reference` 是后续连接 API 找到对象的稳定标识。

`value` 保存器件值或型号，例如 `220`、`1uF` 和 `AP2112K-1.8`。

#### 4.4.2 放置标签

`add_label` 把网络名字和一个局部位置绑定。

标签不仅是页面上的文字，也可以让同名网络在 schematic 中自动电气相连。

这对 `VIN`、`+1V8`、`GND`、`D+` 和 `D-` 这类接口语义尤其重要。

标签可以有 label type 和 text orientation，因而同时包含可读性与接口方向信息。

#### 4.4.3 查询引脚位置

`get_pin_location(symbol_ref, pin_name)` 是语义到几何的桥。

LLM 不需要凭空猜 `U1` 的 `VOUT` 在页面的哪个绝对坐标。

API 根据符号库和变换后的符号姿态返回真实 pin location，后续 wire 生成器再使用它。

这把最容易出错的几何查找交给确定性程序，而不是交给 token 预测。

#### 4.4.4 按 pin name 连接

`connect_pins(symbol_a, pin_a, symbol_b, pin_b)` 表达的是电气意图。

例如：

```python
connect_pins("U1", "VOUT", "#PWR_1V1", "+1V8")
connect_pins("D1", "K", "R1", "1")
connect_pins("R1", "2", "JP1", "A")
```

模型只需选对对象和引脚名，底层接口负责查坐标并生成实际 wire。

这比 `add_new_wire([x1, y1], [x2, y2])` 更接近工程师说的“把两个端点接起来”。

#### 4.4.5 写出全部 wires

`write_out_all_wires()` 汇总当前连接并写出 KiCad schematic。

论文说明它还会执行 basic automatic routing；这里的 routing 是 schematic wire 的几何布置。

它不是 PCB copper router，也不会根据阻抗、层叠、差分对或回流路径优化。

### 4.5 模块二：Code-L1、Code-L2、Code-L3

论文用三个表示版本做控制变量实验。

| 表示 | 相对坐标 | pin-name connectivity | wire 方式 | 用来检验 |
|---|:---:|:---:|---|---|
| **Code-L1** | 有 | 有 | `connect_pins` | 完整语义化表示，SchGen 主方法 |
| **Code-L2** | 无 | 有 | `connect_pins` | 去掉相对坐标后的影响 |
| **Code-L3** | 无 | 无 | `add_new_wire` | 同时去掉相对坐标和引脚语义 |
| **KiCad File** | 原始绝对文件 | 隐含在 s-expression | 原始文本 | 测量工具格式直接生成难度 |

Code-L1 的两个设计选择分别解决两个不同错误源。

- 相对坐标缓解空间回归和数值漂移。
- pin name 连接缓解 wire 端点错位、交叉误判和漏接。

Code-L2 仍保留 pin name，因此其 netlist 指标只比 Code-L1 小幅下降。

Code-L3 改为绝对坐标 wire 后，空间和连线都变成模型必须精确生成的数值任务。

### 4.6 模块三：相对坐标与局部 anchor

论文观察到工程师通常先放置核心器件，再围绕核心器件布置外围器件。

因此每个局部 schematic 区块可以有一个中心 anchor。

```text
中心符号 U1
├── C1：相对 (-20, -5)
├── VIN power：相对 (-20, +5)
├── GND：相对 (-20, -24)
├── +1V8 power：相对 (+13, +5)
└── TP1：相对 (+16, +2)
```

这里的坐标单位沿用 KiCad 页面坐标；模型主要生成偏移关系，而不是整张画布的绝对值。

对于 label，anchor 通常是它附着的 pin；对于 symbol，anchor 通常是中心 symbol。

这种局部坐标系也允许一个大 schematic 被拆成多个功能区块。

### 4.7 模块四：引脚名驱动的连线

PCB schematic 的功能关系经常直接写在 pin name 中。

`VCC`、`VDDIO`、`VIN`、`VOUT`、`TXD`、`D+` 和 `GND` 不只是随机 token，它们提示了电气角色。

SchGen 利用这一点把几何 wire 预测改成语义匹配。

```text
语义层：U1.VOUT 连接到 +1V8
              │
              ▼
解析层：查询 U1 的 VOUT 与 power symbol 的 +1V8 位置
              │
              ▼
几何层：生成若干合法 wire segment
```

如果某个 pin 没有可读名称，论文允许使用 pin ID，例如电容的 `1`、`2`。

因此表示仍然覆盖无 pin name 的普通器件，但这类连接的语义监督更弱。

### 4.8 模块五：数据构造流水线

论文 Figure 3 的数据构造可画成如下流程。


agentic sketch 的意义是把“只存在于网页图片中的设计”变成可执行草图。

但模型对复杂 wire 交叉和是否相连仍可能出错，所以 human alignment 是数据质量环节，不是可有可无的装饰。

论文报告符号草图通常在 5 轮迭代内可以准确复现；每个设计平均验证与潜在修正少于 20 秒，而从零手工绘制可能超过 5 分钟。

### 4.9 模块六：Schematic-to-Code Converter

转换器首先解析 KiCad 的 s-expression 文件。

论文将 pins 和 wires 处理为无向图中的 vertices 与 edges。

通过图遍历识别互相连通的 pin pair，并为每个 symbol 生成相对位置、label 附着和 pin-name connection 操作。

最后执行 `write_out_all_wires`，检查生成代码是否能够复现原始 schematic。

```text
KiCad s-expression
        │ parse
        ▼
无向图：pins + wires
        │ graph traversal
        ▼
connected pin pairs
        │ abstraction
        ▼
Code-L1 Python
```

这一步的价值在于把人工绘图的最终状态反推成模型可学习的动作序列。

它也为 L2、L3 ablation 提供同一设计的不同表示，避免数据内容本身变化造成混淆。

### 4.10 模块七：请求合成与 CoT

外部多模态 LLM 根据已导出的 schematic 图像和 netlist，从用户视角生成请求。

论文让模型参考人工用户撰写的例子，以减少合成请求与真实请求之间的风格差异。

请求分为 concise 和 detailed 两种风格。

之后用 GPT-oss-120B 和 GPT-oss-20B 生成从请求到代码的 CoT reasoning。

这样，1390 个独特设计不是只复制四次，而是得到不同请求风格和不同 reasoning teacher 的组合。

论文实验描述的结果是 2105 个 KiCad schematics、1390 个 unique designs 和 8420 个 samples。

### 4.11 模块八：GPT-oss-20B 的监督微调

SchGen 使用 GPT-oss-20B 作为基础模型。

训练目标是从 user request 和上下文生成 Code-L1 Python，并保留有助于规划的 CoT。

论文采用 SFT 与 LoRA，而不是从头训练一个新的 schematic parser。

训练只对 assistant 输出计算 loss，输入请求和上下文不作为目标 token。

这种设定让模型学习“如何从请求写编辑操作”，而不是学习复制提示模板。

### 4.12 模块九：推理与工程验证

推理阶段接收新请求，生成 Python 代码，再由工程 API 运行。

一个可靠的执行器至少要检查下面四类问题。

1. Python 语法、参数和引用是否有效。
2. symbol library、symbol name、pin name 是否存在。
3. KiCad ERC 是否报告 short circuit、net conflict 或 illegal connection。
4. 生成结果的 netlist 和版面是否值得人工审阅。

模型没有在论文中被描述为自动修复所有错误的闭环推理器；agentic iterative feedback 主要用于数据构造。

因此训练时的草图修正闭环，不应被误写成部署时保证零错误的 runtime verifier。

### 4.14 失败模式如何沿 pipeline 传播

下面把一个常见错误沿路径追踪。

## 5. 关键公式

本节要解决的问题是：把论文用来定义表示复杂度、有效性、网络准确率和训练行为的数学量写清楚，并标注哪些是论文直接给出的、哪些是为解释算法而形式化的。

论文正文没有使用编号的 `align` 公式；下面所有独立公式均单独占行。

### 5.1 有效电路率

论文将 Valid Circuits 定义为同时通过 Python 执行和 KiCad ERC sanity check 的生成电路比例。

$$
\mathrm{ValidRate} = \frac{n_{\mathrm{exec\_and\_ERC}}}{n_{\mathrm{generated}}} \times 100\%
$$

- $n_{\mathrm{exec\_and\_ERC}}$：代码执行成功且 ERC 无 critical error 的样本数。
- $n_{\mathrm{generated}}$：被评估的生成样本总数。
- $\mathrm{ValidRate}$：表格中的 Valid Circuits Pass ratio。

**工程直觉：** 这是“文件能不能被工具接受”的门槛，而不是“电路一定符合规格”的证明。

**为什么这样设计：** 如果 Python 都不能运行，后续 schematic、netlist 和专家评估没有意义；把 ERC critical error 加入门槛可以过滤一部分明显短路和非法连接。

### 5.2 Minimum Description Length

论文用 MDL 近似表示的可压缩性，定义为压缩后字节数相对于原始字节数的比率乘以 8。

$$
\mathrm{MDL} = 8 \cdot \frac{\mathrm{compressed\_bytes}}{\mathrm{raw\_bytes}}
$$

- $\mathrm{compressed\_bytes}$：无损压缩后的字节数。
- $\mathrm{raw\_bytes}$：原始表示的字节数。
- $\mathrm{MDL}$：以 bits-per-byte 近似的描述长度；越低表示越结构化、越容易压缩。

**工程直觉：** 重复的 API 模式、局部偏移和规范化 pin name 会形成可压缩结构；杂乱的绝对坐标和元数据会增加描述负担。

**为什么这样设计：** MDL 不直接等于生成准确率，但可以在训练前预测一种表示是否给 LLM 提供了较低的序列复杂度。

### 5.3 Lempel-Ziv 归一化复杂度

论文采用增量解析得到的 phrase 数量评估序列的内在复杂度。

$$
\mathrm{LZ}_{\mathrm{norm}} = c(n) \frac{\log n}{n}
$$

- $c(n)$：长度为 $n$ 的序列在增量解析中的 phrase 数量。
- $n$：表示序列长度。
- $\log n$：用于长度归一化的对数项。
- $\mathrm{LZ}_{\mathrm{norm}}$：归一化 Lempel-Ziv 复杂度；越低表示序列规律越多。

**工程直觉：** 如果每个 symbol 都重复完整绝对坐标和冗余字段，phrase 会快速增加；相对坐标和统一 API 让相似功能区块共享模式。

**为什么这样设计：** 它从序列本身衡量复杂度，不依赖特定神经网络，因此适合作为 Code-L1/L2/L3 的表示级比较。

### 5.4 空间重叠的加权归一化

Spatial Violation 统计 symbols、labels 和 wires 的 bounding box 交叠数。论文为减轻不同有效通过率造成的统计偏差，使用如下归一化。

$$
\bar{n}_{\mathrm{weighted}} = \frac{\bar{n}_{\mathrm{original}}}{\mathrm{pass\ ratio}}
$$

- $\bar{n}_{\mathrm{original}}$：原始生成样本上的平均 overlap 数。
- $\mathrm{pass\ ratio}$：通过有效性检查的样本比例。
- $\bar{n}_{\mathrm{weighted}}$：表格报告的加权空间违例数。

**工程直觉：** 只有少量样本能生成出来的模型不能靠“未生成样本不计重叠”获得虚假的低违例率。

**为什么这样设计：** 该指标仍只是可读性代理；它没有判断线宽、板框、封装碰撞或真实铜线间距。

### 5.5 Netlist 的集合表示

论文把每个 pin 视为节点，把共享同一电气网络的节点组织成集合。

$$
G = \{N_1, N_2, \ldots, N_m\}, \qquad N_j \subseteq V
$$

- $G$：一个 schematic 的 netlist。
- $N_j$：第 $j$ 个电气网络。
- $V$：所有 component-pin 节点的全集。
- $m$：网络数量。

节点可以写成下面的二元组。

$$
 v_i = (\mathrm{symbol\_reference}_i, \mathrm{pin\_name}_i)
$$

- $v_i$：一个 component-pin 节点。
- $\mathrm{symbol\_reference}_i$：器件的 reference，例如 `U1` 或 `R1`。
- $\mathrm{pin\_name}_i$：引脚名字或 pin ID，例如 `VOUT` 或 `2`。

**工程直觉：** 原理图最重要的逻辑信息是哪些 pin 处在同一个 net，而不是某一条线段的起点坐标。

**为什么这样设计：** 集合表示对 wire 的折线路径和中间拐点不敏感，能直接评估连接是否正确。

### 5.6 Jaccard、Precision 与 Recall

对生成 netlist 和 ground-truth netlist 做集合级比较时，可以把网络集合展平为 component-pin 对或规范化 net 对。论文报告这三类指标；以下是与该定义一致的标准形式化。

$$
\mathrm{Jaccard}(G_{\mathrm{gen}}, G_{\mathrm{gt}}) = \frac{|G_{\mathrm{gen}} \cap G_{\mathrm{gt}}|}{|G_{\mathrm{gen}} \cup G_{\mathrm{gt}}|}
$$

- $G_{\mathrm{gen}}$：生成 netlist。
- $G_{\mathrm{gt}}$：ground-truth netlist。
- $|\cdot|$：集合基数。
- $\mathrm{Jaccard}$：生成与真实网络交并比。

$$
\mathrm{Precision} = \frac{|G_{\mathrm{gen}} \cap G_{\mathrm{gt}}|}{|G_{\mathrm{gen}}|}
$$

- $\mathrm{Precision}$：生成网络中正确网络的比例。
- $|G_{\mathrm{gen}}|$：生成网络集合的大小。
- 交集项的含义同上。

$$
\mathrm{Recall} = \frac{|G_{\mathrm{gen}} \cap G_{\mathrm{gt}}|}{|G_{\mathrm{gt}}|}
$$

- $\mathrm{Recall}$：真实网络中被生成结果恢复的比例。
- $|G_{\mathrm{gt}}|$：真实网络集合的大小。
- 交集项的含义同上。

**工程直觉：** Precision 低说明模型凭空连了不该连的 pin；Recall 低说明漏接了真实连接；Jaccard 同时惩罚两类错误。

**口径说明：** 论文文字给出了 netlist 为网络集合及三项指标，但没有在 TXT 中给出更细的规范化展平算法。上面是解释指标的标准形式化，不应被误写成论文新增的编号公式。

### 5.7 相对坐标的形式化

论文以 anchor 为参考表达符号位置。论文没有给出编号公式，下面是对 Code-L1 行为的形式化。

$$
\mathbf{p}_i = \mathbf{a}_k + \Delta \mathbf{p}_i
$$

- $\mathbf{p}_i$：第 $i$ 个 symbol 或 label 的页面位置。
- $\mathbf{a}_k$：第 $k$ 个局部 anchor 的位置。
- $\Delta \mathbf{p}_i$：相对于 anchor 的局部偏移向量。

**工程直觉：** 把一组电源去耦器件整体平移时，局部关系不变，模型无需重新学习所有绝对坐标。

**为什么这样设计：** L2 的绝对坐标会把页面大小、原始设计排版和数值精度混进目标序列；L1 只保留与功能区块相关的相对关系。

### 5.8 Pin-level 连接的形式化

论文没有给出编号公式，下面把 `connect_pins` 的语义写成一条边。

$$
 e = \bigl((r_a, p_a), (r_b, p_b)\bigr)
$$

- $e$：一条语义连接边。
- $r_a, r_b$：两个 symbol reference。
- $p_a, p_b$：对应的 pin name 或 pin ID。

一组通过 wire 或同名 label 连通的边可以归并为同一个网络。

$$
N(e_1, e_2, \ldots, e_q) = \mathrm{ConnectedComponent}(\{e_1, e_2, \ldots, e_q\})
$$

- $N$：由连接边归并出的 net。
- $e_1, \ldots, e_q$：属于同一连通分量的连接边。
- $\mathrm{ConnectedComponent}$：按图连通性归并的操作。
- $q$：该网络包含的边数。

**工程直觉：** LLM 输出的是“连谁的哪个脚”；几何层才负责找脚的位置和画线。

**边界：** pin name 只有在 symbol library 定义稳定时才可靠；未命名 pin 仍需靠数字 ID 或人工检查。

### 5.9 代码到 schematic 的编译关系

下面是对执行过程的概念化表达，论文没有给出该编号公式。

$$
S = \mathcal{C}(P; L, A)
$$

- $P$：模型生成的 Python API 程序。
- $L$：KiCad symbol library 和 pin 定义。
- $A$：SchGen code-to-schematic API 实现。
- $\mathcal{C}$：执行、解析并写文件的编译过程。
- $S$：生成的 KiCad schematic。

如果 $P$ 中引用了不存在的 symbol 或 pin，$\mathcal{C}$ 可能抛出异常；如果语法合法但连接逻辑错误，错误可能延后到 ERC 或 netlist 检查。

### 5.10 复杂度定义

附录 6.3 将一个 schematic 的 complexity 定义为 symbols 和 labels 数量之和。

$$
C_{\mathrm{sch}} = n_{\mathrm{symbols}} + n_{\mathrm{labels}}
$$

- $C_{\mathrm{sch}}$：schematic complexity。
- $n_{\mathrm{symbols}}$：符号数量。
- $n_{\mathrm{labels}}$：标签数量。

**工程直觉：** 这是一个简单但可复现的规模代理；论文 Figure 5 用它绘制数据集复杂度分布。

**局限：** 它不计 wire 数、pin 数、层级深度、器件库稀有度或网络拓扑难度，因此两个相同 complexity 的设计可能有完全不同的生成难度。

### 5.11 监督微调目标的形式化

论文说明使用 assistant-only SFT，但没有在 TXT 中给出损失公式。下面是该训练行为的标准形式化。

$$
\mathcal{L}_{\mathrm{SFT}} = -\sum_{t \in \mathcal{T}_{\mathrm{assistant}}} \log p_{\theta}(y_t \mid x, y_{<t})
$$

- $\mathcal{L}_{\mathrm{SFT}}$：监督微调损失。
- $\mathcal{T}_{\mathrm{assistant}}$：只包含 assistant 目标输出 token 的位置集合。
- $y_t$：第 $t$ 个目标 token。
- $x$：用户请求、API 上下文和示例。
- $\theta$：模型参数。

**工程直觉：** 模型被奖励生成 Python/CoT，而不是重复 user prompt 或系统说明。

### 5.12 LoRA 参数更新的形式化

论文报告使用 LoRA，但没有在 TXT 中展开低秩更新公式。为说明 rank 和 scaling factor 的含义，可写成如下标准形式。

$$
W' = W + \frac{\alpha}{r} B A
$$

- $W$：冻结的基础模型权重。
- $W'$：训练后实际使用的权重。
- $A$、$B$：低秩可训练矩阵。
- $r$：LoRA rank，论文配置为 8。
- $\alpha$：scaling factor，论文配置为 16。

**工程直觉：** 只训练小矩阵可以降低显存和训练成本，但适配能力受 rank 和目标层选择限制。

### 6.5 评价协议

论文从四个角度评估生成结果。

#### 6.5.1 Valid Circuits

样本必须同时满足两个条件。

- Python code 成功执行，不出现错误参数、未知 reference、未知 pin 或坐标越界等异常。
- KiCad ERC 没有 critical error，包括 short circuit、net conflict 和 illegal connection。

因此一个样本可以“语法正确但 valid 失败”，也可以“执行成功但功能仍不符合请求”。

#### 6.5.2 Spatial Violation

为 symbols、labels 和 wires 分配 bounding box。

任意两个对象相交就计为 overlap，再按照通过率做加权归一化。

它是 schematic readable layout 的代理指标，数值越低越好。

#### 6.5.3 Netlist Accuracy

将节点定义为 `(symbol, pin)`，把共享一个 net 的节点组成集合。

对生成集合与 ground truth 计算 Jaccard、Precision 和 Recall。

这是论文认为最接近下游 PCB layout/wiring 输入正确性的结构指标。

#### 6.5.4 Expert Verification

从测试集中随机抽取 100 个设计，由两位专家按照统一 rubric 检查。

报告 Symbol Error 和 Connection Error 的平均值，以及 Functional Correctness 比例。

论文脚注说明两位专家交叉验证的平均 correctness ratio 差异低于 3%。

### 6.6 为什么不使用 SPICE

论文明确没有使用 SPICE simulation 作为整体评估。

原因是 PCB schematic 是系统级 mixed-domain 设计，包含连接器、数字 IC、被动器件和其他没有可用 SPICE model 的组件。

SPICE 更适合小型模拟子电路，而不是论文覆盖的完整 PCB schematic。

因此“Functional Correctness”来自专家依据设计意图检查，不是统一的 transient、AC 或 power integrity 仿真通过。

### 6.10 结果的因果拆解

从 Table 2 和 Table 3 可以把收益拆成四个层次。

1. **从 raw KiCad 到 Code-L3。** 去掉工具元数据，模型先获得可执行 API 的结构，但 wire 仍然难。
2. **从 Code-L3 到 Code-L2。** 恢复 pin-name connectivity，连接准确率显著改善。
3. **从 Code-L2 到 Code-L1。** 恢复相对坐标，布局和整体有效率进一步改善。
4. **从 Code-L1 without CoT 到 Code-L1。** 加入 reasoning trace 后，复杂器件选择和连接规划的功能正确率大幅提高。

这四步说明“表示”与“推理数据”是相乘关系，而不是互相替代。

仅有 relative coordinates 不能修复错误的 pin selection；仅有 pin names 也不能解决大量绝对几何数字。

### 6.11 实验中的公平性控制

论文对 frontier model 做单次运行，并提供统一 prompts、表示说明、示例代码和相同 Python APIs。

这样比较主要回答“在相同工具接口下，专门微调是否更好”，而不是比较不同模型是否知道 KiCad 文件格式。

同一模型在 L1、L2、L3 和 raw KiCad 下的差异，也把表示因素从模型规模因素中分离出来。

不过单次运行仍然可能受随机采样和 prompt 顺序影响，这属于第 10 节的复现注意事项。

### 6.12 数据构造的时间收益

agentic sketch 的符号复现通常最多迭代 5 轮。

每个设计平均验证和潜在 alignment fix 少于 20 秒。

论文对比从零手工 plot 同一 schematic 可能超过 5 分钟。

这个数字说明数据收集 pipeline 的价值，但不等于端到端模型推理耗时，也不等于人工完全退出流程。

## 7. 创新点

本节要解决的问题是：哪些机制是论文真正的新贡献，哪些只是常规的 LLM 微调组件。

### 7.1 创新点一：定义自然语言到 PCB schematic 的任务

过去的数字 IC 工作多从 Verilog/VHDL 或布尔逻辑开始，模拟 IC 工作多从电路拓扑或性能目标开始。

SchGen 把输入前移到用户的自然语言功能请求，并把输出定义为可编辑的 PCB schematic。

以前的图像到 netlist 或 netlist 到 schematic 工作只覆盖转换链的一段；SchGen 直接研究 request-to-schematic。

这使“器件选择、连接、布局可读性和文件可执行性”同时成为一个生成任务。

### 7.2 创新点二：语义扎根的 Code-L1 表示

以前直接生成 raw KiCad text，模型必须预测大量 tool-specific metadata、版本字段和绝对坐标。

SchGen 改成生成与专家绘图动作对应的 API 序列，因为 API 是更短、更可解释、更容易执行检查的中间层。

以前图片表示不可编辑且无法稳定恢复 pin connectivity；SchGen 改成 pin-name-based `connect_pins`，因为功能连接本来就由 pin 语义决定。

这是论文最核心的 representation contribution。

### 7.3 创新点三：局部相对布局

以前每个器件都直接使用画布绝对坐标，模型需要在一个全局坐标系中同时安排数十个对象。

SchGen 先选中心符号，再用相对偏移放置相关器件，因为工程师实际画 schematic 也会围绕功能中心组织布局。

这不仅降低 token 的数值复杂度，还让一个功能区块整体移动时保持内部关系。

Table 1 的 MDL、LZ Norm 和 validation loss 同时支持这一设计。

### 7.4 创新点四：agent-human 协作的数据扩展

以前公开硬件资源常只有图像，无法直接得到可编辑、可执行监督对。

SchGen 用多模态 LLM 进行 agentic sketch，用运行错误反馈迭代，再由人修正复杂连接，最后反向转换成代码。

这种流程把人类工程判断放在高风险的 wire 对齐位置，把可重复的符号布置和代码转换自动化。

论文报告它把 1390 种设计组织成 8420 个请求、代码和 CoT 样本。

### 7.5 创新点五：双请求风格和 CoT 蒸馏

以前只用一句固定模板训练，模型可能只学会模板词汇，不会适应不同用户知识水平。

SchGen 同时使用 concise 与 detailed request，并让 GPT-oss-120B 和 GPT-oss-20B 生成 reasoning trace。

Code-L1 without CoT 的 functional correctness 只有 14.0，而完整 Code-L1 为 60.5，说明中间规划对复杂 schematic 有实质作用。

这里的 CoT 是训练数据增强策略，不应理解为论文提出了新的解码搜索算法。

### 7.6 创新点六：多层次评估而不是单一字符串指标

以前只看文件是否解析或文本相似度，无法区分布局重叠、漏接和功能错误。

SchGen 同时报告 valid circuits、spatial violation、netlist Jaccard/Precision/Recall、symbol/connection error 和专家 functional correctness。

这种评估使 representation 的收益可以在“工具可接受”“拓扑连接正确”和“工程师认为能工作”三个层次被观察。

### 7.7 创新点七：证明专门化 20B 模型的价值

SchGen 不是靠更大参数量取胜。

在相同 API 和表示提示下，LoRA 微调的 GPT-oss-20B 超过 GPT-5.2、GPT-o4mini 和 Grok-4 的多数指标。

这支持一个更一般的 AI4EDA 结论：领域表示和可执行约束可以比通用模型规模更直接地解决硬件生成的结构错误。

但 OOD 表中的 valid rate 也提醒我们，专门化优势并非在每个指标、每个新项目上都绝对成立。

## 9. 与芯片流程的关系

本节要解决的问题是：SchGen 在完整电子设计链中接手谁、交给谁，以及为什么“PCB schematic 生成”与“芯片 RTL-to-GDSII”不能混为一谈。

### 9.1 在 PCB 工作流中的位置

论文 Figure 1 的直接链路可以写成：

```text
用户请求
   │
   ▼
SchGen Code-L1 Python
   │
   ▼
KiCad schematic design
   │
   ▼
Netlist file
   │
   ▼
PCB layout
   │
   ▼
Gerber file
   │
   ▼
PCB fabrication
```

SchGen 接手的是用户对板级功能的描述。

它交给下游的是可编辑 schematic 和 component-pin netlist，而不是已完成的 board layout。

netlist 会指导后续 footprint placement、铜线 routing 和制造文件生成，但这些步骤不在论文模型内。

### 9.2 和 17 阶段的交接表

| 芯片流程阶段 | SchGen 的最近对应物 | 是否真正交付该阶段产物 |
|---|---|:---:|
| ① RTL 设计 | 选择 PCB 元件、组织功能模块、定义网络 | 否，只有抽象类比 |
| ② RTL 仿真 | Python 执行与 ERC sanity check | 否，验证对象不同 |
| ③ 逻辑综合 | API code 编译为 schematic/netlist | 否，非 gate synthesis |
| ④ 门级仿真 | 无 | 否 |
| ⑤ STA | 无 | 否 |
| ⑥ 形式验证 | 无 | 否 |
| ⑦ Floorplan | schematic 版面中心/相对布局 | 否，非 board floorplan |
| ⑧ Placement | 下游 PCB footprint placement | 论文未做 |
| ⑨ CTS | 无 | 否 |
| ⑩ Routing | schematic wire generation | 否，非铜线 routing |
| ⑪ 后仿真 | 无 SPICE/SPEF | 否 |
| ⑫ DRC/LVS | ERC 的局部前置检查 | 否 |
| ⑬ Signoff | 专家检查和指标报告 | 否，非制造签核 |
| ⑭ Tape-out | 无 GDSII | 否 |
| ⑮ Fabrication | 无实物制造 | 否 |
| ⑯ Package/test | 无板级装配测试 | 否 |
| ⑰ Chip | 无芯片交付 | 否 |

这张表的要点是“有相似动作”不等于“完成同一 EDA stage”。

尤其是 `write_out_all_wires` 只将 schematic 中的语义连接落实为页面线段，不会产生满足 PCB 生产规则的铜箔。

### 9.3 PCB schematic 与 chip RTL-to-GDSII 的对象差异

两条流程的输入、表示、约束和终点分别不同。

| 维度 | SchGen / PCB | 数字芯片 RTL-to-GDSII |
|---|---|---|
| 设计对象 | MCU、稳压器、被动器件、连接器、天线等异构组件 | RTL 中的寄存器、组合逻辑、存储器和 IP |
| 主要关系 | component pin 的电气连通 | 信号、时钟、寄存器传输和逻辑等价 |
| 早期文件 | KiCad `.kicad_sch`、netlist | Verilog/VHDL、约束和库 |
| 中间转换 | schematic 到 PCB netlist | RTL 到门级 netlist |
| 空间语义 | schematic 可读性、后续 footprint 连接 | 芯片 die、standard cell、clock tree 和 metal layers |
| 关键约束 | ERC、器件值、接口和人工电气意图 | SDC、timing、PPA、工艺规则和 signoff |
| 仿真 | 论文未做整体 SPICE | RTL、门级、后仿真和 STA/formal |
| 最终交付 | Gerber/钻孔/装配等 PCB 制造文件 | GDSII、tape-out、晶圆和封装芯片 |

因此，SchGen 的“schematic generation”不能被宣传成“生成芯片”。

### 9.4 明确的 gap：netlist 不是 gate-level netlist

PCB netlist 可能包含：

```text
U1.VOUT -- +1V8 -- TP1.TP1
C1.2    -- GND
R1.2    -- JP1.A
```

它描述哪些器件端子在同一个电气网络。

芯片 gate-level netlist 则会包含标准单元实例、逻辑门连接、触发器时钟和复位等结构。

两者都叫 netlist，但后者还要经过 SDF、STA、形式等价、placement、CTS、routing 和 physical signoff。

把 SchGen 的输出命名为“网表”并不意味着它已经完成芯片逻辑综合。

### 9.5 明确的 gap：ERC 不是形式验证或 DRC

ERC 可以指出某些明显的短路、网络冲突和非法连接。

它不证明每个用户功能在所有输入、负载和电源条件下成立。

它也不检查 PCB 真实铜线的线宽、间距、阻抗、热设计、EMI 或制造能力。

芯片流程中的形式验证证明逻辑等价，DRC 检查版图几何可制造，LVS 检查版图与原理图一致；三者都超出 SchGen 的实验。

### 9.6 明确的 gap：原理图坐标不是物理布局坐标

Code-L1 的 `(center_x, center_y) + offset` 只规定符号在 schematic 页面上的阅读位置。

真实 PCB placement 要把每个 symbol 映射到 footprint，并考虑板框、机械孔、连接器方向、散热、天线净空和装配工艺。

同一份 schematic 可以有多个合法 PCB layout。

因此 SchGen 的布局质量指标 Spatial Violation 只衡量页面重叠，不衡量最终板子的长度、拥塞或电磁性能。

### 9.7 明确的 gap：没有芯片 PPA 目标

论文的核心指标是 valid rate、spatial violation、netlist accuracy 和专家 functional correctness。

它没有优化或报告芯片常说的 Power、Performance、Area。

即使某个 PCB schematic 连接正确，也不能从论文结果推断其板级功耗、热、信号完整性或成本最优。

### 9.8 SchGen 对完整电子链的真实价值

SchGen 的价值仍然很清楚：它自动化了“从功能意图到第一份可编辑原理图”的高人工成本步骤。

这可以减少工程师从网页参考图或自然语言需求开始画符号、查 pin 和逐条布线的时间。

如果下游工具链继续接上 netlist import、footprint 检查、PCB layout、DRC、SI/PI 分析和原型测试，SchGen 可以成为前端 proposal generator。

但它应被部署为“候选方案生成器 + 工程师审阅”，而不是 autonomous manufacturing system。

### 9.9 与数字芯片论文的互补关系

对于数字 IC，LLM 可能生成 Verilog，综合器再生成 gate netlist。

对于 SchGen，LLM 生成的是 Python schematic operations，KiCad 再生成 component-level schematic。

前者的质量通常需要 RTL simulation、formal、PPA 和 timing；后者至少需要 ERC、netlist、专家审阅以及最终 PCB 验证。

两者可以共享“语义化中间表示”和“可执行验证”的思想，但不能共享同一套成功定义。

## 10. 讨论与局限

本节要解决的问题是：论文结果在哪些条件下成立，代码复现会遇到什么门槛，以及从工程角度还缺少哪些验证。

### 10.1 论文自述的局限

#### 局限一：设计范围偏向结构化 SparkFun 设计

论文结论部分明确说 SchGen 当前聚焦于 SparkFun designs 的 structured schematics。

这类设计适合用有限 API 表达，器件规模也相对可控。

它不代表已经覆盖高速 SerDes、复杂 RF、精密电源、柔性板、复杂多板系统或工业安全电路。

#### 局限二：尚未建模 advanced PCB constraints

论文没有把板框、层叠、阻抗、差分对、热、EMI、机械禁布区和制造约束纳入 Code-L1 目标。

当前 relative coordinate 只提高 schematic 的可读布局。

因此一个生成结果即便 Spatial Violation 很低，也可能在 PCB layout 阶段无法布通或无法满足电气规格。

#### 局限三：大而复杂的 PCB 难以扩展

论文指出扩展到 larger and more complex PCBs 仍然受数据量和 LLM 能力限制。

符号数量、标签数量、连接边数量增长后，单个程序的 token length 和组合搜索空间都会增长。

Table 5 的 13312 max token length 也说明长 schematic 需要受限上下文管理。

#### 局限四：需要人工保证 robustness 和 safety

论文结论明确提出 human involvement 仍然需要，以确保生成 schematic 的稳健性和安全性。

这不是简单的用户体验建议，而是因为 ERC 不能覆盖所有功能和物理失效模式。

#### 局限五：没有整体 SPICE 验证

由于设计包含混合域器件和缺失的 SPICE models，论文不采用全板 SPICE simulation。

这使 functional correctness 的主要证据来自专家，而不是可重复的动态电气实验。

### 10.2 代码与复现层面的问题

#### 10.2.1 本地归档没有代码 checkout

当前 SchGen 目录只归档了论文 PDF 和 TXT；代码需要从 [microsoft/SchGen](https://github.com/microsoft/SchGen) 另行获取。

因此本文没有声称已经在本地运行生成、训练或 ERC。

GitHub 页面确认了仓库 URL，并提供了模型和数据集入口；具体脚本和默认参数应以运行时仓库版本为准。

#### 10.2.2 环境依赖跨工具链

README 要求 Python 3.10、KiCad 8.0.9、`PROJECT_PATH` 和配置中的 OpenRouter API key。

训练还需要 PyTorch、Transformers、PEFT/LoRA 相关包，并可能使用 flash-attn。

KiCad symbol library 版本变化会影响 symbol name、pin name 和 pin location，从而影响代码能否执行。

#### 10.2.3 论文与 README 的 epoch 口径

<!-- 修正：论文 TXT 的 Table 5 报告 number of epochs = 3；GitHub README 的当前训练说明可能写成 2 epochs。本文对论文结果和主实验配置以 TXT 的 3 epochs 为准，复现时应记录实际 checkout 版本。 -->

这种差异会影响严格复现实验，但不改变论文 Table 2 至 Table 4 的报告数字。

复现报告应同时注明论文版本、代码 commit、实际 epoch 和数据过滤规则。

#### 10.2.4 外部模型调用影响数据可重复性

agentic sketch、请求合成和 CoT 蒸馏都使用外部多模态或大模型调用。

不同模型版本、system prompt、温度和 API 返回风格可能生成不同草图、请求和 reasoning trace。

若只下载最终 8420 条数据而不保存生成 prompt 和模型版本，就无法完全重建数据构造过程。

#### 10.2.5 人工 alignment 不是自动脚本

复杂 wire 交叉可能需要工程师判断“相交但不连接”还是“相交且连接”。

这一步的质量和时间取决于人员经验，论文报告的少于 20 秒是平均值，不是每个设计的上界。

如果复现者跳过 alignment，训练集的连接标签噪声可能显著改变结果。

#### 10.2.6 未固定代码 commit

论文 TXT 只给出仓库 URL，并未在正文中固定 Git commit。

因此应把下载日期、commit hash、KiCad 版本和 symbol library 版本作为复现元数据。

没有这些信息时，不能把当前仓库运行结果与论文数字做一一归因。

### 10.3 本资料包的批判性分析

#### 10.3.1 Valid Circuit 是必要条件，不是充分条件

Python 成功执行只证明 API 参数和文件生成链没有立即崩溃。

ERC 无 critical error 只过滤工具能识别的规则冲突。

例如稳压器输入输出接反、LED 极性不符用户意图、去耦电容值不合适，可能仍然通过基础执行和部分 ERC。

所以 82.00% 不能直接翻译成“82% 的板子可以生产”。

#### 10.3.2 专家评估规模有限

专家验证随机抽取 100 个测试设计，由两位专家评估。

这个设计比纯自动指标强，但仍然可能受任务类型、专家经验和 rubric 解释影响。

论文报告两位专家平均 correctness ratio 差异低于 3%，说明一致性不错，却没有消除样本数量和覆盖范围的限制。

#### 10.3.3 随机测试划分可能保留设计家族相似性

论文将 500 个样本随机选为 held-out test，而样本由 1390 个 unique designs 扩增得到。

如果同一设计的不同请求风格或 CoT 变体跨越训练和测试，随机样本划分可能比按设计族划分容易。

OOD 的 20 个 GitHub 项目测试缓解了这个问题，但仍只覆盖 988 个样本和有限项目类型。

更严格的评估应按元件家族、功能类别和设计来源做 group split。

#### 10.3.4 表示对 pin name 可用性有隐含假设

Code-L1 假设 symbol library 的 pin name 稳定、语义充分且模型能从请求映射到它。

普通电阻、电容常只有数字 pin ID，连接语义弱于 `VOUT`、`VIN` 或 `GND`。

跨 KiCad 库、厂商库或同一器件不同 symbol 变体时，pin 名称可能变化。

因此表示优势依赖库规范化和上下文扫描，而不是只依赖模型本身。

#### 10.3.5 相对坐标仍然需要 anchor 策略

论文观察到中心符号自然存在，但没有在 TXT 中给出适用于所有拓扑的 anchor 自动选择算法。

对于多个同等重要的模块、环形反馈、长连接器链或层级 schematic，一个中心 anchor 可能不够。

anchor 选择错误会把局部偏移变成很大的数值或破坏阅读顺序。

后续工作需要显式的模块分解、层级调用或 layout constraint solver。

#### 10.3.6 netlist 指标无法覆盖电气规格

Jaccard、Precision 和 Recall 只看连接集合。

它们不看电压容差、电流额定值、功耗、极性、时序、阻抗、热或元器件可采购性。

两个 netlist 可以完全一致，但一个使用额定电压错误的电容或不匹配的稳压器。

因此应把 value、footprint、datasheet constraint 和 power budget 纳入后续评估。

#### 10.3.7 单次 frontier 比较仍有随机性

Table 3 的 frontier models 是 single-run setting。

同一模型不同温度、采样策略和上下文顺序可能产生不同 valid rate。

统一 APIs 和 prompts 提高了公平性，但不等于给出了均值、方差或统计显著性。

如果要把 20B 胜过大模型作为强结论，应报告多次采样置信区间和相同解码预算。

#### 10.3.8 数据许可与衍生内容需要审计

论文说明 SparkFun 参考资源使用 CC BY-SA 4.0；GitHub README 还标示代码为 MIT。

训练数据中的图像、schematic、生成请求和 CoT 是不同类型的衍生内容，发布和商业使用时应分别核对归属与 share-alike 要求。

这不仅是法律问题，也关系到企业是否能将生成的 schematic 放入闭源产品。

#### 10.3.9 安全部署需要人工 gate

错误的电源连接、反向极性、短路或错误连接器可能损坏昂贵硬件甚至造成安全事故。

部署时至少应要求自动 ERC、netlist diff、关键电源规则、datasheet 检查和人工 approval 全部通过。

模型输出应被视为候选设计，而不是制造指令。

### 10.4 哪些结论可以相信，哪些不能外推

| 可以由论文支持的结论 | 不能直接外推的结论 |
|---|---|
| Code-L1 比 raw KiCad 和 L2/L3 更易学习 | 任意 EDA 文件都适合改成同样 API |
| GPT-oss-20B 微调后在论文 benchmark 上表现强 | 20B 在所有大型工业 PCB 上胜过更大模型 |
| pin-name connectivity 对 netlist 很重要 | 所有器件都有稳定可用的 pin name |
| agent-human pipeline 能提高数据规模 | 可完全取消工程师 alignment |
| OOD netlist accuracy 接近 GPT-5.2 | OOD 的所有质量指标都达到生产级 |
| 可生成可编辑 KiCad schematic | 已完成 PCB layout、制造和安全验证 |

### 11.5 复现检查点

建议不要一开始就重跑 8420 样本，而是按四个检查点逐级验证。

#### 检查点一：API 可执行性

用附录的 AP2112K/LED 最小示例测试 symbol library、pin name 和 `PROJECT_PATH`。

目标是得到可打开的 `.kicad_sch`，并记录 Python 与 ERC 的错误。

#### 检查点二：表示转换一致性

把同一份人工对齐 schematic 转成 L1、L2、L3，再执行每份代码。

目标是确认三种表示的 symbols、labels 和 netlist 在语义上保持一致。

#### 检查点三：小规模训练

先使用少量 JSONL 样本训练一个 adapter，检查生成代码的格式、引用编号和 `connect_pins` 调用。

不要在没有通过 API sanity 的情况下直接解释 validation loss。

#### 检查点四：完整 benchmark

固定 500 个 held-out test sample、单次/多次解码策略、KiCad 版本和 netlist 规范化算法。

再计算 Table 2 风格的 valid、spatial、Jaccard、Precision、Recall 和专家子集指标。

### 11.8 工程部署前的额外验证清单

论文指标通过后，实际使用还应追加：

- 根据 datasheet 核对每个器件的 pin function、绝对最大额定值和推荐外围。
- 核对 VIN、VOUT、GND、极性、电压域和电源时序。
- 检查未连接 pin 是否确实允许 NC，而不是模型漏接。
- 对高电流路径、电池、USB、RF 和连接器执行专门规则。
- 将 schematic 导入 PCB layout，检查 footprint、板框、间距和机械冲突。
- 执行 PCB DRC、信号完整性/电源完整性分析和原型测试。
- 在制造前由有资质的工程师批准，而不是直接运行生成脚本下单。

## 12. 一分钟复述版

本节要解决的问题是：在组会或面试中，用 8 到 12 行准确复述 SchGen 而不夸大它。

1. SchGen 研究的是自然语言到 PCB schematic，不是 Verilog 生成，也不是芯片流片。
2. 它让 GPT-oss-20B 生成可执行 Python，再用 KiCad API 写出可编辑 schematic。
3. 核心表示 Code-L1 用局部相对坐标放置符号，用 `connect_pins` 按 pin name 表达连接。
4. L2 去掉相对坐标，L3 进一步改成绝对坐标 wire；两者是表示消融基线。
5. 数据来自 1390 种设计、2105 个 KiCad schematics，扩成 8420 个请求-代码-CoT 样本。
6. 训练采用 SFT + LoRA，论文配置为 3 epochs、1 张 A100 80GB、约 21 GPU-hours。
7. Code-L1 的 valid circuit rate 是 82.00%，netlist Jaccard/Precision/Recall 是 49.08/54.87/52.80%。
8. 两位专家检查 100 个测试设计时，functional correctness 是 60.5%；去掉 CoT 后降到 14.0%。
9. 在 988 个来自 20 个 GitHub 项目的 OOD 样本上，SchGen 的 netlist accuracy 接近 GPT-5.2，但 valid rate 不一定更高。
10. 它覆盖的是 PCB 原理图前端：ERC 和 netlist 不是芯片的 STA、formal、DRC/LVS、GDSII 或制造签核。
11. 真正部署必须继续做 footprint、PCB placement/routing、DRC、SI/PI、原型测试和人工安全审查。
12. 论文最值得记住的结论是：对硬件生成任务，语义化、可执行的中间表示往往比直接堆大模型参数更关键。
