## 1. 一句话定位

**HLS-Eval 是第一个面向"LLM for HLS"任务的综合基准 + 可扩展评估框架：集成 94 个"LLM-ready"HLS 设计（来自 PolyBench 28 + MachSuite 17 + CHStone 20 + Rosetta 8 + C2HLSC 12 + PP4FPGA 3 + FlowGNN 3 + GNNBuilder 3，共 4048 行 C++，平均 HLS 综合时间 38 秒），通过模块化 Python API 集成 Vitis HLS C-Simulation / Synthesis 两套工具接口 + vLLM/simonw-llm 两套 LLM 推理抽象（支持本地 + 远程模型）+ 4 路细粒度并行评估引擎（n_jobs、n_jobs_llm、n_jobs_csim、n_jobs_synth 分别可调），用 4 个递进式指标（parseability → compilability → runnability → synthesizability）镜像真实 HLS 设计师的迭代调试流程，并在两个核心任务（kernel 生成 from 自然语言描述 + 硬件优化驱动的代码编辑（loop labeling、AP 类型转换、dataflow 重构、loop tiling））上提供 4 个开源模型（DeepSeek V3 / Qwen2.5-Coder 32B / Llama 3 70B / Llama 3 8B）的 baseline pass@k 结果作为可复用参考。**

这句话里的八个技术承重点：

1. **首个"LLM for HLS"综合基准** — 之前工作（C2HLSC 10 例 / HLSPilot 19 例 / Gai et al. 52 例）规模小或不开源，HLS-Eval 集 94 例 + 全开源。
2. **"LLM-ready"标准化** — 每个设计都打包成"单头文件 + 单 .cpp + 自然语言描述 + 自包含 testbench"4 件套，让 LLM 可以零样本直接吃。
3. **半自动化 benchmark 构建** — 论文给三个 meta-prompt（Hierarchy Extraction / Description Generation / Testbench Generation），让 LLM 协助从异构 HLS 源码生成标准化 benchmark 案例。
4. **两个核心任务**：(a) kernel 生成：从自然语言描述 → HLS C++ 实现（功能正确 + 可综合）；(b) 4 类代码编辑：loop labeling / AP integer + fixed-point 类型转换 / dataflow pragma 重构 / loop tiling + unrolling。
5. **4 个递进式指标**：parseability（能从 LLM 输出正确解析代码块）→ compilability（C++ 编译通过）→ runnability（testbench 通过）→ synthesizability（HLS 工具能综合成 RTL）。这 4 个指标镜像真实 HLS 设计师调试流程。
6. **unbiased pass@k** — 用 Chen et al. HumanEval 提出的无偏 estimator `pass@k = E[1 - C(n-c,k)/C(n,k)]`，避免低估小样本下的真实能力。
7. **细粒度并行引擎** — 4 路线程池（n_jobs 总、n_jobs_llm 推理、n_jobs_csim 综合、n_jobs_synth 综合）独立可调，避免 HLS 综合长尾阻塞 LLM 推理快任务。
8. **可扩展 Evaluator API** — 用户只需实现 `evaluate_design(benchmark_case, model)`，即可加入新任务定义（如 RAG、HLS agent、分层设计），框架自动并行。

## 2. EDA 阶段映射（①-⑰）

参照 [芯片流程.md](../芯片流程.md) 的 17 阶段标准编号：

| 阶段 | 覆盖 | 说明 |
|------|:---:|------|
| **① RTL 设计** | ⚠️ **间接** | HLS-Eval 不直接生成 RTL，而是评估 LLM 写 HLS C++ 的能力，HLS C++ 会被下游 HLS 工具综合成 RTL（论文评估了 synthesizability 指标）。 |
| ② RTL 功能仿真 | ❌ | 不涉及 RTL 仿真。仿真停留在 C 仿真（C-Simulation）层。 |
| ③ 逻辑综合 | ⚠️ **间接** | 评估指标 `synthesizability` 是 Vitis HLS `csynth_design` 是否能跑通，把 C++ 翻译成 Verilog。这是评估 LLM 输出的 C++ 是否能被综合，不直接做综合后 PPA 评估。 |
| ④ 门级仿真 | ❌ | 不涉及。 |
| ⑤ STA | ❌ | 不涉及。 |
| ⑥ 形式验证 | ❌ | 不涉及。 |
| ⑦-⑬ 后端物理流程 | ❌ | 不涉及。HLS 工具仅做 C-to-RTL，不做布局布线。 |
| ⑭-⑰ 流片→制造→封装→芯片 | ❌ | 纯评估基准，无 tape-out。 |

**覆盖率：0/17 核心 + 3/17 间接评估。** HLS-Eval 是**评估框架而非生成框架**——它的产出是 pass@k 数字（评估 LLM 在 HLS 任务上的能力），而不是可流片的电路。它的 EDA 位置在 **HLS 工具链入口**——评估 LLM 生成的 C/C++ 能否被 HLS 工具综合。

> ⚠️ HLS-Eval 最容易被误读的边界：
> - **它是"评估 LLM"而非"生成 HDL"**——它本身不设计电路，只打分
> - **`synthesizability` ≠ "电路正确"**——HLS 工具能综合不等于综合出的电路功能对。即使 synthesizability 通过，下游还要做功能等价性检查
> - **`pass@k` 在小样本（$n=5$）下波动大**——这是 unbiased estimator 的代价，与 [VerilogEval](../VerilogEval/论文深度讲解.md) 等 HDL 基准类似
> - **仅评估 Vitis HLS 一家**——不评估 Catapult HLS / Intel HLS / LegUp / Bambu。Vitis 的"严格 C++ 子集"和"固定 pragma 语法"是它的特点，不等于其他 HLS 工具

## 3. 输入 / 输出

### 3.1 输入

**(a) HLS-Eval 内置的 94 个 benchmark 案例（"LLM-ready"设计）**

每个案例由 4 个文件组成（论文 Appendix E 有完整示例）：

```text
<benchmark_case_dir>/
├── kernel_description.md    # LLM 生成的自然语言功能描述
├── kernel.h                # 头文件：typedef + 常量 + 顶层函数签名
├── kernel.cpp              # 顶层 kernel 实现（含可选子函数）
└── kernel_tb.cpp           # 自包含测试平台（main() + testcases）
```

**示例：`mul64To128`（CHStone 来源，64-bit × 64-bit → 128-bit 乘法）**

```cpp
// kernel.h
typedef unsigned short int bits16;
typedef unsigned int bits32;
typedef unsigned long long int bits64;
void mul64To128(bits64 a, bits64 b, bits64 *z0Ptr, bits64 *z1Ptr);
```

```cpp
// kernel.cpp
#include "kernel.h"
void mul64To128(bits64 a, bits64 b, bits64 *z0Ptr, bits64 *z1Ptr) {
    bits32 aHigh, aLow, bHigh, bLow;
    bits64 z0, zMiddleA, zMiddleB, z1;
    aLow  = a;            aHigh = a >> 32;
    bLow  = b;            bHigh = b >> 32;
    z1    = ((bits64)aLow) * bLow;
    zMiddleA = ((bits64)aLow) * bHigh;
    zMiddleB = ((bits64)aHigh) * bLow;
    z0    = ((bits64)aHigh) * bHigh;
    zMiddleA += zMiddleB;
    z0 += (((bits64)(zMiddleA < zMiddleB)) << 32) + (zMiddleA >> 32);
    zMiddleA <<= 32;
    z1 += zMiddleA;
    z0 += (z1 < zMiddleA);
    *z1Ptr = z1;
    *z0Ptr = z0;
}
```

```cpp
// kernel_tb.cpp
#include <cstdio>
#include "kernel.h"
int main() {
    int result = 0;
    struct {
        bits64 a, b;
        bits64 expected_high, expected_low;
    } test_cases[] = {
        {0x0000000100000000ULL, 0x0000000100000000ULL, 0x1, 0x0},
        {0xFFFFFFFFFFFFFFFFULL, 0xFFFFFFFFFFFFFFFFULL, 0xFFFFFFFFFFFFFFFEULL, 0x1},
        // ...
    };
    for (int i = 0; i < 5; ++i) {
        bits64 high, low;
        mul64To128(test_cases[i].a, test_cases[i].b, &high, &low);
        if (high != test_cases[i].expected_high || low != test_cases[i].expected_low) {
            printf("Test case %d FAILED ...\n", i);
            result = 1;
        }
    }
    return result;  // 0 = pass, 1 = fail
}
```

### 4.2 核心模块逐个详解

#### 4.2.1 基准构建模块（LLM-aided Benchmark Construction）

**这一模块存在的理由**：现有 HLS benchmark（PolyBench 等）的设计未针对 LLM 优化——缺少自然语言描述、testbench 与 kernel 混在一起、多文件分散。需要"标准化"才能让 LLM 公平评估。

**三个 meta-prompt**：

```text
Meta-Prompt 1 — Hierarchy Extraction:
  "You are a high-level synthesis expert. Help me identify all the 
   sub-components in this HLS hardware design. A sub-component is 
   a separate C++ function in the code that is not the top-level 
   function... Output the list of sub-components in a code block 
   representing markdown."

Meta-Prompt 2 — Description Generation:
  "You are a high-level synthesis expert. Help me write a natural 
   description of this HLS hardware design. The description should 
   cover the algorithm and functionality as well as the high-level 
   dataflow and architecture..."

Meta-Prompt 3 — Testbench Generation:
  "You are a high-level synthesis expert. Help me write a self 
   contained single file testbench for this HLS hardware design... 
   The testbench should always return 0 if the design is correct 
   and the testbench passes..."
```

**Human-in-the-Loop 步骤**（论文 Fig. 2）：LLM 输出后人工审查，特别是 testbench 的输入数据是否合理。

论文用 Llama 3.3 70B Instruct、Llama 3 70B Instruct、Qwen2.5-Coder 32B Instruct 构建 benchmark 自身。

#### 4.2.2 HLS Tool Interface 模块

**这一模块存在的理由**：Vitis HLS 命令行工具有 30+ 子命令，参数复杂。需要统一的 Python API 让 LLM 可以调用。

**两个核心 tool class**：

```python
class VitisHLSCSimTool:
    """两步：先编译，再执行"""
    def run(self, design_dir, source_files, not_source_files):
        # Step 1: csim_design -setup（编译）
        # Step 2: csim.exe（执行 testbench）
        return output_compile, output_run

class VitisHLSSynthTool:
    """一步：综合"""
    def run(self, design_dir, source_files, hls_top_function):
        # csynth_design（C++ → Verilog）
        return synth_output
```

每个 tool 调用捕获 `(return_code, stdout, stderr)`，让 LLM 知道"为什么失败"（区分语法错误 vs 功能错误 vs 综合错误）。

#### 4.2.3 LLM Model Abstraction 模块

**这一模块存在的理由**：本地推理和远程推理 API 接口差异巨大，需要统一抽象。

```python
class Model:
    """统一 LLM 抽象"""
    def generate(self, prompt, temperature, n_samples):
        # 子类实现
        pass

class LocalModel(Model):   # vLLM 后端
    pass

class RemoteModel(Model):  # Together AI / OpenAI / Anthropic 后端
    pass
```

论文 baseline 主要用 Together AI 托管的开源模型，少量用本地 vLLM。

#### 4.2.4 Parallel Evaluation Engine 模块

**这一模块存在的理由**：简单并行（每个 design 一个线程）会让综合长尾任务阻塞推理快任务。HLS 综合单 design 可达 38 秒 × 多个 design = 数小时。

**4 路独立线程池**：

```python
class EvalThreadPools:
    def __init__(self, n_jobs, n_jobs_llm, n_jobs_csim, n_jobs_synth):
        self.pool_llm   = Queue()  # LLM 推理任务
        self.pool_csim  = Queue()  # C 仿真任务
        self.pool_synth = Queue()  # 综合任务
    
    # 4 路独立线程分别消费各自的队列
```

**执行流**：

```text
设计 1: LLM 推理 → 进入 LLM 队列，分配 LLM 线程池里的一个线程
        → 输出后 → 进入 csim 队列，分配 csim 线程池的一个线程
        → 完成 → 进入 synth 队列，分配 synth 线程池的一个线程

设计 2 ~ N: 类似

每个阶段独立并行，瓶颈由各阶段自身的任务数决定。
```

论文 Fig. 4 给出执行轨迹，显示四个 pool 的利用率随时间变化——LLM 推理快（几秒），但综合慢（几十秒），独立池避免了短板效应。

**这一模块存在的理由**：不同任务（generation / editing / verification / RAG / agent 等）的评估逻辑差异大，但都共享同一套并行引擎和 HLS 接口。

- `HLSGenerationZeroShotEvaluator`：kernel 生成任务

## 5. 关键公式

### 5.1 无偏 Pass@k 公式

论文用 Chen et al. (HumanEval) 提出的 unbiased pass@k，避免小样本（$n$ 较小）下的偏差：

$$
\mathrm{pass@k} := \mathbb{E}\left[ 1 - \frac{\binom{n - c}{k}}{\binom{n}{k}} \right]
$$

- $n$：每个 benchmark case 的总采样数（论文 $n = 5$）
- $c$：通过（正确）的样本数
- $k$：pass@k 的 $k$（论文用 $k = 1, 5$）

**数值稳定实现**：

$$
\mathrm{pass@k}(n, c, k) = \begin{cases}
1 & \text{if } n - c < k \\
1 - \prod_{i=0}^{k-1} \frac{n - c - i}{n - i} & \text{otherwise}
\end{cases}
$$

- $n$：总样本数
- $c$：通过数
- $k$：pass@k 的 $k$

**为什么这么设计**：朴素 $\mathrm{pass@k} = 1 - (1 - \hat{p})^k$ 在小样本下高估真实能力。无偏 estimator 用组合计数修正偏差，与 Chen et al. HumanEval 一致。

**工程直觉**：例如 $n = 5, c = 1, k = 1$ 时：

- 朴素：$\hat{p} = 0.2$，pass@1 = 0.2
- 无偏：$1 - \binom{4}{1}/\binom{5}{1} = 1 - 4/5 = 0.2$（恰好相同）

但 $k = 5$ 时：

- 朴素：$1 - 0.8^5 = 0.672$
- 无偏：$1 - 0/1 = 1.0$（因为 $n - c = 4 < k = 5$，所有"通过"的子集都只有 1 个，正确率按"至少 1 个通过"算）

这是 unbiased estimator 的"全有或全无"行为，与朴素 estimator 不同。

### 5.2 4 个递进指标的逻辑关系

4 个指标不是独立的，而是有严格的"逻辑蕴含"关系：

$$
\mathrm{Parse} \implies \mathrm{Parseable}
$$

$$
\mathrm{Parseable} \implies \mathrm{Compilable}
$$

$$
\mathrm{Compilable} \implies \mathrm{Runnable} \implies \mathrm{Synthesizable}
$$

**为什么这么排序**：

1. **Parseability**：LLM 输出必须能正确解析成代码块。这一步失败意味着 LLM 没按 prompt 格式输出（漏了 `<OUTPUT_CODE>` 标签等）
2. **Compilability**：解析出的代码必须能通过 C++ 编译。这一步区分"语法错误"和"逻辑错误"
3. **Runnability**：编译后必须能跑 testbench 并通过。这一步检验"功能正确性"
4. **Synthesizability**：通过 testbench 后，必须能被 HLS 工具综合。这一步检验"硬件可实现性"

每一个指标是下一个指标的"前提"（necessary condition）。论文 Table III 里的 DeepSeek V3 数据：100% → 94.1% → 63.3% → 93.2%（pass@1）—— 可以看到 compilability → runnability 损失最大（30 个百分点），因为"功能正确"是 LLM 的最大短板。

### 5.3 并行引擎的任务公式

并行引擎的执行流可以抽象为：

$$
\mathrm{Job}(d, m, t) = \mathrm{LLM}(d, m, t) \to \mathrm{CSim}(d, m, t) \to \mathrm{Synth}(d, m, t)
$$

- $d$：benchmark design
- $m$：model
- $t$：sample index（$t = 1 \dots n$）
- 每个 Job 由三个子任务组成，必须顺序执行
- 但多个 Job 之间独立，可并行

**并行因子**：

$$
N_{\mathrm{parallel}} = \min\left( n_{\mathrm{jobs}}, |\mathrm{Jobs}| \right)
$$

- $N_{\mathrm{parallel}}$：实际并行数（不超过任务总数）
- $n_{\mathrm{jobs}}$：用户设置的总并行度
- $|\mathrm{Jobs}|$：任务队列大小

每个阶段内部的并行数：

$$
N_{\mathrm{llm,parallel}} = \min\left( n_{\mathrm{jobs\_llm}}, |\mathrm{LLMTasks}| \right)
$$

$$
N_{\mathrm{csim,parallel}} = \min\left( n_{\mathrm{jobs\_csim}}, |\mathrm{CSimTasks}| \right)
$$

$$
N_{\mathrm{synth,parallel}} = \min\left( n_{\mathrm{jobs\_synth}}, |\mathrm{SynthTasks}| \right)
$$

**为什么这么设计**：如果综合慢、长尾（典型 38 秒），固定一个 $n_{\mathrm{jobs}}$ 会让所有线程在综合阶段空等。分阶段并行让 LLM 推理（小任务，多并发）和综合（大任务，少并发）各自适合。

### 5.4 4 个评估模型的规模假设

论文 baseline 的模型规模对比：

$$
\mathrm{params}(\mathrm{DeepSeekV3}) \approx 671 \times 10^9
$$

$$
\mathrm{params}(\mathrm{Llama3\,70B}) = 70 \times 10^9
$$

$$
\mathrm{params}(\mathrm{Qwen2.5\text{-}Coder\,32B}) = 32 \times 10^9
$$

$$
\mathrm{params}(\mathrm{Llama3\,8B}) = 8 \times 10^9
$$

- $\mathrm{params}(\cdot)$：模型参数数
- DeepSeek V3 是最大的（MoE，实际激活参数更少）
- Llama 3 70B 和 Qwen2.5-Coder 32B 是中规模
- Llama 3 8B 是小规模基线

**工程直觉**：从 baseline 数据可以看出"HLS 任务对模型规模的敏感度"——pass@k 数字随规模单调上升（除 Loop Labeling 这种 easy task）。

## 6. 训练与实验设置

### 6.1 是否需要训练

**不需要训练。** HLS-Eval 是纯评估基准：

- 评估的 LLM 是预训练的（DeepSeek V3 / Qwen2.5-Coder 32B / Llama 3 70B / Llama 3 8B）
- Vitis HLS 工具是商业工具，无需训练
- 框架本身是 Python 工具链，不训练

论文是**评测性质**而非方法论性质（不像 [VerilogEval](../VerilogEval/论文深度讲解.md) 或 [ChipSeek](../ChipSeek/论文深度讲解.md) 那种"提出新方法"）。

### 6.2 实验设置

#### 6.2.1 评估模型

| 模型 | 类型 | 来源 |
|------|------|------|
| **DeepSeek V3** | 闭源/托管 MoE | Together AI |
| **Qwen2.5-Coder 32B Instruct** | 开源 32B | Together AI |
| **Llama 3 70B** | 开源 70B | Together AI |
| **Llama 3 8B** | 开源 8B | Together AI |

**温度参数**：$T = 0.7$（让 LLM 输出有随机性，但不至于乱说）

**采样数**：每个 (benchmark, model) 采样 $N = 5$ 次（计算 pass@1 和 pass@5）

#### 6.2.2 评估任务设计

**Task 1 — HLS Kernel Generation**：

- 输入：natural language description + header + tb.cpp
- 输出：kernel.cpp
- 评估子集：PolyBench（28 例，主要任务）+ MachSuite（17）+ CHStone（20）+ Rosetta（8）+ C2HLSC（12）

**Task 2 — Code Editing（4 子任务）**：

| 子任务 | 输入 | 输出 | 评估子集 |
|--------|------|------|----------|
| **Loop Labeling** | HLS kernel | 加 `label:` 的 HLS kernel | PolyBench 子集 |
| **AP + Fixed-Point Type Translation** | 用 `int/uint/float/double` 的 HLS | 用 `ap_int/ap_uint/ap_fixed` 的 HLS | PolyBench + CHStone + C2HLSC 子集 |
| **Dataflow Refactoring** | 普通 HLS kernel | 加 `#pragma HLS DATAFLOW` 的 HLS | PolyBench 子集 |
| **Loop Tiling** | 普通 HLS kernel | 加 tiling + UNROLL + ARRAY_PARTITION 的 HLS | PolyBench 子集 |

### 6.3 关键实验结果

#### 6.3.1 HLS Kernel Generation（Table III）

| 模型 | parse@1 | parse@5 | compile@1 | compile@5 | test@1 | test@5 | synth@1 | synth@5 |
|------|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| DeepSeek V3 | 100.0% | 100.0% | 94.1% | 97.6% | 63.3% | 65.9% | 93.2% | 97.6% |
| Qwen2.5-Coder 32B | 95.5% | 97.6% | 90.8% | 92.9% | 57.6% | 58.8% | 83.8% | 85.9% |
| Llama 3 70B | 98.6% | 100.0% | 84.9% | 87.1% | 53.6% | 54.1% | 82.1% | 84.7% |
| Llama 3 8B | 98.4% | 98.8% | 72.7% | 75.3% | 44.9% | 47.1% | 70.6% | 72.9% |

**关键观察**：

1. **DeepSeek V3 全面领先**——parse 100%、compile 94.1%、test 63.3%、synth 93.2%。
2. **小模型（Llama 3 8B）在 test pass@1 上只有 44.9%**——"LLM for HLS"对模型规模有明显依赖性。
3. **test pass@5 与 test pass@1 的差距有限**（64-65% vs 53-63%）——说明大多数失败 case 是 LLM 多次都搞不定的"硬任务"，不是随机性带来的失败。
4. **synth pass@1 显著高于 compile pass@1（93.2% vs 94.1%）**——这是 metrics 的逻辑蕴含：能综合必须能编译，所以 synth ≤ compile。但 synth 比 compile 高的少数 case 说明 HLS 工具偶尔能"宽容"地综合部分"勉强编译"的代码。
5. **Compile → test 损失 30 个百分点**（94.1% → 63.3%）——这是 LLM 的最大短板：从"语法正确"到"功能正确"。

#### 6.3.2 Code Editing Tasks

**Loop Labeling（Table IV，最简单任务）**：

| 模型 | parse | compile | test | synth |
|------|:---:|:---:|:---:|:---:|
| DeepSeek V3 | 100% | 100% | 100% | 100% |
| Qwen2.5-Coder 32B | 100% | 100% | 100% | 100% |
| Llama 3 70B | 100% | 90.7% (pass@1) | 90.0% (pass@1) | 90.7% |
| Llama 3 8B | 100% | 39.3% | 39.3% | 39.3% |

**关键观察**：Loop Labeling 是"纯文本操作"，几乎所有模型都能做到。Llama 3 8B 是个例外——它的输出经常不能正确解析或保留所有原代码，导致编译失败。

**AP + Fixed-Point Type Translation（Table V）**：

| 模型 | compile@1 | test@1 | synth@1 |
|------|:---:|:---:|:---:|
| DeepSeek V3 | 78.1% | 72.5% | 75.1% |
| Qwen2.5-Coder 32B | 67.5% | 62.6% | 69.8% |
| Llama 3 70B | 57.0% | 54.3% | 51.3% |
| Llama 3 8B | 55.8% | 43.3% | 45.0% |

**关键观察**：这是更有挑战性的任务——需要识别类型 + 推断合适位宽 + 调用 HLS 数学库。DeepSeek V3 的 72.5% test pass@1 是相对基准。

**Dataflow Refactoring（Table VI）**：

| 模型 | compile@1 | test@1 | synth@1 |
|------|:---:|:---:|:---:|
| DeepSeek V3 | 96.4% | 96.4% | 48.6% |
| Qwen2.5-Coder 32B | 89.3% | 89.3% | 24.3% |
| Llama 3 70B | 80.0% | 80.0% | 60.7% |
| Llama 3 8B | 30.7% | 30.7% | 9.3% |

**关键观察**：这是一个非常有意思的反转——Llama 3 70B 的 synth pass@1（60.7%）显著高于 DeepSeek V3（48.6%）和 Qwen（24.3%）。论文推测：Llama 70B 倾向于生成更"保守"的 dataflow 代码（少破坏少出错），而 DeepSeek V3 更激进地重构代码导致违反 HLS dataflow 规则。

**Loop Tiling（Table VII）**：

| 模型 | compile@1 | test@1 | synth@1 |
|------|:---:|:---:|:---:|
| DeepSeek V3 | 100% | 93.6% | 62.9% |
| Qwen2.5-Coder 32B | 95.7% | 95.7% | 57.1% |
| Llama 3 70B | 87.9% | 69.3% | 54.3% |
| Llama 3 8B | 52.1% | 36.4% | 34.3% |

**关键观察**：Loop Tiling 需要插入 `#pragma HLS ARRAY_PARTITION` + `#pragma HLS UNROLL`，容易引入 II 违例。test pass@1 接近 synth pass@1 说明"功能正确"的代码也基本可综合。

### 6.4 任务选择的合理性

| 任务 | 覆盖能力 | 工程意义 |
|------|----------|----------|
| Kernel Generation | NL → HLS C++ 的端到端生成 | "LLM 能写 HLS 吗？" |
| Loop Labeling | 简单文本编辑 | "LLM 能遵从格式指令吗？" |
| AP + Fixed-Point Translation | 类型系统理解 | "LLM 懂 HLS 类型吗？" |
| Dataflow Refactoring | 控制流重构 | "LLM 能理解 HLS 优化规则吗？" |
| Loop Tiling | 内存 + 并行优化 | "LLM 能生成高性能 HLS 吗？" |

**为什么这么选择**：5 个任务覆盖了 HLS 设计师的典型操作链路——从写新代码、加可读性标签、优化类型、应用 dataflow pragma、手动 tiling 优化。覆盖"易-中等-难"三个层次。

## 7. 创新点

### 创新点 1：首个综合"LLM for HLS"基准

**贡献**：第一个开源、综合、可扩展的 HLS 任务评估基准，规模 94 designs 是此前工作的 5-10 倍。

**为什么这么设计**：
- 已有工作（C2HLSC 10 例 / HLSPilot 19 例 / Gai et al. 52 例）规模小或不开源
- 评估 LLM 的能力需要足够大的样本才能有统计意义
- HLS 任务比 HDL 任务更复杂（C++ vs Verilog），需要专门的基准

**对比已有工作**：

| 基准 | 规模 | 开源 | 集成工具 | 并行 |
|------|:---:|:---:|:---:|:---:|
| C2HLSC | 10 | 是 | 无 | 无 |
| HLSPilot | 19 | 是 | 无 | 无 |
| Gai et al. | 52 | 否 | Vitis HLS | 无 |
| **HLS-Eval** | **94** | **是** | **Vitis HLS** | **是（4 路）** |

### 创新点 2：LLM-aided 半自动 benchmark 构建

**贡献**：用 3 个 meta-prompt（Hiearchy / Description / Testbench）让 LLM 协助 benchmark 标准化，配合人工 review 减少人工负担。

**为什么这么设计**：
- 94 个设计如果纯人工标准化，需要数月工作量
- 让 LLM 干"体力活"（切分文件、生成描述、写 testbench），人工只做 final review
- 但完全自动化不可靠（testbench 可能有错），所以 human-in-the-loop

**对比已有方法**：
- C2HLSC 完全手工构造
- HLSPilot 用 LLM 生成 HLS C++，但 benchmark 本身手工
- **HLS-Eval** 第一个把 LLM 用在"benchmark 构建"自身

### 创新点 3：4 个递进式评估指标

**贡献**：parseability → compilability → runnability → synthesizability 四个指标，镜像真实 HLS 设计师的迭代调试流程。

**为什么这么设计**：
- 单个"对/错"指标无法区分"LLM 在哪一步失败"
- 4 个指标提供 fail stage 信息：LLM 是输出格式错误，还是语法错误，还是功能错误，还是综合错误？
- 这个粒度让研究者能针对性改进 prompt / 模型

**对比已有方法**：
- VerilogEval：只报 "pass / fail" 一个指标
- HDLeval：报 2-3 个指标
- **HLS-Eval** 提供 4 个指标，最细粒度

### 创新点 4：4 路细粒度并行引擎

**贡献**：把 LLM 推理、C 仿真、HLS 综合三个阶段的并行度独立可调，避免综合长尾任务阻塞整个评估。

**为什么这么设计**：
- LLM 推理：秒级，可高度并行（10+ 个并行任务）
- C 仿真：秒级，中等并行度
- HLS 综合：38 秒 × 94 designs = 1 小时+ 长尾任务，少量并行（8 个）即可
- 用 1 个 $n_{\mathrm{jobs}}$ 会让所有线程在综合阶段空等

**对比已有方法**：
- VerilogEval：单线程串行
- C2HLSC：手动并行
- **HLS-Eval** 的细粒度并行是工程创新

### 创新点 5：可扩展 Evaluator API

**贡献**：用户只需实现一个 `evaluate_design(case, model)` 方法，即可加入新任务（RAG、agentic、hierarchical 等），框架自动并行。

**为什么这么设计**：
- "LLM for HLS" 是个新兴领域，任务定义还在快速演化
- 框架不应该限定用户只能跑论文给的两个任务
- API 抽象让用户用同一套数据 + 同一套 LLM + 同一套 HLS 工具，扩展自己的任务

**对比已有方法**：
- 大多数 LLM 评估框架（如 lm-eval-harness）专门针对 NLP 任务，不直接适配 HLS
- **HLS-Eval** 第一个把 Evaluator API 用到 HLS 任务上

### 创新点 6：开源的高质量 benchmark 套件

**贡献**：94 个 LLM-ready 设计全部开源，可被任何研究者用于新模型评估、新 prompt 工程、新任务定义。

**为什么重要**：
- 闭源 benchmark 阻碍研究复现
- 开源 benchmark 让社区能共同扩展
- HLS-Eval 提供"LLM-ready" 标准化，方便研究者直接复用

## 9. 与芯片流程的关系

### 9.1 在 EDA 流程中的位置

HLS-Eval 处于 **HLS 工具链入口**——评估"LMM 写的 HLS C++ 是否能被下游 HLS 工具链接受"。

```text
传统 EDA 流程：
算法 spec（C/C++）
   ↓
HLS 工具（Catapult / Vitis / Intel HLS）
   ↓  输出 HDL
① RTL 设计（HDL）
   ↓
② 仿真 → ③ 综合 → ⑤ STA → ⑦-⑬ 后端

HLS-Eval 介入点：
LLM 生成 HLS C++ → HLS-Eval 评估 → pass@k 数字（评估 LLM）
                              ↓
                      HLS 工具综合 → 生成 HDL
```

HLS-Eval 不直接参与 RTL 生成（那是 HLS 工具的工作），它的工作是"评估 LLM 生成 HLS C++ 的能力"。

### 9.2 与下游流程的连接

HLS-Eval 评估通过后，**LLM 生成的 HLS C++ 可以送入 Vitis HLS 综合**：

```text
LLM 生成的 kernel.cpp
   │
   ↓ pass synthesizability 检查
   ↓
Vitis HLS csynth_design
   ↓ 输出
Verilog HDL（符合 RTL 设计 ①）
   ↓
下游 EDA 工具（综合 / 仿真 / 物理设计）
```

但 HLS-Eval 评估通过 ≠ 综合出的电路功能正确。需要下游 RTL 仿真（②）做功能验证。

## 10. 讨论与局限

### 10.1 论文自述局限

#### 局限 1：仅评估 Vitis HLS 一家

论文评估基于 AMD/Xilinx Vitis HLS 2024.1。不同 HLS 工具（Catapult HLS、Intel HLS Compiler、Bambu、LegUp）的 C++ 子集 + pragma 语法 + 综合质量差异巨大。论文承认："evaluation framework can be extended to other HLS tools"。

**影响**：HLS-Eval 的 baseline 数字不能直接推广到 Catapult HLS 等其他工具。

#### 局限 2：仅评估开源 LLM

论文用了 4 个开源模型（通过 Together AI 托管），没有评估 GPT-4、Claude 等闭源旗舰模型。

**影响**：HLS-Eval 没有"上限参考"——读者不知道"最强 LLM 在 HLS 任务上能做到多好"。

#### 局限 3：任务覆盖不全

论文给出 1 个生成任务 + 4 个编辑任务。还有更多 HLS 优化任务未覆盖：

- 算子融合（kernel fusion）
- 数组重组（array reshape）
- 接口综合（interface synthesis）
- 数据流调度（dataflow scheduling）
- 接口协议转换（AXI / AXI-Stream / FIFO 等）

论文提到"future work will extend HLS-Eval by incorporating a broader range of benchmark designs and integrating tool-feedback evaluators"。

#### 局限 4：Zero-shot 任务

论文只评估 zero-shot（无示例）任务。没有评估 few-shot / CoT / RAG / agentic 等高级 prompting 技术。

**影响**：HLS-Eval baseline 数字可能"低"——这些高级方法可能大幅提升。但论文定位"建立 baseline"，未来工作可以扩展。

#### 局限 5：测试集规模

每个 benchmark 通常有 5-10 个 testcases。测试集对功能的覆盖有限，特别是浮点精度、边界 case。

**影响**：runnable ≠ 完全功能正确。更广泛的覆盖需要 property-based testing 或形式验证。

### 10.2 代码/复现层面的问题

#### 问题 1：Vitis HLS 商业依赖

Vitis HLS 是商业工具，免费学术 license 仍需申请。复现门槛：

- 需要 AMD/Xilinx 的账号
- 需要下载 Vitis HLS 2024.1（约 50 GB）
- 需要 FPGA 板卡 license（部分功能需要）

**替代方案**：论文提到可以扩展到其他 HLS 工具，但需要重写 `VitisHLSCSimTool` / `VitisHLSSynthTool` 接口。

#### 问题 2：Together AI API 依赖

论文 baseline 用 Together AI 托管的开源模型。复现门槛：

- Together AI 账号 + API key
- API 成本：$0.1-1/M tokens，每个 (case × model × n) 可能 1k-10k tokens
- 总成本估算：94 cases × 4 models × 5 samples × 多个任务 ≈ 数万次 API 调用，$100-1000+

**替代方案**：用本地 vLLM 部署开源模型（需要 GPU：A100/H100 等），但需要 ~80 GB GPU 内存部署 70B 模型。

#### 问题 3：评估时间

- LLM 推理：单次调用 1-10 秒
- C 仿真：单 design 1-5 秒
- HLS 综合：单 design 平均 38 秒
- 总时间：94 cases × 4 models × 5 samples × 综合时间 ≈ 总耗时 200+ 小时（如果串行）
- 并行（n_jobs_synth = 8）：~25 小时

**影响**：复现论文完整 baseline 需要 1-2 天连续计算。

#### 问题 4：temperature = 0.7 的随机性

论文用 $T = 0.7$ 让 LLM 输出有随机性。这意味着同一 (benchmark, model) 的 pass@k 数字在多次重跑会有波动。

**建议复现**：跑 3-5 次 full benchmark 取平均。

#### 问题 5：94 个 benchmark 的测试集覆盖

CHStone / MachSuite 等的原始测试集规模有限（5-10 个 testcases）。HLS-Eval 沿用了这些测试集，没有扩展。

**影响**：runnable ≠ 完全正确。复现时可以追加 corner case 测试。

### 10.3 本资料包的批判性分析

#### 批判 1：只评估 zero-shot 是"低垂果实"

**问题**：zero-shot 是最简单的 LLM 使用方式。few-shot / CoT / RAG / agentic 等更高级方法可能让 LLM 表现好得多。HLS-Eval 的 baseline 数字代表的是"最弱基线"，不代表"LLM 在 HLS 任务上的真正实力"。

**改进方向**：扩展任务定义，加入 few-shot / RAG / agentic 等 inference-time techniques。

#### 批判 2：synthesizability ≠ functionally correct RTL

**问题**：synthesizability 是"HLS 工具能综合"，但综合出的 RTL 可能有 bug。论文不评估 RTL 功能正确性。

**改进方向**：加入 RTL 仿真（用 Verilog simulator 跑综合出的 HDL），或形式化等价性检查。

#### 批判 3：4 个模型不能完整代表 LLM 生态

**问题**：只用了 4 个模型（DeepSeek V3 / Qwen 32B / Llama 70B / Llama 8B）。其他模型（GPT-4 / Claude 3.5 / Code Llama / StarCoder / DeepSeek Coder 等）未评估。

**改进方向**：扩展 model 集合，加入闭源旗舰模型 + 更多代码专用模型。

#### 批判 4：HLS-Eval 的"易于评估"可能鼓励"刷榜"

**问题**：HLS-Eval 提供清晰 pass@k 指标，可能鼓励研究者针对 benchmark 优化 LLM（微调 / RLHF），而非真正提升 HLS 任务能力。

**影响**：pass@k 数字可能虚高（类似 ImageNet 的 overfitting）。

**改进方向**：保留 10-20% benchmark 作为 held-out，专门测"通用 HLS 能力"。

#### 批判 5：与商业工具的 gap 评估

**问题**：HLS-Eval 只评估 LLM，不与商业 EDA 工具对比。无法回答"LLM 写 HLS C++ vs 人工写 HLS C++，差距多大？"

**改进方向**：加入"human baseline"——人工写 HLS C++ 与 LLM 直接对比。

#### 批判 6：真实 HLS 设计复杂度有限

**问题**：94 个 designs 平均 43 行 C++ kernel 代码。这是"教学 benchmark"规模。真实工业 HLS 设计（如 H.264 编码器、CNN 加速器）往往上万行 C++ + 复杂 pragma 配置。

**改进方向**：加入工业级 HLS benchmark（如 Rosetta 中的大型设计）。

## 12. 一分钟复述版

1. **核心问题**：HLS（High-Level Synthesis）是把 C/C++ 自动编译为 Verilog 的工具链，工程上比手写 HDL 高效，但入门门槛高，需要了解 pragma、约束、I/O 协议。LLM 有潜力降低这个门槛，但缺乏标准化、可比较的评估框架。

2. **方法概述**：HLS-Eval = 94 个"LLM-ready"HLS 设计（标准化文件结构）+ Vitis HLS C-sim/Synth 工具接口 + vLLM/simonw-llm LLM 推理抽象 + 4 路独立线程池的并行引擎 + Evaluator API（用户可扩展）+ 5 个任务（Kernel Generation / Loop Labeling / AP Type Translation / Dataflow Refactoring / Loop Tiling）+ 4 个递进式指标（parseability → compilability → runnability → synthesizability）+ unbiased pass@k 计算。

3. **核心数据**：94 designs × 4 models × 5 samples × 5 tasks × 4 metrics = 全 baseline 评估。DeepSeek V3 在 HLS Generation 的 test pass@1 = 63.3%（最强），Llama 3 8B = 44.9%（最弱）。

4. **关键结果**：(a) DeepSeek V3 全面领先（test pass@1 53-100% across tasks）；(b) 简单任务（Loop Labeling）所有模型接近 100%；(c) 复杂任务（Dataflow Refactoring）模型间差距最大（合成 9-60%）；(d) 编译通过率到 test pass 之间有 30 个百分点损失（这是 LLM 写 HLS 的主要短板）。

5. **最大创新点**：首个"LLM for HLS"开源综合基准 + 可扩展评估框架 + 4 路并行引擎。让"哪个 LLM 更适合 HLS"变成可量化、可复现的问题。

6. **EDA 流程位置**：HLS 工具链入口的**评估层**——它评估 LLM 生成的 HLS C++ 是否能被 Vitis HLS 综合，但本身不直接生成 HDL。

7. **与同类工作的关系**：上游评估 C2HLSC / HLSPilot / Gai et al. 等"LLM for HLS"方法；下游兼容 HLSFactory 数据集；互补 CorrectHDL（用 HLS 输出当参考生成 Verilog，HLS-Eval 评估 LLM 写 HLS C++ 的能力）。

8. **局限**：(a) 仅 Vitis HLS 一家工具；(b) 4 个开源模型基线，无 GPT-4 / Claude 闭源旗舰；(c) Zero-shot only，未评估 few-shot / RAG / agentic；(d) 94 个设计平均 43 行，规模小于真实工业 HLS；(e) 测试集覆盖有限；(f) 复现需商业 license + GPU + 25+ 小时。
