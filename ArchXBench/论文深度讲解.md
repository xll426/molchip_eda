## 1. 一句话定位

**ArchXBench 是一个把 RTL 生成 benchmark 从小模块推向复杂数据通路的六级分层题库：Level 1–6 共 51 道主任务（另加 Level 0 辅助 20 题，全仓库 71 题），覆盖组合逻辑、参数化层次、流水线、浮点、DSP、图像处理与领域加速器，并首次明确把"功能正确"与"架构合规"分开——模型不能用 `assign Y = A * B` 绕过指定的 Booth/Wallace/Dadda 微架构。论文用 Claude Sonnet 4、GPT-4.1、o4-mini-high、DeepSeek R1 做 zero-shot pass@5 基线：o4-mini-high 在摘要口径下解决 16 道（Level 1–3），从 Level 4 起所有模型出现明显"能力悬崖"。**

这句话里的四个技术承重点，后面逐一拆解：

1. **六级复杂度分层（curriculum）** — Level 0 从 mux/decoder 起步，Level 1c 要求显式构建 Kogge-Stone/Booth/Wallace/Dadda 微架构，Level 2 加入流水线，Level 3 引入浮点和迭代算法，Level 4–6 覆盖 FFT/FIR/CNN/3D 卷积/AES core/量化矩阵乘等真实数据通路。这是第一个把 benchmark 从"能否写语法正确的小模块"推向"能否按指定微架构写复杂数据通路"的尝试。
2. **功能正确不等于架构合规** — 这是 ArchXBench 最独特的贡献。Dadda 题里 `assign Y = A * B` 功能 testbench 全通过，但会被架构审核判不合格。真实 SoC 设计中，架构师常强制指定微架构（为了满足 latency/面积/功耗，或复用已验证 IP），ArchXBench 把这个约束前移到 RTL 生成环节。
3. **能力悬崖精确定位** — Level 4+（流水线浮点、DSP、图像/ML 加速器）全员失败，说明 LLM 在深流水线 latency 对齐、定点缩放/溢出、流式数据通路这些真实 SoC 难点上还很弱。训练集 familiarity（AES 常见成功，Dadda 少见全失败）和数学脚手架（gradient descent 明确公式成功率高）进一步揭示失败根因。
4. **为 Agentic 方法提供任务场** — ArchXBench 只做了最简单的 zero-shot baseline，没有 in-context example、没有 iterative repair、没有多 Agent。题目复杂度天然适合与 AutoChip、MAGE、VerilogCoder 等工具反馈 Agent 结合，在固定 token/工具调用/wall-clock 预算下公平比较。

| ⑭-⑰ 流片→制造→封装测试→芯片 | ❌ | — |

**覆盖率：2/17。** ArchXBench 是一个**纯数字前端 spec-to-RTL benchmark**，覆盖阶段 ①② 且在两者之间增加了一个独立的"架构合规"维度。

## 3. 输入 / 输出

### 3.1 输入

ArchXBench 每个任务提供以下文件，模型只能看到前两份：

**(a) problem-description.txt — 自然语言问题描述**

以 Level 1c 的 Dadda multiplier 为例：

```text
Title: 8-bit Dadda Multiplier
Objective: Implement an 8-bit x 8-bit unsigned multiplier using the
Dadda tree partial product reduction structure.
Background: Dadda multiplier uses a specific column-height reduction
schedule to minimize the number of half/full adders...
Design Constraints:
  - Must use Dadda reduction tree (not Wallace, not Booth, not '*')
  - Operand width: 8 bits, product width: 16 bits
  - Must handle all 2^16 input combinations correctly
Performance Expectation: Single-cycle combinational output
Deliverables: Synthesizable Verilog RTL
```

**(b) design-specs.txt — 形式化接口规格**

```text
Design Name: dadda_mult
Module Name: dadda_mult

Inputs:
  - A[7:0]  // Multiplicand
  - B[7:0]  // Multiplier

Outputs:
  - Y[15:0] // Product

Parameters: None

Submodules:
  - half_adder (HA): sum = a ^ b, carry = a & b
  - full_adder (CSA): sum = a ^ b ^ cin, carry = (a&b)|(b&cin)|(cin&a)

Internal Structure:
  - Stage 1: Generate 64 partial products (8x8 AND array)
  - Stage 2-5: Dadda column-height reduction
  - Final stage: Carry-propagate adder

Design Notes:
  - Column height sequence: {2, 3, 4, 6, 9, 13, 19, 28, 42, 63}
  - Prohibit direct use of Verilog '*' operator
```

**(c) testbench.v（隐藏，模型不可见）**

```verilog
module tb();
    reg [7:0] a, b;
    wire [15:0] y;
    dadda_mult dut(.A(a), .B(b), .Y(y));
    integer errors = 0;
    initial begin
        for (int i = 0; i < 256; i++)
            for (int j = 0; j < 256; j++) begin
                a = i; b = j; #1;
                if (y !== i * j) errors++;
            end
        $display("Errors: %0d", errors);
    end
endmodule
```

**(d) Level 4–6 附加材料**

```text
inputs/               # stimuli.json / .mem 激励向量
outputs/              # golden_output.json（参考输出）+ dut_output.json 占位
ref_model/            # Python 参考模型（如 unsharp_mask_ref.py）
scripts/              # compare_outputs.py 批量比较器
```

### 3.2 输出

- **满足架构规格的 Verilog RTL**，通过三重检查：

```verilog
// 合规（真正采用了 Dadda tree 部分积压缩）：
module dadda_mult(input [7:0] A, B, output [15:0] Y);
    // ... 64 partial products ...
    // ... Stage 1-5 Dadda reduction with HA/CSA ...
    // ... Final CPA ...
endmodule

// 不合规（功能对但架构错，会被判不合格）：
module dadda_mult(input [7:0] A, B, output [15:0] Y);
    assign Y = A * B;  // 架构审核拒绝
endmodule
```

## 4. Benchmark 构建方法

这节回答：ArchXBench 的 71 道题是怎么来的，凭什么可信。

### 4.1 题目来源与设计理念

ArchXBench 的题目来自作者对现代 SoC 数据通路难点的系统性梳理。设计理念是：现有 VerilogEval/RTLLM 的题目以小型组合逻辑和控制电路为主，不能代表真实设计中"架构师指定微架构、RTL 工程师实现"的分工模式。因此 ArchXBench 的每道题不仅要求功能正确，还要求**采用指定的微架构**。

### 4.2 六级复杂度分层

论文 Table I 定义了完整的六级分层（Level 1 拆为 1a/1b/1c）：

| 层级 | 题数 | 定位 | 代表性设计 |
|------|:---:|------|------|
| Level 0 | 20 | 辅助简单题（不计入主表） | mux、decoder、encoder、counter、shift register |
| Level 1a | 6 | 简单组合/多周期算术 | 32-bit RCA、8-bit CLA、barrel shifter、LFSR、GF(2^8) mult、AES S-box LUT |
| Level 1b | 5 | 参数化与层次化 | 32-bit RCA with 4-bit CLA blocks、carry-skip、carry-select、parametric shift-and-add mult、approximate adder |
| Level 1c | 7 | 高级算术单元 | Kogge-Stone、Brent-Kung、Booth、Wallace、Dadda multipliers、restoring/constant divider |
| Level 2 | 5 | 流水线算术与密码 | pipelined RCA/CLA/Wallace/Dadda、AES-128 single round |
| Level 3 | 6 | 浮点与迭代算法 | FP adder、FP multiplier、Gauss-Seidel、gradient descent、Newton-Raphson poly/sqrt |
| Level 4 | 7 | 流水线浮点与 DSP | pipelined FP add/mult、iterative FFT/IFFT、low/band/high-pass FIR |
| Level 5 | 6 | 图像/ML 流式模块 | Conv1D/2D、unsharp mask、Harris corner、DCT/IDCT、systolic GEMM |
| Level 6 | 9 | 领域加速器 | AES enc/dec cores、FP FIR filters、streaming FFT/DCT、3D CNN、quantized matmul、multi-channel Conv2D |

计数关系：Level 1–6 主表 6+5+7+5+6+7+6+9 = 51 题，Level 0 辅助 20 题，全仓库 71 题。

### 4.3 难度分层设计原则

```text
Level 0:  基本能力校准 — 接口名遵守、组合/时序写法、X 值传播、reset 极性
    │
Level 1a: 简单算术 — 功能正确即可，架构约束较弱
    │
Level 1b: 参数化层次 — 必须用指定 block size 的子模块搭建
    │
Level 1c: 指定微架构 — 明确要求 Booth/Wallace/Dadda/Kogge-Stone/Brent-Kung
    │          这里开始引入"架构合规"维度的独立检查
    │
Level 2:  流水线 — 加入 latency 对齐、valid 对齐、pipeline flush
    │
Level 3:  浮点/迭代 — IEEE-754 角落情况、定点表示、收敛判定
    │
Level 4:  流水线浮点 + DSP — 深流水、多模块、频域变换
    │
Level 5:  图像/ML 流式 — 行缓存、帧缓存、滑窗、数据复用
    │
Level 6:  领域加速器 — 多模块互联、流式协议、吞吐率约束
```

### 4.4 参考实现与质量把关

- **Level 1–3**：论文声称提供 Verilog reference design（Reference LoC 在 Table II 中标注），但当前 GitHub checkout（commit `f679fdb`）未公开这些参考 RTL。
- **Level 4–6**：多数只有 Python reference model（如 `conv3d_ref.py`），无 Verilog reference。Table II 中这些项的 LoC 标 `*` 表示是 Python reference LoC。
- **Testbench**：71 题每题一个 Verilog testbench，使用 Icarus Verilog 编译 + vvp 仿真。
- **Python comparator**：Level 4–6 使用 `compare_outputs.py` 批量比对 DUT 输出与 golden output。
- **架构合规**：目前主要依赖人工/额外检查，无自动化 checker。论文自己提出的未来方向包括 AST pattern、Yosys netlist、elaborated hierarchy、formal property、synthesis report 多维验证。

## 5. 关键公式与表示法

ArchXBench 作为 benchmark 论文，核心"公式"是其评估表示法。

### 5.1 `(n, t)` 表示法

论文 Table II 的每个单元格使用二元组：

$$
(n,\ t)
$$

- $n$：5 次独立生成中语法正确的候选数（`F` 表示全部语法失败）
- $t$：语法正确候选中，最好一个的 testbench 通过率（%）

例：`(4, 100)` = 5 次中 4 次语法正确，最好的候选 testbench 100% 通过；`(2, 30)` = 2 次语法正确，最好只过 30%；`(F, F)` = 全军覆没。

**工程直觉**：这个表示法比单一的 pass@k 更丰富——它区分了"语法卡住"和"功能卡住"两种失败模式。`(5, 15)` 和 `(1, 100)` 的 pass@5 可能相同，但前者说明模型语法稳定但逻辑欠缺，后者说明模型偶尔能迸发但大多编译不过——对应的改进策略完全不同。

### 5.2 Pass@5 定义

$$
\text{pass@5} = \begin{cases} 1, & \text{if } \exists\ \text{candidate among 5 that passes syntax + functional + architecture} \\ 0, & \text{otherwise} \end{cases}
$$

- $\text{pass@5}$：单题得分，取值只有 0 或 1（不是概率估计）
- $\exists$：存在量词，指 5 个候选中至少有一个同时通过语法、功能、架构三重检查
- 5：每题固定的采样数 $n$

**注意**：ArchXBench 的 pass@5 不是无偏估计式，而是"5 次生成中至少一次完整通过全部标准"。这与 VerilogEval 使用的统计估计式 `pass@k = E[1 - C(n-c, k)/C(n, k)]` 不同——ArchXBench 的 `n` 固定为 5，不做无偏估计。

### 5.3 三重判定逻辑

论文描述的通过逻辑可还原为：

```text
候选 RTL
    │
    ▼
{编译通过?} ──否──> Syntax Failure
    │是
    ▼
{testbench 100%?} ──否──> Functional Partial/Failure
    │是
    ▼
{符合指定微架构?} ──否──> Architecturally Incorrect
    │是
    ▼
该候选完整通过 → 该题 pass@5 success（5 个候选中至少 1 个通过）
```

**这张表说明四个关键发现**：

1. **Dadda multiplier 全部失败**：四个模型在 Dadda 上没有完整功能通过，说明训练集 familiarity 不足时 LLM 难以补全专门的结构知识缺口。
2. **Booth 只有 o4-mini-high 完整通过，Wallace 只有 DeepSeek R1 完整通过**：复杂算术单元上模型分化严重，没有单一模型全面领先。
3. **Pipelined 版本不一定更难**：Sonnet 4 在 pipelined FP adder 上得到 (4, 100)，优于 iterative 版本的 (2, 72)——论文推测 pipeline 模板在训练集中更常见。
4. **数学脚手架显著提升表现**：gradient descent（规格直接给出 `f(x)=ax^2+bx+c`, `f'(x)=2ax+b`, `x_next=x-αf'(x)`）四个模型三个 100%，而 Dadda（依赖专门结构知识）全失败——说明 benchmark 难度同时受电路复杂度和规格给出的 algorithmic scaffolding 影响。

### 6.4 四个关键问题

**Q1：摘要的 "16/30" 与 Table II 的 51 题为何不一致？**

摘要称 "o4-mini-high successfully solves 16 out of 30, spanning Levels 1, 2, and 3"，但 Table I 明确 Level 1–6 共 51 题（Level 1–3 为 29 题）。最可能的解释是：`t=100` 只表示功能 testbench 完整通过，最终成功还需人工确认指定架构，摘要的 16 是进一步架构过滤后的任务数。公开 Table II 没有单独提供 architecture-compliance 列，仓库也没有人工审核记录，因此无法从公开 artifact 严格重算 16。引用时应以表格 51 题为准，或说明摘要口径与主表存在差异。

**Q2：Level 4+ 真的"全员失败"吗？**

摘要写 "From Level 4 onward, however, all models consistently fail"，但 Table II 中 Sonnet 4 在 pipelined FP adder/mult 和 AES-128 encryption 上均有 `t=100`。合理口径是：Level 4–6 整体出现显著复杂度悬崖；少数候选能在 testbench 上达到 100%，但是否满足完整架构要求未在结果表中独立展示。不要简化成 "Level 4 之后绝无任何功能通过"。

**Q3：pass@5 与 `(n, t)` 的关系是什么？**

`(n, t)` 描述的是单模型在单题上的原始数据（语法正确数 + 最好功能通过率），pass@5 是在此基础上加入架构合规后的最终判定。两者不是同一个指标——论文没有为 `(n, t)` 计算无偏估计。

**Q4：AES 为什么能通过而 Dadda 不能？**

论文明确观察到训练集 familiarity 效应：AES 是公开资料中极常见的加密加速器，Dadda multiplier 的专门结构知识在训练数据中出现频率低得多。这说明当前 LLM 主要靠"背过类似设计"，尚不能从规格纯推理补全微架构细节。

## 7. 创新点

### 创新点 1：功能正确不等于架构合规——Benchmark 设计哲学的根本升级

这是 ArchXBench 最独特的贡献。现有 VerilogEval/RTLLM 等 benchmark 只问"功能对不对"，ArchXBench 多问一层"有没有用对方法"。

**已有 benchmark 的做法**：testbench 比对 `Y == A * B`，通过就算对。

**ArchXBench 的做法**：Dadda 题的 design-specs 明确要求 Dadda tree reduction schedule，`assign Y = A * B` 虽功能 100% 通过但架构不合格。

**为什么这很重要**：真实 SoC 设计中，架构师强制指定微架构有三个原因：
- 满足特定 latency（如 Booth 编码减少部分积行数，缩短关键路径）
- 满足面积约束（如 Wallace/Dadda tree 用更少加法器层级）
- 复用已验证 IP（指定 Kogge-Stone 是因为已有该 IP 的时序收敛经验）

ArchXBench 把这个"按图施工"的约束前移到 RTL 生成环节，考查模型能否遵循细粒度架构指令，而非自由发挥。

### 创新点 2：六级复杂度分层——精确定位 LLM 能力悬崖

从 mux/decoder 到 3D CNN 卷积，ArchXBench 的 71 道题形成了一条平滑的复杂度梯度。这让研究者能精确回答"模型在哪一层开始掉队"，而不是给一个笼统的 average pass rate。

Level 1c 的 Kogge-Stone/Booth/Wallace/Dadda 四连击就是最好的例子：同一个 Level 内四个模型表现分化严重，单一 average 完全掩盖了这种结构性的能力差异。

### 创新点 3：为 Agentic 方法提供任务场——但 baseline 本身极简

论文只做了最简单的 zero-shot baseline：没有 in-context examples、没有 iterative repair、没有多 Agent、没有 retrieval。这恰好为后续 Agentic 方法（AutoChip 的编译反馈搜索、MAGE 的多 Agent 协作、VerilogCoder 的 TCRG 规划 + AST-WT 调试）留出了干净的对比空间——因为 baseline 没有吃任何"测试时计算预算"的红利。

### 创新点 4：揭示"数学脚手架 vs 专门结构知识"的难度二因素

论文通过 gradient descent（公式明确，全通过）vs Dadda multiplier（无公式，全失败）的对比，揭示 benchmark 难度同时受两件事影响：(1) 电路本身复杂度；(2) 规格给出的 algorithmic scaffolding 是否充分。这个发现对后续 prompt 工程和 curriculum learning 有直接指导意义。

## 9. 与芯片流程的关系

### 9.1 ArchXBench 在全流程中的位置

```text
  自然语言算法意图
           │
           ▼
  problem-description.txt + design-specs.txt
           │
           ▼
  LLM 生成候选 Verilog RTL     ←── ArchXBench 在这段
           │                      自动评估 syntax +
           ▼                      functional + architecture
  iverilog 编译 + vvp 仿真
           │
           ▼
  人工/半自动 架构合规检查
           │
  ═══════════▼══════════════════
  ⚠️ 交接面：ArchXBench 到此为止
           │
           ▼
  ③ 逻辑综合 → ④ 门级仿真 → ⑤ STA → ... → ⑰ 芯片
```

### 9.2 「功能+架构通过」和「能做成芯片」之间隔着什么

ArchXBench 的"通过"三重标准（语法 + 功能 + 架构）比 VerilogEval 的纯功能标准更接近真实设计验收，但距离"可流片"仍有显著距离。以下环节 ArchXBench 完全不涉及：

**综合关（阶段 ③）**：ArchXBench 不跑 Yosys / Design Compiler。LLM 生成的 RTL 可能存在：
- `initial` 块赋初值（仿真器认，ASIC 综合器不认）
- 组合逻辑环（仿真器迭代收敛，综合器直接拒绝）
- 意外 latch（缺 else 分支，仿真碰巧对，综合行为不一致）
- 阻塞/非阻塞赋值混用导致仿真-综合行为差异

**时序关（阶段 ④⑤）**：ArchXBench 不引入任何门延迟/走线延迟信息。一条组合逻辑深度 50 级的路径在 RTL 仿真中"一个时间步完成"，在真实芯片上可能数百皮秒，根本跑不到目标频率。

**PPA 关**：ArchXBench 不评估面积、性能、功耗。论文自己把 PPA 列为未来扩展方向——对通过架构审核的候选跑 Yosys → OpenROAD，评估 area/timing/power proxy。

## 10. 讨论与局限

### 10.1 评测公平性与可信度分析

**Benchmark evaluator 本身是否可靠？**

当前仓库的 evaluator 存在多个已知问题，直接影响模型排名的可信度：

1. **Testbench 失败不返回非零退出码**：71 个 testbench 中只有 2 个使用 `$fatal`，69 个不含。故意全错的 comparator 仍让 `vvp` 返回 0——如果只看 return code，失败被误判为成功。

2. **Python comparator 有假阳性风险**：多个 comparator 使用 `min(len(ref), len(dut))` 截断比较，不强制长度一致。受控实验显示 DUT 输出只有 golden 的 1/3 也可能被打印 PASS。Level 6 的 multi-channel Conv2D 预存 DUT 输出为 0 项（golden 有 30,752 项），原 comparator 输出 PASS。

3. **空输出可判 PASS**：DUT 输出长度为 0 时 `zip(golden, dut)` 循环体不执行，输出 `0/30752 mismatches → PASS`。

4. **架构审核无自动化**：论文说"我们检查了架构"，但仓库没有逐候选审核记录或自动 checker。外部研究者无法独立复核这一层。

**结论**：在 evaluator 不可靠的情况下，任何模型排名都不可靠。最优先的工作是修复 benchmark harness——这是本领域（ResBench 恒真 bug、ChipBench 入口问题）的共性工程缺陷。

### 10.2 论文自述的局限

1. **不是一键可运行包**：更像题目素材库，缺少统一 LLM 调用器、编译器、结果聚合器。
2. **未公开参考 RTL**：论文称 Level 1–3 提供参考设计，但当前 GitHub checkout 未见正式 reference RTL。
3. **闭源模型/API 不可固定**：temperature、seed、max tokens、system prompt、API 版本未完全公开，难以严格复现。
4. **PPA/吞吐率未系统评价**：论文主要评估功能+架构，area、latency、throughput、power 留作未来工作。
5. **无 LICENSE**：当前 checkout 未见明确许可证，二次使用需谨慎。
6. **摘要与表格口径不一致**：摘要 "16/30" 与主表 "51/71" 存在口径差异。

### 10.3 代码/复现层面的问题

从 [ArchXBench论文与代码复现详解.md](./ArchXBench论文与代码复现详解.md) 提炼：

- **仓库更像素材库而非 harness**：题目规格和 testbench 完整（71/71/71），但缺统一执行框架、参考 RTL（当前 checkout 0 个）、论文五次生成结果、结果聚合器和架构审核证据。
- **论文与仓库可追溯性差**：README BibTeX 少一位作者（缺 Sohan Mupparapu），且页码占位 `pp. xx--yy`；README 提及 SRT、Montgomery、Needleman-Wunsch、IIR、ECC 等任务，当前仓库未实际包含。
- **论文声称"几十到上万行 RTL"**：但 Table II 展示的 reference LoC 最大仅数百行，高层任务还是 Python LoC。更稳妥的解释是：目标系统潜在规模可上万行，但不能把 Python LoC 当 RTL 规模。
- **Makefile 不完整**：只有 2 个 Makefile（conv3d、multi-channel conv2d），且 clean checkout 不能直接 `make all`——Makefile 期待 `conv3d.v`，仓库只有 `conv3d_dummy.v`。
- **复现等级 R2**：本地只完成了论文—仓库逐项核对（artifact audit）+ 代表性 testbench/comparator 行为验证（controlled smoke test）。未重跑四模型每题五次生成。

### 10.4 本资料包的批判性分析

1. **"架构合规"是最有价值也最难落地的贡献**：它抓住了真实设计的本质，但目前靠人工审核，可扩展性差。论文自己提出的方向（AST pattern、Yosys netlist、formal property）才是正解。

2. **能力悬崖 = 下一代模型/Agent 的靶心**：Level 4+ 全失败指明研究方向——流式数据通路、latency 对齐、定点数值是 LLM4RTL 尚未攻克的硬骨头。

3. **与 ResBench 互补**：ResBench 问"综合后省不省资源"，ArchXBench 问"用没用指定微架构"——两者都超越"功能对不对"，共同指向 RTL 质量的多维评测。

4. **Benchmark 工程质量是当前 LLM4EDA 领域最大的系统性风险**：ArchXBench 的空输出 PASS、ResBench 的恒真 bug、ChipBench 的入口问题——多个 benchmark 的 evaluator 都有根本性缺陷。先修 evaluator 再比模型，应该是该领域的铁律。

## 12. 一分钟复述版

ArchXBench（IIIT Hyderabad + UNC Charlotte，MLCAD 2025）是一个**不训练模型的六级分层 RTL benchmark**，把评测从"小模块功能对"推向"复杂数据通路架构合规"。核心四点：

1. **71 题六级分层**：Level 0（20 题，mux/decoder）→ Level 1c（7 题，Kogge-Stone/Booth/Wallace/Dadda，开始要求指定微架构）→ Level 2（5 题，流水线）→ Level 3（6 题，浮点/迭代）→ Level 4–6（22 题，FFT/FIR/CNN/3D 卷积/AES core/systolic GEMM）。

2. **功能正确不等于架构合规**：Dadda 题里 `assign Y=A*B` 功能 testbench 全通过但架构不合格。这是与其他 benchmark（VerilogEval/RTLLM）最根本的分野。

3. **Zero-shot 基线暴露能力悬崖**：Claude Sonnet 4、GPT-4.1、o4-mini-high、DeepSeek R1 四个模型在 Level 1–3 约半数通过，Level 4+ 出现明显能力悬崖。训练集 familiarity（AES 常见成功、Dadda 少见全失败）和数学脚手架（gradient descent 明确公式通过率高）揭示失败根因。

4. **当前仓库是素材库而非 harness**：71 套规格和 testbench 完整开放，但缺统一 runner、参考 RTL、论文生成结果和架构审核记录。Testbench/comparator 的失败传播有多个已知漏洞（空输出 PASS、截断输出 PASS、退出码不反映失败）。先修 evaluator 再比模型是最高优先级。

**边界**：只覆盖阶段 ①②（2/17），PPA 未评估，架构审核未自动化，复现等级 R2。
