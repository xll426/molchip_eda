## 1. 一句话定位

**RealBench 是首个基于真实开源 IP（AES 加解密核、SD 卡控制器、Hummingbirdv2 E203 RISC-V CPU）的 Verilog 生成 benchmark：60 个模块级 + 4 个系统级任务配备加密存储的多模态长文档规格（平均 197.3 行/模块），并用 100% 行覆盖率 testbench → Yosys 综合（Nangate45）→ JasperGold 时序等价检查三层验证严格判定；在现有 benchmark 上轻松超 60% 的 GPT-4-Turbo 在 RealBench 模块级 formal@1 仅 4.4%，最强 o1-preview 也仅 13.3%，系统级所有模型 func/formal 全为 0，首次量化出 LLM 与真实工业设计之间的巨大鸿沟。**

这句话里的五个承重点，后面逐一拆解：

1. **真实 IP 级设计复杂度** -- RealBench 的 60 个模块来自 AES 加解密、SD 卡控制器、E203 RISC-V CPU 四个真实开源项目，平均 241.2 行代码、0.52K cell、1.6 个子模块实例化。系统级平均 3537.3 行代码、1.1M cell、14.5 个子模块。相比 VerilogEval V2（16.1 行 / 31.4 cell），代码量 4.3 倍、cell 数 10.8 倍、子模块数 2.7 倍。

2. **结构化多模态长规格** -- 不是一句"实现一个 ALU"，而是人工手写的完整工程文档：框图、数据流图、状态转移图、I/O 接口表、寄存器表、时钟/复位行为、子模块信息、corner cases、约束条件。规格与 testbench 协同设计——从 reference RTL 提取关键功能点反写入规格，确保"规格说了什么就测什么"。

3. **三层验证——从仿真到形式等价** -- 第一层 Verilator 100% 行覆盖率 testbench（功能仿真）；第二层 Yosys 综合 candidate + reference 到 Nangate45 网表（可综合性检查）；第三层 Cadence JasperGold 时序等价检查（SEC，数学证明 candidate 与 reference 对所有输入序列输出等价）。44.2% 的 GPT-4-Turbo RTLLMV2 testbench 通过候选无法通过形式验证，暴露了"仿真通过不等于逻辑等价"的根本问题。

4. **模块级与系统级双任务** -- 模块级允许使用 golden submodule（模拟"在已有模块库上写新模块"）；系统级要求从零生成完整层级（模拟"从需求到系统的全流程"）。系统级所有模型 func/formal 全为 0，揭示层次化设计是 LLM 进入真实流程的硬门槛。

5. **去污染与安全设计** -- 规格以 `.md.gpg` 加密存储（阻挠 GitHub crawler 自动抓取）；提供 Rouge-L 标准化去污染流程（β=1.0，相似度 > 0.5 移除训练样本）。这是首个将"训练数据污染"作为 benchmark 设计要素正面解决的 RTL 基准。

## 2. EDA 阶段映射（①-⑰）

参照 [芯片流程.md](../芯片流程.md) 的 17 阶段标准编号：

| 阶段 | 覆盖 | 说明 |
|------|:---:|------|
| **① RTL 设计** | ✅ **核心** | 从加密的多模态长规格生成模块级/系统级 RTL。模块级允许使用 golden submodule dependency；系统级要求从零实现完整层级 |
| **② RTL 功能仿真** | ✅ **核心** | Verilator `--cc --exe --binary --trace --assert --coverage-line --timing`，handcrafted 100% reference line coverage testbench，逐信号比较 candidate 与 reference 输出 |
| **③ 逻辑综合** | ✅ **核心** | Yosys + Nangate45 开源 45nm 工艺库，将 candidate 和 reference 分别综合为门级网表。首次将"可综合性"纳入 RTL generation benchmark 的必需验证环节 |
| ④ 门级仿真 | ❌ | 综合后不跑 SDF 反标的门级仿真。本文的 formal 验证走的是网表等价路径（SEC），不依赖门级仿真波形 |
| ⑤ STA | ❌ | 不做静态时序分析。Nangate45 是学术工艺库，时序数据不具备物理意义。PPA 不在评测维度内 |
| **⑥ 形式验证** | ✅ **核心** | Cadence JasperGold SEC（时序等价检查），在 Yosys 综合后的门级网表上做 candidate ↔ reference 等价性数学证明。这是目前 AI4EDA benchmark 中验证纵深最深的一环 |
| ⑦ 布局规划 Floorplan | ❌ | — |
| ⑧ 标准单元摆放 Placement | ❌ | — |
| ⑨ CTS | ❌ | — |
| ⑩ 布线 Routing | ❌ | — |
| ⑪ 后仿真 | ❌ | 无 SPEF |
| ⑫ 物理验证 DRC + LVS | ❌ | — |
| **⑬ 签核 Signoff** | ✅ **局部** | 形式等价（SEC proven）是 RTL 签核前的等价性证明前提条件。RealBench 提供了签核链最前端的形式化证据，但不覆盖 STA/功耗/IR Drop 签核 |
| ⑭-⑰ 流片→制造→封装测试→芯片 | ❌ | — |

**覆盖率：5/17。** RealBench 是目前这批 AI4EDA benchmark 中验证纵深最深的——从 RTL 设计（①）到功能仿真（②）到逻辑综合（③）到形式验证（⑥）到 RTL 签核前提（⑬），形成了一个完整的"前端验证链"。其独特贡献在于把综合和形式等价引入 benchmark oracle：不只问"仿真对不对"，更问"能和 golden 等价吗"和"能综合吗"。

> RealBench 的"formal pass"（SEC proven）是最严格的正确性判定——它用数学证明 candidate 与 reference 对所有输入序列输出等价。但这个严格性也有代价：只有与 golden 结构高度一致的实现才能通过 SEC（如不同流水线深度、不同状态编码的合法替代实现可能被误判）。这不是形式验证的缺陷，而是"以单一 golden 为唯一正确答案"的 benchmark 设计范式所固有的。

## 3. 输入 / 输出

### 3.1 输入：工业级设计规格

RealBench 的输入不是简单的自然语言描述，而是人工撰写的结构化工程文档。以 AES cipher top 模块为例：

**规格文档结构**（每份 `.md` 约 200 行）：

```markdown
# aes_cipher_top

## 1. Introduction
AES-128 encryption core. Performs 10 rounds of SubBytes, ShiftRows,
MixColumns, and AddRoundKey on 128-bit data blocks.

## 2. Block Diagram
[框图：key_expand → round control → sbox → mix_columns → output mux]

## 3. Interface
| Port | Direction | Width | Description |
|------|-----------|-------|-------------|
| clk  | input     | 1     | System clock |
| rst  | input     | 1     | Asynchronous reset, active high |
| ld   | input     | 1     | Load signal: latches key and text_in on rising edge |
| done | output    | 1     | Asserted when encryption completes |
| key  | input     | 127:0 | 128-bit encryption key |
| text_in  | input  | 127:0 | 128-bit plaintext |
| text_out | output | 127:0 | 128-bit ciphertext |

## 4. Clock and Reset
- clk: system clock
- rst: asynchronous reset, active high. When asserted, all registers reset to 0.

## 5. Registers
| Name | Width | Description |
|------|-------|-------------|
| text_in_r | 127:0 | Registered input text |
| round | 3:0 | Current round counter (0-9) |

## 6. Operation Principle
### 6.1 Basic Principle
AES-128 encryption: 10 rounds of transformations on a 4×4 byte state matrix.

### 6.2 Mathematical Principle
- SubBytes: GF(2^8) multiplicative inverse + affine transform
- ShiftRows: cyclic left shift of rows 1,2,3 by 1,2,3 bytes
- MixColumns: matrix multiplication in GF(2^8)
- AddRoundKey: XOR with round key

## 7. Data Flow Diagram
[数据流图]

## 8. State Transition Diagram
[状态转移图：IDLE → LOAD → ROUND(0..9) → DONE]

## 9. Submodules
### 9.1 aes_key_expand_128
Expands 128-bit key into 11 round keys (128-bit each).
Interface: input clk, rst, key, ld; output [1407:0] key_expand

### 9.2 aes_sbox
Performs SubBytes lookup: input [7:0] a; output [7:0] y.

## 10. Corner Cases
- ld=0 while done=1: hold output
- key changes mid-encryption: ignored until next ld pulse

## 11. Constraints
- FIPS-197 compliance required
- Latency: exactly 11 cycles from ld to done (10 rounds + 1 load)
```

**来源 IP（4 个真实开源项目，60 个去重模块）**：

| IP | 模块数 | 典型模块 | 设计特点 |
|------|:---:|------|------|
| AES Encoder | 与 Decoder 共 6 个去重模块 | `aes_cipher_top`, `aes_key_expand_128`, `aes_sbox`, `aes_rcon` | 计算密集型，轮变换包含复杂的 GF(2^8) 矩阵运算 |
| AES Decoder | 与 Encoder 共用 S-box | `aes_inv_cipher_top`, `aes_inv_sbox` | 逆变换，控制流与 Encoder 不同 |
| SD Card Controller | 14 | `sdc_controller`, `sd_cmd_master`, `sd_data_master`, `sd_crc_7`, `sd_crc_16` 等 | 控制密集型，涉及 Wishbone 总线、FIFO、CRC、跨时钟域、多 FSM |
| Hummingbirdv2 E203 | 40 | `e203_cpu_top`, `e203_core`, `e203_exu`, `e203_ifu`, `e203_lsu` 等 | 最复杂，覆盖完整 RISC-V 流水线：取指、译码、执行、LSU、CSR、总线接口 |

**任务分级**：
- **模块级（60 题）**：输入当前模块规格 + 子模块接口信息。验证时使用 golden submodule，不要求 LLM 实现下层模块。
- **系统级（4 题，每个 IP 一个）**：输入整个系统的全层级规格。要求从零生成 top + 全部 submodules。验证只看系统外部行为。

**数据安全**：所有 `.md` 规格默认以 `.md.gpg` 加密存储（`make decrypt` 解密），阻挠 GitHub crawler 自动抓取进训练集。论文提供标准 Rouge-L 去污染流程（β=1.0，相似度 > 0.5 移除训练样本）。

### 3.2 中间产物

**task scaffold**（`mk_bench` 构建的模块级任务目录）：
```text
aes_cipher_top/
├── task.md              # 任务描述：目标模块名 + 输出路径
├── doc/
│   └── aes_cipher_top.md  # 解密后的完整设计规格
├── Makefile             # Verilator 编译/仿真规则
└── dep/
    ├── aes_key_expand_128.v  # golden submodule（允许使用）
    └── aes_sbox.v            # golden submodule（允许使用）
```
注意：golden `.sv` oracle **不**复制到 task 目录，防止答案泄漏。

### 3.3 输出与判定

**输出**：模块级为单个 `.v` 文件（如 `aes_cipher_top.v`），系统级为完整文件集。

**三层验证判定**：

| 层级 | 检查内容 | 工具 | 通过条件 |
|------|------|------|------|
| syntax | 能否编译 | Verilator `--cc --exe --binary` | 无 `%Error` |
| func | 功能是否正确 | Verilator 仿真 + 100% line coverage testbench | 无 `Hint: Output ... mismatches` |
| formal | 是否与 golden 逻辑等价 | Yosys 综合 + JasperGold SEC | `proven` |

**评测指标**（每题采样 n=20，o1-preview 因成本仅 n=1）：

$$
\text{metric@k} = \mathbb{E}_{\text{Problems}} \left[ 1 - \frac{\binom{n-c_m}{k}}{\binom{n}{k}} \right], \quad m \in \{\text{syntax}, \text{func}, \text{formal}\}, \quad k \in \{1, 5\}
$$

- $n$：每题采样次数（20，o1-preview 为 1）
- $c_{\text{syntax}}$：通过 Verilator 编译的次数
- $c_{\text{func}}$：通过功能仿真的次数
- $c_{\text{formal}}$：通过形式等价的次数
- 逐级筛选：$c_{\text{syntax}} \geq c_{\text{func}} \geq c_{\text{formal}}$

## 4. Benchmark 构建方法

### 4.1 题目来源：四个真实开源 IP

RealBench 的设计来源于 OpenCores（AES 加解密核、SD 卡控制器）和 riscv-mcu（Hummingbirdv2 E203 RISC-V CPU 核）的开源项目。四个 IP 覆盖三种典型硬件设计范式：

- **AES 加解密核**：计算密集型，涉及有限域 GF(2^8) 上的矩阵运算、S-box 查表、轮密钥扩展
- **SD 卡控制器**：控制密集型，涉及 Wishbone 总线协议、多 FIFO 缓冲、CRC 校验、跨时钟域同步、复杂状态机
- **E203 CPU**：计算与控制混合，包含完整的 2 级流水线 RISC-V 处理器（取指、译码、执行、访存、写回、CSR、总线接口单元），40 个模块覆盖了从顶层 CPU 到底层 ALU 数据通路的完整层级

### 4.2 设计规格的人工重建流程

RealBench 最核心的工程投入是**人工重写设计规格**。论文作者不直接使用开源项目原有文档（这些文档通常不完整、有歧义、缺少关键细节），而是遵循以下原则：

```text
┌─────────────────────────────────────────────────────────────────┐
│               RealBench 设计规格构建流程                          │
│               （对应论文 Section II-B）                           │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  Step 1: 分析 reference RTL 源码                                 │
│     │   识别关键功能点：接口信号、状态转移、数据通路、            │
│     │   子模块依赖、corner cases                                  │
│     ▼                                                           │
│  Step 2: 撰写设计规格                                            │
│     │   按层级结构：每个模块独立一份规格                          │
│     │   · Introduction + Block Diagram                          │
│     │   · I/O Interface 表（端口名、方向、位宽、功能描述）         │
│     │   · Clock & Reset 行为                                    │
│     │   · Registers 表                                          │
│     │   · Detailed Operation Principle                          │
│     │   · Data Flow Diagram / State Transition Diagram          │
│     │   · Submodule 信息（描述 + I/O 接口）                      │
│     │   · Corner Cases + Constraints                            │
│     ▼                                                           │
│  Step 3: 规格 × testbench 协同设计                               │
│     │   · 从 testbench 的关键检查点反写功能细节到规格             │
│     │   · 确保"规格描述的"和"testbench 测试的"严格对齐           │
│     │   · 禁止跨层级信息泄漏（子模块内部细节不出现在父模块规格中） │
│     ▼                                                           │
│  Step 4: 多轮审核与修订                                          │
│     │   · 不同作者交叉审查                                       │
│     │   · 核验：只看规格，另一个工程师能否独立实现？              │
│     ▼                                                           │
│  Step 5: GPG 加密存储                                            │
│     │   make encrypt → .md.gpg（阻挠自动爬取进训练集）           │
│     ▼                                                           │
│  最终产物：加密的结构化多模态设计规格（60 份模块级 + 4 份系统级）  │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**核心设计原则**：

1. **完整性**：规格必须包含实现所需的所有信息——另一个工程师仅凭规格就能独立实现正确的 RTL。
2. **层级隔离**：每个模块的规格只包含当前层需要的子模块接口信息，不允许跨层级细节泄漏。
3. **格式统一**：所有 64 份规格遵循相同的章节结构，确保模型评测的公平性。
4. **图解辅助**：关键概念（模块框图、数据流图、状态转移图）用图片呈现，模拟工程文档的真实形态。

### 4.3 验证环境的构建与校准

**Testbench 的 100% 行覆盖率保证**：

不同于 VerilogEval 的简单 testbench，RealBench 的 testbench 经历了严格的手工优化：

```text
  参考 RTL 源码
       │
       ▼
  人工分析关键功能点
  · 每个 always 块的触发条件
  · 每个 if/else 分支的覆盖路径
  · 状态机的每个转移弧
  · 边界条件（计数器溢出、FIFO满/空、地址越界）
       │
       ▼
  设计 stimulus 序列
  · 定向测试：覆盖每个 corner case
  · 约束随机激励：覆盖正常操作范围的组合
       │
       ▼
  运行 line coverage 分析
  · verilator_coverage annotate
  · 检查未覆盖行 → 增加 stimulus → 重新验证
  · 迭代直到 100% reference line coverage
       │
       ▼
  写回设计规格
  · 把 testbench 中新发现的关键功能点补充到规格文档
```

**形式验证链**：

```text
  candidate RTL              reference RTL
       │                          │
       ▼                          ▼
  Yosys synth                Yosys synth
  (Nangate45)                (Nangate45)
       │                          │
       ▼                          ▼
  candidate netlist          reference netlist
       │                          │
       └──────────┬───────────────┘
                  │
                  ▼
          JasperGold SEC
          (时序等价检查)
                  │
        ┌─────────┼─────────┐
        │         │         │
        ▼         ▼         ▼
     proven      cex    determined
     (等价)   (反例)   (不确定)
```

**为什么需要形式验证**：论文的核心发现之一是 100% 行覆盖率 testbench 仍不等于逻辑等价。在 RTLLMV2 上，GPT-4-Turbo 生成的代码中，相对 44.2% 的 testbench 通过候选无法通过 JasperGold 形式验证。这些候选在 testbench 覆盖的输入上正确，但在未覆盖的系统性状态空间中存在逻辑偏差。

### 4.5 去污染标准流程

RealBench 提供标准化的训练数据去污染协议：

- **度量**：Rouge-L（基于最长公共子序列的文本相似度）
- **参数**：β = 1.0（F-score 中召回率与精确率等权）
- **阈值**：Rouge-L > 0.5 的样本视为与 RealBench 公开语料重复
- **操作**：从训练集中移除超过阈值的样本

这一流程确保了不同方法在 RealBench 上的评测结果具有可比性——避免了某些模型因"训练时见过类似题目"而获得不公平优势。

## 5. 关键公式

### 5.1 pass@k 三级递进定义

RealBench 使用三层递进指标，每层是上一层的子集：

$$
\text{syntax@k} = \mathbb{E}\left[ 1 - \frac{\binom{n-c_s}{k}}{\binom{n}{k}} \right],\quad n=20,\ k\in\{1,5\}
$$

$$
\text{func@k} = \mathbb{E}\left[ 1 - \frac{\binom{n-c_f}{k}}{\binom{n}{k}} \right],\quad c_f \leq c_s
$$

$$
\text{formal@k} = \mathbb{E}\left[ 1 - \frac{\binom{n-c_m}{k}}{\binom{n}{k}} \right],\quad c_m \leq c_f
$$

- $n$：每题采样次数（固定为 20）
- $c_s$：通过 Verilator 编译的采样数
- $c_f$：通过功能仿真的采样数（必须是 $c_s$ 的子集——先编译通过才能跑仿真）
- $c_m$：通过形式等价的采样数（必须是 $c_f$ 的子集——先功能通过才跑 formal）
- $k$：允许从 k 个候选解中选最优

**工程直觉**：三层指标的递进关系 $c_s \geq c_f \geq c_m$ 反映了芯片验证的真实流程——先过编译（syntax），再过仿真（func），最后过形式等价（formal）。`func@1 - formal@1` 的差距衡量"仿真误导"的程度：模型生成的代码通过了功能测试但实际存在逻辑偏差。`syntax@1 - func@1` 的差距衡量"语法正确但功能错误"的程度。

### 5.2 形式等价（SEC）的判定逻辑

JasperGold 对 Yosys 综合后的两个门级网表执行时序等价检查：

$$
\forall\ \text{state}\ s,\ \forall\ \text{input sequence}\ \vec{x}:\quad F_{\text{candidate}}(s, \vec{x}) = F_{\text{reference}}(s, \vec{x})
$$

- $s$：系统的可达状态（由状态寄存器的值定义）
- $\vec{x}$：任意长度的输入序列
- $F_{\text{candidate}}$：candidate 网表的行为函数
- $F_{\text{reference}}$：reference 网表的行为函数

**工程直觉**：这是数学证明而非抽样测试。testbench 只能验证 $\vec{x} \in \text{test\_stimuli}$（有限子集），而 SEC 验证 $\forall \vec{x}$（所有可能）。这就是"44.2% testbench 通过但正式等价失败"的根本原因——那些候选在 testbench 覆盖的特定激励上碰巧正确，但存在 testbench 未触发到的系统性逻辑偏差。

**为什么不是形式验证的替代方案（如随机仿真）**：随机仿真即使跑 100 万周期，也只覆盖了状态空间的极小部分（组合爆炸）。对于包含 10 个 32-bit 寄存器的简单设计，总状态空间为 $2^{320} \approx 10^{96}$——远超任何仿真预算可覆盖。

### 5.3 Rouge-L 去污染公式

$$
\text{Rouge-L}(A, B) = \frac{(1+\beta^2) \cdot R_{\text{lcs}} \cdot P_{\text{lcs}}}{R_{\text{lcs}} + \beta^2 \cdot P_{\text{lcs}}}
$$

- $A$：训练样本文本
- $B$：RealBench benchmark 规格/代码
- $R_{\text{lcs}}$：召回率 = LCS 长度 / len(B)
- $P_{\text{lcs}}$：精确率 = LCS 长度 / len(A)
- $\beta$：F-score 参数（论文设置 β=1.0，等权）
- 判定：Rouge-L(A, B) > 0.5 → 移除训练样本 A

### 6.5 关键实验分析

**必须回答的四个问题**：

**Q1: 形式验证是否必要？**

绝对必要。论文 Figure 4 展示了一个关键实验：GPT-4-Turbo 在 RTLLMV2 上生成的代码中，相对 44.2% 的 testbench 通过候选无法通过 JasperGold 形式验证。在 RealBench 自身数据中，`func@1 - formal@1` 的差距对所有模型都显著（如 GPT-4-Turbo 9.4% vs 4.4%，差距 5.0 个百分点）。这意味着仅靠 testbench 判定的 benchmark（如 VerilogEval、RTLLM）系统性地高估了 LLM 的真实正确性。

**Q2: 子模块对 pass rate 的影响有多大？**

影响巨大。论文 Table IV 显示，无子模块任务的平均 formal@1 比含子模块任务高 13.0 个百分点（如 o1-preview w/o submodules 最高 50.0% vs w/ submodules 最高 8.6%）。DeepSeek-V3-671B 的差距最大（20.9 pp）。更关键的是：含子模块任务中，除组合电路外几乎所有模型 pass rate 为 0。这说明**子模块接口理解和实例化正确性**是当前 LLM 进入真实设计的最大断层。

**Q3: Reasoning model 在复杂任务上是否有优势？**

不但没有优势，反而可能退步。DeepSeek-R1-671B 在 RealBench 模块级 formal@1=7.8%，比其 base 模型 DeepSeek-V3-671B 的 10.8% 低 3.0 个百分点。论文分析原因是 R1 在复杂长任务中更容易产生**虚构模块头**等低级幻觉——reasoning 的"思考"能力在面对需要精确事实性的一致性问题时可能转化为过度发散。这为 reasoning model 在硬件设计领域的应用提供了重要警示。

**Q4: 多模态模型在工程图上的表现如何？**

提升有限。GPT-4o-V 相对 text-only GPT-4o 在 RealBench 模块级仅提升 2.6% func@1 和 2.9% formal@1。对比 ChipGPTV benchmark（GPT-4o-V 相对 GPT-4o 提升 6.0% func@1），RealBench 上多模态增益更小。原因是 ChipGPTV 每题仅含单张图，而 RealBench 的每份规格通常包含多张图（框图 + 数据流图 + 状态转移图），同时处理多图、长文本、复杂结构对当前多模态模型仍是严峻挑战。

### 6.6 Agent 结果

| Agent | 配置 | 模块级趋势 | 系统级趋势 |
|------|------|------|------|
| Self-reflection | GPT-4o base，4h timeout | 随迭代逐步提升 | 仍为 0（syntax/function/formal 全零） |
| VerilogCoder | GPT-4o base，syntax+sim+AST-WT | 不稳定：语法正确率随迭代下降（代码变复杂后更难保证语法） | 未报告 |

**解读**：简单的 self-reflection（生成 → 验证反馈 → 修复）在模块级有效，但系统级的复杂性超出了当前 agent 的调试能力。VerilogCoder 的语法正确率随迭代下降是一个重要的负面发现——随着 agent 反复修改代码（增加子模块、增加逻辑），代码越来越复杂，语法错误反而越来越多。这说明多 agent 框架面临"复杂度增长失控"问题。

### 6.7 失败因素分析（论文 Table IV + Figure 8）

**电路类型影响**（formal@1）：

| 条件 | 组合电路 | 时序（无 FSM） | 时序（含 FSM） |
|------|:---:|:---:|:---:|
| 无子模块（o1-preview） | 33.3 | **50.0** | 0.0 |
| 无子模块（GPT-4o-V） | 24.6 | **57.5** | 0.0 |
| 含子模块（所有模型） | 0.0-8.6 | 0.0 | 0.0 |

**关键发现**：
- **时序电路无 FSM 反而最好**：数据通路类模块（如 FIFO、流水线乘法器）是 LLM 最擅长的
- **组合电路次之**：在 CPU 中，组合电路往往涉及严格的细节要求（如 CSR 控制、长流水线写回逻辑），容易被 LLM 写错
- **FSM 是最难的**：含 FSM 的模块在无子模块条件下 pass rate 已接近 0%，含子模块则全为 0

**输入/输出长度影响**（论文 Figure 8）：
- o1-preview 和 GPT-4o-V 在短规格（< 200 doc lines）、短代码（< 100 code lines）的任务上通过率显著更高
- 例外：`aes_sbox` 和 `aes_inv_sbox`（规格和代码都长，但是简单的查表映射，因此通过率高）

## 7. 创新点

### 创新点 1：首个真实 IP 级 RTL 生成 benchmark

**已有 benchmark 的问题**：VerilogEval、RTLLM 等使用的是教学级小模块（平均 16-50 行代码、0-0.3 个子模块），模型在这些 benchmark 上已经出现饱和（MAGE 超 95%）。但这些 benchmark 的"通过"与"能用于真实工业设计"之间存在巨大鸿沟。

**RealBench 的做法**：使用四个真实开源 IP（AES 加解密核、SD 卡控制器、E203 RISC-V CPU），60 个模块平均 241.2 行代码、0.52K cell、1.6 个子模块。系统级平均 3537.3 行代码、1.1M cell、14.5 个子模块。设计复杂度比现有 benchmark 提升了一个数量级。

**结果**：GPT-4-Turbo 从 RTLLMV2 func@1=51.3% 骤降至 RealBench func@1=9.4%，降幅达 41.9 个百分点。Benchmark 的区分度被成功恢复。

### 创新点 2：三层递进验证——首次将形式等价引入 benchmark oracle

**已有 benchmark 的验证**：Icarus/Verilator 仿真 testbench。判定逻辑是"在 testbench 覆盖的输入上输出匹配"。

**RealBench 的做法**：
- 第一层（syntax）：Verilator 编译检查——确保生成的代码是可编译的 Verilog
- 第二层（func）：100% 行覆盖率 testbench——比现有 benchmark 的 testbench 覆盖更充分
- 第三层（formal）：Yosys 综合 + JasperGold 时序等价检查——数学证明 candidate 与 reference 对所有输入序列等价

**关键证据**：44.2% 的 GPT-4-Turbo RTLLMV2 testbench 通过候选无法通过形式验证。这直接证明了"仅靠仿真判定的 benchmark 会系统性地高估 LLM 能力"。

### 创新点 3：规格 × testbench 协同设计方法论

**已有 benchmark 的做法**：先写规格，再独立写 testbench。两者之间可能存在"规格说了但没测"或"测了但规格没说"的不一致。

**RealBench 的做法**：从 reference RTL 反向分析关键功能点，将这些功能点同时反映在规格文档和 testbench stimulus 中。这确保了"规格描述的"和"testbench 测试的"严格对齐。规格同时给出 submodule 的接口信息和行为描述，确保模型有充分信息完成模块集成。

### 创新点 4：系统级任务——从规格到完整系统的端到端评测

**做法**：4 个系统级任务（每个 IP 一个）要求 LLM 从全层级规格出发，生成完整的 top + 全部 submodules。不提供任何 pre-built 子模块实现。

**发现**：所有模型系统级 func/formal 全为 0。这说明当前 LLM 连"把多个模块的正确接口拼起来"都做不到——层次化设计的一致性（接口名、位宽、方向、时序协议、参数传播）是进入真实流程的硬门槛。

### 创新点 5：去污染作为 benchmark 的标准配置

**做法**：规格 GPG 加密 + Rouge-L 标准化去污染协议（β=1.0，阈值 0.5）。提供 `make decrypt` / `make clean_encrypt` 的标准化数据管理流程。

**意义**：这是首个将"训练数据污染"作为 benchmark 设计要素正面解决的 RTL 基准。随着 LLM 训练数据规模不断扩大（可能已经抓取了 GitHub 上的开源 RTL 项目，"见过"部分 RealBench 的原代码），去污染机制对评测公平性至关重要。

```text
│        │                                                       │

```

### 9.2 「RealBench 通过」与「芯片可用」之间隔着什么

1. **PPA 完全不涉及**：RealBench 的 formal pass 证明"candidate 和 reference 逻辑等价"，但不涉及面积、频率、功耗。一个面积 3 倍但逻辑等价的实现，在 RealBench 上是满分。

2. **等价但不同构的合法设计被误判**：SEC 要求 candidate 的状态空间与 reference 同构。如果模型写出了功能等价但流水线深度不同、状态编码不同的合法替代设计，SEC 可能返回 cex（反例）。这是"以单一 golden 为唯一正确答案"的范式局限，而非形式验证的缺陷。

3. **系统级全 0 的 benchmark 设计问题**：当所有模型分数都是 0 时，benchmark 无法区分模型优劣。RealBench 需要渐进式评分（如先评层级结构正确性、再逐模块评 func、最后评系统级 formal）才能恢复区分度。

4. **商业工具依赖**：JasperGold 是商业形式验证工具。没有许可证的研究者只能复现到 func@k 层，formal@k 需要通过开源替代（Yosys EQY / SymbiYosys）做"近似等价实验"，无法直接与论文 formal@k 数值对齐。

5. **验证强度阶梯的完成**：VerilogEval（弱仿真）< ChipBench（仿真+跨语言+reset）< RealBench（仿真+综合+形式等价）。三者共同量化了"验证越严格，模型表现越差"的规律，并给出了三个严肃的参考点。

## 10. 讨论与局限

### 10.1 论文自述的局限

1. **系统级任务过难**：所有模型系统级 func/formal 全为 0。论文提出需要渐进式子任务或分阶段评分机制。

2. **JasperGold 商业依赖**：限制开源环境的完整复现。可考虑 Yosys EQY/SymbiYosys 作为开源替代，但需单独报告、无法直接与论文 formal 指标对齐。

3. **100% 行覆盖率不等于全输入覆盖**：行覆盖率说明每行代码至少被执行一次，但不保证所有输入组合、状态转移路径、跨周期关系都被验证充分。

4. **解密后规格公开**：`.md.gpg` 加密阻挡了自动爬取，但解密后规格可被人为泄露或通过替代渠道进入训练集。去污染工具可缓解但无法根治。

5. **等价但不同构的实现**：SEC 要求与 golden 结构高度一致。功能正确但微架构不同的合法设计可能被判定失败。这是 form-based oracle 固有的召回率（recall）上限。

### 10.2 代码/复现层面的问题

从本地代码审计（commit `9bc9a6ac`）中发现的工程问题：

1. **旧版验证脚本的临时目录硬编码**：`run_verify.py` 使用 `tempfile.TemporaryDirectory(dir=f"/run/user/{os.getuid()}")`，不支持无该路径的容器/批处理节点。新版 `realbench_release/evaluation.py` 已修复。

2. **Verilator stderr 判错过于激进**：只要 stderr 非空就置 syntax/function 为 0，再从其中分类 `%Error`/`%Warning`。某些非错误诊断输出也可能写入 stderr，导致误判。更稳妥应同时检查 return code 和分类后的 error list。

3. **`mk_bench` 的 `.v` dependency 守卫冲突**：`mk_bench` 正确复制了 dependency `.v`（合法的 golden submodule），但 `start_container.sh` 的兜底守卫会因任何 `.v` 而拒绝部分合法任务目录。正式使用前需修正为"检查目标模块答案泄漏"。

4. **形式验证不可完全开源复现**：Yosys 综合前处理开源，但最终 equivalence checker（JasperGold）是商业软件。本地当前无 Verilator/Yosys/JasperGold，复现状态为 C+（数据/规格/任务生成链已复现，模型和验证结果未复现）。

5. **bundled model samples 不是本地日志**：仓库 `samples/` 含 11,584 条模型输出记录，是作者发布的原始结果，可重新送入验证器但不等同于本地跑出的结果。

### 10.3 评测公平性与可信度分析

**题目来源与模型训练数据的潜在重叠**：
- RealBench 的四个 IP 来自 OpenCores 和 GitHub 开源项目（Hummingbirdv2 E203）。这些项目的原始 RTL 代码早在 LLM 训练数据爬取之前就已公开。因此存在模型"见过原始 RTL"的风险。
- 论文通过两项措施应对：① 规格重写（人工撰写的规格文本不是原项目的 README）；② GPG 加密 + Rouge-L 去污染建议。
- **残余风险**：模型可能在预训练阶段见过原始的 Verilog 实现文件。虽然规格是重写的，但模块名、接口信号名通常与原项目一致。这对"去污染"提出了更高要求——不仅要去除规格文本，还要考虑代码层面的泄漏。

**形式验证 oracle 的 recall 限制**：
- SEC 要求 candidate 与 reference 的状态空间同构。功能正确但微架构不同的合法实现（如不同流水线深度、不同状态编码、不同资源共享策略）会被判定为 FAIL。
- 这意味着 RealBench 的 formal@k 是"与 golden 结构强相关等价"的通过率，而非"功能正确"的通过率。两者之间的差距难以量化。

**系统级 benchmark 的"全零地板"问题**：
- 当所有模型得分都是 0 时，benchmark 失去了区分度（不能区分"接近但差一点"和"完全错误"）。
- 论文自身也承认需要分阶段评分（先层级结构、再逐模块、最后系统级）。在引入这种评分机制之前，系统级的 0% 更多是"存在性证明"（证明问题很难）而非"比较性工具"。

**商业工具依赖的可复现性**：
- JasperGold 是 RealBench formal 指标的 oracle。没有 JasperGold 许可证的研究者只能复现到 func@k。
- 即使使用开源替代（Yosys EQY/SymbiYosys），其等价性判定逻辑和覆盖率可能与 JasperGold 不同。开源替代的结果不能直接与论文 formal@k 对比，只能作为独立的对照实验。
- 这意味着 RealBench 的 formal 指标在一定程度上是"不可独立验证的"——这是使用商业工具作为 oracle 的 inherent limitation。

**与现有 benchmark 的 fair comparison**：
- 论文 Table III 对比了各模型在 RTLLMV2、VerilogEvalV2、ChipGPTV 和 RealBench 上的表现。值得注意的是：
  - RTLLMV2 func@1 使用原有 testbench（非 100% line coverage）
  - RealBench func@1 使用 100% line coverage testbench
  - RealBench formal@1 使用 SEC
- 三层递增的验证严格度使得"RTLLMV2 func@1"与"RealBench formal@1"不在同一验证维度上，**不能直接做数值对比**。更准确的叙述是："同一模型在 RTLLMV2 的 func@1 为 X%，但在 RealBench 的 formal@1 降至 Y%"，强调的应该是验证严格度提升导致的"分数缩水"，而非"模型在两个 task 上的能力差异"。

### 10.4 本资料包的批判性分析

1. **"真实 IP"的真实性边界**：RealBench 的四个 IP 虽然是真实开源项目，但它们是"学术级真实"而非"工业级真实"。E203 是一个教学级 RISC-V 处理器（2 级流水线、单发射），远非工业级处理器（如 SiFive 的 U74 是 5 级双发射）。"真实"是相对的——比 VerilogEval 的教学小模块真得多，但距台积电 5nm 工艺下的商用 RTL 仍相距甚远。

2. **规格质量的"过度工程化"风险**：RealBench 的规格是人工精心撰写的——完整、结构化、无歧义。但在真实工业项目中，规格往往是**不完整、有歧义、需要在实现过程中不断澄清**的。如果一个 benchmark 的规格过于完美，它可能高估 LLM 在"模糊规格→RTL"这一真实场景中的能力。理想的 benchmark 应逐步引入"噪声"（歧义、缺失细节、矛盾需求）。

3. **formal 验证的"技术债务"**：JasperGold 是商业工具这一事实意味着 RealBench 无法成为一个"开放科学"的 benchmark——formal 指标需要特定的商业许可证才能独立复现。这对 benchmark 的长期可持续性构成挑战。未来的方向应是建立开源 formal 验证的等效 oracle。

4. **系统级全零的"鸡生蛋"问题**：论文指出系统级需要分阶段评分，但没有给出具体方案。这造成了一个困境：因为系统级全零所以需要更细粒度的评分，但没有细粒度评分就无法推动系统级研究。这是所有"前瞻性 benchmark"的共同问题——benchmark 本身定义了问题的难度，但也需要提供攀登的阶梯。

5. **与 ChipBench 的互补关系**：ChipBench 在任务类型上更丰富（生成+调试+参考模型），RealBench 在设计复杂度和验证严格度上更深（真实 IP+100% coverage+形式等价）。两者是目前 AI4EDA benchmark 生态中必要且互补的两极。

## 12. 一分钟复述版

RealBench（中科院计算所等，arXiv 2025）是首个基于真实开源 IP 的 Verilog 生成 benchmark。核心五招：

1. **真实 IP 级设计**：60 个模块级 + 4 个系统级任务来自 AES 加解密核、SD 卡控制器、Hummingbirdv2 E203 RISC-V CPU。平均 241.2 行代码、0.52K cell、1.6 个子模块（系统级 3537.3 行、1.1M cell、14.5 个子模块），分别是 VerilogEval V2 的 4.3 倍、10.8 倍、2.7 倍。

2. **工业级多模态长规格**：人工手写结构化文档（框图 + 数据流图 + 状态转移图 + I/O 表 + 寄存器表 + corner cases），规格与 testbench 协同设计。GPG 加密阻挠自动爬取。

3. **三层递进验证**：100% 行覆盖率 testbench → Yosys 综合（Nangate45）→ JasperGold 形式等价。44.2% 的 GPT-4-Turbo RTLLMV2 testbench 通过候选无法通过形式验证，直接证明"仿真通过不等于正确"。

4. **系统级全零的断崖**：所有模型系统级 func/formal 全为 0。模块级最强的 o1-preview formal@1 也仅 13.3%。DeepSeek-R1 比 base V3 反而低 3.0 pp（复杂任务更易幻觉）。多模态模型 GPT-4o-V 仅比 text-only GPT-4o 高 2.9% formal@1。

5. **首个标准化去污染机制**：Rouge-L 相似度 > 0.5 移除训练样本。Benchmark 的公平性被提升到数据治理层面。

**核心数字**：o1-preview formal@1=13.3%（模块级）、0%（系统级）。GPT-4-Turbo func@1 从 RTLLMV2 51.3% 骤降至 RealBench 9.4%。系统级所有模型全零。子模块是最大瓶颈（w/ submodules 的 formal@1 最高仅 8.6%）。

**边界**：覆盖率 5/17（RTL 设计→仿真→综合→形式验证→签核前提）。JasperGold 是商业工具限制独立复现。SEC 要求与 golden 结构同构（功能等价但微架构不同的实现可能被误判）。PPA 完全不在评测维度。系统级全零需要分阶段评分恢复区分度。
