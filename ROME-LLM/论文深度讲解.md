## 1. 一句话定位

**ROME 不训练任何模型，它把"一次写完整个 RTL 模块"替换为"按层次分解→逐子模块 LLM 生成→Icarus Verilog 编译/仿真→错误反馈修复→通过后进入下一层→最终顶层集成"的 8 阶段 automated pipeline——在 6 个复杂 benchmark 上让 8 个模型全部有改善，Llama 2 从全 0 拉到部分有效，GPT-4 层次化后 pass@1 在多数任务达 0.7–1.0，并完成首个无人类设计干预的 LLM 生成处理器。**

这句话里有四个技术承重点，后面逐个拆：

1. **不训练** —— 全部收益来自推理时编排（inference-time scaling），调用现成 LLM（6 个开源 + 2 个闭源），不做 SFT/RL/DPO。唯一训练的 CL-Verilog 是作者微调的参赛模型，ROME pipeline 本身不更新任何权重。
2. **层次分解 + 逐层工具反馈** —— 把"硬件工程师分模块设计"的做法自动化。不是像 MAGE 那样对单个完整 DUT（Design Under Test，待测设计）反复修复候选，也不是像 ChipSeek 那样用综合/STA 的 PPA（Power, Performance and Area，功耗/性能/面积）数字做 reward 训练。ROME 的创新在于**把复杂度的维度从"代码长度"转换成"层次深度"**，让 errors 局部化到当前子模块的编译/仿真反馈环里。
3. **HDHP vs PGHP 两种 hierarchy 来源** —— HDHP（Human-Driven Hierarchical Prompting）是人给架构、LLM 实现；PGHP（Purely Generative Hierarchical Prompting）是 LLM 自己从顶层需求提出子模块列表。论文把两者分开评测，发现 PGHP 的架构规划能力是比"写 Verilog 语法"更难的瓶颈。
4. **Relay Prompting** —— 针对短上下文文本补全模型（text-completion LLM，如 Llama 2/Code Llama）的上下文压缩技术：最近一层保留完整代码，更早模块只保留实例化/接口行，让开源小模型也能"接力"处理深层层次。

**与 ChipSeek/MAGE 的本质区别**：

| 维度 | ROME | MAGE | ChipSeek |
|------|------|------|----------|
| 改进发生在 | 推理时 | 推理时 | 训练时（SFT + CDPO） |
| 核心机制 | 层次分解 + 逐层工具反馈 | 四 Agent 分工 + 高温采样 + State Checkpoint | RL reward 来自综合/STA 的 PPA 数字 |
| 反馈信号 | Icarus 编译错误 + vvp 仿真 mismatch | 仿真器 mismatch 数（逐拍 checkpoint） | 综合面积/延迟 + 功能正确性 |
| 优化目标 | 功能正确（testbench pass） | 功能正确（testbench pass） | 功能正确 **+ PPA** |
| 层次化 | **核心贡献** | 不涉及 | 不涉及 |
| 工具链 | Icarus Verilog（开源） | Icarus Verilog（开源） | Design Compiler / Yosys（综合） |
| 跨题知识积累 | 无（每题独立） | 无（每题独立） | 有（参数吸收共性） |
| 多模块 | **是（核心）** | 否（单模块） | 否（单模块优化） |

ROME 是这三篇里**唯一把"硬件设计天然就是层次化的"这个工程事实做成 LLM pipeline 第一等公民**的工作。MAGE 和 ChipSeek 都在单模块假设下运作。

> 注意：ROME 的名字是 "Recurrent Optimization via Machine Editing"，这里的 "Optimization" 是指**机器反复编辑当前生成物直到通过测试的迭代修复过程**，不是 PPA（面积/功耗/时序）优化。ROME 的 success 条件是 "top module passes its testbench"，不涉及综合、STA、面积、延迟、功耗中的任何一项。这是理解 ROME 位置的关键。

## 2. EDA 阶段映射（①-⑰）

参照 [芯片流程.md](../芯片流程.md) 的 17 阶段标准编号：

| 阶段 | 覆盖 | ROME 做了什么 / 为什么没做 |
|------|:---:|---------------------------|
| **① RTL 设计** | ✅ **核心** | LLM 按层次顺序逐子模块生成 Verilog RTL（Register-Transfer Level，寄存器传输级），从叶子模块到顶层模块。HDHP 模式下层次由人给定，PGHP 模式下由 LLM 自动规划 |
| **② RTL 功能仿真** | ✅ **核心** | Icarus Verilog（`iverilog` 编译 + `vvp` 执行）对每个子模块跑 unit testbench，对顶层跑集成 testbench。编译错误/仿真失败文本回灌 LLM 请求修复，最多 10 轮 per 子模块 |
| ③ 逻辑综合 | ⚠️ **弱覆盖** | 论文 benchmark 评测不涉及综合。但 processor case study 中将生成的 MIPS/RISC-V 处理器送入 Vivado 综合并仿真指令——这属于非系统性的验证，不是 pipeline 内闭环。论文并未用综合结果作为反馈信号迭代优化 RTL |
| ④ 门级仿真 | ❌ | 无 SDF（Standard Delay Format，标准延时格式）反标。Icarus 仿真假设零延迟，看不到毛刺、建立/保持违例、X 传播 |
| ⑤ STA（Static Timing Analysis，静态时序分析） | ❌ | 不计算任何路径延迟，不设时钟周期约束。ROME 完全不知道生成的电路能跑多快 |
| ⑥ 形式验证 | ❌ | 不做 SAT/SMT 等价性证明。testbench pass 不等于 RTL 和参考设计逻辑等价 |
| ⑦ 布局规划 Floorplan | ❌ | — |
| ⑧ 标准单元摆放 Placement | ❌ | — |
| ⑨ CTS（Clock Tree Synthesis，时钟树综合） | ❌ | — |
| ⑩ 布线 Routing | ❌ | — |
| ⑪ 后仿真 | ❌ | 无 SPEF（Standard Parasitic Exchange Format，标准寄生参数交换格式）信息 |
| ⑫ 物理验证 DRC + LVS | ❌ | — |
| ⑬ 签核 Signoff | ❌ | — |
| ⑭ 流片 | ❌ | — |
| ⑮ 制造 | ❌ | — |
| ⑯ 封装 + 测试 | ❌ | — |
| ⑰ 芯片 | ❌ | — |

**覆盖率：2/17（严格），2.5/17（计入 case study 的弱覆盖）。**

ROME 是一个**数字前端 spec → hierarchy → 逐层 RTL 生成与验证闭环工具**。它在阶段 ①② 之间对每个子模块反复迭代直到 unit test 通过，然后对顶层反复迭代直到集成 testbench 通过。与 MAGE 和 AutoChip 一样，它交棒在阶段 ② 之后。

> 关于工具链的关键澄清：ROME 的反馈环**只用到 Icarus Verilog（开源编译+仿真器）**。论文中 processor case study 用了 Vivado 综合来确认生成的处理器的确可综合，但这不属于 ROME pipeline 的自动反馈环——综合结果不会回灌 LLM 触发修改。因此 ROME **不是**"用商业 EDA 工具做 PPA 闭环反馈"的系统。它和 MAGE、AutoChip 在工具链层级上属于同一梯队（都只用 Icarus），区别在于**是否做层次化分解**。

## 3. 输入 / 输出举例

### 3.1 输入（HDHP 模式，以 64-to-1 Multiplexer 为例）

ROME 的 HDHP 输入由三部分组成：系统提示 + 顶层目标 + 层次子模块列表。

**(a) System Prompt（全局约束，所有模型/所有 benchmark 共用）**

```text
Our goal is to provide complete Verilog modules based on user-provided
specifications. Only the specified module is necessary, no testbenches or
supplementary modules are needed. Examples of compiler and simulation
errors for a given module may be provided, in which case we will proceed
to correct the module. All modules will be provided in their complete and
correct form.
```

核心约束：只输出指定模块、不生成 testbench、遇到错误时输出修正后的完整模块。这和 MAGE 的 RTL Generation Agent system prompt 同构——都试图阻止 LLM "画蛇添足"生成无关代码。

**(b) Global Prompt（顶层目标）**

```text
We will be designing a 64-to-1 multiplexer in Verilog using hierarchical
submodules.
```

**(c) 层次列表（人类定义的架构）**

```python
submodules = [
    ["mux2_1",  "2-to-1 multiplexer",  "input in1, input in2, input select, output out"],
    ["mux4_1",  "4-to-1 multiplexer",  "input [1:0] sel, input [3:0] in, output out"],
    ["mux8_1",  "8-to-1 multiplexer",  "input [2:0] sel, input [7:0] in, output reg out"],
    ["mux16_1", "16-to-1 multiplexer", "input [3:0] sel, input [15:0] in, output reg out"],
    ["mux32_1", "32-to-1 multiplexer", "input [4:0] sel, input [31:0] in, output reg out"],
    ["mux64_1", "64-to-1 multiplexer", "input [5:0] sel, input [63:0] in, output reg out"],
]
```

每个子模块附带 module name（文件名用）、human-readable name（prompt 里引用）、I/O interface（接口字符串）。依赖顺序已隐含：叶子模块（mux2_1）在最前，集成模块（mux64_1）在最后。

**(d) 首个子模块的完整 Prompt（论文 Figure 2a 伪代码 + Figure 2b 的实际模板）**

```
top_module = "64-to-1 multiplexer"
next_module = "2-to-1 multiplexer"
next_io = "input in1, input in2, input select, output out"

prompt = "We will be designing a 64-to-1 multiplexer in Verilog using
hierarchical submodules. We begin by generating a 2-to-1 multiplexer
with the following structure:
module mux2_1(input in1, input in2, input select, output out);
// Insert code here
endmodule"
```

**关键设计**：prompt 里只提供模块名和接口，不提供内部逻辑的任何提示。`// Insert code here` 是留给 LLM 的补全锚点。

**(e) Unit Testbench（每个子模块独立）**

论文附录 Table 5 列出 6 个 benchmark 的全部子模块，每个都配有 unit testbench。以 mux2_1 为例，testbench 会例化 DUT、生成所有 4 种输入组合（sel=0/1, in1=0/1, in2=0/1），逐组合比对 DUT 输出与期望值。testbench 被完整放入 prompt（LLM 看不到 reference implementation）。

### 3.2 中间产物：层次化生成的 Relay Prompt 演变

以 64-to-1 Mux 为例，生成过程的 prompt 演变（论文 Figure 2）：

**生成 mux2_1 后**——此时代码文件 `prev_submods.v` 内容：
```verilog
module mux2_1(input in1, input in2, input select, output out);
    assign out = select ? in2 : in1;
endmodule
```

**生成 mux4_1 的 prompt**：
```
We will be designing a 64-to-1 multiplexer in Verilog using hierarchical
submodules. We have generated the following submodules: ["2-to-1
multiplexer", "4-to-1 multiplexer"] implemented as:

module mux2_1(input in1, input in2, input select, output out);
    assign out = select ? in2 : in1;
endmodule

module mux4_1(input [1:0] sel, input [3:0] in, output out);
    wire out1, out2;
    mux2_1 m1(.in1(in[0]), .in2(in[1]), .select(sel[0]), .out(out1));
    mux2_1 m2(.in1(in[2]), .in2(in[3]), .select(sel[0]), .out(out2));
    mux2_1 m3(.in1(out1), .in2(out2), .select(sel[1]), .out(out));
endmodule

Please use the previous submodules to hierarchically generate a
8-to-1 multiplexer defined as:
module mux8_1(input [2:0] sel, input [7:0] in, output reg out);
// Insert code here
endmodule
```

**Relay Prompt 压缩后的 prompt（论文 Figure 3b，以 5-to-32 Decoder 为例）**：

对于短上下文文本补全模型，更早模块被压缩为仅接口行：

```
The following Verilog implements a 5-to-32 decoder utilizing hierarchical
submodules. We have the following module(s) already available for use:

module decoder2to4(<human-sourced I/O>)

We can then use that module hierarchically to generate a 3-to-8 decoder:

module decoder3to8(<LLM-generated I/O>)
<LLM-generated full module code>
endmodule

We can then use these modules to hierarchically generate a 5-to-32 decoder:
module decoder5to32(
```

注意 decoder2to4 只有一行接口声明（无实现），decoder3to8 保留完整代码（最近一层），decoder5to32 是当前目标。这就是 relay prompt 的核心：**最近一层完整代码 + 更早层接口 = 层次接力**。

### 3.3 工具反馈示例

当子模块编译/仿真失败时，ROME 将 Icarus 的输出回灌 LLM。典型反馈格式：

**编译失败**：
```text
mux8_1.v:12: syntax error
mux8_1.v:12: error: Invalid module instantiation
mux8_1.v:15: warning: Port count mismatch
```

**仿真失败**（testbench 的 mismatch 报告）：
```text
Mismatches: 15 in 256 samples
First mismatch occurred at time 130
```

ROME 的反馈粒度比 MAGE 的 State Checkpoint 粗糙——没有逐拍信号值、没有期望 vs 实际输出的具体数值。它和 AutoChip 处于同一水平：只告诉 LLM "哪里错了"和"错了多少"，但不告诉"在什么输入条件下、期望什么、得到了什么"。这直接影响修复效率，也是 ROME 在复杂模块上需要更多修复轮次的根本原因。

### 3.4 输出

**最终产物**：
- 层次化 Verilog 子模块集合（如 6 个 mux 子模块 + 顶层）
- 顶层模块通过 testbench（判定成功的唯一标准）
- 每层 LLM 调用日志、Icarus 编译/vvp 仿真输出、错误反馈文本、修复轮次、wall-clock 时间

**成功判定**：`top module passes its testbench`。不涉及：
- formal equivalence（形式验证）
- PPA 门槛（面积/延迟/功耗全不评估）
- 代码覆盖率（行覆盖/分支覆盖/FSM 状态覆盖全不检查）
- 可综合性（不跑 Yosys/Design Compiler 综合）

### 3.5 处理器案例的具体输出

论文报告的 GPT-4 PGHP 生成 16-bit MIPS 处理器：
- **生成时间**：23 分 37.85 秒
- **初始 prompt**："Please define the necessary submodules in a 16-bit single cycle MIPS processor"
- **中间过程**：GPT-4 自动规划出 PC、ALU、Register File、Control Unit、Data Memory、Instruction Memory 等子模块，逐模块生成并过 Icarus 仿真
- **最终输出**：完整的层次化 Verilog 处理器，在 Vivado 中综合通过，波形验证 load/store/ADD/OR/SUBI 指令序列
- **人工介入**：论文声称该次运行"no human design intervention was required"——但因 wire/signal 命名不一致导致的接口修复在早期 MIPS/RISC-V 案例中是有人工介入的

### 4.3 Relay Prompt 的上下文压缩策略（论文 Figure 3）

```text
层次深度 ─────────────────────────────────────────────────►

子模块 1        子模块 2        子模块 3        子模块 4（当前）
[完整代码]      [完整代码]      [完整代码]      请求 LLM 生成

非 Relay（全量保留）：
prompt = [mod1 全文] + [mod2 全文] + [mod3 全文] + 当前请求
→ 上下文持续膨胀，短窗口模型（Llama 2 4K context）会溢出

Relay Prompt（论文方法）：
prompt = [mod1 接口行] + [mod2 接口行] + [mod3 全文] + 当前请求
                              ↑                    ↑
                    更早模块只留接口        最近模块保留完整代码

压缩效果：
  5-to-32 Decoder：3 层 → relay 只保留约 30% 的 token 量
  AES-128：8+ 层 → relay 节省 60%+ 的 prompt token
```

**设计直觉**：最近一层的完整代码提供"具体模板"（信号命名风格、实例化模式、逻辑组织方式），更早模块的接口行提供"可用模块清单"（LLM 知道可以实例化哪些模块）。这类似于人类工程师写顶层模块时：只翻阅子模块的 port list，不需要重读子模块的完整实现。

## 5. 关键公式

### 5.1 pass@k 无偏估计

这是 ROME 论文使用的唯一数学公式（论文 Equation 2），其背后是 LLM token 生成的 autoregressive 形式（论文 Equation 1）：

$$
y_n = \arg\max_{v \in V} P_\phi(v \mid \vec{x}, \vec{y}_{<n})
$$

- $\phi$：模型参数
- $\vec{x}$：输入 token 向量
- $\vec{y}_{<n}$：前 $n-1$ 步已生成的输出 token
- $V$：词表
- $y_n$：第 $n$ 步输出的 token

该迭代持续到 end-of-sequence token 出现。

论文 Equation 2 定义了 pass@k 指标：

$$
\text{pass@}k = 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}
$$

- $n$：每个 model-method-module 组合的独立生成次数（论文中 $n=10$）
- $c$：其中成功通过 top-level testbench 的次数
- $k$：成功阈值（论文报告 $k=1$ 和 $k=5$）
- $\binom{n-c}{k}$：从 $n-c$ 个失败样本中选 $k$ 个的组合数
- $\binom{n}{k}$：从全部 $n$ 个样本中选 $k$ 个的组合数

**工程直觉**：$\binom{n-c}{k} / \binom{n}{k}$ 是"从 $n$ 次运行里抽 $k$ 次，全都是失败"的概率，$1-(\cdot)$ 就是"至少一次成功"的概率。这是 Codex/HumanEval 引入的标准做法，用于消除单次采样的方差。

当 $k=1$ 时退化为：

$$
\text{pass@}1 = 1 - \frac{n-c}{n} = \frac{c}{n}
$$

即成功率的期望。所以看到 "ROME GPT-4 H pass@1=0.9 on Mux" 时，正确理解是：**10 次独立运行中 9 次成功**。

**为什么用 pass@5**：当 $n=10$ 时，pass@1=0.1（1 次成功）对应 pass@5=0.5；pass@1=0.5（5 次成功）对应 pass@5=0.996。pass@5 快速接近 1.0——这不是因为模型特别强，而是统计上的必然。组会上不能把 "pass@5=1.0" 说成 "每次都成功"。

**两层"迭代"的区别**（容易混淆）：

```text
一次 run 内部：子模块生成 → 编译失败 → 错误回灌 → 重新生成 → ...
               最多 10 轮内循环修复（per 子模块）

十次 run 之间：独立重复整条 hierarchy pipeline 10 次
               统计成功/失败 → 计算 pass@1 / pass@5
```

论文 Table 1 里的 pass@k 是 **10 次 run 间的统计**，不是一次 run 内 10 次修复的结果。

### 5.2 Relay Prompt 的上下文压缩比（本文推导）

论文没有显式给出公式，但 relay prompt 的压缩逻辑可以形式化。设层次深度为 $D$，第 $i$ 层模块的代码长度为 $L_i$（token 数），接口行长度为 $I_i \ll L_i$。非 relay（全量保留）的总 prompt 长度为：

$$
P_{\text{full}} = \sum_{i=1}^{D-1} L_i + P_{\text{current}}
$$

Relay prompt 的总长度为：

$$
P_{\text{relay}} = \sum_{i=1}^{D-2} I_i + L_{D-1} + P_{\text{current}}
$$

压缩比近似为：

$$
R = \frac{P_{\text{relay}}}{P_{\text{full}}} \approx \frac{\sum I_i + L_{D-1}}{\sum L_i}
$$

以 AES-128 为例（论文提到 "hundreds of lines of code"），$D \approx 8$，$L_i \approx 50\text{-}200$ tokens。Relay 只保留最后一个模块的完整代码和其余 6 个模块的接口行（每个约 5-10 tokens），$R$ 可能在 0.3-0.5 之间。

**为什么只保留最近一层的完整代码**：这来自硬件的**层次实例化模式**。当 LLM 写 `mux32_1` 时，它真正需要参考的不是 `mux2_1` 的具体 `assign out = sel ? in2 : in1`（已经太基本了），而是上层 `mux16_1` 的端口命名风格和实例化结构。`mux2_1` 只需要知道"这个模块存在、接口是什么"就够了。Relay 正是捕获这种**层次距离和信息需求的衰减关系**。

### 5.3 层次化延迟节省（论文 Figure 4）

论文 Figure 4 报告的 average % latency reduction：

$$
\Delta_{\text{time}} = \frac{T_{\text{NH}} - T_{\text{H}}}{T_{\text{NH}}} \times 100\%
$$

其中 $T_{\text{NH}}$ 和 $T_{\text{H}}$ 分别是非层次化和层次化的平均 wall-clock 时间（跨所有模型）。

| Benchmark | $\Delta_{\text{time}}$ |
|-----------|-----------------------:|
| 5-to-32 Decoder | 44.31% |
| 64-to-1 Multiplexer | 45.59% |
| 4x4 Systolic Array | 69.98% |
| UART | 70.39% |
| AES Block Cipher | 73.73% |
| 32-bit Barrel Shifter | 85.41% |

**为什么更难的模块节省更多**：flat prompting 在复杂模块上频繁失败，每次失败后 LLM 被要求重新生成**整段长代码**——这就是主要的时间黑洞。层次化后，错误被限制在短子模块内，重新生成的代码量小得多。同时，子模块通过后就不需要再动，flat prompting 却每次都要重写全部内容。

**wall-clock 包含什么**：LLM 推理时间（本地 GPU 或远程 API）+ Icarus 编译/仿真时间 + 网络延迟 + 多轮修复时间。所以 $\Delta_{\text{time}}$ 不是纯算法复杂度，受模型推理速度和 API 延迟的显著影响。

论文 Table 4 以 GPT-3.5 tokenizer 定价计算的成本对比：

| 模块 | H 输入 tokens | H 输出 tokens | H 成本 | NH 输入 | NH 输出 | NH 成本 | 节省% |
|------|-------------:|-------------:|-------:|--------:|--------:|--------:|------:|
| Multiplexer | 92 | 2,376 | $0.00484 | 91 | 3,283 | $0.00666 | 27.23% |
| 32-bit Barrel | 262 | 1,977 | $0.00422 | 191 | 4,268 | $0.00873 | 51.69% |

**读法**：层次化提示的输入 token 略多（因为要描述层次结构），但输出 token 大幅减少（因为每次只生成一个短子模块而非整段长代码）。注意这些数字基于 2024 年初 GPT-3.5 的定价（$0.0015/1K input, $0.002/1K output），不能直接用于当前 API 成本估算。

## 6. 训练与实验设置

### 6.1 是否需要训练

**ROME 方法本身不需要训练。** 它是一个 prompting + 工具反馈的 pipeline，不训练新模型、不更新权重。全部收益来自推理时编排（inference-time scaling），调用现成 LLM（6 个开源 + 2 个闭源），不做 SFT/RL/DPO。

论文中使用了一个作者自己微调的模型 **CL-Verilog**（基于 Code Llama-13B 在 Verilog 语料上微调）作为参赛模型之一。该模型需要额外微调，但论文未披露具体训练数据规模与超参数。ROME pipeline 本身不依赖任何微调即可工作。

### 6.2 实验设置

**8 个被评测模型**：

| 模型 | 参数 | 开源/闭源 | 定位 |
|------|------|:---:|------|
| Llama 2 | 13B | 开源 | 通用文本模型 |
| Code Llama | 13B | 开源 | 代码模型 |
| VeriGen | 16B | 开源 | Verilog 微调模型 |
| CL-Verilog | 13B | 开源 | 作者微调 Code Llama-Verilog |
| RTL-Coder | 7B | 开源 | Verilog/RTL 专用模型 |
| Llama 3 | 8B | 开源 | 新一代通用模型 |

**推理配置**：temperature=0.5，top-p=0.9。开源模型在单张 NVIDIA A100 80GB GPU 上推理，GPT 系列通过 OpenAI API 调用。

**6 个 Benchmark**（均提供 HDHP 下的子模块 unit test）：

| Benchmark | 层次结构 |

**评估指标**：
- **pass@k**（k=1, 5）：标准无偏估计公式，n=10
- **wall-clock time**：LLM 推理 + Icarus 编译/仿真 + 网络延迟 + 多轮修复的总时间
- **token cost**：基于 2024 年初 GPT-3.5 tokenizer 定价的 API 费用估算
- **hierarchy planning accuracy**：PGHP 模式下 LLM 生成的层次计划与人工 golden plan 的匹配比例（20 次迭代统计）
- **平均延迟下降百分比**：$(T_{\text{NH}} - T_{\text{H}}) / T_{\text{NH}} \times 100\%$

## 7. 创新点

### 创新点 1：层次化提示作为复杂 RTL 生成的第一等方案

这是 ROME 最硬的一个贡献。论文不是第一个在 EDA 领域用 LLM 的工作，也不是第一个用层次化的（RTLLM self-planning 有"计划"概念），但 ROME 是第一个**把硬件层次化设计做成完整的自动化 pipeline**——从 hierarchy extraction 到逐层 tool feedback 到顶层集成，每一步都工程化。

消融实验设计得干净：**NH 基线也使用了同样的 tool feedback loop**，区别只在 prompt 是否包含层次信息。因此 NH → H 的提升**纯粹来自 hierarchy**，不是来自"有工具反馈 vs 没有"。

### 创新点 2：HDHP vs PGHP 的系统性分离

论文不把"人给架构"和"模型自创架构"混为一谈，而是作为两种独立的 modality 分别评测。这是实验设计的亮点。

HDHP 的结果（Table 1）展示了"模型实现能力"的上限——如果架构是对的，LLM 能执行到什么程度。

PGHP 则暴露了更根本的问题：**自动生成合理硬件架构比写 Verilog 代码更难**。论文 Table 2 表明，除 GPT-4 外，所有模型在自动架构规划上表现极不稳定——"理解系统该怎么拆分"和"写出正确的 Verilog"是两个难度不在同一量级的能力。

论文 "golden plan" 匹配标准的局限：不同但功能等价的架构（如 barrel shifter 用不同 stage 组合）可能被判为"不匹配"，导致 accuracy 被低估。

### 创新点 3：Relay Prompting —— 为短上下文模型设计的上下文接力

论文 Section 3.3 专门为 text-completion LLM（非对话式、短上下文窗口）设计了 relay prompt 技术。这在 2024 年初非常有现实意义：大多数开源模型（Llama 2/3、Code Llama）是 text-completion 模式，上下文窗口 4K-8K tokens，深层层次（如 AES 的 8+ 个子模块，每个几十到几百行）的全量 prompt 会溢出。

Relay 的核心思想：**最近一层的完整代码是"模板"，更早层的接口行是"零件清单"**。LLM 不需要知道 `mux2_1` 的 `assign out = sel ? in2 : in1` 来生成 `mux64_1`——它只需要知道 `mux32_1` 的端口命名和实例化风格，以及有哪些下层模块可用。

论文 Table 1 中开源模型在 H 下的成功，相当程度上是 relay prompting 的功劳——没有 relay，这些模型的上下文窗口根本装不下 AES 的全量层次 prompt。

### 创新点 4：让"写不了 HDL 的通用模型"能参与复杂硬件设计

这是 Table 1 最具冲击力的结论之一。Llama 2 是一个**通用文本模型，从未在 Verilog 语料上训练**。NH 下它连一行正确 Verilog 都写不出（所有 benchmark pass@1=0.0）。但层次化提示后，它在 Mux、Decoder、UART 上出现了 0.2-0.5 的 pass@1。

机制的解读：
- NH 下的原文 prompt 太长（全模块规格几百 token），模型注意力被稀释
- 层次化后每个 prompt 只作用于一个几十 token 的子模块接口，"问题规模"压缩到模型的解题能力范围内
- 子模块之间的接口由人固定，LLM 不需要理解跨模块协议——它只需要把给定的 I/O 连起来

**这个结论的推论是**：ROME 增益最大的不是在最强模型上，而是在弱模型 + 人给架构的组合上。对于"已经有一个人类架构师、想用 LLM 加速实现"的场景，ROME 的 HDHP 是最佳匹配。

### 创新点 5：首个无人类设计干预的 LLM 生成处理器

论文 Section 6 报告了用 GPT-4 PGHP 在 23 分 37.85 秒内生成一个 16-bit single-cycle MIPS 处理器，声称"the first-ever purely LLM-designed processor with no human feedback"。

这个声明的精确含义：
- 初始 prompt 只有一句："Please define the necessary submodules in a 16-bit single cycle MIPS processor"
- 所有子模块定义、接口设计、wire/signal 命名由 LLM 自行决定
- 错误处理全自动——工具反馈回灌 LLM，无人中途给提示
- 最终产物在 Vivado 中综合通过，波形验证通过

但这个声明有几个需要标注的边界：
- ROME pipeline、system prompt、testbench、parser 本身**是人工构建的**
- "no human feedback"指的是**生成过程中**无人类逐步介入，不是整个系统无人类设计
- 论文早期 MIPS/RISC-V 案例（GPT-3.5/Code Llama-Verilog）**有人工介入**：wire/signal 命名需要人工统一、control unit 等模块需人工明确请求
- 这次 GPT-4 PGHP 的成功是"该次运行"的成功，不代表可以稳定复现
- LLM 生成的 opcode 编码与标准 MIPS ISA **不完全一致**（论文 Figure 7 说明）

|------|------|--------|
| **LLM** | Large Language Model（大语言模型） | 本文实测 8 个模型：Llama 2/3、Code Llama、VeriGen、CL-Verilog、RTL-Coder（6 个开源）+ GPT-3.5/GPT-4（2 个闭源） |

## 9. 与芯片流程的关系

### 9.1 在全流程中的位置

```text
  人写顶层规格 + （HDHP 时）人给层次架构 + 人准备 unit testbench
             │
             ▼
┌─────────────────────────────────────────────────────┐
│  ① RTL 设计    ←───────────┐                        │  ← ROME 在这两格间
│        ↓                   │                        │     自动循环，
│  ② RTL 功能仿真 ───────────┘                        │     逐子模块推进
│    （Icarus 编译 + vvp 仿真）                        │
│                                                      │
│  层次化特有：外循环（→ 下一子模块）+ 内循环（修复）  │
└────────────┬────────────────────────────────────────┘
             │  交接面：ROME 到此为止，后面靠人
             ▼
   ③ 逻辑综合  ← 第一道可能推翻 ROME 成果的关卡
             ▼
   ④ 门级仿真  ← 第二道
             ▼
   ⑤ STA  ⑥ 形式验证  ← 第三道
             ▼
   ⑦ Floorplan → ⑧ Placement → ⑨ CTS → ⑩ Routing
             ▼
   ⑪ 后仿真 → ⑫ DRC/LVS → ⑬ Signoff → ⑭-⑰ 流片到芯片
```

### 9.2 「功能仿真通过」和「能做成芯片」之间隔着什么

ROME 的 success 条件只要求 top module passes its testbench。以下每种情形都会在后续流程中被拦截：

**在阶段 ③ 逻辑综合被拦下的**：

```verilog
// 情形 A：用 initial 赋初值 —— 仿真器认，ASIC 综合器不认
reg [3:0] count;
initial count = 0;         // ✅ Icarus 跑得好好的
                           // ❌ Design Compiler: Error, initial not synthesizable

// 情形 B：组合逻辑环 —— 仿真可能收敛，综合必炸
assign a = b & c;
assign b = a | d;          // ❌ 组合环，STA 无法分析，综合报错

// 情形 C：无意中产生 latch —— 仿真可能"恰好对"
always @(*) begin
  if (sel) out = in;       // ❌ 缺 else → 综合器推断 latch
end                        //    仿真在 sel=1 时行为正确，sel=0 时 out 保持旧值
                           //    可能符合 testbench 的输入模式，但不符设计意图

// 情形 D：不完整敏感列表（Verilog-2001 风格）
always @(a) y = a & b;     // ❌ 少了 b。仿真和综合行为不一致
                           //    仿真：b 变化不触发 always
                           //    综合：组合逻辑自然包含 b → 行为不一致
```

**在阶段 ④ 门级仿真被拦下的**：

```verilog
// 情形 E：阻塞赋值写时序逻辑 —— RTL 仿真可能碰巧对，门级仿真必错
always @(posedge clk) begin
  q1 = d;                  // 应该用 <=
  q2 = q1;                 // RTL 零延迟仿真：q2 得到 d 的新值
end                        // 门级仿真（有 SDF）：q2 可能得到旧值 → 行为不一致

// 情形 F：跨时钟域无同步器
always @(posedge clk_b) sync_data <= data_from_clk_a;
                           // RTL 零延迟仿真完全看不出问题
                           // 门级仿真：亚稳态、建立/保持违例
```

**在阶段 ⑤ STA 被拦下的**：

ROME 生成的子模块之间可能有极深的组合逻辑路径。比如 LLM 写的 `mux64_1` 可能实例化一层层的 `mux2_1`，形成 6 级 MUX 级联——仿真完全正确，但路径延迟累加后在目标频率下 setup violation。ROME 对此**完全无感知**，因为：
- prompt 里没有时钟周期约束
- 反馈环里没有 STA 工具
- success 条件不包含任何 timing 检查

**在层次化层面特有的问题**：

```verilog
// 情形 G：子模块间接口命名不一致（PGHP 常见失败模式）
// 子模块 A 的输出：wire [7:0] data_out;
// 子模块 B 的输入：wire [7:0] d_out;
// → 顶层集成时 LLM 可能用错名字，导致仿真失败或功能错误

// 情形 H：层次实例化的端口连接错误
mux2_1 m1(
  .in1(in[0]),
  .in2(in[1]),
  .select(sel[0]),
  .out(out1)
);
// 如果子模块的端口顺序被 LLM 记错（如 .select 和 .out 颠倒），
// Icarus 编译能通过（按位置绑定），但功能全错
```

### 9.3 为什么 ROME 对"弱模型"效果更好——一个反直觉解释

ROME 的一个关键现象是：**NH 下全 0 的弱模型，H 下能达到 0.4-0.8 pass@1**。这不能简单解释为"层次化让难题变简单"。

更深层的解释是：**弱模型在 NH 下的失败不是"写不对"，而是"写不完"**。当 prompt 要求一次性生成包含多层逻辑的长代码时，弱模型的 token 生成过程会在中途"迷失"——语法的局部正确性无法维持到模块末尾。层次化把"长代码生成"分解成"多次短代码生成"，每次的任务粒度落在弱模型的可靠输出长度之内。

这就解释了为什么 GPT-4 在 NH → H 的提升（+0.6 pass@1 on average）绝对值上小于弱模型（Llama 2: +0.25, Code Llama: +0.56）：**GPT-4 本身就能稳定生成长代码，层次的增益来自"更好的组织"而非"更短的任务"**。而对于弱模型，层次的增益主要来自后者。

### 9.4 ROME 用到的工具在流程中的角色

| 工具 | ROME 中的用法 | 在真实芯片流程中的地位 |
|------|--------------|----------------------|
| `iverilog` | 编译当前子模块 + prior modules + testbench | 相当于阶段 ② 的 lint 工具。工业界用 VCS/Xcelium/Questa，功能相同但支持 SystemVerilog/UVM、覆盖率、断言 |
| `vvp` | 执行仿真，检查 stdout 是否含 "passed!" | 阶段 ② 的仿真引擎。ROME 不检查 return code，不设 timeout，不验证仿真完整性 |
| Vivado | processor case study 中综合生成的 MIPS/RISC-V（非 pipeline 内闭环） | 阶段 ③ 的 FPGA 综合工具。ROME 只用它验证"生成的处理器确实可综合"，不用它的输出做反馈 |

## 10. 讨论与局限

### 10.1 论文自述的局限

1. **PGHP 层次规划是瓶颈**：除 GPT-4 外，多数模型在自动生成合理硬件架构上不稳定，容易漏模块或加多余模块。这说明 LLM 在硬件领域的两种能力之间有巨大落差——局部的 Verilog 语法生成（中等模型就能做）vs 系统的架构分解（需要非常强的抽象推理）。

2. **AES 对所有模型仍极难**：即使层次化 + 工具反馈，AES pass@1 最高仅 0.5（GPT-4 H），PGHP 为 0。

3. **工具反馈粒度过粗**：ROME 的 feedback 是 Icarus 编译器的 stderr 原始输出或仿真 mismatch 的汇总行。对比 MAGE 的 State Checkpoint（逐拍 `$display` 完整信号快照），ROME 的反馈信息分辨率低得多，直接影响修复效率。

4. **成功标准的结构性盲区**：
   - 没有覆盖率概念（行覆盖/分支覆盖/FSM 状态覆盖/toggle 覆盖全不检查）
   - 所有 testbench 等权，跨 benchmark 的 pass@1 不可直接比较
   - 子模块 unit test 的"局部正确性"不保证集成的"全局正确性"，ROME 没有跨模块的根因定位机制

5. **计算成本不透明**：论文没有报告任何 token 消耗总数、API 成本总和或 total wall-clock time 对比。粗略估算：8 模型 x 6 benchmark x 2 方法(NH/H) x 10 runs x 最多 70 次 LLM 调用 per run = 理论上限约 67,200 次 LLM 调用。

6. **Relay Prompt 的信息损失未量化**：论文没有消融实验回答保留完整代码 vs relay 的 pass@1 差异、哪些模块最依赖完整历史上下文、relay 在什么层次深度下开始出现信息损失。

7. **Benchmark 污染风险**：ROME benchmark 是作者自建的，与 VerilogEval（从 HDLBits 公开题库构建）不同，但 paper 没有讨论数据污染问题，也没有在 RTLLM 或 VerilogEval 上做跨 benchmark 验证。

8. **Single-cycle Processor 声明的边界**：该次运行的成功不代表该能力可复现（只报告了一次 run，没有 n=10 统计），验证只在 Vivado 综合通过 + 波形显示少数指令序列正确，离"完整处理器验证"差距巨大。

### 10.2 代码/复现层面的问题

根据本地代码审计（详见 [ROME论文与代码复现详解.md](./ROME论文与代码复现详解.md)），当前仓库存在以下与论文方法不一致的地方：

1. **默认模型漂移**：当前 notebook 默认模型为 `gpt-5.2`，并支持 Claude/Gemini wrapper，论文使用的是 GPT-4/3.5。

2. **OpenAI wrapper 丢失 system/assistant roles**：所有消息都被标记为 `role: "user"`，破坏了对话交替结构。

3. **Repair context 截断过度**：修复时丢弃原始 design prompt、testbench 原文、prior hierarchy modules 上下文，只保留上一次当前模块 RTL 和最近 compiler/simulation 输出。

4. **未实现 relay compression**：当前实现把全部 prior modules 完整代码放入 prompt，而非论文描述的 relay（最近一层完整代码 + 更早层仅接口）。

5. **Icarus warning 被当作 failure**：任何 stderr 输出（包括无害 warning）都导致进入 repair loop。不检查 vvp return code，success marker 用子串匹配 `"passed!"` 可能误判。

6. **无 timeout 机制**：API、Icarus、vvp 均无超时保护。

7. **最大迭代 off-by-one**：`max_iterations=10` 实际生成 iteration 0-10，共 11 次。

8. **缺少论文批量复算器**：没有 n=10/pass@k/wall-clock 的自动聚合脚本，也没有论文 8 模型统一 runner。

9. **仓库缺少生成产物**：仓库当前无生成 RTL、运行日志、processor case output 或论文结果表。

10. **当前 benchmark 已扩展**：论文只报告 6 个 benchmark，当前目录有 13 个 testbench 家族、92 个 `.v` testbench 文件，新增了 Conv 1D/2D/3D、Harris corner、RCA-32、Unsharp mask 等，但这些新 benchmark 没有配套 hierarchy plan 或运行结果。

### 10.3 本资料包的批判性分析

1. **方法的隐含前提**：ROME 假设"可以把任何复杂硬件分解为线性依赖序列的子模块"——这对 Mux/Decoder 成立，但对有循环依赖或复杂握手协议的模块（如 cache coherence、总线仲裁）不成立。

2. **评测的公平性**：NH 基线也使用了工具反馈，对比设计是干净的。但 testbench 的充分性没有统一标准——Decoder 的 testbench 可能覆盖全部输出编码，AES 的 testbench 不可能覆盖全部 2^128 种输入。

3. **可扩展性天花板**：ROME 的收益来自"人能给出正确的层次分解"。当设计规模大到人类架构师也无法一次性给出完备层次时（如多核 SoC、复杂 NoC），HDHP 模式本身就失效了，而 PGHP 模式当前只有 GPT-4 级别模型可用。

4. **PPA 的完全缺失**：ROME 的 success = testbench pass，但真实芯片设计的核心约束是 PPA。GPT-4 层次化生成的 `mux64_1` 用 6 级 2:1 MUX 级联——功能对，但延迟是 6 级门延迟之和。人类工程师在高频设计里会用更平衡的树结构。ROME 对此完全无感知且无反馈机制。

5. **与 MAGE 的反馈粒度差距**：ROME 的 error feedback 是 Icarus 的原始 stderr，MAGE 是逐拍的完整信号快照（State Checkpoint）。在修复效率上，ROME 天然处于劣势。

## 12. 一分钟复述版

ROME（NYU，MLCAD 2024）是一个**不训练模型的层次化 RTL 生成与修复 pipeline**。核心四招：

1. **层次分解替代一次生成**：复杂 RTL 拆成依赖顺序的子模块列表（HDHP 人给架构 / PGHP LLM 自创架构），逐模块生成 + Icarus 编译/仿真 + 错误回灌修复，通过后才进入下一层，最后顶层集成。6 个 benchmark 上 8 个模型全部改善——Llama 2 从 NH 全 0 拉到 H 部分有效，GPT-4 H 在 Decoder 上达到 pass@1=1.0。

2. **Relay Prompting**：为短上下文文本补全模型设计的上下文压缩——最近一层保留完整代码提供"模板"，更早模块只保留接口行提供"零件清单"。这是开源小模型能处理深层层次（如 AES 8+ 层）的关键使能技术。

3. **PGHP 暴露架构规划比写代码更难**：只有 GPT-4（Decoder 1.0, Mux 0.85, Barrel 0.35）能自动生成合理的硬件层次计划。其余模型准确率 0.00-0.25——"理解系统该怎么拆分"和"写出正确的 Verilog"是两个难度不在同一量级的能力。

4. **错误局部化 + 工具反馈闭环**：每个子模块的编译/仿真错误独立修复，不会像 flat prompting 那样"改了 A 处坏了 B 处"。层次化还大幅节省时间（延迟降低 44%-85%）和 token 成本（节省 27%-59%）。

**边界**：只覆盖流程阶段 ①②（2/17），success=testbench pass，不管综合/PPA/覆盖率/形式验证，PGHP 只在 GPT-4 上可用，processor case study 的可复现性未验证，当前代码 artifact 已漂移到新模型和 provider 且与论文方法有多处不一致。
