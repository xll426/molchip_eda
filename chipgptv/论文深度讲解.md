## 1. 一句话定位

**ChipGPT-V 是一个多模态 Verilog 生成 benchmark 与框架：它证明电路结构图能补充自然语言难以表达的拓扑信息，图文联合输入在 GPT-4V 上将功能成功率从 46.88% 提升到 71.81%（+24.93 pp），同时在 LLaMA/LLaVA 系列上从 13.41% 提升到 25.88%（+12.47 pp）。它不是带权重的自研视觉语言模型，而是调用 GPT-4V/GPT-4/LLaVA/LLaMA 等外部模型进行评测的 benchmark + VLMQL 查询语言框架。**

这句话里的五个承重点，后面逐一拆解：

1. **多模态 benchmark：首次系统比较纯文字与图文联合对 RTL 生成的影响** — 之前所有 benchmark（VerilogEval、RTLLM）都是纯文字输入，ChipGPT-V 第一个引入电路结构图作为视觉输入，构造了 arithmetic / logic / advanced 三层复杂度、simple / medium / complex 三档 prompt 的分层评测体系。

2. **图文职责划分：图负责拓扑和连接，文负责功能和时序** — 电路图提供模块层次、空间位置、端口位宽和连线关系，自然语言提供模块功能、寄存器行为、reset 极性、clock edge 和运算规则。论文通过 image-only 消融实验证明纯图远不如图文联合（GPT-4V V-only 33.90% vs V+T 71.81%），说明两个模态互补。

3. **GPT-4 系列图文增益显著，LLaMA 系列也有提升但绝对值仍低** — GPT 系列 function 46.88% → 71.81%，syntax 68.75% → 84.38%；LLaMA 系列 function 13.41% → 25.88%，syntax 21.88% → 34.38%。增益存在于不同能力层次的基座模型上，但能力差距本身也很明显。

4. **VLMQL 查询语言：形式化多模态 prompt 工程** — 提出用 Python 风格声明来描述 mode（gate-level / algorithm-level / function-block-level）、模型选择、图像路径、功能描述、EDA 工具流程和输出约束，编译为 prompt 输入 VLM。当前仓库实现为 62 行 prompt printer 原型。

5. **Benchmark 的可信性取决于 evaluator 和 testbench 的严格性** — 当前 evaluator 只能输出 20% 倍数的分数，不能复算论文 Table 3 的 98%/34%/10% 等 testcase ratio；多个 testbench 存在静态 bug（adder_32bit 正误都累加 error、parallel2serial 无功能检查等）。论文结果在概念上成立，但数字的严格可复现性受限于代码和 oracle 质量。

## 3. 输入 / 输出

这节要解决的核心问题：ChipGPT-V 的 benchmark 具体接受什么输入、产出什么输出，以及三种任务形式之间的区别。

### 3.1 输入

ChipGPT-V 的输入是**多模态**的——核心思想是"自然语言 + 电路结构图"共同描述硬件规格。

**文字部分（三档 prompt 复杂度）**：

- **simple**：几乎只有电路图，文字极少，主要依赖图来传达设计意图
- **medium**：图 + 简洁核心功能描述
- **complex**：图 + 完整硬件细节（寄存器规格、时钟边沿、端口位宽、运算规则）

三档 prompt 的文件命名约定：
```
simple_design_description.txt   / gpt4_simple_design_description.txt
medium_design_description.txt   / gpt4_medium_design_description.txt
design_description.txt          / gpt4_design_description.txt
```

其中带 `gpt4_` 前缀的是纯文本基线版本（不含图像引用），不带前缀的是图文联合版本。

**图像部分**：

- 格式：PNG 格式的 `Circuit_Structure.png`
- 内容：模块框图、端口标注、内部连线、位宽标注、模块名称
- 举例：FSM 状态转移图（6 个状态、输入为 0/1 时有向边、MATCH 输出）、5-stage pipeline 框图（Fetch→Decode→Execute→Memory Access→Writeback）、4x4 spatial accelerator 结构图（16 个 PE + PE 内部结构）

**完整生成任务的具体输入例子**（以 FSM 为例）：

```text
[Circuit_Structure.png — 一个 6 状态 FSM 图，标注 S0~S5 及转移边]

Implement a FSM detection circuit that detects a single bit input
IN with verilog. When the input is 10011, output MATCH is high,
and MATCH is 0 in other cases. The state transfer diagram is shown
in the picture. Understand the state transfer diagram shown in the
picture first and then give me the verilog code.
```

**代码补全任务**的额外输入：reference RTL 的一个 prefix（从 reference Verilog 随机截断），要求模型从截断点续写。

**next-token 任务**的额外输入：reference RTL 的一个 prefix，要求模型只预测紧接的下一个 token。

**三种模态配置**：
- **V+T**：Vision + Text，图文联合输入（主要评测对象）
- **T**：Text-only，仅自然语言（纯文本基线）
- **V**：Vision-only，仅电路图（消融实验）

### 3.2 中间产物

对于原生 VLM 路线，中间产物包括：
- VLM vision encoder 输出的视觉 embedding / visual tokens
- 与文字 token 在 language decoder 中融合后的中间表示

对于可移植文本投影路线（后续工作），中间产物包括：
```
projector_description.txt → 结构化文本 IR，格式如:
"Module top has ports a[3:0] input, b[3:0] input, y[3:0] output.
Internal wires: n1-n8. AND gate u1: a[0],b[0]→n1 ..."
```

### 3.3 输出

- **完整 Verilog RTL**：`module ... endmodule`，可经 Icarus Verilog 编译
- **代码补全片段**：给定 RTL prefix 后的后续代码
- **next-token 预测**：下一个词法 token
- **评测结果**：
  - Syntax success：5 次生成中无语法错误的比例（以 32 题数量为分母的通过率）
  - Functionality success：5 个候选中表现最好的 Verilog 的 testbench pass rate（pass@5 best-candidate）
  - Next-token accuracy：3 个 prefix 上预测下一个 token 的精确匹配率（4 档：0%/33%/67%/100%）

**输出实例**（GPT-4V V+T 生成的 FSM，功能正确）：

```verilog
module fsm(
    input clk, rst, IN,
    output reg MATCH
);
    ...
    always @(*) begin
        ...
        case(current_state)
            ...
            S2: begin
                if (IN == 1'b0) begin
                    next_state = S3;
                end else begin
                    next_state = S1;
                end
            ...
            endcase
        end
    ...
endmodule
```

对比纯文本 GPT-4 生成的 FSM 在状态转移处出错（如 `S2: next_state = IN ? S3 : S0` 把回退边 S2→S0 丢了），导致 testbench 不通过。

## 4. 方法与架构

这节要解决的核心问题：ChipGPT-V 的 benchmark 框架是怎么运转的，两条技术路线各自的数据流是什么。

### 4.1 整体 Pipeline

论文定义了端到端视觉-语言硬件协同生成工作流（对应论文 Figure 6）：

```text
┌─────────────────────────────────────────────────────────────────┐

│    .png           ─┤                                            │

│  Reference_RTL.v   │                                            │
│                    ▼                                            │
│          ┌──────────────────┐                                   │
│          │  Multi-Modal     │                                   │
│          │  Large Model     │──→ RTL.v                          │
│          │ (GPT-4V/GPT-4/  │                                   │
│          │  LLaVA/LLaMA)   │                                   │
│          └──────────────────┘                                   │

### 4.2 核心模块逐个详解

#### 模块一：原生视觉语言模型路线（路线 A）

这个模块的存在的理由：当电路图作为图像输入时，VLM 的 vision encoder 能否直接从像素中提取拓扑结构并生成正确 Verilog。

```text
文字设计说明 + PNG 电路图
        │
        ▼
VLM 的 vision encoder（外部模型，如 GPT-4V）
        │
        ▼
视觉 token / 视觉 embedding
        │
        ▼
与文字 token 在 language decoder 中融合
        │
        ▼
自回归生成 Verilog tokens
        │
        ▼
提取 ```verilog 代码块 → .v 文件
        │
        ▼
iverilog 编译 → vvp 仿真
        │
        ▼
Syntax / Function / Next-token 指标
```

**关键实现细节**：
- 使用 OpenAI API `gpt-4-vision-preview` 模型，`max_tokens=3000`
- 图片通过另一个 GitHub 仓库的 raw URL 传入（https://raw.githubusercontent.com/rong-hash/chipgptv\_img/main/\<instance\>.png），不是本地文件
- 每次实验对每个设计采样 5 次（`iter = {"default": 5, "complete": 3, "predict": 3}`）
- Verilog 提取器搜索 <code>&#96;&#96;&#96;verilog … &#96;&#96;&#96;</code> 代码块
- vision encoder 细节不在仓库中，因为 GPT-4V 是闭源模型

#### 模块二：可移植文本投影路线（路线 B，后续工作）

这个模块的存在的理由：避免为每个基座 LLM 都训练一个 vision-language connector——先通过传统 CV/OCR 管线把图片转成结构化文本 IR，再交给纯文本 LLM。

```text
电路图 / 表格 / 波形
        │
        ▼
传统 CV 管线:
  ├─ OCR 文字提取（提取图中端口名、模块名、位宽标注）
  ├─ Canny 边缘检测（提取线条边界）
  ├─ 连通组件分析（识别逻辑门符号形状）
  └─ 拓扑重建（追踪连线，确定门间连接关系）
        │
        ▼
projector_description.txt（结构化文本 IR）
        │
        ▼
拼接用户 specification
        │
        ▼
RTL-Coder 或经 SFT/DPO 的 Llama 3.1
        │
        ▼
Verilog / testbench → 编译仿真
```

**关键实现细节**：
- `verilog_parse/mmdata_generation.py` 可以从已有的 instruction-Verilog pair 出发，经 Yosys 综合→网表 JSON→解析端口/单元/连接→绘制 PNG 电路图→保留原 RTL 作为 SFT target
- 真正的 projector/ 目录（从任意图片 OCR/边缘检测到 IR）当前 commit 中缺失
- README 引用的 finetune/、dpo/ 目录在 commit `52ef98d` 中也不存在
- 这条路线的代价：OCR 或连线识别错误会先丢失信息，且 LLM 无法从原图恢复

#### 模块三：VLMQL 查询语言

这个模块的存在的理由：把多模态 prompt 工程从"手工拼字符串"形式化为可声明、可复用的框架，降低 token 消耗。

VLMQL（Verilog Large Model Query Language）的核心声明：

- `mode`：三级视觉抽象 — gate-level / algorithm-level / function-block-level
- `model`：VLM/LLM 选择 — `vlmql.lvm("gpt4v")` / `vlmql.llm("gpt4v")`
- `image_path`：输入电路图路径
- `function`：模块功能自然语言描述（可多行，每行一个模块的功能/端口描述）
- `eda_tool` / `eda_flow`：后端工具选择与约束（如 `siliconcompiler`，面积约束等）
- `module_constraint`：指定只生成哪个子模块，避免额外 token 消耗

论文 Figure 7 的例子（5-stage pipeline 的 execute stage 生成）：

```python
@vlmql.function
def pipeline_5stage():
    vlmql.set_mode("func_block")
    vlmql.lvm("gpt4v")
    vlmql.llm("gpt4v")
    vlmql.image_path("5stage.png")
    vlmql.function(
        "The image show a 5 stage pipeline to add two number",
        "the execution stage add two number from register r1 and register r0",
        "the write back stage write the result to register r2"
    )
    vlmql.eda_flow("the area should large than (1000,1000)")
    vlmql.eda_tool("siliconcompiler")
    vlmql.module_constraint("execute stage")
    return vlmql.run()
```

**当前代码实现与论文的差距**：仓库中 `vlmql.py` 仅 62 行，`run()` 只做 `print()` 输出 prompt 文本，没有 parser、AST、compiler IR、模型调用、EDA tool 执行、constraint checker 等组件。这是概念原型，不是完整 compiler/runtime。

### 4.3 模块职责矩阵

| 模块 | 输入 | 输出 | 用到的模型/工具 | 是否需训练 |
|------|------|------|----------------|:---:|
| 完整 Verilog 生成 | 文字描述 + PNG 电路图 | `module...endmodule` .v 文件 | GPT-4V (API) | 否 |
| 纯文本对照 | gpt4\_\*\_description.txt | Verilog .v 文件 | GPT-4 (API) | 否 |

## 5. 关键公式

这节要解决的核心问题：论文中使用了哪些形式化定义来描述 benchmark 的选择标准、评测指标和输出度量。

### 5.1 Benchmark 选择优化目标

论文将 benchmark 选择形式化为一个分布匹配问题。Benchmark 应该尽可能代表真实世界数据分布（对应论文 Equation 1）：

$$
\min \, D(B \,||\, Data)
$$

- $B$：benchmark 数据集
- $Data$：真实世界的硬件设计数据分布
- $D(\cdot \,||\, \cdot)$：两个分布之间的距离度量（信息论意义上的散度）

**工程直觉**：好的 benchmark 不能太偏——如果全是加法器，就无法评测 FSM 生成能力；如果全是复杂 pipeline，小模型全得 0 分就失去了区分度。论文通过 arithmetic / logic / advanced 三层难度和 simple / medium / complex 三档 prompt 来逼近这个目标。

**为什么这么设计**：之前的 benchmark（RTLLM、Verigen）只做了纯文本 prompt 的难度分层，没有考虑"图文联合输入"这一新维度。这个优化目标试图让 benchmark 的选择变得可解释。

### 5.2 Next-token 预测成功度量

论文定义了细粒度 token 级评测指标（对应论文 Equation 2）：

$$
success^N = \sum_{i=0}^{N} \mathbf{1}_{token'_i = token_i}
$$

- $N$：token 序列长度
- $token'_i$：模型预测的第 $i$ 个 token
- $token_i$：reference RTL 中的第 $i$ 个 token
- $\mathbf{1}_{\text{condition}}$：指示函数，条件成立为 1，否则为 0
- $success^N$：预测正确的 token 数量

**工程直觉**：这相当于逐 token 的 exact match 累加。相比整个程序的对错，它能更细粒度地反映模型在代码补全场景（EDA 编辑器）中的局部预测能力。

**为什么这么设计**：论文指出之前的 benchmark 只报告 holistic program pass rate，无法反映模型在"写一半时下一个 token 应该是什么"这个更贴近实际编码场景的能力。但需要注意：

1. **这不能替代功能评价**——模型可以正确预测 `endmodule`（高频 token），但整个状态机逻辑完全错误。next-token 更接近编辑器的自动补全质量，不等于 RTL 功能正确。
2. **当前代码用 whitespace split 而非模型 BPE tokenizer**——`assign y=a+b;` 在代码中被视为一个 whitespace token，但 GPT 的 BPE tokenizer 可能切分成多个 token。论文的"token"定义与代码实现未严格对齐。

## 6. 训练与实验设置

这节要解决的核心问题：ChipGPT-V 的核心 benchmark 是否需要训练，实验怎么设计的，以及关键结果是什么。

### 6.1 是否需要训练

**核心 benchmark 不需要训练。** 论文直接调用 GPT-4V / GPT-4 / LLaVA / LLaMA 等**外部预训练模型**进行 zero-shot 评测。仓库内没有可下载的自研 VLM checkpoint、LoRA adapter 或 DPO adapter。

论文主实验使用的模型：

| 模型 | 模态 | 是否训练 | 权重可得性 |
|------|------|:---:|------|
| GPT-4V (gpt-4-vision-preview) | 图像+文字 / 仅图像 | 否（闭源API） | 不可下载 |
| GPT-4 | 纯文本 | 否（闭源API） | 不可下载 |
| LLaVA | 图像+文字 / 仅图像 | 否 | 开源但仓库无对应runner/权重 |
| LLaMA | 纯文本 | 否 | 开源但仓库无对应runner/权重 |

**后续投影路线的可选训练**（当前仓库缺失训练代码和权重）：
- **SFT / LoRA**：用 (spec + projector text) → reference RTL 做 teacher-forcing causal LM 训练
- **DPO**：用编译/仿真结果筛选 chosen/rejected RTL 对，在 SFT 模型上训练偏好 adapter

### 6.2 实验设置

**Benchmark 设计**（对应论文 Table 2）：

| 类型 | 题目数 | 涵盖什么 |
|------|:---:|------|
| Arithmetic | 10 | adder_8bit, adder_16bit, add_16bit_csa, adder_32bit, adder_64_bit, div_16bit, multi_booth, multi_pipe_4bit, multipipe_8bit, accu |
| Logic / digital circuit | 10 | Johnson_Counter, alu, edge_detect, freq_div, mux, parallel2serial, pulse_detect, right_shifter, serial2parallel, width_8to16 |
| Advanced | 12 | 1x4 systolic, 1x2 systolic, 2x2 systolic, 4x4 gemm, 5-stage pipeline, 3-stage pipeline, MAC PE, FSM (2~6 state, statemachine) |

**注意**：Table 2 列 30 题，Table 3 实际汇总 32 题（多出 `serial2parallel` 和 `width_8to16`），`main.py` 列 33 题，当前 `benchmark/` 有 45 个目录。口径不一致，后文讨论。

**Prompt 复杂度**：simple / medium / complex 三档
**采样数量**：每个模型、每个设计生成 5 次
**Baseline**：纯文本 GPT-4 / LLaMA
**评估工具**：Icarus Verilog 编译 + vvp 仿真

**评测指标定义**：

- **Syntax success**：以 32 个设计为分母，每个设计 5 次生成中是否至少有一次无语法错误通过 `iverilog` 编译。汇总值如 84.38% = 27/32。

- **Functionality success**：对每个设计取 pass@5 中表现最好的 Verilog，报告其 testbench pass rate。注意：论文 Table 3 中出现 98%、97%、50%、34%、10% 等非整数百分比，说明这是 testcase-level pass ratio（testbench 内部有多个测试向量），而非简单的"5 个候选至少一个完全通过"。

- **Next-token accuracy**：给定 3 个 RTL prefix，模型预测下一个 token 的精确匹配率。结果按 3 次试验分为 0%/33%/67%/100% 四档，最后取平均。

### 6.3 关键实验结果

**Table 3 主结果（32 题，pass@5 best-candidate）**

| 模型/输入 | Syntax success | Functionality success |
|---|---:|---:|
| **GPT-4V，V+T** | **84.38%** | **71.81%** |
| GPT-4，T | 68.75% | 46.88% |
| GPT-4V，V-only | 25.00% | 33.90% |
| LLaVA，V+T | 34.38% | 25.88% |
| LLaMA，T | 21.88% | 13.41% |
| LLaVA，V-only | 25.00% | 3.13% |

**这张表说明了**：加入视觉信息后，GPT 系列的 function 成功率从 46.88% 跃升到 71.81%（+24.93 pp），syntax 成功率从 68.75% 提升到 84.38%（+15.63 pp）。LLaMA/LLaVA 系列也有提升（function 13.41% → 25.88%，+12.47 pp），但绝对水平仍低。**纯图像模式最差**（GPT-4V V-only 仅 33.90%，远低于 V+T 的 71.81%），证明视觉信息主要用来补全拓扑/连接/位宽，功能语义仍高度依赖自然语言。

**Table 5 Prompt 复杂度敏感性**

| 模型 | simple | medium | complex |
|---:|---:|---:|---:|
| GPT-4V | 40.63% | 59.38% | **71.81%** |
| LLaVA | 9.38% | 16.25% | **25.88%** |

**这张表说明了**：总体趋势上，更详细的文字说明（complex prompt）带来更高成功率。但并非单调——逐题存在反例（如 GPT-4V 的 `1x4systolic`: 60% → 20% → 100%；`fsm`: 0% → 100% → 60%），说明更长 prompt 也可能引入歧义，或模型对特定 prompt 措辞敏感。

**Table 4 FSM 状态数敏感性（GPT-4V 基座）**

| State number | 2 | 3 | 4 | 5 | 6 | 7 | 8 | 9 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| Transition success | 100% | 100% | 80% | 60% | 60% | 20% | 0% | 0% |
| State declaration | 100% | 100% | 100% | 100% | 100% | 100% | 100% | 100% |
| Output | 100% | 100% | 100% | 100% | 100% | 100% | 80% | 80% |

**这张表说明了**：模型能声明所有状态，但状态转移随状态数增加迅速退化——到 8/9 状态时转移成功率直接降为 0%。这揭示了当前 LLM 在"长距离时序依赖 / 复杂状态图"上的根本短板：能看懂每个节点，但无法可靠地维护远距离转移边。

**Table 6 Next-token 预测**

| 系列 | 图文协同 | 纯文本 | 增益 |
|---:|---:|---:|---:|
| GPT-4V Series | 71.72% | 63.64% | +8.08 pp |
| LLaVA/LLaMA Series | 28.28% | 20.20% | +8.08 pp |

**这张表说明了**：图文协同在 next-token 预测上也有增益（两个系列恰好都是 +8.08 pp），但 case-level 波动很大——如 GPT 系列的 `3state_fsm` 图文 0% vs 纯文本 100%。next-token accuracy 不能替代功能评价：预测局部 token 正确不等于整体 RTL 功能正确。

## 7. 创新点

### 创新点 1：首个系统性的多模态 Verilog 生成 benchmark，证明文字+图的互补性

**以前是什么**：VerilogEval、RTLLM、Verigen 等 benchmark 都是纯文字→RTL，评测的是 LLM 从自然语言规格生成 Verilog 的能力。

**改成了什么**：引入电路结构图作为第二输入模态，构造了图+文联合输入的评测体系，并做完全消融（V+T / T-only / V-only 三组对比），量化了每种模态的独立贡献和互补增益。

**为什么这样改**：工业界的设计师经常在白板或 Visio 上画框图然后让工程师写代码——这种工作方式天然是多模态的。论文发现纯文字在处理嵌套二维空间结构、多模块互连（描述复杂度 O(n^2)）、精确端口对齐等场景时存在根本缺陷：语言是线性的，硬件拓扑是空间的。图像能直接呈现拓扑关系，自然语言能描述功能语义，两者分工明确。

### 创新点 2：图文职责的清晰划分——word notations + relations 的形式化

**以前是什么**：多模态模型通常当做"黑箱"——把图和文字一起扔进去，不知道模型究竟从图里学到了什么。

**改成了什么**：明确拆分图中信息为 word notations（模块名、端口名、位宽标注、功能标注）和 relations（一对一、一对多、多对多连接），分别对应"图提供什么"和"文提供什么"。自然语言部分再细拆为 module function description 和 module port description。

**为什么这样改**：这不仅是工程实践，更是一种"可解释的多模态规范"。后续研究者可以明确知道 image-only、text-only 各自缺少什么信息，消融实验也因此有了解释基础。

### 创新点 3：VLMQL——把多模态 prompt 工程形式化为查询语言

**以前是什么**：每次调用 VLM 需要手工拼 prompt 字符串，不同实验者可能写出完全不同的 prompt，不可复现。

**改成了什么**：用 Python 声明式语法定义 mode（三级视觉抽象）、模型选择、图像路径、功能描述、EDA tool/flow、输出约束，编译为 prompt。理论上可以实现 prompt 的版本控制、参数化、组合复用。

**为什么这样改**：这和 LMQL（Beurer-Kellner et al., PLDI 2023）的思路一致——把 prompt engineering 提升为 programming。在 EDA 场景下，VLMQL 还额外引入了 EDA tool 声明和 module 约束，使得"只生成 execute stage"这类 token 节省成为可能。

**当前局限**：仓库实现仅是 62 行 prompt printer，没有 parser / compiler IR / 模型调用 / EDA 闭环。但概念本身对多模态 RTL 生成的形式化是有价值的。

### 创新点 4：从 RTL 反向生成多模态训练数据

**以前是什么**：多模态 RTL 训练数据需要人工手动画电路图，成本极高。

**改成了什么**：`verilog_parse/mmdata_generation.py` 可以从已有的 (instruction, RTL) pair 出发，经 Yosys 综合→网表 JSON→解析端口/单元/连接→自动绘制 PNG 电路图→保留原 RTL 作为 target。解决了"多模态 RTL 训练数据的冷启动问题"。

**为什么这样改**：可以使现有的纯文本 RTL 数据集（如 VerilogEval、开源 GitHub 代码）自动扩展为多模态训练数据，大幅降低数据获取门槛。但这同时也引入了数据泄露风险——如果同一设计的 RTL 派生出的不同图像版本落入 train/test 两边，会虚假抬高评测分数。

## 9. 与芯片流程的关系

### 9.1 在全流程中的位置

ChipGPT-V 定位在芯片设计流程的**最前端**（阶段 ①-②）：

```text
         ChipGPT-V 的覆盖范围
        ┌─────────┴─────────┐
        │                    │
        ▼                    ▼
┌────────────┐    ┌────────────────┐    ┌──────────┐    ┌──────────┐
│ ① RTL 设计  │───→│ ② RTL 功能仿真   │───→│ ③ 逻辑综合 │───→│ ④ ...⑰  │
│ (生成)      │    │ (Icarus评测)    │    │ (未覆盖)   │    │ (未覆盖)  │
└────────────┘    └────────────────┘    └──────────┘    └──────────┘
```

**接手谁的输出**：接手的是人类设计师画在白板/Visio 上的框图和手写的功能说明文本——即"规格"（specification）。

**交付给谁**：交付的是可综合的 Verilog RTL 代码，理论上可传递给逻辑综合工具（Design Compiler / Genus / Yosys）。

**解决了什么痛点**：把"从图到代码"这个手工翻译步骤自动化了——工程师不用盯着框图逐行敲 Verilog 端口声明和模块实例化。

### 9.2 「testbench 通过」和「能做成芯片」之间隔着什么

这是理解 ChipGPT-V 定位最关键的边界。论文声称的功能成功率 71.81%，指的是"作者提供的 testbench 能通过"。但这和"能流片"之间隔着至少以下环节：

1. **PPA 完全不保证**：生成的 RTL 没有经过逻辑综合，不知道会综合出多少门、跑多快、功耗多少。论文自己也在 Figure 6 画了 Synthesis → PPA Report 但从未跑过。

2. **可综合性未经检验**：iverilog 是仿真器，对语法的要求比综合工具宽松。RTL 仿真通过不代表能被 Design Compiler 综合为实际门电路（可能用到不可综合的语法结构）。

3. **testbench 本身有 bug**：`adder_32bit` 的 testbench 正误都累加 error，`parallel2serial` 没有功能检查，systolic/spatial 的 `$display` 缺分号——这些 oracle 问题意味着论文的功能正确率数字本身也有不准确之处。

4. **时序完全未评估**：即使功能正确，这版 RTL 能不能跑在目标的时钟频率下？STA（静态时序分析）需要先综合出网表才能做，论文没有这个环节。

5. **物理实现未触碰**：Floorplan、Placement、CTS、Routing、DRC、LVS——从 RTL 到 GDSII 的物理设计全流程完全没有涉及。70% 的功能正确率不等同于 70% 的设计能流片。

6. **IO 和封装未考虑**：benchmark 的设计都是纯数字逻辑核，没有 IO pad、ESD 保护、电源网络等物理设计的必要组件。

一句话总结：这篇论文的"成功"是**逻辑功能层面的成功**，离"能做芯片"隔着整个物理设计后端（阶段 ③-⑰）。

## 10. 讨论与局限

### 10.1 论文自述的局限

1. **复杂结构仍然失败**：5-stage pipeline 和 4x4 spatial accelerator 即使在 GPT-4V V+T 下 function 成功率也是 0%（Table 3）——"能看图"不等于能处理复杂时序逻辑。

2. **FSM 长距离依赖退化**：状态数从 2 增到 9，transition success 从 100% 降到 0%（Table 4），证明当前 VLM 无法可靠维护长距离的时序依赖关系。

3. **benchmark 规模有限**：30 个设计、主要集中在运算单元和控制逻辑，缺乏更复杂的真实工业设计。

4. **prompt 非单调性**：更详细的 prompt 不一定更好——Table 5 揭示了逐题反例，说明 VLM 对 prompt 措辞敏感。

### 10.2 代码/复现层面的问题

从代码审计和复现详解中提炼的关键问题：

1. **Evaluator 与论文指标不一致**：当前 `function_correctness.py` 只检查 stdout 是否含 `pass`，只能输出 20% 倍数的分数（0%/20%/40%/60%/80%/100%），不能生成论文 Table 3 的 98%/34%/10% 等 testcase ratio。论文 Table 3 的细粒度分数需要 testcase-level 计数逻辑，当前 evaluator 中没有。

2. **Benchmark 数量口径不一致**：Table 2 = 30 题，Table 3 = 32 题，`main.py` = 33 题，当前 `benchmark/` = 45 目。四个口径混用会导致统计分母不确定，直接复算论文数字时必须明确用哪一个。

3. **多个 testbench 存在静态 bug**：
   - `adder_32bit`：`error = condition ? error+1 : error+1`，正误都累加 error
   - `parallel2serial`：没有任何功能检查，不比较 dout，不输出 pass
   - `4x4spatialacc` / `2x2systolic`：`$display("...passed...")` 末尾缺分号
   - `advanced/fsm`：reference 文件名拼成 `reeference.v`，模块名 `verified_fsm` 与 testbench 实例化的 `fsm` 不匹配

4. **GPT-4V API 已下线风险**：代码调用 `gpt-4-vision-preview`，这是历史 API 型号。即使 2026 年重新请求，服务端行为也可能不同于 2024 年论文投稿时期。

5. **图片来自远程 URL**：`main.py` 从 GitHub raw URL 读取图片而非本地文件，离线环境或版本不一致时无法复现。

6. **Next-token 评测路径不对称**：GPT-4V 读 `.v`、GPT-4 读 `.txt`，但 next-token 的模型输出是裸 token（不含 <code>&#96;&#96;&#96;verilog</code> 围栏），导致 GPT-4V 的 `.v` 可能为空。

7. **复现参数未记录**：temperature、seed、top_p、API/model revision 均未保存或固定，严格可重复性审计无法进行。

8. **VLMQL 只是原型**：62 行 prompt printer，覆盖 class attribute、lvm() 方法自覆盖、import 副作用等多个工程问题。

9. **后续训练目录缺失**：README 引用的 `projector/`、`finetune/`、`dpo/` 目录在当前 commit 中不存在，不能写成"训练链已完整开源"。

### 10.3 本资料包的批判性分析

1. **方法的隐含前提**：benchmark 假设电路图是"干净的框图"，而不是真实的工业模糊扫描图、手绘草稿或弱标注版图。真实场景中图的质量参差不齐，VLM 的识别率可能大幅下降。

2. **评测的公平性**：纯文本 baselines 的 prompt 是人工从图中转写的信息——转写者可能遗漏或歪曲了某些拓扑信息。如果纯文本 prompt 写得不好，那"视觉增益"就是"差 prompt vs 图"的人为夸大。论文也承认 completion 任务中两个模态的 RTL prefix 有时不一致。

3. **可扩展性天花板**：
   - benchmark 的最长设计约 171 行 Verilog（adder_64_bit），真实芯片动辄百万行。当前 VLM 在 token 长度和生成质量上都远未达到工业级。
   - 5-stage pipeline 全面失败（function 0%）说明复杂时序逻辑仍是硬骨头——不是加一张图就能解决的。
   - FSM 的 0% transition 在 8 状态时出现，说明模型"认识"状态但不能"推理"转移——这是 transformer 注意力扩散到长距离的根本弱点。

4. **"多模态"定义的歧义**：ChipGPT-V 的多模态是"人类设计师的规格中的多模态（文字+框图）"。这与 CircuitNet 3.0 那种"EDA 数据多模态（网表+波形+版图+时序报告）"是完全不同的概念。两者不要混用"多模态 AI4EDA"——前者是输入表示，后者是数据模态。

## 12. 一分钟复述版

1. **问题**：纯自然语言描述硬件有根本局限——嵌套空间结构、多模块互连（O(n^2) 描述成本）、端口精确对齐，这三件事文字做不好，图纸天生擅长。

2. **方法**：ChipGPT-V 构造了首个多模态 RTL 生成 benchmark——给 VLM 同时看电路结构图（PNG）和自然语言说明，让它生成 Verilog。

3. **图文分工**：图负责拓扑（模块层次、空间位置、连接关系、端口位宽），文负责语义（模块功能、时序、reset 极性、clock edge、运算规则）。

4. **核心结果**：GPT-4V 图文联合 function 71.81% vs 纯文本 46.88%（+24.93 pp）；LLaVA 图文联合 25.88% vs LLaMA 纯文本 13.41%（+12.47 pp）。纯图最差（GPT-4V V-only 33.90%）。

5. **FSM 退化**：状态数从 2 增到 9，转移成功率从 100% 降到 0%——模型能声明状态但不能推理转移。

6. **VLMQL**：提出用 Python 声明式语法形式化多模态 prompt（mode/model/image/function/EDA/constraint），优化 token 消耗和可复现性，但当前仅原型实现。

7. **重要边界**：它不是自研 VLM——是调用 GPT-4V 等外部模型的 benchmark；后端 PPA/GDSII 没有实验，不是 spec-to-GDS 闭环。

8. **关键局限**：复杂结构全失败（5-stage pipeline 0%，4x4 spatial 0%），evaluator 与论文指标不一致，testbench 有 bug，benchmark 数量口径不统一。

9. **核心启示**：复杂 RTL 需要视觉+语言联合规格，但 benchmark 可信性取决于 prompt 配对和 evaluator 的严格性——而这两件事在当前代码中都还有明显的改进空间。
