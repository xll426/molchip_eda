## 1. 一句话定位

**ARES 是一个自适应推理力度的 LLM Agent RTL 优化框架**：以面积乘功耗乘延迟的归一化乘积 FoM 为接受判据、Patience Counter 触发 effort 升降级，首次将每次 LLM 调用的归一化美元成本纳入 PPA 优化评测，在 3 个测试设计上以同等成本超越最强固定 effort 4 个百分点、以 12% 的 token 达到 SOTA Dr. RTL 的 1.25 倍 FoM 深度。

这句话里的四个技术承重点，后面逐一拆解：

1. **归一化每调美元成本（Cost-Aware Evaluation）** -- 区分 input/cache-read/cache-write/output 四类 token 的不同单价，计算每次 LLM 调用的真实美元成本，再归一化为 "high-calls" 单位。这使得不同 effort level、不同优化器的质量-成本权衡可以公平比较，而非像前人那样只看终点 FoM 不提花了多少钱。
2. **Long-Term Memory 构造方式不重要** -- 通过 equal-spend 对照实验发现：精心设计的跨设计记忆库（结构化案例 + 反优化策略 + 去重排序 + 匿名化）相比简单拼接同样经验，在 FoM-vs-cost 曲线上无可靠优势。推翻了过去将优化器质量归因于记忆设计的假设。
3. **Patience Counter 自适应 Reasoning Effort** -- 动态调度每次 LLM 调用的 reasoning effort：廉价 medium 覆盖大多数简单编辑，仅当进度停滞时升级到昂贵 high effort。参数 `(p=3, w=2.8, κ=0.05)` 从 21 个训练设计一次性拟合，在 3 个未见测试设计上零调参验证。
4. **FoM 等权三乘积 + 有效改善阈值** -- `FoM = (area/area_0) * (power/power_0) * (delay/delay_0)`，用 κ=0.05 过滤综合噪声，避免把随机波动当作改善触发 patience counter 重置。

## 2. EDA 阶段映射（①-⑰）

参照 [芯片流程.md](../芯片流程.md) 的 17 阶段标准编号。ARES 是一个**以综合级 PPA 反馈驱动的 RTL 迭代优化器**，其核心价值在于将 LLM 调用成本与 PPA 改善量化为统一指标，从而在逻辑综合阶段（③）的反馈闭环中实现 cost-aware 优化决策——优化后的 RTL 作为物理设计的入口，直接影响 Floorplan（⑦）的面积预算和 Placement（⑧）的拥塞程度。

| 阶段 | 覆盖 | 说明 |
|------|:---:|------|
| ① RTL 设计 | **核心** | LLM Agent 反复编辑 RTL 代码（流水线插入、资源共享、架构替换、操作数重排），以综合级 PPA 反馈驱动迭代优化 |
| ② RTL 功能仿真 | **核心** | Icarus Verilog + 10^4 随机向量 Testbench + Cadence JasperGold SEC（Sequential Equivalence Check），确保每次编辑不破坏功能正确性。这是 cost-aware 的前提——只有功能正确的候选才配进入昂贵的综合+功耗分析流程 |
| **③ 逻辑综合** | **核心** | Synopsys Design Compiler 在 Nangate 45nm 开源库上综合，提供 area 和 max_delay 反馈。**cost-aware 的核心落地阶段**：每次综合产生一个 (FoM, dollar_cost) 数据点，adaptive policy 据此决定下一轮 effort level。先搜索 f_max 找到最短时钟周期，再以该频率重综合拿面积 |
| ④ 门级仿真 | ❌ | 仅做 RTL 级 SEC + 网表级 TB 验证，不反标 SDF。综合反馈已提供足够的 PPA 信号 |
| ⑤ STA（静态时序分析） | **核心** | PrimeTime 功耗分析（基于 TB 仿真的翻转活动率）；DC 提供 delay 项。功耗是 FoM 的三个等权维度之一，计入 cost 维度评估 |
| ⑥ 形式验证 | ❌ | JasperGold 用于 SEC（等价检查），非综合前后形式等价证明 |
| **⑦ 布局规划 (Floorplan)** | **受益** | ARES 不直接操作 Floorplan，但优化后的 RTL（面积更小、逻辑结构更规整）使得 Floorplan 阶段的大模块摆放更灵活、面积预算更宽松。**cost-aware 的传导效应**：在 RTL 阶段用最低 LLM 成本获得最大 PPA 改善 → Floorplan 阶段受益于更优的网表入口质量 |
| **⑧ 标准单元摆放 (Placement)** | **受益** | 同上，不直接操作。但 ARES 的优化策略（资源共享减少门数、流水线化均衡路径延迟）产生的网表具有更好的可布线性，降低 Placement 阶段的拥塞风险和迭代次数。**cost-aware 的间接价值**：RTL 级节省的每一分面积和功耗，都在 Placement 阶段转化为更低的布线拥塞和更少的时序违例修复 |
| ⑨ CTS（时钟树综合） | ❌ | — |
| ⑩ 布线 Routing | ❌ | — |
| ⑪ 后仿真 | ❌ | 无 SPEF（Standard Parasitic Exchange Format），不走物理设计闭环 |
| ⑫ 物理验证 DRC + LVS | ❌ | — |
| ⑬ 签核 Signoff | ❌ | — |
| ⑭-⑰ 流片→制造→封装测试→芯片 | ❌ | — |

**覆盖率：3/17 核心，2/17 受益。** ARES 在 ①②③⑤ 四个阶段形成 RTL 优化闭环，其 cost-aware 优化决策直接影响 ⑦⑧ 的物理设计效率。论文的 "cost" 有两层含义：(1) LLM 调用的美元成本（直接计量），(2) 优化后 RTL 在物理设计阶段节省的工程成本（间接效果）。

> **cost-aware 的核心洞察**：传统 RTL 优化器只报 PPA 不报成本，导致无法判断"花 1 美元能达到多好的 PPA"。ARES 将每次 LLM 调用的真实美元成本与 FoM 改善捆绑报告，使得优化策略的选择（fixed effort vs adaptive effort）和优化器之间的比较（ARES vs Dr. RTL vs REvolution）都建立在统一的质量-成本坐标系上。

## 3. 输入 / 输出

### 3.1 输入

| 输入项 | 格式 | 说明 |
|--------|------|------|
| 未优化 RTL 设计 v_0 | Verilog（数百到数千行） | 功能正确（通过 testbench）但 PPA 不理想的 RTL；可来自工程师草稿或 LLM 生成 |
| Testbench | Verilog（自动生成） | 10^4 个固定种子随机输入向量；若未提供则由 ARES 从 v_0 自动生成 |
| Long-Term Memory | Markdown 文档 | 从 21 个训练设计收集的优化经验库，注入 Agent prompt。ARES 使用 engineered memory（结构化规则库），但消融实验证明构造方式不重要 |
| 迭代预算 | 累计 cost（high-calls） | 用户设定的 cost 上限，达到即终止优化 |
| Patience Counter 参数 | 常量 | `p=3, w=2.8, κ=0.05`，从 21 个训练设计的 grid search 一次性拟合 |

**最小具体示例（v_0 -- MAC 乘累加单元 LLM 草稿）**：

```verilog
// LLM 草稿的 MAC 单元，功能正确但 PPA 差
// area_0 = 1200μm², power_0 = 8.5mW, delay_0 = 1.8ns
// FoM_0 = 1.0（归一化基准）
module mac(input clk, rst, input [7:0] a, b, output reg [15:0] acc);
    always @(posedge clk)
        if (rst) acc <= 0;
        else     acc <= acc + a * b;  // 单周期组合乘法 -> 关键路径长、功耗高
endmodule
```

**Long-Term Memory 片段示例（engineered memory 中的一条规则）**：

```markdown
## Optimization Rule: Pipeline Multiplication
- Context: Single-cycle multiplier in datapath with tight timing
- Action: Insert pipeline register after multiplier stage,
  split accumulation into two-cycle operation
- Result: FoM reduced by 12% on training design "fir_filter"
- Anti-pattern: Do NOT pipeline when multiplier width < 4 bits
  (register overhead exceeds timing gain)
```

### 3.2 中间产物

ARES 的每次迭代产生以下中间数据：

**LLM Agent 输出（编辑提案）**：
```verilog
// Agent 在 medium effort 下的编辑提案示例
// 将单周期乘法改为流水线化
module mac(input clk, rst, input [7:0] a, b, output reg [15:0] acc);
    reg [15:0] mult_result;
    always @(posedge clk) begin
        mult_result <= a * b;        // Stage 1: 乘法
        if (rst) acc <= 0;
        else     acc <= acc + mult_result;  // Stage 2: 累加
    end
endmodule
```

**综合反馈（Synopsys DC + PrimeTime）**：
```text
area = 980μm², power = 7.2mW, delay = 1.4ns
FoM = (980/1200) * (7.2/8.5) * (1.4/1.8) = 0.817 * 0.847 * 0.778 = 0.538
Cost of this call: 0.85 high-calls (medium effort)
Cumulative cost: 3.2 high-calls
FoM improved: 0.538 < best_FoM(=1.0) * (1-0.05) -> ACCEPT, C reset
```

**Patience Counter 状态追踪**：
```text
Iteration  Event         FoM       C    Effort
    1      stalled       1.000     1    medium
    2      stalled       1.000     2    medium
    3      failed(verify)  —       4.8  medium  (C += w=2.8)
    4      C >= p(=3)     —        0    HIGH
    5      accepted       0.912    0    HIGH    (改善 >= κ, C reset)
    6      accepted       0.871    0    medium  (降回)
```

### 3.3 输出

| 输出项 | 格式 | 说明 |
|--------|------|------|
| 优化后 RTL 设计 | Verilog | PPA 更优的 RTL 代码 |
| FoM（品质因数） | 标量 | `FoM = (area/area_0) * (power/power_0) * (delay/delay_0)`，归一化 v_0=1.0，越低越好 |
| Cost vs FoM 轨迹 | 曲线数据 | 每轮迭代的 (累计 high-calls, 当前最优 FoM) 数据点，完整展现优化历程 |
| 归一化美元成本 | high-calls | 累计美元 / 该设计单次 high-effort 平均美元 cost |

**具体输出示例（MAC 案例，6 次运行均值）**：

```

  area_0 = 1200μm², power_0 = 8.5mW, delay_0 = 1.8ns -> FoM_0 = 1.00

ARES 自适应策略：
  均值 FoM = 0.73（改善 27%），最深单次 FoM = 0.58
  闭合与手工高度优化 MAC（FoM=18.9 绝对值）之间 83% 的差距
  Run-to-run variance 降 58%（std 从 8.9 降至 5.8 FoM 点）

vs Fixed High（同等累计 cost）：
  Fixed High 仅达 FoM = 0.77 -> Adaptive 多改善 4 个百分点

vs Fixed Medium：
  端点散布从 22.6 缩至 17.6 FoM 点，额外 cost 仅 7.3 high-calls
```

### 4.2 核心模块详解

#### 模块 1：归一化每调成本计算（Cost Accounting）

**做什么**：对每次 LLM 调用计算其真实美元成本，并归一化为 "high-calls" 单位报告，与 FoM 一起构成二维评价。

**为什么这样设计**：此前所有 RTL Agent 优化工作（REvolution、POET、CktEvo、VeriAgent、Dr. RTL）最多报告一个 "整个研究的聚合美元数"，无法在不同 effort level 之间进行公平比较。Low/medium/high effort 的 token 消耗差异极大（high effort 单次调用可能是 medium 的 3-5 倍），仅统计调用次数会严重扭曲成本比较。Token 计数也不够——input/cached/thinking/output token 单价各不相同，需要按类型加权。

**输入**：每次 API 调用的 token 日志（input/cache-read/cache-write/output token 数）+ OpenRouter 公开定价（Claude Opus 4.6）。

**输出**：累计 cost 曲线（论文所有图中的横轴），以 high-calls 为单位。

**为什么以 high-calls 为单位**：high-calls = 累计美元 / 该设计单次 high-effort 调用的平均美元 cost。这个归一化使得比较不受 API 定价变动影响——无论底层模型怎么调价，"1 个 high-call" 始终是 "该设计上一次 high-effort 迭代的钱"。这是论文保证 cost 指标长期可比较的关键设计。

#### 模块 2：Long-Term Memory（跨设计经验库）

**做什么**：存储从训练设计收集的优化经验，以 Markdown 文档形式注入 Agent prompt，使策略跨设计复用。

**三种记忆模式（消融实验核心）**：

1. **Memoryless**：无长期记忆，每次新设计从零开始（仍保留 Short-Term Memory）
2. **Baseline Memory**：将每个训练 run 中成功优化的简单描述拼接成列表
3. **Engineered Memory**：同一批原始经验，施加全部前人技巧的"超集"：
   - 结构化 (context, action, result) 案例记录
   - 保留无效/有害编辑作为反优化策略
   - 跨设计去重合并并按效果排序
   - 匿名化设计特定名称，使规则匹配问题结构而非特定模块名

**关键发现**：在 **equal spend** 下，Engineered Memory 相比 Plain Concatenation **无可靠优势**。三条测试设计的 FoM 曲线在两种模式下几乎重合。Memory 本身有益（带记忆 > 无记忆），但记忆的构造方式不重要。这推翻了 Dr. RTL、VeriAgent 等将优化器质量归因于精心设计记忆库的论断。

**为什么这一发现重要**：它把优化器质量的决定因素从 "你怎么写 memory" 转移到了 "你把 reasoning 花在哪"——这正是 Module 3 的出发点。

#### 模块 3：Patience Counter + 自适应 Effort 策略

**做什么**：动态调度每次 LLM 调用的 reasoning effort（medium/high），使廉价的 medium reasoning 覆盖大多数简单编辑，仅在进度停滞时将昂贵的 high reasoning 精准投入困难迭代。

**为什么这样设计**：

```text
Fixed Low:   简单编辑够用，复杂编辑想不深 -> 卡住，FoM 改善最差
Fixed High:  所有编辑都深度推理 -> 过度思考简单编辑，浪费 token
             （早期 high effort 在 cost 4.6-7.1 high-calls 才产生
              首次有效优化，而 medium 在 0.9-3.9 就完成了）
Adaptive:    先用 cheap medium -> 停滞时才升级 -> 把钱花在刀刃上
```

**Patience Counter C 更新规则**：

```
if 编辑通过验证+综合但 FoM 未改善（stalled）:
    C -> C + 1

if 编辑未能通过验证或综合（failed）:
    C -> C + w   (w = 2.8)
    // 一次 fail 被视为比 stall 更强的不利信号
    // fail 意味着 LLM 连有效候选都产不出

if 编辑使 FoM 改善（accepted）:
    Delta_FoM = (FoM_best - FoM_new) / FoM_best
    C -> C * max(0, 1 - Delta_FoM / kappa)   (kappa = 0.05)
    // 改善 >= 5% -> C 清零；边际改善 -> C 按比例减少但不归零
```

**Effort 切换逻辑**：

```
C >= p (=3) -> effort = HIGH, 重置 C
升级后运行 w (=2.8) 轮 high-effort -> 降回 MEDIUM
```

**参数拟合过程**：`(p, w, kappa)` 从 21 个训练设计的 medium-effort 运行记录中通过 grid search 一次性拟合。目标：捕获尽可能多的 "应该升级" 的时机点（medium 在接下来 3 轮无改善），同时保持至少 90% 的触发升级是有必要的。最终参数捕获了 94% 的 warranted escalation points。

**参数设计直觉**：

- `p = 3`：连续 3 次 stalled 才升级。单次 stalled 是噪声——即使高效 run 也拒绝大部分候选（论文报告 MAC 案例 6 轮运行中多数候选被拒绝）。需要累积证据。
- `w = 2.8 > 1`：一次 failed 编辑被视为比 stalled 更强的信号。Failed 意味着 LLM 连有效候选都产不出——可能是更难的问题需要更深推理。
- `kappa = 0.05`：FoM 改善至少 5% 才算 "有效"。综合结果有微小波动（工具噪声），低于 5% 的改善可能是噪声而非真实进步。

## 5. 关键公式

### 5.1 品质因数（Figure of Merit, FoM）

$$
\text{FoM} = \frac{\text{area}}{\text{area}_0} \times \frac{\text{power}}{\text{power}_0} \times \frac{\text{delay}}{\text{delay}_0}
$$

- $\text{area}$：候选设计的综合后面积（Nangate 45nm 库）
- $\text{power}$：候选设计的 PrimeTime 功耗分析结果
- $\text{delay}$：候选设计在 Synopsys DC 上搜索到的最短时钟周期
- $\text{area}_0, \text{power}_0, \text{delay}_0$：原始未优化设计 v_0 的对应值
- $\text{FoM}(v_0) = 1.0$，数值越低越好

**工程直觉**：三项等权乘积将面积、功耗、延迟这三个量纲不同、数值跨度极大的指标归一化到同一尺度。一个编辑可能用面积换时序（面积增大但频率提升），FoM 通过乘积判断净效应——如果面积增 10% 但延迟降 20%，FoM = 1.1 * 1.0 * 0.8 = 0.88 < 1，接受。

**为什么是等权乘积而非加权和**：乘积使各维度的相对变化率等权——面积减半和延迟减半对 FoM 的贡献相同（各乘 0.5）。如果用加权和，需要为不同设计手工设定权重，且绝对值差异（面积几百 vs 功耗几毫瓦）会使某些维度天然主导。

### 5.2 归一化每调美元成本

$$
\text{Cost} = \sum_{i=1}^{N} \left( p_{\text{in}} \cdot t_{i,\text{in}} + p_{\text{cr}} \cdot t_{i,\text{cr}} + p_{\text{cw}} \cdot t_{i,\text{cw}} + p_{\text{out}} \cdot t_{i,\text{out}} \right)
$$

- $N$：当前 run 的 LLM 调用总数
- $p_{\text{in}}, p_{\text{cr}}, p_{\text{cw}}, p_{\text{out}}$：input / cache-read / cache-write / output token 的 OpenRouter 美元单价（Claude Opus 4.6）
- $t_{i,\text{in}}$ 等：第 $i$ 次调用的各类 token 数量
- 内部 reasoning token 包含在 output token 中计费

归一化单位：

$$
\text{Cost}_{\text{high-calls}} = \frac{\text{Cost}}{\text{MeanHighCallCost}_{\text{design}}}
$$

- $\text{MeanHighCallCost}_{\text{design}}$：该设计上单次 high-effort 调用的平均美元成本
- 以 high-calls 为单位：使得比较不受 API 定价变化影响

**为什么区分四类 token**：不同 effort level 的 token 结构不同。High effort 的 reasoning/output token 远多于 medium，但其 input token（含 prompt cache hit）可能与 medium 相同。只用总 token 计数会高估 input-heavy 调用的成本、低估 reasoning-heavy 调用的成本。此外，prompt caching 使得 cache-read token 的单价远低于 input token——ARES 的设计利用了这一特性（长对话历史大量命中 cache）。

### 5.3 Patience Counter 更新

Stalled iteration（通过验证+综合但 FoM 未改善）：

$$
C \leftarrow C + 1
$$

Failed iteration（未能通过验证或综合）：

$$
C \leftarrow C + w, \quad w = 2.8
$$

Accepted improvement（FoM 改善）：

$$
C \leftarrow C \cdot \max\left(0,\; 1 - \frac{\Delta\text{FoM}}{\kappa}\right), \quad \kappa = 0.05
$$

- $\Delta\text{FoM} = \frac{\text{FoM}_{\text{best}} - \text{FoM}_{\text{new}}}{\text{FoM}_{\text{best}}}$：相对改善幅度
- $\Delta\text{FoM} \geq \kappa$（改善 >=5%）-> C 清零
- $\Delta\text{FoM} < \kappa$（边际改善）-> C 按比例减少但不归零，run 仍可能升级

**Effort 切换条件**：

$$
\text{effort} = \begin{cases}
\text{HIGH}, & C \geq p = 3 \\
\text{MEDIUM}, & \text{otherwise}
\end{cases}
$$

- $C$：加权停滞计数器，由上面两条更新规则累积（failed 加 $w$，改善则按比例衰减）
- $p$：升级阈值，论文设为 3
- $\text{HIGH}$ / $\text{MEDIUM}$：LLM 的两档推理强度（reasoning effort）

升级后运行 $w = 2.8$ 轮 high-effort，然后降回 MEDIUM。


**为什么 failed 的权重 w=2.8 大于 stalled 的权重 1**：论文从训练数据中发现，一次 failed 编辑（连有效候选都产不出）比一次 stalled（产出了但不改善）携带更强的 "需要更深推理" 信号。这对应数学直觉——failed 是更强的负证据。

## 6. 训练与实验设置

### 6.1 是否需要训练

**不需要训练。** ARES 直接调用 Claude Opus 4.6 API（via Claude Code assistant），不做任何微调或 RL。Patience counter 参数 `(p, w, kappa)` 虽然是在训练设计上拟合的，但这是超参数选择（grid search），不是模型训练。参数拟合只需 21 个设计的 medium-effort 运行记录，不需要 GPU，成本极低。

ARES 使用 Claude Code 的 extended thinking 和 prompt caching 功能。Effort level 通过 Claude Code 的 reasoning effort 参数控制（low/medium/high 三档，对应于内部 thinking token 预算的不同档位）。

### 6.2 实验设置

**Dataset**：24 个单模块开源 RTL 设计（数百到数千行 Verilog），来自：
- 19 个 Dr. RTL 的设计（排除 LSTM 模块，因其推断 memory 超出范围）
- FFT butterfly + Huffman decoder（来自 RTLRewriter benchmark）
- CORDIC + pipelined FFT + JPEG DCT（来自 OpenCores）

**Train/Test 划分**：21 个训练设计（收集 Long-Term Memory + 拟合 escalation 参数）/ 3 个测试设计（held-out，零调参验证）：
- tv80：Z80 CPU 的算术逻辑单元
- uart：串行收发器
- controller：AES 核的控制单元

**额外测试设计**（Sec 5.3）：MX multiply-accumulate (MAC) unit（开源，有已发布的手工高度优化版本 MX_fp32 作为 upper bound）。

**EDA 工具链**：
- 功能仿真：Icarus Verilog
- 等价检查：Cadence JasperGold（SEC）
- 逻辑综合+时序：Synopsys Design Compiler（Nangate 45nm 开源库）
- 功耗分析：Synopsys PrimeTime

**为什么用商业综合器而非 Yosys**：论文明确指出，开源综合器（Yosys）的优化能力较弱，会将商业工具自动完成的优化记在 Agent 账上——从而高估 Agent 的实际优化能力。Nangate 45nm 是开源标准单元库，确保无商业工艺库数据泄露给 LLM。

**LLM 配置**：Claude Opus 4.6，extended thinking + prompt caching，via Claude Code assistant。Effort level 通过 Claude Code 的 reasoning effort 参数控制（不指定 effort 时默认等同于 high）。

**Baseline 对比**：
- Fixed Low / Medium / High effort（自身消融）
- REvolution（最强开源 evolutionary LLM-RTL 框架，适配为优化器）
- Dr. RTL（skill-library 优化器，使用其自有 memory 文件）

**评估指标**：FoM vs 累计 cost（high-calls）曲线，非仅终点 FoM。

### 6.3 关键实验结果

**主实验：Fixed Effort 对比（论文 Figure 4）**

| 策略 | tv80 FoM | uart FoM | controller FoM | 改善范围 |
|------|:---:|:---:|:---:|:---:|
| Fixed Low | ~0.84+ | ~0.85+ | ~0.82 | 最弱，最不可靠 |
| Fixed Medium | 0.84 | ~0.81 | 0.77 | 起步快，会停滞 |
| Fixed High | 0.79 | ~0.84 | 0.79 | 起步慢，终点深 |
| **Adaptive (ARES)** | **0.76** | **0.77** | **0.73** | **23-27%** |
| Best Fixed | 16-23% | — | — | — |

**这张表说明什么**：Adaptive 策略在三个测试设计上全面超越所有 Fixed effort level，FoM 改善 23-27% vs 最强 Fixed 的 16-23%。关键机制：Adaptive 早期和 Fixed Medium 一样便宜（首次 5% FoM 改善在 cost 0.9-3.0 high-calls 内完成），但不像 Fixed Medium 那样停滞在平台期——它在 Fixed Medium 花更多钱也突破不了的地方通过升级 effort 继续下降。

**MAC 案例（论文 Figure 5）**

| 指标 | 值 |
|------|-----|
| MX_LLM 初始 FoM（绝对值） | 68.8 |
| MX_fp32 手工优化 FoM | 18.9 |
| ARES 均值 FoM（6 runs） | 33.6 |
| ARES 最深 FoM（单次） | 27.5 |
| 闭合差距 | **83%** |
| Adaptive vs Fixed Medium run-to-run variance | **降 58%**（std 8.9 -> 5.8） |
| 额外 cost 换 variance 降低 | 均值 7.3 high-calls |

**这张表说明什么**：Adaptive 策略的 variance 降低效果来自其 "精准救助" 机制——escalation 恰好发生在 run 被卡住的地方，给落后的 run 更深推理以跳出局部极小值。一个用 Fixed Medium 需要多次采样（如 REvolution 和 POET 的 population 策略）才能获得可靠结果的优化器，在 Adaptive 策略下一次运行就能获得同等可靠性。

**SOTA 对比（论文 Figure 6，controller 设计）**

| 优化器 | FoM | Cost（high-calls） | Token 比 |
|--------|:---:|:---:|:---:|
| **ARES Adaptive** | **0.694** | ~15 | 1x |
| REvolution | 0.943 | ~10 | n/a |
| Dr. RTL | 0.923（best candidate 0.909 被丢弃） | ~130 | 8.7x |

**这张表说明什么**：ARES 以 12% 的 token 达到 Dr. RTL 的 1.33 倍 FoM 深度。Dr. RTL 的 multi-agent pipeline（每轮：critical-path 分析 agent + 多个并行 rewrite agent + evaluation agent）消耗了大量 token 但未能转化为更好的 FoM——因为其优化目标不含功耗，且其 timing-focused 选择逻辑丢弃了在 power-aware FoM 下更优的候选（0.909）。

## 7. 创新点

### 创新点 1：首次将归一化每调美元成本纳入 PPA 优化评测

此前所有 RTL Agent 优化工作（REvolution、POET、CktEvo、VeriAgent、Dr. RTL）**只报告 PPA 改善幅度，不报告花了多少钱**。Dr. RTL 最多给出一个 "整个研究的聚合美元数"，无法在 effort level 之间或优化器之间进行公平的成本-质量比较。

ARES 的贡献不是简单地 "报告了 token 数"——它区分 input/cache-read/cache-write/output 四种 token 的不同单价，计算每次调用的真实美元成本，再归一化为与设计绑定的 high-calls 单位。这使得：(1) 不同 effort level 的成本差异可量化比较（medium vs high 的价格差透明化），(2) 不同优化器的质量-成本权衡可公平对比（ARES vs Dr. RTL 在同一 cost 坐标轴上），(3) 成本指标不受 API 定价变动影响（high-calls 归一化）。

**关键区别**：这不是 "token 计数"。Medium effort 的一次调用可能只有 high effort 的 1/5 输出 token（thinking token 包含在 output 中），但 input token 量相同（因为有 prompt caching）。只用总 token 计数会严重低估 high effort 相对于 medium 的真实成本差异。

### 创新点 2：证明 Long-Term Memory 构造方式不重要（推翻流行假设）

通过 **cost-controlled 对照实验**（三种记忆模式在 equal spend 下比较，而非像前人那样只看终点 FoM），ARES 发现 Engineered Memory 相比 Plain Concatenation **无可靠优势**。

这一发现的方法论价值高于结论本身：此前工作（Dr. RTL、VeriAgent、Memento-Skills 等）将优化器质量归因于记忆设计的精巧程度——distilled markdown rule libraries、manager-curated entry pools、structured skill nodes——但他们的比较是 "有 memory vs 无 memory"，或 "不同 memory vs 不同 memory 但未控制 cost"。ARES 的 equal-spend 比较揭示：在相同的 LLM 调用成本下，精心设计和简单拼接的效果相同。

**这指向一个更深层的 insight**：真正驱动 PPA 改善的不是你怎么组织过去的经验，而是你在当前的每次推理上花多少 "思考预算"——这正是创新点 3 的起点。

### 创新点 3：自适应 Reasoning Effort 调度（Patience Counter 机制）

首次在 RTL 优化 Agent 中引入**跨迭代的动态 effort 调度**。前人工作全部使用固定 effort level，而 LLM 推理领域（Snell et al., ICLR 2025; FrugalGPT 等）的 compute-optimal scaling 和 cost-aware routing 思想仅用于单次 prompt 的预算分配，未适配到序列化迭代优化场景。

ARES 的关键适配：
- **不是单次 prompt 的自适应**（根据 prompt 难度选 effort），而是**优化 run 过程中的跨迭代自适应**——难度随设计优化程度动态变化
- 初始设计有明显低效之处 -> 简单编辑即可改善 -> medium 够用
- 逐渐优化后 -> 剩余改进需要更深推理 -> 需要 high effort 突破瓶颈
- 参数**一次性拟合、零调参验证**——不是 per-design tuning

**实验结果支撑**：在 equal cost 下，Adaptive 超越所有 Fixed effort level（23-27% vs 16-23% FoM 改善）；在 MAC 案例中，Adaptive 将 run-to-run variance 降 58%。

### 创新点 4：FoM 等权三乘积 + 有效改善阈值 kappa

`FoM = (a/a_0) * (p/p_0) * (d/d_0)` 加上 `kappa = 0.05` 的设计解决了两个实际工程问题：
1. 三 PPA 维度归一化到同一尺度，消除绝对值差异（面积数百 μm²、功耗数 mW、延迟数 ns 数值跨度多个数量级），使得乘积公平反映各维度的相对变化
2. kappa 过滤综合噪声——同一设计多次综合的 PPA 有微小波动（工具非确定性），低于 5% 的 FoM 变化可能是噪声而非真实改善，不应触发 patience counter 重置

### 创新点 5：Cost vs Quality 完整轨迹（而非仅终点）

前人工作只报告最终 FoM（一个点）。ARES 提供每轮迭代的 (累计 high-calls, 当前最优 FoM) 数据点，完整展现在不同 cost 预算下的优化表现。这对实际部署至关重要——用户可以根据预算约束选择最优停止点，而非盲目跑到终点。

```text
⑤ STA                <- PrimeTime 提供 power 反馈；DC 提供 delay
⑥ 形式验证            <- JasperGold 用于 SEC（等价检查）
━━━━━━━━━━━━━━  ARES 的边界  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
⑦ 布局规划 Floorplan  <- 受益于 ARES：更小的面积意味着 Floorplan 更灵活
⑧ 摆放 Placement      <- 受益于 ARES：流水线化+资源共享使网表更规整
⑨ CTS ~ ⑬ Signoff    <- ARES 完全不涉及
```

### 9.2 ARES 解决的痛点

大量 RTL 代码（工程师快速草稿或 LLM 生成）**功能正确但 PPA 差**——通过了 testbench 却在浪费面积和功耗。传统上优化这些设计需要稀缺的人类专家工时，且优化过程没有量化的成本意识——"花多长时间、花多少钱达到什么 PPA" 是一笔糊涂账。

ARES 用 LLM Agent 自动化了这个过程，并首次将 LLM 调用成本与 PPA 改善量化为统一指标。其 cost-aware 设计使得：
- 每次迭代的投入产出可量化（每花 1 high-call 的钱，FoM 下降多少）
- 优化策略可基于 cost 比较（adaptive 比 fixed 在同等 cost 下更好）
- 优化器之间可公平对比（ARES vs Dr. RTL 在同一 cost 轴上）

### 9.3 为什么停在综合级 PPA

ARES 的 PPA 反馈来自综合后数据（Nangate 45nm 库），**不是 signoff 级 PPA**。从综合到 signoff 之间还有 placement、CTS、routing、寄生提取等环节，真实硅片的 PPA 可能与综合级存在偏差。这是 RTL 级优化器的天然边界——要进入物理设计闭环，需要用 OpenROAD 或 Cadence Innovus 等物理综合工具替代 Synopsys DC。

但 ARES 优化后的 RTL 作为物理设计的**入口质量更高**——面积更小、功耗更低、时序更宽松的网表会让 Floorplan（⑦）的面积预算更充裕、Placement（⑧）的拥塞更少、CTS（⑨）的 skew 更易控制。论文展示的 MAC 案例中，ARES 将 LLM 草稿的 FoM 从 68.8 降至 27.5（绝对值），闭合了与手工高度优化设计之间 83% 的差距——这节省的通常是数天到数周的资深工程师工时。

### 9.4 cost-aware 的流程级意义

ARES 的 cost-aware 框架对全流程的意义体现在两个层面：

**层面 1 -- 直接可计量**：在 RTL 优化阶段（①-③-⑤），每次 LLM 调用都有明确的 (FoM 改善, dollar cost) 记录。这使项目经理可以设定 "花 X 美元达到 FoM < 0.8" 的量化目标，而非模糊的 "尽可能优化"。

**层面 2 -- 间接传导**：优化后的 RTL 在 Floorplan（⑦）和 Placement（⑧）阶段需要更少的迭代次数和更少的面积/功耗 margin。例如，ARES 将 controller 的 FoM 从 1.0 降到 0.694，意味着面积乘功耗乘延迟乘积降 30.6%——这在物理设计阶段直接转化为更小的 die size、更低的 IR drop 风险和更宽松的时序收敛预算。

## 10. 讨论与局限

### 10.1 论文自述局限

1. **商业工具依赖**：Synopsys DC + PrimeTime + Cadence JasperGold——非开源工具链，个人研究者和大多数学术实验室难以复现。论文指出开源综合器（Yosys）会将商业工具自动完成的优化记在 Agent 账上，因此选择商业工具以保证 PPA 信号的准确性。

2. **训练/测试设计规模有限**：21 个训练设计 + 3 个测试设计（均为数百到数千行 Verilog 的单模块设计）。参数 `(p, w, kappa)` 虽然是一次性拟合且零调参验证，但其泛化性需要在更多样化的设计集和多模块层次化设计上证明。

3. **Backbone 锁定 Claude Opus 4.6**：未测试其他 LLM（GPT-4、Gemini、DeepSeek 等）。不同模型的 effort level 定价结构和对 effort 的敏感度差异巨大——ARES 的策略是否跨模型有效是开放问题。

4. **代码未公开**：论文声明同行评审通过后发布。

5. **FoM 是等权乘积**：`area * power * delay` 三项等权。实际工业约束通常是 "在满足时序（delay <= clock period）的前提下最小化面积和功耗"——不等权的 FoM 可能更贴近实际需求。

6. **仅综合级 PPA**：未涉及 physical design（placement、CTS、routing），signoff 级 PPA 可能与综合级有显著差异。

### 10.2 代码与复现层面的问题

7. **商业 EDA 工具许可证门槛**：Synopsys DC 和 PrimeTime 的 academic license 虽然存在，但获取流程繁琐且受限（通常限特定服务器、限特定工艺库）。使用开源替代（Yosys + OpenSTA）可能导致 PPA 反馈信号质量下降，影响 adaptive policy 的有效性。

8. **Claude Code assistant 的 effort level 映射不透明**：论文使用 Claude Code 的 "extended thinking" 功能和 effort level 参数，但 Claude Code 的内部实现细节（low/medium/high 各自对应多少 thinking token 预算、是否受 prompt 内容影响）未公开，跨版本复现存在不确定性。

9. **Long-Term Memory 的构建成本未计入**：训练阶段对 21 个设计各跑一次完整优化 run 的成本（收集经验+拟合参数）未计入测试设计的 cost 报告。虽然这是一次性投入，但对实际部署而言是必须考虑的前期成本。

### 10.3 本资料包的批判性分析

10. **FoM 的隐含偏好**：三项等权乘积意味着 "面积减半 + 功耗翻倍 = FoM 不变"，但实际上面积和功耗的工业权重往往不同。Dr. RTL 和 REvolution 不包含功耗项——如果移除功耗项，ARES 在 controller 上的相对优势需要重新评估。Dr. RTL 自己的 best candidate（0.909）被其 timing-focused 选择逻辑丢弃了（因功耗增加），这暴露了 FoM 定义对排名的影响——一个看起来 "更低" 的 FoM 可能只是选择了更有利的指标组合。

11. **Long-Term Memory 结论的边界条件**：论文的 "memory 构造不重要" 结论仅限于 "同样原始经验的不同组织方式"。如果：(a) 原始经验本身质量差（训练设计的优化跑得不够充分），(b) 经验规模更大（数百个设计 vs 21 个），(c) 设计领域跨度大（模拟/混合信号 vs 纯数字），Engineered Memory 的去重/匿名化/排序功能可能才开始发挥作用。当前结论的稳健性需要更大规模验证。

12. **Patience Counter 的参数敏感性未充分讨论**：`(p=3, w=2.8, kappa=0.05)` 是在 Claude Opus 4.6 + medium effort 的特定设定下拟合的。如果换模型（GPT-4 的 medium reasoning 质量可能不同）或换综合工具链（开源 Yosys 的综合结果波动更大），这些参数可能需要重新拟合。论文未提供参数敏感性分析或 ablation on parameter values。

13. **Adaptive 策略在极端预算下的表现不明确**：虽然论文在 equal cost 下比较，但如果预算极度紧张（例如只能跑 5 次 LLM 调用），adaptive 策略可能来不及完成 medium -> stall -> escalate -> high -> discharge -> medium 的完整周期，此时 fixed medium 可能更划算。论文的成本曲线未覆盖极低预算区间的详细数据。

14. **Effort level 粗粒度**：论文使用 API 暴露的三档 effort（low/medium/high），但 Claude Opus 4.6 的 extended thinking 实际支持更细粒度的 token budget 控制。将 effort 从三档扩展到连续空间（例如用 RL 学习每轮迭代的最优 thinking token 预算），可能进一步提升 cost-efficiency。

15. **与生成式方法的根本区别**：ARES 优化已有 RTL（迭代编辑），而非从零生成。ChipSeek 等 RL-based 方法做生成+PPA 反馈闭环，搜索空间是 "所有可能的 RTL 结构"。ARES 的搜索空间是 "对已有 RTL 的编辑序列"——更窄但也更可控，有功能正确的 v_0 作为安全底线（SEC 确保不引入功能错误）。但这同时意味着 ARES 的优化上限受限于 v_0 的架构选择——如果 v_0 选择了错误的基本架构，ARES 可能无法通过编辑手段达到最优。

16. **Cost accounting 的实际精度**：论文使用 OpenRouter 的公开定价计算 cost，但实际 API 调用可能涉及批量折扣、credits、免费额度等因素。此外，Claude Code assistant 的内部 tool-calling overhead（如文件读取、命令执行）的 token 消耗如何计入 cost 未详细说明。

## 12. 一分钟复述版

ARES（KU Leuven / Nokia Bell Labs，arXiv 2026）是一个**自适应推理力度的 LLM Agent RTL 优化器**，把 LLM 调用成本和 PPA 改善首次捆绑为统一指标。核心三招：

1. **Cost-Aware PPA 评估**：`FoM = (area/area_0) * (power/power_0) * (delay/delay_0)`，同时计算每次 LLM 调用的真实美元成本（区分 input/cache/read/write/output 四类 token 单价），归一化为 high-calls 单位，使不同 effort level 和优化器可在统一的质量-成本坐标上比较。ARES vs Dr. RTL：FoM 深 25%（0.694 vs 0.923）@ 12% token。

2. **推翻 Memory 构造假说**：通过 equal-spend 对照实验发现——精心设计的跨设计记忆库相比简单拼接同样经验 **无可靠优势**。优化器质量的真正驱动因素不是怎么写 memory，而是 reasoning 花在哪。

3. **Patience Counter 自适应 Effort**：参数 `(p=3, w=2.8, kappa=0.05)` 从 21 个训练设计一次性拟合。廉价 medium 覆盖简单编辑，仅当连续 3 次停滞（C>=3）才升级昂贵 high effort。在 3 个测试设计上：Adaptive FoM 改善 23-27% vs 最强 Fixed 的 16-23%（equal cost）；MAC 案例闭合手工优化差距 83%，run-to-run variance 降 58%。

**边界**：覆盖流程阶段 ①②③⑤（3/17 核心，⑦⑧ 间接受益），依赖商业 EDA 工具（Synopsys DC + PrimeTime），仅综合级 PPA 非 signoff 级，FoM 等权乘积可能不匹配工业不等权需求，参数敏感性未充分分析，代码未公开。
