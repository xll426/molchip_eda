## 1. 一句话定位

**TrojanWhisper 首次系统评估了预训练 LLM（GPT-4o / Gemini 1.5 Pro / Llama 3.1）在 RTL 层硬件木马检测任务上的能力，在 14 个 Trust-Hub 衍生 HT 样本上达到 GPT-4o + Gemini 1.5 Pro 的 100%/100% 完美 Precision/Recall（基线场景），并在变量名混淆、结构重排、冗余逻辑插入三种扰动下测试鲁棒性，发现 Gemini 1.5 Pro 即使在扰动后仍保持 100%/100%，验证了 LLM 的"理解"而非"记忆"能力。**

这句话里的 6 个承重点，下面逐一拆解：

1. **首次系统性 LLM-HT 评估** — 在 TrojanWhisper 之前，硬件木马检测主要靠 (a) 测试向量生成 [3]、(b) 形式验证 [4-5]、(c) 代码分析（FANCI [6]、VeriTrust [7]、DeTrust [8]）、(d) ML/GNN（GNN4TJ [2]、GCN [18]）。本文是**第一篇**把"通用 LLM 直接喂 RTL 代码就能识别 HT"作为主要研究问题的论文。
2. **三层架构** — (A) HT Signature Generation Engine（基于 Trust-Hub 训练集 LLM 提取 trigger/payload 签名）→ (B) Perturbation Generation Engine（变量名混淆 + 冗余逻辑 + FSM 重构）→ (C) LLM HT Detection Engine（签名匹配 + 上下文学习 + XML 输出）。
3. **GHOST benchmark（14 HT × 3 类型）** — 14 个 HT 来自 3 个干净开源设计（SRAM 52 行、UART 430 行、AES-128 768 行），按 Shakya 分类含 4 个 Type-1（功能篡改）、4 个 Type-2（信息泄露）、6 个 Type-3（拒绝服务）。论文明确指出**这些 HT-注入设计上传日期在 LLM knowledge cutoff 之后**，避免训练集泄露。
4. **完美基线 + 鲁棒性下降** — GPT-4o 和 Gemini 1.5 Pro 在 baseline 上 100%/100% 准确，Llama 3.1 在 HT2 上有 4 个 FP（{14, 14, 4, 0}）；扰动后 Gemini 1.5 仍 100%/100%、GPT-4o 退化到 100%/85.7%、Llama 3.1 退化到 66.7%/85.7%。
5. **检测-定位鸿沟** — 所有模型在"是否存在 HT"上接近完美，但在"HT 触发器 / Payload 在哪一行"上 TLC（触发行覆盖）= 0.72-0.98、PLC（Payload 行覆盖）= 0.32-0.46，扰动后进一步降至 TLC 0.72-0.86、PLC 0.20-0.33。
6. **类型分类弱** — HT Category Classification Accuracy（TCCA）在 baseline 上：GPT-4o 0.714、Gemini 1.5 0.571、Llama 3.1 0.444；扰动后 Llama 3.1 跌到 0.222。说明 LLM 的"类型推理"远弱于"存在性检测"。

## 3. 输入 / 输出

### 3.1 输入

TrojanWhisper 的输入是 1 份完整 RTL 源码（Verilog）+ 1 个待审计模块标识（IP core 名）。

```verilog
// AES-128-T220（Listing 2，Type-3 DoS 篡改）
// 这是被注入 HT 的代码，TrojanWhisper 拿到后需判断：
//  1) 是否有 HT? (Yes)
//  2) 触发行在哪? (第 3-9 行：`if (state[7:0] == 8'hAA && key[7:0] == 8'h55)`)
//  3) Payload 行在哪? (第 11-18 行：阻断 XOR 操作)
//  4) HT 类型? (Type-3 拒绝服务)

module aes_128 (
  input clk, input reset,
  input [127:0] state, input [127:0] key,
  output reg [127:0] out
);

  reg [7:0] pq;
  reg [127:0] s0, k0;

  // ====== Trigger ======
  always @(posedge clk)
    if (reset)
      pq <= 8'h00;
    else if (state[7:0] == 8'hAA && key[7:0] == 8'h55)  // ← HT 触发条件
      pq <= pq + 1;
    else
      pq <= 8'h00;

  // ====== Payload (DoS) ======
  always @ (posedge clk)
    if (reset) begin
      s0 <= 128'h0;
      k0 <= 128'h0;
    end else if (pq != 8'hFF) begin                    // ← HT 触发后阻断正常 XOR
      s0 <= state ^ key;
      k0 <= key;
    end
endmodule
```

### 3.2 中间产物

(1) **HT 签名库 S**（从 Trust-Hub 训练集 D = {(Cᵢ, Tᵢ, Mᵢ)} 提取）：

```json
{
  "trigger_signatures": [
    "suspicious_signals",   "suspicious_registers",
    "suspicious_counters",  "suspicious_state_machines",
    "rare_conditions",      "unusual_comparisons"
  ],
  "payload_signatures": [
    "modified_output_logic", "malicious_code",
    "unexpected_transitions", "abnormal_assignments",
    "suspicious_flows"
  ],
  "success_criteria": "trigger OR payload"
}
```

(2) **扰动后的 RTL**（每个原设计 1 份）：

```verilog
// 同一份 AES-T220，变量名混淆后 (mn→uvw, mem→qrst, ...)
// 验证扰动前后的功能等价性靠 Icarus Verilog 跑同一个 testbench
always @(posedge clk0) begin
  if (uvw == 32) begin              // mn 改成 uvw
    uvw1 <= 0;
    ...
  end else if (addr0 == ADDR) begin
    uvw <= uvw + 1;
  end
end
```

(3) **LLM 分析输出**（XML 格式，由 GPT-4o / Gemini / Llama 返回）：

```xml
<TrojanWhisperResult>
  <summary>
    <trojans_found>1</trojans_found>
  </summary>
  <trojan>
    <type>2</type>          <!-- Type-2 信息泄露 -->
    <trigger>
      <line>9</line>
      <code>always @(posedge clk0) begin
        if (uvw == 32) begin ...</code>
    </trigger>
    <payload>
      <line>13</line>
      <code>if (addr0 == ADDR) begin
        uvw <= uvw + 1;
        zabc <= qrst[ijkl];
      end</code>
    </payload>
  </trojan>
</TrojanWhisperResult>
```

## 4. 方法与架构

### 4.1 整体 Pipeline

```text
┌──────────────────────────────────────────────────────────────────┐
│  阶段 A：HT 签名生成 (一次性，离线)                                 │
│                                                                  │
│  Trust-Hub D = {(Cᵢ, Tᵢ, Mᵢ)}                                    │
│       │                                                          │
│       ▼  LLM 函数 L(Cᵢ, Tᵢ, Mᵢ)                                  │
│  候选签名 P = {p₁, ..., pₘ}                                       │
│       │                                                          │
│       ▼  相似度合并 R(P) → S', δ(pₓ, p_y) > θ                    │
│  精炼签名 S'                                                     │
│       │                                                          │
│       ▼  验证 V(s'ⱼ) against D_val, 得性能向量 vⱼ = [α, β, γ]    │

│       │                                                          │
│       ▼  排序 W(vⱼ) → 权重 wⱼ                                    │
│  有序签名库 S = {(s₁, w₁), ..., (s_q, w_q)}                       │
│       │                                                          │
│       ▼  持续改进 I(S, F) 分析失败 case                           │
│  S_t (含 zero-day 扩展 N(Z))                                      │
└──────────────────────┬───────────────────────────────────────────┘
                       │  签名库 S_t
                       ▼
┌──────────────────────────────────────────────────────────────────┐

│                                                                  │

                       ▼
┌──────────────────────────────────────────────────────────────────┐

│                                                                  │
│  ┌─────────────────┐  ┌──────────────────┐  ┌────────────────┐    │

│  ┌─────────────────────────────────────────────────────────┐     │
│  │  In-Context Learning:                                  │     │
│  │   - 输入：S_t (签名库) + RTL T₀/T₁ + 类型描述          │     │

### 4.2 核心模块逐个详解

#### 模块 A：HT Signature Generation Engine

- **做什么**：从 Trust-Hub 训练集 D = {(Cᵢ, Tᵢ, Mᵢ)} 提取 HT 签名 $P = \{p_1, ..., p_m\}$，再合并相似签名 → 验证 → 排序 → 入库。
- **为什么这样设计**：直接让 LLM 读 RTL 检测 HT 缺乏系统化"什么是 HT"的定义，签名库相当于把 HT 形式化为可枚举的 6+5 = 11 个语义类别（6 个 trigger、5 个 payload），让 LLM 在"特征空间"而非"全代码空间"里做判断。
- **输入**：Trust-Hub 训练样本 (clean RTL Cᵢ, infected RTL Tᵢ, 元数据 Mᵢ)。
- **输出**：有序签名库 S = {(s₁, w₁), ..., (s_q, w_q)}，含权重 wⱼ = W(vⱼ) = W([αⱼ, βⱼ, γⱼ])，α = 检测率、β = 误报率、γ = 泛化能力。
- **关键实现细节**：
  - 用 LLM 函数 L(Cᵢ, Tᵢ, Mᵢ) 提取签名，相当于"prompt LLM 列出 clean 与 infected 之间的差异"。
  - 相似度阈值 δ(pₓ, p_y) > θ 时合并并泛化。
  - 持续改进 I(S, F) 分析失败 case，零日检测 N(Z) 自动扩展 S。
  - 最终签名库覆盖 6 个 trigger 类别 + 5 个 payload 类别。

#### 模块 B：Perturbation Generation Engine

- **做什么**：对每个待审计 RTL 应用 3 种变换，生成功能等价的"更难"版本，用于测试 LLM 鲁棒性。
- **为什么这样设计**：直接评估 LLM 容易高估能力 —— LLM 可能只是"记住"了 Trust-Hub 上的 HT 样本。通过扰动让 HT 在源码层面"看起来不一样"，迫使用 LLM 真的去"理解"电路行为。
- **输入**：原始 RTL T₀。
- **输出**：扰动后 RTL T₁，且 Icarus 验证 T₀ ≡ T₁（功能等价）。
- **三阶段变换**：
  1. **变量名混淆**：把 `mn` 改成 `uvw`、`mem` 改成 `qrst`、`csb0_reg` 改成 `abcd`，但保留模块接口和端口名。
  2. **可综合冗余逻辑**：增加额外寄存器、用替代组合实现等价表达式（"挑战模型在装饰代码中保持准确检测"）。
  3. **FSM 重构**：在不改变外部行为的前提下重组状态机结构。
- **关键约束**：所有变换必须**可综合**（synthesizable），否则 Icarus 跑不通功能等价性验证。

#### 模块 C：LLM HT Detection Engine

- **做什么**：对每份 RTL（含原始和扰动版本），用 GPT-4o / Gemini 1.5 Pro / Llama 3.1 三种 LLM 做检测。
- **为什么这样设计**：通过"prompt 工程 + 签名库 + 上下文示例"让通用 LLM 充当 HT 专家，**不**需要 fine-tuning（无 HT 训练数据时微调不可能）。
- **输入**：签名库 S + RTL T₀/T₁ + 类型描述。
- **输出**：XML 格式的检测结果。
- **两阶段分析**：
  - 阶段 1：签名匹配（用 S 中的 11 类签名做 pattern matching）
  - 阶段 2：上下文分类（判断是 Type-1 / Type-2 / Type-3 中的哪一类）
- **关键实现细节**：
  - LLM 配置（Table II）：
    | 参数 | GPT-4o | Gemini 1.5 Pro | Llama 3.1 |
    |---|---|---|---|
    | 版本 | gpt-4o | gemini-1.5-pro-latest | llama-3.1-70b-versatile |
    | Temperature | 1.0 | 1.0 | 1.0 |
    | Top-p | 1.0 | 0.95 | 1.0 |
    | Max Input | 128K | ~200K | 128K |
    | Max Output | ~16K | 8K | ~32K |
    | Knowledge Cutoff | Oct 2023 | Nov 2023 | Dec 2023 |
  - 编程：Python 3.10.14 + OpenAI SDK + Google GenAI SDK 0.8.3 + Groq Client + ElementTree 解析 XML。
  - API key 通过 python-dotenv (1.0.1) 管理。

## 5. 关键公式

### 5.1 Trigger Line Coverage (TLC, Eq. 1)

$$
\text{TLC} = \frac{\text{LoC}_{\text{TP}_{\text{trigger}}}}{\text{LoC}_{\text{TP}_{\text{trigger}}} + \text{LoC}_{\text{FP}_{\text{trigger}}}}
$$

- $\text{LoC}_{\text{TP}_{\text{trigger}}}$：被正确识别为 HT 触发的代码行数
- $\text{LoC}_{\text{FP}_{\text{trigger}}}$：被错误识别为 HT 触发的代码行数（实际是干净代码或 payload）

**工程直觉**：TLC 衡量"LLM 能否精确定位触发条件"——不只是说"这里有 HT"，还要说出"具体哪行是 if(state==...) 触发的"。

**为什么这么设计**：传统 HT 检测只给二元判断（Yes/No），但**定位到行**对人工审查至关重要——审查员需要知道看哪几行代码。TLC 是对定位精度的连续评估。

### 5.2 Payload Line Coverage (PLC, Eq. 2)

$$
\text{PLC} = \frac{\text{LoC}_{\text{TP}_{\text{payload}}}}{\text{LoC}_{\text{TP}_{\text{payload}}} + \text{LoC}_{\text{FP}_{\text{payload}}}}
$$

- $\text{LoC}_{\text{TP}_{\text{payload}}}$：被正确识别为 HT payload 的代码行数
- $\text{LoC}_{\text{FP}_{\text{payload}}}$：被错误识别为 payload 的代码行数

**工程直觉**：payload 是 HT 实际造成危害的代码（修改输出、泄露数据、阻断服务），定位 payload 行比定位 trigger 更重要。

**为什么这么设计**：payload 行的语法特征比 trigger 更弱（payload 经常是看似正常的赋值语句），所以 PLC 普遍低于 TLC。论文实测 GPT-4o baseline PLC = 0.32，确实比 TLC = 0.98 低。

### 5.3 Accuracy of Classification (AC, Eq. 3)

$$
\text{AC} = \frac{\text{LoC}_{\text{TP}_{\text{payload}}} + \text{LoC}_{\text{TP}_{\text{trigger}}} + \text{LoC}_{\text{TP}_{\text{clean}}}}{\text{LoC}}
$$

- $\text{LoC}_{\text{TP}_{\text{clean}}}$：被正确识别为干净代码的行数
- $\text{LoC}$：RTL 设计总行数

**工程直觉**：AC 是"行级别的总分类正确率"，包含 trigger、payload、clean 三类。GPT-4o 在 baseline 上 AC = 0.92 意味着 92% 的代码行被正确分类（仅 8% 误判）。

**为什么这么设计**：AC 给一个汇总指标，便于跨模型对比。但它对"把 trigger 误判成 payload"和"把 clean 误判成 trigger"等同视之，**不区分错误类型**——这需要在 TLC/PLC 单独看。

### 5.4 TCCA（HT Type Classification Accuracy, 论文自定义）

$$
\text{TCCA}_{\text{Type-i}} = \frac{\text{Correctly classified Type-i HTs}}{\text{Correctly classified Type-i HTs} + \text{Misclassified as Type-i}}
$$

例：某设计含 6 个 Type-2 HT，LLM 正确识别 4 个为 Type-2，但同时把 2 个干净组件误标为 Type-2，则 $\text{TCCA}_{\text{Type2}} = 4 / (4+2) = 0.667$。

**工程直觉**：TCCA 衡量"LLM 区分 HT 类型的能力"，是 HT 防御的最后一步（知道 HT 类型才能选择对应 mitigation 策略）。

**为什么这么设计**：论文发现所有 LLM 的"存在性检测"接近完美，但"类型推理"远弱（GPT-4o TCCA 0.714、Llama 3.1 0.444），这是 LLM 的真实瓶颈。

## 6. 训练与实验设置

### 6.1 是否需要训练

**TrojanWhisper 完全不需要训练**。所有 LLM 都用预训练权重（GPT-4o / Gemini 1.5 Pro / Llama 3.1-70B），通过 in-context learning + prompt engineering 实现 HT 检测。

### 6.2 实验设置

- **硬件 / 算力**：
  - LLM API 调用：GPT-4o (OpenAI)、Gemini 1.5 Pro (Google Generative AI SDK 0.8.3)、Llama 3.1-70B-Versatile (Groq Client)
  - RTL 仿真：Icarus Verilog 11.0
  - 软件：Python 3.10.14 + python-dotenv 1.0.1 + ElementTree
- **数据集（Table I）**：
  - 3 个干净源：SRAM 控制器 (52 行)、UART 通信 (430 行)、AES-128 加密 (768 行)
  - 14 个 HT-注入样本（按类型分）：
    - Type-1 (4 个)：SRAM-HT100, UART-HT100, AES-HT100, AES-HT110
    - Type-2 (4 个)：SRAM-HT220, AES-HT210, AES-HT220, UART-HT200
    - Type-3 (6 个)：SRAM-HT120, SRAM-HT320, AES-HT120, UART-HT110, UART-HT220, SRAM-HT110
  - **关键**：HT 注入设计上传到 GitHub 的日期**晚于 LLM knowledge cutoff**，避免训练集泄露。
- **扰动后数据集**：14 个原始 + 14 个扰动 = 28 个测试样本。
- **评估指标**：
  - Detection：{k, TP, FP, FN}
  - Localization：TLC, PLC, AC
  - Classification：TCCA

## 7. 创新点

### 创新点 1：首次系统性 LLM-HT 评估方法学

- **已有方法**：传统 HT 检测四大流派——测试生成 [3]、形式验证 [4-5]、代码分析（FANCI/VeriTrust/DeTrust）、ML/GNN（GNN4TJ/GCN）。**没有**人系统评估过"通用 LLM 直接审计 RTL"的可行性。
- **本文关键区别**：第一次把 GPT-4o / Gemini 1.5 Pro / Llama 3.1 同时放在同一 benchmark 上对比，并定义 4 个维度的评估指标（Detection / Localization / Type Classification / Cost）。
- **具体性**：
  - Trust-Hub HT 衍生 14 个样本，含 3 种 HT 类型。
  - Knowledge cutoff 控制：HT 注入设计**晚于 LLM cutoff 日期**上传，杜绝"记忆 vs 理解"的混淆。
  - 4 个评估指标独立报告，避免"只看准确率"的误导。

### 创新点 2：3-Stage Perturbation Engine 测试 LLM 鲁棒性

- **已有方法**：传统 GNN 评估只在原始 RTL 上跑，缺乏"HT 代码被混淆后还能不能识别"的测试。
- **本文关键区别**：系统实现 3 种扰动（变量名混淆 + 冗余逻辑 + FSM 重构），且所有扰动**保持可综合 + 功能等价**（Icarus 验证），专门测试 LLM 在"代码风格变化"下的稳定性。
- **具体性**：
  - 例：SRAM-T110 的 `mn` 改成 `uvw`、`mem` 改成 `qrst`，但 Icarus 仿真结果完全一致。
  - 扰动后 GPT-4o TLC 0.98 → 0.86，Llama 3.1 TCCA 0.444 → 0.222，揭示不同模型的鲁棒性差距。

### 创新点 3：HT 签名驱动的 In-Context Learning

- **已有方法**：直接 prompt LLM "find hardware trojans in this Verilog"——结果不可控、不可解释。
- **本文关键区别**：先把 HT 形式化为 6+5=11 个签名类别（trigger: suspicious_signals/registers/counters/state_machines/rare_conditions/unusual_comparisons；payload: modified_output_logic/malicious_code/unexpected_transitions/abnormal_assignments/suspicious_flows），再用签名库 + 类型描述构造 prompt。
- **具体性**：
  - 签名库从 Trust-Hub 训练集自动提取，经 LLM 函数 L(Cᵢ, Tᵢ, Mᵢ) 生成。
  - 持续改进 I(S, F) 让签名库随时间扩展，含 zero-day 检测 N(Z)。
  - Prompt 结构稳定，输出 XML 格式，ElementTree 解析。

### 创新点 4：发现"检测-定位鸿沟"作为 LLM 的真实瓶颈

- **已有方法**：传统 HT 检测报告通常只给"是否检测到"，不区分"定位精度"。
- **本文关键区别**：通过 TLC (Trigger Line Coverage) + PLC (Payload Line Coverage) 显式分离"是否存在"和"在哪行"两个问题。
- **具体性**：
  - 全部 3 个 LLM 在 baseline 上达到 14/0/0 完美检测（Detection 100%）。
  - 但定位精度差距大：GPT-4o TLC 0.98 vs PLC 0.32，Gemini TLC 0.82 vs PLC 0.46。
  - 扰动后定位精度进一步下降（TLC 0.72-0.86，PLC 0.20-0.33）。
  - 结论：LLM 在"判断是否存在 HT"上接近完美，但"指出哪一行"仍远弱于人类专家。

### 创新点 5：成本-性能 trade-off 表（Table V）

- **已有方法**：多数 HT 检测论文只报准确率，不报成本。
- **本文关键区别**：首次给出 3 个 LLM 的 Time/Sample、Token/Sample、Cost/Sample 数据，让工业部署可量化选择。
- **具体性**：
  - Llama 3.1 速度最快 (2.63s/sample) 但精度最低 (66.7% precision)。
  - Gemini 1.5 Pro 完美检测但慢 (10.91s/sample) 且免费 tier 限制。
  - GPT-4o 平衡点：6.01s + $0.0079/sample + 100% precision + 85.7% recall。

### 9.1 在全流程中的位置

TrojanWhisper 的工作完全在 **(① RTL 设计) ↔ (⑥ 形式验证)** 之间，作为**源代码审计**层介入。它**不**生成 GDSII，不综合、不仿真门级。

│                                                              │

│   1) 用 GHOST benchmark (14 HT) + ICL prompt 检测             │
│   2) 输出 {trojans_found, trigger/payload 行号, type}          │
│   3) 人工审查 LLM 标出的可疑行                                 │
└──────────────────────┬───────────────────────────────────────┘
                       │
                       ▼

                       │
                       ▼

                       │
                       ▼
                  后续综合 / 后端流程 (论文未触及)
```

### 9.2 与传统 HT 检测方法的对比

| 维度 | 测试生成 | 形式验证 | 代码分析 (FANCI 等) | ML/GNN (GNN4TJ) | **TrojanWhisper** |
|---|---|---|---|---|---|
| 自动化程度 | 中 | 高 | 中 | 高 | **高** |
| 手工特征工程 | 中 | 低 | 中 | 高 | **零** |
| 可处理 RTL 规模 | 小 | 中 | 小 | 中 | **大** (128K context) |
| 状态空间爆炸 | 不适用 | 严重 | 不适用 | 部分 | **不适用** |
| HT 类型覆盖 | 难触发 | 依赖 property | 限于特定模式 | 依赖训练 | **3 类全** |
| 定位能力 | ❌ | ❌ | 部分 | ❌ | ✅ (TLC/PLC) |
| 训练数据需求 | 无 | 无 | 无 | **大量** | **无** |
| 准确率 (%) | <80 | 90-95 | 85-95 | 92-99 | **100/100** |
| Time/Sample | 慢 | 慢 | 中 | 快 | 中 (10.91s) |
| 开源 | 难 | 难 | 部分 | ✅ | ✅ (GitHub) |

**差距分析**：

1. **不替代形式验证**：TrojanWhisper 是在 RTL 层做语义推理，形式验证是数学证明，两者互补。形式验证对"HT 是否存在"有严格证明，TrojanWhisper 给"概率判断 + 行级定位"。
2. **不替代 ML/GNN**：GNN 在门级网表上比 RTL 表现更好（结构化数据更易学），但需要大量训练数据 + 手工图特征。
3. **不替代人工审查**：TLC/PLC 即使最高也只 0.98/0.46，最终仍需人工审查 LLM 标出的可疑行。
4. **不替代商业 EDA 签核**：TrojanWhisper 不做综合、不做 STA、不做功耗分析，**无法**判断 HT 是否会在 P&R 之后"激活"。

**结论**：TrojanWhisper 是 3PIP 验收流程的**预筛工具**——在形式验证之前快速过滤"高概率含 HT"的设计，节省 90% 人工审查时间。

## 10. 讨论与局限

### 10.1 论文自述的局限

1. **Token 限制影响 scalability**："token count impacting scalability, which limits the handling of larger designs (a possible workaround could be partitioning larger designs)"。128K-200K context window 对千万门级 SoC 不够用。
2. **LLM 概率性行为**："The probabilistic behavior of LLMs imposes non-determinism, HT signatures leaking out, and potential circumvention."——同一条 prompt 两次跑结果可能不同；HT 签名库可能通过 prompt injection 泄露；HT 作者可以专门构造"绕过 LLM"的代码。
3. **扰动引擎基础**："The perturbation engine is implementing basic code transformations."——只做了变量名混淆、冗余逻辑、FSM 重构，没做更激进的"代码混淆 + 控制流平坦化 + 不透明谓词"（这些是 obfuscation 工具常用的）。
4. **样本量小**："A small sample of benchmark RTL designs to test our ideas on."——只有 14 个 HT 样本，远不及 VerilogEval 的 156 题。
5. **本地 vs 云成本权衡**："The cost for running locally vs. the risks of using the cloud and risk privacy for critical designs."——用 GPT-4o API 上传 3PIP 源码有 IP 泄露风险，本地跑 Llama 3.1-70B 又贵。
6. **TCCA 仅 50-71%**：Type-3 分类 TCCA 在 baseline 上 GPT-4o 0.500、Gemini 0.333、Llama 0.333，扰动后进一步下降，远未达到实用水平。
7. **缺乏 zero-shot 泛化测试**：所有 LLM 训练截止日期都在 2023Q4，论文声称 HT 样本上传"晚于"cutoff，但没提供具体日期对比。

### 10.2 代码/复现层面的问题

1. **Repository 不完整**：https://github.com/HSTRG1/TrojanWhisper.git 公开了 prompt 模板和评估脚本，但**未公开** 14 个 HT 样本（需要去 GHOST benchmarks 单独下载）。
2. **API key 依赖**：复现必须先申请 OpenAI / Google / Groq 三家 API key，且每次跑都会产生费用（GPT-4o $0.0079/sample × 28 samples ≈ $0.22 + API 配额）。
3. **Icarus 11.0 版本要求**：旧版 Icarus 对 SystemVerilog 2005 部分语法不兼容，需要 11.0+。
4. **XML 解析脆弱**：LLM 输出偶尔会破坏 XML 结构（如未闭合的 `<`、多余的换行），需要健壮的 ElementTree 异常处理。
5. **prompt 模板未给完整**：论文只说"carefully crafted prompts encoding hardware security domain knowledge"，但没公开完整 prompt 文本。复现时 prompt 不同可能结果差异巨大。
6. **GHOST benchmarks 上传日期不明**：论文说"uploaded to GitHub after the knowledge cutoff date"，但 GitHub 仓库 https://github.com/HSTRG1/GHOST_benchmarks 实际创建日期需要核实。

### 10.3 本资料包的批判性分析

**优点**：
- **第一次**系统评估 LLM 在 RTL HT 检测任务上的能力，方法论贡献大于工具贡献。
- **4 维评估指标** (Detection / TLC / PLC / AC / TCCA) 比传统二元"是否检测到"更全面。
- **扰动引擎**直接回应了"LLM 是否靠记忆"的质疑——Gemini 1.5 Pro 在扰动后仍 100/100% 是强证据。
- **成本-性能 trade-off 表**让工业部署有据可依。
- **多 LLM 对比** (GPT-4o / Gemini 1.5 / Llama 3.1) 避免单模型偏见。

**问题**：
- **样本量过小**：14 个 HT 样本，统计显著性弱。Type-1 / Type-2 都只有 4 个样本，TCCA 0.500 vs 0.750 的差异在 n=4 上无法做 t-test。
- **"100/100%" 的解读**：只在 14 个样本上 100%，不代表在 140 个样本上仍 100%。Trust-Hub 上有几百个 HT benchmark，论文只挑了 14 个。
- **Knowledge cutoff 论证不严**：仅说"uploaded after cutoff"，但 LLM 的训练数据可能来自更早的网络爬取（GitHub commits、StackOverflow、HDL 教程）。Trust-Hub 2017 年的 SRAM 经典 HT 可能在多个 LLM 训练集中出现。
- **TCCA 是真正的瓶颈**：50-71% 的 TCCA 意味着 LLM 经常把 Type-1 误判为 Type-2 或 Type-3，**无法用于需要区分 HT 类型的 mitigation 决策**。
- **缺乏 zero-shot 泛化**：所有 LLM 都在 2023Q4 之前 cutoff，没测试"训练集完全没有的新 HT 类型"的表现。
- **没有对比 human expert**：论文说"LLM 接近完美"，但没有请硬件安全专家做同一 benchmark 做对照，无法证明"LLM = 人类专家"。

**与同类工作对比**：

| 方法 | LLM 类型 | Detection | 定位 | 扰动测试 | 公开代码 |
|---|---|:---:|:---:|:---:|:---:|
| **TrojanWhisper** | 通用 LLM | ✅ 100/100% | ✅ TLC/PLC | ✅ | ✅ |
| GNN4TJ [2] | GNN | ✅ 92/97% | ❌ | ❌ | ✅ |
| GCN [18] | GNN | ✅ 98.9/88.4% | ✅ | ❌ | 部分 |
| GBDT [16] | 决策树 | ✅ 99/98% | ✅ | ❌ | ❌ |

| DeTrust [8] | 形式化 | ⚠️ 反例 | ❌ | ❌ | ❌ |

TrojanWhisper 的核心优势是**零训练数据需求 + 完美检测率 + 定位能力**，三者结合在 SOTA 中无对手。主要竞争对手是 GBDT (MLCAD'24)，速度更快但需要手工特征工程。

## 12. 一分钟复述版

1. **核心问题**：硬件木马 (HT) 在 RTL 层难以检测——传统方法（测试生成、形式验证、代码分析、GNN）各有局限（状态爆炸、需 golden reference、需大量训练数据）。
2. **方案**：TrojanWhisper = HT 签名库 + 扰动引擎 + LLM 检测引擎，用 GPT-4o / Gemini 1.5 Pro / Llama 3.1 直接审计 RTL。
3. **数据集**：14 个 HT 样本 (3 类：功能篡改 / 信息泄露 / DoS) 来自 3 个干净开源设计 (SRAM 52 行、UART 430 行、AES-128 768 行)，**上传日期晚于 LLM cutoff**。
4. **基线结果**：GPT-4o + Gemini 1.5 Pro 都达到 **14/0/0 完美检测**，Llama 3.1 在 HT2 上有 4 个 FP。
5. **扰动结果**：Gemini 1.5 Pro **仍 14/0/0 完美**，GPT-4o 退化到 12/0/2，Llama 3.1 退到 12/6/2。证明 Gemini 真的"理解"电路，而非记忆 Trust-Hub。
6. **检测-定位鸿沟**：所有 LLM 在"是否存在 HT"上接近完美，但 TLC (0.72-0.98) 和 PLC (0.32-0.46) 远低于 100%，扰动后进一步下降 (TLC 0.72-0.86, PLC 0.20-0.33)。
7. **类型分类弱**：TCCA 在 baseline 上 GPT-4o 0.714 / Gemini 0.571 / Llama 0.444，扰动后 Llama 跌到 0.222——LLM 难以区分 HT 类型。
8. **成本权衡**：Llama 3.1 速度最快 (2.63s/sample) 但精度最低；Gemini 1.5 完美但慢 (10.91s)；GPT-4o 平衡点 (6.01s + $0.0079/sample + 100%/85.7%)。
9. **局限**：样本量小 (n=14)、TCCA 远未实用、扰动引擎基础、knowledge cutoff 论证不严、缺 human expert 对照。
10. **意义**：唯一同时达到 100/100% 检测率 + 具备行级定位 + 零训练数据需求的 HT 检测方法，是 3PIP 验收流程的高效预筛工具。
