## 1. 一句话定位

**VeriTrace 是首个在 VerilogEval-V2 上达到 100% Pass@1 的多 Agent RTL 生成系统，核心创新是 Agentic Temporal Exploration——赋予 Inspector Agent 对信号选择、时间窗口边界和迭代深度的完全自主控制权，让 LLM 像人类验证工程师一样做假设驱动的根因分析，而非在预设信号/时间戳上做模式匹配。在 Claude Sonnet 4.0 相同骨干上，VeriTrace 比最强开源基线 MAGE 高 +5.1%（97.4% vs 92.3%），且 token 消耗减少 18%。**

这句话里的 5 个承重点，后面逐一拆解：

1. **调试 Action Space 完整性瓶颈** — 论文系统分析了现有 Multi-Agent 系统（MAGE、VerilogCoder）的调试能力缺口：MAGE 无信号选择、无时间自由度、无迭代；VerilogCoder 虽支持信号选择但锚定在首个 mismatch 时间戳。VeriTrace 首次实现三种能力的联合——Agentic Signal Selection × Agentic Temporal Exploration × Iterative Query。
2. **Agentic Temporal Exploration 方法论** — Inspector Agent 不接收完整 VCD dump，而是自主选择信号 σ_i、时间窗口 [t_start, t_end] 发起波形查询，观察结果后形成/修正假设，决定继续查询或终止。这与人类工程师在 Synopsys Verdi 中的工作流一致。
3. **诊断与修复分离架构** — Inspector 负责诊断（输出 Inspector Report 含行为偏差描述、根因推理、建议修复方向），RTL Debugger 负责精准编辑。两个 Agent 各自拥有聚焦的 context window，避免单 Agent 同时处理波形分析和代码修改的 context 膨胀。
4. **单调减错保证** — Debugger 编辑后重新仿真：若 mismatch 数 m(C') < m(C) 则接受编辑，否则回滚。这防止修复一个 bug 引入另一个的回归，确保单调前进。
5. **100% Pass@1 + 18% token 节省** — Claude Sonnet 4.5 达到 156/156 完美；相比无 Inspector 的 baseline，总 token 从 26.7k 降至 21.9k（-18%），debug 阶段的 token 从 8.5k 降至 0.4k + 5.2k（Inspector）= 5.6k。

## 2. EDA 阶段映射（①-⑰）

参照 [芯片流程.md](../芯片流程.md) 的 17 阶段标准编号。VeriTrace 定位于数字前端 RTL 功能验证层。

| 阶段 | 覆盖 | 说明 |
|------|:---:|------|
| **① RTL 设计** | ✅ **核心** | VeriTrace 从自然语言规格自动生成 Verilog RTL（RTL Agent），经仿真→调试循环修复至功能正确 |
| **② RTL 功能仿真** | ✅ **核心** | Simulation Judge 使用 Icarus Verilog + golden testbench 判定 mismatch 数；Inspector 基于 VCD 波形做时序探索 |
| ③ 逻辑综合 | ❌ | 不涉及——VeriTrace 不将 RTL 翻译为门级网表，不评估 PPA |
| ④ 门级仿真 | ❌ | 不涉及 |
| ⑤ STA（静态时序分析） | ❌ | 不涉及 |
| ⑥ 形式验证 | ❌ | 不涉及——VeriTrace 依赖仿真（有穷），不做形式等价性检查 |
| ⑦-⑰ | ❌ | 不涉及物理实现及后续阶段 |

**覆盖率：2/17。** VeriTrace 仅覆盖 RTL 设计 + 功能仿真闭环，属于芯片流程中最前端的「逻辑对不对」验证层。它的输出是仿真通过的 RTL 代码——不保证可综合、不保证时序收敛、不保证 testbench 未覆盖的 corner case。

## 3. 输入 / 输出

### 3.1 输入（数据类型/格式/最小具体示例）

**(1) 自然语言规格**（来自 VerilogEval-V2 benchmark）：

```text
Problem 155: Design a sequence detector that monitors a serial input
stream. The detector should assert 'detected' high for exactly one clock
cycle when the pattern '1011' is detected. Overlapping sequences should
be detected. Include an active-low asynchronous reset.
```

**(2) Golden Testbench**（VerilogEval-V2 提供，用于判定功能正确性）：

```verilog
module tb;
  reg clk, rst_n, in;
  wire detected;
  // ... 实例化 DUT、产生激励、自动比对期望输出 ...
endmodule
```

**(3) Testbench Agent 修改后的 Testbench**（增加全波形 dump）：

```verilog
initial begin
  $dumpfile("dump.vcd");
  $dumpvars(0, tb);  // dump 所有信号供 Inspector 按需查询
end
```

### 3.2 输出

**(1) 功能正确的 Verilog RTL**（mismatch = 0）：

```verilog
module seq_detector (
  input clk, rst_n, in,
  output reg detected
);
  // FSM 状态编码 + 重叠检测逻辑（经 Inspector 调试修正）
endmodule
```

**(2) Inspector Report**（诊断报告，JSON 结构化）：

```text
Diagnosis: FSM state S_B2 transitions to S_IDLE instead of S_B3
when in=1 and current state expects pattern continuation.
Root cause: The next-state logic for S_B2 incorrectly prioritizes
the reset condition over the pattern-matching condition.
Suggested fix: In S_B2, when in==1, transition to S_B3 regardless
of other conditions.
```

**(3) 调试日志**（完整 Inspector 查询序列）：

```text
[Iter 1] signals={detected, state}, t_start=0, t_end=50
  → state transitions: IDLE→B1@t5, B1→B2@t10, B2→IDLE@t15 ⚠
[Iter 2] signals={in, state}, t_start=10, t_end=20
  → in=1 @t15, but state goes B2→IDLE (expected B2→B3)
[Iter 3] signals={state, next_state_logic}, t_start=14, t_end=16
  → Confirmed: next_state = IDLE when state==B2 && in==1
[Diagnosis complete] → output Inspector Report
```

### 4.2 核心模块详解

#### A. Testbench Agent

**功能**：修改 golden testbench，添加 `$dumpvars(0, tb)` 使所有信号可被 Inspector 按需查询。

**设计要点**：
- 不修改 testbench 的逻辑——仅增加波形 dump 语句
- 与 RTL Agent 共享同一 LLM 骨干（Claude Sonnet 4.0/4.5）
- 论文实验显示 Testbench Agent 消耗约 5.4k-6.8k token

#### B. RTL Agent + High-Temperature Sampling

**功能**：从自然语言规格生成初始 Verilog RTL。

**设计要点**：
- 采用 MAGE [11] 的 High-Temperature RTL Sampling 策略（温度 t=0.85），一次生成多个候选，Simulation Judge 挑选 mismatch 最少的
- 严格语法检查（Icarus Verilog 编译）通过后才进入仿真
- 对于中低难度问题（约 149/156），初始生成即通过，不触发调试闭环

#### C. Simulation Judge

**功能**：使用 Icarus Verilog 编译 RTL + testbench，运行仿真，统计输出 mismatch 数。

**输出**：
- 首个 error timestamp t_err
- mismatch 计数 m(C)
- 完整波形 VCD 文件 W

#### D. Inspector — Agentic Temporal Exploration（核心创新）

这是 VeriTrace 区别于所有现有系统的关键模块。

**Action Space 形式化**：

设 S 为自然语言规格，C 为当前 RTL 代码，t_err 为仿真报告的首次 error 时间戳，W 为完整波形。

在第 i 轮迭代中，Inspector 选择：
- 信号集合 σ_i
- 时间窗口 [t_start_i, t_end_i]

波形追踪工具返回自然语言格式的快照：

$$
\omega_i = \text{TRACE}(W, \sigma_i, t^{\text{start}}_i, t^{\text{end}}_i)
$$

- `W`：完整 VCD 波形文件
- `σ_i`：Inspector 第 i 轮选择的信号集合（如 {state, in, detected}）
- `[t_start, t_end]`：Inspector 选择的时间窗口（clock cycles）
- `TRACE`：波形提取函数——从 VCD 中抽取指定信号在指定时间窗的值变化序列，以自然语言描述返回
- `ω_i`：第 i 轮获得的波形快照（文本形式，如 "state transitions: IDLE→B1@t5, B1→B2@t10"）

Inspector 遵循 ReAct [24] 推理模式，在每步产生 thought τ_i：

$$
\tau_i, a_i = \text{THINK}(S, C, t_{\text{err}}, \omega_1, \ldots, \omega_i)
$$

- `τ_i`：第 i 步的推理思考（自然语言，如 "state went B2→IDLE when in=1,让我检查 in 和 state 的关系"）
- `a_i`：动作决策，`a_i ∈ {QUERY, FINISH}`
- `THINK`：LLM 的推理函数——基于累积的波形观察 {ω_1,...,ω_i} 和规格 S、代码 C，决定下一步行动
- 若 `a_i = QUERY`：选择新参数 (σ_{i+1}, t_start, t_end)，发起下一轮查询
- 若 `a_i = FINISH`：终止探索，输出 Inspector Report R

**工程直觉**：这模仿的是人类工程师在 Verdi 中的工作流——工程师看到 mismatch 后不会盲目翻所有波形，而是先选一个"嫌疑信号"（如 state 寄存器），在"嫌疑时间窗"（error 前几个周期）观察，形成假设后再选更深的信号验证。VeriTrace 的 Inspector 正是这套流程的自动化。

**为什么这样设计**：替代方案是给 LLM 喂完整 VCD dump——这会迅速耗尽 context window（一个中等模块的 VCD 可达数百 MB），且 LLM 不擅长从原始波形数值中提取模式。Inspector 的"按需查询"模式让 token 成本随诊断复杂度（而非设计规模）增长，为大设计扩展留下空间。

**最关键的设计决策 —— 不让 Inspector 看到 testbench**：

> "the testbench is not exposed to the Inspector since the goal of self-correction should be finding the mismatched behavior between the RTL Code C and the functional description S instead of the testbench."

Inspector 只能看到：
- 自然语言规格 S（"应该做什么"）
- RTL 代码 C（"实际做了什么"）
- 波形快照 ω（"电路真实行为"）

看不到 testbench（"怎么判定的"）——这防止 Inspector "对着 testbench 调代码"（overfit to testbench）而非理解规格与实现的语义偏差。

#### E. RTL Debugger

**功能**：基于 Inspector Report R 对 RTL 做精准编辑。

**设计要点**：
- 不重写整个模块——只编辑 Inspector 识别出的具体逻辑块
- 编辑后重新仿真：若 m(C') < m(C) 则接受，否则回滚
- 此单调保证防止"修复一个 bug 引入另一个"的退化

#### F. 闭环迭代

```
while m(C) > 0 and iteration < M (M=10):
    1. Inspector 执行 Agentic Temporal Exploration → Report R
    2. Debugger 根据 R 做 targeted edit → C'
    3. Simulation Judge: m(C') vs m(C)
       - m(C') < m(C): C ← C', 继续
       - m(C') ≥ m(C): 回滚, 继续（Inspector 可能需要更准确的诊断）
    4. m(C') = 0: 终止，成功
```

### 4.3 与现有 Multi-Agent 系统的 Action Space 对比

| 能力 | MAGE [11] | VerilogCoder [10] | **VeriTrace** |
|------|:---:|:---:|:---:|
| Agentic Signal Selection | ✗ | ✓ (AST-based) | **✓** |
| Agentic Temporal Exploration | ✗ | ✗ | **✓** |
| Iterative Query | ✗ | ✓ | **✓** |
| 诊断/修复分离 | ✗ | ✗ | **✓** |
| 单调减错保证 | ✗ | ✗ | **✓** |

**关键差距**：
- MAGE：只捕获首个 error 时刻的 I/O 值做 checkpoint，无信号选择、无时间自由度、无迭代
- VerilogCoder：用 AST 分析自动选信号，但时间上锚定在第一个 mismatch 时刻，无法向前追溯错误根因
- VeriTrace：三个维度全自主——Inspector 选信号、选时间窗、迭代探索

## 5. 关键公式

### 5.1 波形查询形式化

$$
\omega_i = \text{TRACE}(W, \sigma_i, t^{\text{start}}_i, t^{\text{end}}_i)
$$

- `W`：完整 VCD 波形文件（由 `$dumpvars` 生成）
- `σ_i`：Inspector 在第 i 轮选择的信号集合
- `[t_start, t_end]`：Inspector 选择的时间窗口
- `TRACE`：波形提取函数——从二进制 VCD 中抽取信号值变化序列，转为自然语言描述
- `ω_i`：第 i 轮获得的文本波形快照

### 5.2 ReAct 推理循环

$$
\tau_i, a_i = \text{THINK}(S, C, t_{\text{err}}, \omega_1, \ldots, \omega_i)
$$

- `τ_i`：第 i 步的推理思考（hypothesis formation/refinement）
- `a_i ∈ {QUERY, FINISH}`：动作决策
- `S`：自然语言功能规格
- `C`：当前 RTL 代码
- `t_err`：仿真报告的首个 error 时间戳
- `{ω_1, ..., ω_i}`：截至第 i 步累积的所有波形快照

### 5.3 单调减错接受条件

论文未给出编号公式，以下是对其算法行为的形式化：

$$
\text{Accept}(C') \iff m(C') < m(C)
$$

- `m(C)`：RTL 代码 C 在 golden testbench 下的输出 mismatch 计数
- `C'`：Debugger 编辑后的 RTL
- 若 `m(C') ≥ m(C)`：回滚，保留原版本 C
- 此条件保证每次接受的编辑都单调减少 mismatch 数

**工程直觉**：共享状态逻辑（如 FSM next-state）有级联效应——修复一个状态转移可能破坏另一个。不做回滚的话，Debugger 可能在多次编辑后把整个模块改得面目全非。该条件等价于"只接受净正向的编辑"。

### 5.4 终止条件

$$
\text{Terminate} \iff m(C) = 0 \;\lor\; \text{iteration} \ge M
$$

- `M = 10`（论文设置的最大调试迭代轮数）
- 理想终止：所有 test case 通过 (`m(C) = 0`)
- 强制终止：达到最大轮数仍无法消除所有 mismatch

## 6. 训练与实验设置

### 6.1 是否需要训练

**不需要训练。** VeriTrace 是一个纯推理时 Multi-Agent 系统——不微调任何模型参数。所有 Agent（Testbench、RTL、Inspector、Debugger、Simulation Judge）使用现成的 Claude Sonnet 4.0 或 4.5 作为 LLM 骨干。

实验设置：
- **LLM 骨干**：Claude Sonnet 4.0 / Claude Sonnet 4.5 [35]
- **温度**：t = 0.85（RTL 生成的 High-Temperature Sampling）
- **最大 Inspector 迭代**：N = 5
- **最大调试闭环轮数**：M = 10
- **Pass@1 采样**：n = 3 次运行取平均（减少采样方差）
- **Benchmark**：VerilogEval-V2（156 道题，覆盖组合逻辑 + 时序电路 + FSM）
- **仿真器**：Icarus Verilog

### 6.2 实验结果

**主结果（Table II）**：

| Method | Open Source | LLM Model | VerilogEval-V2 Pass@1 |
|--------|:---:|------|:---:|
| Single Agent | N/A | Claude Sonnet 4.5 | 81.4% |
| VerilogCoder [10] | ✓ | GPT4-Turbo | 94.2% |
| ACE-RTL [21] | ✗ | Custom + Claude Sonnet 4.0 | 95.5% (APR) |
| MAGE [11] | ✓ | Claude 3.5 Sonnet | 95.7% |
| MAGE (复现) | ✓ | Claude Sonnet 4.0 | 92.3% |
| **VeriTrace** | ✓ | Claude Sonnet 4.0 | **97.4%** |
| **VeriTrace** | ✓ | Claude Sonnet 4.5 | **100%** |

**关键发现**：
- VeriTrace 是首个在 VerilogEval-V2 上达到 100% Pass@1 的开源系统
- 在相同 Claude Sonnet 4.0 骨干上，VeriTrace 比 MAGE 高 +5.1%（97.4% vs 92.3%）——这 5.1% 完全归因于调试 action space 的完整性
- Claude Sonnet 4.0→4.5 的提升（97.4%→100%）表明当前 Multi-Agent 系统仍对底层 LLM 敏感

**消融实验（Table III）**：

| 配置 | Pass@1 | 总 Token | Debug Token | LLM Call 次数 |
|------|:---:|:---:|:---:|:---:|
| w/o Inspector | 98.29% | 26.7k | 8.5k | 6.4 |
| w/ Inspector | **100%** | **21.9k** | 0.4k + 5.2k | 6.7 |

**关键发现**：
- Inspector 使总 token 消耗减少约 18%（26.7k → 21.9k）
- Debugger token 从 8.5k 骤降至 0.4k——因为 Inspector 提供了精准诊断后，Debugger 只需做极小范围的精准编辑
- Inspector 自身消耗 5.2k token——净节省约 3.3k token
- LLM 调用次数略增（6.4→6.7），因为 Inspector 的迭代查询增加了 round-trip

**困难问题分析（Table IV）**：论文进一步分析了 7 个始终触发调试闭环的问题：

| Problem | Type | w/o Inspector Pass@1 | w/ Inspector Pass@1 | w/o Inspector Debug Tokens | w/ Inspector Debug Tokens |
|------|------|:---:|:---:|:---:|:---:|
| Prob062 | Combinational | 100% | 100% | 4k | 7.3k |
| Prob070 | Combinational | 100% | 100% | 10.5k | 6.3k |
| Prob078 | Sequential | 100% | 100% | 18.4k | 7.6k |
| Prob093 | Combinational | 100% | 100% | 47.2k | 36.5k |
| **Prob137** | **FSM** | **0%** | **100%** | 301.7k | 339.6k |
| **Prob149** | **FSM** | **33%** | **100%** | 281.2k | 256.9k |
| **Prob155** | **FSM** | **33%** | **100%** | **530.8k** | **32.6k** |

**最惊人的发现**：
- 3 个 FSM 问题（Prob137/149/155）：w/o Inspector 仅 0-33% Pass@1，w/ Inspector 全部→100%
- Prob155：Inspector 将总 token 从 619k 降至 110k（**减少 5.6×**），因为精准诊断避免了无目标的盲目重试
- 论文观测到 w/o Inspector 时 Debugger 在多次失败后倾向于"重写整个模块"，消耗巨量 token 且仍失败

## 7. 创新点

1. **首次识别调试 Action Space 完整性瓶颈** — 论文通过系统对比揭示：现有 Multi-Agent 系统的 95% 天花板并非 LLM 能力不足，而是调试 Action Space 不完整——缺少 Agentic Signal Selection、Agentic Temporal Exploration 或 Iterative Query 中的至少一项。

2. **Agentic Temporal Exploration** — 赋予 LLM Agent 对信号选择、时间窗口和迭代深度的完全自主权，模拟人类工程师的假设驱动调试流程。这是首个将"人类调试方法论"完整映射到 LLM Agent Action Space 的工作。

3. **诊断与修复分离架构** — Inspector 只诊断不修代码，Debugger 只修代码不读波形。两个 Agent 各自拥有聚焦的 context window，避免单 Agent 同时处理两种异构信息的认知过载。

4. **单调减错回滚机制** — 简单的 `m(C') < m(C)` 条件防止编辑退化，在共享状态逻辑的级联效应下保证净正向进展。

5. **100% Pass@1 + Token 节省** — 首个在 VerilogEval-V2 上达到完美的系统，同时通过精准诊断实现 18% token 节省。Prob155 案例中 token 节省 5.6×。

## 9. 与芯片流程的关系

### 9.1 在全流程中的位置

VeriTrace 工作在芯片流程的最前端——RTL 功能验证闭环。

```text
① RTL 设计 ← VeriTrace 在此介入：生成 RTL + 调试至功能正确
    │
    ▼
② RTL 功能仿真 ← VeriTrace 的验证闭环：Icarus 编译 + testbench 仿真
    │
    ▼
③ 逻辑综合 ← VeriTrace 不涉及，但这是它交付的下游第一步
```

VeriTrace **接手**的是：自然语言规格 + golden testbench。

VeriTrace **交棒**给逻辑综合的是：testbench 下 mismatch = 0 的 Verilog RTL。

### 9.2 「仿真通过」到「芯片可制造」的鸿沟

VeriTrace 的"100% 通过" = 给定 testbench 下 156 道题全部 mismatch = 0。但到真正的芯片：

1. **Testbench 覆盖率**：golden testbench 覆盖多少行为？未覆盖的 corner case 可能仍有 bug
2. **可综合性**：Icarus 仿真通过 ≠ Yosys/Design Compiler 可综合（latch 推断、多驱动等问题）
3. **时序收敛**：不涉及 STA——不知道关键路径延迟能否满足时钟频率
4. **多模块交互**：VerilogEval-V2 是单模块 benchmark，工业设计涉及模块间协议、跨时钟域
5. **PPA 优化**：不评估面积、功耗、性能

## 10. 讨论与局限

1. **VerilogEval-V2 单模块局限**："VerilogEval-V2 comprises 156 single-module problems with provided golden testbenches. Industrial designs involve multi-module hierarchies, incomplete specifications, and far larger signal spaces."——156 道题全是单模块，有 golden testbench。工业设计的模块层级、不完整规格、海量信号空间对 Inspector 的扩展性未知。

2. **Golden Testbench 依赖**：VeriTrace 依赖 golden testbench 判定正确性。在真实场景中，testbench 本身也需要被验证（是否覆盖了规格的所有行为）。

3. **FSM 问题的 token 成本**：虽然 Inspector 减少了盲目重试的浪费，但对 Prob137（最难的 FSM），w/ Inspector 仍消耗 339.6k debug tokens + 56 次 LLM 调用——这对学术预算不可忽视。

4. **全信号 dump 存储开销**：Testbench Agent dump 所有信号——对于 VerilogEval-V2 的单模块可忽略，但对数千信号的工业模块，可能需要自适应 dump 或按需重仿真。

5. **LLM 敏感性**：Claude Sonnet 4.0→4.5 的 Pass@1 从 97.4%→100%，表明当前系统仍高度依赖底层 LLM。论文指出 MAGE 在 Claude Sonnet 4.5 上反而性能退化（归因于 testbench 语法和输出解析的脆弱性）。

6. **CVDP 扩展未完成**：论文报告了在 2 个 CVDP spec-to-RTL 问题上的初步成功，但全面评估留作 future work。CVDP 的多模块、长规格特性才是真正的压力测试。

7. **Action Space 仍有缺口**：虽然 VeriTrace 补全了信号选择+时间探索+迭代三大能力，但与人类工程师相比仍缺——不能修改 testbench、不能添加断言监控、不能在波形上标注和测量（如测量两个信号之间的延迟周期数）。

## 12. 一分钟复述版

1. **问题**：现有 Multi-Agent RTL 生成系统（MAGE、VerilogCoder）卡在 95% Pass@1——不是 LLM 不够强，而是调试 Action Space 不完整。MAGE 只能看首个 error 的 I/O，VerilogCoder 锚定在首个 mismatch 时间戳。都缺假设驱动的根因分析能力。

2. **方法**：VeriTrace = RTL Agent + Testbench Agent + Inspector（Agentic Temporal Exploration）+ Debugger + Simulation Judge。Inspector 像人类工程师用 Verdi 一样：选信号、选时间窗、看波形、形成假设、再查、确认根因→输出诊断报告→Debugger 做精准编辑。

3. **保证机制**：（1）Inspector 看不到 testbench——防止 overfit；（2）m(C') < m(C) 单调接受——防止编辑退化；（3）诊断与修复 Agent 分离——各自聚焦。

4. **结果**：Claude Sonnet 4.5 上 **100% Pass@1**（首个完美系统）；Claude Sonnet 4.0 上比 MAGE 高 +5.1%；总 token 减少 18%；最难的 FSM 问题（Prob155）token 减少 5.6×。

5. **局限**：单模块 benchmark、依赖 golden testbench、FSM 问题的 token 成本仍高、LLM 模型敏感、工业多模块扩展性未知。
