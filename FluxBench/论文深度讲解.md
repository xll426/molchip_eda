## 1. 一句话定位

**FluxBench 是一个评测 LLM Agent 能否端到端完成 RTL-to-GDS 全链路的工具交互式基准框架**——在 PicoRV32 + 商业 55nm 工具链的统一任务上，固定变量地比较 3 种 Agent 架构 x 4 个基础模型 x 2 个时钟目标（共 24 次完整 run），用端到端得分（0-100）、阶段完成率、Token ROI 和 9 类失败分布回答一个核心问题：**现有 AI Agent 到底能不能可靠地跑完从综合到签核的完整物理设计流程？** 答案：能，但不靠模型强，靠执行架构好——FluxEDA 架构下所有模型均取得 90+ 分并完成全部三个阶段，而命令行 agent 有 56.8% 的物理实现失败来自 Tcl 命令和文件路径错误。同时发现相同设计进展下 Token ROI 可相差约 141 倍，揭示了"低成本早失败"与"高效验证进展"之间的巨大效率鸿沟。

这句话里的 6 个承重点，后面逐一拆解：

1. **RTL-to-GDS 全链路作为 Agent 评测任务** — FluxBench 将物理设计流程从"单次代码生成"升级为"长周期多轮工具交互的工程闭环"，要求 agent 在连续的设计数据库上跨 7 个子阶段自主决策。
2. **3x4x2 固定变量交叉评测** — 在相同任务、相同工具链、相同工艺下，系统比较 3 种 Agent 架构（Claude Code / CC+EDA Skills / FluxEDA）x 4 个基础模型（DeepSeek-V4 / GLM-5.2 / Claude Sonnet 5 / Kimi K3）x 2 个时序目标（350MHz loose / 700MHz tight）。
3. **执行架构决定可靠性，而非基础模型** — DeepSeek-V4 在三种架构下得分跨度 11.67 → 97.94（差 86.27 分），同一模型在不同执行层下表现天壤之别。所有 FluxEDA run 均得分 90+ 并完成全部阶段。
4. **EDA Skills 效果不稳定** — 注入领域过程知识对 GLM-5.2 在 350MHz 下提升巨大（13.33 → 95.97），却严重降低 Claude Sonnet 5（87.05 → 11.67）和 Kimi K3（82.33 → 11.67）在 700MHz 的表现。
5. **Token ROI 揭示 141 倍效率差异** — 两个同为 13.33 分的 run，Token ROI 分别为 12.71 和 0.09，差约 141.2 倍。低成本的早期失败虽然便宜，但没有端到端价值。
6. **工具接口失配是首要瓶颈** — 31.7% 的物理实现失败来自 Tcl 命令与工具版本/模式不兼容，FluxEDA 的结构化接口将该类错误消为零。

## 2. EDA 阶段映射（①-⑰）

FluxBench 覆盖的是从 RTL 输入到最终 GDS 交付的**完整后端实现链**，但各阶段的评测深度并不均等。按照 [芯片流程](../芯片流程.md) 的 17 阶段标准编号，逐一精确映射：

| 阶段 | 覆盖 | FluxBench 中的具体工作 | 评测深度与失败情况 |
|------|:---:|------|------|
| **① RTL 设计** | ❌ | RTL 作为输入给定（PicoRV32），不要求 agent 生成 Verilog | 不在评测范围内 |
| **② RTL 功能仿真** | ❌ | 不涉及功能仿真验证 | 假设 PicoRV32 RTL 功能正确 |
| **③ 逻辑综合** | ✅ **核心** | RTL → 门级网表 + 时钟门控检查。使用商业综合工具（推测 Synopsys Design Compiler 或 Cadence Genus），SDC 约束驱动综合 | **唯一零失败阶段**：所有架构 8/8 通过。评测依据：netlist 生成 + clock-gating 检查 |
| **④ 门级仿真** | ❌ | 不涉及门级仿真验证 | 不在评测范围内 |
| **⑤ STA（静态时序分析）** | ✅ **核心** | setup/hold WNS/TNS 检查，**贯穿物理实现和 ECO 各步**，不是独立阶段而是嵌入式的持续验证 | 作为结果得分 S_result 的六项指标中的四项（Ws, Ts, Wh, Th），不单独评分 |
| **⑥ 形式验证** | ❌ | 不涉及逻辑等价性检查 | 不在评测范围内 |
| **⑦ 布局规划 (Floorplan)** | ✅ **核心** | die 定义、IO 引脚摆放、电源/地网格规划（powerplan） | **物理实现的第一关且是最大失败点**：全部 6 次命令行物理实现失败均涉及不完整的 I/O placement。评测子检查：I/O placement |
| **⑧ 标准单元摆放 (Placement)** | ✅ **核心** | 标准单元全局放置，目标最小化后续布线长度 | **0 失败**，说明标准单元 placement 本身对 agent 不是瓶颈。评测子检查：std-cell placement |
| **⑨ 时钟树综合 (CTS)** | ✅ **核心** | 生成时钟树、平衡 clock skew，插入缓冲器逐级放大驱动力 | 1 次失败（伴随 IO placement 失败），独立 CTS 失败少见。但 CTS 错误在总体失败类别中占 10.4%。评测子检查：CTS |
| **⑩ 布线 (Routing)** | ✅ **核心** | 详细布线，使用多个金属层连接所有门 | 0 失败作为"阶段未完成"，但布线 DRC 违例在错误分类中占 5.9%。评测子检查：routing |
| **⑪ 后仿真** | ❌ | 不涉及布线后的 SPEF+SDF 时序仿真 | 不在评测范围内 |
| **⑫ 物理验证 (DRC/LVS)** | ✅ 辅助 | DRC 规则检查（作为 routing 后验），不单独评分但 DRC 违例属于错误类别 T6（占 5.9%） | 作为 routing 的自然延伸，不设独立门控检查点 |
| **⑬ 签核 (Signoff)** | ✅ **核心** | 物理感知 ECO 迭代修复 setup/hold 违例 → 最终 GDS layout + QoR 报告。包含时序签核和物理签核的最终检查 | **最频繁的晚期失败点**：CC 仅 3/8 完成 ECO，CC+Skills 仅 2/8 完成。ECO 是区分"跑通流程"与"跑出可用芯片"的关键 |
| **⑭~⑰ 流片/制造/封装/测试** | ❌ | 不涉及 | 不在评测范围内 |

**覆盖率：8/17 核心 + 1/17 辅助 = 9/17 阶段。** 在 8 个核心覆盖阶段中，③ 逻辑综合是 agent 最容易通过的阶段（8/8），⑬ 签核/ECO 是最困难的阶段（CC 仅 3/8，CC+Skills 仅 2/8）。

> FluxBench 的核心边界：它评测的是"给定正确 RTL，Agent 能否完成物理实现"，而非"Agent 能否从零设计 RTL"。这与 RTLLM（评测 RTL 生成）和 VerilogEval（评测 RTL 功能正确性）是正交维度——前者测"后端流能力"，后者测"前端设计能力"。两者合在一起才构成完整的芯片设计 agent 评测。

## 3. 输入 / 输出

### 3.1 输入

FluxBench 的输入不是单一的 prompt，而是一个**完整的工程任务包**：

| 输入项 | 内容 | 格式/来源 | 说明 |
|--------|------|-----------|------|
| 目标 RTL | PicoRV32 RISC-V CPU core | Verilog（约 2000 行） | Clifford Wolf 开源，面积优化的 RISC-V 实现，支持 RV32I/E/M/C 指令集 |
| 设计约束 (SDC) | 两套时钟约束 | SDC 格式 | 350 MHz（周期 2.857ns，宽松）/ 700 MHz（周期 1.429ns，紧约束）。同一 RTL，不同时序压力 |
| 工艺配置 | 商业 55-nm 工艺库 | TECH / LIB / LEF | 完整标准单元库 + IO 库 + 内存编译器。含 timing/power/physical 三种库视图 |
| 任务 prompt | task id + session id + 设计描述 | 结构化文本 | 驱动外部 agent 连接本地 Agentic EDA 服务器 |
| Agent 架构 | 3 种：Claude Code / CC+EDA Skills / FluxEDA | 软件基础设施 | 固定任务和工具链，只变 agent 架构 |
| 基础模型 | 4 种：DeepSeek-V4 / GLM-5.2 / Claude Sonnet 5 / Kimi K3 | LLM API / 模型服务 | 每种架构配每种模型 |
| 本地 EDA 服务器 | 承载商业工具链的运行环境 | 服务器 + License | 含综合工具、P&R 工具、STA 工具的完整商业 EDA 软件栈 |

**SDC 约束的具体形态**（论文未给出完整 SDC 文本，以下为基于论文描述的示例性重构）：

```tcl
# 350 MHz loose target
create_clock -period 2.857 -name clk [get_ports clk]
set_input_delay  -max 1.0 -clock clk [get_ports {data_in[*]}]
set_output_delay -max 0.8 -clock clk [get_ports {data_out[*]}]
set_clock_uncertainty -setup 0.1 [get_clocks clk]
set_clock_uncertainty -hold  0.05 [get_clocks clk]

# 700 MHz tight target（其余约束相同，仅周期变化）
create_clock -period 1.429 -name clk [get_ports clk]
```

两个时钟目标的差异在于：350 MHz 下，每个时钟周期有 2.857ns 的时间窗口供组合逻辑完成运算；700 MHz 下只有 1.429ns——这对综合阶段的逻辑优化深度、floorplan 的面积-延迟权衡、placement 的拥塞控制、ECO 阶段的修复策略都提出了更高的要求。论文设计这一对目标的用意是区分"按食谱被动执行"和"主动优化决策"。

**任务 prompt 的结构**（论文未公开完整 prompt，以下为基于论文描述的逻辑结构）：

```
Task: Complete RTL-to-GDS implementation of PicoRV32
Design: PicoRV32 RISC-V core
Technology: Commercial 55nm
Clock target: 350MHz / 700MHz
Required stages: Logic Synthesis → Floorplan & Power → Placement → CTS → Routing → ECO → Signoff
Agent: [Claude Code | CC+EDA Skills | FluxEDA]
Model: [DeepSeek-V4 | GLM-5.2 | Claude Sonnet 5 | Kimi K3]
Session ID: <unique-id>
```

### 3.2 中间产物

Agent 在 RTL-to-GDS 流程中产生的关键中间产物（论文未展示具体内容，但根据 EDA 工具标准输出可推知）：

- **门级网表**（综合后）：PicoRV32 的 Verilog 网表，所有逻辑映射到 55nm 标准单元（如 AND2X1、DFFRHQX1 等），约数万门规模
- **DEF 文件**（floorplan 后）：芯片物理尺寸定义、IO pin 位置、电源/地 stripe 布局
- **DEF 文件**（placement 后）：每个标准单元的 (x, y) 坐标已确定
- **DEF 文件**（CTS 后）：时钟缓冲器插入后的完整物理布局
- **DEF 文件**（routing 后）：所有金属层的走线几何信息
- **时序报告**（每步后）：WNS/TNS 值，记录时序收敛进度
- **DRC 报告**（routing 后）：设计规则违例清单

每个中间产物都对应当前工具 session 的设计状态——这是 agent 理解"走到哪了"的唯一途径。

### 3.3 输出

每次完整评测 run 产出以下交付物和评测数据：

**最终设计交付物**（仅当三阶段全部完成时）：
- 门级网表（综合产物）
- 布局布线后的物理设计数据库（DEF + GDS）
- setup/hold WNS/TNS 报告
- 面积报告（以平方微米或等效门数计）
- 功耗报告（动态功耗 + 静态功耗）
- 最终 GDS layout（物理签核产物，可直接提交流片）

**评测数据**（每次 run 都产出，无论是否完成）：
- 端到端得分 S（0-100 标度）
- 阶段完成状态（综合 / 物理实现 / ECO 各自的门控结果）
- 货币成本（美元 $）
- 运行时间（wall-clock 分钟）
- Token ROI（归一化版本）
- 失败事件分类（9 类标签）

**具体结果示例**——FluxEDA + DeepSeek-V4 / 350 MHz（最佳 cost-QoR 组合）：

```
端到端得分: 97.94 / 100
  - 阶段得分 S_stage: 满分（综合 + 物理实现 + ECO 全部通过，S_stage = 100）
  - 结果得分 S_result: ≈ 97.43（6 项归一化指标平均）
成本: $0.56
运行时间: 120.83 分钟（约 2 小时）
归一化 Token ROI: 39.91
```

对比——Claude Code + DeepSeek-V4 / 350 MHz（最便宜但无价值的 run）：

```
端到端得分: 13.33 / 100
  - 阶段得分 S_stage: 约 16.66（综合满分，物理实现不足，ECO 未通过）
  - 结果得分 S_result: 0（三阶段未全部完成，门控规则触发）
成本: $0.11
运行时间: 58.78 分钟（约 1 小时）
归一化 Token ROI: 12.71（注意：高分来自"成本极低"而非"设计进展好"）
```

这个对比揭示了 FluxBench 评测体系的核心理念：**成本效率必须与验证过的设计进展联合解读**。$0.11 跑出 13.33 分看似"便宜"，实则因为 agent 在物理实现阶段就失败了，没有产出可用的 GDS 数据——这是 0 端到端价值的结果。

## 4. Benchmark 构建方法

本节回答：这个 benchmark 是怎么搭出来的？题目从哪来？怎么分层？参考实现是什么？质量怎么保证？

### 4.1 题目来源

FluxBench 的题目来源是**人工设计的工程案例**，而非自动爬取或合成生成：

- **设计选择**：选择一个被社区广泛验证的开源 RISC-V CPU 核 PicoRV32，确保 RTL 本身的功能正确性不引入额外噪声
- **流程定义**：由具有商业 EDA 工具使用经验的物理设计工程师定义完整的 RTL-to-GDS flow，包括每一阶段的脚本模板、检查点、和交付物标准
- **约束设定**：基于 55nm 工艺的物理特性，设定两个有意义的时钟目标——350MHz 代表该工艺下 PicoRV32 容易达到的频率，700MHz 代表需要积极优化才能收敛的频率

FluxBench 的题目不是"从互联网爬取的 RTL 问题集"（如 VerilogEval 的 HDLBits 来源），也不是"合成生成的模板变体"（如 RTLCoder 的数据合成 pipeline），而是一个**真实的、端到端的工业级物理设计任务**。这种题目的优势在于生态效度高（直接反映真实工作场景），劣势在于题目数量极少（只有 1 个设计 x 2 个约束 = 2 道题），统计效力有限。

### 4.2 题目数量与难度分层

| 维度 | 配置 | 说明 |
|------|------|------|
| 设计数量 | 1 个（PicoRV32） | 单一 RISC-V CPU 核 |
| 难度分层 | 2 级（350 MHz loose / 700 MHz tight） | 通过改变时钟约束实现难度梯度，而非改变设计 |
| 架构配置 | 3 种 agent 架构 | Claude Code / CC+EDA Skills / FluxEDA |
| 模型配置 | 4 种基础模型 | DeepSeek-V4 / GLM-5.2 / Claude Sonnet 5 / Kimi K3 |
| 总评测次数 | 3 x 4 x 2 = 24 次完整 RTL-to-GDS run | 每次 run 独立从一个干净的 tool session 开始 |
| 每次 run 的重复 | 1 次（无重复） | 论文明确承认这是局限——无法计算方差 |

**难度分层的设计逻辑**：

350 MHz（宽松目标，时钟周期 2.857ns）：测试 agent"能不能走通流程"。在这个频率下，PicoRV32 的综合结果大概率天然满足时序——agent 需要做的更多是"正确调用工具"而非"做聪明的优化决策"。这是一个**流程完成度**测试。

700 MHz（紧约束，时钟周期 1.429ns）：测试 agent"会不会主动优化"。在这个频率下，综合的默认参数大概率不满足时序——agent 必须读懂时序报告、判断瓶颈位置、调整 floorplan/placement 策略、或通过 ECO 迭代修复违例。这是一个**优化能力**测试。

论文通过这一对目标的对比来区分两类能力：**操作正确性**（能不能把工具调对）和**优化有效性**（能不能在参数空间里做出改善 QoR 的决策）。

### 4.3 参考实现与 Testbench

FluxBench 的"testbench"不同于传统 RTL benchmark 的功能仿真 testbench——因为这里被测的不是 RTL 代码，而是 agent 的**工具交互行为**。其"参考实现"和"testbench"的构成如下：

**参考实现（ground truth flow）**：

论文没有明说，但从实验设计可以推断：每个阶段的"通过标准"是由人工物理设计专家预定义的检查规则。例如：
- 逻辑综合通过 = 网表文件存在 + 无致命 error + clock-gating 通过
- 物理实现通过 = I/O placement 完整 + std-cell placement 完成 + CTS 完成 + routing 完成
- ECO 通过 = setup/hold WNS/TNS 满足预设门限

这些检查规则构成了隐含的"ground truth"——不要求 agent 跑出特定 PPA 数字，但要求和人工专家会产出的交付物类别一致。

**质量验证（testbench 等价物）**：

1. **自动化检查脚本**：针对每个阶段的交付物运行检查（文件存在性、格式合法性、关键数据字段的合理性范围）
2. **EDA 工具内建检查**：综合、P&R、STA 工具各自的 DRC/LVS/时序检查作为"自动 grading"
3. **人工审核**：论文作者团队（物理设计经验者）对评分公式中的参考值、归一化下界、门控规则进行人工设定

FluxBench 没有公开这些检查脚本和参考值——这是其可复现性方面的主要局限。

### 4.4 质量把关流程

FluxBench 构建质量通过以下机制保证：

1. **门控评分规则**：阶段得分采用级联门控——物理实现检查仅在综合完成后触发，ECO 检查仅在前两者完成时触发。这防止了"跳过中间步骤直接生成报告"的作弊行为。
2. **结果得分的二值门控**：S_result 只有当所有三个阶段全部完成时才非零——即使 agent 生成了看起来不错的时序报告，如果 ECO 阶段没通过，S_result = 0。这防止了"部分输出被当作有效设计"。
3. **多维指标矩阵**：不依赖单一 pass/fail——端到端得分、阶段完成率、Token ROI、成本、运行时间、错误分类共 6 个维度联合评估，任何单一维度的"好看"都需要在其他维度的上下文中解读。
4. **统一的工具环境**：所有 24 次 run 在同一个本地 EDA 服务器上执行，使用相同版本的工具链和工艺库，排除环境差异对评测结果的干扰。

## 5. 关键公式

本节覆盖论文所有编号公式（Eq.1 - Eq.4），并补充评分机制的完整数学细节。

### 5.1 Token ROI 定义（Eq.1）

论文将 Token ROI 定义为：

$$
\text{TokenROI} = \frac{\text{normalized EDA return}}{\text{token investment} \times \text{execution-time investment}}
$$

- $\text{normalized EDA return}$：归一化 EDA 收益——任务特定的设计质量与完成度的组合，将 0-100 得分映射到可比尺度
- $\text{token investment}$：token 投入——API 调用消耗的 token 总量转换为成本度量（以美元或 token 数计）
- $\text{execution-time investment}$：执行时间投入——EDA 工具实际运行的 wall-clock 时间（分钟）

**工程直觉**：Token ROI 的灵感来自金融领域的 ROI（投资回报率）。在 Agentic EDA 场景中，"投资"包括两部分——调用 LLM 的 token 费用（像咨询费）和等待 EDA 工具运行的时间成本（像工期）。一个 agent 可能很聪明（高分），但每次决策都要几千个 token 的冗长推理，反复生成废弃的脚本，反复触发慢速 EDA run——这些隐性成本在只看最终得分的评测中完全不可见。

**归一化版本**：论文额外定义归一化 Token ROI，对 token cost 和 execution time 分别做 rescaling，消除两个成本维度量级差异对乘积的影响。具体 rescaling 方式论文未给出公式，但从表 2 数据可推知：归一化使得不同模型的 API 定价差异（如 DeepSeek-V4 远便宜于 Claude Sonnet 5）不会主导 Token ROI 的相对比较。

### 5.2 端到端得分（Eq.2）

$$
S = 0.2 \cdot S_{stage} + 0.8 \cdot S_{result}
$$

- $S$：端到端得分（0-100 标度）
- $S_{stage}$：阶段得分——衡量"流程走到了哪"（门控三阶段平均）
- $S_{result}$：结果得分——衡量"设计质量有多好"（6 项 PPA 指标归一化平均，三阶段全部完成才非零）
- 权重 0.2 vs 0.8：强调最终设计质量（PPA）比单纯"跑通流程"更重要

**为什么 0.2/0.8 而非 0.5/0.5？** 如果 S_stage 和 S_result 等权，可能出现"跑通流程但 PPA 很差"仍得高分的偏倚。0.8 的结果权重确保只有在产出高质量最终设计时才能得高分——这是对"能做成芯片"而非"能写出脚本"的强调。

### 5.3 阶段得分的门控机制

阶段得分是三阶段门控得分的算术平均：

$$
S_{stage} = \frac{1}{3}(g_{syn} + g_{phys} + g_{eco})
$$

- $g_{syn}$：逻辑综合门控得分——基于 netlist 生成 + clock-gating 检查
- $g_{phys}$：物理实现门控得分——基于 I/O placement + std-cell placement + CTS + routing 四个子检查
- $g_{eco}$：ECO 门控得分——二值（通过 = 满分，失败 = 0）

**门控规则**（论文第 3.3 节原文）：
- $g_{phys}$ 仅在 $g_{syn}$ 完全通过后才计入，否则 $g_{phys} = 0$
- $g_{eco}$ 仅在 $g_{syn}$ 和 $g_{phys}$ 都完全通过后才计入，否则 $g_{eco} = 0$

这意味着：如果 agent 在综合阶段就失败了，无论物理实现和 ECO 有没有产出，S_stage 按 0 计算。这是防止"跳过关键步骤直接生成下游报告"的关键设计。

**物理实现阶段的子检查**：

$g_{phys}$ 本身不是单一二值判定，而是 I/O placement、std-cell placement、CTS、routing 四个子检查的综合——论文未给出子检查的具体加权方式，但从表 3 可知：全部 6 次物理实现失败均涉及 I/O placement 不完整，1 次同时涉及 CTS 失败。这暗示 I/O placement 是四个子检查中最容易失败的一环。

### 5.4 结果得分（Eq.3 - Eq.4）

结果得分仅在全部三个阶段完成时计算，否则直接为 0：

$$
S_{result} = \begin{cases} \displaystyle\frac{1}{6}\sum_{m \in M} S_m, & \text{若三阶段全部完成} \\[10pt] 0, & \text{否则} \end{cases}
$$

其中指标集合 M 的定义（Eq.3）：

$$
M = \{A, P, W_s, T_s, W_h, T_h\}
$$

- $A$：面积（Area）——越小越好，按频率相关参考值归一化
- $P$：功耗（Power）——越小越好，按频率相关参考值归一化
- $W_s$：setup WNS（Worst Negative Slack，最差建立时间负余量）——越大越好，非负值 = 满分
- $T_s$：setup TNS（Total Negative Slack，总建立时间负余量）——越大越好
- $W_h$：hold WNS（Worst Negative Slack，最差保持时间负余量）——越大越好
- $T_h$：hold TNS（Total Negative Slack，总保持时间负余量）——越大越好

**归一化方式**（论文第 3.3 节）：

面积和功耗（越小越好类指标）：
- 按频率相关的参考值归一化。论文未给出参考值的具体数字，但逻辑是：以该工艺下该频率的人工专家合理预期为参考，达到或低于参考值得满分，高于参考值按超出的比例扣分

时序指标（越大越好类指标）：
- $W_s, T_s, W_h, T_h \geq 0$：$S_m = 1.0$（满分，时序无违例）
- $W_s, T_s, W_h, T_h < 0$：按预设下界做分段线性缩放。下界由人工专家根据工艺和频率设定，表示"不可接受的最差时序"

这个归一化方案的特点是**非对称性**：时序指标在非负时全满分（没有"更好"——Slack 为正说明信号提前到达，再提前也不会让芯片更快），但在负值时严格扣分。这反映了物理设计的实际逻辑——时序收敛是硬门槛，一旦过了门槛（WNS >= 0），PPA 的区分靠面积和功耗。

**计算示例**——以 FluxEDA + DeepSeek-V4 / 350 MHz（得分 97.94）为例推演：

```
已知 S = 0.2 * S_stage + 0.8 * S_result = 97.94
三阶段全部完成 → S_stage = 100（全部通过，每项满分）
→ 0.8 * S_result = 97.94 - 20 = 77.94
→ S_result ≈ 97.43

S_result = (S_A + S_P + S_Ws + S_Ts + S_Wh + S_Th) / 6 = 97.43
→ 六项总和 ≈ 584.55，平均每项约 97.43
说明：面积、功耗、时序均接近参考值，特别是 WNS/TNS 大概率非负（时序收敛）
```

### 5.5 论文未编号但重要的评分细节

1. **物理实现阶段的分层检查**：IO placement > std-cell placement > CTS > routing，顺序执行且各自有独立的检查逻辑
2. **ECO 阶段的二值判定**：ECO 被简化为通过/失败的二值指标——论文承认这是粒度损失（未区分"修了几个违例""引入多少面积开销"）
3. **归一化参考值的频率依赖性**：350 MHz 和 700 MHz 使用不同的面积和功耗参考值——更高频率天然需要更多面积和功耗来满足时序，所以参考值随频率上调

## 6. 评测协议与打分

本节全面展开 FluxBench 的评测协议：打分公式的完整数学细节、PPA 度量的一体化归一化方案、评测环境的技术规格、baseline 配置与主结果、以及评测框架必须回答的四个核心问题。

### 6.1 打分公式

端到端得分的完整定义（已在第 5 节逐一展开公式推导）：

$$
S = 0.2 \cdot S_{stage} + 0.8 \cdot S_{result}
$$

$$
S_{stage} = \frac{1}{3}(g_{syn} + g_{phys} + g_{eco}), \quad \text{各 } g \text{ 受门控规则约束}
$$

$$
S_{result} = \begin{cases} \displaystyle\frac{1}{6}\sum_{m \in M} S_m, & \text{三阶段全部完成} \\[10pt] 0, & \text{否则} \end{cases}, \quad M = \{A, P, W_s, T_s, W_h, T_h\}
$$

### 6.2 PPA 打分的归一化方式

FluxBench 需要将 6 个物理量纲不同的指标（面积 μm²、功耗 mW、时序 ns）统一到 0-1 的归一化得分——这不是一个简单的"min-max"问题。

**面积指标归一化**：

$$
S_A = \begin{cases} 1.0, & A \leq A_{ref}(f) \\ \max\left(0, \; 1 - \frac{A - A_{ref}(f)}{A_{bound}(f) - A_{ref}(f)}\right), & A > A_{ref}(f) \end{cases}
$$

- $A_{ref}(f)$：频率 $f$ 下的参考面积——人工专家在该工艺下对该设计的合理预期
- $A_{bound}(f)$：不可接受的上界——超过此值的面积被认为"没有实用价值"
- 参考值和上界均随频率变化（700 MHz 下的参考面积应大于 350 MHz——为时序付出的面积代价）

**功耗指标归一化**：与面积相同的形式，使用 $P_{ref}(f)$ 和 $P_{bound}(f)$。

**时序指标归一化**（以 W_s 为例）：

$$
S_{W_s} = \begin{cases} 1.0, & W_s \geq 0 \\ \frac{W_s - W_{s,lower}}{0 - W_{s,lower}}, & W_{s,lower} \leq W_s < 0 \\ 0, & W_s < W_{s,lower} \end{cases}
$$

- $W_{s,lower}$：预设的 WNS 下界（负数，如 -0.5ns）——低于此值认为时序完全不可接受
- $T_s, W_h, T_h$ 使用相同形式，各自有独立的下界参数
- 非负值得满分的设计逻辑：Slack 为正只说明信号提前到达——再多提前也不会让芯片更快（频率由最慢路径决定），但 Slack 为负说明有路径慢于时钟周期，需要修复

**论文未公开的关键参数**：$A_{ref}$、$P_{ref}$、$W_{s,lower}$ 等参考值和下界的**具体数字**论文没有给出。这是评分透明度的显著缺陷——外部无法独立验证一个特定 score 的归一化过程是否合理。这些参数的设定直接影响不同设计配置之间的相对排名。

### 6.3 Token ROI 的打分方式

Token ROI 的归一化版本使用如下形式（论文根据 Eq.1 和原文描述推断）：

$$
\text{nTokenROI} = \frac{\mathcal{R}_{norm}}{\tilde{C}_{token} \cdot \tilde{T}_{exec}}
$$

- $\mathcal{R}_{norm}$：将 end-to-end score 和阶段完成率组合为标量收益（论文未给出具体组合公式）
- $\tilde{C}_{token}$：rescale 后的 token 成本（除以所有 run 的 token 成本的中位数或均值）
- $\tilde{T}_{exec}$：rescale 后的执行时间（除以所有 run 的执行时间的中位数或均值）

Rescaling 的目的：如果原始 token 成本量级（$0.11 ~ $51.58）和执行时间量级（58.78 ~ 472.13 min）不匹配，乘积会被一个维度主导。Rescaling 使两个成本维度在乘积中的贡献大致均衡。

2. **DeepSeek-V4 在三种架构下跨度 11.67 → 97.94（差 86.27 分）**——同一模型的"能力"在不同执行架构下天差地别。这说明 Agentic EDA 的能力是一个系统属性，而非模型属性。
3. **Token ROI 的极端差异**：FluxEDA + DeepSeek-V4 在 700MHz 下以 $0.45 + 94.28min 取得 90.99 分，ROI = 48.06。而 CC+Skills + Kimi K3 在 350MHz 下以 $29.77 + 472.13min 仅得 13.33 分，ROI = 0.09。两者之间的 Token ROI 比值为 48.06 / 0.09 ≈ 534 倍——虽然论文强调的 141 倍是相同得分（都是 13.33）下的对比。

### 6.7 阶段完成率

论文 Table 3——各架构在 8 次 model-target run 中的阶段完成次数：

| 架构 | Synthesis | Physical Implementation | ECO |
|------|:---------:|:-----------------------:|:---:|
| Claude Code | 8/8 | 7/8 | 3/8 |
| CC + EDA Skills | 8/8 | 3/8 | 2/8 |
| FluxEDA | 8/8 | 8/8 | 8/8 |

关键观察：
- 综合阶段无失败——所有 agent 都能将 RTL 转化为门级网表
- CC+Skills 的物理实现完成率（3/8）反而低于纯 CC（7/8）——EDA skill 的引入在某些配置下反而降低了流程稳定性
- FluxEDA 是唯一在所有 run 中完成全部三个阶段的架构
- 全部 6 次命令行物理实现失败均涉及不完整的 I/O placement——说明 I/O placement 的 Tcl 脚本是 agent 的薄弱环节

### 6.8 评测必须回答的四个问题

**问题一：评测什么能力？**

FluxBench 评测的是 LLM Agent 在**工具交互式、长周期、多阶段 EDA 工作流**中的以下能力：

1. **设计状态维护能力**：跨多个工具 session 保持对"当前设计数据库在哪一步、时钟是否已定义、MMMC 是否已初始化"的准确理解
2. **工具反馈解读能力**：从 EDA 工具的 log/report/error message 中提取有效信息并据此调整策略
3. **流程阶段识别能力**：判断当前处于哪个阶段、哪些步骤已完成、下一步应该做什么
4. **错误恢复能力**：在 Tcl 命令失败后诊断原因、修正命令、重新执行，而非从头开始
5. **PPA 优化能力**：在满足时序约束的前提下平衡面积和功耗

FluxBench **不评测**的是：RTL 代码生成能力、功能验证能力、从零探索最优 flow 的能力（因为参考 flow 已隐含在工具链中）。

**问题二：怎么打分？**

多维打分体系（详见 6.1-6.3）：
- **完成度维度**：S_stage（三阶段门控平均）和 S_result（6 项 PPA 归一化平均，三阶段全部完成才非零）
- **效率维度**：Token ROI（归一化后的"设计收益 / (token 成本 x 执行时间)"）、绝对成本（$）、绝对运行时间（min）
- **诊断维度**：9 类失败分布（T1-T9）

门控规则是打分体系的关键：后一阶段的得分以前一阶段完全通过为前提，结果得分以三阶段全部完成为前提。这套规则确保"跑了一半"和"跑完了"之间有质的区别。

**问题三：和谁比？**

FluxBench 的比较对象分两个层级：

1. **架构层级**：Claude Code（通用 Agent）vs CC+EDA Skills（通用 Agent + 领域知识）vs FluxEDA（EDA 专用执行架构）
2. **模型层级**：DeepSeek-V4 vs GLM-5.2 vs Claude Sonnet 5 vs Kimi K3

因为是首个 RTL-to-GDS agent benchmark，FluxBench 没有"已有方法"作为 baseline——它在建立一个新赛道。论文的比较逻辑是"架构消融"：固定任务、工具链、工艺，逐一替换架构和模型，看哪个变量对最终结果的方差贡献更大。

**问题四：评测可信吗？**

这一问题的详细分析见第 10.4 节。简要而言：FluxBench 的主要可信度优势在于固定环境下的交叉比较（内部有效性较好），主要劣势在于单设计、单工艺、单次 run、商业闭源工具、未公开评分参数（外部有效性和可复现性较差）。

## 7. 创新点

### 创新点 1：首次将 RTL-to-GDS 全链路形式化为工具交互 Agent 评测问题

在 FluxBench 之前，EDA agent 评测止于单点任务——RTL 代码生成（RTLLM / VerilogEval）、单步综合优化、placement 预测。这些 benchmark 的评测范式是"一次 prompt → 一次输出 → 和标准答案对比"。

FluxBench 把评测范式升级为"持续任务 → 多轮工具交互 → 根据反馈调整策略 → 产生最终交付物"。在这个范式中，agent 需要在**同一个连续的设计数据库**上，跨 7 个子阶段（综合 → floorplan → placement → CTS → routing → ECO → 签核），每一步根据 EDA 工具的反馈（log、report、error message）自主决策下一步动作。

**与已有工作的根本区别**：

- RTLLM / VerilogEval：评测"能不能生成正确的 RTL"，一次 prompt 一次输出，评测指标是 pass@k
- PDAGENT-BENCH：评测物理设计 ⑦~⑩，但不含综合和 ECO
- CLOSER-Bench：强调跨阶段迭代 closure，但不以 agent 架构对比为核心
- Design Conductor (Verkor)：演示一个大设计上的 agent 能力，但不提供标准化评测框架
- **FluxBench**：唯一覆盖 ③~⑬ 全链路 + 多 agent 架构系统比较 + 多维效率指标的标准化 benchmark

### 创新点 2：提出过程感知的多维评测体系

不是单一 pass/fail，而是五维联合评估：

- **阶段完成**（走到哪）：门控三阶段完成率
- **设计质量**（好不好）：6 项 PPA 归一化平均
- **运行成本**（花多少钱）：以美元计的实际 API 开销
- **Token ROI**（投入产出比）：归一化后的综合效率指标
- **失败归因**（卡在哪类问题）：9 类量化错误分类

这套体系的核心价值在于**区分"低成本早失败"和"高效验证进展"**。在传统评测中，两个"没通过"的 run 被同等对待——都是"失败"。但 FluxBench 的多维指标揭示：一个 58.78 分钟、$0.11 的"失败"和一个 472.13 分钟、$29.77 的"失败"，其工程代价差了数百倍。这个区分对于实际部署 agent 的资源规划至关重要。

### 创新点 3：提出 Token ROI 指标并发现 141 倍效率差异

Token ROI 将设计收益与 token 和时间投入联合度量——这是 Agentic EDA 领域的首个端到端成本效率指标。

最惊人的发现：在 350 MHz 下，CC + DeepSeek-V4 和 CC+Skills + Kimi K3 均得 13.33 分（综合 + 物理实现通过，ECO 未通过），但前者的 Token ROI = 12.71、后者的 Token ROI = 0.09——**相差约 141.2 倍**。

这个数字的含义：如果只看"得分"（都是 13.33），两者似乎"差不多"。但实际上一个是快速便宜地验证了"我做不到 ECO"，另一个是冗长昂贵地验证了"我也做不到 ECO"——相同的最终结论，但到达这个结论的"代价"差了 141 倍。

### 创新点 4：系统比较 Agent 架构 x 基础模型的交叉效果

在相同任务、相同工具链、相同工艺下，固定变量地比较 3 架构 x 4 模型 x 2 目标 = 24 次完整 RTL-to-GDS run——这是 Agentic EDA 领域首次在实验层面证明：**可靠的端到端完成取决于整个 agent 系统，而非仅靠基础模型**。

具体证据：
- DeepSeek-V4 在三种架构下得分：11.67（CC+Skills, 350MHz）→ 13.33（CC, 350MHz）→ 97.94（FluxEDA, 350MHz），跨度 **86.27 分**
- Claude Sonnet 5 在 CC 下 700MHz 得分 81.33，但在 CC+Skills 下 700MHz 得分仅 11.67——**EDA skill 的加入反而降低了 69.66 分**

这说明：在一个好的执行架构上（FluxEDA），弱模型也能跑出好结果；在一个差的执行架构上（CC+Skills），强模型的推理能力可能被错误的 skill 引导所破坏。

### 创新点 5：量化揭示工具接口失配是首要瓶颈

31.7% 的物理实现失败来自 Tcl 命令与工具版本/模式/MMMC 初始化不兼容。加上文件路径错误（25.1%），**56.8% 的失败源于"工具接口层"而非"设计优化层"**。

这不是一个"模型不知道怎么做 floorplan"的问题——这是一个"模型不知道这个版本的 ICC2 需要先 set_db 再 place_opt，而不是先 create_floorplan 再 set_attribute"的问题。这种失败在静态 RTL 生成 benchmark 里完全不可见，是 flow-grounded 评测特有的发现。

更关键的是，FluxEDA 通过 structured API + 持久化 tool session + 操作约束，**将 Tcl 兼容性错误消为零**。这证明这类错误的根源不是模型能力不足，而是 agent-工具接口缺乏结构化抽象。

### 创新点 6：证明 EDA Skills 的效果不稳定且可能反效果

CC+EDA Skills 对不同模型的效果截然相反：
- GLM-5.2 @ 350MHz：Score 13.33 → 95.97（+82.64 分，巨大提升）
- Claude Sonnet 5 @ 350MHz：Score 87.05 → 11.67（-75.38 分，毁灭性下降）
- Kimi K3 @ 700MHz：Score 82.33 → 11.67（-70.66 分，毁灭性下降）

这种"一部分模型受益、另一部分模型被毁"的模式说明：EDA skill 的效果不是 additive（叠加）的，而是 interactive（交互）的。Skill 中的过程知识可能与模型的推理模式冲突——例如 skill 说"执行命令 X"，但模型自身判断"应该执行命令 Y"，两者冲突导致生成自相矛盾的 Tcl 脚本。

这是对"skill 越多越好"直觉的有力反驳——为 agent 注入领域知识需要更精细的机制（如 skill 选择、冲突消解、skill 与模型推理的融合），而非简单的 prompt 拼接。

## 8. EDA 缩写表

| 缩写 | 全称 | 一句话解释 |
|------|------|-----------|
| **RTL** | Register Transfer Level | 寄存器传输级——用 Verilog/VHDL 描述电路行为，不指定门电路 |
| **GDS** / **GDSII** | Graphic Data System | 芯片版图的标准文件格式，发给代工厂流片的最终交付物 |
| **SDC** | Synopsys Design Constraints | 设计约束文件——定义时钟频率、输入/输出延迟等时序约束 |
| **DEF** | Design Exchange Format | 物理设计交换格式——记录标准单元位置、走线等物理信息 |
| **LEF** | Library Exchange Format | 库交换格式——标准单元的抽象物理视图（pin 位置、blockage） |
| **LIB** | Liberty Format | 时序库格式——标准单元的时序/功耗/面积模型 |
| **STA** | Static Timing Analysis | 静态时序分析——不跑仿真，用数学模型计算所有路径的延迟 |
| **WNS** | Worst Negative Slack | 最差负时序余量——所有路径中时序违例最严重的那条的 slack 值（负值 = 违例，非负 = 时序收敛） |
| **TNS** | Total Negative Slack | 总负时序余量——所有违例路径的 slack 之和（衡量违例的"总量"） |
| **setup** | Setup Time | 建立时间——数据在时钟沿**之前**必须稳定的最小时间 |
| **hold** | Hold Time | 保持时间——数据在时钟沿**之后**必须保持的最小时间 |
| **ECO** | Engineering Change Order | 工程变更命令——在不重跑全流程的前提下局部修复时序/功能问题 |
| **MMMC** | Multi-Mode Multi-Corner | 多模式多工艺角——不同工作模式（功能/测试/待机）x 不同 PVT 条件的组合时序分析 |
| **PVT** | Process-Voltage-Temperature | 工艺-电压-温度——STA 分析的三个变化维度，构成工艺角 |
| **CTS** | Clock Tree Synthesis | 时钟树综合——插入缓冲器构建时钟分配网络，使所有触发器"同时"收到时钟沿 |
| **DRC** | Design Rule Check | 设计规则检查——验证版图几何尺寸满足制造工艺的物理极限 |
| **LVS** | Layout vs. Schematic | 版图与原理图对比——验证从版图提取的网表和原始网图逻辑一致 |
| **QoR** | Quality of Result | 结果质量——面积、功耗、时序等设计指标的综合评价 |
| **PPA** | Power, Performance, Area | 功耗、性能、面积——芯片设计的三大优化目标 |
| **PDK** | Process Design Kit | 工艺设计包——代工厂提供的标准单元库、设计规则、模型文件 |
| **ROI** | Return On Investment | 投资回报率——本文特指 Token ROI：归一化设计收益 / (token 投入 x 执行时间) |
| **P&R** | Place and Route | 布局布线——物理设计的核心阶段，包含 placement + CTS + routing |
| **Tcl** | Tool Command Language | EDA 工具的脚本命令语言——Synopsys/Cadence 工具的标准交互接口 |
| **I/O placement** | Input/Output Placement | 输入输出引脚摆放——决定芯片与外部通信的物理位置（bond pad 到内部逻辑的连接） |
| **Slack** | Timing Slack | 时序余量——(要求到达时间) - (实际到达时间)，正 = OK，负 = 违例 |
| **Skew** | Clock Skew | 时钟偏差——不同触发器收到时钟沿的时间差，CTS 的目标是最小化 skew |
| **IR Drop** | Voltage (IR) Drop | 电源电压降——电源网络电阻导致远端电压低于标称值，降低门开关速度 |
| **SPEF** | Standard Parasitic Exchange Format | 标准寄生参数交换格式——记录走线的寄生电阻电容 |
| **SDF** | Standard Delay Format | 标准延时格式——记录每个门和每根线的延迟信息 |

## 9. 与芯片流程的关系

### 9.1 在全流程中的位置

FluxBench 接手的是"**已经写好的 RTL 代码 + 工艺库 + 时序约束**"，交付的是"**可以提交流片的 GDS 版图数据**"。它在 17 阶段流程中的位置如下：

```text
芯片流程 17 阶段                 FluxBench 的角色                    传统做法
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
① RTL 设计              ← RTL 作为输入（PicoRV32, 不生成）           人手写 Verilog
② RTL 功能仿真          ← 不涉及（假设 RTL 功能正确）                人手跑 testbench
③ 逻辑综合              ← ★ 第一个评测阶段：RTL → 门级网表         人手写综合脚本
④ 门级仿真              ← 不涉及                                  人手跑仿真
⑤ STA                   ← ★ 嵌入物理实现和 ECO 各步的持续验证      人手分析时序
⑥ 形式验证              ← 不涉及                                  人手跑 Formality
⑦ 布局规划              ← ★ Floorplan + Powerplan                 人手做 floorplan
⑧ 标准单元摆放           ← ★ Placement                             人手调 placement
⑨ 时钟树综合            ← ★ CTS                                   人手调 CTS
⑩ 布线                  ← ★ Routing                               人手跑 routing
⑪ 后仿真                ← 不涉及                                  人手跑后仿真
⑫ 物理验证              ← DRC 作为 routing 后验                   人手跑 Calibre
⑬ 签核                  ← ★ ECO → 最终 GDS + QoR 报告             人手做 ECO
⑭~⑰ 流片/制造/封测      ← 不涉及                                  流片
```

**解决了什么痛点**：传统 RTL-to-GDS 流程由经验丰富的物理设计工程师手动执行，一个中等规模设计的后端实现周期以周至月计。FluxBench 试图评测的是：LLM Agent 能否自动化或大幅加速这个流程？如果 agent 能可靠完成 ③~⑬，芯片后端实现的周期可以从"月"缩短到"小时"——这正是 FluxEDA + DeepSeek-V4 所展示的：$0.56 + 120.83 分钟 = 约 2 小时跑出 97.94 分的 PicoRV32 物理实现。

### 9.2 "Agent 能完成流程" 和 "能做成芯片" 之间隔着什么

FluxBench 评测的"完成"和真实的"流片成功"之间存在以下鸿沟：

1. **没有功能验证**：PicoRV32 的 RTL 功能正确性是被"假设"的。真实流片前需要跑遍 RTL 仿真、门级仿真、后仿真、形式验证——任何一个环节的失败都会导致昂贵的 re-spin。FluxBench 没有验证 agent 产出的 GDS 对应的是否还是原来的 PicoRV32 逻辑。

2. **没有完整的签核检查**：论文的 ECO 阶段是二值通过/失败——但真实签核需要所有 PVT corner 下的 setup/hold WNS/TNS 均为非负（或可接受范围内）、IR Drop 在 5% 以内、信号完整性（串扰、地弹）在规范内、DFM（可制造性设计）规则通过。FluxBench 用 6 个归一化指标做代理，但这些代理和真实签核之间的对应关系未经校准。

3. **没有物理验证的独立评分**：DRC 违例在错误分类中占 5.9%（T6），但这不是"这个 GDS 能不能制造"的完整答案。真实流片需要 DRC clean（0 违例），而 FluxBench 没有将 DRC clean 设为硬性通过条件。

4. **没有多 corner 验证**：论文提到 MMMC 初始化但未给出具体的 corner 组合。真实签核通常在 SS/FF/TT x 温度 x 电压的 20+ 个 corner 下做 STA——FluxBench 的评测可能只在单一 corner 下进行。

5. **PicoRV32 的规模和工业 SoC 差距巨大**：PicoRV32 约数万门，而工业 SoC 数亿门、数百个 macro、复杂时钟域。Agent 在 PicoRV32 上能跑通的 flow，在更大设计上可能因为 runtime 爆炸（单次 P&R 从 2 小时变成 2 天）、内存溢出、或时序收敛难度指数增长而完全失败。

## 10. 讨论与局限

### 10.1 论文自述的局限

1. **单一设计与单一工艺**：仅以 PicoRV32 和商业 55nm 工艺为案例——PicoRV32 约 2000 行 Verilog、综合后数万门，远不能代表工业 SoC（数亿门、数百个 macro、复杂时钟域和多电压域）的规模和签核复杂度。先进工艺节点（7nm/5nm/3nm）的 DRC 规则数量级增长、多重曝光、FinFET 效应等完全不涉及。

2. **商业工具依赖且未公开版本**：所有实验基于商业 EDA 工具（综合、P&R、STA），论文未公开具体工具和版本号。这意味着：(a) 结果不能直接迁移到 OpenROAD/Yosys 等开源流程；(b) 社区无法独立复现——商业工具的 license 成本是显著门槛；(c) Tcl 兼容性问题的具体工具版本依赖完全不可知。

3. **每配置仅运行一次**：每个架构-模型-目标组合只跑一次。LLM 输出的随机性（temperature sampling）意味着单次 run 的得分可能不是该配置的"典型"表现。无统计重复导致无法计算方差、置信区间，也无法判断 97.94 和 97.72 的差异（0.22 分）是真实的架构优势还是随机波动。

4. **受限的模型与目标集**：仅测试 4 个模型和 2 个 timing target。未覆盖更紧的约束（如 1 GHz）、多 corner 签核（SS/FF/TT x 温度 x 电压）、多电压域等真实场景。

5. **ECO 评测粒度过粗**：ECO 被评为二值通过/失败——但 ECO 有丰富的质量差异（修复了几个违例、引入了多少面积开销、是否破坏了已有 hold 时序、是否需要多轮迭代）。当前二值评价丢失了大量信息。

6. **评分参数未公开**：面积/功耗的参考值 $A_{ref}$、$P_{ref}$、WNS/TNS 的下界参数均未公开。这些参数直接影响 final score，其设定是否合理、是否对某些模型有利，外部无法独立审计。

7. **未涵盖前端验证**：不包含功能仿真、形式验证、覆盖率闭合——这些是真实签核必须通过的门槛。当前评测只能回答"agent 能不能跑完工具流程"，不能回答"agent 跑出的 GDS 是不是正确的芯片"。

### 10.2 代码/复现层面的问题

FluxBench 截至 2026-08 为 **论文-only**，无公开代码仓库、无 artifact、无公开数据集。

具体不可复现的组件：
- **Agent prompt 模板**：task id / session id 的具体格式和内容未公开
- **EDA Skills 的具体内容**：IC Agent Hub 的哪些 skill 被注入、skill 的文本形式和结构未公开
- **FluxEDA Gateway 的实现**：gateway 的能力发现机制、动作结构化方式、session 持久化逻辑均未公开
- **评分脚本**：阶段完成的自动检查脚本、归一化参数的配置、Token ROI 的 rescaling 权重未公开
- **工具链环境**：商业 EDA 工具的版本、license 配置、环境变量设定未公开

复现等级：**R0**（不可复现）——论文-only，依赖商业闭源工具，核心组件（gateway、skills、评分参数）全未公开。

### 10.3 本资料包的批判性分析

**隐含前提 1：参考 flow 模板的质量决定了 agent 的表现上限**

FluxEDA 在所有配置下均 90+ 分——但这很可能不是因为 FluxEDA 让 agent 变聪明了，而是因为 FluxEDA 的 gateway 内置了"正确的流程模板"。Agent 实际上是在模板定义的参数空间内搜索，而非"从零发现物理设计流程"。如果模板本身是由人工专家写好的最优流程，那么 agent 的贡献更多是参数选择和错误处理，而非自主决策——这两种能力在概念上非常不同。

论文未做关键消融实验：如果让 FluxEDA gateway 直接按模板跑（无 agent 参与），得分是多少？如果 agent 的贡献只是模板参数的微调，那 agent 在 97.94 分中的"增值"部分可能非常小。

**隐含前提 2：PicoRV32 的"最佳 flow"可能已经饱和**

PicoRV32 是一个被社区广泛研究的设计。商业 EDA 工具的默认参数可能已经针对这个规模的设计调到了很好的工作点。Agent 在这个设计上面对的核心挑战是"能不能调对 Tcl 命令"而非"能不能做出创造性的 floorplan 决策"。这意味着 FluxBench 目前主要评测的是**操作正确性**而非**优化创造性**——换一个从未被研究过的全新设计（如某专有 AI accelerator），agent 的 floorplan 决策质量可能完全不同。

**隐含前提 3：Token ROI 的可比性受模型定价的严重干扰**

FluxEDA + DeepSeek-V4 的 Token ROI = 39.91，FluxEDA + Claude Sonnet 5 的 Token ROI = 0.68——这个 58.7 倍的差距大部分来自 DeepSeek-V4 和 Claude Sonnet 5 的 API 定价差异，而非 agent 效率差异。Token ROI 的"归一化"版本并未完全消除定价差异——因为论文未公开 rescaling 的具体方法。

在实际部署中，选择便宜的模型比优化 agent 架构更容易提升 Token ROI——但这不意味着便宜模型就是"更好"的选择，如果它需要更多的交互轮次（增加 wall-clock 时间）或产出的 QoR 更差。

**隐含前提 4：FluxEDA 的"消除 Tcl 错误"是否以牺牲灵活性为代价**

FluxEDA 通过 structured API 禁用了自由 Tcl 交互——这消除了 31.7% 的 Tcl 兼容性错误，但也可能阻止了 agent 使用一些"非常规但有效"的优化技巧（如自定义 Tcl proc、手动插入 buffer、调特定工具的内部参数）。在 PicoRV32 这个相对简单的设计上，这种灵活性损失可能无关紧要——但在更复杂的设计上，限制 agent 只能使用预注册的 API 可能成为优化天花板。

### 10.4 评测公平性与可信度分析

这一节对 FluxBench 作为 benchmark 的评测质量做系统分析。

**内部有效性（Internal Validity）——优势**：

- **固定环境**：所有 24 次 run 在同一本地 EDA 服务器上执行，工具版本和工艺库完全相同，排除了环境差异
- **交叉控制**：3 架构 x 4 模型 x 2 目标的完整因子设计，能独立估计架构效应、模型效应、目标效应
- **门控评分**：级联门控规则防止跳过中间步骤的作弊行为，S_result = 0 的惩罚防止部分输出被当作有效设计
- **多维指标**：5 个维度的联合评估避免了一维指标的偏倚

**内部有效性——劣势**：

- **单次 run 无统计**：每个配置只跑一次，无法区分"架构差异"和"采样噪声"。例如 FluxEDA + DeepSeek-V4（97.94）和 FluxEDA + GLM-5.2（97.72）的 0.22 分差极有可能在 re-run 中反转
- **评分参数不透明**：归一化的参考值和下界由作者设定且未公开——如果参考值恰好对某些模型后端更有利（例如 DeepSeek-V4 在 FluxEDA 下可能碰巧产生接近参考值的 PPA），评分就不公平
- **FluxEDA vs 其他架构的环境不对称**：FluxEDA 享有 gateway 的结构化执行支持（能力发现、动作验证、状态持久化），而 CC 和 CC+Skills 是"裸"shell 交互。这就像让一个有自动导航的车和一辆手动挡的车比赛——两者的"驾驶难度"完全不对等

**外部有效性（External Validity）——严重局限**：

- **设计泛化性**：PicoRV32 是单一设计，结果不能推广到其他规模/架构的设计
- **工艺节点泛化性**：55nm 是成熟工艺，先进节点的物理效应（FinFET、多重曝光、复杂的 DRC 规则）完全不涉及
- **工具链泛化性**：商业 Synopsys/Cadence 工具链的结果不能外推到 OpenROAD/Yosys 等开源工具
- **模型泛化性**：4 个模型的结果不能代表所有 LLM——特别是只能评测"2026 年中"的模型，未来更强模型的表现无法预测
- **任务泛化性**：RTL-to-GDS 只是 Agentic EDA 的一个子集——RTL 生成、验证、DFT（可测试性设计）等完全不同类型的工作流不能从本研究中推断

**公平性特别关注**：

FluxEDA 是由同一作者团队（Zhengrui Chen, Qi Sun, Cheng Zhuo）开发的——论文将 FluxEDA 与 Claude Code 和 CC+Skills 对比，存在隐含的利益相关。虽然实验设计（固定任务、统一环境、公开所有数据点）缓解了一部分担忧，但关键评分参数的未公开（归一化参考值、Token ROI 的 rescaling 权重）使得外部难以独立判断 FluxEDA 的优势是否部分来自评分体系的倾向性。

如果这篇文章提交到会议/期刊被接收，审稿人应该要求：(1) 公开所有评分参数；(2) 至少对关键配置做 3 次重复 run 并报告均值与标准差；(3) 做消融实验——FluxEDA gateway 直接跑模板（无 agent 参与）vs FluxEDA + agent，量化 agent 的净贡献。

## 12. 一分钟复述版

1. **问什么问题**：AI agent 能不能可靠完成从 RTL 到 GDS 的完整物理设计流程（综合→floorplan→placement→CTS→routing→ECO→签核）？
2. **怎么测的**：用 PicoRV32 + 商业 55nm + 两个时钟目标（350/700MHz），比较 3 种 agent 架构 x 4 个基础模型 = 24 次完整 RTL-to-GDS run
3. **核心发现一（能，但靠架构不靠模型）**：FluxEDA 在所有 run 中得分 90+ 并完成全流程，而命令行 agent 在物理实现和 ECO 阶段大量失败。DeepSeek-V4 在三种架构下得分差 86.27 分——执行架构比基础模型更能决定成败
4. **核心发现二（EDA skill 可能帮倒忙）**：CC+EDA Skills 对 GLM-5.2 大幅提升（+82.64），但对 Claude Sonnet 5 和 Kimi K3 大幅下降（-75.38、-70.66）——领域知识的注入效果高度依赖模型，甚至可能冲突
5. **核心发现三（效率差 141 倍）**：两个得分相同的 run（13.33），Token ROI 差 141 倍。低成本的失败虽然便宜但无端到端价值
6. **核心发现四（失败根因在工具接口）**：56.8% 的物理设计失败来自 Tcl 命令和文件路径错误，而非设计优化能力不足。FluxEDA 的结构化 API 将 Tcl 错误消为零
7. **三大教训**：领域技能不保证端到端完成；效率必须以验证过的进展为条件；必须区分操作有效性（命令合法吗）和优化有效性（命令优化了设计吗）
8. **局限**：单设计、单工艺、单次 run、商业闭源工具、评分参数不公开、ECO 二值化粒度过粗
9. **一句话**：Agentic EDA 的下一个突破不在更强的模型，而在为 agent 设计的结构化工具接口和执行层——让 agent 不再在脆弱的 Tcl shell 里试错
