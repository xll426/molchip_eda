## 1. 一句话定位

**VerilogLAVD 是第一个用 LLM 辅助生成图遍历规则来做 Verilog 硬件安全漏洞检测的框架——它不直接让 LLM 读代码找漏洞（LLM 对 HDL 并发语义理解差、误报率极高），而是让 LLM 根据 CWE 漏洞的自然语言描述生成结构化的"漏洞检测规则"（vulnerability detection rule，下文统称"图遍历检测模式/TDP"，TDP 是本资料包为方便阅读引入的简称，非论文术语），再由一个确定性规则执行器在 VeriPG（融合 AST + CFG + DDG 的统一代码属性图）上执行这些规则。在覆盖 12 种 CWE 类型的 77 个 Verilog 设计上达到 F1=0.54，相比 LLM-only baseline 提升 0.31，相比 LLM+外部知识 baseline 提升 0.27。**

> **术语说明**：论文原文使用"vulnerability detection rule""traversal rule""vulnerability traversal rule"等说法来指代由 LLM 生成的、最终在 VeriPG 上执行的规则。本资料包为叙述简洁，在中文行文中使用 **"TDP（Traversal Detection Pattern，图遍历检测模式）"** 作为统称，但请注意：
> - "TDP" 这一缩写以及"图遍历检测模式"这一中文译法是本资料包引入的，**不是论文原文使用的术语**。
> - 论文中与之对应的概念是 "vulnerability detection rule" / "traversal rule" / "vulnerability traversal rule"。
> - 在引用论文图表/数据时，本文档会恢复使用论文原文术语。

这句话里的 5 个承重点：

1. **LLM 负责生成规则，而非直接检测** — 这是全文最核心的设计选择。论文指出 LLM 直接检测的痛点在于"对 Verilog 代码结构理解弱（weak understanding of Verilog code structure）"导致输出不稳定、误报高。VerilogLAVD 将 LLM 的角色从代码分析器转变为规则生成器——LLM 根据 CWE 自然语言描述生成 VeriPG 遍历规则，避免了直接对 Verilog 代码进行结构化推理（"avoids direct structural reasoning"）。

2. **VeriPG 统一代码表示** — 以 AST 节点为融合锚点，将 AST（语法）、CFG（控制流）、DDG（数据依赖）三张图融合成一张有向图。这个设计借鉴了 Code Property Graph（CPG），但针对 Verilog 的并发语义做了适配。

3. **TDP 规则体系** — 规则不是自然语言，而是结构化的图遍历原语序列（如 `Exist(AssignStatement) → DDG-Traverse → NotHas("debug")`），可以直接被规则执行器机械执行，结果是确定性的。

4. **规则验证闭环** — LLM 生成的 TDP 可能用错遍历原语（类似软件代码生成中的 API misuse），VerilogLAVD 内置了规则验证工具（基于 VeriPG 的有限状态机），实时检测 TDP 的有效性并反馈给 LLM 修正。

5. **确定性执行，结果可复现** — 一旦 TDP 规则生成并验证通过，规则执行器以确定性的图遍历方式在 VeriPG 上执行规则，同一 VeriPG + 同一 TDP → 永远返回相同结果。这避免了 LLM 直接推理的随机性（论文指出 LLM 输出具有"inherent output randomness"），是工程稳定性的关键。

## 2. EDA 阶段映射（①-⑰）

参照 [芯片流程.md](../芯片流程.md) 的 17 阶段标准编号：

| 阶段 | 覆盖 | 说明 |
|------|:---:|------|
| **① RTL 设计** | ✅ **核心** | 直接分析 RTL 级 Verilog 代码，在设计的早期阶段检测 CWE 安全漏洞 |
| ② RTL 功能仿真 | ❌ | VerilogLAVD 是静态分析方法，不运行仿真 |
| ③-⑰ | ❌ | 不涉及后续流程 |

**覆盖率：1/17。** VerilogLAVD 是纯 RTL 阶段的安全分析工具，定位在"RTL 代码写完之后、综合之前"的漏洞检测环节——越早发现安全问题，修复成本越低。

> ⚠️ **最容易被误读的边界**：VerilogLAVD 检测的是 CWE（Common Weakness Enumeration）类型的**潜在安全漏洞**（如 debug 模式下的配置寄存器未保护、敏感数据路径缺少访问控制），而不是功能 bug（如逻辑错误、时序违规）。它回答的问题是"这个设计有没有安全弱点"，不是"这个设计功能正不正确"。

### 3.2 中间产物

**LLM 生成的 TDP 规则**（JSON 格式的图遍历模式，源自论文 Figure 2 的示例片段）：

```json
{
  "Prim": "Node",
  "Params": ["Assign"],
  "Filter": {
    "Operator": "AND",
    "Condition": [
      {
        "Path": [
          {"Prim": "LoadVar", "Params": [], "Filter": "None"},
          {"Prim": "NotHas", "Params": ["debug"], "Filter": "None"}
        ]
      }
    ]
  }
}
```

> ⚠️ **论文文本观察**：论文 Figure 2 的规则示例 JSON 中出现了 `"Params": ["Asign"]`（注：该字符串来源于论文 PDF Figure 2 的图示文字，随附 txt 文本提取中未直接出现），与正文其它位置使用的 "AssignStatement" / "DriverStatement" 等拼写不一致。**复现实现中建议以正文使用的 "AssignStatement" 为准**。

该规则的含义：找到所有 assign 语句节点，然后沿数据依赖路径追溯，检查路径上是否**没有**名为 `debug` 的信号——如果没有，说明该赋值不受 debug 信号保护，可能存在漏洞。

### 3.3 CWE-1280 案例研究（论文 Figure 5）

论文给出了一个 CWE-1280（Access Control Check Implemented After Asset Is Accessed）的代表性案例，用以说明 VeriPG 的**数据依赖（DDG）** 在漏洞检测中的关键作用。

**漏洞代码（论文 Figure 5a，逐字复现）**：

```verilog
...
always @ (posedge clk or negedge rst_n)
begin
if (!rst_n)
data_out = 0;
else
data_out = (grant_access) ? data_in : data_out;
grant_access = (usr_id == 3'h4) ? 1'b1 : 1'b0;
end
...
```

**核心问题**：`grant_access` 在 `data_out = (grant_access) ? ...` 一行被用作访问控制条件（决定 `data_in` 能否写入 `data_out`），但实际赋值发生在下一行 `grant_access = (usr_id == 3'h4) ? ...`——**先使用、后赋值**，导致访问控制检查在信号初始化之前就生效，可能引起非确定性执行行为。

**对应的 TDP 规则片段（论文 Figure 5b，逐字复现）**：

```json
...
"Func": "Variable",
...
{"Func": "LoadStatement", "Params": []},
{"Func": "DriverStatement", "Params": ['=']}
{"Func": "Exist", "Params": []}
...
```

**规则的 4 个核心步骤**（论文 Figure 5b 配套文字说明，逐字复现）：
1. 用 `Variable` 原语收集模块中所有信号，并通过 Filter 筛选出相关信号；
2. 从每个被筛选的信号出发，沿 DDG 边的 `LoadStatement` 原语追踪到它的使用点；
3. 从使用点出发，沿 DDG 边找到对应的阻塞赋值（论文正文此处用 `AssignStatement`，Figure 5b 的 JSON 中则写作 `DriverStatement`，二者所指同一概念，应理解为论文自身的术语一致性瑕疵）；
4. 用 `Exist` 原语判断"先使用后赋值"模式是否存在，返回布尔结果。

这个案例展示了 VeriPG 通过 DDG 边追踪"赋值"与"使用"先后关系的能力——论文强调 DDG 在此类检测中起关键作用（"emphasizing its essential role in enabling semantic-level vulnerability detection"），而纯语法分析或纯控制流分析难以可靠捕捉这种"先 use 后 assign"的数据依赖缺陷。

### 4.2 核心模块逐个详解

#### 4.2.1 VeriPG 构建

**做什么**：将 Verilog 源码转换为统一的代码属性图，融合语法（AST）、控制流（CFG）、数据依赖（DDG）三种信息。

**为什么这样设计**：传统 CPG（Code Property Graph）面向 C/C++/Java 等顺序执行语言，而 Verilog 的硬件并发语义（多个 always 块并行执行）给 CFG 和 DDG 的构建带来了独特挑战。论文特别指出"unlike the CFG of software program language, the CFG of Verilog requires handle parallel statements"。VeriPG 的设计关键：
- **以 AST 节点为融合锚点**：AST 是唯一同时被 CFG 和 DDG 引用的结构
- **Common Node Extraction**：从 AST 中提取被 CFG 和 DDG 共同引用的节点，作为图融合的锚点（论文形式化：`∃vcommon ∈ VA, ∃vC ∈ VC, ∃vD ∈ VD, vcommon ∈ vC or vcommon ∈ vD`）
- **Feature Combination**：将 CFG 控制流边和 DDG 数据依赖边附加到同一个 AST 节点上
- **AST 子树分解**：把 AST 沿公共节点断开（`eA ∈ EA, eA = (vi_common, vj_common) → eA = ∅`），变成多个以公共节点为根的子树，每棵子树对应 CFG/DDG 中的一个节点；再把 CFG/DDG 的边重接到这些公共节点上

**工具链**（论文 §3.2 与 §4.3）：使用 PyVerilog（Takamaeda-Yamazaki 2015）进行 AST 解析，自定义脚本完成 CFG、DDG 构建；最终将 VeriPG 存入 Neo4j 图数据库（Webber 2012）。

#### 4.2.2 基于验证的 TDP 规则生成

**做什么**：LLM 读 CWE 自然语言描述，生成 JSON 格式的图遍历检测规则。

**为什么这样设计**：论文指出 LLM 直接分析 Verilog 代码存在两个关键问题——对 Verilog 代码结构理解弱（weak understanding of Verilog code structure），以及由此导致的输出不稳定、事实性错误（"producing unreliable results with factual errors"）。此外，已有工作中 LLM 结合外部知识的方法（如 Fang et al. 2025, Saha et al. 2024）仍存在高误报率（"suffer from a high rate of false positives"），论文归因于 LLM "被不相关信息误导（misled by irrelevant information）"。而"生成规则→确定性执行"的范式通过引入代码图结构分析（"code graph structure analysis via static techniques"）来缓解这些问题——LLM 只负责语义理解到规则转译，确定性执行器保证结果的可重复性。

**三阶段子流程**（论文 §3.4）：
1. **Vulnerability Condition Extraction**：用 Chain-of-Thought（CoT）从 CWE 描述中提取漏洞判定条件。论文指出，CWE 描述通常包含"漏洞表现（vulnerability manifestations）"和"根因（root causes）"两个关键部分；通过迭代优化 prompt engineering 获得稳定、标准化输出。
2. **Rule Generation**：LLM 根据条件生成 VeriPG 遍历规则。
3. **Rule Validation**：基于 VeriPG 结构的有限状态机（FSM）实时检查规则的合法性，错误则反馈给 LLM 修正。规则验证采用迭代优化，**成功即停止，或达到 50 次迭代后停止**。

**图遍历原语体系**（论文 §3.4 给出三类）：

| 类别 | 原语示例 | 功能 |
|------|---------|------|
| 通用图遍历 (Generic graph traversal) | DFS、BFS、沿 AST 边遍历 | 基础图操作组件 |
| 布尔操作 (Boolean operations) | AND/OR 组合、结果过滤 | 组合其他原语的结果 |
| VeriPG 专用遍历 (VeriPG-specific traversal) | `Node(t)`、`Branch(m)`、`Variable`、`DriverVar`、`LoadVar`、`DriverStatement`/`AssignStatement`、`LoadStatement`、`Exist`、`SensList`、CFG/DDG Traversal | 面向 Verilog 语法元素的语义感知处理 |

> 注：论文 Figure 2 在原图中列举的"Node, Variable, Branch, Senslist, DriverVar, LoadStatement..." 与正文 §3.4 给出的原语类别一致，本表格据此整理。

**规则验证器**：基于 VeriPG 的有限状态机。LLM 选定的公共节点作为起始状态，遍历原语驱动状态转移；当某条转移路径不合法时立即停止追踪，保留合法分支继续验证。最终通过 FSM 验证的规则才进入执行阶段。

#### 4.2.3 规则执行器

**做什么**：将验证通过的 TDP 规则在 VeriPG 上执行，输出检测结果。

**三个子组件**（论文 §3.5）：
- **Primitive Executor**：核心入口，调用其他执行器解析参数（primitive 或 path），执行遍历并施加 filter。
- **Filter Executor**：在规则执行过程中施加过滤条件。
- **Path Executor**：管理和解释规则指定的遍历路径。

**为什么确定性强**：规则执行器是纯确定性的图算法（BFS/DFS + 模式匹配），不涉及任何随机性或模型推理。同一个 VeriPG + 同一个 TDP → 永远返回相同结果。

## 5. 关键公式

### 5.1 VeriPG 形式化定义

Verilog 模块表示为有向图（论文 §2.2）：

$$
G = (V, E, A_V, A_E)
$$

**符号说明**（逐项与论文对应）：
- $V = V_A$：AST 节点集合
- $E$：边集合，论文原文："$E$ contains $E_A$, $E_C$ and $E_D$"，即包含 AST 边、CFG 边与 DDG 边
- $A_V$：节点属性，包含 `name`（标识符）、`type`（节点类型）、`lineno`（行号）、`value`（字面值）（论文原文："$A_V$ is property of $V$, contains name, type, lineno and value"）
- $A_E$：边属性，包含 `type`（AST / CFG / DDG）、`condition`（条件表达式）（论文原文："$A_E$ is property of $E$, contain type, condition"）

### 5.2 遍历原语的形式化定义

论文 §2.2 给出了遍历原语的一般性符号定义（"symbolic definition of traversal primitives"）：

$$
P(m) = \{n \mid V_A.\text{property}(n) = t_1,\ V_E.\text{property}(m, n) = t_2\}
$$

**符号说明**：
- $m$：当前节点（current node）
- $n$：下一节点（next node）
- $t_1$：节点 $n$ 的类型约束
- $t_2$：从 $m$ 到 $n$ 的边类型约束

> 这条定义给出了"从节点 m 出发，按指定类型 t2 的边，到达所有满足类型 t1 的节点 n"这一统一图遍历动作的符号表达。论文 §3.4 中给出了两个具体的实例化原语（Equation 1 与 Equation 2）：

**Equation 1 — Node 原语**（匹配指定类型的所有节点）：

$$
\text{Node}(t) = \{n \mid V_A.\text{type}(n) = t\}
$$

**符号说明**：
- $t$：要匹配的节点类型
- $V_A.\text{type}(n)$：取节点 $n$ 的 `type` 属性
- 该原语返回 VeriPG 中所有 `type` 属性等于 $t$ 的节点

**Equation 2 — Branch 原语**（从 IfStatement 节点出发沿 CFG 边到达的所有节点）：

$$
\text{Branch}(m) = \{n \mid V_A.\text{type}(m) = \text{IfStatement}\ \&\ V_E.\text{type}(m, n) = \text{CFG}\}
$$

**符号说明**：
- $m$：当前 IfStatement 节点
- $V_E.\text{type}(m, n)$：取从 $m$ 到 $n$ 的边的 `type` 属性
- `IfStatement`：节点类型值；`CFG`：边类型值
- 该原语返回所有从 IfStatement 节点沿 CFG 边可达的节点

**工程直觉**：这些原语本质上是一个针对硬件代码属性的迷你查询语言——LLM 的任务是把自然语言的漏洞描述"编译"成这种查询语言，而执行器是这种查询语言的解释器。

## 6. 训练与实验设置

### 6.1 是否需要训练

**不需要训练。** VerilogLAVD 中的所有模块都不涉及模型训练：
- LLM 规则生成使用现成的 GPT-4o 与 DeepSeek-V3，通过 prompt engineering + CoT 引导
- VeriPG 构建和规则执行器是确定性算法
- 规则验证器是基于 VeriPG 结构的静态检查工具（FSM）

### 6.2 实验设置

- **数据集**：自建数据集。论文 §4.1 Dataset 段落陈述：种子样本来自开源仓库 Hack@21，通过三种变异策略扩增——(1) name substitution（替换与漏洞相关的信号/寄存器名）；(2) process block extension（插入无关过程块以增加代码复杂度与长度）；(3) structural complication（拉远文件中漏洞组件之间的距离，或引入额外分支/循环结构）。**论文文字部分**：59 个正样本 + 18 个负样本 = 77 个 Verilog 设计，覆盖 12 种 CWE 类型。
  - **论文内部不一致说明**：论文 §4.1 文字段落明确写出 "18 negative samples" 与 "77 Verilog designs"，但 Table 1 中 Non-Vulnerability 一行标为 12，按 Table 1 加总仅为 71（17+13+11+11+7+12）。文字叙述与 Table 1 在负样本数量上不一致，本资料包如实保留两处原始数据。
- **Baseline**（论文 §4.2 Baseline 段落）：
  - **为何不直接对比既有工具**：论文给出三条理由——(1) 缺乏公开代码；(2) 研究目标不一致；(3) 严重依赖人类专家。
  - **LLM-only**：直接让 LLM 分析 Verilog 代码检测漏洞（prompt 中仅含 CWE 简述）
  - **LLM+外部知识（LLM+Knowledge）**：在 LLM-only 基础上补充从 MITRE 官方 CWE 数据库检索到的详细 CWE 信息（类似 RAG）
- **评估指标**：Precision（P）、Recall（R）、F1-score（论文明确指出因正负样本不均衡，避免使用 accuracy）
- **LLM 配置**：**同时使用 GPT-4o（OpenAI 2024）和 DeepSeek-V3（DeepSeek-AI 2024）两个代表模型**——前者是公认的强基线模型，后者是开源模型，兼顾准确性与计算效率
- **Pass@5 评估策略**（论文 §5.1）：为缓解 LLM 输出的随机性，每个方法独立执行 5 次；只要任意一次检出某 Verilog 样本存在漏洞，就判定该样本为脆弱
- **实现细节**（论文 §4.3 Implementation Detail 段落，逐字复现）：
  - Python 3.10
  - PyVerilog（Takamaeda-Yamazaki 2015）解析 Verilog 为 AST
  - **Neo4j**（Webber 2012）作为图数据库存储和操作 VeriPG
  - **Autogen**（Wu et al. 2024）多智能体框架实现规则生成模块的 agent

## 7. 创新点

### 创新点 1：LLM 角色从"检测器"变为"规则生成器"

此前所有 LLM4Hardware-Security 的工作（如 Fang et al. 2025, Saha et al. 2024）都是让 LLM 直接分析代码找漏洞。VerilogLAVD 第一个提出了"LLM 生成图遍历规则→确定性执行器执行"的范式。这个转变的本质是：**让 LLM 做它擅长的事（语义理解→规则转译），不让它做它不擅长的事（理解 HDL 并发语义）。**

### 创新点 2：VeriPG — 面向 Verilog 的统一代码属性图

CPG（Yamaguchi et al. 2014）已经被广泛用于软件安全分析，但直接移植到 Verilog 会遇到并发语义不匹配的问题。VeriPG 的核心贡献是在 Verilog 语境下重新设计了图的构建方式——以 AST 为融合锚点，先在 AST 中提取被 CFG 和 DDG 共同引用的节点（common node），再把 AST 沿这些公共节点断开为子树，最后将 CFG 控制流边和 DDG 数据依赖边重接到公共节点上。这种"以公共节点为锚的子树化 + 边重映射"机制是 Verilog 适配的关键。

### 创新点 3：规则验证闭环

LLM 生成代码（包括规则）的一大痛点是"API misuse"——论文引用 Zhong and Wang 2024 的工作指出 LLM 在软件代码生成中存在 API misuse，并指出 LLM 在规则生成中"similarly exhibit misuse of traversal primitives"。VerilogLAVD 的规则验证器（基于 VeriPG 的有限状态机）在 LLM 生成规则**之后、执行之前**就拦截这类错误，并通过反馈让 LLM 修正。这个设计降低了规则生成对 LLM 能力的依赖——即便 LLM 对遍历原语不太熟悉，也能通过验证循环逐步修正。

### 创新点 4：与执行器协同优化的规则体系

论文 §3.5 强调规则体系（Functions + Filters + Paths）**与执行器联合优化**，既保证遍历效率，又对新漏洞类型具有可扩展性。

## 9. 与芯片流程的关系

### 9.1 在全流程中的位置

VerilogLAVD 位于 RTL 设计阶段（阶段 ①），在代码编写完成后、功能仿真之前插入了安全分析这一环节：

- **接手**：RTL 设计者完成的 Verilog 代码
- **交棒给**：功能仿真（阶段 ②），或 RTL 修改（如果发现漏洞需修复）
- **解决的痛点**：传统安全审计需要资深安全专家手工审查代码，耗时长、成本高、不可规模化。VerilogLAVD 把它自动化了。

### 9.2 「检测到漏洞」和「芯片安全」之间隔着什么

1. **CWE 覆盖度有限**：12 种 CWE 类型远不能覆盖所有硬件安全威胁（例如侧信道、故障注入等物理攻击在覆盖范围，但论文覆盖的 1255/1300 与之相关，物理实现层攻击仍不在范围内）
2. **代码可达性未验证**：检测到的"漏洞"可能在真实使用场景中永远不可达（例如 debug 信号只在测试模式下拉高），导致误报
3. **无 exploitability 判定**：VerilogLAVD 只说"这里有符合 CWE 模式的结构"，不判断这个结构是否真的能被利用
4. **无修复建议**：只检测不修复——与 RTLFixer 等工具互补
5. **不涉及物理层 / 后端安全**：物理不可克隆函数（PUF）、侧信道抗性、版图级 Trojan 等都不在 VerilogLAVD 视野内

## 10. 讨论与局限

### 10.1 论文自述的局限

论文 Conclusion 与 Future Work 段落中明确陈述的唯一局限是：

> "Verilog vulnerabilities tend to be concentrated within specific functional modules. However, our current approach does not incorporate functional context into the detection process. In future work, we plan to explore integrating functional module information to improve vulnerability localization and detection accuracy."
>
> （译：Verilog 漏洞往往集中在特定功能模块内，而当前方法未把功能模块信息纳入检测流程。未来工作将探索集成功能模块信息以提升漏洞定位与检测准确率。）

> ⚠️ **本资料包对原文的澄清**：论文 Conclusion 与 Future Work 段落仅讨论"功能模块信息未利用"这一项局限。任何超出此范围的局限列举（如"无法发现零日漏洞""训练数据样本数少"等）**均非论文原文所列**——请以本节为准。

### 10.2 代码/复现层面的问题

- **代码未发布**：论文脚注 1 注明 "Code will be released upon paper acceptance"，是否已实际公开需以论文官网 / 仓库为准
- **数据集不公开**：77 个 Verilog 设计的自建数据集未公开，无法独立评估
- **LLM 依赖**：规则生成质量依赖 GPT-4o / DeepSeek-V3 级别模型的推理能力，更弱的模型可能导致规则质量下降
- **规则验证器的能力边界**：验证器只能检查"规则语法是否正确"（即 IPTR/IPMR 所衡量的违规），不能检查"规则语义是否真正匹配 CWE 描述"——后者的验证仍然是开放问题
- **Pass@5 评估的代价**：5 次独立运行虽缓解随机性，但也带来 5× 的 LLM 调用成本

> ⚠️ **论文文本观察（Asign / AssignStatement / DriverStatement）**：
> - 论文 Figure 2 的规则示例 JSON 中出现了 `"Params": ["Asign"]`（该字符串来源于论文 PDF Figure 2 的图示文字，随附 txt 文本提取中未直接出现），与正文其它位置使用的 "AssignStatement" 等拼写不一致。
> - 论文 Figure 5b 正文使用 "AssignStatement"，Figure 5b 的 JSON 中却写作 "DriverStatement"，同一概念在不同位置使用了不同的术语。

### 10.3 本资料包的批判性分析

1. **F1=0.54 的绝对水平**：虽然相对 baseline 提升显著，但 0.54 的绝对 F1 仍有提升空间——Table 2 显示 DeepSeek-V3 上的 Total F1 为 0.50、GPT-4o 上为 0.57，不同 backbone 的检测性能差异明显。论文自身 Abstract 与 Conclusion 之间的 F1 提升数值存在不一致（0.27 vs 0.25），复现时建议以 Table 2 的精确数值为准。

2. **"LLM 生成规则"范式的泛化性**：这个方法能工作的前提是漏洞类型可以被形式化为图遍历模式——但不是所有 CWE 都能被精确映射为图模式。例如，信息流安全（information flow security）类漏洞可能无法用简单的图遍历表达。

3. **规则验证器的能力边界**：验证器只能检查"规则语法是否正确"（即 IPTR/IPMR 所衡量的违规），不能检查"规则语义是否真正匹配 CWE 描述"——后者的验证仍然是开放问题。

4. **与 SystemVerilog Assertion 的关系**：SVA 是工业界已有的硬件属性检查方法（论文 §1 / §6 相关工作多次提及 Orenes-Vera et al. 2021、2023 的 AutoSVA 等），但 SVA 需要手工编写、要求极高专业知识。VerilogLAVD 的 LLM 生成规则可以看作 SVA 的自动化替代方案，但 expressiveness 不如 SVA。

5. **Abstract vs Conclusion 的数值不一致**：Abstract 写"F1 improvement of 0.31 and 0.27"（vs LLM-only / vs LLM+Knowledge），Conclusion 写"0.31 and 0.25"。复现时建议以 Table 2 的精确数值为准（vs LLM+Knowledge：DeepSeek-V3 +0.16，GPT-4o +0.32）。

6. **数据集 Table 1 与正文不一致**：Table 1 加总 71，正文 §4.1 写 77，正样本一致（59），负样本不一致（12 vs 18）。

## 12. 一分钟复述版（One-minute Recap）

> **如果只有 60 秒，给同事这样介绍 VerilogLAVD：**

**问题**：现有 Verilog 漏洞检测要么靠专家手工写规则（成本高、不可扩展），要么直接让 LLM 读代码找漏洞（误报高、不稳定）。

**思路**：把 LLM 的角色从"检测器"变成"规则生成器"——让 LLM 读 CWE 自然语言描述，生成结构化的图遍历规则（论文称之为 vulnerability detection rule），再由确定性执行器在统一代码图上执行。

**三个关键设计**：
1. **VeriPG** — 融合 AST + CFG + DDG 的统一 Verilog 代码图，以 AST 公共节点为锚点融合
2. **Validation-Based Rule Generation** — 基于 VeriPG 有限状态机的规则验证器，把 LLM 的"原语误用"率从 ~40% 降到 ~10%
3. **Vulnerability Rule Executor** — Primitive + Filter + Path 三层执行器，执行结果完全确定性

**实验亮点**（77 个 Verilog 设计 / 12 种 CWE）：
- 整体 F1=0.54（论文摘要），对应 Table 2 中 GPT-4o: 0.57 / DeepSeek-V3: 0.50
- 相对 LLM+Knowledge baseline，GPT-4o 上 F1 提升 133%，DeepSeek-V3 上提升 44%
- 规则验证消融：总误用率从 40.87% 降至 10.10%
- 规则执行时间与代码长度不呈线性增长

**位置**：RTL 设计阶段（EDA 流程 ① 阶段），纯静态分析

**实现栈**：Python 3.10 + PyVerilog + Neo4j + Autogen + GPT-4o / DeepSeek-V3

**局限**：未利用功能模块信息；仅覆盖 12 种 CWE；F1 绝对值仍待提升

**本质一句话**：**让 LLM 做它擅长的事（NL→规则），让执行器做它擅长的事（确定性图遍历）——这种"LLM 生成 + 符号执行"的解耦，是 VerilogLAVD 相对前人工作的核心范式贡献。**
