## 1. 一句话定位

**ChipVerilog 是首个从 OpenCores 真实 IP 派生的大规模、层次感知的 RTL 生成 benchmark——不依赖 textbook 习题或合成数据，而是从 5 个经过 FPGA/ASIC 验证的真实芯片项目中手工提取 64 个层次化设计目标（中位 268 行，最大超 1,000 行），用 bounded equivalence checking（对 standalone/multi-module 目标）和仿真（对 full-system 目标）做分级验证，在 GPT-5.4、Claude Opus 4.5、DeepSeek V4 Pro 三个 SOTA 模型上的实验揭示：当前 LLM 在长上下文 RTL 生成上的功能正确率最高仅 23.55%，且当模块涉及 2 个以上子模块时功能正确率骤降至 0.00%。**

这句话里的四个技术承重点，后面逐一拆解：

1. **真实 IP 来源 + 层次化设计** -- 64 个目标来自 OR1200（38 题）、MIPS-16（11 题）、Double-Precision FPU（9 题）、I2C（3 题）、CORDIC（3 题）五个真实芯片项目，覆盖 standalone（37 题）、multi-module（10 题含 1 个子模块，17 题含 2+ 子模块）、full-system（5 题）三个层次级别。
2. **分级验证策略** -- standalone/multi-module 用 Yosys-based bounded equivalence checking（比仿真更强，覆盖 bounded depth 内所有可能输入），full-system 用 Icarus testbench 仿真（因状态空间爆炸）。在验证强度和可扩展性之间取得平衡。
3. **手工 curated 设计描述** -- 每个 prompt 从官方 spec 文档 + 参考 RTL 手工提取，组织 interface/behavior/execution 三层信息，人工审核去歧义、确保与参考 RTL 一致。
4. **暴露 LLM 在层次化、长上下文 RTL 上的根本局限** -- 功能正确率 pass@1 仅 13-24%，且随代码长度（>500 lines 降至 0%）和子模块数（2+ 降至 0%）急剧下降。

## 2. EDA 阶段映射（①-⑰）

参照 [芯片流程.md](../芯片流程.md) 的 17 阶段标准编号：

| 阶段 | 覆盖 | 说明 |
|------|:---:|------|
| **① RTL 设计** | ✅ **核心** | Benchmark 任务：自然语言 spec -> Verilog RTL。每个目标的 prompt 包含详细的 interface/behavior/execution 描述 |
| **② RTL 功能仿真** | ✅ | Full-System 目标（5 个：or1200_top, mips_16_core_top, i2c_master_top, fpu_double, cordic）通过 Icarus testbench 仿真验证 |
| **⑥ 形式验证** | ✅ | Standalone + Multi-Module 目标（59 个）通过 Yosys-based bounded equivalence checking 进行形式等价性验证 |
| ③ 逻辑综合 | ❌ | 虽然使用 Yosys 进行等价性检查（需要 elaboration），但不评测综合结果的质量（面积/时序/功耗）。Yosys 仅作为验证工具而非综合评测工具 |
| ④ 门级仿真 | ❌ | 无 SDF（Standard Delay Format，标准延时格式）反标 |
| ⑤ STA（Static Timing Analysis，静态时序分析） | ❌ | 不评估时序性能 |
| ⑦ 布局规划 Floorplan | ❌ | — |
| ⑧ 标准单元摆放 Placement | ❌ | — |
| ⑨ CTS（Clock Tree Synthesis，时钟树综合） | ❌ | — |
| ⑩ 布线 Routing | ❌ | — |
| ⑪ 后仿真 | ❌ | 无 SPEF（Standard Parasitic Exchange Format，标准寄生参数交换格式） |
| ⑫ 物理验证 DRC + LVS | ❌ | — |
| ⑬ 签核 Signoff | ❌ | — |
| ⑭-⑰ 流片→制造→封装测试→芯片 | ❌ | — |

**覆盖率：3/17（①RTL设计 + ②功能仿真 + ⑥形式验证）。** ChipVerilog 是一个纯前端 benchmark——从 NL specification 到 RTL 功能验证的闭环。与 VerilogEval 相比，它将验证级别从"仿真 pass/fail"提升到了"bounded equivalence proof"，但完全不涉及综合优化和物理设计。

> ⚠️ ChipVerilog 的 "功能正确" 由等价性检查或仿真通过定义。一段面积翻 3 倍、频率只有 10MHz、但逻辑等价于参考设计的 RTL，在 ChipVerilog 眼里是满分。PPA（Power, Performance and Area，功耗/性能/面积）完全不在评测范围内。这与 GenBen（评测 synthesizability 和 PPA）形成关键分野——GenBen 覆盖 4 阶段（含综合和 STA），ChipVerilog 覆盖 3 阶段但验证更严格（形式等价而非仿真）。

## 3. 输入 / 输出

### 3.1 输入：Benchmark Prompt 的结构

ChipVerilog 的每个 benchmark 实例的 prompt 由三部分组成：

**(a) Interface and boundary definitions**：输入/输出端口、信号宽度、时钟/复位假设、宏控制端口

**(b) Dataflow and datapath behavior**：数据依赖、算术运算、mux 选择、寄存器更新、输出计算规则

**(c) Control-flow and FSM behavior**：控制条件、分支决策、状态转移、enable/stall 行为、异常路径

以 **fpu**（double-precision FPU top-level）的 prompt 为例（论文 Appendix A.1 的完整示例）：

```text
Module Objective. The module fpu is the top-level controller
for a double-precision floating-point unit. It integrates the add,
subtract, multiply, divide, rounding, and exception-handling blocks
to produce IEEE-754 double-precision results.

Input Ports:
  - clk: clock signal
  - rst: reset signal
  - enable: rising-edge start signal
  - rmode[1:0]: rounding-mode selector (2'b00=nearest, 2'b01=zero,
    2'b10=+inf, 2'b11=-inf)
  - fpu_op[2:0]: operation selector (3'b000=add, 3'b001=sub,
    3'b010=mul, 3'b011=div)
  - opa[63:0], opb[63:0]: IEEE-754 double-precision operands

Output Ports:
  - out[63:0]: final IEEE-754 result
  - ready: asserted when operation completes
  - underflow, overflow, inexact, exception, invalid: status flags

Submodule Integration: instantiates six submodules:
  - fpu_add, fpu_sub, fpu_mul, fpu_div, fpu_round, fpu_exceptions

Fixed-Latency Completion:
  - addition: 20 cycles, subtraction: 21 cycles,
    multiplication: 24 cycles, division: 71 cycles

Processing Flow: 12-step description of input capture, operation
decode, add/sub routing by operand signs, datapath selection,
rounding, exception handling, and output publication.
```

这个 prompt 的长度约 100 行英文描述。LLM 需要从中提取接口定义、子模块例化关系、控制逻辑（add/sub 路由）、时序约束（固定延迟）——然后生成完整的 Verilog RTL。

- Icarus testbench 仿真结果（full-system 目标）
- pass@k 统计（k=1 和 k=5）

## 4. Benchmark 构建方法

### 4.1 设计来源与规模

ChipVerilog 的 64 个目标全部来自 OpenCores 的真实 IP/core 设计：

| 设计家族 | 目标数 | 类型 | 代码量 | 设计特征 |
|------|:---:|------|------|------|
| **OR1200** | 38 | 32-bit RISC 处理器子系统 | ~6,000 lines | Pipeline + 控制通路 + Cache/MMU + Wishbone 总线 |
| **MIPS-16** | 11 | 16-bit 处理器核 | ~5,000 lines | 五级流水线：取指/译码/执行/访存/写回 |
| **Double-Precision FPU** | 9 | 浮点运算单元 | ~4,500 lines | 算术数据通路 + IEEE-754 舍入 + 异常处理 |
| **I2C** | 3 | 总线协议控制器 | ~1,500 lines | 协议状态机（top/byte/bit 三级） |
| **CORDIC** | 3 | 坐标旋转数字计算 | ~2,000 lines | 迭代计算数据通路 |

这些设计家族的互补性很强：FPU + CORDIC 侧重算术数据通路生成，MIPS-16 侧重紧凑流水线组织，I2C 侧重协议控制逻辑，OR1200 提供最丰富的 IP 级层次结构（包含与外部 RTL 组件交互的集成接口）。

### 4.2 难度分层：Standalone / Multi-Module / Full-System

ChipVerilog 的难度分层是按**结构复杂度**而非人工标注：

| 级别 | 定义 | 目标数 | 验证方式 | 代表目标 |
|------|------|:---:|------|------|
| **Standalone Module** | 自包含，不实例化其他 RTL | 37 | Bounded Equivalence Checking | or1200_alu, fpu_mul, i2c_master_bit_ctrl |
| **Multi-Module Target** | 实例化或依赖外部 RTL 模块（1 个子模块 10 个，2+ 子模块 17 个） | 27 | Bounded Equivalence Checking（替换目标模块，保留参考子模块） | or1200_cpu (13 sub), fpu_double (7 sub), cordic (4 sub) |
| **Full-System Target** | 完整的 IP/core，集成主要子系统 | 5 | Icarus Testbench Simulation | or1200_top, mips_16_core_top, i2c_master_top, fpu_double, cordic |

**为什么是手工 curated 而非自动生成**：自动从 spec 和 RTL 提取的描述可能包含歧义、无关噪声、或残留参考实现的文本线索。手工审核确保：描述与参考 RTL 一致、清晰度足以生成、不泄露 reference implementation 的原文——这保证了 benchmark 的评测有效性。

### 4.4 验证方法论的独特性：Equivalence Check vs Simulation

这是 ChipVerilog 与 VerilogEval/RTLLM 等 benchmark 的最大差异：

**Standalone + Multi-Module 目标**：Bounded Equivalence Checking

- 将生成 RTL 和参考 RTL 同时读入 Yosys
- 展开到 bounded depth（受状态空间限制）
- 用形式工具证明等价性
- **比仿真更强**：仿真只覆盖 testbench 激励的场景，等价性检查覆盖 bounded depth 内**所有可能输入**
- **局限**：不等同于完整形式证明（state-space bound），对迭代设计（如 CORDIC）的 Yosys elaboration 有已知问题

**Full-System 目标**：Simulation-based Validation

- 完整系统（如 OR1200 pipeline）的状态空间太大，等价性检查不可行
- 使用 Icarus testbench 仿真
- **局限**：仿真的覆盖率仅为 testbench 定义的场景，可能遗漏 corner cases

这种分级验证策略在验证强度和可扩展性之间取得了平衡——这是之前 benchmark 都没有做到的。

## 5. 关键公式

### 5.1 Pass@k 定义

ChipVerilog 采用与 VerilogEval 相同的 pass@k 无偏估计：

$$
\text{pass@k} = \mathbb{E}_{\text{Problems}} \left[ 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}} \right]
$$

- $n$：每个问题的总生成样本数（ChipVerilog 固定 n=5）
- $c$：功能正确的样本数（通过等价性检查或仿真）
- $k$：选出的候选数（报告 pass@1 和 pass@5）

**工程直觉**：pass@k 是无偏估计量。Naive 的"k 中至少一个对"比例会系统性低估真实概率，这个公式用组合数学修正了采样偏差。

### 5.2 Syntax Pass Rate（编译通过率）

论文未给编号公式，但其定义为：

$$
\text{SyntaxPass@k} = \mathbb{E}_{\text{Problems}} \left[ 1 - \frac{\binom{n-c_{\text{syn}}}{k}}{\binom{n}{k}} \right]
$$

其中 $c_{\text{syn}}$ 是 5 次生成中通过 iverilog 编译（含 elaboration）的样本数。Table 3 报告的是每个 target 的 5 次中编译通过的具体次数（0-5）。

### 5.3 层次复杂度与功能正确率的关系

从论文 Table 5 的数据可以形式化：

$$
\text{Submodules} = 0: \text{pass@1} = 23.06\%, \text{pass@5} = 44.14\%
$$

$$
\text{Submodules} = 1: \text{pass@1} = 25.33\%, \text{pass@5} = 46.67\%
$$

$$
\text{Submodules} \geq 2: \text{pass@1} = 0.00\%, \text{pass@5} = 0.00\%
$$

**工程直觉**：这不是一个渐进下降，而是一个**悬崖式跌落**。1 个子模块的题目功能正确率甚至略高于 0 子模块（25.33% vs 23.06%，可能因为 1-submodule 题目的 prompt 更详细），但一旦达到 2+ 子模块，所有模型的 pass@1 和 pass@5 都归零——LLM 在跨模块接口匹配（port wiring, width matching, timing alignment, cross-module control/data coordination）上存在根本性缺陷。

## 6. 评测协议与打分

### 6.1 打分公式与评测流程

```text
┌─────────────────────────────────────────────────────────────────┐
│                 ChipVerilog 评测流水线                            │
│                                                                 │
│  Step 1: Prompt → LLM                                            │
│    Curated NL description → LLM API (temperature sampling)      │
│    每题 5 次独立生成（n=5）                                      │
│                                                                 │
│  Step 2: Syntax 过滤                                             │
│    iverilog -g2012 编译 + elaboration                            │
│    → 编译失败的输出直接丢弃，不计入功能验证                       │
│                                                                 │
│  Step 3: 分级功能验证                                            │
│    ┌─────────────────────────────────────────────────────────┐  │
│    │ Target Type         │ Method          │ Coverage        │  │
│    │─────────────────────┼─────────────────┼─────────────────│  │
│    │ Standalone (37)     │ Yosys Bounded   │ All inputs      │  │
│    │                     │ Equiv. Check    │ (bounded depth) │  │
│    │ Multi-Module (27)   │ Yosys Bounded   │ Target module   │  │
│    │                     │ Equiv. Check    │ + ref submodules│  │
│    │ Full-System (5)     │ Icarus Sim      │ Testbench       │  │
│    │                     │                 │ scenarios       │  │
│    └─────────────────────────────────────────────────────────┘  │
│                                                                 │
│  Step 4: Pass@k 统计                                             │
│    pass@k = E[1 - C(n-c, k)/C(n, k)]                            │
│    按目标级别、设计家族、代码长度、子模块数分解                    │
└─────────────────────────────────────────────────────────────────┘
```

### 6.3 主实验结果

**Table A: 综合 pass@k 结果（论文 Table 4）**

| Model | Syntax pass@1 | Syntax pass@5 | Function pass@1 | Function pass@5 |
|------|:---:|:---:|:---:|:---:|
| Claude Opus 4.5 | 78.44% | **96.88%** | 18.06% | **37.50%** |
| **GPT-5.4** | **83.13%** | 93.75% | **23.55%** | **37.50%** |
| DeepSeek V4 Pro | 45.94% | 78.12% | 13.44% | 23.44% |

> 数据来源：论文 Table 4，与原文精确一致。括号中引用编号 [1][15][7] 为原文参考文献。

**这张表说明什么**：

1. **Syntax pass@1 远高于 Function pass@1**：即使最强的 GPT-5.4（83.13% syntax），功能正确率也仅 23.55%。约 60% 的"能编译"的代码在功能上是错的。

2. **增加采样次数确实能恢复很多语法级失败**：Claude 的 Syntax pass@5 达到 96.88%（比 pass@1 提升 18 个百分点），DeepSeek 从 45.94% 跳到 78.12%（+32 个百分点）。但 Function pass@5 的提升有限——最好也仅 37.50%。**额外采样对功能正确的帮助远小于对语法的帮助**。

3. **Claude 和 GPT-5.4 的 Function pass@5 相同（37.50%）**，但 GPT-5.4 的 Function pass@1 更高（23.55% vs 18.06%），说明 GPT-5.4 的"单次生成即正确"的概率更高。

4. **DeepSeek V4 Pro 在 syntax 上明显落后**（pass@1 仅 45.94%），但在 function 上与 Claude/GPT 的差距（13.44% vs 18-24%）小于 syntax 的差距。说明 DeepSeek 生成的代码语法错误多，但一旦编译通过，功能正确的概率不低。

### 6.4 四个核心问题

**问题 1：代码长度 vs 功能正确性（论文 Figure 2）**

按参考 RTL 长度分组的 pass@1：

| 代码长度 | Syntax pass@1 | Function pass@1 |
|------|:---:|:---:|
| < 100 lines | 61.6% - 80.7% | **58.0%** |
| 100-300 lines | — | 17.7% |
| 300-500 lines | — | 3.2% |
| > 500 lines | — | **0.0%** |

**关键发现**：Syntax pass@1 随代码长度变化不大（61.6-80.7%），但 Function pass@1 从 58.0% 断崖式跌至 0.0%。**长上下文 RTL 生成的瓶颈不是语法（LLM 可以生成语法正确的长代码），而是语义（保留控制行为、时序依赖、接口约束、corner cases）。**

Claude 和 GPT-5.4 在大多数长度组上保持相对较高的 syntax pass rate，DeepSeek 对长代码更敏感。但三者在长目标上的 functional correctness **都趋近于零**。

**问题 2：子模块数量 vs 功能正确性（论文 Table 5）**

聚合所有模型的 pass@k（按子模块数分组）：

| 子模块数 | 目标数 | Syntax pass@1 | Syntax pass@5 | Function pass@1 | Function pass@5 |
|------|:---:|:---:|:---:|:---:|:---:|
| 0 | 37 | 77.48% | 95.50% | 23.06% | 44.14% |
| 1 | 10 | 61.33% | 93.33% | 25.33% | 46.67% |
| **2+** | **17** | 55.69% | 74.51% | **0.00%** | **0.00%** |

**关键发现**：这是整篇论文最触目惊心的数据。0 子模块和 1 子模块的目标 syntax pass@5 相似（95.50% 和 93.33%），function pass@5 也接近（44.14% 和 46.67%）。但一旦达到 **2+ 子模块，功能正确率归零**——syntax pass@5 仍维持 74.51%，但没有一个生成样本能通过等价性检查。

**这意味着**：LLM 可以生成语法正确的、包含多个子模块例化的长代码，但无法保证跨模块的 port wiring、width matching、timing alignment 和 control/data coordination 的一致性。这是当前 LLM 在"理解模块间交互"上的结构性缺陷。

**问题 3：编译通过 = 功能正确？**

否。大量生成的 RTL 编译通过但等价性检查失败。论文 per-instance Table 3 显示大量 "Syn. 5, Func. x"（5 个样本全部编译通过但功能失败）的案例，例如 or1200_ctrl、fpu_mul、i2c_master_bit_ctrl 等。

**问题 4：ChipVerilog 为什么比 VerilogEval 难？**

| 维度 | VerilogEval | ChipVerilog |
|------|------------|------|
| 平均代码长度 | ~50-80 lines | **~268 lines**（中位） |
| 最大目标 | ~150 lines | **>1,000 lines** |
| 模块层次 | 单模块 | **3 级**（standalone/multi/full-system） |
| 跨模块依赖 | 无 | **有**（实例化+接口交互） |
| 验证方式 | 仿真 | **等价性检查+仿真** |
| 设计来源 | HDLBits/教科书 | **真实 OpenCores IP** |

GPT-4 在 VerilogEval 上 pass@1 ~75%，但在 ChipVerilog 上，最强模型（GPT-5.4）的 Function pass@1 仅 23.55%。**真实 IP 设计的层次化复杂度对 LLM 是一个数量级的难度提升。**

## 7. 创新点

### 创新点 1：首个大规模、层次感知的 RTL benchmark

ChipVerilog 的 64 个目标、中位 268 行、最大超 1,000 行的规模，远超所有已有 module 级 benchmark。更大的区别在于**层次化**：之前的 benchmark（VerilogEval 156 题、RTLLM 50 题、ArchXBench 51 题）全部是单模块题目，ChipVerilog 引入了 multi-module target（实例化/依赖外部 RTL）和 full-system target。

**论文 Table 1 的数据**：在 ChipVerilog 之前，只有 RealBench（60 题，open-source IPs，simulation+formal）涉及跨模块依赖和 IP 级设计，但 RealBench 也没有 1,000+ lines 的目标，且 ChipVerilog 的验证更系统（分级等价性检查+仿真）。

### 创新点 2：分级验证策略——在验证强度和可扩展性间取得平衡

ChipVerilog 的验证不是一刀切。Standalone/Multi-Module 用 bounded equivalence checking（比仿真更强，覆盖 bounded depth 内所有输入），Full-System 用仿真（状态空间太大，等价性检查不可行）。这是在验证完备性和可扩展性之间的工程权衡——之前 benchmark 都没有这样细分的验证策略。

### 创新点 3：真实 OpenCores IP 来源——不再只是教科书习题

ChipVerilog 的设计来源不是 HDLBits 教学题或手写的小模块，而是从 OpenCores 成熟开源 IP 中手工提取的。OR1200、MIPS-16、FPU、I2C、CORDIC 这些设计**经过真实 FPGA/ASIC 验证**，具有工业级的设计复杂度（pipeline 时序、总线协议、MMU/TLB、cache 控制、异常处理）。这使 benchmark 的评测结论比教科书习题更有工程参考价值。

### 创新点 4：手工 curated 描述质量——信息完整且无泄露

ChipVerilog 的每个 prompt 由 interface/behavior/execution 三层信息组成，从官方 spec 文档 + 参考 RTL 手工提取，人工审核去歧义。关键设计原则：**描述足够详细以指导生成，但不暴露参考实现的原文**——这保证了 benchmark 的评测有效性（不是代码翻译测试）。

### 创新点 5：首次系统暴露 LLM 在层次化、长上下文 RTL 生成上的根本局限

论文的 per-instance results（Table 3）、code length analysis（Figure 2）、hierarchy analysis（Table 5）构成了一个完整的失败分析框架。核心发现是：(a) 语法正确率受代码长度影响小，(b) 功能正确率在 >500 lines 和 2+ 子模块处断崖式归零，(c) 不同模型在不同设计家族上的强项不同。这些发现为后续 LLM+RTL 研究指明了明确的改进方向。

### 9.1 在全流程中的位置

```text
│  ⑥ 形式验证（Bounded Equivalence）          │
│        │                                    │
├────────┼────────────────────────────────────┤
│  ～～～ ChipVerilog 的覆盖边界 ～～～      │

└─────────────────────────────────────────────┘
```

### 9.2 「等价性检查通过」和「能流片」之间的距离

ChipVerilog 的 "等价性检查通过" 只证明生成 RTL 和参考 RTL 在 bounded depth 内逻辑等价。但以下环节仍然缺失：

**在阶段 ③ 逻辑综合被拦下的**：等价性检查使用 Yosys 进行 elaboration，但这不等于"代码可综合"。参考 RTL 可能包含仿真用构造（initial 块、$display 等），这些在综合时会失败。ChipVerilog 的等价性检查只验证逻辑行为是否一致，不验证代码是否可综合（没有跑 Yosys 的完整 synthesis flow）。

**在阶段 ⑤ STA 被拦下的**：等价性检查不关心时序。一段逻辑等价但关键路径延迟 10ns 的代码，在 2ns 时钟周期下无法工作。ChipVerilog 对此完全无感知。

**验证覆盖的局限**：Bounded equivalence check 受 state-space bound 限制，不是完整的形式证明。Full-system 目标的仿真覆盖率由 testbench 决定，可能存在未覆盖的 corner cases。论文在 README 中明确提到了 CORDIC reference 的 Yosys elaboration 和 bounded equivalence 的证明边界。

**代工厂/工艺依赖性**：真实流片需要代工厂提供的标准单元库、PDK、工艺 corner models。ChipVerilog 不涉及任何物理设计阶段。

## 10. 讨论与局限

### 10.1 论文自述的局限

1. **无仓库级 LICENSE**：官方仓库可见但未检测到标准开源许可证；上游 OpenCores IP 各自有独立许可条款。用于训练数据时需要逐项审查。

2. **验证边界**：Bounded equivalence checking 受展开深度限制，不等同于完整形式证明。CORDIC 等迭代设计的 Yosys elaboration 有已知问题。

3. **仿真覆盖率有限**：Full-system 目标的 testbench 仿真仅覆盖测试激励的场景，可能遗漏未触发的 corner cases。

4. **无综合/PPA 评估**：仅验证功能正确性，不评估生成 RTL 的可综合性、面积、时序、功耗。这使 ChipVerilog 无法回答"生成的 RTL 能不能变成实际芯片"。

5. **64 个目标仍有限**：工业级 IP 验证通常需要数百个设计变体。5 个设计家族也偏少（缺少 DSP、NoC、加密加速器、SerDes 等类别）。

6. **描述质量依赖人工审核**：当前 benchmark 描述经手工整理，实际使用中自动生成的描述可能质量更低。这限制了 benchmark 的规模化能力。

7. **未来方向**：扩展到更多设计家族、完善 LICENSE 声明、增加综合/PPA 评估维度、支持增量式/迭代式生成评测。

### 10.2 代码/复现层面的问题

1. **仓库 LICENSE 缺失**：代码仓库目前没有仓库级别的 LICENSE 文件。OpenCores 上游 IP（如 OR1200 是 LGPL）有各自的许可条款——商用训练需谨慎。

2. **工具链版本依赖**：Icarus Verilog 和 Yosys 的版本差异可能导致等价性检查结果不同。论文未详细说明所用版本号。

3. **CORDIC 的已知问题**：README 明确提到 CORDIC reference 的 Yosys elaboration 和 bounded equivalence 的边界问题——某些 CORDIC 设计可能在特定 Yosys 版本下无法正确 elaborate。

4. **手写 testbench 的覆盖率缺乏定量数据**：与 GenBen 不同（明确报告 95.17% 覆盖率），ChipVerilog 的 full-system testbench 覆盖率没有给出具体数字。

5. **未提供完整复现脚本**：仓库包含 reference RTL、prompts、results、tools，但端到端评测脚本（自动下载模型、跑 64 题、收集结果）可能需要自行组装。

### 10.3 评测公平性与可信度分析

**维度 1：等价性检查 vs 功能正确性**

Bounded equivalence check 在理论上比仿真更强（覆盖 bounded depth 内所有输入），但实际受限于：(a) Yosys 的 bounded check 实现可能存在 bug，(b) reference RTL 本身可能存在 bug（虽然 OpenCores IP 是成熟的，但并非 bug-free），(c) state-space bound 意味着超过 bound depth 的行为没有验证。因此"等价性检查通过"应解读为"在 bounded depth 内与参考设计一致"，而非"完全功能正确"。

**维度 2：模型评测的公平性**

三个被评测模型（Claude Opus 4.5、GPT-5.4、DeepSeek V4 Pro）都是闭源商业模型。它们的版本可能在评测时不同，temperature 设置可能影响结果。论文未详细说明 prompting strategy（如是否提供系统 prompt、few-shot examples），不同模型对这些因素的敏感度不同。

**维度 3：prompt 质量对结果的影响**

ChipVerilog 的 prompt 质量依赖人工审核——这是优势（更高一致性）也是局限（难以扩展到更多设计）和 bias（人工审核的 prompt 可能对某些模型更"友好"）。例如，Claude 在长 prompt 上的理解能力更强，可能部分因为其训练数据中包含更多技术文档。

**维度 4：Multi-Module 验证的替换策略**

在 multi-module 等价性检查中，只有目标模块被替换为生成 RTL，其余子模块保留参考实现。这意味着：(a) 生成模块的功能正确性依赖于参考子模块的接口行为，(b) 如果生成模块的接口与参考子模块不完全匹配，等价性检查会正确报告失败。但这也意味着测试的是"在正确子模块环境下目标模块的行为正确性"而非"独立正确性"——如果参考子模块本身有 bug，可能导致合理的生成模块被错误判为失败。

**维度 5：统计可信度**

n=5 的小样本量在功能正确率极低（如 0%）时无法区分"真的 0%"和"极低概率事件"。17 个 2+ submodule 目标全部 0% function pass@1 和 pass@5 是强有力的信号，但如果将来有模型在某个 2+ 目标上偶尔成功一次，统计显著性会如何？需要更大的 n 或更系统的失败分析。

## 12. 一分钟复述版

ChipVerilog（HKUST(GZ), arXiv 2026）是首个从 **OpenCores 真实 IP** 派生的大规模、层次感知 RTL generation benchmark。核心四招：

1. **64 个目标、5 个设计家族**：OR1200（38 题）、MIPS-16（11 题）、Double-Precision FPU（9 题）、I2C（3 题）、CORDIC（3 题）。总计约 20,400 行 Verilog，中位 268 行，3 个目标超 1,000 行。远超 VerilogEval（~50-80 行）和 RTLLM（~50-100 行）。

2. **三个层次级别**：Standalone（37 题，不实例化其他模块）、Multi-Module（27 题，含 1-13 个子模块实例化）、Full-System（5 题，完整 IP/core 集成）。

3. **分级验证策略**：Standalone + Multi-Module 用 Yosys bounded equivalence checking（比仿真更强，覆盖 bounded depth 内所有输入），Full-System 用 Icarus testbench 仿真（状态空间太大，等价性检查不可行）。

4. **手工 curated 描述**：每个 prompt 由 interface/behavior/execution 三层信息组成，从官方 spec + 参考 RTL 手工提取，人工审核去歧义、避免泄露参考实现。

**关键数据**：GPT-5.4 Function pass@1 23.55%，Claude 18.06%，DeepSeek 13.44%。**两个断崖**：(a) 代码长度 >500 lines 时 functional pass rate 归零（虽然 syntax pass rate 完好），(b) 子模块 >=2 时 functional pass@1 和 pass@5 全部归零（虽然 syntax pass@5 仍有 74.51%）。揭示 LLM 在"语法对但跨模块逻辑错"上的结构性缺陷。

**边界**：覆盖流程阶段 3/17（RTL+仿真+形式验证），无综合/PPA 评估，无 LICENSE，64 题仍偏少，等价性检查受 state-space bound 限制。适合用于：评测 LLM 的层次化 RTL 生成能力、发现长上下文中的语义保持缺陷、SFT 训练数据来源（需审查 IP 许可）。不适合用于：评测"能否做出芯片"（离流片还有 14 个阶段）。
