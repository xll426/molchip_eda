## 1. 一句话定位

**CreativEval 是第一个系统评估 LLM 硬件代码"创造力"的 benchmark 框架：它将认知科学中的 fluency/flexibility/originality/elaboration 四维映射到 RTL 设计任务，用 GNN4IP 图嵌入相似度量化生成实现与 golden 的结构差异，在 120 道 HDLBits 题目上评测 6 个模型（CodeLlama-7B/13B、VeriGen-6B/16B、GPT-3.5/4），发现 GPT-3.5 等权创造力总分最高（0.2201），而 GPT-4 功能正确性最强（pass@10 = 0.3750），首次揭示了"功能正确"之外的设计多样性维度。**

这句话里的三个技术承重点，后面逐一拆解：

1. **四维创造力指标定义** -- 将认知科学经典的发散思维四维度映射到 RTL 代码生成场景：fluency（同一规格能产生多少种不同正确实现）、flexibility（看过 golden 后能否写出结构不同的替代实现）、originality（成功实现与 golden 有多不相似）、elaboration（能否用小模块组合成更大功能模块），每个维度都有量化的计算公式。
2. **GNN4IP 图嵌入作为结构相似度的代理指标** -- 不是用文本 diff 或 AST 树编辑距离，而是将 Verilog 代码转为 Data-Flow Graph（DFG），经两层 GCN + SAGPool 嵌入为 16 维向量，用 cosine similarity 判断"两个实现有多像"。这使得相似度对重构、命名差异和表达式重排具有一定鲁棒性。
3. **六模型横向对比 + 条件成功偏差** -- 首次系统比较开源/闭源 LLM 在硬件创造力上的差异，同时暴露了"功能正确性不进入创造力总分""全失败题从分母消失"等指标设计边界。

## 2. EDA 阶段映射（①-⑰）

参照 [芯片流程.md](../芯片流程.md) 的 17 阶段标准编号：

| 阶段 | 覆盖 | 说明 |
|------|:---:|------|
| **① RTL 设计** | ✅ **核心** | 从自然语言规格生成 Verilog 模块。CreativEval 的核心评测目标：同一规格下能否产生结构不同的多种正确 RTL 实现 |
| **② RTL 功能仿真** | ✅ **核心** | Icarus Verilog 10.3 编译 + vvp 执行 + testbench 比对。功能正确是进入创造力评分的先决条件——只有 testbench 全通过的候选才进入 GNN4IP 相似度分析 |
| ③ 逻辑综合 | ❌ | 不调 Yosys / Design Compiler。结构差异的"设计价值"（面积、时序、功耗差异）完全不评估。两段 RTL 可能在 DFG 嵌入空间中距离很远，但综合后面积差不到 5% |
| ④ 门级仿真 | ❌ | 无 SDF（Standard Delay Format，标准延时格式）反标，不检查毛刺/建立保持违例/X 传播 |
| ⑤ STA（Static Timing Analysis，静态时序分析） | ❌ | 不计算任何路径延迟。论文的"结构不同"是指 DFG 图结构不同，不涉及时序路径差异 |
| ⑥ 形式验证 | ❌ | — |
| ⑦ 布局规划 Floorplan | ❌ | — |
| ⑧ 标准单元摆放 Placement | ❌ | — |
| ⑨ CTS（Clock Tree Synthesis，时钟树综合） | ❌ | — |
| ⑩ 布线 Routing | ❌ | — |
| ⑪ 后仿真 | ❌ | 无 SPEF（Standard Parasitic Exchange Format，标准寄生参数交换格式） |
| ⑫ 物理验证 DRC + LVS | ❌ | — |
| ⑬ 签核 Signoff | ❌ | — |
| ⑭-⑰ 流片→制造→封装测试→芯片 | ❌ | — |

**覆盖率：2/17。** CreativEval 是一个**纯 RTL 设计阶段的多样性评测框架**。它关心的问题是"同一份规格能有多少种正确的 RTL 写法"，而不是"这些写法哪个更快/更省面积/更省电"。它的输出是对 LLM"设计空间探索能力"的量化，不涉及任何 downstream 阶段。

> 该论文的一个关键边界需要明确：CreativEval 的"创造力"不等于 PPA（Power, Performance and Area，功耗/性能/面积）质量。一个用冗余逻辑故意把 golden 实现改写得很不相似的候选，在 Creativity 评分上反而得分更高，但在综合/STA 阶段会被当成劣化实现直接丢弃。创造力指标是功能正确的"必要但不充分"的扩展维度——它告诉你有多少种走法，不告诉你哪条路最好。

## 3. 输入 / 输出

### 3.1 输入（三类 Prompt）

CreativEval 定义了三种 prompt 类型，对应创造力的不同子维度。

**(a) Fluency / Originality Prompt（111 题）**

来源为 HDLBits（通过 AutoChip 筛选），包含自然语言描述 + 固定模块接口头。每题独立采样 t = 10 次，截断到第一个 `endmodule`。

```verilog
// Create a full adder.
// A full adder adds three bits (including
// carry-in) and produces a sum and carry-out.

module top_module (
    input a, b, cin,
    output cout, sum
);
```

**(b) Flexibility Prompt（110 题）**

给出 golden 实现 `true_module`，要求模型在 `top_module` 中写一个 **different and unique** 的替代实现。同样每题 t = 10 次采样。

```verilog
// You are a professional hardware designer
// that writes correct, fully functional
// Verilog modules.
// Given the fully implemented example of
// the Verilog module below:

module true_module(
    input a, b, cin,
    output cout, sum
);
    assign sum = a ^ b ^ cin;
    assign cout = a & b | a & cin | b & cin;
endmodule

// Finish writing a different and unique
// implementation of the provided true_module
// in the module below, top_module.

module top_module (
    input a, b, cin,
    output cout, sum
);
```

**(c) Elaboration Prompt（9 题）**

给出若干小模块接口，要求组合成更大功能模块。

```verilog
// You are given a module add16 that
// performs a 16-bit addition.
// Instantiate two of them to create a 32-bit
// adder.

module add16 (input[15:0] a, input[15:0] b,
    input cin, output[15:0] sum, output cout );

module top_module (
    input [31:0] a,
    input [31:0] b,
    output [31:0] sum
);
```

9 题涵盖：Module_1、Module_add、Module_addsub、Module_cseladd、Module_fadd、Module_name、Module_pos、Module_shift、Module_shift8。

### 3.2 推理超参数

| 参数 | 值 |
|---|---|
| temperature | 0.3 |
| max tokens | 1024 |
| top-k | 10 |
| top-p | 0.95 |
| 每题采样数 t | 10 |
| 截断策略 | 第一个 `endmodule` |

### 3.3 输出

每个模型在全部 120 题（111 单模块 + 9 elaboration）上各生成 10 个候选，总计 1200 个 Verilog 文件。经 Icarus 仿真筛选后，功能正确的候选进入 GNN4IP 相似度分析，最终聚合为 6 维评测结果：Functionality、Fluency、Flexibility、Originality、Elaboration、Creativity。

## 4. Benchmark 构建方法

### 4.1 题目来源与数据集规模

CreativEval 的 prompt/testbench 数据集来自 **HDLBits** 教学平台，经由 **AutoChip** 筛选整理。数据集构成：

| 子集 | 题数 | 用途 |
|------|:---:|---|
| 单模块题（single-module） | 111 | fluency / originality |
| 灵活性改写题（flexibility format） | 110 | flexibility |
| 多模块组合题（elaboration） | 9 | elaboration |
| functionality 总题数 | 120（111 + 9） | pass@10 功能覆盖率 |

题目涵盖组合逻辑（含卡诺图 K-map）、时序逻辑、有限状态机（FSM，含文字描述/波形示例/状态转移表多种描述形式）、以及迷宫游戏、旅鼠游戏、定时器等应用描述题。

### 4.2 难度分层

CreativEval 不显式标注每道题的难度等级，但题目本身隐含了从简单组合逻辑（如 andgate）到复杂多周期 FSM（如旅鼠游戏）的自然难度梯度。论文从多组消融配置的失败题中提取并集共 65 道，按 prompt 类型分为 5 类：

| 题型类别 | 失败题数 | 占比 |
|------|:---:|:---:|
| Application (Descr.) 应用描述 | 23 | 35.4% |
| Comb+Seq+FSM (Descr.) 文字描述 | 19 | 29.2% |
| Comb+Seq+FSM (Waveform) 波形示例 | 8 | 12.3% |
| Comb (Kmap) 卡诺图 | 6 | 9.2% |
| FSM (Trans. Table) 状态转移表 | 9 | 13.9% |

### 4.3 参考实现（Golden Response）

- 单模块题：110/111 有 golden solution（`Exams_ece241_2013_q12` 缺 golden）。
- Elaboration 题：9/9 有 golden solution。
- Golden 由人工撰写或从 HDLBits 标准答案中提取，作为 GNN4IP 相似度计算的参考锚点。

### 4.4 质量把关流程

CreativEval 作为评测框架，其"质量"体现在数据一致性和指标可重复性上：

1. **功能正确性第一关**：所有候选必须通过 Icarus Verilog 10.3 编译 + testbench 仿真，仿真输出包含 `all tests passed` 或 `All tests passed` 才进入创造力分析。
2. **截断规范**：每题采样截取到第一个 `endmodule`，排除后续解释性文字和重复模块。
3. **相似度去重**：fluency 指标使用 Python `set` 对浮点相似度值去重，不同相似度值被视为不同实现。
4. **多 testbench 支持**：代码框架允许每道题有多份 testbench，任意一份不通过即标记为失败。
5. **断点续跑**：脚本内置目录切片功能，支持大规模实验的断点续跑。

## 5. 关键公式

论文给出了完整的数学定义（Equation 1-6）。以下公式均直接来自原文，符号与含义与原文一致。

### 5.1 符号约定（贯穿全部公式）

- $p$：总 prompt 数（单模块 111，elaboration 9）
- $t = 10$：每题采样数
- $n$：至少有一个功能正确候选的 prompt 数
- $R_i$：第 $i$ 个成功 prompt 的功能正确候选集合
- $S(R_i)$：$R_i$ 中每个候选与 golden 的 GNN4IP 相似度值集合，$S(\cdot) \in [-1, 1]$

### 5.2 Fluency（流畅性）

衡量模型在单个 prompt 上产生"不同且正确"实现的数量。$|S(R_i)|$ 是不同相似度值的个数（用 Python `set` 去重）。

$$
F = \frac{1}{n} \sum_{i=1}^{n} \frac{|S(R_i)|}{t}
$$

- $F$：fluency 指标，取值 $[0, 1]$
- $|S(R_i)|$：第 $i$ 个 prompt 中功能正确候选的不同相似度个数
- $t$：每题总采样数（固定为 10）
- $n$：至少有一个功能正确候选的 prompt 数

**工程直觉**：这个公式同时做了两件事——十次采样中失败越多，$|S|/t$ 越低；但十次全失败的题不进入 $n$，从均值中完全消失。因此它不是"全体题目上的独特实现数"，而是"条件于至少成功一次的题目上的独特相似度比例"。这就是条件成功偏差的来源。

**为什么用相似度做去重而不是 AST 比较**：GNN4IP 的 16 维图嵌入对语义保持变换（如表达式重排、信号重命名）具有一定鲁棒性，而对结构差异（如 ripple-carry vs carry-lookahead 加法器）产生不同的嵌入向量。相比 AST 编辑距离，GNN 嵌入更能捕捉"功能等价但结构不同"的差异。

### 5.3 Flexibility（灵活性）

衡量模型在看到 golden 实现后，能否写出结构明显不同的替代实现。阈值函数 $T(s)$ 以 $s < 0$（余弦相似度为负表示嵌入方向相反）作为"不同结构"的判据。

$$
T(s) = \begin{cases} 1 & \text{if } s < 0 \\ 0 & \text{if } s \geq 0 \end{cases}
$$

- $T(s)$：阈值函数，$s < 0$ 时判定为"灵活/不同于 golden"

$$
X = \frac{1}{n} \sum_{i=1}^{n} T(\min S(R_i))
$$

- $X$：flexibility 指标，取值 $[0, 1]$
- $\min S(R_i)$：第 $i$ 个 prompt 中所有功能正确候选与 golden 的最小相似度

**为什么阈值选 $s < 0$**：余弦相似度的零点是一个自然的语义分界线——正值表示两个向量在同一半空间（结构相近），负值表示在不同半空间（结构显著不同）。threshold = 0 是仅依赖 embedding 空间几何性质、无需人工调参的客观边界。

### 5.4 Originality（原创性）

衡量成功实现与典型 golden 的"偏离程度"。将最小相似度从 $[-1, 1]$ 线性映射到 $[0, 1]$，1 表示最独特。

$$
O = \frac{1}{n} \sum_{i=1}^{n} \frac{-\min S(R_i) + 1}{2}
$$

- $O$：originality 指标，取值 $[0, 1]$
- $\min S(R_i)$：第 $i$ 个 prompt 的最小相似度
- 线性映射关系：$\min S = 1 \Rightarrow O = 0$（完全相同）；$\min S = 0 \Rightarrow O = 0.5$；$\min S = -1 \Rightarrow O = 1$（最独特）

**与 Flexibility 的区别**：Flexibility 是二元判定（是否有任一候选与 golden 足够不同），Originality 是连续度量（最不同的那个候选到底有多不同）。一个模型可能每次都能写出略微不同的实现（中等 Originality），但永远写不出方向相反的嵌入向量（零 Flexibility）。

### 5.5 Elaboration（精细加工）

衡量模型利用给定子模块组合成更大功能模块的能力。

$$
E = \frac{n_{\text{elab}}}{p_{\text{elab}}}
$$

- $E$：elaboration 指标，取值 $[0, 1]$
- $n_{\text{elab}}$：功能正确且确实实例化/使用了给定子模块的题数
- $p_{\text{elab}} = 9$：elaboration 题型总数

### 5.6 Overall Creativity（综合创造力）

四个子指标等权平均。注意 Functionality 不进入 C，仅并列报告。

$$
C = 0.25 F + 0.25 X + 0.25 O + 0.25 E
$$

- $C$：综合创造力指标，取值 $[0, 1]$
- $F, X, O, E$：四个子指标

## 6. 评测协议与打分

### 6.1 评测什么能力？

CreativEval 评测 LLM 在 **RTL 代码生成** 中的四种发散思维能力：

| 维度 | 评测的能力 | RTL 场景含义 |
|------|-----------|-------------|
| Fluency | 产生多样正确方案的量 | 同一 full adder 规格，能否生成 assign、case、门级等多种功能正确的实现 |
| Flexibility | 不被范例束缚的改写能力 | 看了 `assign sum = a^b^cin` 的实现后，能否用行为级 `always @(*)` 或门级结构写出不同版本 |
| Originality | 偏离常规模板的程度 | 生成的实现与标准答案在 DFG 结构上有多不像 |
| Elaboration | 层次化组合能力 | 能否用两个 `add16` 模块正确拼出 32-bit adder，而非把所有逻辑写平 |

### 6.2 怎么打分？

**步骤 1：功能正确性前置筛选**

- 每题生成 t = 10 个候选
- 截断到第一个 `endmodule`
- Icarus Verilog 10.3 编译 + testbench 执行
- 通过条件：simulation stdout 包含 `all tests passed` 或 `All tests passed`
- 编译失败 -> reward = -1；仿真失败 -> reward = -0.5；全部通过 -> reward = 1

**步骤 2：GNN4IP 图嵌入相似度计算**

对每个功能通过的候选：

```text
Verilog 源码
    ↓ Pyverilog / HW2GRAPH
Data-Flow Graph (DFG)
    ↓ 2 层 GCN + SAGPool + max readout
16 维图嵌入向量
    ↓ cosine similarity with golden embedding
S ∈ [-1, 1]
```

GNN4IP 使用预训练权重（来自上游 HW2VEC，原用于 IP piracy 检测，`model.pth` 约 7.6 MiB，不是本论文新训练）。模型配置：2 层 GCN、SAGPool 池化、max readout、dropout=0.5。

**步骤 3：按公式聚合**

- 每个成功 prompt 收集所有功能正确候选的相似度值集合 $S(R_i)$
- 按公式 (1)-(5) 分别计算 F/X/O/E
- 按公式 (6) 等权平均得 C
- Functionality 单独报告为 pass@10（每题 10 次中至少一次成功即为该题通过）

| LLM | Functionality | Fluency | Flexibility | Originality | Elaboration | **Creativity** |
|------|:---:|:---:|:---:|:---:|:---:|:---:|
| CodeLlama-7B | 0.2417 | 0.1483 | 0.0000 | **0.2926** | 0.2222 | 0.1658 |
| CodeLlama-13B | 0.3167 | 0.1611 | 0.0260 | **0.3021** | 0.3333 | 0.2056 |
| VeriGen-6B | 0.3667 | 0.1244 | 0.1000 | 0.2527 | 0.3333 | 0.2026 |
| VeriGen-16B | 0.3250 | 0.1189 | 0.0556 | 0.2771 | 0.3333 | 0.1962 |
| GPT-3.5 | 0.3083 | 0.1343 | **0.1600** | 0.2526 | 0.3333 | **0.2201** |
| GPT-4 | **0.3750** | **0.1644** | 0.0795 | 0.2657 | 0.3333 | 0.2107 |

**这张表说明什么**：

1. **GPT-3.5 创造力总分最高（0.2201）**，主要得益于 Flexibility 碾压式领先（0.1600 vs 第二名 VeriGen-6B 的 0.1000）。GPT-3.5 更容易在被给定 golden 后"跳出模板"写出结构不同的替代方案。
2. **GPT-4 功能正确性最强（0.3750）且 Fluency 最高（0.1644）**，但创造力总分（0.2107）低于 GPT-3.5。更大的模型倾向于生成与训练数据中"标准答案"更接近的实现，这可能抑制了结构多样性。
3. **CodeLlama-13B 的 Originality 最高（0.3021）**，说明其成功实现与 golden 差异最大——但这可能来自冗余逻辑或非标准写法，而非真正的架构创新。
4. **Elaboration 区分度严重不足**：仅两档（CodeLlama-7B 的 0.2222 = 2/9，其余五模型 0.3333 = 3/9）。9 题的样本量不足以区分模型间的层次化组合能力。
5. **模型规模增大并不必然提升创造力**：VeriGen-16B 的创造力（0.1962）低于 VeriGen-6B（0.2026），GPT-4（0.2107）低于 GPT-3.5（0.2201）。功能正确性与设计多样性是两个不同的能力维度。

### 6.6 局限性在哪？

从评测框架本身的角度，CreativEval 存在以下结构性局限：

1. **功能正确性与创造力脱钩**：Functionality 不进入 C，功能覆盖率极低的模型（如 CodeLlama-7B 仅 24%）仍可能因少数题的高多样性获得中等 C。C 应被称为"条件于做对的情况下，设计多样性有多高"。
2. **条件成功偏差**：F/X/O 仅在"至少有一个功能正确候选"的 $n$ 个 prompt 上平均，全失败题被完全排除。理想做法应同时报告无条件创造力（全失败题记 0）与条件创造力。
3. **单一 golden 相似度的局限性**：GNN4IP 来自 IP piracy 检测任务，domain shift 未经验证；低相似度可能来自冗余逻辑、parser 差异或混淆，而非真正的架构创新。没有一项独立校准实验证明 GNN 分数与人工新颖性判断一致。
4. **exact-float 去重问题**：fluency 用 Python `set` 对浮点数去重，两个结构完全不同的实现若恰好产生相同 scalar similarity 会被错误合并，两个相同实现若因 Dropout（训练模式下未关闭）产生微小浮点差异则被错误分开。
5. **Elaboration 样本过少**：仅 9 题，单题权重 0.1111，无法可靠区分模型能力。
6. **评测不包含硬件质量维度**：PPA、可综合性、资源利用率完全不评估。

## 7. 创新点

### 创新点 1：首次将认知科学四维创造力框架映射到 RTL 代码生成

在 CreativEval 之前，所有 LLM+RTL 评测（VerilogEval、RTLLM、AutoChip 等）只看"功能是否正确"。CreativEval 将认知科学中经典的 divergent thinking 四维度（Fluency/Flexibility/Originality/Elaboration）**首次映射到硬件代码生成任务**，并给出了每个维度的量化公式。

已有方法的评测逻辑："给定规格，模型能否生成一个功能正确的 RTL？"（yes/no 二元判定）

CreativEval 的评测逻辑："给定规格，模型能生成多少种结构不同但都正确的 RTL？每种与标准答案有多不像？被展示范例后还能否主动换架构？"（连续值 + 多维剖面）

这相当于把评测从"应试分数"扩展到了"设计空间探索能力"。在芯片设计实践中，规格往往是不完全确定的，工程师需要在多种可行实现中根据下游约束（面积/功耗/时序）做 trade-off——CreativEval 首次量化了 LLM 在这个 trade-off 空间中的覆盖广度。

### 创新点 2：引入 GNN 图嵌入相似度作为结构多样性的代理指标

传统的代码相似度度量（AST 编辑距离、token-level BLEU、文本 diff）无法区分"语义保持的重构"和"真正的结构差异"。例如：

```verilog
// 实现A：连续赋值
assign sum = a ^ b ^ cin;
assign cout = a & b | a & cin | b & cin;

// 实现B：行为级（与A语义等价，DFG相同）
always @(*) begin
    sum = a ^ b ^ cin;
    cout = (a & b) | (a & cin) | (b & cin);
end
```

在 AST 编辑距离上 A 和 B 不同（`assign` vs `always @(*) begin...end`），但在 DFG 图结构上完全相同——应被视为同一种实现。反之，相同的 "assign" 语法但不同的布尔表达式（如用 NAND-only 实现 vs AND-OR 实现）应被视为不同实现。

GNN4IP 通过 DFG 图嵌入自然地处理了这种区分：语义保持的重构产生相似嵌入，结构差异（不同门级结构、不同状态编码方式）产生不同嵌入。

### 创新点 3：多 LLM 横向对比揭示"功能正确"之外的多样性维度

CreativEval 对六个模型进行了系统的 head-to-head 创造力对比。结果挑战了"越大越好"的直觉——GPT-4 功能最强但创造力不如 GPT-3.5，VeriGen-16B 在 creativity 上不如 6B 版本。这证明功能正确性和设计多样性需要分别评测，未来的 LLM 优化方向需要在"更准"和"更活"之间做平衡。

## 9. 与芯片流程的关系

### 9.1 在全流程中的位置

```text
  人写规格 + 人准备 golden testbench
             │
             ▼
┌─────────────────────────────────────────────────────────┐
│  ① RTL 设计    ←───────── CreativEval 在此处 ────────→ │
│        ↓            评测 "同一规格能有多少种正确RTL写法"  │
│  ② RTL 功能仿真                                          │
│    (Icarus 10.3 编译 + testbench 仿真)                  │
└────────────┬────────────────────────────────────────────┘
             │  CreativEval 到此为止
             ▼
   ③ 逻辑综合  ← 唯一能回答 "哪种写法更好" 的阶段
             ▼
   ④ 门级仿真  ⑤ STA  ⑥ 形式验证
             ▼
   ⑦ Floorplan → ⑧ Placement → ⑨ CTS → ⑩ Routing
             ▼
   ⑪ 后仿真 → ⑫ DRC/LVS → ⑬ Signoff → ⑭-⑰ 流片→芯片
```

CreativEval 的输入来自上游人类写的规格和 testbench（通常来自 HDLBits/AutoChip），输出是"哪种 LLM 在给定规格下能产生更多种不同结构的正确 RTL"。它的下游——逻辑综合阶段——才是唯一能判断"创造力"是否转化为了真实硬件价值的阶段。

### 9.2 「结构不同」和「硬件更好」之间隔着什么

CreativEval 的"创造力"回答的是 diversity，不是 quality。以下每一种情形在创造力评分中都得高分，但在综合/物理实现阶段会被否决：

**(a) 冗余逻辑产生"结构不同"的假象**

```verilog
// Golden（相似度接近 1.0）
assign out = a & b;

// 模型生成的"不同"实现（相似度可能远低于 0）
assign tmp1 = a | b;
assign tmp2 = ~(a ^ b);
assign out = tmp1 ^ tmp2;  // 数学等价于 a & b，但多了 3 个门
```

在 GNN4IP 嵌入空间中两者距离可能很大（DFG 节点数和边数完全不同），CreativEval 判定为"高 creativity"。但综合后，下方实现面积约为上方的 4 倍，延迟多出 2 级门。

**(b) 意外 latch 产生"独特"结构**

```verilog
always @(*) begin
  if (en) out = in;  // 缺 else → 综合器推断 latch
end
```

如果 testbench 恰好只测 en=1 的情况，这个实现功能正确且 DFG 结构与 golden 不同（多了 latch 回路），CreativEval 给高分。但在真实流程中，综合阶段直接报 latch inference warning，形式验证阶段报告不等价。

**(c) 不同状态编码被误判为不同架构**

FSM 的 binary / one-hot / Gray 编码在 GNN4IP 嵌入中可能产生不同向量，CreativEval 据此判定为"不同实现"。但实际上它们只是同一状态转移表的不同编码方式，综合后的门级网表可能有相似的 PPA profile——差异在"值"而非"结构"。

**结论**：CreativEval 的"创造力"是一个前端设计空间的 diversity proxy，不是后端物理实现质量的 proxy。要完整回答"哪种 LLM 的设计最好"，必须将 CreativEval 的多样性指标与逻辑综合后的 PPA 报告结合——这正是 ResBench 试图填补的空白。

## 10. 讨论与局限

### 10.1 论文自述的局限

1. **创造力总分不含 functionality**：功能覆盖差的模型仍可能因少数题的多样性获得高 C；建议后续报告无条件创造力或 `Functionality x C`。
2. **条件成功偏差**：F/X/O 只在"至少成功一次"的题上平均，全失败题被排除，可能夸大低覆盖率模型。
3. **单一 golden 相似度代理**：GNN4IP 来自 IP piracy 任务，domain shift 未经验证；低相似度可能来自冗余逻辑、混淆或 parser 差异，而非真正的架构创新。
4. **exact-float 去重**：fluency 用 Python `set` 对浮点相似度去重，缺乏 epsilon 与聚类，可能合并不同实现或拆分相同实现。
5. **参数漂移**：论文写 temperature=0.3，但公开 fluency 脚本多为 0.7；top-k/top-p 在 GPT 脚本中未一致设置。
6. **数据缺口**：当前单模块 golden 仅 110/111；无统一 runner；脚本绑定作者机器绝对路径。
7. **Elaboration 样本过少**：仅 9 题，难以可靠区分模型能力。

### 10.2 代码/复现层面的问题

从本地代码审计发现的关键问题：

- **温度不一致**：论文统一写 temperature=0.3，但公开 GPT-3.5/4 fluency/originality 脚本、CodeLlama fluency/originality 脚本、VeriGen fluency/originality 脚本均为 0.7。temperature 从 0.3 升到 0.7 会显著增加采样多样性，直接用公开脚本跑出的结果与论文 Table I 不可比。
- **GPT API 版本不可冻结**：GPT 脚本使用 `gpt-3.5-turbo` 和 `gpt-4-turbo-preview`，这些 API 端点指向的模型版本随时间演进。今天重调同名 API 不是论文同模型。
- **仓库无统一 Runner**：实验通过 7+ 份独立脚本运行，每份脚本绑定作者机器 `/mnt/shared-scratch` 绝对路径。没有一条命令可从 120 题重建 Table I。
- **GNN4IP 推理未设 eval 模式**：`directPD.py` 直接调用 `trainer.inference_epoch_ip()`，没有设置 `model.eval()` 和 `torch.no_grad()`。配置中 dropout=0.5，在 training mode 下每次推理产生不同的相似度分数。
- **Parser 失败静默排除**：DFG 构建失败被 `except Exception` 静默捕获并跳过。不同模型代码风格导致的 parser 可接受性差异，可能系统性影响创造力样本集合。
- **VeriGen-16B 需 8-bit 量化加载**：因显存限制，16B 模型以量化方式加载，推理结果与全精度可能有差异。
- **保存日志与论文表的数值漂移**：CodeLlama-7B originality 日志重建值 0.3095 vs 论文 0.2926，不一致。六模型 fluency 可从日志完整重建，但部分 functionality/originality 与论文表存在漂移。

### 10.3 本资料包的批判性分析

**"创造力与正确性脱钩"是最根本的隐患**：一个模型可以靠"写出一堆功能正确但故意绕弯（冗余、混淆）的实现"刷高 Originality/Flexibility，而这些在真实流程里是负资产（面积大、可读性差、综合结果更差）。C 更应被理解为"设计多样性的描述性度量"，而非"越高越好的优化目标"。论文的一句话定位也承认这点。

**GNN4IP 的可解释性问题最致命**：余弦相似度 < 0 到底意味着"创新架构"还是"parser 把等价代码解析成了不同图"？没有人工验证，Flexibility=1 的语义是模糊的。更稳妥的做法是"形式等价确认功能相同 + 综合后 PPA 差异衡量结构不同"。

**方法论价值超过具体分数**：即使指标脆弱，CreativEval 提出的问题是真的——功能正确率单一指标正在饱和（VerilogEval 已被 Agent 系统刷到 94%+），下一代评测需要多维度（多样性、资源效率、可综合性、成本）。ResBench 的资源感知、ChipBench 的成本效率，都是"跳出单一 pass@k"的同类努力。

**定位建议**：CreativEval 适合作为功能正确性之外的补充诊断（"这个模型只会背标准答案吗？"），不适合作为独立优化目标。

## 11. 评测公平性与可信度分析

### 11.1 指标设计中的偏差

**(a) 条件成功偏差（Selection Bias）**

Fluency、Flexibility、Originality 三个指标只在"至少有一个功能正确候选"的 $n$ 个 prompt 上计算均值。全失败题从分母中消失，不产生任何惩罚。这意味着：

```text
模型 A：10/111 题成功，每成功题产生 4 种不同实现 → F ≈ 0.4
模型 B：100/111 题成功，每题平均 2 种实现 → F ≈ 0.2
```

CreativEval 判定 A 的 fluency 是 B 的两倍，但 A 在 90% 的题目上完全不会做。这会使功能覆盖率差但在简单题上"耍花样"的模型获得虚高评分。

**(b) 无功能正确性加权**

综合创造力 C 不包含 Functionality 这一维度。即使两个模型的 C 值相同，一个 functionality=0.37（GPT-4，至少成功约 45/120 题）和一个 functionality=0.24（CodeLlama-7B，至少成功约 29/120 题）的"实际设计能力"差距巨大。更合理的做法是报告 $C_{\text{effective}} = \text{Functionality} \times C$。

**(c) Elaboration 样本极小化偏差**

仅 9 题的 elaboration 子集使 E 的有效分辨率为 0.1111（单题步长）。两个模型间需要 2 题以上的差异才能超过 0.22，而所有模型的结果落在 2/9 和 3/9 两档——实际上无法区分任何模型在该维度的能力。

### 11.2 GNN4IP 相似度的可信度

**(a) Domain Shift 未校准**

GNN4IP 的预训练任务是 IP piracy detection：判断两个大规模硬件设计是否来自同一 IP。CreativEval 将其迁移到小型 HDLBits 教学题的结构相似度判断，没有任何 calibrating 实验证明：
- GNN 分数与人工硬件工程师的"新颖性"判断一致
- 负 cosine similarity 必然代表有效的替代架构（而非冗余/混淆）
- 相似度对语义保持变换是单调的（重构不改变分数）
- 相似度不被无关因素（命名、位宽写法、parser 差异）欺骗

**(b) Dropout 未关闭导致推理不确定性**

`directPD.py` 直接调用 `trainer.inference_epoch_ip()`，没有设置 `model.eval()` 和 `torch.no_grad()`。模型配置中 dropout=0.5，默认处于 training mode 时启用 dropout——这意味着对同一对图两次推理可能产生不同相似度分数。虽然 `PairwiseGraphTrainer` 构造时重设了 NumPy/Torch seed，但这仍不是标准 deterministic inference。

**(c) Parser 失败静默排除**

Pyverilog 解析失败、GNN 推理失败的候选被 `except Exception` 静默捕获并跳过，不进入 similarity 计算。不同模型的代码风格导致不同比例的 parser 失败率（VeriGen 的代码可能更易被 Pyverilog 解析，CodeLlama 可能产生更多非标准写法），从而系统性影响进入评分的样本集合——这不是"创造力"差异而是"与 parser 兼容性"差异。

### 11.3 代码与论文的配置漂移

**(a) 温度大面积不一致**

| 脚本类别 | 论文声称 | 当前代码 |
|------|:---:|:---:|
| GPT-3.5 fluency/originality | 0.3 | **0.7** |
| GPT-4 fluency/originality | 0.3 | **0.7** |
| CodeLlama fluency/originality | 0.3 | **0.7** |
| VeriGen fluency/originality | 0.3 | **0.7** |
| GPT flexibility | 0.3 | 0.3 |
| CodeLlama flexibility | 0.3 | **0.7** |
| VeriGen flexibility | 0.3 | **0.7** |

目录名中多处有 `tmp3`、`tmp7`，表明实验曾在温度 0.3/0.7 间切换，但当前代码没有保留一套干净、参数化、与论文一致的 runner。

**(b) top-p/top-k 在 GPT 脚本中缺失**

论文报告 `top_k=10, top_p=0.95`。本地 HuggingFace 脚本确实传这两个参数，但 GPT ChatCompletions 脚本只设置 temperature/max_tokens——OpenAI API 的 Chat Completions 没有 top-k 接口，top-p 脚本中也未传。

**(c) GPT API 端点不可冻结**

GPT 脚本使用 `gpt-3.5-turbo`（静态快照已下线）和 `gpt-4-turbo-preview`（同样已下线）。今天重调同名 API 不是论文同模型，结论的纵向可比性永久受损。

### 11.4 公平性总结

CreativEval 作为首个探索性 benchmark，在问题定义和指标构造上具有创新价值。但其评测的"公平性"受限于：

1. 条件成功偏差使低覆盖率模型不会因"不会做"被扣分
2. GNN 相似度 proxy 未经人工校准，domain shift 可能导致系统性误判
3. 代码与论文参数不一致（温度 0.3 vs 0.7），降低了可复现性
4. Elaboration 样本过小，无法可靠排序
5. GPT API 版本不可冻结，纵向可比性受损

这些限制不妨碍 CreativEval 作为"设计多样性"问题的开题之作的价值，但使用者不应将其 Creativity 排名等同于"模型设计能力强弱"的排名。

## 13. 一分钟复述版

CreativEval（Texas A&M，arXiv 2024）是第一个系统评测 LLM 硬件代码"创造力"的 benchmark 框架。核心贡献三件事：

1. **四维创造力指标**：将认知科学的 fluency/flexibility/originality/elaboration 映射到 RTL 生成场景。Fluency 数"同一规格有多少种正确实现"，Flexibility 看"被给定范例后还能否换写法"，Originality 量"离标准答案多远"，Elaboration 测"能否用小模块拼大模块"。四个指标等权平均得 Creativity，Functionality 单独报告不进入总分。

2. **GNN4IP 图嵌入做结构相似度 proxy**：不用文本 diff 或 AST 距离，而是把 Verilog 转 DFG，经 2 层 GCN + SAGPool 嵌入为 16 维向量，用 cosine similarity 判断两个实现的结构相似度。这比 token 级比较更能捕捉"功能等价但结构不同"的差异。

3. **六模型横向对比**：CodeLlama-7B/13B、VeriGen-6B/16B、GPT-3.5/4 在 120 道 HDLBits 题目上评测。结果：GPT-3.5 创造力总分最高（0.2201，Flexibility 0.1600 碾压式领先），GPT-4 功能正确性最强（0.3750 pass@10），CodeLlama-13B originality 最高（0.3021）。

**边界与问题**：只覆盖流程阶段 ①②（2/17），不评估 PPA/可综合性；功能正确性不进入创造力总分，全失败题从 F/X/O 分母消失（条件成功偏差）；GNN4IP 的 domain shift 未校准，similarity 的"创新 vs 冗余"区分能力未知；elaboration 仅 9 题区分度不足；公开脚本温度 0.7 vs 论文 0.3 存在配置漂移；仓库无统一 runner 不能一键重建 Table I。最适合与 ResBench 组合使用——CreativEval 回答"是否不同"，ResBench 回答"不同是否带来资源价值"。
