# CraftRTL 论文深度讲解

> **CraftRTL: High-Quality Synthetic Data Generation for Verilog Code Models with Correct-by-Construction Non-Textual Representations and Targeted Code Repair**
> Mingjie Liu, Yun-Da Tsai, Wenfei Zhou, Haoxing Ren
> NVIDIA Corporation
> ICLR 2025 · arXiv:2409.12993v2 (6 Feb 2025)
> 代码：https://github.com/NVlabs/CraftRTL
> 原文：[2409.12993_CraftRTL.pdf](./2409.12993_CraftRTL.pdf)

---

## 1. 一句话定位

**CraftRTL 是 NVIDIA 提出的「Verilog 代码 LLM 微调数据治理」框架：在 80K LLM 合成的 Self-Instruct / OSS-Instruct / Docu-Instruct / Non-textual 基础数据之上，叠加 28.5K 的「Correct-by-Construction」合成数据（针对 Karnaugh Maps、FSM、Waveforms 三种非文本表示，用算法+模板机械生成正确解）和 1.4K 的「Targeted Code Repair」修复数据（用 LLM 从 checkpoint 差异生成错误报告、验证后再注入开源代码），最终在 Starcoder2-15B / DeepSeek-Coder-6.7B / CodeLlama-7B 三个 base 上微调，pass@1 在 VerilogEval-Machine / VerilogEval-Human / RTLLM v1.1 三个基准上比之前 SOTA 分别提升 +3.8 pp（vs CodeV CodeLlama 78.1）、+10.9 pp（vs GPT-4o 57.1）、+6.6 pp（vs CodeV DeepSeek-Coder 42.4）；且修复数据显著降低了"训练后期 pass rate 退化"的训练不稳定性（Pearson 相关系数从 0.638 升到 0.782）。**

这句话里的 7 个技术承重点：

1. **「正确即构造」（Correct-by-Construction, CC）** — 不依赖 LLM 来生成代码正确性，而是用算法（随机采样 minterms + don't-care → SOP → Verilog；随机生成状态转移图 → FSM code；编译后仿真 → VCD → 波形表）机械生成 100% 正确的 problem-solution 对。KMap 12.5K、FSM 8.0K、Waveforms 8.0K 共 28.5K。
2. **针对非文本表示的「直接对齐」** — VerilogEval-Human 的 45 个非文本题目（占 Human 集 ~30%）用 KMap / FSM / Waveform 三种表示，论文发现 Starcoder2-15B 在这类题目 pass@1 仅 10.3%，GPT-4o 也只有 27.0%。CC 数据直接补齐这块空白。
3. **Targeted Code Repair 数据（CR）** — 收集 847 份「LLM 生成的错误报告」（从 benchmark 题目 + checkpoint 差异分析），注入开源代码片段生成 2736 修复样本，过滤后保留 1406 条。让模型学会"避免常见错误模式"。
4. **Self-Consistency Check 两阶段验证** — 阶段一：让 LLM 仅凭错误报告去修复错误代码，能修 → 报告有效。阶段二：直接 prompt LLM 修同样的错误，13% 才能修——证明"高质量错误报告"是关键。Self-Consistency 是"质量保证"的护栏。
5. **三种 LLM base × 三种数据组合的 ablation** — 在 Starcoder2-15B / DeepSeek-6.7B / CodeLlama-7B 上分别测 SDG / SDG-CC / SDG-CC-Repair 三种数据 blend。CraftRTL 显著优于 SDG-only 和 SDG-CC。
6. **SDG 数据的训练不稳定性问题** — 论文 Figure 1a 揭示：训练后期 ~15% 题目在两个 checkpoint 之间出现显著 pass rate 退化（同时也有 ~15% 改善）。Figure 1b 加入 Repair 数据后这种波动被显著压制，Pearson 相关 0.638 → 0.782。
7. **VerilogEval-NonText benchmark 贡献** — 从 VerilogEval-Human 抽出 45 个含 KMap / FSM / waveform 的题目，命名为 VerilogEval-NonText，作为社区评估 LLM 在非文本表示上能力的子基准。

**覆盖率：1/17 核心 + 1/17 验证手段。** CraftRTL 聚焦在 **RTL 设计阶段（①）的 LLM 微调数据治理**，仅用 RTL 功能仿真（②）作为数据验证手段。它不涉及任何后端物理、综合优化。

> ⚠️ **本论文最容易被误读的两个边界**：
> 1. **"High-quality synthetic data" ≠ "Real Verilog code"**：CraftRTL 生成的训练数据是 (problem-description, verilog-code) 对，用于训练 LLM，不是生成可流片的 RTL。生成的 Verilog 代码确实能在 Icarus Verilog 上仿真通过，但远不是工业级 RTL。
> 2. **"Correct-by-Construction" 的边界**：CC 数据仅覆盖 KMap / FSM / Waveform 三类非文本表示 + 小规模组合 / 时序电路（变量数 ≤ 4，状态数 4/6/10，输入位宽 1/2）。工业 RTL（多周期 FSM、复杂流水线、多端口 SRAM 控制器）不在 CC 数据覆盖范围。

## 3. 输入 / 输出

### 3.1 输入

**(a) Base LLM**

论文微调了三个 base LLM：

| Base LLM | 参数量 | 上下文长度 | 来源 |
|----------|:---:|:---:|------|
| Starcoder2-15B | 15B | 16K | BigCode (Lozhkov et al., 2024) |
| DeepSeek-Coder-6.7B-Instruct | 6.7B | 16K | DeepSeek-AI (Guo et al., 2024) |
| CodeLlama-7B-Instruct | 7B | 16K | Meta (Roziere et al., 2023) |

**(b) Verilog 种子语料**

- **Self-Instruct 种子**：50 道随机生成的 Verilog 题（无 in-context example）
- **OSS-Instruct 种子**：The Stack v2 中的 Verilog / SystemVerilog 代码（经 Pyverilog 语法检查 + self-contained 筛选）
- **Docu-Instruct 种子**：~100 本硬件教材 + 过滤后的 Wikipedia 硬件条目
- **Non-textual 种子**：从 The Stack 抽取的 Verilog 代码 + 鼓励 LLM 引入 KMap / FSM / waveform

**(c) Benchmark 题库（用于生成 Repair 数据 + 评估）**

- VerilogEval-Machine：GPT-3.5 生成描述
- VerilogEval-Human：HDLBits 人工转述（156 题）
- VerilogEval-NonText：VerilogEval-Human 的 45 题子集（含 KMap/FSM/waveform）
- RTLLM v1.1：~50 个设计规格（含 adder_8bit、multi_booth_8bit 等）

**(d) Nemotron-4-340B-Instruct（数据生成的 teacher LLM）**

- 用于生成 Self-Instruct / Docu-Instruct / Non-textual 数据
- 用于生成错误报告 + 注入错误到开源代码

### 3.2 中间产物

**(a) 110K 微调样本（按类型分）**

| 类型 | 来源 | 数量 | 生成方式 |
|------|------|:---:|------|
| Self-Instruct (SDG) | Nemotron-4-340B 从 50 道种子题扩展 | 24.7K | LLM prompt + 语法检查 + self-verification |

每个样本包含：(a) problem description（自然语言）、(b) erroneous implementation（注入错误后的代码）、(c) hints for fixing、(d) correct code（修复后）。

### 3.3 输出

**(a) 微调后的 Verilog LLM**

- 输入：problem description（含 KMap / FSM / waveform 等非文本表示）
- 输出：完整的 Verilog `module` 代码（可被 Icarus Verilog 编译 + 通过 testbench）

```verilog

// ab   0   1
// 00 | 1 | 0
// 01 | 0 | 0
// 11 | 0 | 0
// 10 | 0 | 0
// module top_module(
//     input a, b, c,
//     output out
// );

// 模型输出（correct by construction）：
module top_module(
    input a, b, c,
    output out

    assign out = (~a & ~b & ~c);
```

### 4.2 模块 1：Synthetic Data Generation（SDG，80.1K）

#### 4.2.1 Self-Instruct（24.7K）

参考 Wang et al. (2022) 的做法：随机从 LLM 生成 50 道 Verilog 题，从中随机选 1-5 道作为 in-context example，生成新题。

```text
Prompt template:
[1-5 道种子题]
Generate a new Verilog coding problem that is similar to the above examples 
but covers different scenarios...
```

#### 4.2.2 OSS-Instruct（28.4K）

参考 Wei et al. (2023) 的做法：从 The Stack v2 抽取 Verilog/SystemVerilog，用 Pyverilog 做语法检查 + self-contained 筛选，再用 LLM 把代码改写为 (problem, solution)。

```text
Prompt template:
[Verilog 代码片段]
Generate a coding problem that would produce this code as its solution...
```

#### 4.2.3 Docu-Instruct（12.0K）

从 Wikipedia 过滤硬件相关条目 + 100 本教材，分段（<2K tokens/段），prompt LLM 生成 coding problem。

#### 4.2.4 Non-textual（15.0K）

鼓励 LLM 在生成 problem 时引入 KMap / FSM / waveform 三种非文本表示。

```text
Prompt template (Non-textual):
Generate a Verilog coding problem that includes a Karnaugh map / state-
transition diagram / waveform representation...
```

#### 4.2.5 SDG 的关键问题

论文 Figure 1a 揭示 SDG 数据的核心问题：**pass rate 在训练后期显著退化**。

```text
训练 Step 256 → Step 320（最后 64 步）：
  · ~15% 题目 pass rate 显著退化
  · ~15% 题目 pass rate 显著改善
  · Pearson 相关系数仅 0.638
```

### 4.3 模块 2：Correct-by-Construction（CC，28.5K）

#### 4.3.1 Karnaugh Maps and Truth Tables（12.5K）

**算法**：

```text
1. 随机选变量数 n ∈ {3, 4}
2. 随机选 valid minterms + don't-cares（每个位置 ∈ {0, 1, x}）
3. 从 minterms 推导 SOP（sum-of-products）
4. 根据选定的 minterms/don't-cares 生成 Truth Table 和 Karnaugh Map
   · 默认 Gray 编码
   · 随机 transpose 或 swap 相邻 row/column
5. 模板化生成 (problem with KMap, Verilog code) 对
```

**示例（Figure 8）**：

```
Problem: Implement the circuit described by the Karnaugh map below.
//     c
// ab   0       1
// 00 | 1   |   0
// 01 | 0   |   0
// 11 | 0   |   0
// 10 | 0   |   0
module top_module(input a, b, c, output out);

Solution: assign out = (~a & ~b & ~c);
```

**为什么 correct-by-construction**：所有步骤（minterms → SOP → assign）是机械确定性的，没有 LLM 参与 hallucination。

#### 4.3.2 State Transition Graphs and Tables（8.0K）

**算法**（Algorithm 1，Moore FSM）：

```text
Input: number of states n, input bit width w
Output: FSM graph with transitions and states

1. Initialize n states and w-bit input
2. Randomly generate a tree with n nodes (确保 reachability)
3. Define root of the tree as the reset state
4. For each node in tree:
     Assign a unique state encoding
     Assign an output to the node (Moore)
5. For each node in tree:
     Add additional transition edges to form a graph
     Ensure each node has out-degree = 2^w
6. Generate Verilog:
     case(state)
       A: next_state = in ? C : D;
       ...
     endcase
```

**两种 Verilog 编码策略**（Figure 2）：
- **Out-edge focused**（default）：用 `case(state)` 列举每个状态的输出转移
- **In-edge focused**：用 `next_state[B] = (state[A] & in) | (state[C] & ~in)`，对 one-hot 编码友好

**Mealy FSM**：把 output 放到 edge 而非 state（简单修改算法即可）。

#### 4.3.3 Waveforms（8.0K）

**算法**：

```text
1. 用上述 KMap / FSM 模板生成 (problem, Verilog code) 对
2. 跑 Icarus Verilog 仿真生成 VCD
3. 解析 VCD → 时间序列
4. 表格化 (signal, time) → value
5. 输出：波形表作为 problem + code 作为 solution
```

**覆盖范围**：KMap（组合电路）+ FSM（时序电路）→ 两类波形。

#### 4.3.4 CC 的 critical design choices

| 选择 | 论文的取舍 | 理由 |
|------|-----------|------|
| 变量数 | $n \in \{3, 4\}$ | 与 VerilogEval-NonText 题目分布一致 |
| 状态数 | 4 / 6 / 10 | 与 VerilogEval-Human 分布一致 |
| 输入位宽 | 1 / 2 bit | 与 FSM 题目分布一致 |
| Gray 编码 | 默认 | KMap 相邻 cell 仅 1 bit 变化 |
| 训练 / 测试去污染 | 严格 | 11 个 VerilogEval-NonText 模板被排除 |

### 4.4 模块 3：Targeted Code Repair（CR，1.4K）

#### 4.4.1 错误报告生成

```text
输入：
  [PROBLEM] VerilogEval 某题的 problem description
  [ERROR CODE] 训练 checkpoint 中 LLM 生成的错误代码
  [CORRECT CODE] 该题的标准答案

Prompt:
  Now, generate a detailed error report.

输出 (Error Report):
  Error Type: Incorrect vector concatenation and splitting
  Category: Combinatorial: wiring
  Description: the output vectors are assigned in the wrong order...
  Steps to Repair:
    1. Concatenating the two 1 bits at the beginning...
    2. Assign the output vectors in the correct order and bit ranges...
```

论文生成了 847 份错误报告。

#### 4.4.2 错误类型分布（Table 15）

| 错误类型 | 占比 | 描述 |
|---------|:---:|------|
| Vector Concatenation | 15.3% | 向量拼接或位切片错误 |
| Incorrect Initialization | 13.1% | 寄存器 / 信号初始化遗漏或错误 |
| Boolean Logic Flaws | 12.4% | 组合逻辑表达式错误 |
| Shift Operation Faults | 10.2% | 移位操作未对齐或行为错误 |
| Timing Violations | 10.2% | 时序违例（race condition） |
| KMap Misinterpretation | 8.8% | KMap 推导 Boolean 表达式错误 |
| Latch Hazards | 6.5% | 缺少条件导致 latch |
| Bit Manipulation Bugs | 7.3% | masking / flipping / extracting 位错误 |
| Casez Priority Conflicts | 4.4% | casez / case 优先级冲突 |
| Nested Loop Design Flaws | 3.7% | 嵌套循环设计错误 |
| Others | 8.1% | 其他 |

#### 4.4.3 Repair 数据生成

```text
输入：
  [ERROR REPORT] (一份错误报告)
  [CODE SNIPPET] (从开源代码抽取的 Verilog 片段)

Prompt:
  Inject the commonly made error into the above Verilog module and create 
  an error-fixing practice problem.

输出 (Repair Sample):
  · Problem description (自然语言)
  · Erroneous implementation (注入错误后的代码)
  · Hints for fixing
  · Correct code solution
```

论文生成 2736 条，过滤后保留 1406 条。

#### 4.4.4 两阶段验证（Self-Consistency Check）

```text
阶段 1：报告质量验证
  · 输入：错误代码 + 错误报告
  · 让 LLM 尝试仅凭错误报告修复代码
  · 能修复 → 报告有效
  · 直接 prompt LLM 修复同样的错误，仅 13% 能修
  → 高质量错误报告是关键

阶段 2：数据集去污染
  · Deduplication
  · 语法过滤
  · Benchmark 去污染（防止泄漏到评估集）
```

## 5. 关键公式

### 5.1 Pass@k 指标

Codex / Chen et al. (2021) 提出的无偏 pass@k 估计器：

$$
\text{pass@k} = \mathbb{E}_{\text{Problems}} \left[ 1 - \frac{\binom{n - c}{k}}{\binom{n}{k}} \right]
$$

- $n$：每个问题的总采样次数（论文 $n = 20$）
- $c$：通过的次数
- $k$：评估的 $k$ 值
- $\binom{\cdot}{\cdot}$：二项式系数

**直觉**：分子 $\binom{n-c}{k}$ 是从 $n-c$ 个错误样本中选 $k$ 个的方案数；分母 $\binom{n}{k}$ 是从所有 $n$ 个中选 $k$ 个。1 - 这个比例 = 至少有一个样本通过的估计概率。

### 5.2 训练损失

标准的 cross-entropy loss，mask 掉 prompt tokens：

$$
\mathcal{L} = - \frac{1}{N_{\text{resp}}} \sum_{i=1}^{N_{\text{resp}}} \log p_\theta(y_i | y_{<i}, x)
$$

- $x$：prompt tokens（mask）
- $y_i$：response tokens
- $N_{\text{resp}}$：response token 数
- $p_\theta$：模型预测概率

### 5.3 数据混合效果（隐式）

虽然论文没有显式给出 "data blend" 的损失公式，但 ablation 实验展示了：

$$
\text{pass@k}_{\text{final}} = f(\text{SDG}, \text{CC}, \text{Repair}, \text{base LLM})
$$

其中 $f$ 由 SFT + 推理 pipeline 实现。论文通过 4 个数据 blend（Starcoder2-15B / DeepSeek-Coder-6.7B / CodeLlama-7B base × SDG / SDG-CC / SDG-CC-Repair blend）展示：

| 数据 blend | Starcoder2-15B Human | DeepSeek-6.7B Human | CodeLlama-7B Human |
|------------|:---:|:---:|:---:|
| SDG (80.1K) | 54.7% | ~52% | ~45% |
| SDG-CC (108.6K) | 62.0% | ~58% | ~55% |
| **SDG-CC-Repair (110K)** | **68.0%** | **65.4%** | **63.1%** |

### 5.4 训练不稳定性度量

Figure 1 用两个 checkpoint 之间 pass rate 的 Pearson 相关系数衡量稳定性：

$$
\rho_{\text{ckpt1}, \text{ckpt2}} = \frac{\text{Cov}(r_{\text{ckpt1}}, r_{\text{ckpt2}})}{\sigma_{r_{\text{ckpt1}}} \cdot \sigma_{r_{\text{ckpt2}}}}
$$

- SDG：$\rho = 0.638$
- SDG-CC-Repair：$\rho = 0.782$

Pearson 越高，两个 checkpoint pass rate 越一致 → 训练越稳定。

### 5.5 Pass rate 变异性分析

对每个问题 $p$，定义 pass rate 在两个 checkpoint 的差异：

$$
\Delta_p = r_p^{\text{ckpt2}} - r_p^{\text{ckpt1}}
$$

论文把题目分为：
- Solvable：$r_p^{\text{ckpt1}} > 0.67$ 且 $r_p^{\text{ckpt2}} > 0.67$
- Unsolvable：$r_p^{\text{ckpt1}} < 0.33$ 且 $r_p^{\text{ckpt2}} < 0.33$
- 其他：可变（volatile）

SDG 数据下 ~15% 题目从 solvable 退化成 volatile；SDG-CC-Repair 数据下这个比例显著降低。

## 6. 训练与实验设置

### 6.1 是否需要训练

**需要训练**：Base LLM 微调（Starcoder2-15B / DeepSeek-Coder-6.7B / CodeLlama-7B）

**不训练**：所有数据生成 pipeline（CC 算法、SDG prompts、Repair generation 都用预训练 LLM 调用 + 算法）

### 6.2 训练设置

- 硬件：32× NVIDIA A100-80GB，DDP
- 优化器：Adam（Kingma & Ba, 2017）
- 学习率：CodeLlama-7B / DeepSeek-Coder-6.7B 用 5e-5；Starcoder2-15B 用 1e-5
- Batch size：256 samples
- 序列长度：截断到 4096 tokens
- Epochs：1（论文发现再多训没帮助）
- Loss：cross-entropy，仅在 response tokens 上计算，prompt tokens 被 mask

### 6.3 推理设置

- 推理引擎：vLLM（Kwon et al., 2023）
- Dtype：bf16
- Tensor parallel size：8
- Max tokens：4096
- 每个问题采样 20 次
- 报告 temperature 0.2 和 0.8 中最好的结果（与 Liu et al. 2023c, Zhao et al. 2024 一致）

## 7. 创新点

### 7.1 Correct-by-Construction 数据生成

**贡献**：用算法 + 模板机械生成 KMap（12.5K）、FSM（8.0K）、Waveform（8.0K）三种非文本表示的 problem-solution 对，**100% 保证 solution 正确**，无需 LLM 验证。

**为什么重要**：传统 SDG 数据依赖 LLM 生成 solution，然后用 testbench 验证。但 (a) testbench 本身可能有错，(b) Verilog 验证远比 Python 复杂（需要 testbench + 仿真器）。CC 完全绕过这个瓶颈——solution 是机械生成的，"正确"是构造性证明的。

### 7.2 揭示并解决 SDG 数据的训练不稳定性

**贡献**：Figure 1a 量化展示了 SDG 数据的"pass rate 退化"问题（Pearson 0.638），并提出"Targeted Repair"作为系统化解决方案（Pearson 0.782）。

**对比之前的认知**：之前的 Verilog LLM 工作普遍报告最终 checkpoint 的 pass@k，对训练过程中的 pass rate 波动要么没观察到要么忽略。CraftRTL 把这个现象第一次明确定量展示。

### 7.3 Targeted Code Repair 数据生成

**贡献**：用 LLM 生成错误报告 + 注入开源代码 + 两阶段验证，构造 (problem, error code, hint, fix) 形式的训练数据。让模型学会"避免 LLM 自身最常犯的错误"。

**对比传统 RLHF**：RLHF 需要 reward model + PPO/DPO，复杂且不稳定；Repair 数据是 supervised fine-tuning，简单且有效。

### 7.4 VerilogEval-NonText 子基准

**贡献**：从 VerilogEval-Human 抽出 45 道非文本题目建立子基准，专门评估 LLM 处理 KMap / FSM / waveform 的能力。

**意义**：之前评测 LLM 在 KMap/FSM 上的能力只能"看 VerilogEval-Human 整体 pass rate"，无法隔离非文本表示的贡献。VerilogEval-NonText 把这个维度显式化。

### 7.5 跨 base LLM × 跨数据 blend 的系统 ablation

**贡献**：在 Starcoder2-15B 上做了完整的 SDG / SDG-CC / SDG-CC-Repair 四配置 ablation（Table 6），并在 DeepSeek-Coder-6.7B 和 CodeLlama-7B 上用 SDG-CC-Repair 验证了跨模型泛化性，证明三种数据 blend 的递进收益。

**意义**：证明了 "CC + Repair 不是某个 base 的偶然偏好"——而是跨 base 稳健有效。

## 9. 与芯片流程关系

### 9.1 在 EDA 流程中的位置

CraftRTL 是 **RTL 设计阶段（①）的 LLM 微调数据治理**——它不生成可直接流片的 RTL，也不做综合优化。它的目标是让 LLM 在被问到 "implement a Verilog module for ..." 时能给出更高质量的 Verilog 代码：

```text
传统 LLM-for-RTL：
spec → LLM(SFT on bad data) → Verilog（语法正确但容易出 minor 错误）

CraftRTL 介入点：
spec → LLM(SFT on 110K curated data) → Verilog（更鲁棒、更少错误）
       ↑
       CC 数据修复非文本表示盲点
       Repair 数据修复 LLM 自身常见错误
```

下游任务（VerilogEval、RTLLM 的 pass@k 评估）是衡量 LLM 写 Verilog 能力的指标。

### 9.2 "能仿真通过"和"能做芯片"之间隔着什么

CraftRTL 生成的 Verilog 代码确实能在 Icarus Verilog 上通过 testbench——这是"RTL 功能仿真（②）"级别的验证。但一个真实可制造的芯片还需要：

1. **可综合到门级 netlist** — CraftRTL 不验证。论文 Verilog 代码在语法上是可综合的（用 assign / always），但没跑过 DC 综合。
2. **满足时序** — 不涉及。CraftRTL 完全在 RTL 文本层面，不关心综合后的 timing。
3. **可布局布线** — 不涉及。
4. **DRC / LVS clean** — 不涉及。
5. **签核 (sign-off)** — 不涉及。

> **本资料包的提示**：CraftRTL 的"成功"是 **LLM 微调效果** 意义上的成功（pass@k 提升），而不是"生成可流片芯片"。论文自己也没声称这个——它明确说自己做的是 "Verilog code models"。

## 10. 讨论与局限

### 10.1 论文自述局限

#### 局限 1：CC 数据的覆盖范围有限

CC 数据只覆盖 KMap（$n \in \{3, 4\}$）、FSM（4/6/10 states, 1/2-bit input）、Waveform。工业 RTL 的常见模式（多周期 FSM、复杂流水线、SRAM 控制器、AMBA 总线协议）都不在 CC 覆盖范围。

#### 局限 2：Non-textual 数据的多样性

虽然 CC 让 KMap / FSM pass@1 接近 100%，但多样性下降（Table 14 显示 TSED 等多样性指标变差）。模型可能"过拟合"到 CC 模板的具体写法。

#### 局限 3：评估方法对 VerilogEval 的依赖

论文主要用 Icarus Verilog（开源）评估，而之前的工作用 Synopsys VCS（商业），两者支持的语法不完全一致。这可能导致论文报告的 pass@k 与之前报告的数字不能直接比较。

#### 局限 4：真实工业数据的缺失

整个 110K 训练集都是 LLM 生成的（SDG）或算法生成的（CC）或注入的（Repair），没有真实工业 RTL 代码。论文承认这是个局限——但同时这也是论文的贡献（解决数据稀缺问题）。

#### 局限 5：错误报告的覆盖率

847 份错误报告是手工 / LLM 生成 + 过滤得到的，不能保证覆盖所有可能的 Verilog 错误模式。

### 10.2 代码/复现层面

#### 复现门槛

1. **Base LLM**：Starcoder2-15B / DeepSeek-Coder-6.7B / CodeLlama-7B 需自备（公开下载）
2. **SDG 生成**：需要 Nemotron-4-340B-Instruct 的 API 或本地部署（论文用 NVIDIA 的商业模型）
3. **CC 生成**：纯算法（KMap、FSM），无额外门槛
4. **Repair 生成**：需要 Nemotron-4-340B + 2-phase validation
5. **训练硬件**：32× A100-80GB（论文配置）；单卡不可行
6. **评估硬件**：vLLM tensor parallel size 8（8× A100）

#### 已知差异

- **Icarus Verilog vs Synopsys VCS**：RTLLM 上 Icarus 评估分数可能略低
- **Nemotron-4-340B 版本**：训练用 340B 模型的版本可能随时间变化，导致 SDG 数据有波动
- **去污染的精确性**：论文说做了 benchmark decontamination，但完全去污染很难

### 10.3 本资料包的批判性分析

#### 批判 1：CC 数据的"过拟合"风险

Table 14 显示非文本表示题目上微调模型多样性下降（BLEU、Jaccard、TSED 都有降低）。这意味着模型可能"记住"了 CC 数据的特定模板。论文没深入讨论这个现象，但作者承认 "code diversity 下降是 expected"。

#### 批判 2：Repair 数据的"修复模式有限"

Repair 数据集只覆盖 10 大类错误（Vector Concatenation 15.3% 等）。LLM 可能犯的其他错误（如 off-by-one、edge case、状态编码不一致）不在覆盖范围。这可能解释了为什么 RTLLM 上 Functional pass@1 提升相对较小（49-53%）——RTLLM 设计更复杂，错误类型更多。

#### 批判 3：Temperature 的双 temperature 选择

论文报告 temperature 0.2 和 0.8 中最好的结果。这有点像 "test set tuning"——选择最好的 temperature 报告可能高估真实能力。标准的做法应该是报告一个固定 temperature 的结果，或报告两个 temperature 的平均值。

#### 批判 4：跨 base LLM 的稳定性问题

Table 4 显示 Starcoder2-15B 在 Machine 上 81.9%，但在 RTLLM Functional 上只 49.0%；DeepSeek-Coder-6.7B 在 Human 上 65.4%，但在 RTLLM Functional 上 53.1%。说明**没有一个 base + 数据组合在所有 benchmark 上都最优**。CraftRTL 的"胜出"依赖于选择合适的 base。

#### 批判 5：与 SynC-LLM 的真正区别

SynC-LLM 和 CraftRTL 都在 EMNLP/ICLR 同期做 LLM-for-RTL 数据生成，但**目标完全不同**：
- SynC-LLM：生成新 RTL 设计（数据增强下游 PPA 预测）
- CraftRTL：生成 (problem, solution) 对（提升 LLM 微调效果）

两者可以互补——SynC-LLM 生成的电路可以做 CraftRTL 的训练数据，让 LLM 学"如何写出 SynC-LLM 风格的大电路"。

#### 批判 6："RTLLM Functional 49.0%" 的解读

Starcoder2-15B + CraftRTL 在 RTLLM Functional pass@1 = 49.0%（vs CodeV 39.4%，+9.6 pp）。但 RTLLM 的设计规模比 VerilogEval 大（更接近真实工业），pass@1 49% 仍意味着 ~51% 的设计完全错误。离"工业可用"还差很远。

## 12. 一分钟复述版

1. **核心问题**：LLM-for-Verilog 微调受限于 SDG 数据质量差（hallucination、testbench 难验证）+ 训练后期 pass rate 退化（Pearson 0.638）。
2. **方法概述**：CraftRTL = SDG（80.1K Self-Instruct + OSS + Docu + Non-textual）+ CC（28.5K 算法生成 KMap / FSM / Waveform）+ Repair（1.4K LLM 错误报告 + 注入开源代码）。三个数据流合并 110K 微调数据。
3. **核心数据**：Starcoder2-15B base，在 VerilogEval-Machine / Human / RTLLM v1.1 上 pass@1 比之前 SOTA（CodeV CodeQwen 7B）提升 +3.8% / +10.9% / +6.6%；Human 上 68.0% 首次超过 GPT-4o（57.1%）。
4. **关键结果**：CC 数据让 KMap pass@1 从 ~10% 提到 98.6%；Repair 数据让训练后期 Pearson 相关从 0.638 升到 0.782；错误报告的 2-phase validation 比直接注入错误更稳健。
5. **最大创新点**：(a) Correct-by-Construction 用算法绕过 LLM hallucination、(b) Targeted Repair 让 LLM "自我纠错"、(c) VerilogEval-NonText 子基准。
6. **EDA 流程位置**：RTL 设计阶段（①）的 LLM 微调数据治理；只做 RTL 功能仿真（②）级别的验证，不涉及综合 / STA / 后端。
7. **与同类工作的关系**：与 [RTLCoder](../RTLCoder/)、[BetterV](../BetterV/)、[CodeV](../CodeV/)、[OriGen](../OriGen/) 同问题域（LLM-for-RTL 微调），CraftRTL 是新一代 SOTA；与 [SynC-LLM](../SynC-LLM/) 互补（SynC-LLM 生成新设计，CraftRTL 提升 LLM 写设计的能力）。
8. **局限**：CC 仅覆盖简单 KMap / FSM / Waveform；Repair 仅覆盖 10 类错误模式；RTLLM Functional 仍只有 ~50%；依赖 NVIDIA 商业 Nemotron-4-340B。

## 附录 A：CraftRTL 与 [SynC-LLM](../SynC-LLM/论文深度讲解.md) 的对比

虽然 CraftRTL 和 SynC-LLM 都在 EMNLP/ICLR 同期、都做"LLM-for-RTL 合成数据"，但目标完全不同：

| 维度 | CraftRTL | SynC-LLM |
|------|----------|----------|
| 目标产物 | 训练样本 (problem, solution) | 新的 Verilog 设计 |
| 规模 | 110K 个 (problem, solution) 对 | 25 个完整设计 |
| 生成方法 | SDG + Correct-by-Construction + Repair | 骨架图扩散 + 检索增强 LLM |
| LLM 角色 | 既是数据源（80K SDG），又是被训练对象（Starcoder2-15B） | 生成器（API 调用） |
| 解决的问题 | LLM 微调数据质量差 + 训练不稳定 | 真实 RTL 数据稀缺 |
| 评估方式 | VerilogEval / RTLLM pass@1 提升 | 下游 PPA 预测 R→1 提升 |
| 关键技巧 | Correct-by-Construction（KMap/FSM/Waveform）、Targeted Repair | Skeleton + Flesh 分解、Layer-by-Layer Prompt |
| 与下游 EDA 工具的关系 | 仅用 Icarus Verilog 仿真，不跑综合 | 生成的代码走 DC / Innovus 验证 |
| 阶段定位 | EDA 流程外（LLM 训练方法） | EDA 流程上游（数据源） |

两者都属于"AI4EDA 中的合成数据"大方向，但研究问题不同：CraftRTL 解决"有数据但数据质量差 + LLM 学不好"，SynC-LLM 解决"没数据"。
