> **AutoVCoder: A Systematic Framework for Automated Verilog Code Generation using LLMs**
> Mingzhe Gao, Jieru Zhao*, Zhe Lin*, Wenchao Ding, Xiaofeng Hou, Yu Feng, Chao Li, Minyi Guo（* 通讯作者）
> 上海交通大学 · 中山大学 · 复旦大学 · IEEE ICCD 2024
> arXiv: 2407.18333v1（2024-07-21）· 原文：[2407.18333_AutoVCoder.pdf](./2407.18333_AutoVCoder.pdf)
> 代码：https://github.com/sjtu-zhao-lab/AutoVCoder（MIT License，本地 commit `7cbf320d68e6`）

## 1. 一句话定位

**AutoVCoder 不发明新模型架构，它把 7B 代码 LLM 的真实 Verilog 分布学习、规格到代码的任务对齐、以及领域知识检索拆成三个独立管线——先用轻量 code scorer 从百万 GitHub 模块中筛出约 168k "教育价值高"的真实 RTL 做第一轮 LoRA 继续训练，再用 ChatGPT-3.5 合成且经语法/功能双重校验的 problem-code 对做第二轮 LoRA 指令微调，最后在推理时通过 example retriever（top-2 相似 RTL 示例）和 knowledge retriever（top-3 硬件知识片段）构建 RAG prompt，让 7B 模型在 VerilogEval-Machine pass@5 上以 79.9% 超过 GPT-4（70.6%）。**

这句话里四个技术承重点：

1. **code scorer 过滤** -- 不是人工挑数据，而是用 15k ChatGPT-3.5 标注训练轻量 MLP 外推到百万样本，阈值 6.5 保留约 21.7%
2. **两轮 LoRA 分工** -- 第一轮学"Verilog 长什么样"（真实代码分布），第二轮学"规格怎么变成 Verilog"（任务映射），串联优于单独任一轮
3. **双路 RAG** -- example retriever 回答"类似模块怎么实现"，knowledge retriever 回答"这个硬件概念是什么"，信息源分离构建与训练
4. **基于执行反馈的 retriever 训练** -- 不是用文本相似度，而是用"加了这篇文档后生成代码的 F(V) 是否提升"来定义正负样本对

## 2. EDA 阶段映射（①-⑰）

这节回答一个问题：AutoVCoder 到底管芯片设计的哪一段，不管哪一段。

参照 [芯片流程.md](../芯片流程.md) 的 17 阶段标准编号：

| 阶段 | 覆盖 | AutoVCoder 做了什么 / 为什么没做 |
|------|:---:|----------------------------------|
| **① RTL 设计** | ✅ **核心** | 两轮 LoRA 微调的 7B 代码 LLM，从自然语言规格 + RAG 检索结果生成完整 Verilog module |
| **② RTL 功能仿真** | ✅ **核心** | Icarus Verilog 编译 + testbench 仿真。在训练阶段（code filter）和评测阶段（VerilogEval/RTLLM 判分）均使用 |
| ③ 逻辑综合 | ❌ | 不做任何综合。生成的代码"语法+功能双通过"不等于"可综合" -- 没有检查 latch 推断、组合环、不可综合结构（initial 块等） |
| ④ 门级仿真 | ❌ | 无 SDF 反标，无门延迟信息 |
| ⑤ STA（Static Timing Analysis，静态时序分析） | ❌ | 不计算任何路径延迟 |
| ⑥ 形式验证 | ❌ | 不做 SAT/SMT 等价性证明。论文未提及形式方法 |
| ⑦ 布局规划 Floorplan | ❌ | -- |
| ⑧ 标准单元摆放 Placement | ❌ | -- |
| ⑨ CTS（Clock Tree Synthesis，时钟树综合） | ❌ | -- |
| ⑩ 布线 Routing | ❌ | -- |
| ⑪ 后仿真 | ❌ | 无 SPEF 寄生参数信息 |
| ⑫ DRC（Design Rule Check，设计规则检查）/LVS（Layout Versus Schematic，版图与原理图一致性） | ❌ | -- |
| ⑬ 签核 Signoff | ❌ | -- |
| ⑭ 流片 | ❌ | -- |
| ⑮ 制造 | ❌ | -- |
| ⑯ 封装 + 测试 | ❌ | -- |
| ⑰ 芯片 | ❌ | -- |

**覆盖率：2/17。** AutoVCoder 是一个**纯数字前端"自然语言规格-RTL-功能仿真验证"框架**。它在阶段 ①② 内部完成闭环 -- 训练时用这两个阶段的工具做数据过滤，推理时用它做评测 -- 然后交棒给人和传统工具链。

> 区分"训练时"和"推理时"对 EDA 工具的使用：
>
> - **训练时**：Icarus 编译+仿真用于过滤合成数据（code filter），确保训练集不包含功能错误的样本。这是数据管线的一环，不构成系统交付物。
> - **推理时**：评测阶段使用 Icarus 编译+仿真计算 pass@k。系统本身在推理时不自带仿真反馈循环（不像 MAGE 那样生成-仿真-修改-再生成）-- 推理就是一次前向生成，工具调用只在验证阶段发生。
>
> 另外注意：AutoVCoder 的"功能正确"严格指**给定 testbench 下 Icarus 仿真通过**，不等价于"在所有输入下都正确"（形式验证），也不等价于"能做成芯片"（缺乏综合/时序/物理验证）。

## 3. 输入 / 输出

### 3.1 训练输入（第一轮 LoRA，168,906 条）

第一轮数据格式（真实 GitHub Verilog，code scorer 过滤后 score > 6.5）：

```json
{
  "code": "module counter #(parameter WIDTH = 8) (\n  input clk, rst_n, en,\n  output reg [WIDTH-1:0] count\n);\n  always @(posedge clk or negedge rst_n) begin\n    if (!rst_n) count <= 0;\n    else if (en) count <= count + 1'b1;\n  end\nendmodule",
  "score": 8.234
}
```

第一轮训练使用标准因果语言建模（causal LM）：整段 `code` 被 tokenize，`labels = input_ids`，模型逐 token 做 next-token prediction。**这不是 instruction tuning** -- 模型只学习"Verilog 代码长什么样"，不学习"从规格生成代码"。

### 3.2 训练输入（第二轮 LoRA，22,558 条）

第二轮数据格式（ChatGPT-3.5 合成，code filter 验证后保留）：

```json
{
  "circuit_type": "sequential logic",
  "problem": "Design a 3-bit up-counter with synchronous reset. The counter increments on each positive edge of the clock when enable is high. When reset is high, the counter should return to 0.",
  "verilog_code": "module up_counter (\n  input clk, rst, en,\n  output reg [2:0] count\n);\n  always @(posedge clk) begin\n    if (rst) count <= 3'b0;\n    else if (en) count <= count + 1;\n  end\nendmodule",
  "verilog_testbench": "module tb_up_counter;\n  reg clk, rst, en;\n  wire [2:0] count;\n  up_counter uut (.clk(clk), .rst(rst), .en(en), .count(count));\n  always #5 clk = ~clk;\n  initial begin\n    clk=0; rst=1; en=0; #10 rst=0; #10 en=1;\n    #80 $display(\"Test passed\"); $finish;\n  end\nendmodule",
  "python_code": "def up_counter(initial, steps, en, rst):\n    count = initial\n    for _ in range(steps):\n        if rst: count = 0\n        elif en: count = (count + 1) % 8\n    return count",
  "id": 1,
  "level": "easy",
  "problem_type": "counter"
}
```

第二轮的正确做法是 **instruction tuning**：prompt = problem 文本，completion = verilog_code。但当前代码存在字段名错误 -- 训练脚本读的是 `example["code"]` 而数据文件提供的是 `verilog_code`，详见第 10 节讨论。

### 3.3 推理输入（带 RAG）

User specification（以 VerilogEval 风格为例）：

```text
Implement a module of a 3-bit counter with synchronous reset.
When rst is 1, count is cleared to zero.
When en is 1, count increments by 1 on each positive edge of clk.

module top_module (
    input clk,
    input rst,
    input en,
    output [2:0] count
);
```

Example Retriever 检索到的 top-2 RTL 片段（论文原文未给具体示例，以下为根据论文描述的合理推断）：

```text
Chunk 1 (example): 
module counter_4bit (input clk, rst, en, output reg [3:0] out);
  always @(posedge clk) begin
    if (rst) out <= 4'b0;
    else if (en) out <= out + 1'b1;
  end
endmodule

Chunk 2 (example):
module sync_counter #(parameter N=8) (input clk, rst, inc, output reg [N-1:0] q);
  always @(posedge clk) if (rst) q <= 0; else if (inc) q <= q + 1;
endmodule
```

Knowledge Retriever 检索到的 top-3 硬件知识片段（论文原文未给具体示例，以下为合理推断）：

```text
Chunk 1 (knowledge):
In Verilog, sequential logic is typically described using 
'always @(posedge clk)' blocks. For synchronous reset, the 
reset logic and clock logic share the same clock edge.

Chunk 2 (knowledge):
Non-blocking assignment (<=) should be used for sequential 
logic to ensure correct behavior after synthesis. Blocking 
assignment (=) in sequential blocks can cause simulation-
synthesis mismatches.

Chunk 3 (knowledge):
Parameterized designs improve reusability. Use 'parameter' 
keyword to define configurable bit-widths and thresholds.
```

### 3.4 推理输出

重构 prompt（RAG 模块构建，将 spec + example + knowledge 拼接）：

```text
Implement a module of a 3-bit counter with synchronous reset.
When rst is 1, count is cleared to zero.
When en is 1, count increments by 1 on each positive edge of clk.

You can refer to these documents:
Example 1: module counter_4bit (input clk, rst, en, output reg [3:0] out);
  always @(posedge clk) begin if (rst) out <= 4'b0; else if (en) out <= out + 1'b1; end endmodule

Example 2: module sync_counter #(parameter N=8) (input clk, rst, inc, output reg [N-1:0] q);
  always @(posedge clk) if (rst) q <= 0; else if (inc) q <= q + 1; endmodule

Knowledge 1: In Verilog, sequential logic is typically described using 
'always @(posedge clk)' blocks...

Knowledge 2: Non-blocking assignment (<=) should be used for sequential logic...

Knowledge 3: Parameterized designs improve reusability...
```

模型输出（两轮 LoRA 微调后的 LLM 自回归生成）：

```verilog
module top_module (
    input clk,
    input rst,
    input en,
    output reg [2:0] count
);
    always @(posedge clk) begin
        if (rst)
            count <= 3'b0;
        else if (en)
            count <= count + 1'b1;
    end
endmodule
```

### 3.5 Icarus 编译/仿真日志（评测阶段）

```text
$ iverilog -Wall -Winfloop -Wno-timescale -g2012 -o test.vvp TASK.sv
$ vvp -n test.vvp
Mismatches: 0 in 200 samples
```

通过条件：stdout 匹配 `Mismatches: 0 in N samples`。这是 VerilogEval benchmark 的标准判定方式。

### 3.6 软件幻觉案例（论文 Figure 1 的核心反例）

论文 Figure 1 展示了一个没有 RAG 时 LLM 的典型软件幻觉：

```verilog
// LLM 的错误输出（把 Verilog 当成 C/Python 写）
for (int i = 0; i < 32; i = i + 1)
    sum[i] = a[i] ^ b[i] ^ c[i],
    c[i+1] = (a[i] & b[i]) | ...
```

这正是 knowledge retriever 试图解决的问题：检索"Verilog 的 for 循环是 generate/展开语义而非运行时迭代"这类知识，让模型避免软件习惯污染硬件代码。

```text
┌─────────────────────┐
│ MLP                  │  ← 唯一可训练部分
│ (hidden → scalar)    │
└─────────┬───────────┘
          │
          ▼
      scalar score
```

设计意图：只训练一个轻量 MLP 打分头，基础 embedding 复用预训练 BERT 级模型。这样从 15k 标注外推到 1M 样本时，推断成本远比反复调用 ChatGPT 低。论文没有公开 code scorer 的训练代码和权重，复现者必须自己实现。

### 4.5 Code Filter 的分支验证（论文 Figure 6）

```text
ChatGPT-3.5 生成: {problem, Verilog, testbench, Python}
                        │
                        ▼
              Icarus 语法检查 (iverilog)
                   │            │
               syntax err → 丢弃
                   │
              syntax OK
                   │
         ┌─────────▼──────────────┐
         │                        │
    combinational             sequential
         │                        │
         ▼                        ▼
  Python reference         ChatGPT testbench
  生成随机输入              直接仿真验证
         │                        │
         ▼                        │
  用 Python 输出重构              │
  Verilog testbench              │
         │                        │
         ▼                        ▼
    Icarus 仿真比对              Icarus 仿真比对
         │                        │
         ▼                        ▼
   功能正确?                  功能正确?
         │                        │
    保留 / 丢弃               保留 / 丢弃
```

**为什么组合逻辑与时序逻辑分开验证**：

- 组合逻辑（如加法器、ALU、MUX）：LLM 的数值计算能力弱，让 ChatGPT 写的 testbench 可能期望值就是错的。用 Python reference 生成输入输出对更可靠 -- Python 在纯数值计算上的正确率远高于 Verilog testbench 编写。
- 时序逻辑（如计数器、状态机、FIFO）：LLM 擅长理解序列行为（语言本身就是序列的），ChatGPT 写的 testbench 相对可信。

**但这套验证的边界**：即使完整实现，也只能证明"在生成的有限测试向量上 Verilog 与 Python/testbench 行为一致"。它不能证明所有输入都正确、Python 模型本身正确、代码可综合、综合后与 RTL 等价。更要命的是：**同一个 ChatGPT-3.5 同时生成了规格、RTL、testbench 和 Python -- 如果它在一个概念上理解错了，四个产出物会共同犯错**，code filter 完全无法检测这种系统性错误。

## 5. 关键公式

### 5.1 第一轮因果语言建模损失

$$
\mathcal{L}_{\text{R1}} = -\frac{1}{N} \sum_{i=1}^{N} \sum_{t=1}^{|x_i|} \log P_\theta(x_{i,t} \mid x_{i,<t})
$$

- $N$：训练样本数（168,906）
- $x_i$：第 $i$ 个 Verilog module 的完整 token 序列
- $x_{i,t}$：序列中第 $t$ 个 token
- $P_\theta$：参数为 $\theta$（包括 LoRA adapter）的模型输出概率
- $x_{i,<t}$：前 $t-1$ 个 token 作为上下文

**工程直觉**：这就是标准的 causal language modeling -- 每个 token 都做 next-token prediction。第一轮不做任何 prompt 格式，模型纯粹学习 Verilog 语言的 token 分布。

**为什么第一轮用这个损失**：第一轮的目标不是"规格到代码"，而是让模型知道 Verilog 代码长什么样。对于这个目标，普通的 next-token prediction 就是正确且充分的损失函数。

### 5.2 第二轮指令微调损失

$$
\mathcal{L}_{\text{R2}} = -\frac{1}{M} \sum_{j=1}^{M} \sum_{t=1}^{|y_j|} \log P_{\theta'}\big(y_{j,t} \mid \text{prompt}_j,\ y_{j,<t}\big)
$$

- $M$：合成 problem-code 对数（22,558 ~ 50,000）
- $\text{prompt}_j$：第 $j$ 个问题的自然语言规格文本
- $y_j$：第 $j$ 个答案的 token 序列（Verilog code）
- $\theta'$：从第一轮合并模型出发的 LoRA 参数

**工程直觉**：第二轮把输入从"裸代码"换成"规格 + 代码"对。prompt 提供上下文，模型学习的是 $P(\text{Verilog code} \mid \text{design specification})$，这正是推理时的任务。

### 5.3 Code Scorer 的 MLP 回归损失

$$
\mathcal{L}_{\text{scorer}} = \frac{1}{K} \sum_{k=1}^{K} \big(\text{MLP}(\text{embed}(x_k)) - s_k^{\text{GPT}}\big)^2
$$

- $K$：ChatGPT 标注的样本数（15,000）
- $\text{embed}(x_k)$：frozen sentence-transformer 输出的固定维度向量
- $\text{MLP}(\cdot)$：可训练的多层感知机，映射到标量分数
- $s_k^{\text{GPT}}$：ChatGPT-3.5 给出的质量评分（0-10 整数值）

**工程直觉**：这就是一个最简单的回归任务 -- 学一个从 Verilog embedding 到"教育价值分数"的映射。发布数据的 score 范围为 6.50-11.50（MLP 输出没有 clamp），但阈值过滤（score > 6.5）只依赖相对顺序，不影响筛选质量。

### 5.4 执行反馈函数 F(V)

$$
F(V) = \begin{cases}
0, & \text{syntax is incorrect} \\
1, & \text{syntax is correct but functionality is incorrect} \\
2, & \text{syntax and functionality are correct}
\end{cases}
$$

- $V$：一个 Verilog 代码片段（由 LLM 生成）
- 语法正确性：由 Icarus Verilog（`iverilog`）编译判定
- 功能正确性：由 testbench 仿真 + golden output 比对判定

**工程直觉**：$F(V)$ 是一个三级离散评分函数，把一个复杂的主观问题（"这代码好不好"）降维成三个可自动判定的状态。retriever 训练需要约 200k 对比样本对，0/1/2 的离散分级已足够做正负样本分类：$F(V_i) > F(V)$ 就是 positive pair。

### 5.5 Retriever 的 InfoNCE 对比学习损失

$$
\mathcal{L}_{\text{retriever}} = \sum_{(P, C_+)} -\log \frac{\exp\big(\langle e_P,\ e_{C_+}\rangle / \tau\big)}{\sum_{C_- \in \mathcal{D}} \exp\big(\langle e_P,\ e_{C_-}\rangle / \tau\big)}
$$

- $P$：一个设计问题（查询）
- $C_+$：正样本文档 chunk（加了它之后生成的代码质量提升：$F(V_i) > F(V)$）
- $C_-$：负样本文档 chunk（加了没用或变差：$F(V_i) \leq F(V)$）
- $e_P, e_{C_+}, e_{C_-}$：通过 BGE-M3 encoder 得到的归一化向量
- $\langle\cdot, \cdot\rangle$：向量点积（归一化后即余弦相似度）
- $\tau$：温度参数（train.bash 设为 0.02）
- $\mathcal{D}$：负样本集合

**工程直觉**：这个损失函数同时做了两件事 -- 拉近 query 与正样本的向量（分子），推远 query 与负样本的向量（分母）。标准 contrastive loss 只关心 pairwise 差距，InfoNCE 的 softmax 形式使所有负样本竞争同一个概率质量，harder negatives 贡献更大的梯度。

**温度 $\tau = 0.02$ 的含义**：小温度值使得 exp 的输入被放大 50 倍，softmax 分布更尖锐 -- 模型需要更大的余弦相似度差距才能降低 loss。这迫使 retriever 学到更有区分度的表示。

### 5.6 Retriever 的三路打分融合

$$
\text{score}(P, C) = \text{dense}(P, C) + 0.3 \cdot \text{sparse}(P, C) + \text{colbert}(P, C)
$$

- $\text{dense}(P, C)$：CLS/池化向量的余弦相似度（密集语义匹配）
- $\text{sparse}(P, C)$：学习到的 token 权重稀疏匹配（类似学习版 BM25 关键词匹配）
- $\text{colbert}(P, C)$：token 级 max-sim 聚合（query 的每个 token 找 passage 中最相似的 token，求和）

**工程直觉**：dense 捕捉整体语义相似，sparse 捕捉关键词/术语匹配（硬件领域精确术语很重要，如"D flip-flop"和"JK flip-flop"语义相似但电路完全不同），ColBERT 捕捉 token 级细粒度对齐。0.3 的权重系数是代码默认值，论文没有报告这个系数的消融实验。

### 5.7 Pass@k 无偏估计

$$
\text{pass@}k = \mathbb{E}_{\text{Problems}} \left[ 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}} \right]
$$

- $n$：每题的独立生成次数（论文设 $n = 10$）
- $c$：其中通过的次数
- $k = 1$ 或 $k = 5$（论文报告 pass@1 和 pass@5）

当 $k=1$ 时化简为：

$$
\text{pass@}1 = \mathbb{E}\left[1 - \frac{n-c}{n}\right] = \mathbb{E}\left[\frac{c}{n}\right]
$$

即成功率的期望。当 $k=5$ 时，$\binom{n-c}{5} / \binom{n}{5}$ 是"从 $n$ 次里抽 5 次全是失败"的概率，$1 - (\cdot)$ 就是"至少一次成功"。这个无偏估计的关键在于：即使每道题只跑了 10 次，仍然可以通过这个公式无偏地估计"如果允许跑 5 次，至少有一次通过的概率"。

论文的生成设置：temperature = 0.8, top-p = 0.95, $n=10$。注意这个 temperature 是 0.8 而非极低值，说明 AutoVCoder 依赖采样多样性来达到更高的 pass@5。

### 6.1 是否需要训练

## 7. 创新点

### 创新点 1：代码质量自动筛选 pipeline（code scorer）

**问题**：GitHub 上有百万级 Verilog 代码，但质量参差不齐 -- 测试代码、门级网表、模板代码、不完整模块混在一起。人力无法筛选。

**方案**：用 ChatGPT-3.5 标注 15k 个模块（五维度：readability / modular design / efficiency / scalability / robustness），训练一个 frozen sentence-transformer + 可训练 MLP 的轻量 code scorer，外推到其余百万样本，保留 score > 6.5 的约 168,906 个模块（21.7%）。

**为什么不是直接全量使用**：Table II 中 Round 1 only 相比 Base 的提升（如 CodeLlama Machine p@5: 41.3% -> 46.7%）证明了过滤数据的价值。如果不用 scorer 过滤，低质量代码（不可综合、不完整、格式混乱）会稀释模型学习信号。

**为什么不用 ChatGPT 直接全量评分**：成本。15k x API 费用已经不小，100 万次的 API 费用和耗时是天文数字。轻量 MLP 的推断成本趋近于零。

**工程代价**：当前仓库未公开 code scorer 训练/推理代码和权重。复现者需要：(1) 重新设计打分 prompt；(2) 重新调用 ChatGPT 标注；(3) 重新训练 MLP；(4) 校调阈值。这是一个完整的子项目。

### 创新点 2：两轮 LoRA 的分工解耦（真实分布 vs 任务对齐）

**问题**：单轮 fine-tuning 无法同时兼顾"多样性"和"任务正确性"。只用真实代码 -> 不知道如何从规格生成。只用合成 QA -> 覆盖窄、长尾硬件知识缺失。

**方案**：第一轮用大规模真实 GitHub Verilog 做因果语言建模学分布，第二轮从第一轮合并模型出发用合成 problem-code 对做指令微调学任务映射。

**为什么一定是这个顺序而不是反过来**：先做分布学习再做任务对齐是标准做法。如果反过来（先做 instruction tuning 再做因果语言建模），第二轮的因果语言建模会"冲掉"第一轮学到的 instruction following 能力 -- 这是一个常见的坍缩。

### 创新点 3：双路 RAG（example + knowledge）的分离设计

**问题**：一个设计问题需要两类不同的上下文 -- "类似模块怎么实现"（代码示例）和"这个硬件概念是什么"（领域知识）。传统 RAG 把它们混在一起，检索精度下降。

**方案**：分别训练 example retriever 和 knowledge retriever，各自建库、各自训练、推理时各自检索 top-k 然后合并。Example retriever 检索 top-2 相似 RTL 示例，knowledge retriever 检索 top-3 硬件知识片段。

### 创新点 4：基于执行反馈的 retriever 训练范式

**问题**：标准的 sentence embedding retriever 用文本相似度训练 -- "这个问题文本和这个文档文本相似"。但文本相似不等于"对代码生成有用"。

**方案**：用 $F(V)$（执行后的三级评分）来定义正负样本 -- 不是看文本是否相似，而是看**加了这篇文档后，生成的代码质量是否提升**。$F(V_i) > F(V)$ 即 positive，否则 negative。自动构造约 200,000 对比样本对。

**为什么这是一个突破**：它将 retriever 的优化目标从"语义相似"切换到"因果效用" -- 不是检索"看起来相关的"，而是检索"实际能帮模型生成更好代码的"。这种范式在 RAG 研究中称为 "execution-guided retriever training"，应用到 Verilog 领域是首次。

### 创新点 5：组合逻辑与时序逻辑的差异化验证（code filter）

**问题**：ChatGPT 生成的 testbench 对组合逻辑不可靠 -- LLM 的数值计算能力弱，testbench 的期望输出可能本身就是错的。

**方案**：组合逻辑用生成的等价 Python 代码做 reference -- Python 生成随机输入、计算标准输出、重构 Verilog testbench、仿真比对。时序逻辑用 ChatGPT 生成的 testbench 直接验证（LLM 对序列模式的描述更强）。

**局限性**：Python reference 和 Verilog 的语义不完全一致 -- Python 没有 X/Z 值、没有位宽截断、没有 signed/unsigned 区分、没有阻塞/非阻塞赋值的概念。code filter 能过但实际不等价的情况是存在的。

### 创新点 6：BGE-M3 三路检索表示（dense + sparse + ColBERT）

**问题**：单纯的 dense bi-encoder 在精确术语匹配上弱 -- "Booth multiplier" 和 "multiplier circuit" 在 dense embedding 空间中可能不近。

**方案**：借鉴 BGE-M3 的多向量表示，用 dense（CLS pooling 语义匹配）+ sparse（学习版词表维度 token weight 关键词匹配）+ ColBERT（query token 对 passage token max-sim 细粒度对齐）三路融合。这三路不是简单的 ensemble -- sparse 让 retriever 保留对精确术语的敏感性，ColBERT 捕捉 token 级的细粒度对齐。


### 9.2 "Icarus 仿真通过"和"能做成芯片"之间隔着什么

这是一个评估 AutoVCoder 实际工程价值时最该问的问题。以下是仿真通过但后续阶段会拦截的具体情形：

**在阶段 ③ 逻辑综合被拦下的**：

```verilog
// 情形 A：initial 块赋初值 -- 仿真器完美执行，ASIC 综合器直接拒绝
reg [7:0] data;
initial data = 8'hFF;        // iverilog 仿真完全正常
                              // Design Compiler: initial blocks are not synthesizable

// 情形 B：组合逻辑环 -- 仿真可能收敛，综合必报错
assign a = b & c;
assign b = a | d;             // 组合环 → STA 无法分析 → 综合报错

// 情形 C：latch 推断 -- 功能"对"，但综合出意料之外的锁存器
always @(*) begin
  if (sel) out = data_in;     // 缺 else → 综合推断出 latch
end                           // 仿真行为可能恰好符合 testbench，但设计意图是组合逻辑

// 情形 D：不完整敏感列表 -- 仿真和综合行为不一致的经典陷阱
always @(a) y = a & b;        // 敏感列表少了 b
                              // 仿真: 只在 a 变化时更新 y
                              // 综合: 忽略敏感列表，当组合逻辑处理
                              // → 仿真与门级行为不一致
```

**在阶段 ② 功能仿真中就暴露但 AutoVCoder 可能没有 testbench 覆盖的**：

```verilog
// 情形 E：时序逻辑用了阻塞赋值 -- RTL 仿真碰巧对，真实硬件必错
always @(posedge clk) begin
  q1 = d;                     // 应该用 <=
  q2 = q1;                    // 阻塞赋值 → 综合后行为和 RTL 仿真不一致
end

// 情形 F：跨时钟域无同步器 -- RTL 零延迟仿真完全看不出问题
always @(posedge clk_b)
  sync_data <= data_from_clk_a;  // 缺两级同步器
                                  // RTL 仿真: 零延迟，完美传输
                                  // 真实硬件: 亚稳态，随机输出
```

**在阶段 ⑤ STA 被拦下的**：

```verilog
// 情形 G：组合逻辑深度过大 -- 仿真完全正确但跑不到目标频率
assign result = a * b + c * d + e * f + g * h;  // 64-bit 运算, 级联多级
// RTL 仿真: 零延迟，瞬间出结果
// STA: 关键路径延迟 4.2ns > 2ns 时钟周期 → 建立时间违例
```

**AutoVCoder 对这些全部无感知**。它的目标函数（pass@k）只关注 Icarus 仿真是否 pass/fail，完全没有延迟、面积、功耗、可综合性的信号。

### 9.3 AutoVCoder 用到的 EDA 工具在流程中的角色

| 工具 | AutoVCoder 中的用法 | 在真实芯片流程中的地位 |
|------|-------------------|----------------------|
| `iverilog -Wall` | code filter 的语法门；评测时的编译步骤 | 相当于工程师保存文件后跑的 linter。真实流程会用更严格的 Spyglass / Verilator lint |
| `vvp -n` | code filter 的功能验证；评测时的仿真执行 | 阶段 ② 的核心。工业界用 VCS / Xcelium / Questa |
| testbench + golden output | 功能判定的"标准答案" | 对应真实验证环境里的 scoreboard + reference model |
| Pyverilog | 评测时的语法解析 | 学术界的 Python Verilog 解析器 |
| ChatGPT-3.5 生成的 Python reference | code filter 中组合逻辑的验证桥梁 | 不是标准 EDA 工具。Python 没有 Verilog 的 X/Z/位宽语义 |

## 10. 讨论与局限

### 10.1 论文自述的局限

1. **RAG 语料规模有限**：example database 927 chunks，knowledge database 2,003 chunks。论文在 RTLLM 上 RAG 增益有限，归因于 example 数据库对复杂问题覆盖不足
2. **依赖公开 testbench**：无法做无 testbench 的开放式设计验证
3. **无 PPA/综合反馈**：仅评估语法和功能，未进入逻辑综合阶段
4. **合成数据质量**：由 ChatGPT-3.5 同时生成规格、RTL、testbench、Python，存在共同错误风险

### 10.2 代码/复现层面的问题

以下关键发现来自对开源仓库 `7cbf320d68e6` 的逐文件审计：

1. **code scorer 训练/推理代码和权重未公开**：论文 Figure 4 的设计（sentence-transformer + MLP）只有描述，没有实现。复现者必须从头设计完整的打分 pipeline。

2. **code filter 完整实现缺失**：`code_gen_by_gpt.py` 只做 GPT 调用和正则解析，不执行论文 Figure 6 的 Icarus 验证、Python reference 测试、testbench 重构等核心过滤步骤。发布的 22,558 条 data tar 是"成品"，不是"从生成到过滤的完整管线"。

3. **第二轮训练 schema 不兼容**：训练脚本读 `example["code"]`，但发布数据只有 `verilog_code` 字段。这不是"改一行就行"的问题 -- 正确的 instruction tuning 需要把 `problem` 放入 prompt、把 `verilog_code` 放入 completion，而不是继续做因果语言建模。

4. **RAG 训练和推理入口缺失**：`train.bash` 指向不存在的 `toy_finetune_data.jsonl` 和 `ds_stage0.json`；没有检索、索引、prompt re-construction 的推理入口。端到端 RAG 推理调用链完全缺失。

5. **AutoVCoder LoRA / retriever 权重未公开**：`tests/test.py` 写死的 checkpoint 路径（`checkpoint-84453`, `checkpoint-33828`）均不在仓库中，README 也没有下载链接。仅下载三个基座模型不等于得到 AutoVCoder。

6. **测试脚本与论文采样配置不一致**：论文使用 `temperature=0.8, top-p=0.95, n=10`；当前 `test.py` 使用 `do_sample=False`（greedy）+ 每题 1 个样本 -- 无法复现 pass@5。

7. **论文与代码的超参数不一致**：LLM 学习率论文写 `2e-4`，代码写 `2.5e-5`；第二轮 epoch 论文 3，代码 1；retriever epoch 论文 3，train.bash 写 2。

8. **第一轮数据存在大量重复**：168,906 行中，完全重复的 code 有 37,346 行（22.1%），单一 code 最大重复次数高达 989。如果训练时不做去重，相同代码会被重复加权。

9. **code scorer 分数语义漂移**：论文声称评分范围 0-10，但发布数据的 score 分布为 6.50-11.50，其中 68 个样本 score > 10。MLP 输出没有被 clamp 到 [0,10] 范围，分数不能直接解释为"教育价值 8.5/10"。

10. **不是真正的 QLoRA**：代码调用了 `prepare_model_for_kbit_training`，但 `from_pretrained` 实际写的是 `load_in_8bit=False`，基础权重未进行量化加载。

11. **输出路径硬编码**：两个训练脚本都硬编码 `base_model_name = "codellama"`，即使训练 DeepSeek 或 CodeQwen，checkpoint 也会被写入 `models/codellama/` 下。

12. **requirements.txt 格式不标准**：使用的是类似 conda export 的格式（`accelerate=1.0.1=pypi_0`），不是标准 pip requirement 的 `package==version` 语法，不能直接 `pip install -r`。

**结论**：当前仓库的状态是"数据和部分训练/评价代码开源"，不是"论文模型完整开源"。可以基于开源材料重建 baseline，但不能严格复现论文实验。当前复现等级为 **R1** -- 代码、数据和评价路径已核对，但模型闭环未跑且开放资产不足。

### 10.3 本资料包的批判性分析

**合成数据的共同错误风险（单一模型依赖）**：ChatGPT-3.5 同时生成四个产物：problem、RTL、testbench、Python reference。如果 ChatGPT 在某个硬件概念上理解错了，四个产物会共同犯错 -- code filter 本身就是用这些产物互相校验，无法检测这种系统性错误。对比：如果 testbench 由人类专家编写（或由不同的模型独立生成），这种共同错误就能被捕获。

**功能正确率的剩余瓶颈**：即使在最佳配置（AutoVCoder-CodeQwen + ER&KR）下，EvalHuman pass@5 = 55.9%（44.1% 的设计在 5 次尝试内无法功能正确），RTLLM Function pass@5 = 51.7%（近一半题目功能失败）。对于实际工程场景，一轮生成的成功率仍然远不能"交钥匙"。

**无推理时反馈循环**：与 MAGE 的关键差异 -- AutoVCoder 在推理时不做反馈循环。模型生成一次 Verilog -> 评估 pass/fail -> 结束。不会根据仿真结果重新生成或修复。MAGE 把努力放在每次推理时（多候选 + 仿真 + 修复），AutoVCoder 把努力前移到训练时（数据管线 + 两轮 LoRA + retriever 训练）。

**无 PPA 信号**：AutoVCoder 的优化目标就是 pass@k。生成的代码只要仿真通过就算好，面积、频率、功耗完全不在优化目标里。一段"功能完全正确但面积大 3 倍"的代码和一段"功能正确且面积最优"的代码，AutoVCoder 给它们完全相同的"好"的评价。这与 ChipSeek 形成明确对照：ChipSeek 的训练目标中 PPA 是核心优化维度。

**Benchmark 污染和数据泄漏风险**：第一轮数据来自 GitHub（2010-2023 年的 Verilog 仓库）。VerilogEval 和 RTLLM 的题目/答案也存在于 GitHub 上。论文没有报告是否过滤了与 benchmark 相似的训练样本。如果第一轮训练数据中包含了 benchmark 题目的答案片段，模型可能通过"记忆"而非"理解"来通过测试。

**值得追问的开放问题**：
1. code scorer 阈值 6.5 是怎么选的？如果是基于开发集 grid search，在未见过的 benchmark 上的泛化性如何？
2. 如果去掉 22.1% 的完全重复 code，第一轮 LoRA 的效果会变差还是变好？
3. 能否用 `yosys -p synth` 替换 `iverilog` 做 code filter 的语法门，直接在数据管线阶段过滤掉不可综合的合成数据？
4. example top-2 + knowledge top-3 的 chunk 数是最优的吗？有没有"太多文档反而损害性能"的 context pollution 拐点？
5. 如果先做 instruction tuning 再做 causal LM（反向），是否完全不可行？

## 12. 一分钟复述版

AutoVCoder（上海交大/中山大学/复旦，IEEE ICCD 2024）是一个**不改变 transformer 架构、通过三管齐下让 7B 模型生成更正确的 Verilog** 的系统。

**数据管线**：从 GitHub 约 20k 仓库提取百万 Verilog module -> 训练轻量 code scorer（ChatGPT 标 15k + MLP 外推）-> score > 6.5 保留约 168k 条。同时用 ChatGPT-3.5 合成 problem-code-testbench-Python 四元组，经 Icarus 语法门 + 分电路类型功能验证（组合逻辑用 Python reference 辅助、时序逻辑用 testbench 直接仿真）过滤。

**两轮 LoRA**：Round 1（真实 GitHub RTL，causal LM，1 epoch）学 Verilog 分布；Round 2（合成 problem-code 对，instruction tuning，3 epoch）学规格到代码的任务映射。两轮串联在三个基座上都优于单独任一轮。

**双路 RAG**：example retriever 检索 top-2 相似 RTL 示例，knowledge retriever 检索 top-3 硬件知识片段。retriever 用执行反馈构造正负样本训练 -- 不是看文本相似度，而是看"加了这个 chunk 后生成的代码质量 F(V) 是否提升"。基于 BGE-M3 的 dense+sparse+ColBERT 三路表示。

**结果**：CodeQwen 版在 EvalMachine pass@5 79.9%（超 GPT-4 的 70.6%）、EvalHuman pass@5 55.9%、RTLLM Function 51.7%。

**边界**：只覆盖 ①② 两个 EDA 阶段（2/17），不验证可综合性/时序/PPA，依赖 benchmark 自带 testbench，RAG 语料仅 927+2003 chunks，开源资产不完整（权重/retriever/scorer 未公开，RAG 推理入口和完整 code filter 管线缺失），推理不做反馈循环。当前复现等级 R1。
