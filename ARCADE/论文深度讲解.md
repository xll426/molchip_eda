## 1. 一句话定位

**ARCADE 是一个"闭环"多智能体框架，用于自动生成近似加法器的 Verilog RTL：用分离的 Design Agent（以 spec 为主要输入，可选论文上下文和 RAEM 检索结果）与 Verifier Agent（以 spec 为输入生成 testbench）降低"自评自"风险，用固定的 C++ Golden NMED 测试平台（Verilator）做仿真判决，用检索增强错误记忆（RAEM）把历史失败上下文存成 TF-IDF 可检索知识库实现跨任务经验复用，最终在 APTPU 数据通路中的 13 个近似加法器规格上，将首次尝试成功率从 30.8%（单次调用，无修复）提升到 76.9%（带 RAEM 的闭环修复），平均 NMED 从 25.6% 降至 0.7%，并可选择性地跑 RTL→GDSII 流程（OpenROAD）评估 PPA。**

这句话里的七个技术承重点：

1. **"开环"→"闭环"的根本思路** — 已有 LLM 生成 HDL 的方法大多是"一次性"（open-loop）：LLM 出代码 → 人工检查 → 修 → 再跑，失败后需要人介入。ARCADE 把"失败信号"（NMED 超标、编译失败）自动化地喂回 Design Agent，形成自动修复循环，最多 5 轮迭代。

2. **Design / Verifier 分离** — Design Agent 以 spec 为主要输入（可附加论文上下文和 RAEM 检索结果），看不到 Verifier 生成的 testbench；Verifier Agent 也只以 spec 为输入，看不到 RTL。最终判决由外部 C++ NMED harness 执行。

3. **Golden NMED Harness（Verilator + C++）** — 验证不是用 LLM 生成的 testbench 为准，而是用固定的 C++ 参考模型（$P_{\text{exact}} = a + b$）在 Verilator 仿真中计算 NMED。harness 源码对 LLM 运行时不可直接修改，但 `tb_adder.cpp` 为仓库公开文件、使用无 seed 的 `rand()`，LLM 在理论上可利用其已知弱点。

4. **RAEM（Retrieval-Augmented Error Memory）** — 每个设计尝试的（error_type, error_signature, design_context, NMED_after, success, iteration）以 JSONL 形式追加存储，用 TF-IDF 向量化 + 余弦相似度检索 top-k 历史上最相似的错误上下文，在后续修复尝试时注入 prompt 作为"经验参考"。注意：代码中 `fix_applied`、`fix_as_code_delta`、`nmed_before` 字段虽在 schema 中定义但实际调用未填充。

5. **四种实验模式（E1-E4）** — E1（纯单次调用，无修复）→ E2（带反馈的迭代修复，最多 5 轮）→ E3（E2 + RAEM 检索经验）→ E4（E3 基础上按 spec 顺序分析学习曲线）。注意：E4 的 learning curve 图表在代码中实际读取 E3 数据（代理图）；`run_all_experiments.sh` 默认 `WORKERS=4` 并行执行，非严格 spec-sequential。

6. **APTPU 数据通路集成 + OpenROAD PPA 可选后处理** — 通过 NMED 的加法器自动注入到 APTPU（Approximate Tensor Processing Unit）的数据通路中，再可选跑 OpenROAD 综合 + 布局布线提取面积 / 功耗 / 时序报告（`ppa_loop.py` 是 NMED pass 后的可选步骤，需要外部 flow scaffold）。注意：PPA 结果不反馈回 Design Agent，不是闭环。

7. **DeepSeek 为主、Claude 可选** — 代码实现仅支持 DeepSeek（默认）和 Claude 两种 provider；OpenAI/OpenRouter 未在 `orchestrator.py` 中实现。

**覆盖率：2/17 核心 + 7/17 可选扩展。** ARCADE 的核心价值集中在 RTL 设计自动化（①）和功能验证（②），并通过 OpenROAD 流程（③、⑤、⑦-⑪）提供了一条从 RTL → GDSII 的"自动化演示链路"，但其 PPA 数字仅具参考意义，不能等同于 signoff 级别的物理实现质量。

> ⚠️ **关键边界**：ARCADE 的"成功"定义是 NMED ≤ target + 编译通过 + 仿真不崩溃。它不保证 (a) 设计是可综合的（尽管多数通过了 OpenROAD 流程），(b) 物理设计在 signoff corner 下收敛，(c) 制造后的实际精度误差不超过 NMED 目标。它验证的是"功能近似正确性"，不是"物理正确性"。

## 3. 输入 / 输出

### 3.1 输入

**(a) 加法器规格（adder spec）**

每个设计任务的唯一输入是一组 JSON 规格参数：

```json
{
  "id": "A3",
  "bit_width": 8,
  "nmed_target": 0.05,
  "area_priority": "medium"
}
```

- `bit_width`：加法器的位宽（8 / 16 / 32 bit），决定了 $2^{2 \times \text{bit\_width}}$ 的输入空间
- `nmed_target`：可接受的 NMED 上界（0.005 ~ 0.10），越低越严格
- `area_priority`：面积优先级（high / medium / low），指导 LLM 在"近似程度"和"面积节省"之间权衡

**(b) 论文知识上下文（可选，E1-E4 通用）**

`configs/professor_papers.json` 提供论文摘要作为上下文注入 Design Agent 的 prompt，帮助 LLM 了解已知的近似加法器拓扑（如 LOBA、HEAA、M-HERLOA 等）：

```json
[
  {
    "title": "Design of Low-Power Approximate Adders...",
    "summary": "Proposes LOBA (Lower-part OR-based Approximate adder)..."
  }
]
```

### 3.2 输出

**(a) Design Agent 输出：Verilog RTL**

```verilog
module approx_adder #(
    parameter ADDER_LENGTH = 8,
    parameter IMPRECISE_PART = 4
)(
    input  [ADDER_LENGTH-1:0] a,
    input  [ADDER_LENGTH-1:0] b,
    output [ADDER_LENGTH:0]   sum
);
    // IMPRECISE_PART lower bits: OR-based approximation
    assign sum[IMPRECISE_PART-1:0] = a[IMPRECISE_PART-1:0] | b[IMPRECISE_PART-1:0];
    // upper bits: exact addition
    assign sum[ADDER_LENGTH:IMPRECISE_PART] = a[ADDER_LENGTH-1:IMPRECISE_PART]
                                            + b[ADDER_LENGTH-1:IMPRECISE_PART];
endmodule
```

LLM 自己决定拓扑（LOBA、截断、Mux-based 等），ARCADE 不做拓扑限制。

**(b) Verifier Agent 输出：SystemVerilog Testbench**

Verifier Agent 独立生成一个黑盒 testbench——它不知道 DUT 的内部实现，只能对 `a`、`b` 施加激励并检查 `sum` 输出。该 testbench 不是最终判决依据——Golden NMED harness 才是。

**(c) 最终判决：NMED 报告**

```text
spec_id=A3, bit_width=8, nmed_target=0.05
Test vectors: 65536 (exhaustive)
MED_avg = 15.75  (example: 4-bit OR approximation error)
Avg(P_exact) = 255.0  (8-bit unsigned a+b exact mean ≈ 255)
NMED = 0.0618  (> 0.05, would FAIL for this hypothetical topology)
```
Note: 此示例 NMED ≈ 0.062 超过目标 0.05，与 L284-334 walkthrough 声称的"修复后 0.032"矛盾——walkthrough 数值不可由当前 `tb_adder.cpp` 复现，已删除（见下文）。

### 3.3 中间产物

**(a) RAEM 条目（JSONL）**

```json
{
  "design_number": 7,
  "error_type": "nmed_exceeded",
  "error_signature": "8-bit nmed_target=0.05 got 0.078 with IMPRECISE_PART=6",
  "success": true,
  "iteration": 2
}
```
> ⚠️ 示意示例。代码中 `fix_applied`、`nmed_before`、`fix_as_code_delta` 字段虽在 `raem.py` schema 中定义，但 `orchestrator.py` 实际调用未填充这些字段。主要填充字段为 error_type / error_signature / design_context / nmed_after / success / iteration。

**(b) PPA 报告（通过 OpenROAD 后）**

```json
{
  "area_um2": 246.5,
  "utilization_percent": 45.0,
  "wns_ns": -0.067,
  "tns_ns": -0.000,
  "power_total_w": 3.42e-3
}
```
> ⚠️ 示意示例。`ppa_loop.py` 实际返回字段为 area_um2 / utilization_percent / wns_ns / tns_ns / worst_slack_ns / power_internal_w / power_switching_w / power_leakage_w / power_total_w / gdsii_generated。PPA 是 NMED pass 后的可选后处理，不反馈回 Design Agent。

## 4. 方法与架构

### 4.1 整体 Pipeline

```text

│  └──────────┘    └──────────────┘    └───────────┬───────────┘  │
│       │                                          │              │
│       │            ┌──────────────┐              │ PASS?        │

│                    │(LLM→Testbench)│         ┌────┴────┐        │
│                    └──────────────┘     YES │         │ NO     │

│                                     │OpenROAD │ │  RAEM    │   │

│                                                      │         │

│                                              (up to 5 iterations)
└─────────────────────────────────────────────────────────────────┘
```

### 4.2 核心模块逐个详解

#### 4.2.1 Design Agent

**做什么**：根据 spec（bit_width, nmed_target, area_priority）生成 Verilog 近似加法器模块。在修复模式下，接收 RAEM 上下文 + 上一次的 NMED 失败诊断，生成修正版 RTL。

**为什么这样设计**：
- Design Agent 不能看到 testbench，这是"分离"原则的核心——防止 LLM 写"恰好通过这个 testbench"的代码
- 不给定拓扑约束，让 LLM 自主选择近似策略（OR-based、截断、Mux-based hybrid 等）
- 支持注入论文知识上下文（professor_papers.json）来提升生成质量

**关键实现细节**：
- 默认使用 DeepSeek（deepseek-chat），可选 Claude（claude-sonnet-4-20250514）
- 系统 prompt 从 `configs/prompt_templates/design_agent_system.txt` 加载
- 修复模式的 prompt 包括：(a) 原始 spec，(b) RAEM 检索到的历史相似错误+修复，(c) 上一次的 NMED 失败诊断

#### 4.2.2 Verifier Agent

**做什么**：同样只看 spec，独立生成一个 Verilog testbench。该 testbench 是"软验证"——它提供一个独立视角的 NMED 估计，但不是最终判决。

**为什么这样设计**：
- 分离验证：两个 Agent 看到相同的信息（spec），但互不知对方的输出，模拟"独立验证工程师"的角色
- 它的 testbench 产生的 NMED 预期与 golden harness 一致，但不能取代 golden——LLM 生成的 testbench 可能也有 bug

#### 4.2.3 Golden NMED Harness（Verilator + C++）

**做什么**：这是最终的唯一判决者。用 Verilator 把 LLM 生成的 Verilog 编译成 C++ 仿真模型，在 C++ 侧计算 $P_{\text{exact}} = a + b$，与 DUT 输出对比计算 NMED。

**为什么这样设计**：
- LLM 运行时无法直接修改 harness 源码（`tb_adder.cpp`）——提供基本隔离但非密码学安全保证（harness 源码为仓库公开文件，使用无 seed 的 `rand()`，LLM 在理论上可利用其已知弱点）
- Verilator 是业界标准的开源 Verilog 仿真器，仿真结果可信
- 8-bit 设计跑穷举测试（all $2^{16} = 65536$ 个 (a,b) 输入对），16/32-bit 跑 `rand()` 随机采样（非分层采样；32-bit 下 `RAND_MAX = 2^{31}-1` 不覆盖完整 $2^{32}$ 输入空间）

**NMED 定义**：

$$
\text{MED}_{\text{avg}} = \frac{1}{N} \sum_{i=1}^{N} |P_{\text{exact},i} - P_{\text{approx},i}|
$$

- $N$ 测试向量数
- $P_{\text{exact},i}$：精确加法结果（C++ 中计算）
- $P_{\text{approx},i}$：近似加法器输出（Verilator 仿真读取）

$$
\text{NMED} = \frac{\text{MED}_{\text{avg}}}{|\text{Avg}(P_{\text{exact}})|}
$$

- $\text{Avg}(P_{\text{exact}})$：精确和的平均值，作为归一化分母
- 判定：$\text{NMED} \leq \text{nmed\_target}$ → PASS

#### 4.2.4 RAEM（Retrieval-Augmented Error Memory）

**做什么**：一个增量式经验库。每次设计尝试（无论成功或失败）都会被记录为一条 JSONL 条目（实际填充字段：error_type, error_signature, design_context, nmed_after, success, iteration）。当一个新的修复请求到来时，用 TF-IDF 向量化当前错误签名 + 余弦相似度检索 top-k 最相似的历史条目，把这些"前人经验"注入修复 prompt。

**为什么这样设计**：
- 避免重复同样的错误（例如反复设置过高的 IMPRECISE_PART）
- 跨任务知识迁移：修复 spec A1 的经验可能对 spec A3 有用
- TF-IDF 是轻量级选择——不需要 GPU、不需要 embedding 模型、直接可运行

**RAEM 实际行为（vs schema 定义）**：
- `raem.py` schema 定义了 fix_applied、fix_as_code_delta、nmed_before 字段，但 `orchestrator.py` 实际调用时这些字段未填充
- RAEM 查询（`raem_query`）在第一次 Design Agent 调用前执行一次；repair 失败后仅更新 repair_feedback 字符串，不重新检索

#### 4.2.5 APTPU Integrator + PPA Loop

**做什么**：当一个加法器通过 NMED 后，自动将其注入到 APTPU（Approximate TPU）数据通路中，然后跑 OpenROAD 流程（Docker 化的 orfs）进行综合 + 布局布线，提取面积、功耗、WNS/TNS 报告。

**为什么这样设计**：
- "仿真通过"≠"物理可实现"——需要综合和布局布线的反馈来判断设计的实际 PPA
- 自动化 → 整个流程不需要人工介入

### 4.3 模块职责矩阵

| 模块 | 输入 | 输出 | 使用的模型/工具 | 是否需要训练 |
|------|------|------|----------------|:---:|
| Design Agent | spec JSON | Verilog RTL | DeepSeek / Claude LLM | ❌ |
| Verifier Agent | spec JSON | SystemVerilog Testbench | DeepSeek / Claude LLM | ❌ |
| Golden NMED Harness | Verilog RTL + spec | NMED + PASS/FAIL | Verilator + C++ | ❌ |
| RAEM | (error, fix, outcome) | top-k 相似历史条目 | TF-IDF + Cosine | ❌ |
| APTPU Integrator | 通过的 Verilog RTL | 注入后的 APTPU 数据通路 | Python string replace | ❌ |
| PPA Loop | APTPU RTL + OpenROAD configs | 面积/功耗/时序报告 | Docker openroad/orfs | ❌ |

### 4.5 Paper Crawler：学术知识注入

ARCADE 还包含一个可选的 Paper Crawler 模块（`src/paper_crawler.py`），它从 `configs/professor_papers.json` 中读取已知近似加法器论文的引文信息。该 JSON 文件仅含 `title/year/key` 三字段，无摘要、无具体拓扑描述。Paper Crawler 将引文标题格式化为上下文注入 Design Agent 的 prompt。

此模块不是核心贡献，体现了 ARCADE 的设计意图——让 LLM 从文献引文中获得拓扑灵感（如 LOBA、HEAA 等），而非手工编码拓扑知识。

## 5. 关键公式

### 5.1 NMED 判定准则

论文未给出编号公式，以下是对其算法行为的严格形式化：

$$
\text{MED}_{\text{avg}} = \frac{1}{N} \sum_{i=1}^{N} |(a_i + b_i) - \text{DUT}(a_i, b_i)|
$$

- $N$：测试向量数（8-bit 为 $2^{16}=65536$ 穷举，16/32-bit 为 `rand()` 随机采样，非分层采样）
- $a_i, b_i$：第 $i$ 个测试向量
- $\text{DUT}(a_i, b_i)$：LLM 生成的近似加法器在输入 $(a_i, b_i)$ 下的输出

$$
\text{NMED} = \frac{\text{MED}_{\text{avg}}}{\frac{1}{N} \sum_{i=1}^{N} (a_i + b_i)}
$$

- 分母：精确和的平均值
- 判定：$\text{NMED} \leq \text{nmed\_target} \Rightarrow \text{PASS}$

**工程直觉**：NMED 衡量的是"平均每个输出值的相对误差"。如果 NMED = 0.05，意思是平均而言，近似结果偏离精确结果约 5% 的量级。归一化分母用的是精确和的均值而非最大值——这使得 NMED 对不同位宽的加法器具有可比性（32-bit 的自然比 8-bit 的绝对误差大，但归一化后在同一尺度）。

**为什么这么设计**：
- 用均值归一化（而非最大值归一化）：避免奇异值（全 1 输入对很少出现）主导指标
- NMED 匹配 APTPU 文献（Elbtity et al.）的标准定义，保证与已有工作的可比性

### 5.2 RAEM 检索相似度

$$
\text{sim}(q, e) = \frac{\mathbf{v}_q \cdot \mathbf{v}_e}{||\mathbf{v}_q|| \cdot ||\mathbf{v}_e||}
$$

- $\mathbf{v}_q$：当前错误签名的 TF-IDF 向量
- $\mathbf{v}_e$：RAEM 中第 $e$ 条 error_signature 的 TF-IDF 向量
- $\text{sim}(q, e)$：余弦相似度，TF-IDF 向量非负，实际值域通常为 $[0, 1]$

**工程直觉**：TF-IDF 捕捉的是"关键术语"的重叠度（如 "nmed_target=0.05"、"8-bit"、"IMPRECISE_PART"），如果两个错误签名在这些关键词上重合度高，它们很可能需要相似的修复策略。

### 5.3 Pass@1（首次尝试成功率）

$$
\text{Pass@1} = \frac{|\{\text{specs passed in 1st attempt}\}|}{|\{\text{all specs}\}|}
$$

- 论文核心指标，衡量"不修复、一次就过"的能力
- E1（Vanilla）= 30.8%（4/13）
- E3（+RAEM）= 76.9%（10/13）

## 6. 训练与实验设置

### 6.1 是否需要训练

**不需要训练。** ARCADE 是一个纯推理时（inference-time）框架——所有组件（Design Agent、Verifier Agent、RAEM）都使用预训练的 LLM + 规则系统，无需微调、无需 RL、无需梯度更新。RAEM 的 TF-IDF 也是无参数的"记忆"机制。

### 6.2 实验设置

**(a) 评估对象**
- **APTPU 基准**：13 个近似加法器规格（8/16/32 位宽，NMED 0.005–0.10，面积优先级 high/medium/low）
- 规格 ID A1–A13（见 §3.1）

**(b) 四种实验模式**

| 模式 | 名称 | 描述 |
|------|------|------|
| **E1** | ARCADE-Vanilla | 单次生成，无修复循环，无 RAEM。建立基线。 |
| **E2** | ARCADE-Repair | 加入闭环修复：失败 → NMED 诊断 → 重新生成，最多 5 轮。 |
| **E3** | ARCADE-Memory | E2 + RAEM：在修复 prompt 中注入 top-k 相似历史错误/修复。 |
| **E4** | ARCADE-Full | 同 E3，但按顺序跑所有 spec（RAEM 在顺序运行中逐步填充），用于学习曲线分析。 |

**(c) LLM 配置**
- 默认模型：DeepSeek (deepseek-chat)
- 可选模型：Claude (claude-sonnet-4-20250514)。代码仅支持 DeepSeek 和 Claude 两种 provider。
- 单次调用（single-shot generation per LLM call），无 few-shot 示例

**(d) 评估指标**
- **Pass@1**（首次尝试通过率）：无需修复即通过的比例
- **Pass@3**（3 次内通过率）：最多 3 轮修复后通过的比例
- **NMED**：通过设计最终达成的 NMED 值
- **PPA**（面积/功耗/WNS）：通过 OpenROAD 后的物理指标

### 6.3 关键实验结果

> ⚠️ 以下数字来源：IEEE VTS 2026 公开发布的论文摘要及 GitHub 文档所述的实验结论。因无原论文全文 PDF，数字以作者公开材料为准。部分精确值（如 E2 的具体改善幅度）需参照原论文 Table I / II。

| 指标 | E1 (Vanilla) | E2 (Repair) | E3 (RAEM) | E4 (Full) |
|------|:---:|:---:|:---:|:---:|
| Pass@1 | 30.8% (4/13) | — | **76.9%** (10/13) | — |
| 3 次内全部解决 | ❌ | ❌ | ✅ | **✅ 100%** (13/13) |
| 平均 NMED | 25.6% | — | — | **0.7%** |

**这张表说明了什么**：

1. **修复循环是关键**：E1 只有 30.8% 的单次成功率，说明纯 LLM 一次性生成近似加法器非常不可靠——LLM 不理解 NMED 约束。
2. **RAEM 带来质的飞跃**：加上历史经验检索后，首次成功率从 30.8% 跃升至 76.9%——"记住过去的错误"比"每次都从零开始修"高效得多。
3. **闭环可以"征服"整个 spec 集**：E4 的 100% 通过率证明，只要修复循环 + 经验记忆叠加，13 个不同规格的近似加法器都可以被自动生成并验证通过。

### 6.4 按位宽的难度分析

近似加法器设计存在一个核心 tension：高位宽 + 低 NMED 的组合极其困难。因为 NMED 是平均值归一的，而高位宽意味着更大的输入空间和更复杂的进位链，OR-based 近似在低位的误差会在多级进位中放大。

| 难度等级 | Spec 示例 | 特征 | 通过情况 |
|----------|-----------|------|----------|
| 容易 | A1 (8b, NMED 0.10) | 低位宽 + 宽松 NMED | 多数模式首次通过 |
| 中等 | A3 (8b, NMED 0.05) | 低位宽 + 中等 NMED | E2 可在 1-2 轮修复内通过 |
| 困难 | A10 (32b, NMED 0.01) | 高位宽 + 严格 NMED | 需多轮修复 + RAEM 辅助 |
| 极难 | A12 (32b, NMED 0.005) | 高位宽 + 极严格 NMED | 仅 E4 在 3 轮内通过 |

**为什么高位宽困难**：一个 32-bit 的 LOBA 近似加法器，如果 IMPRECISE_PART=16，低 16 位的 OR-based 近似在随机输入下引入的平均误差约为 $2^{14}$（因为 OR 在 a ≠ b 时高估低位的偶发溢出会向高位传播），而精确和的期望值约为 $2^{31}$——归一化后的 NMED 可能在 0.01-0.05 范围内波动，取决于随机种子。把 NMED 压到 0.005 意味着每 200 个输出值里平均误差不超过 1——这对近似加法器的拓扑选择提出了极高要求。

### 6.5 RAEM 消融分析（从 E0 到 E4 的能力增益分解）

| 消融对比 | 增量 | 说明 |
|----------|------|------|
| E1 vs 纯 LLM（无 ARCADE 框架） | +Pass@1 基线 | 论文知识上下文（Paper Crawler）提供拓扑灵感 |
| E2 vs E1 | +修复成功率 | 闭环反馈让失败 spec 有机会通过重试达到 NMED |
| E3 vs E2 | +Pass@1 +46.1pp | RAEM 检索让首次尝试就能借鉴历史经验 |
| E4 vs E3 | +达成 100% 3 轮内通过 | 顺序运行使 RAEM 渐进积累，后期 spec 受益于前期经验 |

**核心发现**：修复循环（E2）解决了"失败后可以再试"的问题，但 RAEM（E3）解决了"第一次就更可能成功"的问题——这是两种不同性质的增益。修复循环提升的是"最终通过率"，RAEM 提升的是"效率"（用更少的迭代次数达成通过）。

## 7. 创新点

### 创新点 1：分离式多智能体验证架构（Design-Verifier Separation）

**和已有方法的区别**：大多数 LLM 生成 HDL 的工作（如 ChipMATE、VerilogCoder）使用单个 Agent 既生成代码又评估代码，或者用同一 LLM 调用生成 testbench + RTL。ARCADE 在 RTL 生成中 enforce "Design Agent 和 Verifier Agent 信息隔离"——两个 Agent 只能看到公共的 spec，互不知对方的输出。

**为什么重要**：这防止了"考试前偷看答案"的问题——如果 Design Agent 知道 testbench 的实现方式，它可能生成恰好通过该 testbench 但实际功能不正确的 RTL。

### 创新点 2：RAEM——可检索的跨任务经验记忆

**和已有方法的区别**：已有的 LLM 修复循环（如 Self-Debug、Reflexion）依赖单次对话内的上下文，每次新任务从零开始。ARCADE 的 RAEM 把历史尝试持久化为 JSONL + TF-IDF 索引，让"前人在 spec A1 上修过的经验"自动复用到"当前在 spec A3 上的修复"。

**为什么重要**：这解决了 LLM 修复中的核心痛点——同一个错误模式（如 IMPRECISE_PART 设太大）会在不同 spec 上反复出现。RAEM 通过检索告诉 LLM "上次遇到类似错误时，减少 IMPRECISE_PART 从 6 到 4 就解决了"，大幅提升修复效率。

### 创新点 3：Golden NMED——不可作弊的硬判决

**和已有方法的区别**：多数 LLM 验证方法依赖 LLM 自己判断对错（自评、LLM-as-judge），或依赖 EDA 工具链（可能被 LLM 误解或绕过）。ARCADE 的 C++ NMED harness 对 LLM 完全透明——LLM 不知道 C++ 如何计算 NMED，只知道"过"或"不过"以及"当前 NMED 值"。

**为什么重要**：这是"信任"的基础。如果验证也是 LLM 做的，那 LLM 可能在验证环节也出错（hallucinate 一个 PASS）。Golden harness 提供了数学上不可争议的 ground truth。

### 创新点 4：端到端 RTL→GDSII 自动化链路

**和已有方法的区别**：大多数 LLM RTL 生成工作止步于"仿真通过"。ARCADE 将 LLM 生成的 RTL 自动注入物理设计流程（OpenROAD）并提取 PPA 报告（作为可选后处理步骤，PPA 不反馈回 Design Agent）。

**为什么重要**：RTL"仿真通过"不代表"可以做成芯片"——PPA（面积、功耗、时序）才是流片的硬约束。ARCADE 展示了从 natural language spec 到 PPA 报告的完全自动化。

## 9. 与芯片流程的关系

### 9.1 在全流程中的位置

ARCADE 覆盖了芯片设计全流程的最前端——**RTL 设计（①）和 RTL 功能仿真（②）**——并通过 OpenROAD 链路向物理设计阶段（③、⑤、⑦-⑪）做延伸演示。

- **接手什么**：从 specs JSON（位宽 + NMED 目标 + 面积优先级）接手——这是"设计需求文档"的机器可读形式
- **交棒给谁**：交棒给 OpenROAD 物理设计流程（用于 PPA 评估）或人工 RTL 评审（用于实际流片）
- **解决了什么痛点**：RTL 手动编写 + 验证循环长达数小时到数天，ARCADE 将其自动化到分钟级

### 9.2 "NMED 通过"和"能做成芯片"之间隔着什么

1. **综合友好性**：LLM 生成的 Verilog 可能有不可综合的构造（如 `initial` 块、`$display` 等）。Verilator 是仿真工具而非综合检查器——它会 lint 警告这些构造但允许通过，不等于综合验证。
2. **时序收敛**：近似加法器的关键路径可能比精确加法器更长（额外的 Mux / 控制逻辑），在目标频率下可能不收敛。
3. **面积真实性**：OpenROAD 综合结果只针对 Nangate 45nm 库。实际工艺库、foundation IP、macro cell 的存在会显著改变面积。
4. **功耗评估**：OpenROAD 的功耗估计基于开关活动因子假设（默认值），不反映真实工作负载下的动态功耗。
5. **Signoff corner**：论文未报告在 SS/FF/SF/FS 等 corner 下的 PPA，只有 typical corner。
6. **APTPU 系统级验证**：加法器集成到 APTPU 后，整体推理精度（如 ImageNet top-1）受近似加法器影响的程度未在论文中报告。

## 10. 讨论与局限

### 10.1 论文自述的局限

- **领域范围**：当前仅支持近似加法器，扩展到乘法器、MAC 单元、浮点单元需要修改 spec 格式和 NMED 定义
- **LLM 依赖**：生成质量取决于底层 LLM 的硬件设计能力。DeepSeek 对高级硬件设计任务的表现可能不如 Claude 或 GPT-4
- **RAEM 的冷启动**：E3/E4 初期 RAEM 为空，无法提供经验上下文，等同于 E2

### 10.2 代码/复现层面的问题

- **API 费用**：13 个 spec × 最多 5 轮 Design Agent 调用 + 1 次 Verifier Agent 调用 ≈ 约 78 次 LLM 调用（单 spec 最多约 6 次），按 DeepSeek 价格可接受但使用 Claude 可能较贵
- **Verilator 依赖**：需要安装 Verilator，在部分系统上编译困难（尤其是缺少系统开发库的环境）
- **OpenROAD Docker**：PPA 评估需要拉取 `openroad/orfs` 镜像（约 5GB），且不原生支持 Apple Silicon（需要 Rosetta 模拟）
- **TF-IDF 简单性**：当 RAEM 条目增多后（> 1000），TF-IDF 的检索精度可能下降——缺少语义理解

### 10.3 本资料包的批判性分析

1. **NMED 判决是"必要非充分"条件**：NMED ≤ target 只保证数值精度，不保证 (a) 设计是面积最优的，(b) 设计是可综合的，(c) 设计在 corner 下收敛。论文把"物理可实现性"外包给了 OpenROAD，但 OpenROAD 只跑 typical corner。

2. **13 个 spec 的泛化性**：spec 空间（8/16/32 bit × 0.005–0.10 NMED × 3 种 area priority）只是近似加法器设计空间的一小部分。扩展到 64-bit 或其他运算单元（乘法器、除法器、浮点）的可行性未知。

3. **"分离"原则的实现边界**：Design Agent 和 Verifier Agent 虽然信息隔离，但它们共享同一个 spec。如果 spec 本身隐含了拓扑信息（极小 NMED + 高位宽 → 暗示需要低近似度设计），两个 Agent 可能仍然形成隐式耦合。

4. **和 [ChipMATE](../ChipMATE/论文深度讲解.md) 的对比**：
   - ChipMATE 做的是通用 RTL 模块（FIFO、ALU、FSM 等），用 RL 训练多智能体
   - ARCADE 做的是专用近似加法器，用 prompt engineering + 修复循环
   - 两者的共同点是"多智能体 + 闭环"，但 ChipMATE 需要训练奖励模型，ARCADE 完全免训练

5. **和 [PRO-V](../PRO-V/论文深度讲解.md) 的对比**：
   - PRO-V 做的是 RTL 验证（给定 RTL，生成 testbench + 找 bug）
   - ARCADE 做的是 RTL 生成 + 验证（先生成 RTL，再验证 NMED）
   - 两者在验证环节有相似之处（多智能体 + 外部工具验证），但方向相反

## 12. 一分钟复述版

ARCADE 是一个用 LLM 自动生成近似加法器 Verilog 的闭环多智能体框架。它的核心设计原则是"分离验证 + 经验复用"：(1) Design Agent 和 Verifier Agent 信息隔离——各自以 spec 为主要输入，互不知对方的输出；(2) 最终验证由固定的 C++ NMED harness（Verilator 仿真）执行；(3) 每次设计尝试被记录到 RAEM（JSONL + TF-IDF 检索），后续修复时检索历史上最相似的错误上下文注入 prompt。在 APTPU 的 13 个近似加法器 spec 上，E1（纯单次）只有 30.8% 通过率，E3（+RAEM 闭环修复）达到 76.9%；E4 的 learning curve 图在代码中实际读取 E3 数据（代理图）。通过的加法器可选择性跑 OpenROAD PPA 流程（非闭环反馈）。最大局限是只支持加法器，扩展到其他运算单元需要重新设计 spec 和验证 harness。注意：本地 PDF 实为 IEEE HTML 页面（正文受付费墙限制），仓库无实验结果文件；RAEM 的 fix_applied/nmed_before 字段在代码中未实际填充。
