## 0. 先理解：AST（抽象语法树）到底是什么？

### 0.1 从一段 Verilog 代码说起

```verilog
module half_adder (
    input  A,
    input  B,
    output Sum,
    output Cout
);
    assign Sum  = A ^ B;
    assign Cout = A & B;
endmodule
```

这段代码对人类来说很好理解——一个半加器，Sum = A 异或 B，Cout = A 与 B。但计算机处理的是字符串，它看到的只是：

```
"module half_adder (\n    input  A,\n    input  B,\n    ..."
```

**文本级操作**的致命问题是：你要把 `A ^ B` 改成 `A | B`，怎么做？正则表达式 `A \^ B` → `A | B` 替换？但万一代码里有 `A ^ B` 出现在注释里呢？万一操作数之间有空格（`A  ^  B`）呢？万一括号嵌套导致匹配错误呢？

**AST 解决了这个问题**：它把代码从"字符串"变成"结构化的树"，每个语法元素都有明确的类型和位置。

### 0.2 半加器代码对应的 AST 树形结构

```
Module: half_adder
├── PortList
│   ├── Port: A (input, wire)
│   ├── Port: B (input, wire)
│   ├── Port: Sum (output, wire)
│   └── Port: Cout (output, wire)
│
├── Assign: Sum = XOR(A, B)
│   ├── Lvalue: Sum                        ← 左值，不可变异（是目标信号名）
│   └── Rvalue: XOR                        ← 右值，可以变异！
│       ├── Left:  Identifier("A")
│       └── Right: Identifier("B")
│
└── Assign: Cout = AND(A, B)
    ├── Lvalue: Cout
    └── Rvalue: AND                        ← 可以变异！
        ├── Left:  Identifier("A")
        └── Right: Identifier("B")
```

现在你有了树，要改 `^` 为 `|`，你不需要做字符串替换——你直接找到 `XOR` 节点（类型精确匹配），把它替换成 `OR` 节点。不会误伤注释，不会被空格干扰，不会搞错嵌套。

## 1. Algorithm 2 完整走读：AST 变异的七个步骤

论文的 Algorithm 2 是整个数据增强引擎的核心。我用论文原文的伪代码，逐行解释：

```
Algorithm 2: AST-Based RTL Mutation Process
Require: RTL code R, mutation count N
Ensure:  Mutated RTL code R′
```

**输入**：一个已验证的 RTL 代码 R，要执行的变异次数 N
**输出**：变异后的 RTL 代码 R′

### Step 1: 解析 RTL → AST

```
1: ast ← ParseVerilogToAST(R)
```

**工具**：使用 **PyVerilog 1.3.0**（论文 Table 13 明确写了版本号）。

PyVerilog 做的事情：
- 词法分析（Lexer）：把字符流切成 token 流 —— `module`, `half_adder`, `(`, `input`, `A`, `,`, ...
- 语法分析（Parser）：按 Verilog IEEE 1364 语法规则把 token 组织成树
- 输出：一个 `ast` 对象，树根是 `Module` 节点

这时候，代码从"字符串"变成了"可遍历、可修改的树结构"。

![Algorithm 2: 论文原图 — AST-Based RTL Mutation Process 完整伪代码](figures/algo2-ast-mutation.png)

> **论文原图 Algorithm 2**：ParseVerilogToAST → BuildNodePaths → 遍历所有可变异节点 → GetMutationCandidates → RandomSample → ApplyMutation + CheckConsistency → ASTToVerilog → PassesSynthesis。以下为中文逐行解读。

### Step 2: 构建节点路径 —— 论文的创新点

```
2: node paths ← BuildNodePaths(ast)
```

**这是论文的一个重要工程创新**。路径由三元组 `(parent, attribute, index)` 组成：

- **parent**：父节点引用
- **attribute**：该子节点在父节点中的属性名。比如对于 `assign Sum = A ^ B`：
  - 左值 `Sum` 的 attribute 是 `'left'`
  - 右值 `XOR` 节点的 attribute 是 `'right'`
  - `XOR` 的左操作数 `A` 的 attribute 是 `'left'`
- **index**：如果属性是列表（比如多个 assign 语句），用 index 定位第几个。如果是标量属性，用 -1

**为什么需要路径？** 因为变异会修改 AST 结构。如果你存的是"第 3 个 Assign 节点"的裸指针，前面插入或删除一个节点后，"第 3 个"可能已经是另一个节点了。路径机制保证了引用的稳定性——即使 AST 结构变了，只要路径还在，就能精确定位到原始目标节点。

### Step 3: 收集所有可变异节点

```
3: mutations ← []
4: for each node in ast do
5:     if IsMutable(node) then
6:         candidates ← GetMutationCandidates(node)
7:         mutations.append(candidates)
8:     end if
9: end for
```

**IsMutable(node)** 判断节点是否可以变异：

| 节点类型 | 可变异？ | 原因 |
|---------|---------|------|
| `+`, `-`, `*`, `/`, `%` | ✅ | 算术运算节点，有同类替换目标 |
| `&&`, `\|\|`, `&`, `\|`, `^` | ✅ | 逻辑/位运算节点 |
| `==`, `!=`, `>`, `<`, `>=`, `<=` | ✅ | 关系运算节点 |
| `posedge clk`, `negedge clk` | ✅ | 时序边沿 |
| `<=` 赋值 | ✅ | 阻塞/非阻塞转换 |
| 常量 `8'd10` | ✅ | ±1 微调 |
| 模块名、端口名 | ❌ | 改了接口就变了，不再是"同一个设计" |
| 注释 | ❌ | 不影响硬件行为 |
| `always @(*)` 敏感列表 | ❌ | 改了这个语义完全变 |

**GetMutationCandidates(node)** 为每个可变异节点生成候选变换：

```
如果 node 是 XOR(A, B)：
  → 候选1: OR(A, B)       // 同属位运算大类
  → 候选2: AND(A, B)      // 同属位运算大类
  → 候选3: XNOR(A, B)     // 如果标准单元库支持
  → 不会候选: +(A, B)     // 位运算↛算术运算，类型不兼容！
```

**约束检查发生在候选生成阶段，不是变异执行阶段**。这比"先变了再说、不行就回滚"高效。

### Step 4: 随机采样 N 个变异

```
10: selected ← RandomSample(mutations, N)
```

从所有候选变异中随机选取 N 个。论文强调的采样策略有四层过滤：

1. **节点类型过滤**：只考虑有定义变异算子的节点类型
2. **上下文验证**：检查变异在当前的 AST 上下文中是否合法。例如：
   - `always @(posedge clk)` 中的 `posedge` 可以变异为 `negedge`
   - 但在 `assign c = a ^ b;` 中就不能做边沿变异——这里根本没有时序信号
3. **多样性最大化**：选出的 N 个变异尽量覆盖不同的节点类型和代码位置，避免全部命中同一个 always 块
4. **综合可行性优先**：历史上容易导致综合失败的变异类型（比如除零风险）被降权

### Step 5: 逐个应用变异 + 一致性检查

```
11: for each mutation in selected do
12:     ast ← ApplyMutation(ast, mutation)
13:     CheckConsistency(ast)
14: end for
```

**ApplyMutation** 的核心操作：在 AST 中定位到目标节点，用变异后的新节点替换它。

```
变异前:                         变异后:
Rvalue: XOR                     Rvalue: OR
├── Left:  A                    ├── Left:  A
└── Right: B                    └── Right: B

assign Sum = A ^ B;     →      assign Sum = A | B;
```

**CheckConsistency** 每次变异后立即执行（不是等 N 个全做完），检查内容包括：
- always 块内是否混用了 `=` 和 `<=`？→ 触发 Algorithm 3 修复
- 位宽是否匹配？`a[3:0] | b[7:0]` 会报错
- 是否有除零风险？`a / 0` 会被拦截
- 赋值目标是否合法？不能对 wire 用 `<=`，不能对 reg 用 `assign`

##### 补充：阻塞赋值 vs 非阻塞赋值（为什么混用是大忌）

这是 Verilog 里最容易踩的坑，也是论文 Algorithm 3 存在的根本原因。

```verilog
// 假设时钟沿到来前：a=1, b=2, c=0

// === 阻塞赋值 =  ===                  === 非阻塞赋值 <= ===
always @(posedge clk) begin          always @(posedge clk) begin
    a = b;       // a 立刻变成 2         a <= b;      // "a 的新值"暂记为 2，不生效
    c = a;       // c 变成 2             c <= a;      // "c 的新值"暂记为旧值 1
end                                  end
// 结果：a=2, c=2                     // 结果：a=2, c=1
```

**根本区别**：
- `=`（阻塞）：像普通编程语言，上一行执行完下一行立刻看到新值。`c = a` 拿到的 `a` 已经是 2 了。
- `<=`（非阻塞）：always 块开始时，所有右边的值先"拍照快照"（b=2, a=1）。无论你怎么排顺序，左边的赋值都在块结束时**同时生效**。所以 `c <= a` 拿到的 `a` 是快照值 1。

**为什么混用会出大事**：

```verilog
// ❌ 专业 RTL 代码绝对不会这么写
always @(posedge clk) begin
    a =  b;       // 阻塞：立刻生效
    c <= a;       // 非阻塞：用快照值
end
```

这段代码在**仿真器**和**真实硬件**上的行为完全不同——仿真器按顺序执行，综合器产生不可预测的硬件。这就是论文 Section C.3.1 说的 **race conditions** 和 **simulation/synthesis mismatch**。很多综合工具直接拒绝编译混用赋值。

**Algorithm 3 多数投票法的逻辑**：统计 always 块内 `=` 和 `<=` 的数量 → 如果混用，以数量多的那种为准，把全部赋值统一成一种。论文说多数类型"最可能代表设计者本意"且"最小化修改量"。

### Step 6: AST 转回 Verilog 代码

```
15: R′ ← ASTToVerilog(ast)
```

PyVerilog 的代码生成器把修改后的 AST 重新输出为合法的 Verilog 文本。由于变异全程在 AST 级别操作（保证语法正确），输出的代码一定符合 Verilog 语法——**从根源上消除了语法错误**。这是 AST 方法相比文本级正则替换的核心优势。

### Step 7: 综合验证 —— 最后一道关卡

```
16: if not PassesSynthesis(R′ ) then
17:     return ApplyTextMutation(R, N )   // 降级方案
18: end if
19: return R′
```

**PassesSynthesis** 用的是 **Synopsys Design Compiler 2020.09**（论文 Table 13），跑真实综合。如果综合失败（比如变异引入了不可综合的结构），则触发降级方案 **ApplyTextMutation**。

**降级方案（极少触发）**：回到原始 RTL 的文本层面，做更保守的字符串级替换（比如只改变注释、改名不影响综合的部分），确保总能生成一些变体。论文没有展开讲这个降级方案的具体细节，说明主路径（AST 变异）的综合通过率已经足够高。

### Step 7 之后：三层过滤与 73% 丢弃率是怎么来的

论文 Table 19 明确列出了增强设计的过滤标准。Step 7 的综合验证是第一层，后面还有两层：

```
AST 变异后的 RTL 变体（生成量大）

  │ 第一层：综合验证（Step 7）
  │ Synopsys DC 编译
  │
  ├── 综合失败 → 丢弃
  │   （组合环路、语法错误、不可综合结构）
  │
  ▼ 通过

  │ 第二层：结构相似度检查
  │ 网表级图结构比较
  │
  ├── 与源设计相似度 ≥ 97% → 丢弃（"伪变异"）
  │   例：AST 把 a & b 改成了 ~(~a | ~b)，综合出来还是同一个与门
  │
  ▼ 通过

  │ 第三层：训练价值评估
  │ 分任务判断
  │
  ├── 时序任务：关键路径太短、时序极其宽松 → 丢弃
  ├── 功耗任务：死逻辑比例太高、大部分门从不翻转 → 丢弃
  └── 通过 → 保留！

最终：约 27% 通过，73% 被丢弃
```

**为什么用网表比较而不是 RTL 比较来判断相似度？** 因为有些 AST 变异虽然改了代码文本，但综合工具会做逻辑优化，最终产生完全相同的门级电路（比如德摩根等价变换）。只有比较综合后的网表才能发现这种"伪变异"。

**97% 的阈值**是论文设定的经验值——相似度低于 97% 说明电路结构确实发生了实质性变化，值得保留。如果阈值设太低（比如 90%），可能漏掉真正的结构变体；设太高（比如 99%），可能保留大量近乎重复的设计。

### 为什么"路径长的难设计"对训练有帮助？—— 一个完整的因果链

在讲因果链之前，先搞清楚三个前置概念：**路径是什么、路径长短有什么影响、同一个 RTL 能不能搞出不同路径。**

#### 前置概念一：什么是"路径"？路径长短为什么影响时序？

数字电路里，信号从触发器出发，经过一堆组合逻辑门，到达下一个触发器，这条传播链叫一条**时序路径**：

```verilog
// 假设这段代码综合后：
always @(posedge clk) begin
    a <= x + y;        // FF1 输出 → 加法器
    b <= a * z;        // 加法器结果 → 乘法器
    c <= b ^ w;        // 乘法器结果 → 异或门
    q <= c | v;        // 异或结果 → 或门 → FF2 输入
end
```

信号从 FF1 到 FF2 经过：加法器 → 乘法器 → 异或 → 或门，4 级逻辑深度。这就是一条**路径长度为 4 级的时序路径**。

芯片有一个统一节拍器——时钟。论文工艺是 1GHz，时钟周期 = **1.0ns**。这意味着任何信号必须在 1.0ns 内从上游 FF 传到下游 FF。假设每级门约 0.2ns，加上连线延迟：

| 路径长度 | 估算延迟 | vs 1ns 周期 | WNS | 含义 |
|---------|---------|-----------|-----|------|
| 2 级门 | ~0.4ns | 轻松 | +0.6ns | ✅ 安全，大把余量 |
| 5 级门 | ~1.0ns | 刚好 | ~0ns | ⚠️ 卡线 |
| 8 级门 | ~1.6ns | 超时 | -0.6ns | ❌ 违例，跑不到 1GHz |

**结论：路径越长 → 信号传播延迟越大 → 越容易超过时钟周期 → WNS 越容易为负 → 时序违例。WNS = 可用时间 - 实际需要时间，负值就是"来不及了"。**

#### 前置概念二：同一个 RTL 真能搞出不同路径长度的后端吗？

**当然可以。这是 CircuitNet 3.0 数据增强的核心机制之一，有三种方式：**

**方式一：AST 变异直接改 RTL 的硬件结构**

```verilog
// 原始 RTL：路径 2 级门
assign c = (a + b) & d;      // 加法器 → 与门

// AST 变异把 & 改成 | + ^
assign c = (a + b) | (d ^ e); // 加法器 → 异或 → 或门，路径变成 3 级
```

加减乘除互换、比较器反转、位运算替换——每次变异都可能改变综合后的门级结构，从而改变路径长度。

**方式二：同一个 RTL 用不同综合约束，综合出不同的网表**

```verilog
// 相同的 RTL
assign p = a * b;        // 乘法器
```

综合工具可以选不同实现策略：

| 综合配置 | 策略 | 路径长度 | 功耗 | 门数 |
|---------|------|---------|------|------|
| 面积优先 | 串行进位乘法器 | **长**（多级进位链） | 低 | 少 |
| 时序优先 | 超前进位乘法器 | **短**（并行进位） | 高 | 多 |
| 默认 | Booth 乘法器 | 中等 | 中等 | 中等 |

同一个 `a * b`，面积优先配置综合出来的路径可能比时序优先长好几级。

**方式三：物理布局影响连线延迟**

即使网表完全相同，版图阶段：
- 门放得远 → 连线长 → 寄生 RC 大 → 路径延迟大
- 门放得近 → 连线短 → 延迟小
- 论文的 Innovus 迭代优化（密度 85%~95%，10-50 次迭代）就是在探索不同物理布局下的实际路径延迟。

#### 前置概念三："筛选路径长"到底筛的是什么？

不是在说"路径长就好"或者"路径短就不好"。**是在筛"时序紧张程度"**：

```
时钟周期 = 1ns

电路 A：路径短 → 延迟 0.3ns → WNS = +0.7ns → 时序非常安全  → ❌ 丢弃
电路 B：路径中等 → 延迟 0.9ns → WNS = +0.1ns → 勉强安全 → ✅ 保留
电路 C：路径长 → 延迟 1.3ns → WNS = -0.3ns → 时序违例   → ✅ 保留
```

论文保留的是 **B 和 C —— 濒临违例或已经违例的电路**，丢弃的是 A —— 怎么都安全的电路。

**路径长度是工程师用来选择"哪些样本值得进训练集"的筛选标准，不是直接喂给 AI 模型的特征。** AI 模型的输入是 RTL 文本和网表图，它学的是："看到 RTL 里有这种结构模式（连续几级乘法、大扇出、深嵌套）→ 最终 WNS 大概率是负的"。如果训练数据里全是电路 A 这种"绝对安全"的案例，模型遇到电路 C 就完全不会判断。

### 因果链：筛选"路径长"怎么帮助 AI 模型？

这是很多人的疑问："你筛出了路径长的电路，然后呢？这对 AI 有什么好处？" 用两组训练数据对比来说清楚：

**场景 A：不做过滤，自然收集的数据**

```
训练集里的电路：
  ┌────────────────────────────────────────────┐
  │ 电路1: WNS = +3ns   │███░░░░░░░░░░░░░░░░░ │ 时序非常宽松，轻松达标
  │ 电路2: WNS = +5ns   │█░░░░░░░░░░░░░░░░░░░ │ 大把余量
  │ 电路3: WNS = +2ns   │████░░░░░░░░░░░░░░░░ │ 没问题
  │ 电路4: WNS = -0.1ns │███████████████████░ │ 刚好差一点（极少出现）
  │ ... (99% 都是 WNS > 0 的设计)              │
  └────────────────────────────────────────────┘

用这个数据训练的 AI 学到了什么？
  → "给啥电路都往正数猜，基本不会错" 
  → 问题是：工业场景下关心的恰恰是那 1% 的违例案例
  → 遇到真正时序紧张的电路，模型要么猜错，要么过度乐观
```

**场景 B：CircuitNet 3.0 的任务导向过滤后**

```
训练集里的电路：
  ┌────────────────────────────────────────────┐
  │ 电路1: WNS = -3ns   │██████████████████████│ 严重违例！必须修
  │ 电路2: WNS = -1ns   │███████████████████░░ │ 轻微违例，要优化
  │ 电路3: WNS = 0ns    │███████████████████░░ │ 刚好卡线
  │ 电路4: WNS = +0.5ns │█████████████████░░░░ │ 勉强通过
  │ 电路5: WNS = -6ns   │██████████████████████│ 极端案例
  │ ... (WNS 均匀分布在 -6ns 到 0ns，各种难度的都有)
  └────────────────────────────────────────────┘

用这个数据训练的 AI 学到了什么？
  → "RTL 结构有 A/B/C 特征时，WNS 会变成 -2ns"
  → "RTL 结构有 X/Y/Z 特征时，WNS 能到 +0.5ns"
  → 模型学到了 RTL 特征 → 时序结果的真实映射关系
  → 遇到新设计时，能准确判断"这个会违规"还是"这个安全"
```

**核心逻辑链**：

```
筛选"路径长的难设计"作为训练样本
         │
         ▼
训练数据的 WNS 分布从"集中在 >0 的宽松区"
        变成"均匀覆盖 -6ns 到 0ns 的紧张区"
         │
         ▼
模型在训练时被迫学习"什么 RTL 结构会导致时序违例"
而不是偷懒学"所有设计都安全"
         │
         ▼
推理阶段 → 模型能准确识别真正有时序风险的设计
         → 触发早期 ECO，避免"画完版图才发现跑不动"
         │
         ▼
这就是 Shift-Left 的工程价值
```

**一个具体例子**：

```
不加过滤的训练：                  加过滤的训练：
"连了 20 级组合逻辑还加了         "连了 20 级组合逻辑 → WNS = -2ns ❌"
 大扇出负载？应该没问题            "连了 5 级组合逻辑 → WNS = +1ns ✅"
 吧..."（瞎猜，没见过违例）        "同样 20 级，扇出小的 → WNS = -0.5ns"
                                  "扇出大的 → WNS = -2ns" 
                                  → 模型学会了"大扇出是关键风险因子"
```

简单说：**如果训练数据里没有"病人"，医生就永远不会诊断疾病。CircuitNet 3.0 故意往训练集里塞"重症患者"，让 AI 学会识别"什么样的电路结构会导致时序问题"。**

##### 补充：为什么只做综合验证，不跑 testbench 功能仿真？

你可能会问：正常 ASIC 设计流程是先功能验证（testbench 仿真）再综合，为什么这里跳过了功能仿真？

这里有两个关键认知：

**1. AST 变异是故意改变功能的，不是保持功能等价**

| 变异 | 原始 | 变异后 | 功能变了？ | testbench 能过？ |
|------|------|--------|----------|---------------|
| `a + b` → `a - b` | 加法器 | 减法器 | ✅ 变了 | ❌ 必挂 |
| `a > b` → `a < b` | 大于比较 | 小于比较 | ✅ 变了 | ❌ 必挂 |
| `posedge` → `negedge` | 上升沿触发 | 下降沿触发 | ✅ 变了 | ❌ 必挂 |

这和传统软件测试思路完全不同。传统思路是"我改代码，跑测试保证行为不变"。但 CircuitNet 3.0 的思路是：**故意生成不同功能的电路，只要它能被综合工具编译成真实硬件，它就是一个结构多样化的有效训练样本。**

**2. 训练目标不是功能正确性，是时序/功耗预测**

AI 模型要学的是：*"这个综合出来门数多、路径长的电路，WNS 和功耗大概是多少"*。电路做的是加法还是减法、大于还是小于，对时序/功耗的影响是通过**结构特征**（门数、路径深度、扇出、开关活动）间接体现的。一个能综合通过的"加法器变减法器"，它的门级结构和功耗特征确实不同于原始加法器——这就够了，它为数据集贡献了**结构多样性**。

**3. 但原始设计确实做过功能仿真**

功能仿真只用在数据收集阶段（论文 Section 4.2）：

```
原始数据收集阶段：
  收集 RTL → 跑 testbench 功能仿真 → 保证原始 8,659 个设计功能正确

数据增强阶段（AST 变异）：
  对验证过的设计做变异 → 只跑综合验证 → 保证能做成硬件即可
  不跑功能仿真——因为变异后功能本来就变了
```

功能正确性由原始设计保证，增强设计负责提供**结构多样性**。两者合在一起，构成了 15,863 个"既根植于真实功能电路、又覆盖广泛结构空间"的训练样本。

## 2. Algorithm 3：赋值一致性强制算法

![Algorithm 3: 论文原图 — Assignment Consistency Enforcement 多数投票法](figures/algo3-assignment-consistency.png)

> **论文原图 Algorithm 3**：提取 always 块中所有赋值 → 统计 blocking/nonblocking 数量 → 若混用则以多数类型统一全部赋值。

论文专门用了一个算法来处理 Verilog 中一个非常微妙的问题。

### 2.1 问题：为什么 `=` 和 `<=` 混用是大忌？

```verilog
// ❌ 这是错的！专业 RTL 代码绝对不会这么写
always @(posedge clk) begin
    q1 =  d1;      // 阻塞赋值 —— 立刻生效
    q2 <= d2;      // 非阻塞赋值 —— 等到 always 块结束才生效
end
```

混用的后果：
- **仿真与综合行为不一致**：仿真器按顺序执行，综合器产生完全不同的硬件
- **竞态条件**：`=` 赋值后的新值立刻被后面的语句看到，`<=` 赋值要等到时钟沿结束
- **很多综合工具直接拒绝**

### 2.2 Algorithm 3 详解：多数投票统一法

```
Algorithm 3: Assignment Consistency Enforcement
Require: Always block A with assignments
Ensure:  Consistent assignment types

1:  assignments ← ExtractAssignments(A)
2:  blocking_count ← 0
3:  nonblocking_count ← 0
4:  for each assign in assignments do
5:      if assign is NonblockingSubstitution then
6:          nonblocking_count ← nonblocking_count + 1
7:      else if assign is BlockingSubstitution then
8:          blocking_count ← blocking_count + 1
9:      end if
10: end for
11: if blocking_count > 0 AND nonblocking_count > 0 then
12:     if nonblocking_count ≥ blocking_count then
13:         target_type ← nonblocking
14:     else
15:         target_type ← blocking
16:     end if
17:     ConvertAllAssignments(A, target_type)
18: end if
```

**逐步解释**：

**Step 1-3**：提取 always 块中所有赋值语句，初始化两个计数器。

**Step 4-9**：遍历所有赋值：
- 如果这条赋值是"被变异改成了非阻塞赋值"→ `nonblocking_count += 1`
- 如果这条赋值是"被变异改成了阻塞赋值"→ `blocking_count += 1`
- 如果本来就是一致的（没被变异改过类型），不计入（不属于变异引入的问题）

**Step 11**：关键判断 —— **只有当两种类型都有时才触发修复**（说明存在混用问题）。

**Step 12-16**：多数投票 —— 数量多的类型胜出：
- `nonblocking_count ≥ blocking_count` → 全部统一为 `<=`（非阻塞）
- 反之 → 全部统一为 `=`（阻塞）

**Step 17**：`ConvertAllAssignments` 执行转换，**递归处理**以下边缘情况（论文 Section C.3.3）：
- **嵌套 begin-end 块**：递归追踪所有嵌套层级的赋值
- **case 分支内的赋值**：`case` 的每个分支内如果有赋值也要纳入
- **if-else 条件赋值**：遍历所有分支路径
- **generate 块**：动态生成的赋值语句在 AST 级别分析

**为什么是多数投票而不是"全部改成非阻塞"？** 论文的解释（Section C.3.2）：
- 多数类型最可能代表设计者本意
- 最小化修改量（少数改多数，不是全部改一种）
- 转换过程保持逻辑行为不变

## 3. 六类变异算子的技术原理

![Table 3: 论文原图 — 六类 AST 变异算子概览](figures/table3-ast-mutation-operators.png)

> **论文 Table 3 概览**：Arithmetic / Logical / Relational / Temporal / Assignment / Constant 六类变异，每类列出算子、变换方式及约束条件。下文 Table 9 有更详细的逐项对照。

![Table 9: 论文原图 — AST Mutation Operators 完整详表](figures/table9-detailed-operators.png)

> **论文 Table 9 完整版**：每个变异算子的 Original → Mutated 映射及具体 Constraint。以下逐一分析各类算子的设计原理。

论文 Table 9 列出了完整的变异算子表。下面逐一分析每一类的设计原理：

### 3.1 算术变异（Arithmetic Operators）

| 原始 | 变异 | 约束 |
|------|------|------|
| `a + b` | `a - b` | 类型保持（同为算术） |
| `a - b` | `a + b` | 类型保持 |
| `a * b` | `a / b` | **静态分析除零** |
| `a / b` | `a * b` | 类型兼容 |
| `a % b` | `a + b` | 类型兼容 |

**为什么加减是双向的？** 论文的解释：加减互为逆运算，双向替换反映了常见的"设计替代方案"——同一个数据通路可以用加法器或减法器实现，只是控制信号不同。

**除法变异的特殊处理**：`a * b` → `a / b` 不是无条件执行的。论文用**静态分析**检查除数 `b` 的取值范围：
- 如果 `b` 是常量且可能为 0 → 拒绝这个变异
- 如果 `b` 是变量且无法证明非零 → 标记为"有风险"，降权
- 如果 `b` 是 `parameter` 且值为非零 → 允许

### 3.2 逻辑变异（Logical Operators）

| 原始 | 变异 | 约束 |
|------|------|------|
| `a && b` | `a \|\| b` | 布尔上下文 |
| `a \|\| b` | `a && b` | 布尔上下文 |
| `a & b` | `a \| b` | **位宽匹配** |
| `a \| b` | `a & b` | **位宽匹配** |
| `a ^ b` | `a & b` | **位宽匹配** |

**注意区分 `&&` 和 `&`**：
- `&&` 是逻辑与（结果 1 bit 的 0/1）→ 只能在布尔上下文中变异
- `&` 是位与（结果位宽等于操作数）→ 要求位宽匹配，比如 `a[7:0] & b[7:0]` 合法但 `a[7:0] & b[3:0]` 不合法

论文明确说了：**逻辑 AND/OR 之间的变异建模不同的决策逻辑实现方式**。位运算 AND/OR/XOR 之间的变异探索数据处理电路中常见的位操作替代策略。

### 3.3 关系变异（Relational Operators）

| 原始 | 变异 | 约束 |
|------|------|------|
| `a > b` | `a < b` | 操作数类型相同 |
| `a >= b` | `a <= b` | 操作数类型相同 |
| `a == b` | `a != b` | 类型兼容 |
| `a != b` | `a == b` | 类型兼容 |

论文说这是为了"**系统化探索 FSM 和控制路径中的决策边界变化**"。例如：

```verilog
// 原始 FSM 跳转条件
if (count > 10)  → next_state = IDLE;

// 变异后
if (count < 10)  → 完全不同的状态跳转行为
// 如果 count ≥ 10 变到 count < 10，整个控制流都变了
```

这类变异对控制逻辑丰富的设计（FSM、序列器）特别有效。

### 3.4 时序变异（Temporal Operators）

| 原始 | 变异 | 约束 |
|------|------|------|
| `@(posedge clk)` | `@(negedge clk)` | 仅在时序块内 |
| `q <= d` | `q = d` | always 块一致性 |

**边沿翻转（posedge ↔ negedge）** 的硬件影响：
- 上升沿触发的寄存器和下降沿触发的寄存器是不同的硬件单元
- 改变了时钟树设计和建立/保持时间关系
- 论文特别提到这对**接口电路**非常重要，因为很多接口协议（SPI、I2C）同时使用两种边沿

**赋值类型转换（<= ↔ =）** 的语义差异：
- `<=`（非阻塞）：所有右边的值在 always 块开始时"快照"，赋值在块结束时同时发生
- `=`（阻塞）：逐行顺序执行，上一行结果立刻影响下一行
- 论文限定**只在同一个 always 块内做一致性检查后统一修改**

### 3.5 常量变异（Constant Mutations）

| 原始 | 变异 | 约束 |
|------|------|------|
| `8'd10` | `8'd11` | 位宽保持 + 进制保持 |
| `8'd11` | `8'd10` | 同上 |
| `16'hFF` | `16'hFE` | 同上 |

**为什么只 ±1？** 论文解释：这探索的是参数空间中的"相邻设计点"。±1 的变化在硬件层面可能影响：
- 计数器阈值：计数 10 次 vs 11 次
- 分频系数：不同分频比对应不同功耗
- 条件比较边界：边界值差 1 可能在时序和功耗上产生可见差异

**约束：位宽保持 `8'dXX` 不能变成 `16'dXX`；进制保持，`'d`（十进制）不能变成 `'h`（十六进制），因为数值表示范围不同。**

## 4. AST 变异方法相比传统方法的优势

论文 Section C.1.1 列出了四大优势：

| 优势 | 含义 | 为什么重要 |
|------|------|-----------|
| **语法保证** | 所有变异结果一定符合 Verilog 语法规范 | 文本级方法（正则替换）经常产生语法错误，需要反复回退 |
| **语义感知** | 变异遵守作用域规则、类型约束、语言语义 | 不会把 wire 赋值改成 reg 赋值，不会跨 scope 引入变量 |
| **目标化变换** | 可以精确控制"只改哪一种节点" | 你可以说"只改所有算术运算，不动逻辑运算" |
| **设计意图保持** | 高层结构不变，只变底层实现细节 | 加法器变成减法器，但仍然是数据通路——大架构不变 |

**对比文本级方法的典型失败案例**：

```verilog
// 原始代码
assign sum = a + b;  // 想把 + 改成 -

// 文本级正则 /(+)/  →  "-" 的问题：
// 1. 注释 "// sum = a + b" 里的 + 也被改了 → 代码和注释不一致
// 2. 信号名 "data_plus_minus" 不受影响（但正则可能误匹配 _plus_）
// 3. 多行格式 "+ \n b" 的情况正则匹配不到

// AST 级操作：
// 只修改 Rvalue 节点的类型属性 XOR→XNOR，其他一切不动
// 不会误伤注释、不会漏掉多行格式、不会改变信号名
```

## 6. 总结：AST 变异为什么是论文的核心技术贡献

1. **不是简单的"代码改写"** —— 而是把编译器前端的完整技术栈（词法分析 + 语法分析 + 语法树操作 + 代码生成）引入到数据增强中。这是从"手工作坊"到"工业化流水线"的范式升级。

2. **三层质量保证**：AST 级别保证语法正确 → 一致性检查保证语义合法 → Design Compiler 综合验证保证可硬件实现。任何一层失败都不会产出"带病数据"。

3. **27% 的接受率来自三层过滤**：综合失败（不可实现）→ 结构过于相似（伪变异，网表级图比较相似度 ≥ 97% 的被丢弃）→ 训练价值低（时序任务丢弃短路径的、功耗任务丢弃死逻辑多的）。73% 的丢弃不是浪费，恰恰证明了筛选严格。更重要的是，保留"难案例"（路径长、时序紧张的电路）让 AI 模型在训练时被迫学习"什么 RTL 结构会导致时序违例"，而不是偷懒猜"所有设计都安全"——这正是工业场景下预测模型的核心价值。

4. **算法设计的工程智慧**：节点路径机制（Algorithm 2 的 Step 2）解决了"变异过程中 AST 结构变化导致引用失效"的核心工程问题；多数投票法（Algorithm 3）是处理 Verilog 赋值一致性的巧妙方案。
