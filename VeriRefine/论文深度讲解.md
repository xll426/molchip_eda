## 1. 一句话定位（30 秒理解论文做了什么）

**VeriRefine 在 LLM 生成 Verilog 之前，先让模型把"对规格的理解"写成一份可审计的中间表示 ASTF（Abstract Signal Transition Functions，抽象信号转移函数），经过 5 层审计确认理解无误后再生成 RTL；仿真失败时按"理解错误"或"编码错误"分类，并路由到不同模块定向修复。** 它不是在代码层面改 bug，而是在"模型读懂了规格没有"这个语义层面纠错。

## 2. EDA 阶段映射（①-⑰）

参照 [芯片流程.md](../芯片流程.md) 的 17 阶段标准编号：

| 阶段 | 覆盖 | 说明 |
|------|:---:|------|
| **① RTL 设计** | ✅ **核心** | ASTF 精化 + 从 ASTF 生成可综合 Verilog——框架的主输出阶段。H(s) 在生成代码前固定每个信号的逻辑风格、时钟域、复位行为，可综合性成为结构属性而非事后检查 |
| **② RTL 功能仿真** | ✅ **核心** | Verification & Debug 模块用 Icarus 仿真驱动定向修复——仿真失败被分类为"理解错误"（回 ASTF 修正）或"编码错误"（回 RTL 修正），最多 2 轮迭代 |
| **③ 逻辑综合** | ✅ 辅助 | Yosys 0.30+48 + OpenLane v1.0.2 + SkyWater sky130A PDK 验证可综合性并评估 PPA（面积/时序/功耗），不参与生成回路。综合通过率 > 95% |
| ④ 门级仿真 | ❌ | 不做 SDF 反标仿真，无法检测毛刺、建立/保持违例、X 传播 |
| ⑤ STA（静态时序分析） | ❌ | OpenLane 内部流经部分布局布线步骤以获取 PPA 数值，但不做 signoff 级 STA——不计算所有路径的 slack |
| ⑥ 形式验证 | ❌ | 不做 SAT/SMT 等价性证明。5 层审计是 LLM-based + 规则检查，不是形式验证——审计可能漏 subtle bugs |
| ⑦ 布局规划 Floorplan | ❌ | — |
| ⑧ 标准单元摆放 Placement | ❌ | — |
| ⑨ CTS（Clock Tree Synthesis，时钟树综合） | ❌ | — |
| ⑩ 布线 Routing | ❌ | — |
| ⑪ 后仿真 | ❌ | 无 SPEF（寄生 RC）信息 |
| ⑫ 物理验证 DRC + LVS | ❌ | — |
| ⑬ 签核 Signoff | ❌ | — |
| ⑭-⑰ 流片→制造→封装测试→芯片 | ❌ | — |

**覆盖率：3/17。** VeriRefine 是一套**作用于阶段 ① 的生成方法**，但把阶段 ② 的仿真从"事后验证"变成了"生成过程中的反馈驱动"，并通过阶段 ③ 的综合验证可综合性。核心创新在于：在生成任何 RTL 之前先验证"对规格的理解是否正确"——这是传统方法（Direct Generation、MAGE、VerilogCoder、ChipSeek）都没有做到的。

> ⚠️ VeriRefine 的"综合通过率 > 95%"仅基于 Yosys + SkyWater 130nm 教学 PDK。在先进工艺节点（7nm/5nm/3nm）下，可综合性的门槛更高（更复杂的设计规则、更多物理约束），ASTF 的 H(s) 结构是否能同样保证可综合性，论文未验证。

## 3. 输入 / 输出举例（数据类型/格式/最小具体示例）

### 3.1 输入（数据类型/格式/最小具体示例）

**输入**：纯自然语言设计规格，来自 RTLLM v2.0（50 题：算术/FSM/数据结构/控制逻辑）或 VerilogEval-Human v2（156 题：HDLBits 衍生，组合/时序多层级）。规格只描述行为意图，不含实现细节。

**端到端具体示例（RTLLM pulse_detect）**：

```
模块 pulse_detect 接收 1-bit data_in 和时钟 clk，
当 data_in 出现 0→1→0 脉冲时，data_out 在脉冲的最后一周期输出 1。
时序示例：data_in = 01010 对应 data_out = 00101。
```

**隐含歧义**："最后一周期"没有明确区分"该周期内"还是"结束后"。所有 Direct Generation baseline 模型都理解为"结束后"——输出延迟一拍，两个模型犯相同的理解错误。这种歧义在芯片验证中是致命的（见第 8 章）。

**额外输入**：规格中可解析的表格数据（Karnaugh 图、真值表、MUX 选择表）被解析器提取后作为权威事实注入 prompt。ITB 仅从规格生成，不使用参考 RTL 或官方 testbench。

---

### 3.2 输出（内容/格式/具体示例）

VeriRefine 的输出分两级：**中间产物 ASTF**（每个被驱动信号一份 JSON，是本文的核心贡献）与**最终产物 RTL**（通过审计与仿真的可综合 Verilog）。下面以第 3.1 节的同一个例子 `pulse_detect` 贯穿说明。

#### 3.2.1 ASTF 输出（pulse_detect 的 data_out 信号，JSON）

```json
{ "signal_name": "data_out",
  "hardware_type": { "logic_style": "combinational", "clock_domain": null, "reset_behavior": null },
  "guarded_commands": { "commands": [
    { "gca_expression": "state == S1 && data_in == 0 : data_out = 1",
      "spec_citation": "The indicating signal dataout is 1 at the end cycle of the pulse" },
    { "gca_expression": "!(state == S1 && data_in == 0) : data_out = 0",
      "spec_citation": "returns to 0 until the corresponding pulse appears again" }
  ] }
}
```

**关键**：`logic_style: "combinational"` —— data_out 不在时钟沿更新，在 `state==S1 && data_in==0` 成立的**同一拍**就输出 1。Direct Generation 两个模型都将其放入时钟块导致输出延迟一拍——H(s) 在 ASTF 阶段就固定了这个时序决策。

#### 3.2.2 其他输出

- **Verilog RTL**：H(s) 决定 always 块类型（`always @(posedge clk)` 或 `assign`），G(s) 优先级链直接映射为 if/else if
- **5 层审计报告**：Soundness/Completeness/Consistency/FSM Integrity/Core RTL Design Rules，逐条标注违规
- **失败分类**：ASTF Issue（理解错误）或 RTL Issue（编码错误），附根因解释和修复提示
- **PPA 报告**：Yosys 综合 + OpenLane 布局布线后的面积/时序/功耗

## 4. 方法与架构

### 4.1 整体流程图（三模块协作 + "渐进精化"循环）

```
                      NL Specification
                            │
               ┌────────────▼────────────┐
               │  Module 1: Refinement    │
               │  ┌──────────────────┐    │
               │  │ ASTF Generation   │◄───┤ 审计失败→定向修复反馈
               │  │ (关键词分类→Prompt│    │ "只修报告的错误，保留
               │  │  组装→LLM 生成)    │    │  其余合法信号定义"
               │  └────────┬─────────┘    │
               │           ▼              │
               │  ┌──────────────────┐    │
               │  │ Schema Validation │    │  形式错误→机械拒绝 (零LLM调用)
               │  └────────┬─────────┘    │
               │           ▼              │
               │  ┌──────────────────┐    │
               │  │ 5-Layer Audit     │────┘
               │  └────────┬─────────┘
               │           │ 通过
               │    Verified ASTF (JSON)
               └───────────┬────────────┘
                           │
               ┌───────────▼────────────┐
               │  Module 2: Implementation│
               │  ASTF → RTL Generation   │
               │  7 条编码规则 + iverilog  │
               │  编译检查（违反→重新生成） │
               │  H(s)→always块类型       │
               │  G(s)→if/else if 链      │
               └───────────┬────────────┘
                           │
               ┌───────────▼────────────┐
               │  Module 3: Verification │
               │         & Debug          │
               │  ┌──────────────────┐    │
               │  │ ITB Generation    │    │  仅从Spec生成(不含参考RTL)
               │  └────────┬─────────┘    │
               │           ▼              │
               │  ┌──────────────────┐    │
               │  │ Icarus Simulation │    │
               │  └────┬──────┬──────┘    │
               │   通过  │      │ 失败      │
               │    ▼    │      ▼          │
               │  Final  │ Failure Analyzer│
               │  RTL ✅ │ ┌──────┴──────┐ │
               │         │ │ ASTF Issue?  │─┤─ 回 Module 1 (改理解)
               │         │ │ RTL Issue?   │─┤─ 回 Module 2 (改代码)
               │         │ │ 最多2轮迭代  │ │
               │         │ └─────────────┘ │
               └─────────┴─────────────────┘
```

**渐进精化机制**：规格从"一段英文"逐信号展开为 H(s)+G(s)——粗到细。审计失败的 ASTF 不丢弃，带具体违规描述返回定向修复（保留合法部分）。仿真失败按根因路由——理解错了改 ASTF，代码错了改 RTL。避免在代码层反复修一个根因在理解层的 bug。

### 4.2 核心模块详解

#### ASTF 形式化定义

对每个被驱动信号 $s$（规格为 $S$）：

$$
ASTF(s) = \langle H(s),\ G(s) \rangle
$$

- $s$：一个被驱动信号（RTL 中出现在赋值左侧的信号）
- $S$：该信号对应的自然语言规格片段
- $H(s)$：实现类别（header）——逻辑风格、时钟域、复位行为
- $G(s)$：优先级有序的守卫动作列表

- **$H(s)$ — 实现类别**：逻辑风格（combinational/sequential/latch）、时钟域、复位行为（同步/异步/无）。三个字段有条件约束——combinational 必须 leave clock/reset 为 null，sequential/latch 必须命名时钟域。这足以让 Implementation 模块不需要查任何其他信号就能确定 always 块的 header。

- **$G(s) = \{(c_i, a_i, \sigma_i)\}_{i=1}^{n}$ — 优先级有序的守卫动作列表**：
  - $c_i$：布尔守卫条件，仅引用 ASTF 中已声明的信号（不引用未声明或外部状态）
  - $a_i$：当 $c_i$ 为真时对 $s$ 的赋值
  - $\sigma_i \subseteq S$：出处（provenance），逐字从原始规格复制的句子，共同证明 $(c_i, a_i)$ 的合法性
  - **优先级语义**：从 $i=1$ 到 $n$ 评估，首个满足的 $c_i$ 决定 $s$ 的值——等价于 RTL 的 `if/else if` 链语义。使用优先级有序而非无序列表，避免了重叠 guard（如复位和 valid 输入同时到达）时的歧义。

#### ASTF 生成：Prompt 组装的四要素

Prompt 组装四要素：(1) 基础段——固定输出纪律（先接口、逐信号分类、每条命令带规格引文）；(2) 子类型规则段——15 种设计模式（FSM/双时钟/计数器/FIFO/移位器/流水线等）关键词扫描 + 对应结构规则，主类型按 FSM→双时钟→时序→组合固定优先序；(3) 示例段——1~2 个完整 "规格→ASTF" 配对；(4) 权威事实段——K-map/真值表解析注入，解析器也支持一致性审计所以模型收到与后续被检查的事实永远不矛盾。

**设计意图**：ASTF 生成阶段不受 Verilog 语法约束，LLM 专注"这个信号该是什么行为"，分类+示例+权威事实减少 LLM "脑补"空间。

#### ASTF Schema（闭包 JSON Schema）

闭包 JSON schema（Draft 2020-12），禁止未声明字段。jsonschema 验证器在零 LLM 调用下机械拒绝形式错误。结构：module_name + optional parameters + input/output/internal 三组信号。输入仅需声明；output/internal 必须带 hardware_type 和 guarded_commands。位宽支持字面量或表达式如 WIDTH-1。FSM 设计额外提供 state_transition_table + fsm_meta。

**分工**：形式错误（缺字段、类型错）由 schema 零 token 捕获；语义错误（漏行为、幻觉）进审计。Implementation 模块因此获得"输入结构必然合法"的硬保证。

#### 5 层审计

| 层 | 名称 | 检查什么 | 防什么错误 |
|----|------|---------|-----------|
| 1 | Soundness（健全性） | 每条 spec_citation 在原始规格中能找到逐字匹配 | LLM 脑补规格没要求的"合理"行为 |
| 2 | Completeness（完整性） | 规格中每个端口/行为是否都有 G(s) 条目覆盖 | 漏掉边缘行为 |
| 3 | Consistency（一致性） | 信号间矛盾假设；模块名/位宽一致；与 K-map/真值表/波形/边界索引一致 | 信号间逻辑矛盾 |
| 4 | FSM Integrity | 状态骨架完整性（fsm_meta 一致、状态寄存器声明、复位态在表中）；转移完整性（每状态有出边、无不可达、二进制输入两分支都覆盖）；复位规则；输出类型一致性（Moore 输出不读输入）；输出时序（单周期指示器保持 Moore、未寄存）；序列/帧模式时序检查 | 死状态、挂起输入、复位泄露、Mealy 行为被错误实现为 Moore、off-by-one 输出时序 |
| 5 | Core RTL Design Rules | 时序/组合分离（schema 强制执行）；赋值符匹配风格（`<=` for sequential, `=` for combinational/latch）；组合逻辑覆盖所有输入情况（小空间穷举、大空间互补对分析）；无组合依赖环（读依赖图环检测） | 混合 always 块、仿真-综合 mismatch、意外锁存推断、电不稳定反馈 |

#### Implementation Module

核心洞察：LLM 不再需要从 NL "理解"设计，只需将 ASTF 机械翻译为 Verilog。H(s) 决定 always 块类型，G(s) 优先级链直接映射为 if/else if。7 条编码规则：port contract（端口与 ASTF 完全一致）、self-contained module（无外部子模块实例化）、style fidelity（`<=` / `assign` 由 H(s) 决定）、GCA fidelity（逐字翻译不重新推导）、startup definedness（无复位寄存器 initial 赋 X）、no internal tri-state（除非规格显式要求）、standalone compilability（iverilog 编译，失败则重新生成）。

#### Verification & Debug Module

**ITB（Internal Testbench，内部测试平台）**：仅从规格生成，不使用参考 RTL 或官方 testbench——避免测试偏向候选 RTL。流程：规格 → LLM 生成 schema 约束验证计划 → SystemVerilog 刺激模块 → 确定性装配 harness。每个场景含 8~15 周期显式序列 + 伪随机压力（组合 80/时序 200 周期）。

**Failure Analyzer**：接收规格 + 压缩 ASTF + 仿真日志（pass/fail、mismatch 计数/时间、期望 vs 实际值、mismatch 时刻内部信号状态）。输出结构化决策——ASTF Issue（理解错误→回 Module 1）或 RTL Issue（编码错误→回 Module 2），附根因解释和修复提示。最多 2 轮迭代。

## 5. 关键公式

**PPA 综合指标**（乘积形式，三维度同等重要。越小越好）

$$
PPA = (P_{int} + P_{sw} + P_{leak}) \times A \times T_{cp}
$$

- $P_{int}$：内部功耗（$\mu W$，典型工艺角）
- $P_{sw}$：开关功耗（$\mu W$）
- $P_{leak}$：泄漏功耗（$\mu W$）
- $A$：芯片面积（$mm^2$）
- $T_{cp}$：关键路径延迟（$ns$）

## 6. 训练与实验设置

### 6.1 是否需要训练

**不需要训练。** VeriRefine 直接使用 Claude Sonnet 4.6 API（主实验）和 GPT-4 Turbo（对比实验），不做任何模型微调。所有能力来自 ASTF 中间表示 + 三模块 Agentic 架构 + 5 层审计机制。论文中的 "VeriRefine-Direct" 对应跳过 debug loop 的纯 ASTF 生成（即只使用 Refinement + Implementation 模块）。

### 6.2 实验设置

**Benchmark**：
- RTLLM v2.0：50 道题（算术、FSM、数据结构、控制逻辑），包含 PPA 参考值
- VerilogEval-Human v2：156 道 HDLBits 衍生题

**Baseline**：
- Direct Generation（Claude Sonnet 4.6 和 GPT-4 Turbo 的单次生成）
- VerilogCoder（GPT-4 Turbo，多 Agent 框架，作为 SOTA 对比）

**评估指标**：
- 功能正确性：testbench 仿真全部通过的比例
- 可综合性：Yosys + OpenLane 综合通过率
- PPA：面积 × 时序 × 功耗的乘积指标
- Token 成本：总 token 消耗（与 VerilogCoder 对比）

**消融设计**（Figure 7）：
- iter0（VeriRefine-Direct，纯 ASTF 生成，无 debug loop）
- iter1（第 1 轮 debug 修复后）
- iter2（第 2 轮 debug 修复后）

### 6.3 关键实验结果

**功能正确性**：

| Benchmark | VeriRefine | Direct Generation | 提升 |
|------|:---:|:---:|:---:|
| RTLLM v2.0 | **94.0%** | 64.0% | **+30.0 pp** |
| VerilogEval-Human v2 | **98.1%** | 85.3% | **+12.8 pp** |

**这张表说明什么**：VeriRefine 在两个 benchmark 上均显著超越 Direct Generation。RTLLM v2.0 上的 30 个百分点提升尤其显著——RTLLM 题目更复杂、规格歧义更多，ASTF 的语义精化优势更明显。

**Token 成本对比**：

| 方法 | 相对 Token 成本 | VerilogEval 总 token |
|------|:---:|:---:|
| VerilogCoder | 4× | 30.5M |
| **VeriRefine** | **1×** | **8.1M** |

**这张表说明什么**：VeriRefine 在功能正确率接近 VerilogCoder（98.1% vs 99.4%，仅差 2 题）的同时，token 消耗仅为其 1/4。每个正确设计的 token 成本为 54K vs 197K，约 3.7 倍效率。

**可综合性**：

| 方法 | 综合通过率 |
|------|:---:|
| Direct Generation | < 80% |
| **VeriRefine** | **> 95%** |

**消融实验（Figure 7，RTLLM v2.0）**：
- iter0（纯 ASTF）：82.0%（贡献 18/30 = 60% 的提升）
- iter1（第 1 轮 debug）：88.0%（+3 题）
- iter2（第 2 轮 debug）：94.0%（+3 题）

**这张表说明什么**：ASTF 精化贡献了 60% 的提升（18/30），debug loop 贡献 40%（12/30）。说明"先验证理解"是主要增益来源，而 debug 阶段提供增量修正。最多 2 轮迭代限制意味着无法收敛的设计会被放弃。

**pulse_detect 案例**：Direct Generation（Claude Sonnet 4.6 + GPT-4-turbo）两个模型均将 `data_out` 在脉冲结束后的下一周期输出——同一个时序理解错误（off-by-one）。VeriRefine 的 ASTF 将 `data_out` 声明为 combinational，同一周期输出，完美匹配规格。

## 7. 创新点

### 创新点 1：ASTF — 首个带出处追踪的 per-signal 中间表示

已有 IR（AoT-RTL、ComplexVCoder GIR、QiMeng-CRUX CRUX）是一次性生成、不经验证就喂给 RTL 生成。ASTF 独有的：(a) per-signal 粒度——错误不跨信号传播；(b) 出处追踪——每条行为声明带原规格逐字引文 $\sigma_i$，审计器从源头验证而非信任 LLM 记忆；(c) 优先级语义——G(s) 列表顺序直接对应 RTL if/else if 链，消除 IR 到代码的语义间隙。

### 创新点 2：将规格精化视为可验证的独立生成阶段

Direct Generation 和已有 Agentic 框架（VerilogCoder、MAGE、VeriOpt）的循环是"生成代码→仿真失败→修改代码"——隐含假设"模型理解对了，只是代码写错了"。但 pulse_detect 案例证明：两个 baseline 模型犯**同一个理解错误**（时序偏移 1 拍），在代码层面修再多也不会触及根因。VeriRefine 是首个在生成 RTL 前单独验证"理解是否正确"的框架。

### 创新点 3：按抽象层次路由修复

MAGE 将所有仿真失败统一路由回 RTL 修复；ChipSeek 用 RL 隐式学习。VeriRefine 的 Failure Analyzer 分类为"ASTF 错"或"RTL 错"并路由到不同模块——修复定向而非重复。

### 创新点 4：可综合性是结构属性

H(s) 在代码生成前就固定逻辑风格/时钟域/复位行为——combinational 不会有 always 块，sequential 不会丢失时钟域。典型不可综合错误（混合 always 块、锁存推断、多驱冲突）在设计层被排除。综合通过率 95%+。

### 创新点 5：Token 效率——SOTA 水平 1/4 成本

vs VerilogCoder：VerilogEval-Human v2 上 98.1% vs 99.4%（仅少 2 题），token 8.1M vs 30.5M，每个正确设计 54K vs 197K——**3.7 倍效率**。同等 token 预算下 VerilogCoder 只能尝试约 42/156 题。

## 8. EDA 缩写解释

| **PPA** | Power, Performance, Area | 功耗/性能/面积——芯片设计三大核心指标，本文用乘积形式 $P \times A \times T_{cp}$ 综合评估 |
| **FSM** | Finite State Machine | 有限状态机——时序电路的核心设计范式，VeriRefine 的第 4 层审计专门验证 FSM 完整性 |
| **PDK** | Process Design Kit | 工艺设计套件——本文使用 SkyWater sky130A 130nm 开源 PDK |

| **STA** | Static Timing Analysis | 静态时序分析——纯数学计算所有路径延迟，验证时序闭合（本文未使用） |

| **HDL** | Hardware Description Language | 硬件描述语言——Verilog 和 VHDL 的总称 |

## 9. 与芯片流程的关系

### 9.1 VeriRefine 作用于哪个环节

核心贡献集中在 **① RTL 设计**——从根本上改变了 RTL 生成方式：传统方法让 LLM 同时承担"理解规格"和"写正确代码"两个交织任务；VeriRefine 将它们分离为 ASTF 精化（可审计的理解阶段）和 ASTF→RTL（确定性翻译阶段），并通过 ② 仿真反馈驱动 ASTF/RTL 修复，③ 综合验证可综合性+PPA。

### 9.2 痛点：规格不完整/有歧义为什么在芯片验证中致命

芯片验证是分层的——RTL 仿真（②）抓逻辑 bug、门级仿真（④）抓毛刺和 X 传播、STA（⑤）算时序、形式验证（⑥）证综合未改错逻辑、后仿真（⑪）抓走线串扰。但所有验证有一个**共同盲区**：都不验证"RTL 是否实现了你脑子里想要的设计"。形式验证证明 RTL 和网表等价，但不证明 RTL 和"你的设计意图"等价。

如果 RTL 设计阶段（①）的规格理解就有错——例如 pulse_detect "最后一周期输出 1"被理解为"下一周期输出 1"——那么一旦通过 ②，阶段 ③/④/⑤/⑥ 全部**无法**发现这个语义错误（它们只检查结构合法性或等价性）。错误潜伏到后续阶段才发现，修改成本将大幅上升。

VeriRefine 的对策：在生成代码前先验证理解——"规格精化"从 LLM 不可见的内部推理变成可逐条审计的显式过程。pulse_detect 案例：ASTF 将 data_out 声明为 combinational → 同一拍输出；Direct Generation 错误地放入时钟块 → 延迟一拍——两类 baseline 模型犯相同的理解错误。

### 9.3 VeriRefine 不覆盖什么

不涉及 ④ 门级仿真、⑤ STA、⑥ 形式验证、⑦~⑰ 物理设计到流片。PPA 评估使用 Yosys+OpenLane 真实综合流程但基于教学级 130nm PDK。不处理多模块/SoC 级设计。ASTF 审计是 LLM-based + 规则检查而非形式验证——可能漏 subtle bugs。

## 10. 讨论与局限

### 10.1 论文自述局限

**(1) ASTF 审计不完备**：5 层审计是 LLM-based + 规则检查，非形式验证。serial2parallel 失败——output valid 可在第 8 位周期或下一周期断言，两种解读都"忠实于规格"——审计只检查忠实度而非唯一性。

**(2) 规格缺陷无解**：6 个未解决设计中 4 个是规格缺陷（radix2_div/freq_divbyeven/Prob099/serial2parallel）。VeriRefine 忠实于规格，而规格本身有缺陷。ITB 通过了 radix2_div 和 Prob099，证明缺陷在规格-testbench 之间而非生成的 RTL。

**(3) 模型依赖性**：Claude Sonnet 4.6 上 VeriRefine-Direct 82.0%，GPT-4-turbo 上仅 68.0%——backbone LLM 能力是框架效果上限。

**(4) ITB 不替代 benchmark testbench**：ITB 也是 LLM 生成，可能继承同样理解偏差。

### 10.2 额外分析

**(1) "渐进精化"的实际运行是循环而非线性**。Ablation（Figure 7）：iter0（ASTF alone）= 82.0%；iter1（第 1 轮 debug）= 88.0%（+3 题）；iter2（第 2 轮）= 94.0%（+3 题）。VerilogEval: iter0=91.7% → iter1=96.2%（+7 题）→ iter2=98.1%（+3 题）。ASTF 贡献 60%（18/30），debug loop 贡献 40%（12/30）。最大 2 轮迭代限制意味着无法收敛的设计（Prob149 gshare 分支预测器——常数级 mismatch 签名表明稳定理解错误）会被放弃。

**(2) 与 VerilogCoder 的 3.7 倍效率差异**：不是模型能力问题，而是 agent 架构设计差异。VerilogCoder 三个 agent 间传递完整设计历史上下文；VeriRefine 的 ASTF 作为显式中间产物，每次 LLM 调用上下文更聚焦、无冗余历史。

**(3) "可综合性是结构属性"在 benchmark 中尚未充分体现**。Table 4 显示 Synthesizability 在 Direct 和 VeriRefine 间差异不大（93.8%~100% 窄带）——benchmark 规模有限，结构性不可综合错误本不高发。该创新点价值需在复杂设计中验证。

**(4) 未来方向的根本性意义**："框架应质疑规格，检查内部一致性并标记矛盾句、欠定行为和强制假设"。当前 VeriRefine 信任规格——如果未来能反过来改进规格质量，LLM RTL 生成的上游瓶颈就被打通。这与 NL2Silicon [12] 发现一致：表示形式选择（而非模型选择）主导了成功率（3%~88% 跨度）。

**(5) ASTF 作为设计文档的价值**：每条行为声明有原文出处，设计评审可逐条追溯"这个 if 对应规格哪句话"。在 safety-critical 芯片设计中这可能比功能正确率更有价值——但论文未涉及。

## 12. 一分钟复述版

VeriRefine 的真正贡献不在于又提了一个 agentic 框架，而在于**把 RTL 生成中"理解规格"这一步从 LLM 黑盒推理变成可审计、可修复的显式过程**——代价是多轮 LLM 调用，换来的是理解错误在生成代码前被拦截，以及 3.7 倍 token 效率的结构性优势。

---

> **实验核心数据速查**：RTLLM v2.0 功能正确率 94.0%（Direct 64.0%，+30.0%）；VerilogEval-Human v2 98.1%（Direct 85.3%，+12.8%）；综合通过率 95.7%/98.7%；Ablation——audited ASTF (VeriRefine-Direct) 贡献 18.0/30.0 = 60% 的提升，debug loop 贡献 12.0/30.0 = 40%；Token 成本 3.0M/8.1M vs VerilogCoder 22.7M/30.5M；PPA 与 VerilogCoder 持平（RTLLM: 4.052e-03 vs 5.046e-03, VerilogEval: 3.321e-04 vs 3.300e-04）。
