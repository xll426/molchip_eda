# RTLFixer 论文深度讲解

> 论文：RTLFixer: Automatically Fixing RTL Syntax Errors with Large Language Models
> 作者：YunDa Tsai, Mingjie Liu, Haoxing Ren (NVIDIA)
> 会议：DAC 2024 (61st ACM/IEEE Design Automation Conference)
> arXiv：2311.16543v3
> 代码：github.com/NVlabs/RTLFixer

---

## 1. 一句话定位

**RTLFixer** 是 NVIDIA 提出的一种将 LLM 变成"自主调试代理"的自动化 Verilog 语法修复框架。它把 **ReAct 提示工程**（Reasoning + Acting 交替推理）和 **RAG 检索增强生成**（基于人工专家纠错经验库）结合起来，让 GPT-3.5/GPT-4 像一个有经验的 RTL 工程师一样，与 Icarus Verilog / Quartus 编译器进行多轮交互，自动定位并修复 LLM 生成代码中的语法错误。

核心数据：
- 在自建的 **VerilogEval-syntax** 数据集（212 个错误实现）上达到 **98.5%** 的语法修复率
- VerilogEval-Machine pass@1 提升 **+32.3%**，VerilogEval-Human pass@1 提升 **+10.1%**
- RTLLM 基准上语法成功率从 73% → 93%
- 仅靠语法修复就能让 pass@1 大幅提升，说明 LLM 生成 Verilog 的错误里 **约 55% 是语法错误**（远超逻辑/仿真错误）

## 2. EDA 阶段映射（①-⑰）

参照 [芯片流程](../芯片流程.md) 的 17 阶段标准编号。RTLFixer 定位于 RTL 生成后的语法修复环节。

| 阶段 | 覆盖 | 说明 |
|------|:---:|------|
| **① RTL 设计** | ✅ **核心** | 接收 LLM 生成的（含语法错误）Verilog 代码，输出语法正确的 Verilog |
| **② RTL 功能仿真** | ✅ **核心** | 通过 Icarus Verilog（iverilog）编译反馈驱动多轮修复；后期用 Quartus Prime 商业编译器增强反馈质量 |
| ③ 逻辑综合 | ❌ | 不涉及——RTLFixer 只保证编译通过，不评估可综合性 |
| ④ 门级仿真 | ❌ | 不涉及 |
| ⑤ STA | ❌ | 不涉及 |
| ⑥ 形式验证 | ❌ | 不涉及——RTLFixer 用编译错误驱动修复，不做逻辑等价性检查 |
| ⑦-⑰ | ❌ | 不涉及物理实现及后续阶段 |

**覆盖率：2/17。** RTLFixer 仅覆盖 RTL 设计语法层 + 编译验证——解决的是"代码能编译通过"的问题，不涉及"编译后逻辑对不对""能综合吗""时序收敛吗"。

## 3. 输入/输出

### 3.1 输入

**(1) 含语法错误的 Verilog 代码**（来自 LLM 生成或人工编写）：

```verilog
module top_module (
    input wire clk,
    input wire [7:0] in,
    output wire [7:0] out
);
    always @(posedge clk) begin
        out <= in + 1;  // 语法错误：out 声明为 wire，不能用在 always 块左侧
    end
endmodule
```

**(2) 编译器错误日志**（Icarus Verilog 或 Quartus Prime）：

```text
main.v:15: error: out is not a valid l-value in top_module.
main.v:22: error: Index cannot fall outside the declared range for vector 'data'.
```

**(3) RAG 知识库**（人工专家指导，按错误类别索引）：共 iverilog 30 条 + Quartus 45 条。

### 3.2 输出

**(1) 语法正确的 Verilog 代码**（编译通过，可进入仿真）：

```verilog
module top_module (
    input wire clk,
    input wire [7:0] in,
    output reg [7:0] out   // 修复：wire → reg
);
    always @(posedge clk) begin
        out <= in + 1;
    end
endmodule
```

**(2) 编译通过状态**：Icarus Verilog / Quartus Prime 返回无错误。

## 4. 方法与架构

### 4.1 总体架构

框架由三大核心组件构成：

```
┌────────────────────────────────────────────────────┐
│                  RTLFixer                          │
│                                                    │
│   ┌─────────┐      ┌──────────┐      ┌─────────┐  │
│   │   LLM   │◄────►│   ReAct  │◄────►│   RAG   │  │
│   │(GPT-3.5)│      │(思考-行动)│      │(检索库) │  │
│   └────┬────┘      └─────┬────┘      └────┬────┘  │
│        │                 │                │        │
│        ▼                 ▼                ▼        │
│   生成/修改代码      调用工具        检索专家经验    │
│        │                 │                │        │
│        └────────────────►├◄───────────────┘        │
│                          │                         │
│                          ▼                         │
│                  ┌──────────────┐                  │
│                  │  iverilog/   │                  │
│                  │  Quartus     │                  │
│                  └──────────────┘                  │
└────────────────────────────────────────────────────┘
```

### 4.2 系统提示词（System Prompt）

RTLFixer 采用两类提示词模板：

**(a) One-shot 提示词模板**（基线对比用）：
- System Prompt：指示 LLM 实现 Verilog 模块
- Problem Description：自然语言设计描述
- Erroneous Implementation：错误代码
- Feedback：单轮编译器错误日志

**(b) ReAct 提示词模板**（核心方法）：

```
Solve a task with interleaving Thought, Action, Observation steps.
Thought can reason about the current situation, and Action can be the
following types:
(1) Compiler[code], which compiles the input code and provide error
    message if there is syntax error.
(2) Finish[answer], which returns the answer and finished the task.
(3) RAG[logs], input the compiler log and retrieve expert solutions to fix
    the syntax error.
```

LLM 在每一轮必须输出 Thought（推理）和 Action（行动），观察（Observation）则来自环境反馈。

### 4.3 ReAct 自主调试循环

RTLFixer 将 LLM 视作"自主代理"，执行如下循环：

1. **Thought**：LLM 思考当前错误的原因
2. **Action**：选择三种动作之一
   - `Compiler[code]`：调用编译器编译并返回错误日志
   - `RAG[logs]`：以错误日志为查询从知识库检索专家指导
   - `Finish[answer]`：输出最终修复后的代码
3. **Observation**：环境（编译器/检索器）返回结果
4. 重复最多 10 轮，直到选择 Finish 或达到上限

这种"思考-行动-观察"的交错结构让 LLM 拥有 **显式的推理过程**，而不仅仅是"输入→输出"的隐式映射。

### 4.4 RAG 检索增强

**(1) 知识库构建**：
- 对编译器的错误日志按错误标签分类
- 人工为每类错误撰写"专家指导"（Human Expert Guidance）
- iverilog：7 个常见错误类，30 条条目
- Quartus：11 个常见错误类，45 条条目

**(2) 知识库示例**：

错误 1：
```
Compiler Logs:
Object 'clk' is not declared. Verify the object name is correct.

Human Expert Guidance:
Check if 'clk' is an input. If not, and if 'clk' is used within the
module, make sure the name is correct. If it's meant to trigger an
'always' block, replace 'posedge clk' with '*'.
```

错误 2：
```
Compiler Logs:
Index cannot fall outside the declared range for vector

Human Expert Guidance:
Carefully examine the index values to prevent encountering 'index out
of bound' errors in your code. When utilizing parameters for indexing,
try to use binary strings for performing the indexing operation
instead.
```

**(3) 检索方式**：实验中采用 **精确匹配错误标签** 的简单方式（错误类别数有限，无需复杂向量检索）。实际工程中也可使用模糊匹配或向量数据库。

### 4.5 与 SelfDebug 的关键区别

| 维度 | SelfDebug | RTLFixer |
|------|-----------|----------|
| 语言 | 通用（Python 优先） | 专注 Verilog/RTL |
| 反馈来源 | 仅执行结果 | 编译器 + 人工专家库 |
| 推理机制 | 简单自反思 | ReAct 多步推理 + 工具调用 |
| 检索增强 | 无 | RAG + 专家知识库 |
| 目标 | 通用代码调试 | 专攻语法错误修复 |
| 自主代理能力 | 弱 | 强（多工具协同） |

### 4.6 一个完整的 ReAct 调试轨迹示例

论文 Figure 2(c) 给出了一个具体的 ReAct 轨迹，下面把它展开：

**Thought 1**：LLM 分析当前模块，识别任务为"在字节流中搜索消息边界"的有限状态机。

**Action 1: Compiler**：调用编译器对初始代码做编译。

**Observation 1**：
```
main.v:15: error: out is not a valid l-value in top_module.
```

**Thought 2**：LLM 推理得到错误根因是"out 被声明为 wire，但代码在 always 块中对其赋值，需要改为 reg"。

**Action 2: RAG["..not a valid l-value.."]**：以错误信息为查询，从知识库检索相关指导，命中条目 "Use assign statements instead of always block if possible."。

**Action n: Finish**：LLM 综合 Thought 1/2 与 Observation 1/2 后输出修订后的代码，结束流程。

这个轨迹体现了 RTLFixer 的三个关键优势——**推理显式化、工具可组合、知识可外挂**。

### 4.7 简单规则后置修复器（Simple Syntax Fixer）

在所有 LLM 输出上都会先经过一个"基于规则的语法修复器"，处理诸如 `timescale 指令位置错误`、`include 路径错误` 等简单的可模式化错误。这一步不消耗 LLM 调用，作用是让 LLM 集中精力处理更复杂的语法问题。

### 4.8 失败模式与启发式

论文通过失败案例分析（Figure 6）总结了 LLM 在 Verilog 上的典型困难：

1. **算术索引计算错误**：例如 `((i-1) & 15)*16 + j` 的循环展开超出数组范围
2. **C/C++ 习惯残留**：在 for 循环中使用 `int` 而非 `integer`
3. **always 块中混淆阻塞/非阻塞赋值**
4. **缺失 begin/end 配对**

这些错误模式具有高度的领域特异性，通用语言模型训练数据中 Verilog 比例极低，因此 RAG 知识库的引入尤为关键。

## 5. 关键公式

### 5.1 编译修复率（Compile Fix Rate）

用于衡量 RTLFixer 修复语法错误的能力。对每个问题采样 n = 10 次，记录成功修复的次数 c，求期望修复率：

$$

\text{fix rate} = \mathbb{E}_{\text{problems}}\left[\frac{\langle c \rangle}{n}\right]

$$

- `fix rate`：编译修复率，取值范围 [0, 1]
- `E_problems`：对所有问题求期望的算子
- `c`：单次实验中成功修复的样本数（即通过编译的样本数）
- `n`：每个问题的总采样次数（论文取 10）
- `\langle c \rangle`：c 的样本均值

该指标反映"多次尝试后平均能修复多少比例的语法错误"。之所以采用多次采样取平均，是为了降低 LLM 随机性带来的方差——同样的问题，温度 0.4 下可能给出不同的修复轨迹。

### 5.2 pass@k 功能正确性

参考 Codex 的无偏估计器。对每个问题采样 n = 20 个样本，统计通过测试的样本数 c：

$$

\text{pass@}k = \mathbb{E}_{\text{problems}}\left[1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}\right]

$$

- `pass@k`：k 次机会中至少一次通过测试的概率
- `n`：每个问题的总采样数（论文取 20，远大于 k）
- `c`：通过测试的样本数
- `binom(n-c, k)`：从 (n-c) 个失败样本中选出 k 个的组合数
- `binom(n, k)`：从 n 个总样本中选出 k 个的组合数
- 整个分数 `binom(n-c, k) / binom(n, k)`：k 次采样全部失败的概率
- `1 - ...`：至少一次成功的概率

这个无偏估计器避免了朴素估计在 c 接近 n 时的高方差问题，是评估代码生成的标准方法。直观解释：当我们从 n 个样本中无放回地抽 k 个，若至少一个成功（即没有全部失败），则视为该问题解决。

### 5.3 错误率分解（隐含的统计模型）

虽然论文没有显式给出公式，但根据 Figure 4 可推导出 VerilogEval 上的错误构成模型：

$$

P(\text{fail}) = P(\text{syntax error}) + P(\text{sim error} \mid \text{pass syntax})

$$

$$

P(\text{syntax error}) \approx 0.55

$$

- `P(fail)`：失败概率（1 - pass@1）
- `P(syntax error)`：语法错误导致的失败概率（约 55%）
- `P(sim error | pass syntax)`：通过语法后仿真仍失败的概率
- 两条失败路径近似互斥（先过编译再仿真）

这意味着在 Human 描述上，pass@1 = 0.267 对应约 73.3% 的失败，其中 ~40% 是语法失败、~33% 是仿真失败。修复语法后能拿回那 40%，但已无更多空间用于 hard 问题。

### 6.5 主要实验结果：VerilogEval-syntax


VerilogEval-syntax 数据集上的修复率（GPT-3.5 vs GPT-4）：

| Prompt | RAG | Simple | iverilog | Quartus | GPT-4 |
|--------|-----|--------|----------|---------|-------|
| One-shot | w/o | 0.414 | 0.536 | 0.587 | 0.91 |
| One-shot | w/  | -     | 0.800 | 0.899 | 0.98 |
| ReAct    | w/o | 0.671 | 0.731 | 0.799 | 0.92 |
| ReAct    | w/  | -     | 0.820 | 0.985 | 0.99 |

**关键观察**：

1. **ReAct vs One-shot**：ReAct 在所有反馈质量档位上均显著优于 One-shot
   - Simple：0.414 → 0.671（+25.7%）
   - iverilog：0.536 → 0.731（+19.5%）
   - Quartus：0.587 → 0.799（+21.2%）

2. **RAG 的提升**：
   - Quartus + One-shot：0.587 → 0.899（+31.2%）
   - Quartus + ReAct：0.799 → 0.985（+18.6%）

3. **ReAct + RAG + Quartus 达到 98.5%** 的最佳修复率

4. **GPT-4 接近天花板**：即便 One-shot + RAG + Quartus 也能达 0.98，GPT-4 对 ReAct 的边际收益较小


| 数据集 | 子集 | pass@1 原始 | pass@1 修复后 | pass@5 原始 | pass@5 修复后 |
|-------|------|-----------|-------------|-----------|-------------|
| Human | All  | 0.267 | **0.368** | 0.458 | 0.506 |
| Human | easy | 0.521 | **0.666** | 0.808 | 0.847 |
| Human | hard | 0.053 | **0.120** | 0.164 | 0.221 |
| Machine | All | 0.467 | **0.799** | 0.691 | 0.891 |
| Machine | easy | 0.568 | **0.833** | 0.782 | 0.892 |
| Machine | hard | 0.367 | **0.771** | 0.601 | 0.890 |

**结论**：
- VerilogEval-Machine pass@1 提升 +32.3%
- VerilogEval-Human pass@1 提升 +10.1%
- 简单问题获益更大（Human: easy +14.5% vs hard +6.7%）
- Hard 子集仍受限于逻辑能力，语法修复并不能解决所有问题

#### 错误构成的可视化（Figure 4）

论文 Figure 4 用环形图清晰展示了 RTLFixer 修复前后 VerilogEval 上错误的构成变化：

**VerilogEval-Machine（内圈原始 → 外圈修复后）**：
- Passed-easy：40.3% → 56.8%（+16.5pp）
- Passed-hard：17.4% → 28.2%（+10.8pp）
- Compilation Error-easy：12.9% → 2.0%（-10.9pp）
- Compilation Error-hard：11.1% → 3.3%（-7.8pp）
- Simulation Error-easy：8.5% → 2.0%（-6.5pp，注意此数据中两个圆圈都有 simulation 部分）
- Simulation Error-hard：7.1% → 3.3%（-3.8pp）

**VerilogEval-Human（内圈原始 → 外圈修复后）**：
- Passed-easy：27.0% → 36.2%（+9.2pp）
- Passed-hard：2.6% → 2.9%（+0.3pp）
- Compilation Error-easy：23.8% → 7.5%（-16.3pp）
- Compilation Error-hard：24.6% → 13.4%（-11.2pp）
- Simulation Error-easy：8.3% → 2.2%（-6.1pp）
- Simulation Error-hard：13.4% → 29.3%（+15.9pp，原图标注较复杂，请以原文为准）

直观结论：**修复语法错误几乎全部转移到 Passed 上**，而 Simulation Error 部分基本保持不变——这正是论文强调的"语法错误约占总错误 55%"的强证据。


| LLM | 语法成功率 | pass@1 |
|-----|----------|--------|
| GPT-3.5 原始 | 73% | 11% |
| GPT-3.5 + RTLFixer | 93% | 16% |

在未重新生成 RAG 知识库的情况下，RTLFixer 仍能将 RTLLM 基准的语法成功率提升 20 个百分点，说明框架具有 **良好的跨基准泛化能力**。同时 pass@1 从 11% 提升到 16%，相对增幅约 45%。


- **初始采样**：通过 One-shot 和 ReAct 各 10 次采样 VerilogEval 问题，保留引发编译错误的样本，得到 174 个。
- **扩展到 212 个**：通过 DBSCAN 聚类 + Jaccard 距离去重后，再补充相关变体，最终数据集规模为 212 个。
- **覆盖**：横跨 VerilogEval 的全部问题，涵盖 easy 和 hard 子集。


论文隐含比较了几个关键的"零修复"基线：
- **One-shot 无反馈**：0.414（仅靠 LLM 自身知识）
- **ReAct 无反馈**：0.671（仅靠推理）
- **One-shot + iverilog**：0.536
- **One-shot + Quartus**：0.587

这些基线表明：
- 单纯加反馈（无 RAG）提升有限（+12 到 +17pp）
- 单纯 ReAct 提升显著（+26pp）
- ReAct + RAG + Quartus 才是天花板（+57pp）

### 6.6 消融研究：反馈质量与LLM对比


观察 Table 1 列向变化：

- **Simple → iverilog → Quartus**：反馈质量越高，修复率越高
- **ReAct + RAG 的组合放大反馈质量的价值**：在 iverilog 上 ReAct + RAG 仅 0.820，但切换到 Quartus 后跃升至 0.985
- **推断**：高质量的编译器日志使得 LLM 能更有效地利用检索到的专家指导


- **GPT-3.5 → GPT-4**：One-shot + RAG 从 0.899 → 0.98，提升显著
- **GPT-4 在 One-shot 与 ReAct 间差异仅约 1%**：GPT-4 已经具备很强的自我纠错能力，对 ReAct 的边际需求较小
- **RTLFixer 对弱模型更友好**：帮助较弱模型（包括开源模型）缩小与 GPT-4 的差距


约 90% 的问题在 **单次修订** 内被解决。剩余 10% 需要多轮迭代：
- 修复一个错误可能暴露新的错误
- 多轮交互是必要的，但迭代成本可控


无法修复的少数失败模式：

**(1) LLM 能力上限型失败**：
- 例：vector100r 任务中 LLM 无法正确完成算术索引计算
- 错误信息：index -17 cannot fall outside the declared range [255:0]
- 表明即使是简单索引计算，LLM 也会出错

**(2) C/C++ 习惯性错误**：
- LLM 把 C/C++ 的语法习惯搬到 Verilog
- 例：使用 `int` 类型变量在 for 循环（Verilog 应使用 `integer`）

这些失败暴露了 LLM 在硬件描述语言上的"领域知识盲区"。


论文 Figure 5 给出了同一段错误代码在 iverilog 与 Quartus 上的反馈对比：

**任务**：vector100r（100-bit 矢量反转）

**错误代码片段**：
```verilog
always @(posedge clk) begin
   for (int i = 0; i < 100; i = i +1) begin
       out[i] <= in[99 - i];
   end
end
```

**iverilog 输出**：
```
vector100r.sv:5: error: Unable to bind wire/reg/memory 'clk' in 'top_module'
vector100r.sv:5: error: Failed to evaluate event expression 'posedge clk'.
2 error(s) during elaboration.
```

**Quartus 输出**：
```
Error (10161): Verilog HDL error at vector100r.sv(5): object "clk" is not
declared. Verify the object name is correct. If the name is correct, declare
the object.
```

对比可见：
- iverilog 仅指出 "Unable to bind"，但没说怎么修
- Quartus 明确建议 "Verify the object name is correct" 或 "declare the object"
- Quartus 的可操作性显著更强

这正是 RTLFixer 中反馈源选择会显著影响结果的根本原因。

## 10. 讨论与局限


iverilog 与 Quartus 的对比清楚地表明：
- **错误信息的清晰度直接影响 LLM 调试能力**
- iverilog 偶发 "I give up" 提示，对 LLM 而言是无效信号
- Quartus 错误信息含"原因 + 修复建议"，极大降低了 LLM 的推理负担

### 10.2 RAG vs ReAct 的协同

- 单独使用 ReAct（无 RAG）就能带来 +25.7% 的提升
- 单独使用 RAG（One-shot + RAG）也带来 +31.2%（Quartus）的提升
- **两者结合**产生最大收益，但具有部分重叠的提升空间

### 10.3 模拟（仿真）错误的局限

论文坦诚指出：
- 把仿真错误（logic error）反馈给 LLM 时，提升有限
- LLM 在理解波形对比、错误计数等仿真反馈上能力不足
- 仅在简单问题上才能修复逻辑错误
- **高级推理与问题求解能力** 仍是瓶颈

### 10.4 弱模型的潜在收益

RTLFixer 对开源 / 弱 LLM 尤其有价值，因为它把"调试能力"以外部工具（RAG 知识库 + 编译器）的形式外挂，弥补了模型自身的不足。这一点对工业部署意义重大。

---

### 10.5 局限性与未来方向

1. **仅处理语法错误**：仿真/逻辑错误未充分覆盖
2. **依赖编译器质量**：编译器反馈差时性能下降明显
3. **RAG 库人工构建**：7 类 iverilog + 11 类 Quartus 仍需人力维护
4. **固定迭代上限**：10 轮可能不够处理极端复杂问题
5. **GPT 系列为主**：未充分验证开源模型上的实际表现
6. **未来方向**：(1) 仿真错误修复——探索 LLM 对仿真波形的理解；(2) 自动构建 RAG 库；(3) 扩展到 SystemVerilog / Chisel；(4) 结合形式化验证

## 12. 一分钟复述版

1. **问题**：LLM 生成的 Verilog 代码中约 55% 是语法错误（非逻辑错误），导致一次生成可用率极低。

2. **方法**：RTLFixer = ReAct 提示工程（LLM 自主推理+调用编译器/RAG 工具）+ RAG 检索增强（人工专家错误→修复知识库）+ 编译器反馈闭环（Icarus/Quartus）。LLM 像工程师一样：编译→读错误→思考→查手册→改代码→再编译。

3. **结果**：VerilogEval-syntax 上 **98.5% 语法修复率**；VerilogEval-Machine pass@1 提升 +32.3%；VerilogEval-Human pass@1 提升 +10.1%；RTLLM 跨基准语法成功率 73%→93%。

4. **局限**：不修仿真/逻辑错误，RAG 知识库人工构建，Quartus 依赖商业工具，GPT 系列验证为主。
3. 构建 **VerilogEval-syntax** 数据集（212 个错误实现）
4. 在 VerilogEval 上 **pass@1 提升 +32.3%（Machine）和 +10.1%（Human）**
5. 在 RTLLM 上 **语法成功率 73% → 93%**
6. 开源工具链，便于社区复现和扩展

### 12.2 对工程实践的启示

- **优先修复语法错误**：是性价比最高的改进点（成本低、收益大）
- **选择更好的反馈源**：商业工具（Quartus）的错误信息比开源更利于 LLM
- **外挂知识库有效**：用 RAG 让弱模型逼近强模型，无需昂贵微调
- **ReAct 是必备**：让 LLM "显式思考"比"直接生成"显著更稳
- **闭环迭代**：编译器反馈循环让自动化调试成为可能

### 12.3 对学术研究的启示

- 揭示了 **基准难度被低估** 的现象（语法层就让 LLM 大面积翻车）
- 提出 **"反馈质量" 作为新维度** 的消融方法论
- 展示了 **LLM Agent + 工具调用 + 领域知识库** 在垂直领域落地的范式

### 12.4 一句话推荐语

> 如果你在做 LLM 生成 HDL 的相关工作，RTLFixer 是你绕不开的参考文献——它不仅给出 98.5% 修复率的工程方案，更重要的是确立了"ReAct + RAG + 编译器反馈"的自主调试范式，奠定了后续研究的方法论基础。
