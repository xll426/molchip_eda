## 1. 一句话定位

**CVDP 是当前规模最大、任务类型最全的 RTL 设计与验证 benchmark：783 道由约 35 名 4 年以上经验硬件工程师手写的题目覆盖 13 类任务（生成、修改、模块复用、lint/QoR、testbench 激励/checker、assertion、调试与代码理解），首次将 tool-using agent 作为一等评测对象（Non-Agentic 617 题 vs Agentic 166 题），以 hidden executable harness 客观评分；SOTA 模型代码生成最高仅 33.56% pass@1（Claude 3.7 Sonnet），验证类任务（testbench checker 最好仅 11%、assertion 最好 25%）尤其薄弱，清晰揭示了 LLM 在真实硬件工作流中的巨大能力缺口。**

这句话里的五个技术承重点，后面逐一拆解：

1. **783 题 13 类任务覆盖** -- CVDP 是第一个系统覆盖"设计侧"（RTL 补全/生成/修改/复用/lint-QoR）+ "验证侧"（testbench 激励/checker/assertion）+ "理解侧"（代码问答/对应关系）的 benchmark，此前如 VerilogEval/RTLLM 几乎只测"写 RTL"。
2. **35 名硬件工程师手写 + 专家审核 + 质量过滤** -- 1,313 题经博士级专家审核、LLM judge 四维打分（ambiguity/consistency/category_match/behavioral_match）后保留 783 题（过滤率 40.4%），是目前最难被训练数据污染的 RTL 评测集。
3. **首次将 tool-using agent 作为一等评测对象** -- 提供 Non-Agentic（单轮 prompt）与 Agentic（Docker 内读写文件、调用 iverilog/yosys/verilator 迭代修改）两种形态，独立 harness Docker 评分防止 agent 作弊。
4. **hidden executable harness 客观评分** -- 代码生成用 Cocotb/pytest/Icarus/Yosys/Verilator/Xcelium 所有 sub-tests 通过才算 passed；代码理解用 BLEU + LLM judge，避免人工评分的主观性。
5. **验证侧全线薄弱 -- 最有价值的"负结果"** -- 真实芯片项目中验证工程师常多于设计工程师，但 LLM 在 testbench checker（最高 13%）和 assertion（最高 28%）上的灾难性表现，精确指出了 LLM4EDA 的真实短板。

**覆盖率：3/17。** CVDP 覆盖芯片前端最广的一段（①②③⑥），最大特点是**第一次系统纳入"验证侧"任务**——此前 benchmark 几乎只测"写 RTL"。而真实芯片项目中验证工程师常多于设计工程师，写 testbench/checker/assertion 占据大量工时。

## 3. 输入 / 输出

### 3.1 输入

CVDP 的输入因任务类别和交互形态而异，以下以代表性类别举例：

**(a) Non-Agentic cid03（规格→RTL）输入**

```json
{
  "id": "cvdp_copilot_lfsr_0001",
  "categories": ["cid003", "easy"],
  "input": {
    "prompt": "Implement an 8-bit Linear Feedback Shift Register (LFSR)...",
    "context": {
      "docs/specification.md": "The LFSR uses a Galois configuration...",
      "rtl/lfsr_8bit.sv": ""
    }
  },
  "output": {
    "response": "",
    "context": {"rtl/lfsr_8bit.sv": ""}
  }
}
```

`output.context` 的 key 决定模型应生成哪些文件。多文件输出需结构化 JSON，单文件可用 code block。

**(b) Agentic cid03 输入**

```json
{
  "id": "cvdp_agentic_fixed_arbiter_0001",
  "categories": ["cid003", "easy"],
  "system_message": "可用文件与仿真工具说明（iverilog/yosys/verilator）",
  "prompt": "按 docs/specification.md 实现 fixed priority arbiter",
  "context": {
    "docs/specification.md": "...",
    "rtl/fixed_priority_arbiter.sv": ""
  },
  "harness": {...}
}
```

Agent 在 Docker workspace 中查看 docs/rtl/verif，创建或修改文件，运行 iverilog/vvp/yosys/verilator，根据结果迭代修复。runner 比较 before/after 生成 `agent_changes.patch`，再由独立 harness Docker 评分。

**(c) cid16 调试输入**

```json
{
  "id": "cvdp_copilot_sorting_0001",
  "categories": ["cid016", "medium"],
  "input": {
    "prompt": "Fix the bug in the brick sort implementation below...",
    "context": {
      "rtl/sorting_engine.sv": "// 含 bug 的 RTL 代码 + testbench",
      "rtl/tb_sorting.sv": ""
    }
  }
}
```

### 3.2 中间产物

CVDP 作为 benchmark 框架，中间产物主要是评测基础设施产物：

- **Mini repository**：每题被展开为一个包含 docs/rtl/verif 文件的独立目录
- **System/user prompt**：`run_benchmark.py` 根据 category ID 注入不同 system guidance（如 cid003 的 "Specification to RTL Translation" 指导语）
- **agent_changes.patch**（Agentic 特有）：记录 agent 对 mini repo 的所有文件修改
- **raw_result.json / report.json / report.txt**：每次评估的输出产物

按任务类型，模型/agent 输出：

| 任务类型 | 输出 | 判定方式 |

| cid03 规格→RTL | 从规格生成的完整 RTL | hidden harness 所有 sub-tests 通过 |

## 4. Benchmark 构建方法

### 4.1 题目来源与出题流程

CVDP 的题目完全由**人工手写**，而非从公开题库/考试题收集，流程如下：

```text
  约 35 名 4 年以上 Verilog/验证经验硬件工程师
              │  手写出题（1,313 题初稿）
              ▼
  博士级硬件设计/工程管理专家逐题审核
  （准确性、任务适配性、范围适当性）
              │
              ▼
  早期批次密集人工审核校准
              │
              ▼
  进入质量过滤流水线（见 4.3）
              │
              ▼
  保留 783 题（过滤率 40.4%）
```

- **难度分层**：Non-Agentic 仅含 easy/medium，Agentic 涵盖 easy/medium/hard（因 hard 题对单轮评测过难）
- **主题多样性**：出题人被要求类别内覆盖 (1) FSM/控制逻辑（Mealy/Moore、仲裁、计数器）；(2) 算术与数据通路（加法器、乘法器、移位器）；(3) 互连（crossbar、router、FIFO）；(4) 存储系统（cache、CAM）；(5) 架构（CPU、加速器）

### 4.2 13 类任务拆解

| cid02 | RTL Code Completion | 94 | 0 | hidden harness |
| cid03 | NL Spec to Code | 78 | 37 | hidden harness |

### 4.3 质量过滤

质量过滤分两个阶段：

**阶段一：Harness 健全性检查**
- Golden reference solution 必须使 harness 通过（确认 harness 与 reference 一致）
- 不完整 context 必须使 harness 失败（确认正确解是必需的——空实现不能通过）

从 1,313 题中排除 78 题（健全性失败），进入 1,235 题。

**阶段二：LLM Judge 四维评分**

对每题用 GPT 系列模型打分（1-10）：

1. **ambiguity_score**：原 prompt 的清晰度，1=不可能理解，10=完全清晰
2. **consistency_score**：prompt/input/output/harness 之间的一致性
3. **category_match_score**：类别标签与题目实际类别的匹配度
4. **behavioral_match_score**：prompt 描述的行为与 reference solution/harness 的实际行为匹配度

综合分数阈值 8.0，低于则剔除。最终保留 783 题（过滤率 40.4%）。

过滤率最高类别：cid16 Debugging（64.1%）、cid07 Code Improvement（60.6%）；最低：cid02 Code Completion（7.8%）。

### 4.4 评测基础设施架构（对应论文 Figure 1）

```text
        JSONL Dataset（783 题）
                │
                ▼
        run_benchmark.py（按 ID 前缀分流）
                │
    ┌───────────┴───────────────┐
    │ cvdp_copilot_*            │ cvdp_agentic_*
    │ (Non-Agentic)             │ (Agentic)
    ▼                           ▼
CopilotBenchmark              AgenticProcessor
    │ 合成 system/user prompt     │ 构建 mini repo + docker-compose
    │ 调 LLM → 解析响应           │ Agent 在 Docker 内工作
    │ 写入 mini repo              │ 监控修改 → agent_changes.patch
    ▼                           ▼
启动 Docker harness            独立 harness Docker 评分
(Cocotb/pytest/Icarus/         │ 报告 status/violations/ignored
 Yosys/Verilator/Xcelium)       │
    │                           │
    └───────────┬───────────────┘
                ▼
        收集 return code / log
        所有 sub-tests 通过 → passed
                │

```

**关键设计**：Agentic 的评分 harness 与 Agent 工作区独立——Agent 修改的代码先打成 patch，再应用到独立评测 repo 中评分，Agent 看不到 hidden test，防止作弊。

## 5. 关键公式

### 5.1 pass@k 定义（论文实现，有放回近似）

$$
\text{pass@k} = 1 - \left(1 - \frac{c}{n}\right)^k
$$

- $c$：$n$ 次采样中通过的次数
- $n$：每题的采样次数（论文 $n=5$）
- $k$：允许的候选数（论文报告 pass@1）

<!-- 修正：论文使用有放回近似 $1-(1-c/n)^k$，而非 HumanEval 标准无偏估计 $1-\binom{n-c}{k}/\binom{n}{k}$。在 $n=5$ 时差异较小，但跨论文引用需注明口径差异。-->

**为什么是有放回近似**：`run_reporter.py` 的实现假设每次采样独立（有放回），而非不放回超几何分布。$n=5$ 时两者数值差异小，但 pass@5 等更大 $k$ 值实验必须先固定定义。

### 5.2 Problem Passed 判据

$$
\text{passed} \iff \bigwedge_{t \in \text{sub-tests}} \text{pass}(t)
$$

一道题含多个 sub-test，**全部通过才算该题 passed**。这是比 "大部分通过" 更严格的判据。

### 5.3 质量过滤综合得分

$$
\text{score}_{\text{agg}} = f(\text{ambiguity}, \text{consistency}, \text{category\_match}, \text{behavioral\_match})
$$

论文设通过阈值 8.0（满分 10）。

### 5.4 失败聚类 K-means

对于失败样例集合 $F_c = \{f_{c,1}, \ldots, f_{c,n}\}$：

$$
k^* = \arg\max_{k \in [2,11]} \text{silhouette\_score}(\text{Kmeans}(\text{Embedding}(\text{Reflect}(F_c)), k))
$$

- $\text{Reflect}(\cdot)$：o1 对失败原因的反思
- $\text{Embedding}(\cdot)$：SentenceTransformer 嵌入
- $\text{Kmeans}(\cdot,k)$：K-means 聚类
- $\text{silhouette\_score}$：轮廓系数，选最佳 $k$

### 6.2 打分公式

**代码生成**（cid02-05/07/12-14/16）：

$$
\text{PassRate} = \frac{\#\{\text{所有 sub-tests 通过的样题}\}}{\#\{\text{总样题}\}},\quad n=5
$$

期望 pass@1 是 5 次采样的平均单次通过概率。

**代码理解**（cid06/08）：BLEU（n-gram 精度的几何平均 x 简短惩罚），与 reference 片段匹配。

**代码理解**（cid09/10）：LLM subjective judge（GPT o4-mini），比较模型回答与参考答案（在原始 prompt 上下文中评分），强调原问题明确要求的信息。

**这张表说明什么**：(1) QA 任务（cid09/10）得分普遍较高（68-89%），聊天式问答已较成熟，未能拉开模型差距。(2) Correspondence 任务（cid06/08）对开源/小模型极难（Llama 405B 仅 10%/1%），但对 Claude 3.7 Thinking 可达 70%/48%。

### 6.4 四个关键研究问题

**Q1: 质量过滤对 pass rate 有多大影响？**

过滤后 pass rate 在 cid07（+10-14 pp）和 cid16（+10-17 pp）上提升显著，说明原题歧义是主要瓶颈。但 cid12-14 即使激进过滤也提升有限——反映 LLM 根本上不擅长 SystemVerilog testbench 代码。

**Q2: Agentic 是否比 Non-Agentic 更有利于模型？**

恰好相反——Agentic 转 Non-Agentic 格式评分下几乎所有模型 pass rate 都更低（Claude 3.7 从 33.56% 降 29%）。因为 Agentic 题更难（含 hard 级别的 module reuse 等），且提示中包含更大上下文。

**Q3: 验证类为什么比 RTL 生成更难？**

失败分析揭示验证类任务失败簇数显著更高，除语法/功能错误外还包括：Misplaced SVA、Insufficient Coverage、Missing timescale、Incorrect modulo/synchronization、Truncated code、Uninitialized variables、Multiple drivers。原因：(a) testbench 更偏 procedural/imperative；(b) checker 需理解 DUT 跨周期正确行为；(c) stimulus 要覆盖边界与状态空间；(d) assertion 涉及 clocking、sampling、implication 和 reset disable。

**Q4: 不同类别任务的 model ranking 是否一致？**

不一致。GPT-4.1 在 cid02（37%）上表现最好，但 cid12（16%）远不如 Claude 3.7（25%）。cid16 调试上 Claude 3.7（53%）大幅领先 GPT-4.1（45%）。不存在"全能模型"——不同 RTL 子任务需要不同的模型能力组合。

## 7. 创新点

### 创新点 1：规模最大、任务最全的 RTL 设计+验证 benchmark

此前 benchmark（VerilogEval 156 题、RTLLM 50 题、FVEval 192 题、CreativEval 119 题）几乎只覆盖 RTL 生成。CVDP 以 783 题、13 类任务首次系统覆盖：(1) RTL 设计侧五种姿势（补全/生成/修改/复用/lint-QoR）；(2) 验证侧（testbench stimulus/checker、assertion generation）；(3) 理解侧（代码问答、规格对应）。类别数量是之前最全 benchmark 的 6+ 倍。

### 创新点 2：首次将 tool-using agent 作为一等评测对象

提供 Non-Agentic 与 Agentic 两种交互形态并列评估。Agentic datapoint 构建 mini repository（含 docs/rtl/verif），Agent 在 Docker 内读写文件、运行 EDA 工具迭代修改。**独立评分的防作弊设计**：Agent 修改的代码先打成 patch，再应用到独立评测 repo——Agent 看不到 hidden test。

### 创新点 3：hidden executable harness 替代人工评分

使用 Cocotb/pytest/Icarus/Yosys/Verilator/Xcelium 客观判定，所有 sub-tests 通过才算 passed。这比 "跑一个 testbench 对拍" 更严格——Cocotb 框架允许每个 datapoint 自带多 sub-test 组成的 test suite。

### 创新点 4：质量过滤 + 失败聚类分析流程

先以 LLM judge 四维评分去噪（1,313→783），再用 o1 反思 + SentenceTransformer 嵌入 + K-means 聚类形成**任务级失败分类**（如 Misplaced SVA、Insufficient Coverage、Missing timescale）。质量过滤后 cid13 的失败簇从 6 个降至 2 个（Claude 3.7），验证了过滤对提示清晰度的改善。

### 创新点 5：专家出题 + 隐藏参考实现——防污染设计

约 35 名 4 年+ 工程师手写题目 + 博士级审核，是目前最难被训练数据污染的 RTL 评测集。完整数据集的 reference solution/patch 不公开发布，公开的 `*_with_solutions.jsonl` 仅为 6 条样例，仅供工具链验证。论文明确警告不要用公开 example 当训练集后报评测。

## 9. 与芯片流程的关系

### 9.1 在全流程中的位置

CVDP 覆盖芯片流程**前端最广的一段（①②③⑥）**：

```text
  人写规格 + 人提供 context 文件
             │
             ▼
  ┌──────────────────────────────────────────────┐
  │ ① RTL 设计：cid02补全/cid03生成/cid04修改    │
  │    cid05模块复用/cid07 lint-QoR              │
  │        ↓                                      │
  │ ② RTL 功能仿真：hidden harness               │
  │    Cocotb + Icarus/Verilator + Yosys          │
  │    cid12激励/cid13 checker/cid16调试          │
  │        ↓                                      │
  │ ⑥ 形式验证：cid14 assertion (SVA)            │
  └──────────────┬───────────────────────────────┘
                 │  ⚠️ CVDP 到此为止
                 ▼
   ③ 逻辑综合（Yosys lint only，无真实综合）
                 ▼
   ④ 门级仿真 → ⑤ STA → ⑦ Floorplan → ...
                 ▼
   ⑰ 芯片（CVDP 不评估可综合性/PPA/物理验证）
```

### 9.2 最大特点：首次系统纳入"验证侧"

真实芯片项目中**验证工程师常多于设计工程师**。写 testbench/checker/assertion、驱动覆盖率占据大量工时。此前所有 RTL benchmark 几乎只测"写 RTL"。CVDP 把这块最缺、最贵的能力量化出来。

**cid12/13/14 全线 <25% 是本领域最有价值的"负结果"** — 它告诉工业界：别指望现在的 LLM 帮你写验证环境。在芯片流程中，② 功能仿真的质量直接决定芯片能否一次流片成功（避免昂贵的重新流片）。

### 9.3 Agent 反而更难 — 重要警示

Agentic 整体 pass rate 反而更低（Claude 3.7 从 33.56% 降 29%，GPT-4.1 从 28.91% 降 21%）。说明"给工具"不等于"会用工具"——弱模型在多轮工具环境中更易累积错误。agent 的价值高度依赖底座模型的规划/自查能力。

### 9.4 "所有 sub-tests 通过"相当于什么验证级别

CVDP 的 passed 判据（所有 sub-tests 通过）比 VerilogEval 的 "Mismatches: 0 in N samples" 更严格——Cocotb 框架支持多 sub-test 组成的 test suite，而非单个随机激励对拍。但这仍然是 testbench 级验证（和 formal 全覆盖有本质区别），且 testbench 本身由出题工程师编写——"testbench 的质量" 本身也是一个变量。

## 10. 讨论与局限

### 10.1 论文自述的局限

1. **完整数据需从 HuggingFace 下载**：本地仓库仅 example 数据集，不含全部 783 题。
2. **商业工具依赖**：部分 testbench/assertion 任务需 Cadence Xcelium，开源替代无法完全复现。
3. **LLM judge 主观性**：cid09/10 依赖 GPT o4-mini judge，受 judge prompt 与模型版本影响。
4. **pass@k 公式不一致**：`run_reporter.py` 用 `1-(1-c/n)^k`（有放回近似），非 HumanEval 标准无偏估计；$n=5$ 差异小但跨论文引用需注明。
5. **公开 example 可能泄漏**：`*_with_solutions.jsonl` 仅供工具链验证，不能替代 hidden harness 盲测。
6. **Agentic 上下文仍为 oracle**：不含跨文件引用额外单元的真实仓库场景，未测 retrieval 能力。
7. **QA 任务偏简单**：cid09/10 得分高（68-89%），未拉开差距。
8. **范围有限**：仅标准设计+验证，未涵盖立项到流片制造全流程。
9. **计算/存储开销**：单模型评估可能 6.4-15 GB 磁盘；框架设 100 MB/run 上限。
10. **调试开关**：`--force-agentic-include-golden/harness` 仅供调试，不能作正式结果。

### 10.2 代码/复现层面的问题

从 [CVDP论文与代码复现详解.md](./CVDP论文与代码复现详解.md) 提炼：

- **数据集版本与论文不一致**：本地 PDF 是 v1（783 题），当前仓库已演进到 v1.1.0（含 heavy agentic、local inference 等新能力）。v1.1 的 `example_dataset` 只是工具样例（6 条），不能与论文的 783 题混淆。
- **local_export 模式仍初始化 Docker network**：即使明确不需 evaluation 的 export 模式，程序仍尝试创建 Docker network，无权访问 daemon 时报错（但不影响 prompt 导出）。
- **subjective scoring 被无条件打开**：`use_sbj_scoring = True` 硬编码，即使 cid003 code-generation prompt export 也会尝试创建 judge model。
- **pass@k 有放回近似不是 bug 但需警惕**：在 $n=5$ 时不影响论文主表（pass@1 退化为 $c/n$），但做 pass@5 等实验必须先固定定义。部分帮助文字又把 $k$ 描述为 "至少 $k$ 个样本通过" 的 threshold——两者不是同一统计量。
- **score-based 类别不能与二元 pass 直接相加**：cid06/08/09/10 的 BLEU/LLM 分数是连续评分，混合成"总体准确率"会掩盖任务定义差异。
- **完整数据集缺失**：本地仅有 example 数据，完整 783 题需从 HuggingFace 下载。本地已跑通一条 cid003 LFSR 样例的 prompt 构造，但未做模型推理和 harness 评测。

### 10.3 评测公平性与可信度分析

**（一）出题来源的公平性**

CVDP 的题目全由 NVIDIA 内部工程师手写。虽然这对质量（4 年+ 经验）和防污染（非公开题库）是好事，但题目的设计风格、难度偏好、模块命名习惯可能隐式偏向 NVIDIA 的设计文化。一个来自不同公司/学界的工程师群体是否会给出不同难度的题目分布，难以评估。

**（二）pass@k 公式口径问题**

CVDP 用 `1-(1-c/n)^k` 而非 HumanEval 的 `1-C(n-c,k)/C(n,k)`。论文自己诚实标注了公式，但二手引用极易忽略。$n=5$ 时差异小，但直接和 VerilogEval（无偏估计）对比时必须注明口径不同。这是与 ResBench（ordered pass@k）、ArchXBench（(n,t)）一样的"指标口径未标准化"现象的又一个例证。

**（三）LLM judge 的循环依赖**

cid09/10 用 GPT o4-mini 作 judge。如果 judge model 和被评测 model 来自同一 provider 或同年份，存在"judge 偏好自己生态"的风险。论文没有做多种 judge model 的交叉验证。

**（四）Agentic 评测方式的局限性**

论文当时无可用开源硬件 agent，Agentic 题被转成 Non-Agentic 格式给模型单轮回答。这意味着论文报告的Agentic 数字是 **agentic-origin tasks under single-turn models**，不是 agent 真实多轮工具使用的性能。真正的 Docker agent 评测结果需要后续工作填补。

**（五）testbench 质量作为隐藏变量**

CVDP 的 correctness 完全由 hidden testbench 定义。"所有 sub-tests 通过"的严格程度取决于出题工程师写的 testbench 质量——如果 testbench 覆盖率低、边界条件不全，功能错误的模型输出也可能"通过"。论文通过质量过滤缓解了这个问题，但 testbench 质量本身的方差不可消除。

**（六）不同任务类比的困难**

cid02-16 之间的 pass rate 不能直接类比——每类题目的难度、token 数、context 大小都不同。cid13 的 6%（最难）和 cid16 的 53%（最易）的差距可能部分来自题目分布的非均匀性，而非模型能力本身在"写 checker"和"修 bug"之间的真实差距。

## 12. 一分钟复述版

CVDP（NVIDIA，2025 arXiv）是**当前规模最大、任务最全的 RTL 设计与验证 benchmark**。核心事实：

1. **783 题 13 类任务**：由约 35 名 4 年+ 经验硬件工程师手写，经博士审核 + LLM judge 四维质量过滤，涵盖 RTL 设计（补全/生成/修改/复用/lint-QoR）+ 验证（testbench 激励/checker/assertion）+ 理解（代码问答/对应关系）。首次把验证侧系统纳入 benchmark。
2. **两种交互形态**：Non-Agentic 617 题（单轮 prompt）+ Agentic 166 题（Docker 内读写文件、调 EDA 工具迭代）。Agentic 评分独立——hidden harness 与 agent workspace 分离，防作弊。
3. **客观评分体系**：hidden executable harness（Cocotb/Icarus/Yosys/Verilator/Xcelium），所有 sub-tests 通过才算 passed；理解任务用 BLEU + LLM judge。
4. **主结果**：SOTA 模型代码生成最高仅 **33.56%** pass@1（Claude 3.7 Sonnet），远低于 VerilogEval v2 的 63%。验证类全线崩溃：testbench checker 最好仅 **11%**，assertion 最好 **25%**。Agentic 整体更难（Claude 3.7 降 29%）。cid16 调试相对最容易（53%）。
5. **失败分析**：o1 反思 + K-means 聚类，揭示验证类失败类型显著多于 RTL 生成——Missing timescale、Insufficient Coverage、Misplaced SVA 等是 LLM 在验证侧的特有短板。

**边界**：完整数据需从 HuggingFace 下载；部分商业工具依赖；LLM judge 主观性；pass@k 公式与 HumanEval 标准不同；Agentic 评测实际是单轮作答而非真实 agent 多轮工具使用；不覆盖物理设计/签核/流片。
