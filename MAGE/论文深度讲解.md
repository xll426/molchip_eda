## 1. 一句话定位

**MAGE 不训练任何模型，它把"写 RTL"这件事拆成四个各自独立上下文的 Agent，用高温采样撒出 20 个候选，再用 Icarus Verilog 仿真器逐时钟沿打分排序，最后只把"第一个出错的那一拍的信号快照"喂给调试 Agent 做定向修复——在 VerilogEval-Human/V2 上把 Claude 3.5 Sonnet 的 75.0%/72.4% 抬到 94.8%/95.7%。**

这句话里有四个技术承重点，后面逐个拆：
1. **不训练** → 全部收益来自推理时编排（inference-time scaling）
2. **四 Agent 分工** → 解决 context-switch 问题（合成 vs 非合成代码混在一个对话里会互相污染）
3. **高温采样 + 仿真排序** → 用确定性工具替代 LLM 自评
4. **State Checkpoint** → 把反馈粒度从"整体 pass/fail"降到"单拍信号级"

## 2. EDA 阶段映射（①-⑰）

参照 [芯片流程.md](../芯片流程.md) 的 17 阶段标准编号：

| 阶段 | 覆盖 | MAGE 做了什么 / 为什么没做 |
|------|:---:|---------------------------|
| **① RTL 设计** | ✅ **核心** | RTL Generation Agent 从自然语言规格 + module header 生成 Verilog |
| **② RTL 功能仿真** | ✅ **核心** | Judge Agent 调 `iverilog` 编译 + `vvp` 执行，逐时钟沿比对 DUT 输出与期望值 |
| ③ 逻辑综合 | ❌ | 从不调 Design Compiler / Yosys。生成的代码"仿真通过"不等于"可综合"——比如用了 `initial` 块赋初值、多驱动、组合环，仿真器全都能跑，综合器直接报错 |
| ④ 门级仿真 | ❌ | 无 SDF 反标，因此看不到毛刺、建立/保持违例、X 传播 |
| ⑤ STA（Static Timing Analysis，静态时序分析） | ❌ | 不计算任何路径延迟。论文 Intro 里提到"fails to meet timing constraints"是指逻辑上写错了时序行为（比如该用非阻塞赋值用了阻塞），不是物理时序 |
| ⑥ 形式验证 | ❌ | 不做 SAT/SMT 等价性证明 |
| ⑦ 布局规划 Floorplan | ❌ | — |
| ⑧ 标准单元摆放 Placement | ❌ | — |
| ⑨ CTS（Clock Tree Synthesis，时钟树综合） | ❌ | — |
| ⑩ 布线 Routing | ❌ | — |
| ⑪ 后仿真 | ❌ | 无 SPEF（寄生 RC）信息 |
| ⑫ 物理验证 DRC + LVS | ❌ | — |
| ⑬ 签核 Signoff | ❌ | — |
| ⑭-⑰ 流片→制造→封装测试→芯片 | ❌ | — |

**覆盖率：2/17。** MAGE 是一个**纯数字前端 spec→RTL→功能仿真闭环工具**。它在阶段 ①②之间来回迭代直到 ② 完全通过，然后交棒给人。

> ⚠️ 这是理解 MAGE 位置的关键：它优化的是 `s(r)=1` 这个目标，而 `s(r)` 只由 testbench 的 mismatch 数决定。一段**面积翻 3 倍、频率只有 100MHz、但功能完全正确**的 RTL，在 MAGE 眼里是满分。PPA（Power, Performance and Area，功耗/性能/面积）完全不在优化目标里。这是它和 ChipSeek（把 EDA 工具报出的面积/延迟做成 reward）的根本分野。

## 3. 输入 / 输出举例

### 3.1 输入（三件套）

以 VerilogEval-V2 的 `Prob011_norgate` 为例：

**(a) 自然语言规格 SP_i**
```text
Implement a NOR gate. A NOR gate is an OR gate with its output inverted.
The module has two inputs a and b, and one output out.
```

**(b) 模块接口头（module header）**
```verilog
module top_module (
    input  a,
    input  b,
    output out
);
```

**(c) Golden Testbench TB_i**（benchmark 自带，只会打印 pass/fail 汇总）
```verilog
module stimulus_gen (input clk, output reg a, b, output reg[511:0] wavedrom_title, ...);
  ...
  always @(posedge clk) begin
    {a, b} <= $random;   // 随机激励
  end
endmodule

module tb();
  ...
  always @(negedge clk) begin
    if (out_ref !== out_dut) begin
      errors <= errors + 1;   // ← 只累加错误计数
    end
  end
  final $display("Mismatches: %0d in %0d samples", errors, total);
endmodule
```

注意这个 golden TB 的输出形态：**只有一个汇总数字**。这正是论文 Sec II-C 攻击的靶子——"pass rates alone lack detailed insights into timing analysis, signal interactions, variable values, and mismatch information"。

### 3.2 中间产物：改造后的 Testbench（TB Agent 的输出）

TB Agent 把上面那个"哑巴 TB"改造成**逐拍播报员**：

```verilog
always @(negedge clk) begin
  if (out_ref !== out_dut) errors <= errors + 1;
  // ↓ TB Agent 加的这一句是整个 MAGE 的信息命脉
  $display("[CHECKPOINT] time=%0t a=%b b=%b expected=%b actual=%b match=%b",
           $time, a, b, out_ref, out_dut, (out_ref === out_dut));
end
```

产生的仿真日志（textual waveform，文本波形）：
```text
[CHECKPOINT] time=15 a=0 b=0 expected=1 actual=1 match=1
[CHECKPOINT] time=25 a=0 b=1 expected=0 actual=0 match=1
[CHECKPOINT] time=35 a=1 b=0 expected=0 actual=1 match=0   ← 首个 mismatch
[CHECKPOINT] time=45 a=1 b=1 expected=0 actual=1 match=0
```

**为什么必须是文本而不是 VCD 波形？** 论文 Sec II-C 直接点名 VerilogCoder：它用 AST（Abstract Syntax Tree，抽象语法树）分析 + 图形化波形追踪工具，"LLM can not directly apply"（LLM 无法直接消费图形），且工具闭源。MAGE 的选择是把波形降维成 LLM 原生就能读的 token 序列——这是一个**接口设计决策**，不是技术妥协。

### 3.3 输出

**最终 RTL**：
```verilog
module top_module (input a, input b, output out);
    assign out = ~(a | b);
endmodule
```

**伴随产物**：
- 候选 RTL 列表 + 每个候选的 `s(r)` 得分
- 改造后的可观测 TB
- 每个 Agent 的完整轨迹（输入 prompt、输出、工具调用、返回值）
- token 使用量统计

**本地实测记录**（Qwen2.5-Coder-1.5B Q4_K_M GGUF，纯 CPU/本地推理）：`Prob011_norgate` 在 219 个采样点上 0 mismatch 一次通过，单题 40.81s，API 成本 0。

## 4. 模型流程（ASCII 图）

### 4.1 五步主流程（对应论文 Figure 1(a)）

```text
        输入：自然语言规格 SP_i  +  module header  +  golden TB_i
                             │
    ═════════════════════════▼══════════════════════════════════════════
    Step 1  TestBench Generation Agent
    ─────────────────────────────────────────────────────────────────────
      读规格（+ golden TB 消歧）→ 生成带 $display CHECKPOINT 的优化 TB
      工具：iverilog（自检 TB 本身能编译）
      产出：TB'  ——  每个时钟沿打印 {输入向量, DUT输出, 期望输出}
                             │
    ═════════════════════════▼══════════════════════════════════════════
    Step 2  RTL Generation Agent（低温：T=0, top_p=0.01, n=1）
    ─────────────────────────────────────────────────────────────────────
      规格 + header + TB' → 1 份 Verilog
      工具：iverilog -t null（纯语法检查，不生成可执行文件）
      语法错 → 错误信息喂回 LLM 重写，最多 s=5 轮
                             │
    ═════════════════════════▼══════════════════════════════════════════
    Step 3  Judge Agent  —— 仿真打分
    ─────────────────────────────────────────────────────────────────────
      iverilog 编译 → vvp 执行 → 解析 CHECKPOINT 日志
      算 s(r) = 1 - m(r)/tc(r)
                             │
              ┌──────────────┼──────────────────┐
              │              │                  │
        s(r) == 1.0     0.5 \leq s(r) < 1     s(r) < 0.5
              │              │                  │
              │              │        ┌─────────▼──────────────────────┐
              │              │        │ Step 4  高温采样 & 排序        │
              │              │        │ T=0.85, top_p=0.95, c=n=20     │
              │              │        │ 20 个候选各跑一遍仿真          │
              │              │        │ 按 s(r) 降序 → 取 Top-K        │
              │              │        └─────────┬──────────────────────┘
              │              │                  │
              │              └────────┬─────────┘
              │                       ▼
              │      ═══════════════════════════════════════════════════
              │      Step 5  Debug Agent —— State Checkpoint 定向修复
              │      ───────────────────────────────────────────────────
              │        ① 定位最早失配时刻 t_m
              │        ② 截取窗口 W = [max(t_m - L_W, 0), t_m]
              │           （只给首错前 L_W 拍 + 首错那拍，不给全日志）
              │        ③ Debug Agent 输出 replace 动作（旧代码段→新代码段）
              │        ④ Judge 重新仿真 → 新 s(r')
              │             s(r') > s(r) → 接受
              │             s(r') \leq s(r) → ROLLBACK 回退到 r
              │        ⑤ while max s(r) < 1.0 且未达迭代上限：回到 ①
              │      ═══════════════════════════════════════════════════
              │                       │
              └───────────┬───────────┘
                          ▼
                最终 RTL（s(r)=1，0 mismatch）
```

### 4.2 四 Agent 职责矩阵（对应论文 Figure 1(b)）

```text
┌──────────────┬─────────────────────┬──────────────────┬────────────────────┐
│    Agent     │      写什么代码      │    调什么工具     │   独立上下文的意义  │
├──────────────┼─────────────────────┼──────────────────┼────────────────────┤
│ ① TB 生成    │ 非可综合            │ iverilog         │ 不被 RTL 实现细节  │
│              │ (testbench/behav)   │ (TB 自检)        │ 带偏，保持客观性   │
├──────────────┼─────────────────────┼──────────────────┼────────────────────┤
│ ② RTL 生成   │ 可综合              │ iverilog -t null │ 只想"硬件怎么搭"   │
│              │ (synthesizable)     │ (语法门)         │ 不想测试怎么写     │
├──────────────┼─────────────────────┼──────────────────┼────────────────────┤
│ ③ Judge      │ 不写代码            │ iverilog + vvp   │ 决策与生成解耦，   │
│              │ (只解析日志/打分)   │ (编译+执行)      │ 打分不受生成者影响 │
├──────────────┼─────────────────────┼──────────────────┼────────────────────┤
│ ④ Debug      │ 可综合（增量 patch）│ Judge Agent      │ 只看首错窗口，     │
│              │                     │ (改完重新验证)   │ 上下文极短、聚焦   │
└──────────────┴─────────────────────┴──────────────────┴────────────────────┘
```

**为什么 ①② 必须分家**：论文 Sec II-B 引用 AgentCoder 的发现——同一个对话里同时生成 testbench 和被测代码，测试会被代码"带偏"（"test cases generated in this manner can become biased and influenced by the code, resulting in a loss of objectivity"）。硬件场景更严重：testbench 是**非可综合**代码（`initial`、`#delay`、`$display`、`force/release` 全部合法），RTL 是**可综合**代码（这些全部非法）。让一个 Agent 在两套语法子集之间反复横跳，正是论文标题里 "context-switch" 的本义。

### 4.3 State Checkpoint 的信息增益（论文 Figure 3，Prob093 ece241-2014-q3）

```text
有 bug 的 RTL：
    always @(*) begin
      mux_in[0] = (~c & d) | (c & ~d);      ← 缺 (c & d) 项
      mux_in[1] = 1'b0;
      mux_in[2] = (~c & ~d) | (c & ~d);
      mux_in[3] = (c & d);
    end

┌─── 无 checkpoint（传统 golden TB 反馈）──────────────────────────┐
│ 日志：Output 'mux_in' has 11 mismatches.                        │
│       First mismatch occurred at time 50.                       │
│                                                                  │
│ LLM 推理：11 个错、时刻 50…… 大概是 mux_in[2] 有问题？          │
│ 动作：mux_in[2] = (~c&~d)|(c&~d)  →  (~c&~d)|(c&~d)|(c&d)      │
│ 结果：❌ SIMULATION FAILED（改错了位）                          │
└──────────────────────────────────────────────────────────────────┘

┌─── 有 checkpoint（MAGE）──────────────────────────────────────────┐
│ 日志：First mismatch at time 50:                                 │
│         Inputs: c=1, d=1                                         │
│         Got mux_in=1000 (8), Expected mux_in=1001 (9).           │
│                                                                   │
│ LLM 推理：8 vs 9，差在 bit0。cd=11 时 mux_in[0] 应为 1。         │
│           枚举 mux_in[0] 需覆盖：cd=01 有(~c&d) ✓                │
│                                  cd=10 有(c&~d) ✓                │
│                                  cd=11 缺 (c&d)  ✗ ← 就是它      │
│ 动作：mux_in[0] = (~c&d)|(c&~d)  →  (~c&d)|(c&~d)|(c&d)         │
│ 结果：✅ SIMULATION PASSED                                        │
└───────────────────────────────────────────────────────────────────┘
```

**信息论视角**：无 checkpoint 时，反馈是 `(错误总数, 首错时刻)` \approx 2 个标量；有 checkpoint 时，反馈是 `(首错时刻, 完整输入向量, 实际输出向量, 期望输出向量)` \approx 一个完整的**反例（counterexample）**。这在形式方法里就是 SAT 求解器返回的 counterexample trace，只是这里用文本而非波形承载。LLM 拿到反例就能做**演绎推理**（"输出 bit0 该是 1 但实际是 0，找哪个乘积项没覆盖 cd=11"），而不是**猜测**。

## 5. 关键公式（LaTeX）

### 公式 (1)：高温多候选采样

$$
R_i = \{r_{i1}, r_{i2}, \ldots, r_{ic}\}, \qquad r_i \sim P_T\!\left(r \mid p_{sys},\, SP_i,\, TB_i\right)
$$

- $T$：温度系数。低温配置 $T=0,\ \text{top\_p}=0.01,\ n=1$；高温配置 $T=0.85,\ \text{top\_p}=0.95,\ n=20$
- $p_{sys}$：RTL 生成的 system prompt
- $SP_i$：第 $i$ 题的自然语言规格（Specification）
- $TB_i$：对应的 testbench
- $c$：候选数量（论文实验中 $c=20$；Figure 1(c) 示意图用 $c=4$）

**温度做了什么**：softmax 采样时把 logits 除以 $T$：

$$
P_T(x_t \mid x_{<t}) = \frac{\exp(z_t / T)}{\sum_j \exp(z_j / T)}
$$

$T \to 0$ 退化成 argmax 贪心解码（确定性，但只探索一条轨迹）；$T = 0.85$ 让概率分布变平，低概率 token 也有机会被采到。

**这里有个反直觉点**，论文 Sec II-A 专门讨论：此前研究（如 VeriGen、VerilogEval）发现**RTL 生成在高温下表现更差**——因为 Verilog 语法刚性强，随机性更容易破坏语法/语义正确性。MAGE 的论断是：那是因为单 Agent 架构**没法有效筛选**高温产出的噪声。一旦有了独立的 Judge Agent + 客观打分，高温的探索收益就能被榨出来、噪声被过滤掉。Table I 是这个论断的直接证据：

| 配置 | VerilogEval-Human Pass@1 | VerilogEval-V2 Pass@1 |
|------|---:|---:|
| Low Temp（$T=0, n=1$） | 89.1% | 93.6% |
| **High Temp（$T=0.85, n=20$）** | **94.8%** | **95.7%** |

### 公式 (2)：归一化失配得分

$$
s(r) = 1 - \frac{m(r)}{tc(r)}
$$

- $m(r)$：候选 $r$ 在仿真中的 mismatch 数（DUT 输出 \neq 期望输出的检查点个数）
- $tc(r)$：总检查点数（total checks）
- $s(r) \in [0, 1]$，$s(r) = 1$ 表示完全正确

**这个公式的分量在于"谁来算"**：$m(r)$ 和 $tc(r)$ 都来自 `vvp` 的真实执行输出，不是 LLM 的主观判断。这是 MAGE 三大设计原则之一——**LLM 不自评，仿真器评**。对比很多 LLM-as-judge 的代码生成工作，它们的排序信号本身就带模型偏见；MAGE 的排序信号是可复现的确定性量。

**为什么归一化**：不同题目的 testbench 检查点数量差异极大（有的 100 拍，有的 1000 拍）。不归一化的话，$m(r)$ 在跨题聚合时不可比。

### 公式 (3)：Top-K 候选选择

$$
R^{\star}_{i,0} = \arg\max_{A \subseteq R_i,\ |A| = K} \sum_{r \in A} s(r)
$$

在 $c$ 个候选里选出得分和最大的 $K$ 元子集。因为目标函数是可分解的求和，这个组合优化等价于**按 $s(r)$ 降序取前 $K$ 个**——不需要真的做子集搜索。写成这个形式是为了和后续迭代式 (4) 的记号统一。

$K$ 的作用是**剪枝**：Debug 阶段每轮都要跑 LLM + 仿真，成本高。论文 Sec II-B 的说法是 "we prioritize candidate selection at an early stage by identifying top-scoring candidates. This approach allows us to reduce the exploration cost by filtering suboptimal results early."（早期过滤次优结果以降低探索成本）。

### 公式 (4)：Debug 迭代的接受/回退规则

$$
R^{\star}_{i,m} = \left\{ \arg\max_{r \in \{D(r^{\star}),\, r^{\star}\}} s(r) \ \middle|\ r^{\star} \in R^{\star}_{i,m-1} \right\}
$$

- $D(r)$：Debug Agent 对候选 $r$ 的一次修复尝试，产出 $r^{\star}_{trial} = D(r^{\star})$
- $m$：debug 迭代轮次
- 终止条件：$\max_{r \in R^{\star}_{i,m}} s(r) = 1$ 或达到迭代上限

**这个 $\arg\max$ 就是回退（rollback）机制的数学表达**：在 `{修复后, 修复前}` 两者中取分高者。所以每一轮 debug 的得分**单调不减**：

$$
\max_{r \in R^{\star}_{i,m}} s(r) \;\geq\; \max_{r \in R^{\star}_{i,m-1}} s(r)
$$

这是一个**爬山法（hill climbing）**，$D(\cdot)$ 是随机邻域算子，$s(\cdot)$ 是确定性适应度函数。单调性保证了"越修越烂"不会发生——这在纯 LLM 自迭代的系统里是常见失败模式（改 A 处引入 B 处新 bug，且模型意识不到）。

Figure 4(b) 的实证：进入 debug 的题目，平均得分从 **0.669 → 0.890**。

### 公式 (5)：最早失配时刻

$$
t_m = \min\{\, t \mid O_{DUT}(t) \neq O_{exp}(t),\ t \geq 0 \,\}
$$

- $O_{DUT}(t)$：DUT（Design Under Test，待测设计）在时刻 $t$ 的输出向量
- $O_{exp}(t)$：时刻 $t$ 的期望输出向量

**为什么是"最早"而不是"任意一个"或"全部"**：这是数字电路的**因果性**决定的。时序电路里，$t_1 < t_2$ 时刻的错误往往不独立——$t_1$ 时刻状态寄存器被写错，会污染 $t_2, t_3, \ldots$ 所有后续输出。第一个错误是**根因（root cause）**，后面的错误多半是**传播（propagation）**。给 LLM 看第 500 拍的错误，它可能去改一段其实没问题的逻辑。

对应 Figure 3 的例子：11 个 mismatch，但根因只有一个（`mux_in[0]` 缺一项）。

### 公式 (6)：文本波形窗口

$$
W = \left\{ \left( I(t'),\ O_{DUT}(t'),\ O_{exp}(t') \right) \ \middle|\ t' \in \left[\max(t_m - L_W,\, 0),\ t_m\right] \right\}
$$

- $I(t')$：时刻 $t'$ 的输入向量
- $L_W$：窗口长度参数（超参）
- 窗口右端点闭合在 $t_m$，即**不包含首错之后的任何信息**

**三个设计考量**：

1. **上下文预算**：一个 1000 拍的仿真日志可能几万 token，塞满上下文后 LLM 的注意力会被稀释（lost-in-the-middle 效应）。$L_W$ 把它压到几十行。
2. **时序电路需要历史**：为什么不只给 $t_m$ 那一拍？因为 $t_m$ 的输出取决于寄存器状态，而状态是历史累积的。要判断"计数器为什么在第 55 拍输出 010 而不是 011"，必须看到第 35、45 拍的 `en`/`rst` 是什么。$L_W$ 拍历史提供了这个状态演化上下文。
3. **截断未来是刻意的**：$t_m$ 之后的错误是噪声（传播的结果），给了反而干扰根因定位。

$L_W$ 是一个典型的**信息量 vs 噪声**权衡旋钮：太小则丢失状态演化线索，太大则退化成全日志。

### 公式 (7)：Pass@k 无偏估计

$$
\text{pass@}k = \mathbb{E}_{\text{Problems}} \left[ 1 - \frac{\dbinom{n - c_p}{k}}{\dbinom{n}{k}} \right]
$$

- $n$：每题的独立运行次数
- $c_p$：其中通过的次数
- $k = 1$（论文全部报告 Pass@1）

**这个公式在读数字时极其重要，容易被误读**。$\binom{n-c_p}{k} / \binom{n}{k}$ 是"从 $n$ 次运行里抽 $k$ 次，全都是失败"的概率，$1 - (\cdot)$ 就是"至少一次成功"的概率。

当 $k=1$ 时化简为：

$$
\text{pass@}1 = \mathbb{E}\left[1 - \frac{n - c_p}{n}\right] = \mathbb{E}\left[\frac{c_p}{n}\right]
$$

即**成功率的期望**，而不是"跑一次的运气"。这是 Codex/HumanEval 引入的标准做法，用于消除单次采样的方差。所以看到 "MAGE 94.8%" 时，正确理解是：**每题独立跑 $n$ 次，平均 94.8% 的运行通过**——不是"跑一次有 94.8% 概率通过某题"。

> 补充陷阱：MAGE 的一次"运行"内部已经包含了 20 个候选采样 + 多轮 debug。所以 MAGE 的 Pass@1 和 vanilla LLM 的 Pass@1 **消耗的计算量差了一到两个数量级**。这是公平性上最大的争议点，论文没有报告 token 预算对齐的对比。

## 6. 训练与实验设置

### 6.1 是否需要训练

**不需要训练。** MAGE 是一个纯推理时（inference-time）多 Agent 编排系统，不涉及任何形式的模型权重更新。

- 使用**固定的预训练 LLM**：论文主实验全部基于 **Claude 3.5 Sonnet 2024-10-22**（Anthropic，闭源 API）
- 不进行 SFT（Supervised Fine-Tuning，监督微调）、RL（Reinforcement Learning，强化学习）、DPO（Direct Preference Optimization，直接偏好优化）等任何形式的模型训练
- 所有改进来自**推理时的多候选采样、仿真反馈排序、迭代修复**
- 架构支持切换不同 LLM（通过 LlamaIndex 的 LLM-agnostic 接口），本地实测已接入 Qwen2.5-Coder-1.5B GGUF

**与 ChipSeek 的根本分野**：MAGE 的全部收益来自推理时编排（inference-time scaling），ChipSeek 的收益来自训练时 RL（SFT + CDPO，用 EDA 综合结果做 reward）。详见 [ChipSeek](../ChipSeek/论文深度讲解.md) 和本节末尾的交叉对比。

### 6.2 实验设置

**Benchmark**：VerilogEval-Human v1 和 VerilogEval v2，源自 HDLBits 教学平台。v1 含 156 题，v2 含 156 题（题目有重叠但 testbench 格式不同）。

**评估指标**：Pass@k 无偏估计（Codex/HumanEval 标准），消除单次采样的方差。

$$
\text{pass@}k = \mathbb{E}_{\text{Problems}} \left[ 1 - \frac{\dbinom{n - c_p}{k}}{\dbinom{n}{k}} \right]
$$

- $n$：每题的独立运行次数（高温配置 $n=20$，等价于 $c=20$ 个候选）
- $c_p$：其中通过的次数
- $k = 1$（论文全部报告 Pass@1）

当 $k=1$ 时化简为 $\text{pass@}1 = \mathbb{E}[c_p / n]$，即每题的期望通过率。

**基线方法**（Table II）：

| 系统 | 模型 | 训练方式 | VerilogEval-Human | VerilogEval-V2 |
|------|------|------|:---:|:---:|
| GPT-4o | Vanilla | — | 51.3% | — |
| Claude 3.5 Sonnet | Vanilla | — | 75.0% | 72.4% |
| ITERTL | 微调 | SFT | 42.9% | — |
| CodeV | 微调 | SFT | 53.2% | — |
| OriGen | DeepSeek-Coder-7B+LoRA | SFT | 54.4% | — |
| VeriAssist | GPT-4 | Agent | 50.5% | — |
| AutoVCoder | CodeQwen1.5-7B | SFT | 48.5% | — |
| AIVRIL | Claude 3.5 Sonnet | Agent | 64.7% | — |
| VerilogCoder | GPT-4 Turbo | Agent | — | 94.2% |
| **MAGE（低温）** | **Claude 3.5 Sonnet** | **Agent** | **89.1%** | **93.6%** |
| **MAGE（高温）** | **Claude 3.5 Sonnet** | **Agent** | **94.8%** | **95.7%** |

**消融设计**：
- Vanilla LLM（单次生成，无任何反馈）
- Single-Agent（四角色合并，共享对话历史，保留全部工具）
- Multi-Agent（四角色专职分工，独立上下文）

### 6.3 关键实验结果

**主结果（Table I）**：MAGE 高温配置在 VerilogEval-Human 达到 94.8% Pass@1，在 VerilogEval-V2 达到 95.7% Pass@1，同模型 vanilla 分别为 75.0% 和 72.4%，提升 19.8 和 23.3 个百分点。

**这张表说明什么**：MAGE 将同一个基座模型的 pass rate 从"勉强可用"（75%）推到"接近完美"（95%），证明推理时编排可以大幅放大基座模型的能力——前提是有可靠的客观评分机制（仿真器 mismatch 计数）。

**Agent 分工消融（Table III，低温，VerilogEval-V2）**：

| 配置 | Pass@1 | 相对 Vanilla 提升 |
|------|:---:|:---:|
| Vanilla LLM（单次生成） | 72.4% | — |
| Single-Agent（四角色共享上下文，保留全部工具） | 83.9% | +11.5 pp |
| **Multi-Agent（专职分工，独立上下文）** | **93.6%** | **+21.2 pp** |

**这张表说明什么**：Single-Agent 已经有仿真反馈、语法检查、迭代修复——它和 Multi-Agent 的唯一差别是上下文是否隔离。83.9% -> 93.6% 的 9.7 个百分点，是纯粹的"任务隔离"红利。这直接验证了 MAGE 的核心论断：testbench（非可综合）和 RTL（可综合）混在一个对话里会互相污染。

**Debug 阶段提升（Figure 4）**：进入 Debug 阶段的题目，平均候选分数从 0.669 提升到 0.890，证明 State Checkpoint + 回退机制的修复有效性。

**本地实测**（Qwen2.5-Coder-1.5B Q4_K_M GGUF，纯 CPU）：VerilogEval V2 的 Prob011_norgate 在 219 个采样点上 0 mismatch，单题约 40.81s，API 成本为 0。但仅一道最简单题目的通过不足以推断小模型整体表现。

## 7. 创新点

### 创新点 1：可综合 / 非可综合代码的 Agent 级隔离

这是 MAGE 最硬的一个洞察，也最容易被读者滑过去。

Verilog 是一门**双子集语言**：
- **可综合子集**：`always @(posedge clk)`、`assign`、`case`、非阻塞赋值 `<=`。综合器能把它变成门电路。
- **非可综合子集**：`initial`、`#10`（延时）、`$display`、`$random`、`force`/`release`、`fork/join`。只在仿真器里有意义，综合器直接报错或忽略。

**testbench 必须用后者，RTL 必须用前者。** 一个 Agent 在同一个对话历史里交替写这两种代码，就是在两套互斥的语法直觉之间反复切换——这正是标题里 "context-switch between tasks, programming languages, and knowledge domains" 的具体含义。

Table III 的消融实验直接量化了这个隔离的价值（Claude 3.5 Sonnet，低温，VerilogEval-V2）：

| 配置 | Pass@1 | 相对 Vanilla 提升 |
|------|---:|---:|
| Vanilla LLM（单次生成，无反馈） | 72.4% | — |
| Single-Agent（四角色合并，共享对话历史，**保留全部工具**） | 83.9% | +11.5 |
| **Multi-Agent（专职分工）** | **93.6%** | **+21.2** |

**读法**：Single-Agent 已经有了仿真反馈、语法检查、迭代修复——它和 Multi-Agent 的唯一差别是**上下文是否隔离**。83.9% → 93.6% 的 9.7 个百分点，是纯粹的"分工"红利。这个消融设计得很干净。

### 创新点 2：把高温采样从"RTL 的毒药"翻转成"RTL 的解药"

**既有共识**（Thakur et al. VeriGen、Pinckney et al. VerilogEval 都观察到）：RTL 生成任务下，提高温度会降低正确率。这和软件代码生成的规律相反——软件代码高温 + 多次采样通常能提升 pass@k。

**MAGE 的反驳**不是"之前的观察错了"，而是"之前的架构没法用高温"：

```text
单 Agent 高温：              MAGE 高温：
  生成 20 个候选              生成 20 个候选
       │                           │
  LLM 自己看代码判断哪个好      Judge Agent 跑 20 遍 iverilog+vvp
       │                           │
  ❌ 判断本身就带同样的模型偏见   ✅ 得到 20 个客观的 s(r) 标量
     写错的代码往往"看起来对"        错的就是错的，mismatch 数不会撒谎
       │                           │
  高温噪声无法被过滤 → 净效果变差   噪声被完全过滤 → 只保留探索收益
```

关键在于：**高温采样的收益是 $\max_r s(r)$ 的提升，代价是 $\mathbb{E}[s(r)]$ 的下降。** 只要你有一个可靠的 $\arg\max$ 算子（= 仿真器），代价就不用付。Figure 2 的小提琴图正是这个论断的可视化：高温候选的**均值 mismatch 更低**（蓝点分布整体下移）。

### 创新点 3：State Checkpoint —— 把 pass rate 升级为反例

已在 §4.3 展开。补一句方法论定位：这本质上是把**形式验证里的 counterexample 概念**移植到仿真反馈里。SAT/SMT 求解器判定不可满足时会给出具体赋值，工程师据此定位；MAGE 让 testbench 在功能仿真里也吐出等价物。

同时它是一个**开源化**主张：VerilogCoder 用闭源 AST 分析 + 图形波形工具达到类似效果，MAGE 用"改 testbench 加 `$display`"这个纯文本、零依赖的手段达到——**任何仿真器、任何 LLM 都能用**。论文原话："This shifts the reliance on closed-source tools to a fully open-source LLM-based textual protocol."

### 创新点 4：带回退的爬山式 debug

公式 (4) 保证得分单调不减。这看似是工程细节，实则解决了 LLM 迭代修复的**核心失效模式**：模型改完 A 处，无意中破坏了 B 处，而它自己完全不知道（因为它不跑仿真）。MAGE 让每次修复都过一遍 Judge，分数降了就丢弃。

**代价**：每轮 debug 至少 1 次 LLM 调用 + 1 次完整仿真。这是 MAGE 成本高的直接原因之一。

### 创新点 5：首个开源的多 Agent RTL 系统

论文 Sec II-B 把这条单独列为一个 opportunity："we found that all of them [existing multi-agent systems] are closed-source and dependent on third-party proprietary tools that are not LLM-directly-adapted."

- AIVRIL：只有两个 Agent（生成 + review），且仍让单个 Agent 同时处理可综合 RTL 和非可综合验证代码——没有触及根本问题
- VerilogCoder：闭源，依赖专有 AST 和波形追踪组件

MAGE 全栈开源：Icarus Verilog（编译+仿真）+ LlamaIndex（LLM-agnostic 接口）+ 自身代码 MIT 协议。LLM-agnostic 这点使它能直接跑本地小模型（本地实测用的 Qwen2.5-Coder-1.5B）。

### 创新点 6：与 ChipSeek 的范式对照 —— 推理时编排 vs 训练时 RL

本资料包中，MAGE 与 [ChipSeek](../ChipSeek/论文深度讲解.md) 构成了两条互补的技术路线，理解两者的分野是读懂 AI4EDA Agent 方向的关键。

**根本差异**：

| 维度 | MAGE（推理时编排） | ChipSeek（训练时 RL） |
|------|------|------|
| **改进发生在** | 推理时（inference-time） | 训练时（SFT + CDPO + EDA Reward） |
| **是否需要训练** | 否，直接调用现成 LLM | 是，需 SFT 微调 + CDPO 偏好优化 |
| **反馈信号用途** | 候选排序 + 修复提示（不更新模型） | Reward / Advantage 信号回传更新模型参数 |
| **反馈来源** | 仿真器 mismatch 数（功能正确性） | EDA 综合工具报的面积/延迟 + 功能正确性 |
| **优化目标** | 功能正确（$s(r)=1$） | 功能正确 **+ PPA（功耗/性能/面积）** |
| **每题成本** | 高（20~50 次 LLM 调用 + 多次仿真） | 训练后可单次生成（也可再采样） |
| **跨题知识积累** | 无（每题独立，不跨题学习） | 有（参数吸收共性设计知识） |
| **对基座模型依赖** | 强（94.8% 基于 Claude 3.5 Sonnet） | 训练后弱化（参数已适应 RTL 领域） |
| **EDA 工具参与度** | 轻（仅 Icarus 仿真） | 重（综合 + STA，构成 reward 计算） |
| **适用场景** | 题少、规则变化快、无训练资源 | 有大规模训练题、可承担 RL 训练成本 |
| **开源程度** | 全栈开源（MIT） | 开源（模型权重 + 代码公开） |

**为什么两者互补而非互斥**：

1. **MAGE 解决的是"如何用现有 LLM 最好地写 RTL"**——通过推理时的多 Agent 编排、高温采样、仿真反馈来最大化基座模型的潜力。代价是每题推理成本高，且不积累知识。
2. **ChipSeek 解决的是"如何让 LLM 学会写好的 RTL"**——通过训练时的 RL 闭环，让模型参数吸收 EDA 工具反馈（综合面积/延迟），使模型在推理时甚至不需要多轮反馈就能一次生成 PPA 优化的代码。代价是需要训练数据和训练算力。
3. **理想组合**：用 ChipSeek 的方式训练一个领域特化模型，再用 MAGE 的编排方式在推理时进一步放大——训练时 RL 提升模型的下限（基座能力），推理时编排提升模型的上限（通过多候选 + 反馈迭代）。

**反馈粒度的连续性**：

```text
Vanilla LLM         MAGE               ChipSeek              人类工程师
    │                  │                    │                     │
    │ 无反馈           │ 仿真 mismatch       │ 综合面积/延迟       │ 全部 EDA 指标
    │                  │ (功能正确性)        │ (PPA)               │ + 经验直觉
    │                  │                    │                     │
    └──────────────────┴────────────────────┴─────────────────────┘
         反馈信息量递增，但获取反馈的成本也递增
```

MAGE 和 ChipSeek 在这个谱系上占据相邻但不同的位置。MAGE 证明了"不训练也能做很好"的上限，ChipSeek 证明了"训练能让模型学会物理感知"的下限提升。两者结合（训练时学 PPA + 推理时多 Agent 编排）是当前 AI4EDA RTL 生成方向最自然的下一步。

## 8. EDA 缩写解释

按文中首次出现顺序，每个都给全称 + 一句实质解释：

| 缩写 | 全称 | 是什么 |
|------|------|--------|
| **RTL** | Register Transfer Level（寄存器传输级） | 数字设计的抽象层次：只描述"每个时钟沿，数据从哪个寄存器经过什么组合逻辑流到哪个寄存器"，不指定具体用什么门实现。对应流程阶段 ① |
| **EDA** | Electronic Design Automation（电子设计自动化） | 芯片设计工具链的总称，覆盖综合、仿真、布局布线、验证等全部环节 |
| **HDL** | Hardware Description Language（硬件描述语言） | 描述硬件的编程语言，主流是 Verilog / SystemVerilog / VHDL。和软件语言的本质区别：语句默认**并行**执行（描述的是同时存在的电路），不是顺序执行 |
| **VLSI** | Very Large Scale Integration（超大规模集成电路） | 单芯片集成度达到百万门以上的集成电路 |
| **LLM** | Large Language Model（大语言模型） | 本文中特指 Claude 3.5 Sonnet / GPT-4o / Qwen2.5-Coder 等 |
| **DUT** | Design Under Test（待测设计） | testbench 里被例化、被施加激励、被检查输出的那个模块。公式 (5)(6) 里的 $O_{DUT}$ 就是它的输出 |
| **TB** | TestBench（测试平台） | 一段**非可综合**的 Verilog：生成时钟、施加激励、采集 DUT 输出、和期望值比对。它不会变成硅片上的电路，只在仿真器里跑 |
| **Golden TB** | Golden TestBench（黄金测试平台） | benchmark 提供的标准答案测试平台，含参考实现（reference model）。MAGE 用它来消除自然语言规格的歧义 |
| **AST** | Abstract Syntax Tree（抽象语法树） | 把源代码解析成树状结构。VerilogCoder 用它做代码分析，MAGE 明确**不用**（因为闭源 + LLM 不易消费） |
| **VCD** | Value Change Dump（值变化转储） | 仿真器输出的标准波形文件格式，记录每个信号每次跳变的时刻和新值。是二进制/半结构化的，需要波形查看器（GTKWave 等）才能看 |
| **Pass@k** | — | 代码生成任务的标准指标，见公式 (7) |
| **SFT** | Supervised Fine-Tuning（监督微调） | 用 (输入, 标准答案) 对更新模型权重。**MAGE 不做** |
| **RL** | Reinforcement Learning（强化学习） | 用奖励信号更新模型权重。**MAGE 不做** |
| **DPO** | Direct Preference Optimization（直接偏好优化） | 用偏好对（好答案 > 坏答案）直接优化策略，绕过显式奖励模型。**MAGE 不做**，ChipSeek 的 CDPO 是其变体 |
| **LoRA** | Low-Rank Adaptation（低秩适配） | 参数高效微调方法：冻结原权重，只训练低秩增量矩阵。Table II 中 OriGen 用的是 DeepSeek-Coder-7B + LoRA |
| **PPA** | Power, Performance and Area（功耗、性能、面积） | 芯片设计的三大核心指标。**MAGE 完全不优化 PPA** |
| **GGUF** | GPT-Generated Unified Format | llama.cpp 生态的模型权重量化格式。本地实测用的 Q4_K_M 即 4-bit 量化 |
| **API** | Application Programming Interface（应用程序接口） | 此处指调用商业 LLM 的付费接口 |
| **SDF** | Standard Delay Format（标准延时格式） | 综合/布线后生成的每个门/每条路径的延迟清单，门级仿真时反标入仿真器。MAGE 阶段用不到（阶段 ④ 才需要） |
| **SPEF** | Standard Parasitic Exchange Format（标准寄生参数交换格式） | 从版图提取的走线寄生 RC 参数，后仿真（阶段 ⑪）用 |
| **STA** | Static Timing Analysis（静态时序分析） | 不跑仿真，纯数学枚举所有寄存器到寄存器路径，累加延迟与时钟周期比较。阶段 ⑤ |
| **iverilog / vvp** | Icarus Verilog / 其虚拟机 | 开源 Verilog 编译器 + 仿真执行器。`iverilog -t null` 只做语法/语义检查不生成输出（MAGE 的语法门），`iverilog` 正常编译产生 `.vvp` 文件，`vvp` 执行它产生仿真日志 |

## 9. 与芯片流程的关系

### 10.1 MAGE 在全流程中的位置

```text
  人写规格
     │
     ▼
┌─────────────────────────────────┐
│  ① RTL 设计    ←───┐            │  ← MAGE 在这两格里
│        ↓           │            │     自动循环，
│  ② RTL 功能仿真 ───┘            │     直到 s(r)=1
│    （Judge Agent 判定 s(r)=1）  │
└────────────┬────────────────────┘
             │  ⚠️ 交接面：MAGE 到此为止，后面全靠人和传统工具
             ▼
   ③ 逻辑综合  ← 第一道可能推翻 MAGE 成果的关卡
             ▼
   ④ 门级仿真  ← 第二道
             ▼
   ⑤ STA  ⑥ 形式验证
             ▼
   ⑦ Floorplan → ⑧ Placement → ⑨ CTS → ⑩ Routing
             ▼
   ⑪ 后仿真 → ⑫ DRC/LVS → ⑬ Signoff → ⑭ 流片 → ⑮ 制造 → ⑯ 封测 → ⑰ 芯片
```

### 10.2 「功能仿真通过」和「能做成芯片」之间隔着什么

这是评估 MAGE 实际工程价值时最该问的问题。列举 MAGE 通过而后续阶段会拦截的具体情形：

**在阶段 ③ 逻辑综合被拦下的**：

```verilog
// 情形 A：用 initial 赋初值。仿真器认，ASIC 综合器不认
reg [3:0] count;
initial count = 0;         // ✅ iverilog 跑得好好的
                           // ❌ Design Compiler: 无法综合（ASIC 没有上电初值）

// 情形 B：组合逻辑环。仿真可能收敛，综合必炸
assign a = b & c;
assign b = a | d;          // ❌ 组合环，STA 无法分析，综合报错

// 情形 C：latch 推断。功能"对"，但综合出锁存器
always @(*) begin
  if (sel) out = in;       // ❌ 缺 else → 综合出 latch
end                        //    仿真行为可能恰好符合 testbench，但设计意图是组合逻辑

// 情形 D：不完整敏感列表（Verilog-2001 风格）
always @(a) y = a & b;     // ❌ 少了 b。仿真和综合行为不一致
```

**在阶段 ④ 门级仿真被拦下的**：

```verilog
// 情形 E：阻塞赋值写时序逻辑。RTL 仿真可能碰巧对，门级仿真必错
always @(posedge clk) begin
  q1 = d;                  // 应该用 <=
  q2 = q1;                 // 阻塞赋值 → 综合后行为和 RTL 仿真不一致
end

// 情形 F：跨时钟域无同步器
always @(posedge clk_b) sync_data <= data_from_clk_a;
                           // RTL 零延迟仿真看不出问题
                           // 门级仿真（有 SDF）→ 亚稳态、建立/保持违例
```

**在阶段 ⑤ STA 被拦下的**：MAGE 生成的组合逻辑可能极深（比如 64 位行波进位加法器），仿真完全正确但跑不到目标频率。MAGE 对此**完全无感知**——它的目标函数里没有延迟这一项。

**结论**：MAGE 的 $s(r)=1$ 是**必要条件而非充分条件**。它是一个高质量的"RTL 初稿生成器 + 功能自查器"，把工程师从"写第一版 + 调到功能对"里解放出来，但"从功能对到能流片"这段路它一步没走。

### 10.3 MAGE 用到的三个工具在流程中的角色

| 工具 | MAGE 中的用法 | 在真实芯片流程中的地位 |
|------|--------------|----------------------|
| `iverilog -t null` | RTL Agent 的语法门（最多重试 5 次） | 相当于工程师保存文件后跑的 lint。真实流程里会用更严格的 Verilator lint / Spyglass，能查 latch 推断、敏感列表、CDC 等 MAGE 查不到的问题 |
| `iverilog` + `vvp` | Judge Agent 的功能仿真引擎 | 阶段 ② 的核心。工业界用 VCS / Xcelium / Questa，功能相同但支持 SystemVerilog/UVM、覆盖率、断言 |
| 改造后的 TB（`$display` checkpoint） | 反馈信息载体 | 真实验证环境里对应的是 **scoreboard + monitor**（UVM 术语）。MAGE 相当于把 scoreboard 的比对结果实时打印成文本，供 LLM 消费 |

## 10. 讨论与局限

### 10.1 Golden Testbench 依赖 —— 最致命的一条

MAGE 的整条反馈链条建立在"存在一个可信的期望输出 $O_{exp}(t)$"之上。公式 (5)(6) 全部依赖它。

**在 benchmark 上完全合理**：VerilogEval 每题都自带 golden TB 和 reference model。
**在真实项目里通常不成立**：

- 如果你已经有了完备的 golden testbench，说明你已经**完全理解并形式化了设计规格**——而这往往是 RTL 设计中最难、最耗时的部分。RTL 编码本身反而是相对机械的。
- 循环困境：MAGE 用 TB Agent 从规格生成 TB，但如果规格有歧义（真实项目里必然有），生成的 TB 就会带着歧义的错误理解；然后 RTL 被"修"到符合这个错误的 TB。$s(r)=1$ 变成了自我一致，而非正确。
- 论文 Step 1 的措辞很谨慎："since natural language specifications may contain ambiguities, we combine the input with the golden testbench **if available**"。这个 "if available" 是整篇论文最重要的条件从句。

**这不是 MAGE 独有的问题**，是整个"LLM + 仿真反馈"范式的共同前提。但它决定了 MAGE 当前的适用边界：**benchmark 和已有参考实现的场景**（比如重写遗留模块、跨语言移植、教学）。

### 10.2 计算成本不透明

论文没有报告任何 token 消耗、API 成本或墙钟时间数据。粗略估算单题最坏情况：

```text
Step 1  TB 生成                              1 次 LLM  (+ 若 TB 有误则重生成)
Step 2  RTL 生成（低温）                     1 次 LLM  (+ 最多 5 次语法重试)
Step 3  Judge 打分                           1 次仿真
Step 4  高温采样 20 候选                     20 次 LLM (+ 各自最多 5 次语法重试)
        20 个候选各跑仿真                    20 次仿真
Step 5  Debug × M 轮 × Top-K 候选            M×K 次 LLM + M×K 次仿真
────────────────────────────────────────────────────────────────────
       \approx 20~50 次 LLM 调用  +  20~40 次仿真   vs   vanilla 的 1 次 LLM
```

**这直接影响 Table II 的可读性**：MAGE 的 94.8% 和 GPT-4o 的 51.3% 不在同一个成本量级上。一个公平的对照应该是"vanilla Claude 3.5 Sonnet 采样 20 次 + 用 golden TB 选最好的那个"（即 pass@20 而非 pass@1）——论文没做这个对照。

模型梳理里的判断很准确：*"效果常被'更多 token/更多候选'混淆。研究时必须与 one-shot 在相同总 token、调用次数和候选预算下比较。"*

### 10.3 基础模型强依赖

全部主结果基于 Claude 3.5 Sonnet 2024-10-22。论文没有做跨模型消融。

值得注意的隐含风险：MAGE 的收益公式大致是 `收益 = 探索空间大小 × 基座模型命中概率`。如果基座模型在某题上的正确率接近 0（比如复杂的多时钟域状态机），采 20 个候选也全是错的，$\max_r s(r)$ 依然很低，Debug Agent 也无从下手。**MAGE 放大能力，不创造能力。**

本地 Qwen2.5-Coder-1.5B 的实测只覆盖了 `Prob011_norgate`（一个 NOR 门，最简单的题之一），无法据此推断小模型上的整体表现。

### 10.4 Benchmark 污染风险

VerilogEval-v1（2023 ICCAD）和 v2（2024）都是**完全公开**的数据集，题目和答案都在 GitHub 上。Claude 3.5 Sonnet 2024-10-22 的训练数据截止时间在其后，题目大概率进入了预训练语料。

**这不能证伪 MAGE 的贡献**——因为 vanilla 同模型只有 75.0%，说明记忆不足以解题。但它使**绝对数值**的意义打折：94.8% 反映的是"这个系统在这个已知题库上的表现"，不是"在未见过的设计任务上的表现"。

一个更有说服力的实验会是：在 RTLLM（另一个 benchmark，题目风格不同）或私有题目上复测。

### 10.5 评分函数的结构性盲区

$s(r) = 1 - m(r)/tc(r)$ 有几个内在问题：

**(a) 所有检查点等权。** 一个只在 reset 后第一拍出错的设计（可能是初始化问题，容易修）和一个在 500 个随机激励下有 5 个错的设计（可能是边界条件问题，难修），如果 mismatch 数相同，得分完全一样。但它们的"距离正确的远近"完全不同。

**(b) 覆盖率不在目标里。** $tc(r)$ 只是 testbench 实际跑到的检查点数。如果 TB 生成得很弱（比如只测了 4 个输入组合），$s(r)=1$ 毫无意义。**MAGE 没有任何覆盖率指标**（行覆盖、分支覆盖、FSM 状态覆盖、toggle 覆盖），而这是工业验证的基本要求。

**(c) 局部最优陷阱。** 爬山法 + 单调接受规则意味着：如果正确解需要**同时**修改两处（改一处会让分数暂时下降），MAGE 会拒绝这个中间步骤而卡住。公式 (4) 的 $\arg\max$ 保证了不倒退，但也封死了"先退一步再前进两步"的路径。这在需要重构（而非局部 patch）的场景下是硬伤。

### 10.6 单模块假设

VerilogEval 全部是**单文件、单模块**任务。MAGE 的整套机制——单个 TB、单个 DUT、单个 `s(r)`——都建立在这个假设上。

真实 RTL 设计是**层次化**的：顶层模块例化十几个子模块，子模块又例化更小的模块。此时会遇到：
- 跨模块接口协议（AXI/AHB 握手时序）
- 参数化（`parameter` / `generate` 块）
- 模块间时序约束传递
- 集成后才暴露的 bug（各子模块单测都过，集成失败）

MAGE 对这些完全没有机制。模型梳理里把"多模块"列为最值得进入的方向之一，判断准确。

### 10.7 优化目标缺失整个 PPA 维度

已在 §2 强调，这里补充一个具体后果：LLM 在没有 PPA 压力时倾向于生成**最直白**的代码。比如实现 64 位加法，它会写 `assign sum = a + b;`——综合器会给你一个行波进位加法器（面积小、延迟大）。而人类工程师在高频设计里会显式写超前进位或流水化。

MAGE 生成的 RTL 在功能上是对的，在**微架构质量**上是无优化的。这也是它和 ChipSeek 定位差异的本质：

| 维度 | MAGE | ChipSeek |
|------|------|----------|
| 改进发生在 | 推理时（inference-time） | 训练时（SFT + CDPO） |
| 反馈信号用途 | 候选排序 + 修复提示 | Reward / Advantage 回传更新参数 |
| 反馈来源 | 仿真器 mismatch 数 | EDA 工具报的面积/延迟 + 功能正确性 |
| 优化目标 | 功能正确 | 功能正确 **+ PPA** |
| 每题成本 | 高（20~50 次 LLM + 多次仿真） | 训练后单次生成即可 |
| 跨题知识积累 | ❌ 无（每题独立） | ✅ 参数吸收共性 |
| 适用场景 | 题少、规则变化快、无训练资源 | 有大规模训练题、可承担 RL 成本 |

### 10.8 值得追问的开放问题

1. **$L_W$ 和 $K$ 的敏感性如何？** 论文没有报告这两个超参的消融。$L_W$ 太小丢状态历史、太大退化成全日志，最优值应该和电路的状态深度相关（组合逻辑 vs 深流水线），但论文用的是固定值。

2. **Top-K 的 $K$ 取多少？** 论文正文没给具体数值。$K$ 直接决定 Step 5 的成本（$M \times K$ 次 LLM 调用）。

3. **回退机制会不会导致早停？** 假如某轮 debug 连续 3 次都被回退，系统是继续采样新候选，还是就此放弃？论文只说 "until the iteration limit is reached"，没说迭代上限是多少。

4. **能否把语法门升级为综合门？** 把 `iverilog -t null` 换成 `yosys -p synth`，就能在阶段 ① 直接过滤掉不可综合的代码（§8.2 的情形 A-D），把 MAGE 的输出质量从"仿真通过"提到"可综合且仿真通过"。这是一个成本极低、收益明确的改进——Yosys 是开源的，符合 MAGE 的全开源主张。

5. **checkpoint 机制能否推广到断言（assertion）？** 当前 checkpoint 只记录 I/O 端口。如果 TB Agent 能同时插入 SVA（SystemVerilog Assertions）断言并报告哪条断言失败，反馈会从"输出值不对"升级到"违反了哪条设计性质"——这在时序协议类设计上信息量高得多。

## 12. 一分钟复述版

MAGE 是 UCSD 发在 DAC 2025 的多 Agent RTL 生成系统，**不训练任何模型**。核心三招：

1. **四 Agent 隔离上下文**（TB 生成 / RTL 生成 / Judge / Debug）——因为 testbench 是非可综合代码、RTL 是可综合代码，混在一个对话里会互相污染。消融证明光靠隔离就有 +9.7 个百分点。
2. **高温 $T=0.85$ 采 20 个候选 + 仿真器客观打分 $s(r)=1-m(r)/tc(r)$ 排序**——高温对 RTL 有害的旧结论，前提是没有可靠筛选器；有了 Judge Agent 就翻转了。
3. **State Checkpoint**——改造 testbench 逐拍 `$display` 信号快照，定位最早失配 $t_m$，只把 $[t_m-L_W, t_m]$ 这个窗口给 Debug Agent。把"11 个 mismatch"这种模糊反馈变成"cd=11 时 bit0 该是 1 但得到 0"这种可演绎的反例。

Debug 采用带回退的爬山法，得分单调不减（公式 4）。结果：VerilogEval-Human 94.8%、V2 95.7%，同模型 vanilla 分别是 75.0% 和 72.4%。

**边界**：只覆盖流程阶段 ①②（2/17），依赖 golden testbench，不管 PPA、不管可综合性、不管覆盖率、单模块、成本未披露。
