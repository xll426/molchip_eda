## 1. 一句话定位

**HierSVA 是首个面向"层次化硬件形式验证"的端到端 LLM 三件套：(1) HierSVA-SP（合成管线）——把工业验证方法学（VC Formal + FPV + FTA + FC + assume-guarantee 组合 + 参数交叉展开）封装成一个"LLM-as-actor, 形式工具作 controller"的迭代回路，从 BaseJump STL 342 个分层模块上各解析出一份参考 SVA + 假设 + 假设承诺；(2) HierSVA-DS（数据集）——342 个主集模块（深度 0-9）+ 28 对 deep-eval bug pair（27 个独立模块），每条 RTL 经过 formal-evidence 过滤（FPV 全 prove、FTA 100% 故障检出、FC 无 design statement 落在 formal core 之外）；(3) HierSVA-B（基准）——把"断言质量"拆成 6 个独立 metric 轴（C1 compile、C2-P non-vacuous proof、C2-V vacuity、C3 faithfulness、C4 mutation coverage、C5 formal core coverage），用 static vs agentic 两种模式评估 12 个近期 LLM（含 Claude Opus 4.7、DeepSeek V4 Pro、Gemini 3.1 Pro、GPT-5.5、Qwen 3.6 Max、Kimi K2.6、MiniMax-M2.7、GLM 5.1 等），揭示三个反直觉发现：(a) 模块编译率 67.1% 时，非空 proof 率 82.1% 但 mutation coverage 仅 70.2% 且 formal core coverage 仅 36.2%（最高项 C2-P 到最低项 C5 缺口 46 个百分点——证明单看 pass-rate 严重高估验证强度）；(b) deep subset 211 条 evaluable entries 上 recall 0.87 但 precision 仅 0.60（40% 假阳性，模型把"正确 RTL"误报为有 bug）；(c) agentic 模式 7 轮迭代平均涨 +21.1 pp C2-P、+10.6 pp C4、+13.2 pp C5，但 C4 / C5 单调波动不收敛。**

这句话里的九个技术承重点：

1. **"层次化形式验证"是工业 SVA 的核心痛点** — 大型 SoC 验证必须沿模块层级树 bottom-up 验证：先验证 leaf，把 leaf 的 proven assertions 当 assume，再用 assume-guarantee 缩放验证 parent。**所有现有 LLM-for-SVA benchmark（AssertionBench / FVEval / AssertEval / AssertLLM / VERT / CVDP）都把设计当作 flat 或小模板，不验证 cross-module 假设-承诺链**。HierSVA 是首个直接在 LLM 流程里跑 assume-guarantee composition 的基准
2. **三件套可独立复用** — HierSVA-SP 不依赖 HierSVA-DS（在新的 RTL 库上也能用），HierSVA-DS 不依赖 HierSVA-SP（数据集就是静态的 RTL + SVA bundle），HierSVA-B 不依赖两者（接受任何产出 assertion 文件的 LLM）。这种解耦让研究社区可以**只复用管线 / 只用数据集 / 只跑基准**
3. **6 维 metric 分解** — 不只报"pass-rate"，而把"断言质量"拆成：C1 编译（语法）+ C2-P 非空证明（语义通过）+ C2-V vacuity（是否有意义）+ C3 faithfulness（跟 spec 而不是 RTL）+ C4 mutation coverage（能抓多少注入故障）+ C5 formal core coverage（覆盖设计多少）。**任一断言过了 C2-P 但 C5 = 0% 时仍是"假验证"**
4. **VC Formal 工业级工具链** — 区别于 SymbiYosys 等开源 FV（只支持 SVA 子集 + 非标准扩展），HierSVA 全部跑在 Synopsys VC Formal 上：FPV（formal property verification）+ FTA（formal testbench analyzer）+ FC（formal core）。这是**工业 signoff 流程里真实使用的工具**，不是教学工具
5. **BaseJump STL tapeout-validated RTL** — 342 个模块来自 BaseJump Standard Template Library，这是被多个研究和生产 tapeout 用过的开源 SystemVerilog 标准库。**模块层级深度 0-9，覆盖 8 大类**（bsg_async / bsg_cache / bsg_dataflow / bsg_link / bsg_mem / bsg_misc / bsg_noc / bsg_tag）；每条参考 SVA 都通过 formal evidence filter（FPV prove + FC 100% + FTA 100% 检出）后才被收录
6. **Deep subset 28 bug pair 的双源** — 7 对来自上游 fix commit 提取的"历史真实 bug"，21 对来自 held-out LLM 注入的"合成 bug"（已用 prompt 限定 bug 类型到 5 类：P1 protocol / P2 FSM state / P3 atomicity / P4 corner case / P5 parameter quantitative）。**每条 bug 都有 senior industrial DV engineer 人工评审**：bug well-formedness / patch isolation / spec faithfulness
7. **assume-guarantee 子模块契约 (Contract) 复用** — 验证 parent 时，把 child 的 proven assertion 反向作为 assume，child 的 assumption 反向作为待证 assert。这套机制让 HierSVA 不仅做 leaf 模块，**还能验证 8 层深度模块**（论文 Table 8 显示 L8 = 25.0% FC 等数字）
8. **参数交叉展开 (Type-2 parameter combinations)** — LLM 必须对每个模块的 parameter 分类（Type-1 数据大小 / Type-2 行为模式 / Type-N 综合提示），并构造 param_combinations 让 EDA 工具对每个组合独立验证。这模拟了"用同一份 RTL 在不同参数配置下都跑 FPV"——**这是工业里 PSS / SystemVerilog 参数化测试的标准做法**
9. **发现的"pass-rate 严重高估"现象** — 12 个 LLM 的 C2-P（proof rate）均值 82.1%，但 C5（formal core coverage）均值仅 36.2%，中间掉 46 个百分点。原因是模型倾向于生成"语法对、形式上能 prove、但只触及设计 1/3 区域"的弱断言。**这条发现直接挑战了所有 LLM-for-SVA 论文"pass-rate 涨了 X%"的乐观叙述**——只要它们不报 FC coverage，就无法证明实际验证强度提升

## 2. EDA 阶段映射（①-⑰）

参照 [芯片流程.md](../芯片流程.md) 的 17 阶段标准编号：

| 阶段 | 覆盖 | 说明 |
|------|:---:|------|
| ① RTL 设计 | ⚠️ **数据源** | 数据集 RTL 是 BaseJump STL 已设计好、tapeout-validated 的代码。HierSVA 不做"从 spec 写 RTL"，只**消费** RTL 来生成 SVA。但同时它提供的 pipeline 可以反过来：对同一份 RTL 跑 LLM 反复生成 SVA，对比哪种 LLM 写得对 |
| ② RTL 功能仿真 | ❌ | 仿真验证不在 HierSVA 的工具链里——形式验证不需要仿真（数学证明覆盖所有可达状态） |
| ③ 逻辑综合 | ❌ | 不涉及 |
| ④ 门级仿真 | ❌ | — |
| ⑤ STA | ❌ | — |
| **⑥ 形式验证** | ✅ **核心** | HierSVA 全程在形式验证阶段工作：FPV（证明 SVA）、FTA（mutation 测试）、FC（formal core 分析）。这是论文的唯一目标阶段 |
| ⑦ 布局规划 (Floorplan) | ❌ | — |
| ⑧ 标准单元摆放 (Placement) | ❌ | — |
| ⑨ 时钟树综合 (CTS) | ❌ | — |
| ⑩ 布线 (Routing) | ❌ | — |
| ⑪ 后仿真 | ❌ | — |
| ⑫ 物理验证 (DRC/LVS) | ❌ | — |
| ⑬ 签核 (Signoff) | ⚠️ **评估目标** | VC Formal FPV + FTA + FC 整体在工业 sign-off 流程里被使用；HierSVA 是 sign-off 前的形式化质量闸门 |
| ⑭ 流片 | ❌ | 纯算法 + 数据工作，无 tape-out |
| ⑮ 制造 | ❌ | — |
| ⑯ 封装 + 测试 | ❌ | — |
| ⑰ 芯片到手 | ❌ | — |

**覆盖率: 1/17 核心 + 1/17 数据源 + 1/17 评估目标。** HierSVA 完全聚焦在 ⑥ 形式验证阶段，目标是把 LLM 生成的 SVA 变得**和工业 DV 工程师写的一样好**（甚至达到"通过 formal evidence filter"的程度）。它不解决 RTL 生成质量本身，但和 ① 阶段 LLM-for-RTL 生成（[DecoRTL](../DecoRTL/论文深度讲解.md)、[CASS-RTL](../CASS-RTL/论文深度讲解.md)、[ChipMATE](../ChipMATE/论文深度讲解.md) 等）形成"RTL 生成 → SVA 验证 → formal sign-off"的下游链条。

> ⚠️ **容易误读的边界**：
> - HierSVA **只测形式验证**，不测仿真 / 模拟回归。"实验通过 formal 工具证明"与"实验能跑在 SoC 级 testbench 上"不是同一概念
> - 数据集只覆盖 **BaseJump STL**，**不是工业级全功能 SoC**（OpenTitan、Cortex-M、OR1200 等）。在 BaseJump 上能达到 C5 80% 不代表在完整 SoC 上能
> - VC Formal 是商业工具，**SymbiYosys 等开源 FV 对 SVA 子集支持不全**——把 HierSVA pipeline 移植到开源 FV 可能需要在 SVA 语法上妥协
> - 12 个被评估 LLM 包括 **MiniMax-M2.7**（其实是 MiniMax 的模型，但论文里写的是 MiniMax M2.7），具体能力对比时需注意

### 3.2 中间产物

**(a) 阶段一生成的 SVA 文件**

```systemverilog
module bsg_fifo_assertions
   (input clk, input reset_i,
    input  [width_p-1:0] data_i,
    input               v_i,
    output              ready_o,
    output [width_p-1:0] data_o,
    output              v_o,
    input               yumi_i);

  // ── assume: 环境约束 ──
  // 只约束输入协议，不约束输入值
  assume property (@(posedge clk) disable iff (!reset_i)
    v_i |-> ##[1:5] (v_o || ready_o));

  // ── assert: 内部不变量 ──
  no_overflow: assert property (@(posedge clk) disable iff (!reset_i)
    !full_o || !v_i);

  // ── cover: 关键事件 ──
  fifo_pushed: cover property (@(posedge clk) disable iff (!reset_i)
    v_i && ready_o && !full_o);
endmodule

bind bsg_fifo bsg_fifo_assertions
   #(.width_p(width_p), .depth_p(depth_p))
   i_assertions (.*);
```

## 4. 方法与架构

### 4.1 整体 Pipeline

HierSVA 由**三个相对独立的组件**构成（HierSVA-SP / HierSVA-DS / HierSVA-B），每个都可独立使用：

```text
                HierSVA 端到端 LLM-for-SVA 生态
   ═══════════════════════════════════════════════════════════════

   ┌──────────────────────────────────────────────────────────────┐
   │  HierSVA-SP (Synthesis Pipeline)                             │
   │  ───────────────────────────────                             │
   │  输入: BaseJump STL .v 文件（multi-file, hierarchical）       │
   │                                                              │
   │  Stage 1: RTL Preprocessing                                  │
   │    输入: 原始 .v 文件们                                       │
   │    输出: 展平 + 标准化 + design_info.json + 依赖图           │
   │          ↓                                                   │
   │  Stage 2: Bottom-up Verification  (assume-guarantee)         │
   │    L0 → L1 → ... → L9                                         │
   │    每个 module: 迭代 loop with LLM-as-actor, VC Formal as     │
   │    controller                                                │
   │          ↓                                                   │
   │  Stage 3: Formal Evidence Filter                              │
   │    保留条件: FPV prove ALL + FC 100% in core + FTA 100% detect │
   │          ↓                                                   │
   │  输出: golden/ + json/                                       │
   └──────────────────────────────────────────────────────────────┘

   ┌──────────────────────────────────────────────────────────────┐
   │  HierSVA-DS (Dataset)                                        │
   │  ────────────────────────                                    │
   │  来源: HierSVA-SP outputs + 3 个 LLM (GPT-5.3 Codex,         │
   │         Claude Opus 4.6, DeepSeek V3.2) → formal filter      │
   │                                                              │
   │  rtl/                预处理后的 BaseJump STL                  │
   │  golden/             每模块参考 SVA bundle                   │
   │  json/               层级化 manifests                        │
   │  buggy_rtl/          21 synthetic bugs                        │
   │  buggy_rtl2/         7 real-history bugs                      │
   │  spec/               27 NL module specifications              │

   │  ────────────────────────                                    │
   │  输入: HierSVA-DS, 评估的 LLM                                │
   │                                                              │
   │  S1: Static mode × 12 LLMs × 342 modules → C1/C2/C4/C5       │

   │                                                              │
   │  输出:                                                      │
   │    Table 4-9 (tables)                                         │
   │    Figure 2 (per-iteration trajectories)                      │
   │    Confusion matrices per model                               │
   └──────────────────────────────────────────────────────────────┘
```

### 4.2 模块 1：HierSVA-SP §3.2 RTL Preprocessing

5 个独立 pass，按顺序执行：

| Pass | 工具 | 输出 |
|---|---|---|
| macro expander | SystemVerilog 解析 | ``\`define` / ``\`include` 展平 |
| module dependency graph builder | 自研 | DAG, 标 leaf |
| comment filter | 可选 | 去注释 |
| syntax normalizer | 自研 | whitespace / port / param 风格统一 |
| design info extractor | 自研 | design_info.json (clk / rst polarity / latch / combinational) |

latch-containing 与 non-combinational 标签沿 dependency graph 自底向上传播：parent 继承任一 child 的 latch-containing 标签。

### 4.3 模块 2：HierSVA-SP §3.3 Hierarchical Composition

沿 module dependency DAG 自底向上验证：

```text
L0 (150 modules)
   ↓ leaf：跑 HierSVA-SP §3.4 的 iterative loop
   ↓ 输出: leaf_assertions.v (each SVA proven under leaf contract)
L1 (61 modules)
   ↓ parent：把 L0 child 的 proven → assume
   ↓ 把 child 的 assumption → 待证 assert
   ↓ 用 L1 自己的 logic 跑 iterative loop
   ↓ 输出: L1_assertions.v (use L0 as contracts)
L2 (27 modules)
   ↓ ...
L9 (1 module)
   ↓ 把所有 L0..L8 当 contract；只剩 bsg_top + bsg_chip_arb
```

子模块以下被 blackbox，parent 只看 direct child contract——把"形式验证规模爆炸"问题通过 assume-guarantee 隔离到一层。

### 4.4 模块 3：HierSVA-SP §3.4 Iterative Synthesis Loop

每个模块内部跑 iterative loop（论文 Figure 1）：

```text
        RTL ─→ ① 收敛? ─Y→ Done
            │ N
            ▼
        Prompt Builder ② ─→ LLM ─→ assertions.v + param_combinations
            │                  ↑
            │                  │ JSON object (verified, no commentary)
            ▼                  │
        FPV ③ ─→ 5 stage checks ─→ per-stage status / per-property verdict
            │                      (parsed by static rule-based parser)
            │ FPV Fatal? Y → Abort
            │
            ▼
        FC & FTA ④ ─→ informal checks
            │
            ▼
        convergence check ⑤ ─→ 收敛? / Plateau 3 轮? / MAX_ITER 达?
            │
            ├─ 收敛 → Done
            ├─ Plateau / MAX_ITER → exit
            └─ 未收敛 → Debug Prompt Builder ⑥ → Prompt Builder ⑦ → 回到 ②
```

LLM 在每轮可以修改两个工件：`assertions.v` 和 `param_combinations`。每个 parameter 必分类为：

| 类型 | 性质 | 是否进 param_combinations |
|---|---|---|
| Type-1 (Sizing/Structural) | width / depth / count，不改 behavior | 默认值 + 1 个边界 |
| Type-2 (Behavioral/Mode) | mode 切换 / 优先级 / 操作类型 | **所有合法值的 cross-product** |
| Type-N (Non-functional) | 综合提示（harden / strength / debug） | 不变 |

EDA 工具对 `param_combinations` 每个实例独立验证。

### 4.5 模块 4：HierSVA-DS §4.x 数据集构造

来源：跑 HierSVA-SP on BaseJump STL，用以下 3 个 LLM 之一跑：

- GPT-5.3 Codex
- Claude Opus 4.6
- DeepSeek V3.2

两种过滤器：

- **Formal Evidence Filter**（主集必备）：FPV 全 PROVEN + FC 100% in core + FTA 100% 检出 → 才作为参考断言
- **Expert Review Filter**（deep subset 额外）：senior industrial DV engineer 对每条 reference assertion 做评审，对 bug pair 做 well-formedness / patch isolation / spec faithfulness 检查

**Deep subset 的 bug 来源**：

- 7 对：recovered from upstream fix commits（开源 BaseJump 仓库历史）
- 21 对：generated by held-out LLM（与主集 LLM 不同的另一模型，按 5 类 bug pattern 注入）

### 4.6 模块 5：HierSVA-B §5 Metric 分解

**6 个 metric 轴**（按是否参与三层评估汇总）：

| Metric | 粒度 | 来源 | 参与评估 |
|---|---|---|:---:|
| **C1** Syntax Correctness | module-level binary | VC Formal 编译是否过 | S1 ✓ S3 ✓ |
| **C2-P** Assertion Proof Success (non-vacuous) | property-level % | FPV PROVEN 比例 | S1 ✓ S3 ✓ |
| **C2-V** Vacuity | property-level % | FPV VACUOUS 比例 | S1 ✓ |
| **C3** Faithfulness | module-level (P/R/F1/Acc) | deep subset, 在 buggy + correct RTL 上都跑 | S2 ✓ |
| **C4** Mutation Coverage | fault-level % | FTA on eligible 故障集 | S1 ✓ S3 ✓ |
| **C5** Formal Core Coverage | design-statement-level % | FC union of all asserts | S1 ✓ S3 ✓ |

**三种评估 setting**：

- **S1**：12 LLMs × static mode × main set → 报 C1/C2-P/C2-V/C4/C5
- **S2**：12 LLMs × static mode × deep subset → 报 C3
- **S3**：5 LLMs × agentic mode × 40 modules × ≤7 iters → 报 C1/C2/C4/C5 的 trajectory

### 4.7 模块 6：HierSVA-B §5.1 / §5.2 Task & Confusion Matrix

**Static mode task**：prompt LLM 一次，吐 `assertions.v + bind_command` → VC Formal 在所有 param_combinations 上跑 FPV + FTA + FC → 按 verdict 统计各 metric

**Agentic mode task**：LLM 进入 HierSVA-SP §3.4 同样的 iterative loop；最多 7 轮；记录 C1/C2/C4/C5 在每轮的轨迹

**Deep-subset task（S2）**：把每个 module 的 "spec" + buggy_rtl 同时塞给 LLM（提示是"spec 是 source of truth"）；生成 SVA 后分别在 buggy RTL 和 correct RTL 上跑 FPV，得到混淆矩阵：

|  | Buggy RTL: at least one assertion fails (b=1) | Buggy RTL: no fail (b=0) |
|---|:---:|:---:|
| **Correct RTL: no fail (c=0)** | Spec-Aligned (TP + TN) | Mirror-RTL / accepts both (FN + TN) |
| **Correct RTL: at least one fail (c=1)** | Broken: over-strong (TP + FP) | Broken: spurious and missing (FN + FP) |

- **Spec-Aligned** = 真验证（理想）
- **Mirror-RTL** = 跟着 RTL 描述，没照 spec（验收标准失败）
- **Broken** = 在 correct RTL 上也报错（无法部署）

## 5. 关键公式

论文核心是评估，不是预测，所以公式集中在 C1-C5 的定义和 confusion matrix 的派生。

### 5.1 C1 — Syntax Correctness（module-level binary）

$$
C1(m) = \mathbb{1}\!\left[\, \mathrm{VCFormalCompile}(L_m) = \text{success} \,\right]
$$

- $L_m$：LLM 对模块 $m$ 生成的 SVA 文件
- $\text{success}$：parsing 通过、无 fatal error
- $C1 \in \{0, 1\}$

### 5.2 C2-P — Non-Vacuous Proof Rate

$$
\mathrm{C2\!-\!P}(m) = \frac{|\{\, p \in \mathrm{asserts}(L_m) \;|\; \mathrm{FPV}(L_m, p) = \mathrm{PROVEN} \,\}|}{|\{\, p \in \mathrm{asserts}(L_m) \;|\; \mathrm{FPV}(L_m, p) \in \{\mathrm{PROVEN}, \mathrm{VACUOUS}\} \,\}|}
$$

- FPV verdicts：$\{\mathrm{PROVEN}, \mathrm{VACUOUS}, \mathrm{FALSIFIED}, \mathrm{INCONCLUSIVE}\}$
- PROVEN 表示 "非空证明 + 设计确实满足"；VACUOUS 表示 "形式上通过但 antecedent 永远不成立"

### 5.3 C2-V — Vacuity Rate

$$
\mathrm{C2\!-\!V}(m) = \frac{|\{\, p \in \mathrm{asserts}(L_m) \;|\; \mathrm{FPV}(L_m, p) = \mathrm{VACUOUS} \,\}|}{|\{\, p \in \mathrm{asserts}(L_m) \;|\; \mathrm{FPV}(L_m, p) \in \{\mathrm{PROVEN}, \mathrm{VACUOUS}\} \,\}|}
$$

- $\mathrm{C2\!-\!V}(m)$ + $\mathrm{C2\!-\!P}(m)$ 之和 ≈ 1（在 PROVEN/VACUOUS 池中）

### 5.4 C3 — Faithfulness（module-level）

对每个 model × module entry：

- 在 buggy RTL 上跑 FPV：得到 $b \in \{0, 1\}$（是否有断言失败）
- 在 correct RTL 上跑 FPV：得到 $c \in \{0, 1\}$（是否有断言失败）

**变体级 (variant-level) 混淆矩阵元素**：

| 案例 | TP | FN | FP | TN |
|---|---|---|---|---|
| $(b=1, c=0)$ | +1 | | | +1 |
| $(b=0, c=0)$ | | +1 | | +1 |
| $(b=1, c=1)$ | +1 | | +1 | |
| $(b=0, c=1)$ | | +1 | +1 | |

**Precision / Recall / F1 / Accuracy**：

$$
P = \frac{\mathrm{TP}}{\mathrm{TP} + \mathrm{FP}}, \quad R = \frac{\mathrm{TP}}{\mathrm{TP} + \mathrm{FN}}
$$

$$
F_1 = \frac{2 P R}{P + R}, \quad \mathrm{Acc} = \frac{\mathrm{TP} + \mathrm{TN}}{\mathrm{TP} + \mathrm{TN} + \mathrm{FP} + \mathrm{FN}}
$$

### 5.5 C4 — Mutation Coverage (FTA)

对一组 eligible faults $F$（来自 limit.json 手工审计），

$$
\mathrm{C4}(m) = \frac{|\{\, f \in F \;|\; \mathrm{FTA}(L_m, f) = \mathrm{DETECTED} \,\}|}{|F|}
$$

- $F$：手工审计的 fault 集合，排除了"无法被 SVA 表达"的故障（如纯注释 typo）

### 5.6 C5 — Formal Core Coverage

定义形式核心 $\mathrm{FC}(p)$ 为证明 SVA $p$ 所需的设计语句集合。

对 $\mathrm{asserts}(L_m)$ 的所有 $p$：

$$
\mathrm{FC}_m = \bigcup_{p \in \mathrm{asserts}(L_m)} \mathrm{FC}(p)
$$

$$
\mathrm{C5}(m) = \frac{|\mathrm{FC}_m \cap \mathrm{COI}|}{|\mathrm{COI}|}
$$

- $\mathrm{COI}$：module 的 cone-of-influence（与验证相关的所有语句）
- $\mathrm{C5}(m)$ ∈ [0, 1]，越接近 1 表示断言触达的设计部分越多

### 5.7 Dilution Gap（论文 §6.4 探索性诊断）

$$
\mathrm{Dilution}(m) = \mathrm{C2\!-\!P}^{\mathrm{macro}}(m) - \mathrm{C2\!-\!P}^{\mathrm{micro}}(m)
$$

- macro：每模块"全证明"率的算术平均
- micro：按总 assertion 加权平均的"全证明"率
- 正 dilution：典型模块比"加权的"还强；负 dilution：模型在某些模块写了大量好 assertion 拉高加权平均

## 7. 创新点

### 7.1 首个工业级层次化 LLM-for-SVA 基准

**贡献**：把"LLM 在硬件形式验证上"这件事从 academic 推到了 industrial practice——用 VC Formal（不是 SymbiYosys）、BaseJump STL（不是 toy / template）、assume-guarantee composition（不是 flat verification）、industrial DV engineer review（不是 only auto-metric）。

**对比**：

| Benchmark | LLM 类型 | 验证模式 | 报告 vacuity? | 报告 mutation coverage? | 报告 formal core? |
|---|---|---|:---:|:---:|:---:|
| AssertionBench | 100 / OpenCores | Formal (JasperGold) | ❌ | ❌ | ❌ |
| FVEval | 79+300+192 / Expert+synth | Formal | ❌ | ❌ | ❌ |
| AssertEval | 18 / Open-source | Formal | ❌ | ❌ | FC |
| AssertLLM | 20 / Open-source | Formal | ❌ | ❌ | ❌ |
| VERT | fragments / Synthetic | Dataset-only | ❌ | ❌ | ❌ |
| CVDP cid14 | 98 / Human | Sim | ❌ | ❌ | ❌ |
| **HierSVA** | **342 main + 28 deep** | **Formal (VC Formal)** | **✅** | **✅** | **✅** |

### 7.2 6 维 metric 拆解 + 3 维 setting 矩阵

**贡献**：把"断言质量"这一通常用单一 pass-rate 表达的概念拆成 **6 个独立轴 × 3 种 setting × 12 个模型** = **216 个独立数据点**。让"哪个模型擅长什么"这类问题可以被精确回答。

**意义**：例如"Kimi K2.6 的 C4 = 89.0% 但 C1 = 64.4%"——这种粒度的诊断在前 LLM SVA 时代是不可能得到的。

### 7.3 Pass-rate 高估现象的实证揭示

**贡献**：明确测出 C2-P 平均 82.1% 与 C5 平均 36.2% 之间 **46 个百分点的缺口**。这意味着：用一个 LLM 自动写的 SVA 即使"形式化通过"，**也只覆盖了设计的约 1/3**。

**意义**：所有之前 LLM-for-SVA 论文报告"pass-rate 涨 X 个点"都应该重新审视——如果它们没报 FC coverage 或 mutation coverage，**结果不能直接解读为"验证强度改善"**。

### 7.4 三件套解耦设计

**贡献**：HierSVA-SP、HierSVA-DS、HierSVA-B 三个组件可独立使用：

- 想要新 RTL 库跑 synthesis → 单独用 HierSVA-SP
- 想要新 SVA / 形式验证 benchmark → 用 HierSVA-DS
- 想要在新模型上评估 → 用 HierSVA-B

**意义**：任何后续工作（Sangam [ICLAD'25] / AssertionForge [ICLAD'25] / Spec2Assertion [2025] / LASA / LASSO）都可以 attach 到这套基础设施上，无需重复造轮子。

### 7.5 Deep Eval Subset 的双源 + 人工审查

**贡献**：28 对 bug pair 中 7 对来自上游 fix commit（real-world bugs），21 对来自 held-out LLM 注入（synthetic bugs）——但**所有 28 对都过 senior industrial DV engineer review**：bug well-formedness / patch isolation / spec faithfulness。

**意义**：把 "synthetic bug injection" 这一研究方法学的可信度从"LLM 自己注入自己看"提升到 "人工审计确认过"。

### 7.6 Agentic 模式的震荡不收敛发现

**贡献**：明确展示 agentic loop（S3, 7 轮）对 C4 / C5 不会单调改善——模型在"删除 falsified 断言 → 重新引入"的循环里反复震荡。

**意义**：揭示了当前 agentic-FV workflow 的结构性弱点，提示未来工作需要"防震荡"机制（例如定期保持 C4 metric 最低阈值不更新低于它的版本）。

## 10. 讨论与局限

### 10.1 论文自述局限

#### 局限 1：Main Set 不全 0 编译率

7 个 LLM 的 C1 低于 70%（DeepSeek V4 Flash 59.6%, GPT-5-mini 55.0%, Claude Haiku 58.1%, Kimi 64.4%）。**这些模型在 30+% 模块上直接输出"不能编译"的 SVA**，意味着它们的输出对工业部署而言还需人工过滤

#### 局限 2：Agentic 模式震荡不收敛

论文 Figure 2 显示 C4 / C5 在多轮迭代后**不单调改善**——agentic loop 自身有结构性弱点。论文没有给出 "convergence guarantee" 或 "plateau detection improvement"

#### 局限 3：Deep Subset 偏向少量可评估 entries

MiniMax-M2.7 仅 1 个 evaluable entry（C1 太低），DeepSeek 系 4 个模型也只 16-20 个。**evaluable entries 数少**让 P/R 估计方差大

#### 局限 4：仅 BaseJump STL，覆盖 RTL 风格单一

BaseJump 是 tapeout-validated 但**风格相对统一**（来自同一作者团队）。OpenTitan、Cortex-M0 等其他工业 RTL 风格未覆盖。论文提到的 "BaseJump 工业真实性" 是优势也是局限——它**不能代表所有工业 RTL**

#### 局限 5：VC Formal 闭源

NDA 限制让 raw EDA tool logs 不能公开。复现者必须有 VC Formal license——这对学术界 + 开源界是显著门槛。论文建议 SymbiYosys 作为替代，但明确指出 SVA 子集支持差异

#### 局限 6：人工评审预算限制

342 模块全过 industrial DV engineer review 会超预算。所以只在 28 个 deep subset 上人工评审。这意味着**主集 SVA 的正确性完全靠 formal-evidence filter 间接保证**，没有直接的人工 ground truth

### 10.2 代码 / 复现层面的问题

- **GitHub HierSVAAnon/HierSVACodeAndArtifacts**：双盲投稿，匿名仓库。本地资料包生成时无法直接核验 commit；建议复现前对照论文附录 B 的 prompt template 一致性
- **HuggingFace AnonymousHierSVA/HierSVA**：匿名数据集。同样原因无法核验版本
- **VC Formal license**：Synopsys 商业工具，需要通过 Synopsys 学术 program 申请、或付费 license
- **LLM gateway**：用 OpenRouter，但 12 个评估模型里有几个（GPT-5.5 / Claude Opus 4.7 / Qwen 3.6 Max）的具体 API endpoint 需要付费

### 10.3 本资料包的批判性分析

1. **Hierarchical 合成的"子模块假设"假设过强**：论文假设"验证 leaf 后，leaf 的 SVA 可以反向作 parent 的 assume"。但工业里 assume-guarantee 需要证明 (environment 满足 assume → 满足 assertion) — HierSVA 用 FPV 跑 assume 不能保证这条 chain 完整（assume 的接口契约可能在更上层的语境下失效）。一种更严谨的方法是用 IC3 / k-induction 风格的 inductive proof
2. **C5 的归一化基准（COI）也有歧义**：用 cone-of-influence 做分母意味着"设计越大，C5 越容易小"。但工业里常用 "active statements in scope" 作为分母——不同分母导致同一 C5 数字意义不同。论文需要更清晰定义
3. **Deep subset 是 LLM-generated**：28 对 bug pair 里 21 对是 "held-out LLM 注入"，这意味着 bug pattern 偏向 LLM 能模拟的类型。对人类真的在 signoff 阶段发现的 bug（如 race condition 跨时钟域）可能代表性不足
4. **Agentic 模式只跑了 5 个模型**：S3 的 5 × 40 = 200 个 (model, module) pair（每个 pair 跑 7 轮迭代），相比 S1 的 4104 个 pair 样本量小一个数量级。结论的 robustness 受限
5. **没有 SVA "correctness axiom" 维度**：HierSVA-B 全部从工具 verdict 推断 SVA 质量，没有任何 "ground-truth SVA" 来直接对比。在主集层级，**reference SVA 也只是"被形式化证明 + 通过 formal evidence filter"**，并不一定是"ideal SVA"
6. **Dilution gap 的解读过宽**：§6.4 把 C2-P macro − C2-P micro 的差异解读为 "distribution diagnostic"，但其实它高度依赖 "评估的模块数量 / 每个模块的 assertion 数"。论文没明确说"两个 LLM 比 dilution gap 是否公平"——其实 LLM A 在 100 个模块上每个写 5 条 vs LLM B 在 50 个模块上每个写 50 条时，micro 含义就差很大
7. **缺少"断言的最小化"参考**：一种强的 verifier 应能找出"最少 / 最必需的" SVA 集合；论文没有 baseline 对比这条

## 12. 一分钟复述版

1. **核心问题**：现有 LLM-for-SVA benchmark（AssertionBench / FVEval / AssertEval / AssertLLM / VERT / CVDP）规模小、设计 flat、只报 pass/fail，**不能评估 LLM 在工业级层次化形式验证上的真实强度**
2. **方法概述**：HierSVA = ① SP（合成管线）：macro expand → dep graph → bottom-up assume-guarantee → iterative loop with VC Formal feedback → formal evidence filter；② DS（数据集）：342 BaseJump STL 模块 + 28 bug pair（7 real + 21 synthetic-with-human-review）；③ B（基准）：6 维 metric (C1/C2-P/C2-V/C3/C4/C5) × 3 维 setting (S1/S2/S3) × 12 模型（OpenRouter gateway）
3. **核心数据**：12 LLM 主集平均 C1=67.1%, C2-P=82.1%, C2-V=2.7%, C4=70.2%, C5=36.2%；deep subset aggregate R=0.87 / P=0.60 / F1=0.71 / Acc=0.65；agentic 平均涨 +21.1 pp C2-P, +10.6 pp C4, +13.2 pp C5（但 C4/C5 震荡）
4. **关键结果**：C2-P (82.1%) → C5 (36.2%) **落差 46 pp** 揭示 "pass-rate 严重高估验证强度"；C5 随深度 L0=75.5% → L8=5.9% 验证"深层 hierarchy 是共同难题"；agentic 在 C4/C5 上**不收敛**
5. **最大创新点**：三件套解耦 + 6 维 metric 拆解 + 工业级工具链（VC Formal + BaseJump STL + 工业 DV 评审）+ "pass-rate 高估"现象的实证
6. **EDA 流程位置**：⑥ 形式验证阶段，下游接 ⑥ 的 signoff，但不生成 RTL、不做综合
7. **与同类工作的关系**：上游链上与 [DecoRTL](../DecoRTL/论文深度讲解.md) / [CASS-RTL](../CASS-RTL/论文深度讲解.md) / [ChipMATE](../ChipMATE/论文深度讲解.md) 等 ① RTL LLM 生成互补；同领域（形式 / SVA）与 [OpenSource-Formal-RTL](../OpenSource-Formal-RTL/论文深度讲解.md)、[CktFormalizer](../CktFormalizer/论文深度讲解.md)、[VClare](../VClare/论文深度讲解.md)、[AutoVCoder](../AutoVCoder/论文深度讲解.md)、[SynC-LLM](../SynC-LLM/论文深度讲解.md) 等形成家族；与 Sangam / AssertionForge / Spec2Assertion / LASA / LASSO 等都同方向，独立方法
8. **局限**：VC Formal 闭源 + 工业 license；BaseJump STL 风格单一；deep subset evaluable 数少；agentic C4/C5 震荡不收敛；main set 缺人工 ground truth；C5 分母定义有歧义；缺"最小必需 SVA"baseline
