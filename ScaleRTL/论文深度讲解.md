## 1. 一句话定位

**ScaleRTL 是 NVIDIA 提出的「首个面向 RTL 编码的推理型 LLM」：从 500 万条抓取的 Verilog 脚本经多阶段过滤保留 62K 高质量脚本 (≈200M tokens)，再让 DeepSeek-R1 对每条脚本反向生成平均 56K tokens 的长 CoT 推理轨迹，最终得到 3.5B tokens 的 <规格, 推理, 代码> 三元组数据集，在 DeepSeek-R1-Distill-Qwen-32B 上做 SFT 后得到 ScaleRTL；推理阶段则通过反复把 `</think>` 替换成「Wait, my reasoning must be incorrect. Let's check the reasoning rules...」的纠错 prompt，让模型反思并自纠正之前的推理步骤（ScaleRTL† 变体）。最终在 VerilogEval / RTLLM v1.1 上以 32B 规模超越 18 个基线（最大 +18.4% pass@5 on VerilogEval，+12.7% pass@5 on RTLLM），同时在 HumanEval/MBPP/IFEval 三个通用基准上保持甚至超过 DeepSeek-R1-Distill-Qwen-32B 原版的通用能力。**

这句话里的 7 个技术承重点：

1. **「首个推理型 RTL LLM」**：区别于 RTLCoder / CodeV / CraftRTL 等「非推理型」模型——ScaleRTL 引入 reasoning trace 训练 + test-time self-reflection scaling，能在生成代码前先思考。
2. **「3.5B tokens CoT 数据」**：62K 高质量脚本 × 平均 56K tokens 推理 trace = 3.5B，是 CodeV (165M) 的 21 倍、CraftRTL (110M) 的 32 倍、RTLCoder (6M) 的 583 倍（Table 1）。
3. **「过滤 pipeline 保质量」**：从 500 万条原始 snippet (189B tokens) 经「dedup → 去 64K+ → 语法验证 → Jaccard 5-gram 去污染 (阈值 0.8) → embedding 语义相似度过滤」五级筛到 62K，每一级都有具体技术细节。
4. **「两阶段 CoT 数据生成」**：第一步 prompt DeepSeek-R1 从 Verilog 脚本反向生成 specification（沿用 OSS-Instruct 思路）；第二步再 prompt DeepSeek-R1 以 specification 为输入生成 <think>...</think> 推理 + <answer>...</answer> 代码，由 R1 原生的特殊 tag 结构保证可靠拆分。
5. **「SFT 损失同时建模推理 + 代码」**：$\mathcal{L}_{SFT}$ 对推理轨迹 $r$ 和最终代码 $y$ 联合取负对数似然，鼓励模型先想后写。
6. **「Test-time iterative self-correction」**：推理失败时把 `</think>` 换成「Wait, my reasoning must be incorrect. Let's check the reasoning rules: {R}. Wait, I did not follow the rules. Let's try again.」让模型继续生成，最多 T 次迭代。论文实验显示 reasoning token 数与 pass@k 呈对数型 scaling 关系。
7. **「SOTA 且不损通用能力」**：在 VerilogEval pass@1 上超最强 prior baseline 10.7%，pass@5 上超 18.4%；同时在 HumanEval 65.2%/MBPP 75.0% 仍优于 DeepSeek-R1-Distill-Qwen-32B 原版 49.1%/71.3%，IFEval 73.2% 仅略低于 76.8%。

### 4.2 Phase 1-A: 数据过滤 Pipeline（5M → 62K）

论文用五级漏斗过滤原始 snippet：

```text
原始 5M snippet (189B tokens)
     │
     ▼ ① 去重（exact duplicate removal）
     ▼ ② 长度截断：删除 > 64K tokens（视为机器生成）
     ▼ ③ 语法验证：合法 Verilog 保留
     ▼ ④ Jaccard 5-gram 去污染（与 benchmark golden）
     │   Jaccard(A,B) = |T5(A) ∩ T5(B)| / |T5(A) ∪ T5(B)|
     │   阈值 0.8，> 0.8 则丢弃
     ▼ ⑤ Embedding 语义相似度过滤
     │   删除与 RTL benchmark 分布显著偏离的 outlier
     62K 高质量脚本 (200M tokens)
```

**Jaccard 5-gram 去污染公式**：

$$
J(A,B) = \frac{|T_5(A) \cap T_5(B)|}{|T_5(A) \cup T_5(B)|}
$$

其中 $T_5(\cdot)$ 表示从脚本中提取的所有 5-gram 集合（unique）。论文用阈值 0.8 严格防止 benchmark 泄漏。

**为什么选 5-gram**：相比 1-gram（太宽松）和 10-gram（太严格），5-gram 是经验最优——既能捕获代码片段级相似度，又对变量重命名等无关修改鲁棒。

### 4.3 Phase 1-B: CoT 数据生成

论文借鉴 OSS-Instruct（Wei et al. 2023）的两阶段策略，但用 DeepSeek-R1 替代普通 LLM：

```text
Step 1: 反向生成 specification
┌──────────────────────────────────────────────────────┐
│ Prompt: "You are an expert Verilog engineer. Generate │
│  a Verilog problem inspired by the following code.    │
│  Enclose the problem in <PROBLEM></PROBLEM> tags."   │
│ Input: 一条高质量 Verilog snippet                     │
│ Output: <PROBLEM>...</PROBLEM>（自然语言规格）       │
└──────────────────────────────────────────────────────┘
              │
              ▼
Step 2: 生成 <推理, 代码>
┌──────────────────────────────────────────────────────┐
│ Prompt: "Solve this Verilog problem step-by-step.     │
│  Enclose reasoning in <think></think>, code in        │
│  <answer></answer>."                                 │
│ Input: spec + reference code (作 inspiration)         │
│ Output: <think>...</think> (推理 trace)               │
│         <answer>...</answer> (Verilog 代码)          │
└──────────────────────────────────────────────────────┘
```

**为什么靠 DeepSeek-R1 的特殊 tag 自动拆分**：R1 原生就用 `<think>` 包推理、`</answer>` 包答案。论文直接利用这种结构化格式，**无需额外的解析器**就能可靠地把推理和代码分开。

**数据集统计对比**（Table 1）：

| 方法 | # Samples | Avg Tokens/Sample | Total Tokens |
|------|:---:|:---:|:---:|
| RTLCoder | 26K | 0.2K | 6M |
| MG-Verilog | 11K | 1.5K | 16M |
| OriGen | 222K | 0.6K | 139M |
| CodeV | 165K | 1K* | 165M* |
| CraftRTL | 110K | 1K | 110M |
| **ScaleRTL** | **62K** | **56K** | **3.5B** |

平均每样本 tokens 从 ~1K 跃升到 56K，总量提升 21~583 倍。

### 4.4 Phase 1-C: 联合 SFT 损失

每个训练样本是三元组 $\langle x, r, y \rangle$，其中 $x$ = spec, $r$ = reasoning trace, $y$ = code solution。

$$
\mathcal{L}_{\text{SFT}}(\theta) = - \sum_{i=1}^{N} \left( \sum_{t=1}^{|r^{(i)}|} \log P_\theta(r_t^{(i)} | x^{(i)}, r_{<t}^{(i)}) + \sum_{t=1}^{|y^{(i)}|} \log P_\theta(y_t^{(i)} | x^{(i)}, r^{(i)}, y_{<t}^{(i)}) \right)
$$

**关键设计**：

- 第一项：$P_\theta(r_t | x, r_{<t})$ — 给定 spec 和之前的推理，预测下一个推理 token
- 第二项：$P_\theta(y_t | x, r, y_{<t})$ — 给定 spec + **完整推理** + 之前的代码，预测下一个代码 token
- **顺序不可换**：必须先生成完整 $r$ 再生成 $y$（即条件概率 $y$ 依赖 $r$）— 这强迫模型「先想后写」

**为什么不像标准 SFT 那样 mask 掉 prompt**：在 RTL 任务里，**推理步骤本身就是答案的一部分**。Mask 掉推理会丢掉这部分监督，导致模型只学到「生成代码」而学不到「如何推理」。

### 4.5 Phase 2: Test-Time Iterative Self-Correction

Algorithm 1 的核心循环：

```text
Algorithm 1 Iterative Test-Time Scaling for RTL Coding
┌────────────────────────────────────────────────────────┐
│ Input:  M (微调模型), P (测试问题), R (reasoning rules),│
│         T (最大迭代次数)                                │
│ Output: T (最终推理 trace), S (RTL solution)            │
│                                                        │
│  1: T ← Inference(M, P)              # 首次推理          │
│  2: S ← ExtractSolution(T)                              │
│  3: t ← 0                                              │
│  4: while t < T and not IsCorrect(S):                   │
│  5:   delete S after </think> in T                     │
│  6:   append "Wait, my reasoning must be incorrect.     │
│  7:           Let's check the reasoning rules: {R}.    │
│  8:           Wait, I did not follow the rules.         │
│  9:           Let's try again."                         │
│ 10:   T ← Inference(M, T)            # 用纠正后 trace   │
│ 11:   S ← ExtractSolution(T)          # 作为新 prompt   │
│ 12:   t ← t + 1                                         │
│ 13: return T, S                                         │
└────────────────────────────────────────────────────────┘
```

**和朴素 "Wait" trick 的本质区别**：

```text
朴素 s1 方法：                ScaleRTL 方法：
┌─────────────┐              ┌─────────────────────┐
│ ...reasoning│              │ ...reasoning        │
│ </think>    │              │ </think>            │
│ <answer>    │              │ (delete <answer>)   │
│ code        │              │ + "Wait, ... {R}    │
│ </answer>   │              │  Let's try again."  │
└─────────────┘              └──────────┬──────────┘
       │                              │
       ▼                              ▼
  append "Wait"                feed back to M
       │                              │
       ▼                              ▼
  Model continues              Model extends reasoning
  (often repeats               (revisits specs, fixes bugs,
   same answer)                generates new code)
```

朴素 trick 只追加 "Wait"，模型常「同意自己之前的结论」并重复原始 code。ScaleRT 删除原始 code 并插入「reasoning rules 检查」+「Let's try again」，让模型**真正反思**而非敷衍。

## 5. 关键公式

### 5.1 pass@k 指标（无偏估计器）

$$
\text{pass@k} = \mathbb{E}_{\text{Problems}} \left[ 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}} \right]
$$

- $n$：每个问题的总采样次数（论文 $n = 10$）
- $c$：通过的次数
- $k$：评估的 $k$ 值
- $\binom{\cdot}{\cdot}$：二项式系数

**直觉**：$\binom{n-c}{k}$ 是「从 $n-c$ 个错误样本中选 $k$ 个都失败」的方案数；$1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}$ 是「至少有一个样本通过」的概率。

### 5.2 Pass Rate（论文新增指标）

论文强调 pass rate 比 pass@k 更直接反映 test-time scaling 的效果：

$$
\text{pass rate} = \frac{1}{M} \sum_{j=1}^{M} \mathbb{1}\left[\exists \text{ trial of } j \text{ that passes} \right]
$$

- $M$：问题总数
- $\mathbb{1}[\cdot]$：指示函数（10 次试验中至少 1 次过即算过）

**与 pass@k 的区别**：pass@k 是「采样 $k$ 个全过」的概率，pass rate 是「$n$ 次试验覆盖到正确答案」的概率。test-time scaling 期望后者提升（即使 pass@k 不变，因为多给推理机会能「撞到」正确答案）。

### 5.3 Jaccard 5-gram 去污染公式

$$
J(A,B) = \frac{|T_5(A) \cap T_5(B)|}{|T_5(A) \cup T_5(B)|}
$$

其中 $T_5(A)$ 和 $T_5(B)$ 分别是脚本 $A, B$ 中所有 unique 5-gram token 序列的集合。

**直觉**：5-gram 集合的 Jaccard 相似度比 exact match 更鲁棒（对变量名、注释顺序、空白鲁棒），又比 1-gram（仅 token 集合）更严格（保留局部顺序信息）。阈值 0.8 是经验值。

### 5.4 SFT 联合损失（重申 §4.4）

$$
\mathcal{L}_{\text{SFT}}(\theta) = - \sum_{i=1}^{N} \left( \sum_{t=1}^{|r^{(i)}|} \log P_\theta(r_t^{(i)} | x^{(i)}, r_{<t}^{(i)}) + \sum_{t=1}^{|y^{(i)}|} \log P_\theta(y_t^{(i)} | x^{(i)}, r^{(i)}, y_{<t}^{(i)}) \right)
$$

**两项的语义解读**：

- $P_\theta(r_t | x, r_{<t})$：模型学「如何逐步推理」（chain-of-thought 能力）
- $P_\theta(y_t | x, r, y_{<t})$：模型学「给定推理后如何写代码」（reasoning-grounded generation）

**为什么联合训练而非分段**：分段训练（先学推理再学代码）容易遗忘；联合训练把推理当作「生成代码的前置条件」，让模型内化「推理 → 代码」的因果关系。

### 5.5 Test-Time Scaling 律

论文 Figure 3 实证发现 RTL 任务也符合 reasoning token 数对 pass@k 的对数型 scaling：

$$
\text{pass@k} \approx a + b \cdot \log(\text{reasoning tokens})
$$

- $a, b$：基准相关常数
- 推理 tokens 越多，pass@k 越高，但边际收益递减（log 曲线）

**对比 general reasoning**：Snell et al. 2024 在数学任务上观察到 log-linear 或 power-law；RTL 任务上 ScaleRTL 观察到的是更平坦的对数曲线——可能因为 RTL 代码有「固定模板」，纯推理收益有限。

#### 6.5.6 案例研究：PS/2 Mouse FSM（Figure 4）

- **初始错误推理**：ScaleRTL 误读「done is signaled in the cycle immediately after the third byte was received」，导致把 done 写成 `assign done = (state == DONE)`，在下一个 cycle 才拉高
- **纠错 prompt 触发**：「Wait, my reasoning must be incorrect. Let's check the reasoning rules...」
- **修正后正确**：done 在 BYTE2 → IDLE 转移的**同一 cycle** 拉高（直接 `done_reg <= (state == BYTE2)`）

这个案例展示了 test-time scaling 的价值：模型原本「理解错了」spec 的时序语义，靠 reasoning rules 提示回到规格本身纠错。

## 7. 创新点

### 7.1 首个 Reasoning LLM for RTL

**贡献**：区别于 RTLCoder/CodeV/CraftRTL 等「instruction-tuned」模型，ScaleRTL 在 SFT 阶段就引入 56K tokens 平均长度的 reasoning trace，让模型先想后写。

**意义**：把 DeepSeek-R1 / o3 的「慢思考」范式搬到硬件描述语言任务上，证明 reasoning data 是 RTL LLM 的「缺失维度」。

### 7.2 3.5B tokens CoT 数据集

**贡献**：62K 高质量脚本 + DeepSeek-R1 生成的 3.5B tokens reasoning traces，是 CodeV (165M) 的 21 倍、CraftRTL (110M) 的 32 倍。

**为什么重要**：表 1 显示这是数量级跃迁——把 RTL LLM 的数据规模从「百万级」推到「十亿级」，与 LLM scaling laws 一致。

### 7.3 多阶段过滤保质量

**贡献**：5M → 62K 的五级漏斗（dedup + 长度截断 + 语法验证 + Jaccard 5-gram 去污染 + embedding 语义过滤），每级有明确技术细节。

**与 CraftRTL 对比**：CraftRTL 强调「正确即构造」算法生成 CC（Correct-by-Construction）数据；ScaleRTL 强调「保留真实 RTL 多样性」——后者数据来源是真实 snippet（虽然过滤严苛），多样性可能更好。

### 7.4 Test-Time Iterative Self-Correction

**贡献**：Algorithm 1 把朴素 "Wait" trick 升级为「删除 code + 插入 reasoning rules + 重新生成」三步，让模型真正反思而非敷衍。

**关键 insight**：「Wait」不够，需要 (a) 删除错误答案避免模型重复，(b) 提供具体可检查的 rules 而非空泛提示，(c) 显式说「我没遵守规则」刺激反思。

### 7.5 通用能力不损

**贡献**：表 3 显示 ScaleRTL-32B 在 HumanEval/MBPP 上**超过**原 DeepSeek-R1-Distill-Qwen-32B，IFEval 仅略低。

**对比**：CodeV/OriGen/CraftRTL 在 IFEval 暴跌（24-47%）— 专门化训练损害通用能力。ScaleRTL 通过 reasoning-aligned SFT（而非 instruction-only SFT）保留了底座模型的通用推理能力。

### 7.6 RTL 任务的 Test-Time Scaling Law

**贡献**：Figure 3 实证 reasoning tokens 数 vs pass@k 在 RTL 任务上呈对数型 scaling（与数学/代码任务一致）。

**意义**：和 Snell et al. 2024 在数学上观察的 log-linear/power-law scaling 一起，证明 test-time scaling 在 RTL 上是普适现象。

## 9. 与芯片流程关系

### 9.1 在 EDA 流程中的位置

ScaleRTL 是 **RTL 设计阶段（①）的 LLM 推理扩展**——它不生成可直接流片的 RTL，也不做综合优化。它的目标是让 LLM 在被问到 "implement a Verilog module for ..." 时能给出更高质量的 Verilog 代码：

```text
传统 LLM-for-RTL：
spec → LLM(SFT on instruction data) → Verilog（语法对但可能语义错）

ScaleRTL 介入点：
spec → ScaleRTL (CoT-fine-tuned) → Verilog（先推理后生成）
       ↑                            ↑
       3.5B tokens CoT 数据 SFT      iterative self-correction
       62K 高质量脚本 + DeepSeek-R1  删除旧 code + 插入 rules
       平均 56K tokens 推理轨迹       重新生成 → 再过 testbench
```

下游任务（VerilogEval、RTLLM 的 pass@k 评估）是衡量 LLM 写 Verilog 能力的指标。

### 9.2 「能仿真通过」和「能做芯片」之间隔着什么

ScaleRTL 生成的 Verilog 代码能在 Icarus Verilog 上通过 testbench——这是「RTL 功能仿真（②）」级别的验证。但一个真实可制造的芯片还需要：

1. **可综合到门级 netlist** — ScaleRTL 不验证。论文 Verilog 代码语法上是可综合的，但没跑过 DC 综合。
2. **满足时序** — 不涉及。ScaleRTL 完全在 RTL 文本层面。
3. **可布局布线** — 不涉及。
4. **DRC / LVS clean** — 不涉及。
5. **签核 (sign-off)** — 不涉及。

> **本资料包的提示**：ScaleRTL 的「成功」是 **LLM 推理能力 + 推理时扩展** 意义上的成功（pass@k 提升），而不是「生成可流片芯片」。论文自己也没声称这个——它明确说自己做的是「reasoning LLM for RTL coding」。

## 10. 讨论与局限

### 10.1 论文自述局限

#### 局限 1：数据来源限于公开 web

论文承认抓取自公开 web 的 snippet 与 NVIDIA 内部工业 RTL 仍有差距。和 ChipNeMo 用 NVIDIA 内部数据相比，ScaleRTL 数据多样性可能不够。

#### 局限 2：DeepSeek-R1 蒸馏链路的固有偏差

论文用 DeepSeek-R1 生成 CoT 轨迹，再用 DeepSeek-R1-Distill-Qwen-32B 微调——中间多了一层「蒸馏」。模型学到的 reasoning pattern 受限于 R1 的能力上限和蒸馏损失。

#### 局限 3：Test-time scaling 算力成本

每次纠错迭代需要重新跑 inference，最坏情况 $T$ 次额外推理。论文用 2 iter 时 token limit 已经到 49152，单问题推理成本显著高于一次性推理。

#### 局限 4：闭源模型对比的公平性

DeepSeek-R1 / Claude3.7-Sonnet / OpenAI o3 等闭源模型的训练数据 cutoff **晚于 VerilogEval/RTLLM benchmark 的公开发布**。ScaleRTL 严格去污染，闭源模型可能见过 benchmark → 对比不公平。

#### 局限 5：只评估两个 RTL benchmark

论文只用 VerilogEval + RTLLM 评估，没测其他 RTL benchmark（如 CodeV 自己发布的 benchmark）。对其他 benchmark 的泛化性未验证。

#### 局限 6：Reasoning Rules 的离线生成

{R} 由 Claude3.7-Sonnet offline 生成一次后复用。如果 benchmark 升级或新增设计类别，{R} 可能过时。

### 10.2 代码/复现层面

#### 复现门槛

1. **Base 模型**：DeepSeek-R1-Distill-Qwen-32B 公开下载
2. **数据生成**：需要 DeepSeek-R1 部署（论文用 DeepSeek 官方或自部署），算力可观
3. **过滤 pipeline**：纯算法实现（dedup、长度截断、语法验证、Jaccard、embedding 相似度）
4. **训练硬件**：32 节点 × 8 A100 = 256 × A100（论文配置）；即便小规模复现也需多节点
5. **评估硬件**：vLLM TP=4（4× A100）
6. **闭源对比**：Claude3.7-Sonnet、OpenAI o3 等需要 API 访问

#### 已知差异

- **DeepSeek-R1 版本**：蒸馏模型可能随 DeepSeek 官方更新而变化
- **Reasoning Rules 质量**：offline prompt 依赖 Claude3.7-Sonnet 表现
- **去污染的精确性**：Jaccard 阈值 0.8 是经验值，可能漏掉部分重叠
- **Temperature 选择**：论文只用 0.2，没探索 0.8 / 多 temperature 取最优

### 10.3 本资料包的批判性分析

#### 批判 1：CoT 数据可能含 LLM 幻觉

DeepSeek-R1 生成的推理 trace 可能含有错误推理（幻觉）。论文只用了 syntax validation 过滤代码，没验证推理 trace 本身的对错。如果 R1 推理错了，ScaleRTL 可能学到了「错误推理模式」。

#### 批判 2：Test-time scaling 的边际收益

Figure 3 显示 scaling 曲线接近饱和。1 iter 提升约 +3-5 pp，2 iter 再 +3-5 pp。继续往上扩 iter 次数的收益不明确，但成本线性增长。

#### 批判 3：3.5B tokens 的实际收益

论文没有 ablation 显示「3.5B vs 0.5B vs 3.5B vs 10B tokens」的训练效果曲线。3.5B 是「能训出来」的规模，但未必是最优规模——可能 10B 还能涨，也可能 1B 就够。

#### 批判 4：和 Agent 方法的真正比较

论文承认 VerilogCoder 等 agent 方法是「广义 test-time scaling」，但没用 ScaleRTL + agent 的组合做实验。如果让 ScaleRTL 也调用 waveform 工具或 testbench planner，效果可能更好。论文留作 future work。

#### 批判 5：32B 参数 vs 70B+ 参数的边界

CraftRTL-70B 在某些 benchmark 上仍接近 ScaleRTL-32B。如果 ScaleRTL 也用 70B base（DeepSeek-R1-Distill-Llama-70B），提升可能更大。论文没用 70B base 微调是个未探索方向。

#### 批判 6：闭源模型对比的「不公」是双刃剑

论文强调闭源模型可能见过 benchmark → 数据泄漏。但反过来，论文自己用 DeepSeek-R1 生成 CoT 数据，DeepSeek-R1 也可能见过 benchmark —— 这个风险论文没明确排除。

## 12. 一分钟复述版

1. **核心问题**：LLM-for-RTL 微调受限于 (a) 高质量 RTL 训练数据稀缺（之前最多 165M tokens），(b) 现有模型都不是 reasoning 型（不能反思自纠）。
2. **方法概述**：ScaleRTL = 5M → 62K 过滤（dedup + 长度截断 + 语法 + Jaccard 去污染 + embedding 语义）→ 62K 三元组 CoT 数据 (3.5B tokens by DeepSeek-R1) → 在 DeepSeek-R1-Distill-Qwen-32B 上 SFT 联合建模 r (推理) + y (代码) → ScaleRTL。推理时 ScaleRTL† 反复把 `</think>` 替换成「Wait, my reasoning must be incorrect. Let's check the reasoning rules: {R}. Wait, I did not follow the rules. Let's try again.」让模型反思自纠。
3. **核心数据**：32B 模型在 VerilogEval / RTLLM 上以 pass@5 超最强 prior baseline 最大 +18.4pp（ScaleRTL† 90.8 vs CraftRTL-15B 72.4 on VerilogEval-Human）和 +12.7pp（RTLLM）；pass@1 上分别 +10.7pp 和 +11.7pp。32B 优于 CraftRTL-70B。
4. **关键结果**：(a) CoT 数据规模从 110M (CraftRTL) 跃升 32× 到 3.5B；(b) Test-time scaling 实证对数型 law 在 RTL 成立；(c) 通用能力不损：HumanEval 65.2%/MBPP 75.0% 超 DeepSeek-R1-Distill-Qwen-32B 原版 49.1%/71.3%。
5. **最大创新点**：(a) 首个 reasoning LLM for RTL coding；(b) 3.5B tokens 长 CoT 数据集；(c) Algorithm 1 test-time self-correction（朴素 "Wait" trick 的升级版）；(d) 通用能力保留的 reasoning-aligned SFT。
6. **EDA 流程位置**：RTL 设计阶段（①）的 LLM 推理扩展；只做 RTL 功能仿真（②）级别的验证，不涉及综合 / STA / 后端。
7. **与同类工作的关系**：与 RTLCoder/BetterV/CodeV/CraftRTL/OriGen 同问题域（LLM-for-RTL 微调），ScaleRTL 是新一代 SOTA 且升级为 reasoning 范式；与 VerilogCoder 互补（VerilogCoder agentic，ScaleRTL single-model reasoning）。
8. **局限**：数据来自公开 web（非工业内部）；DeepSeek-R1 蒸馏链路可能有偏差；test-time scaling 算力成本线性增长；闭源模型对比有数据泄漏嫌疑；3.5B tokens 是否最优规模未探索；和 agent 方法未组合实验。

## 附录 A：ScaleRTL 与 CraftRTL 的方法论对比

虽然 ScaleRTL 和 CraftRTL 都做「LLM-for-RTL」，但**核心方法论完全不同**：

| 维度 | CraftRTL | ScaleRTL |
|------|----------|----------|
| 模型范式 | instruction-tuned (非推理型) | reasoning LLM (推理型) |
| 数据规模 | 110M tokens (110K 样本) | 3.5B tokens (62K 样本) |
| 数据来源 | LLM 生成 / SDG（Synthetic Data Generation）+ 算法生成 / CC（Correct-by-Construction）+ 错误注入 (Repair) | web 抓取 (5M) + DeepSeek-R1 反向 CoT 生成 |
| 数据特点 | 多样性 vs 正确性平衡 | 长 CoT 推理 trace |
| Base 模型 | Starcoder2-15B / DeepSeek-Coder-6.7B / CodeLlama-7B | DeepSeek-R1-Distill-Qwen-32B (单一) |
| 推理时增强 | 无 (纯单次) | iterative self-correction (ScaleRTL†) |
| 通用能力 | IFEval 暴跌至 24-47% | IFEval 73.2% 保留原版 76.8% 的能力 |
| 参数量级 | 6.7B-15B | 32B |
| 关键 insight | 「Correct-by-Construction 用算法绕过 LLM hallucination」 | 「长 CoT 推理 trace 让模型学会慢思考」 |
| Test-time scaling | 不支持 (非推理型) | 核心贡献 (Algorithm 1) |
| Pass@1 vs SOTA | +3.8% / +10.9% / +6.6% (Machine/Human/RTLLM) | +10.7% / +11.7% (VerilogEval/RTLLM) |
| Pass@5 vs SOTA | (未单独强调) | +18.4% (VerilogEval) / +12.7% (RTLLM) |

两者代表了 LLM-for-RTL 的两条路线：**数据质量派**（CraftRTL，改进 instruction data）和 **推理范式派**（ScaleRTL，引入 CoT + test-time scaling）。两者可以互补——用 ScaleRTL 的 CoT 生成方法补充 CraftRTL 的 SDG 数据，或用 CraftRTL 的 CC 数据补充 ScaleRTL 的多样性。

## 附录 B：ScaleRTL 与 DeepSeek-R1 的关系

ScaleRTL 的 base 模型是 DeepSeek-R1-Distill-Qwen-32B，可以理解为：

```text
DeepSeek-R1 (671B MoE, 原生 reasoning LLM)
     │
     │ RL + SFT 蒸馏 (DeepSeek 官方)
     ▼
DeepSeek-R1-Distill-Qwen-32B (32B, 保留 reasoning 能力)
     │
     │ ScaleRTL 用 3.5B tokens RTL CoT 数据 SFT
     ▼
ScaleRTL-32B (32B, RTL-specialized reasoning LLM)
     │
     │ Test-time scaling (Algorithm 1)
     ▼
ScaleRTL†-32B (32B, iterative self-correction)
```

**关键点**：
1. ScaleRTL 没用 DeepSeek-R1 原版（671B 太贵），而用蒸馏版 32B
2. 蒸馏版已具备通用 CoT 能力（IFEval 76.8%，HumanEval 49.1%）—— ScaleRTL 只需注入 RTL 领域知识
3. ScaleRTL 的「reasoning」是从 DeepSeek-R1 蒸馏继承的，不是 ScaleRTL 训练出来的新能力——这是论文未明确说明但容易误读的边界

## 附录 C：Test-Time Scaling 的工程实践细节

论文 Algorithm 1 的实现细节：

```text
def scale_rtl_dagger_inference(M, P, R, T=2):
    """
    M: 微调后的 ScaleRTL 模型
    P: 测试问题 (specification)
    R: reasoning rules (offline 生成)
    T: 最大迭代次数
    """
    # 1. 首次推理
    trace = M.generate(P, max_tokens=16384, temperature=0.2)
    solution = extract_answer(trace)
    
    for t in range(T):
        if is_correct(solution):
            return trace, solution
        
        # 2. 删除 </think> 后的所有内容
        idx = trace.find('</think>')
        if idx >= 0:
            trace = trace[:idx + len('</think>')]
        
        # 3. 附加纠错 prompt
        corrective_prompt = (
            f"Wait, my reasoning must be incorrect. "
            f"Let's check the reasoning rules: {R}. "
            f"Wait, I did not follow the rules. "
            f"Let's try again."
        )
        
        # 4. 用纠正后的 trace 作为新 prompt
        trace = M.generate(
            trace + corrective_prompt,
            max_tokens=32768 if t == 0 else 49152,
            temperature=0.2
        )
        solution = extract_answer(trace)
    
    return trace, solution
```

**关键实现点**：
1. **`is_correct` 是 testbench pass**：需要实际仿真（Icarus Verilog）判定，不是 LLM 自我评估
2. **删除 </think> 后内容**：避免模型「看见自己之前的错误答案」并重复
3. **纠错 prompt 必须包含 {R}**：纯 "Wait" 不够，需要具体可检查的规则
4. **递增 token limit**：1 iter 给 32K，2 iter 给 49K —— 让模型有足够空间展开新推理
