## 1. 一句话定位

**OpenRTLSet 是迄今最大的完全开源 Verilog 模块数据集（131,272 个 module，覆盖 102K GitHub Verilog + 5K VHDL 翻译 + 24K HLS C/C++ 翻译），用 DeepSeek-R1-70B 自动给每个模块生成 NL 功能描述（支持可选 Verilator C++ 配对），并通过系统性的消融证明「Verilog-only INT4 标签」是 Granite 8B / Qwen2.5-Coder 7B-32B 微调的最优配置；在 VerilogEval 上 Qwen2.5-32B 全量微调达到 Pass@1=65.1%、Pass@10=89.3% 的 Machine 和 Pass@1=42.4%、Pass@10=64.2% 的 Human——比 MG-Verilog 基线提升 +5.7%/+8.3%/+7.9%（Machine）和 +9.7%/+13.0%/+14.2%（Human）。**

这句话里的七个技术承重点，后面逐一拆解：

1. **「最大 + 完全开源」的双重定位** — 已有 Verilog 数据集（VGen, PyraNet, MG-Verilog, VeriGen）要么规模小，要么 license 受限（PyraNet 用 ChatGPT 生成违反 OpenAI TOS）。OpenRTLSet 是 131K 规模且全部 permissive license 的稀有组合，让学术和商业使用都没有法律障碍。
2. **三源融合（GitHub Verilog + VHDL 翻译 + C/C++ HLS 翻译）** — 单一来源的 Verilog 数据集容易产生风格偏见。三源融合引入：(a) GitHub Verilog（102K，风格多样但需要 robust 解析）；(b) VHDL→Verilog 翻译（5K，用 vhd2vl 工具，补充传统硬件描述）；(c) C/C++→Verilog 翻译（24K，用 Vitis HLS，补充算法电路和信号处理模块）。
3. **DeepSeek-R1 70B 作为标签生成器** — 选择 DeepSeek-R1 而不是 GPT-4 是因为：(a) OpenAI TOS 禁止用 ChatGPT 输出训练竞品 LLM，PyraNet 因此只能学术用；(b) DeepSeek-R1 是 reasoning model，能产生带思考痕迹的、更结构化的功能描述。
4. **「Verilog-only INT4」消融最优配置** — 论文系统比较了三种增强策略（仅 Verilog / Verilog+C++ / 仅 Verilator 通过的）和两种量化（INT4 vs BF16），证明：(a) 加 Verilator C++ 反而损害性能（因为 C++ 不是真正的 HDL，过滤后样本量太少）；(b) INT4 比 BF16 精度损失可忽略，但节省 50% 显存和推理时间。
5. **可比规模下超 MG-Verilog** — 把 131K 降采样到 11K 与 MG-Verilog（11K）等量对比，OpenRTLSet 在所有模型（Granite 8B / Qwen2.5 7B / Qwen2.5 32B）和所有 Pass@k（1/5/10）上都优于 MG-Verilog 原版标签，Pass@1 提升最高 +16.4 个百分点（Qwen2.5-32B Machine）。这证明**数据来源质量 > 标签质量**。
6. **全量微调 131K 后 Qwen2.5-32B SOTA** — 11K 降采样 → 131K 全量的 scaling 实验表明：每涨一个数量级的训练数据，Pass@10 涨 5~6 个百分点。Qwen2.5-32B 在 131K 上达到 Pass@10 = 89.3%（Machine），比降采样版的 83.9% 高 5.4 pp，比 11K MG-Verilog 81.4% 高 7.9 pp。
7. **完全 Apache-2.0 license + HuggingFace 公开发布** — HuggingFace dataset `ESCAD/OpenRTLSet` 上直接 `load_dataset()` 加载，每个样本带 `Repo_url` 和 `lic_name` 字段可追溯到原始开源仓库。这解决了 EDA 领域长期存在的「数据来源黑盒」问题。

## 2. EDA 阶段映射（①-⑰）

参照 [芯片流程.md](../芯片流程.md) 的 17 阶段标准编号：

| 阶段 | 覆盖 | 说明 |
|------|:---:|------|
| **① RTL 设计** | ✅ **核心** | OpenRTLSet 的全部价值是为 LLM 学习「写 Verilog RTL」提供训练数据。设计师不再是唯一能写 RTL 的人——LLM 经过 OpenRTLSet 微调后能根据 NL spec 自动生成 Verilog 模块。这是「LLM 辅助 RTL 设计」在 ① 阶段的应用 |
| ② RTL 功能仿真 | ⚠️ 间接 | OpenRTLSet 本身不做 verification。但论文提到 [OpenABC-D] 的 Verilator 输出用于辅助标签生成——这是用 ② 的仿真器来生成 ① 的训练数据 |
| ③ 逻辑综合 | ❌ | OpenRTLSet 不评估生成的 RTL 能不能综合。论文只评估 VerilogEval 的 pass@k，没跑 yosys/ABC 综合检查可综合性 |
| ④-⑬ | ❌ | OpenRTLSet 不触及后端流程 |
| ⑭-⑰ | ❌ | — |

**覆盖率：1/17。** OpenRTLSet 是一个**纯数据资源**——它不解决任何具体 EDA 阶段的问题，而是为「LLM 自动生成 RTL」这一研究方向提供基础训练集。它的下游应用集中在 ①RTL 设计阶段。

> ⚠️ OpenRTLSet 的局限：它评估的是「LLM 生成 Verilog 代码在 VerilogEval 上能否产生期望输出」，但**没有评估生成的 RTL 能不能被综合成实际电路**。一篇声称能写 RTL 的论文，至少应该跑一遍 yosys 综合检查。OpenRTLSet 没做这个验证。

## 3. 输入 / 输出

### 3.1 输入

OpenRTLSet **不是一个推理系统**——它是一个**数据集**。所以它的「输入」是数据集构建流程的输入。

**(a) GitHub 仓库（Verilog/VHDL/C/C++）**

通过 GitHub 搜索 API 抓取的开源仓库：

```text
~81k Verilog repos    → 102k Verilog modules
~5k VHDL repos        → 5k VHDL modules (→ Verilog via vhd2vl)
~103k C/C++ repos     → 24k C/C++ modules (→ Verilog via Vitis HLS)
```

每个仓库必须有 permissive license（MIT/Apache/BSD 等）才能被保留。

**(b) 转换工具链**

- **vhd2vl**：开源 VHDL → Verilog 转换器（仅转换成功文件保留）
- **Vitis HLS 2024.2**：AMD/Xilinx 的高级综合工具，把 C/C++ → Verilog
- **Verilator 5.x**：开源 Verilog 仿真器，可选生成 C++ reference

**(c) 标签生成器**

**DeepSeek-R1-Distill-Llama-70B**：开源 reasoning LLM，为每个 Verilog 模块生成 NL 功能描述。

可选输入：Verilator 生成的 C++ reference（C++ 代码作为额外上下文提供给 R1）。

### 3.2 中间产物

**(a) JSONL 数据条目**

每行一个 JSON 对象：

```json
{
  "index": 12345,
  "ioheader": "module mux2(input [3:0] a, input [3:0] b, input sel, output reg [3:0] y);",
  "verilog_code": "always @(*) begin\n  if (sel) y = a;\n  else y = b;\nend\nendmodule",
  "full_code": "module mux2(...) always @(*) ... endmodule",
  "llm_response": "This is a 2-to-1 multiplexer with 4-bit data inputs...",
  "Repo_url": "https://github.com/user/repo/blob/main/mux2.v",
  "lic_name": "MIT"
}
```

**(b) 标签消融实验的三种配置**

| 配置 | 含义 |
|---|---|
| **Verilog** | 只把 Verilog 代码喂给 DeepSeek-R1 |
| **Verilog & C++** | Verilog + Verilator 生成的 C++ reference（仅对 Verilator 能编译的 ~40%） |
| **Verilator Passed** | 只保留 Verilator 通过的子集（牺牲样本量换代码「可执行性」） |

**(c) 量化实验**

| 量化 | 用途 |
|---|---|
| **INT4** | 标签生成时用 INT4 量化 DeepSeek-R1，省显存 |
| **BF16** | 标签生成时用 BF16 全精度 |

### 3.3 输出

OpenRTLSet 的输出就是**最终发布的 HuggingFace 数据集** `ESCAD/OpenRTLSet`：

```python
from datasets import load_dataset
ds = load_dataset("ESCAD/OpenRTLSet")
# 131,272 条样本，Apache-2.0 license
# 字段：index, ioheader, verilog_code, full_code, llm_response, Repo_url, lic_name
```

下游消费方式：

```python
# 用户可以加载数据集并微调自己的 LLM
from transformers import AutoModelForCausalLM, AutoTokenizer, TrainingArguments
# ... 标准 SFT pipeline ...
```

### 4.2 核心模块逐个详解

#### 模块 1：GitHub 数据抓取 + License 过滤

**做什么**：在 GitHub 上搜索包含 Verilog / VHDL / C/C++ 文件的仓库，只保留 permissive license 的（MIT、Apache、BSD、MPL 等）。

**输入/输出**：

- 输入：GitHub 搜索关键词
- 输出：~81k Verilog repos、~5k VHDL repos、~103k C/C++ repos（全部 permissive license）

**为什么 permissive license 关键**：

商业 LLM 微调需要 license 兼容。GPL/AGL 等 copyleft license 会污染整个训练 pipeline 的法律地位。Apache-2.0 数据集（OpenRTLSet 本身的 license）可以无障碍用于商业模型。

#### 模块 2：语言转换（VHDL & C/C++ → Verilog）

**VHDL → Verilog**：

用 `vhd2vl`（开源工具）逐文件转换。失败的转换（如 vhd2vl 不支持的语法）剔除，最终从 5k VHDL 文件得到 5k Verilog 模块（~100% 成功率，因为 vhd2vl 对标准 VHDL 支持良好）。

**C/C++ → Verilog**：

先用正则检查剔除不可综合代码：

```python
# 移除包含这些模式的 C/C++ 文件
forbidden_patterns = [
    r'\bmalloc\b', r'\bfree\b',         # 动态内存
    r'->',                                # 指针
    r'\bwhile\b',                         # 循环
    r'\brecursion\b',                     # 递归
    r'\bgoto\b',                          # goto
    # ... 更多
]
```

12k C/C++ 仓库通过这步后，用 Vitis HLS 综合为 Verilog。但 ~91% 失败——失败原因主要是 HLS 不支持的标准库调用（如 `std::map`、`std::vector` 等）。最终只有 ~1k 仓库成功生成 Verilog，得到 24k Verilog 模块（说明单个仓库平均产出 24 个 HLS 模块）。

**输入/输出**：

- 输入：VHDL 文件 / C/C++ 文件
- 输出：Verilog 文件

#### 模块 3：Module Extraction & Preprocessing

**做什么**：把多 module 的 Verilog 文件拆成单 module，按规则清洗。

```python
# 1. 按 module/endmodule 关键字切分
modules = re.findall(r'module\s+(\w+)\s*\(.*?\);.*?endmodule', verilog_code, re.DOTALL)

# 2. 清洗
clean_code = remove_comments(verilog)       # 去掉 // 和 /* */
normalize_indent(clean_code)                 # 统一缩进
extract_io(module)                           # 提取 input/output/inout 端口

# 3. JSONL 输出
{"header": "module foo(input clk, ...)", "code": "always @(posedge clk) ..."}
```

**为什么这样设计**：让每条训练样本 = 一个完整 module，避免 LLM 学到「跨 module 的杂质」（如文件级注释、include、package 定义）。

#### 模块 4：DeepSeek-R1 NL 标签生成

**做什么**：用 DeepSeek-R1-Distill-Llama-70B（INT4 量化）对每个 Verilog 模块生成 NL 功能描述。

**为什么用 DeepSeek-R1 而不是 GPT-4**：

1. **License 兼容**：OpenAI TOS 禁止用 ChatGPT 输出训练竞品 LLM。PyraNet 数据集因此只能学术用。
2. **Reasoning 能力**：R1 是 reasoning model，生成的功能描述带有思考痕迹（`<thinking>...</thinking>` 段落），更结构化、更准确。
3. **开源 + 自托管**：数据可控，无 API 费用（虽然 INT4 量化仍需 GPU）。

**输入/输出**：

- 输入：Verilog 代码（+ 可选 Verilator C++ reference）
- 输出：NL 功能描述（200-500 字，含 I/O 接口说明 + 行为描述 + 时序/协议细节）

**INT4 量化的设计**：

论文用 INT4 量化的 DeepSeek-R1 而非 BF16，原因是：(a) 标签生成阶段不是性能瓶颈，质量损失可忽略；(b) INT4 让 70B 模型能跑在单张 A40 48GB 显存上。消融证明 INT4 vs BF16 在 Pass@10 上仅差 1-3 pp，可以接受。

#### 模块 5：质量过滤

**做什么**：剔除低质量样本：

- **超长 token**：>4096 tokens 的样本剔除（避免训练时 OOM）
- **重复文本**：完全相同的代码或描述剔除（去重）
- **无终止符**：NL 描述缺少句号/问号的剔除（说明 R1 生成中断）
- **骨架模块**：纯声明无功能逻辑的 module 剔除（`module foo(input clk); endmodule` 这种）

**为什么这些过滤必要**：R1 不是万能的，会产生截断、重复、空响应的样本。这些样本进训练集会污染梯度。

## 5. 关键公式

### 5.1 Pass@k 指标（Chen et al. 2021 标准定义）

$$
\text{Pass}@k = \mathbb{E}_{\text{problems}} \left[ 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}} \right]
$$

- $n$：每个问题生成的样本数（论文 $n=10$）
- $c$：通过单元测试的样本数
- $k$：评估的 top-k 数（$k=1, 5, 10$）

**工程直觉**：Pass@k 衡量「在前 $k$ 个候选中至少有一个通过的概率」，避免了 Pass@1 对单次采样波动过敏感。分子 $\binom{n-c}{k}$ 是「从 $n-c$ 个不通过样本里选 $k$ 个」的数量，分母 $\binom{n}{k}$ 是「从 $n$ 里选 $k$ 个」的总组合数。

**为什么这么设计**：Chen et al. 2021 提出的无偏估计形式，比简单的「$c/n$」更准确。论文设置 $n=10, T=0.7$ 是 VerilogEval 的标准评估协议。

### 5.2 Label Quality vs Dataset Quantity Tradeoff

论文没有显式公式，但隐含一个权衡：

$$
\text{Performance} \approx f(\underbrace{N}_{\text{samples}}, \underbrace{Q}_{\text{label quality}}, \underbrace{Q_v}_{\text{code quality}})
$$

- $N$：训练样本数（11K → 131K）
- $Q$：标签质量（DeepSeek-R1 vs LLaMA-3 原版）
- $Q_v$：Verilog 代码本身的质量（OpenRTLSet 多源 vs MG-Verilog 单一 GitHub）

消融结论：**$Q_v$ 的影响 > $Q$**——把 MG-Verilog 的 11K 用 OpenRTLSet 的 DeepSeek-R1 流程重标，提升有限；但换成 OpenRTLSet 的 11K 数据本身，性能立即全面超过。

### 5.3 Verilator Pass Rate 估计

$$
p_{pass} = \frac{N_{verilator\_passed}}{N_{total}} \approx 0.40
$$

- $p_{pass}$：Verilog 模块通过 Verilator 编译 + 仿真的比率
- 论文发现：MG-Verilog 子电路中只有约 40% 能成功跑 Verilator（其他 60% 因语法错误、未声明端口、模块依赖等失败）

**工程直觉**：Verilator 是开源严格仿真器，比商业 VCS 严格得多。40% 通过率说明 GitHub 抓取的 Verilog 质量参差不齐——很多仓库的代码是「实验性的」「学习用的」「未完成的」。

**为什么重要**：「Verilator Passed」配置（只保留能 Verilator 跑通的 40% 子集）相比「Verilog-only」配置性能下降——证明**样本量比代码可执行性更重要**。

## 6. 训练与实验设置

### 6.1 是否需要训练

**OpenRTLSet 本身不需要训练**——它是一个数据集。但论文实验涉及训练 LLM 的下游消费，所以：

**OpenRTLSet 论文做两类训练**：

- **(a) 标签生成器**：DeepSeek-R1-Distill-Llama-70B 是预训练模型，OpenRTLSet 论文只跑 inference（生成 NL 标签）
- **(b) 下游 LLM 微调**：Granite-3.3-8B / Qwen2.5-Coder-7B / 32B 在 OpenRTLSet 上做 SFT

### 6.2 实验设置

**硬件**：NVIDIA A40-48GB GPU（SLURM 调度），16 CPU + 160GB RAM + 2 A40 per job

**微调配置**（论文未明示全部超参，从论文上下文推断）：

| 超参 | 值 |
|---|---|
| Training framework | HuggingFace Trainer |
| 优化器 | AdamW |
| Batch size | 未明示 |
| Learning rate | 未明示 |
| Epochs | 未明示 |

## 7. 创新点

### 创新点 1：迄今最大完全开源 Verilog 数据集

**和已有方法的关键区别**：

| 数据集 | 规模 | License | 可商用 |
|---|---:|---|:---:|
| VeriGen | ~0.1K module | 研究用 | ❌ |
| VGen | ~10K | 部分开源 | ⚠️ |
| PyraNet | ~10K | ChatGPT 生成（违反 OpenAI TOS） | ❌ |
| **MG-Verilog** | 11,144 | 部分 GitHub 仓库许可 | ⚠️ |
| **OpenRTLSet** | **131,272** | **Apache-2.0（全 permissive）** | **✅** |

OpenRTLSet 是第一个**既大（>100K）又完全可商用**的 Verilog 数据集。规模上一个数量级领先 MG-Verilog，license 上无可挑剔。

### 创新点 2：三源融合（Verilog + VHDL + HLS）

**和已有方法的关键区别**：

VGen、MG-Verilog、VeriGen 全部只用 GitHub Verilog。OpenRTLSet 额外引入：
- VHDL → Verilog（5K）：补充传统硬件描述
- C/C++ → Verilog via Vitis HLS（24K）：补充算法类电路（DSP、filter、crypto 等）

这让 OpenRTLSet 涵盖的电路类型比单一 Verilog 来源广。HLS 来源尤其独特——传统 RTL 工程师写不出 HLS 风格的 Verilog（大量 `for` loop、unrolled、pipeline pragma），但 OpenRTLSet 提供了训练样本。

### 创新点 3：「Verilog-only INT4」的最优消融

**和已有方法的关键区别**：

直觉上「Verilog + C++ 上下文」应该让 DeepSeek-R1 生成更准确的功能描述（因为 C++ 是「已经在跑的代码」）。但论文证明：**对 32B 大模型，纯 Verilog 输入 + INT4 量化已经足够，加 C++ 反而引入噪声**。

这是一个反直觉但有数据支持的结论。它告诉后续工作：**数据量 × 数据质量 > 数据增强**。与其加 C++ 上下文试图让 label 更好，不如用更多原始 Verilog 让模型自己学。

### 创新点 4：等规模 vs 全量 scaling 实验

**和已有方法的关键区别**：

已有数据集论文通常只展示「在我们数据集上微调」的效果，没有**严格控制变量**地对比。OpenRTLSet 做了两层对比：
- **等规模 11K 对比**：控制训练数据量，对比 OpenRTLSet vs MG-Verilog 的数据质量差异
- **11K → 131K scaling**：控制数据集来源，对比数据量的影响

这让论文结论非常 robust：**OpenRTLSet 比 MG-Verilog 好** 不是因为它更大，而是因为**它的数据来源更多样**（多源融合）。

### 9.3 工业落地差距分析

| 维度 | OpenRTLSet 现状 | 工业实践需求 |
|---|---|---|
| 电路规模 | 子模块（平均 ~100 行 Verilog） | 完整 SoC（数十万行） |
| 综合验证 | 未验证可综合性 | 必须 yosys/DC 综合通过 |
| 时序验证 | 未涉及 | 需 STA signoff |
| 协议覆盖 | VerilogEval 控制流为主 | 需 AXI/PCIe/DDR PHY 等 |
| 验证用 TB | 未生成 | 需配套 testbench（见 [PRO-V](../PRO-V/论文深度讲解.md)） |

| 许可证 | Apache-2.0（完美） | 同 |

**结论**：OpenRTLSet 是「LLM 学 RTL」研究的**完美起跑线**，但工业落地还需：
1. 可综合性验证（跑 yosys 综合）
2. testbench 配套（用 PRO-V 之类工具）
3. 私有 IP 微调（OpenRTLSet 做 base model，工业数据做 SFT）
4. STA / 时序 closure（与 [PRO-V](../PRO-V/论文深度讲解.md) 等 verification 工具集成）

## 10. 讨论与局限

### 10.1 论文自述的局限

1. **VHDL 转换 vhd2vl 失败的文件被剔除**——损失了一些 VHDL 风格数据
2. **C/C++ → Verilog 仅 ~1k 仓库成功**（103k 仓库中只有 ~1% 通过 Vitis HLS），主要失败原因是 `std::map`、`std::vector` 等不可综合的标准库
3. **VerilogEval 覆盖率仅 ~40% 能跑 Verilator**——说明 GitHub 抓取的代码质量参差不齐
4. **「Verilator Passed」配置性能下降**——证明样本量比代码可执行性更重要（这是 findings，不是 limitation）
5. **Chisel / Veryl / Spade 等现代 HDL 被排除**——因为 GitHub 上仓库数量太少（数百 vs 数十万）
6. **仅评估 Granite + Qwen 两个模型家族**——结果未必能泛化到其他架构

### 10.2 代码/复现层面的问题

1. **Vitis HLS 需要 Xilinx 账号 + 许可证**——虽然是免费版，但注册流程繁琐
2. **DeepSeek-R1-Distill-Llama-70B 的 INT4 量化版本**——HuggingFace 上有现成的吗？论文未明示具体 quantization 库（可能是 AutoGPTQ 或 BitsAndBytes）
3. **Pass@k 评测需要生成 10 个 sample per problem × 156 problems × 2 splits**——单次评测需要数百次 LLM forward pass，耗时长
4. **论文未公开 SFT 的 learning rate / batch size / epochs 等关键超参**——复现者需要自己调
5. **VerilogEval 评测脚本**——需要用作者维护的 [verilog-eval](https://github.com/UIUC-ChenLab/verilog-eval) 仓库版本，可能有版本依赖

### 10.3 本资料包的批判性分析

| 论点 | 评价 |
|---|---|
| **「131K 是最大开源 Verilog 数据集」** | 截至 2025 ICLAD 时点是，但已有更新的数据集（如 [ChipMATE](https://huggingface.co/)）可能更大。建议定期 recheck HuggingFace Datasets 趋势 |
| **「Qwen2.5-32B 达到 Pass@10 = 89.3%」** | 这个数字漂亮，但**没有评估可综合性**——生成的 RTL 可能只是 VerilogEval 单元测试通过，yosys 综合直接报错。这是 OpenRTLSet 最大的盲点 |
| **「DeepSeek-R1 比 LLaMA-3 标签好」** | 论文在 11k 重标实验里证明了这一点（Qwen2.5-32B MG-Verilog Original 0.594 P@1 vs Re-labeled Verilog 0.515——重标反而**下降**了！）。这说明**标签质量提升不能弥补数据量不足** |
| **「Apache-2.0 完全可商用」** | 是的，HuggingFace 数据集页面明确标注。但**数据集里的 Verilog 模块本身来自 GitHub 第三方仓库**，这些仓库各自的 license 才是真正约束——Apache-2.0 数据集 ≠ 每个子模块的 license 都是 Apache-2.0 |
| **「三源融合比单源好」** | 论文没明确分离三源的边际贡献，消融只比较了「是否加 C++ 上下文」。如果 VHDL 和 HLS 来源其实贡献微小，主要还是 GitHub Verilog 撑场，那「三源融合」就只是 marketing |

## 12. 一分钟复述版

1. **问题**：LLM-for-Verilog 数据集要么小，要么 license 受限，要么用 ChatGPT 生成（违反 TOS）。OpenRTLSet 填补「大规模 + 完全开源 + 可商用」的空白。
2. **方法**：GitHub 抓取 81k Verilog + 5k VHDL + 103k C/C++ 仓库 → vhd2vl 翻译 VHDL → Vitis HLS 综合 C/C++ → DeepSeek-R1-70B INT4 自动 NL 标签 → 质量过滤 → 131K Apache-2.0 数据集。
3. **消融关键**：**Verilog-only INT4** 是最优配置（不是 Verilog+C++，不是 BF16）。样本量 > 标签增强 > 代码可执行性过滤。
4. **训练**：Granite-3.3-8B / Qwen2.5-Coder-7B-32B 全量微调；A40-48GB GPU。
5. **结果**：Qwen2.5-32B 在 131K 上达到 VerilogEval-Machine Pass@10 = **89.3%**、Human Pass@10 = **64.2%**；等规模 11K 对比 OpenRTLSet 全面超 MG-Verilog（最高 +16.4 pp P@1）。
6. **创新**：131K 最大完全开源 Verilog 数据集、三源融合（Verilog+VHDL+HLS）、Verilog-only INT4 消最优配置、严格控制变量的等规模对比。
7. **局限**：未验证可综合性、未评估在 RTLLM / ChipBench 等其他 benchmark、未公开 SFT 详细超参。
8. **位置**：EDA 17 阶段里的 ①RTL 设计上游——为「LLM 自动生成 RTL」提供基础训练数据，与 [PRO-V](../PRO-V/论文深度讲解.md) 等 verification 工具互补。

## 附录 A：数据集字段详细定义

从 HuggingFace 数据卡片（`ESCAD/OpenRTLSet`）提取的每个样本字段语义：

| 字段名 | 类型 | 含义 | 示例 |
|---|---|---|---|
| `index` | int | 全局唯一样本 ID | `12345` |
| `ioheader` | str | 模块 I/O 声明（含 module 关键字） | `module mux2(input [3:0] a, input [3:0] b, input sel, output reg [3:0] y);` |
| `verilog_code` | str | 模块主体实现（不含 module 声明行） | `always @(*) begin\n  if (sel) y = a;\n  else y = b;\nend` |
| `full_code` | str | ioheader + verilog_code 拼接 | `module mux2(...) always @(*) ... endmodule` |
| `llm_response` | str | DeepSeek-R1 生成的功能描述 | `This is a 2-to-1 multiplexer that selects between two 4-bit inputs based on a select signal...` |
| `Repo_url` | str | 原始 GitHub 仓库链接 | `https://github.com/user/repo/blob/main/mux2.v` |
| `lic_name` | str | 仓库 license 名 | `MIT`, `Apache-2.0`, `BSD-3-Clause` |
| `children_index` | list[int]（实验性） | 该模块实例化的子模块 ID | `[678, 901]` |

**注意 `children_index` 是实验性字段**，并非所有样本都有。它的存在暗示未来可以构建模块层级关系图——这对 EDA 的 hierarchical verification 和 design space exploration 有价值，但 OpenRTLSet v1 还没利用这个字段做下游任务。

## 附录 D：建议的扩展方向

基于 OpenRTLSet 的现状，可以从以下几个方向扩展：

### D.1 加入可综合性验证

**现状问题**：OpenRTLSet 评估 Pass@k 时只检查 VerilogEval 的 reference output，不跑 yosys 综合。

**建议改进**：

```python
# 在评估流程中加入
import subprocess
result = subprocess.run(['yosys', '-p', f'read_verilog {rtl}; synth;'], 
                       capture_output=True)
if result.returncode != 0:
    return "synthesis_failed"  # 算作 pass=false
```

这能让数据集真正反映「能用的 RTL」而非「语法对就行」。

### D.2 加入 sequential 电路比例

**现状问题**：OpenRTLSet 大量来自 GitHub Verilog，其中 sequential 电路（带 `always @(posedge clk)`）占比可能较低。

**建议改进**：
- 主动从 OpenCores 等社区收集大型 sequential IP（CPU core、DDR controller、Ethernet MAC）
- 增大 VerilogEval-Human 类复杂电路在训练集中的占比

### D.3 探索 LoRA 微调

**现状问题**：论文只做了全量微调，对 32B 模型显存压力大（>160GB）。

**建议改进**：

```python
# 用 LoRA 把显存压到 24GB（A40）
from peft import LoraConfig, get_peft_model
lora_config = LoraConfig(r=16, lora_alpha=32, target_modules=["q_proj", "v_proj"])
model = get_peft_model(base_model, lora_config)
# 训练 → 合并 LoRA → 推理
```

这能让 OpenRTLSet 微调在消费级 GPU 上可行。

### D.4 与 [PRO-V](../PRO-V/论文深度讲解.md) 集成

**现状问题**：OpenRTLSet 只生成 RTL，不生成 testbench。设计师用 OpenRTLSet 微调的 LLM 生成 RTL 后，还要手动写 testbench。

**建议改进**：
- 把 OpenRTLSet 微调后的 LLM 和 PRO-V 串联：LLM_RTL → Verilog → PRO-V → testbench
- 形成「NL spec → RTL + testbench」的端到端自动化流水线

这是未来 EDA Agent 的方向。
