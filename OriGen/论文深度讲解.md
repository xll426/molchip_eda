## 1. 一句话定位

**OriGen 是一个完全开源的双 LoRA 框架：冻结 DeepSeek-Coder-7B，通过 code-to-code augmentation 用 Claude3-Haiku 蒸馏出高质量 RTL 训练数据训练 Gen LoRA（规格->RTL），再构造错误修正数据集训练 Fix LoRA（错误+编译器反馈->修复 RTL），在 VerilogEval-Human pass@1 达到 54.4%（超过 GPT-4 Turbo 54.2%），VerilogFixEval 语法修复率 89.1%（超过 GPT-4 Turbo 19.9 pp），但功能修复率仅 33.5%。**

这句话里的 5 个承重点，后面逐一拆解：

1. **完全开源的双 LoRA 架构** -- 基础模型选择 DeepSeek-Coder-7B-Instruct-v1.5（当时 7B 级 Verilog 最强），冻结全部 7B 参数，仅训练两个 rank-32 的 LoRA adapter（各约 75M 参数），避免修复数据污染生成能力。
2. **Code-to-code augmentation** -- 从开源 RTL 出发，让 Claude3-Haiku 反向生成高层次自然语言描述，再用描述重新生成 RTL 并通过 Icarus 编译验证，最终构建约 180K 样本的高质量 (description, RTL) 数据集。
3. **Self-reflection 修复机制** -- 训练 Fix LoRA 专门接收"原始规格 + 错误 RTL + 编译器 stderr"，输出修复后的 RTL，推理时若生成代码编译失败则进入修复循环，最多迭代 N 轮。
4. **VerilogEval-Human pass@1=54.4%** -- 超越前序最佳开源模型（RTLCoder-DeepSeek 41.6%）12.8 pp，超越 GPT-4 Turbo (54.2%) 0.2 pp，在 Machine 子集 (74.1%) 甚至超越 Claude3-Opus (60.2%)。
5. **VerilogFixEval 语法修复率 89.1%** -- 自建的 221 样本 benchmark，语法修复显著领先 GPT-4 Turbo (69.2%)，但功能修复率 (33.5%) 说明"修到能编译"远不等于"修对逻辑"。

## 3. 输入 / 输出

本节以一个贯穿全文的 walkthrough 例子展开：用 OriGen 生成一个 1-bit 半加器。

### 3.1 输入（生成任务）

自然语言设计规格，通过 `### Instruction` / `### Response` 模板组织：

```text
### Instruction
Create a 1-bit half adder with inputs a and b, and outputs sum and carry.
The sum is the XOR of a and b, the carry is the AND of a and b.

### Response
```

- **模块名、端口名、位宽**由用户指定（也可由模型推断）。
- 训练阶段，Description 由 code-to-code augmentation 自动生成（见第 4 节）。
- 可选的已知模块头（module header）可约束输出接口。

### 3.2 输入（修复任务）

```text
### Instruction
Create a 1-bit half adder...

### Buggy RTL
module half_adder(input a, input b, output sum, output carry)
    assign sum = a ^ b
    assign carry = a & b
endmodule

### Compiler Error
half_adder.v:2: syntax error
half_adder.v:2: error: Missing ';'.
half_adder.v:3: syntax error
half_adder.v:3: error: Missing ';'.

### Response
```

修复任务的输入由四部分组成：任务描述、错误 RTL、编译器 stderr、可选模块头。错误 RTL 和 stderr 由前置生成步骤自动产生——真实流程是先跑 OriGen 生成，再跑 Icarus 编译，编译失败时才触发 Fix LoRA。

### 3.3 输出

生成任务输出完整的 Verilog 模块：

```verilog
module half_adder (
    input wire a,
    input wire b,
    output wire sum,
    output wire carry
);
    assign sum = a ^ b;
    assign carry = a & b;
endmodule
```

修复任务的输出同样是完整 Verilog 模块——细看发现两个分号已补全。本地实测输出经 Icarus 编译成功，4-vector testbench 全部 PASS。

## 4. 方法与架构

这节要解决的问题：OriGen 的 code-to-code augmentation 如何构造高质量训练数据，以及双 LoRA 的推理闭环如何工作。

### 4.1 整体 Pipeline（训练阶段）

```text
开源 RTL 代码（VeriGen/StarCoder2 等）
    │
    ▼
┌──────────────────────────────────────────┐
│  1. 过滤 (Section 3.2)                   │
│  - 超过 300 行或 1536 tokens 的丢弃       │
│  - 平均每行超过 30 tokens 的丢弃          │
│  - 必须含 module/endmodule                │
│  - 必须含 always(含变种) 或 assign        │
│  - 删除所有注释                           │
└──────────────────┬───────────────────────┘
                   │ 过滤后代码
                   ▼
┌──────────────────────────────────────────┐
│  2. 描述生成 (Figure 1 / Figure 3)       │
│  Claude3-Haiku："分析这段 Verilog，用     │
│  高层次概念描述其功能和信号，像写          │
│  电路设计规格书，只输出自然语言"           │
│  输出：自然语言 Description               │
└──────────────────┬───────────────────────┘
                   │ (code, description) 对
                   ▼
┌──────────────────────────────────────────┐
│  3. 代码重新生成 + 编译验证               │
│  Claude3-Haiku 根据 Description 重写 RTL  │
│  → Icarus Verilog 编译验证                │
│  ├─ 编译通过 → enhanced code dataset     │
│  └─ 编译失败 → 进入 4                     │
└──────────────────┬───────────────────────┘
                   │
                   ▼
┌──────────────────────────────────────────┐
│  4. Error-correction dataset 构造         │
│  失败样本 + compiler stderr + 修复后代码   │
│  → 过滤掉"改了模块声明而非模块体"的样本   │
│  → error-correction dataset              │
└──────────────────┬───────────────────────┘
                   │
                   ▼
┌──────────────────────────────────────────┐
│  5. 双 LoRA 训练 (Section 3.4)           │
│  enhanced code dataset → Gen LoRA        │
│  error-correction dataset → Fix LoRA     │
│  （在 Gen LoRA 基础上继续训练）            │
└──────────────────────────────────────────┘
```

### 4.2 推理阶段的 Self-Reflection 闭环（Figure 2）

```text
自然语言 Instruction
    │
    ▼
┌───────────────────────────────┐
│ DeepSeek-Coder 7B + Gen LoRA  │
│ Instruction → 初始 RTL        │
└──────────────┬────────────────┘
               │ 初始 RTL
               ▼
┌───────────────────────────────┐
│ Icarus Verilog 编译           │
│  ├─ 编译通过 → 运行 testbench │
│  │   ├─ 通过 → ✅ 最终 RTL    │
│  │   └─ 失败 → (功能错误,     │
│  │      OriGen 不处理)        │
│  └─ 编译失败 → 进入修复循环   │
└──────────────┬────────────────┘
               │ compiler stderr + buggy RTL
               ▼
┌───────────────────────────────┐
│ DeepSeek-Coder 7B + Fix LoRA  │
│ Instruction + buggy RTL       │
│ + stderr → 修复后 RTL         │
└──────────────┬────────────────┘
               │ 修复后 RTL
               │ 回到编译步骤，循环直到：
               │ - 编译通过 或
               │ - 达到最大迭代次数
               ▼
        最终 RTL (或放弃)
```

关键设计：**不喂回功能仿真失败**。Self-reflection loop 只处理编译失败（语法错误），不处理 testbench mismatch（功能错误）。论文在 VerilogFixEval 的评估证明了这一点——语法修复可做到 89.1%，但功能修复仅 33.5%。

### 4.3 核心模块详解

#### 4.3.1 Code-to-Code Augmentation（论文 Figure 1）

**存在的理由**：开源 RTL 数据集量大但质量参差不齐（没有 review、风格不一致、缺少描述）。直接从开源代码训练效果不佳（baseline pass@1 仅 41.6%）。code-to-code augmentation 用商业 LLM 的知识"蒸馏"和"标准化"这些代码，同时自动产生配对的自然语言描述。

**四步过滤的工程意义**：
- **300 行 / 1536 tokens 上限**：模型 context window=4096，长代码的描述生成质量会退化。
- **平均每行 >30 tokens 丢弃**：非标准格式（如一行写到底），LLM 难以理解也难以为其生成准确描述。
- **必须含 always/assign**：排除纯声明/连线代码（没有行为的模块不值得训练）。
- **删除所有注释**：防止注释里的半成品规格干扰描述生成，确保描述从代码行为而非注释中提取。

**为什么用 Claude3-Haiku 而不是 GPT-4**：论文未明确说明，但 Haiku 是当时性价比最高的商业 LLM，成本低且速度足够快。180K 样本规模的描述生成+代码重写对 API 开销不小。

**迭代修复在数据增强中的作用**：论文 Figure 4 展示了一个具体例子——原始代码是带有同步复位和使能的 flip-flop，增强后的代码结构更规范、风格更统一。更重要的是，编译失败样本及其修复过程构成了 error-correction dataset 的原材料，一举两得。

#### 4.3.2 Gen LoRA（规格->RTL）

**存在的理由**：把 code-to-code augmentation 得到的高质量 (description, RTL) 监督知识注入冻结的 DeepSeek-Coder 7B，避免全量微调带来的灾难性遗忘和高计算成本。

**训练数据格式**（以 `### Instruction / ### Response` 模板组织）：
```text
### Instruction
{code-to-code augmentation 生成的自然语言描述}

### Response
{对应的 Verilog RTL 代码}
```

训练时仅对 `### Response` 之后的 token 计算 causal-LM cross-entropy loss，避免模型在 Instruction 部分浪费容量。

#### 4.3.3 Fix LoRA（错误+反馈->修复 RTL）

**存在的理由**：开源 LLM 的自我反思能力普遍弱于商业模型。OriGen 的做法是——既然生成能力可以通过蒸馏获得，修复能力同样可以。在 Gen LoRA 的基础上，用 error-correction dataset 继续训练，得到专门做修复的 Fix LoRA。

**为什么用两个 LoRA 而不是一个**：论文实验表明，直接在 error-correction dataset（含语法错误的代码）上训练的单一 LoRA，在正常生成任务上表现反而不如 Gen LoRA——训练数据里的语法错误会削弱模型的正常代码生成能力。因此采用分离策略。

**修复 prompt 模板**（论文 Figure 6）：
```text
As a professional Verilog designer, you are tasked with debugging
a Verilog module that has some errors. Below are the details of the
assignment, the original Verilog code with some syntax and functional
errors, and the error messages produced by the compiler.

Task:
{task}

Original Code:
{original_code}

Compiler Error Message:
{error}
```

**error-correction dataset 的过滤**：排除掉"通过修改模块声明而非模块体来修复"的样本——论文认为修改声明（如增删端口）不是真正的修复能力，且会破坏模块接口兼容性。

### 4.4 模块职责矩阵

| 模块 | 输入 | 输出 | 用到的模型/工具 | 是否需训练 |
|------|------|------|---------------|:---:|
| Code-to-code 过滤 | 开源 RTL 代码 | 过滤后的 RTL | 规则（行数/token数/关键词） | 否 |
| Description 生成 | 过滤后的 RTL | 自然语言 Description | Claude3-Haiku | 否（API） |
| Code 再生+验证 | Description | (RTL, pass) 或 (错误 RTL, stderr) | Claude3-Haiku + Icarus | 否 |
| Error-correction 构造 | 编译失败的 (RTL, stderr, 修复后RTL) | 三元组监督数据 | Icarus | 否 |
| Gen LoRA 训练 | (Description, RTL) 对 | Gen LoRA adapter | DeepSeek-Coder 7B (冻结) + LoRA rank=32 | **是** |
| Fix LoRA 训练 | (instruction, buggy RTL, stderr, fixed RTL) 四元组 | Fix LoRA adapter | DeepSeek-Coder 7B (冻结) + Gen LoRA + LoRA rank=32 | **是** |
| 推理-生成 | 自然语言 Instruction | 初始 Verilog RTL | DeepSeek-Coder 7B + Gen LoRA | 否 |
| 推理-修复 | Instruction + buggy RTL + stderr | 修复后 Verilog RTL | DeepSeek-Coder 7B + Fix LoRA | 否 |

## 5. 关键公式

### 5.1 pass@k 评估指标

论文唯一编号公式 (1)，用于评估 RTL 代码生成的功能正确率：

$$
\text{pass@k} := \mathbb{E}_{\text{Problems}} \left[ 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}} \right]
$$

- $\text{pass@k}$：每个问题生成 $n$ 个样本，如果其中至少有 1 个样本通过单元测试，问题算解决，该指标估计这个概率的无偏估计。
- $n$：每题生成的样本总数（论文取 $n=10$）。
- $c$：$n$ 个样本中通过测试的数量（$c \leq n$）。
- $k$：阈值参数（pass@1 表示 1 个样本就够，pass@5 表示 5 个中至少 1 个通过）。
- $\binom{n-c}{k}$：从失败样本中选 $k$ 个的组合数（理解为"选出的 $k$ 个全错"的情况数）。

**工程直觉**：这个公式不是简单的 $c/n$（那只是单样本通过率），而是从 $n$ 次生成中抽取 $k$ 个样本都没有通过的"坏运气概率"的补集。它给出的是"如果你让用户生成 $k$ 个候选然后选一个，有多大把握至少有一个对的"的无偏估计。

## 6. 训练与实验设置

### 6.1 是否需要训练

**需要训练**，为两阶段 LoRA 微调（不是从头训练，不是全量微调）：

**第一阶段 -- Gen LoRA（生成能力）**：
1. 固定 DeepSeek-Coder-7B-Instruct-v1.5 全部 7B 参数。
2. 在 code-to-code augmentation 得到的约 180K 样本 enhanced code dataset 上训练 rank-32 LoRA。
3. 目标：仅对 `### Response` 之后的 token 计算 causal-LM cross-entropy。
4. 监控 validation loss 做早停。

**第二阶段 -- Fix LoRA（修复能力）**：
1. 以已合并 Gen LoRA 的模型为基础（base 仍冻结）。
2. 在 error-correction dataset 上继续训练第二个 rank-32 LoRA。
3. 目标同上。

### 6.2 训练超参

| 参数 | 数值 | 来源 |
|------|------|------|
| 基础模型 | `deepseek-ai/deepseek-coder-7b-instruct-v1.5` | 论文 Section 4.1 |
| LoRA rank `r` | 32 | 代码/model card（论文正文未给出具体 rank） |
| LoRA alpha | 32（缩放系数=1） | 代码/model card |
| 目标层 | 每层 7 个线性层：`q_proj, k_proj, v_proj, o_proj, gate_proj, up_proj, down_proj` | 代码 |
| LoRA 参数量 | 约 75M（30 层 x 7 层 x 2 矩阵 x 32 x 4096 / 每层） | 计算 |
| 精度 | bfloat16 模型 + float16 混合精度训练 | 论文 Section 4.2 |
| 优化器 | AdamW，$\beta_1=0.9$，$\beta_2=0.999$ | 论文 Section 4.2 |
| 学习率调度 | cosine decay + warmup ratio 0.03 | 论文 Section 4.2 |
| Batch size | 8 | 论文 Section 4.2 |
| Context length | 4096 | 基础模型元数据 |

这张表说明了三点：(1) OriGen 在 Human pass@1 上以 54.4% 略微超过 GPT-4 Turbo 的 54.2%，并在 Machine 子集 (74.1%) 上全面碾压所有商业模型（Claude3-Opus 仅 60.2%），因为 OriGen 的训练数据本身就由 LLM（Claude3-Haiku）生成，天然适应 LLM 风格的描述。(2) 它在 open-source 阵营中全面领先，比最佳对手 RTLCoder-DeepSeek 高 12.8 pp。(3) 在 RTLLM 上与 GPT-4 Turbo 持平 (65.5%)，说明泛化到未见过的真实设计任务时仍有竞争力。

## 7. 创新点

### 创新点 1：Code-to-Code Augmentation -- 从 RTL 反向生成描述而非从关键词正向合成

**以前的做法**：RTLCoder 从几百个数字设计关键词出发，让 GPT-3.5 生成指令再生成 RTL。问题是关键词集合有限，限制了数据规模和多样性。

**OriGen 的做法**：从已有开源 RTL 代码出发，用 Claude3-Haiku 反向提取高层次自然语言描述，再让 Claude3-Haiku 根据描述重新写 RTL 并用 Icarus 编译验证。这相当于"从任意 RTL 生成配对的 (spec, code) 监督数据"——不再受关键词集合限制，可以覆盖开源代码中出现的任何设计模式。

**为什么更好**：数据的规模和多样性不再受限于预定义的关键词集合。同时，重写+编译验证的流程天然产生 error-correction dataset 的原材料——失败样本直接拿来训练 Fix LoRA。

### 创新点 2：Self-Reflection 作为显式训练的修复能力而非推理时 prompt engineering

**以前的做法**：RTLFixer 维护一个约 80 条错误的 guidance 数据库，生成失败时检索最相似 guidance 喂给模型；AutoChip 直接把编译器 stderr 贴进 prompt。两者都依赖商业 LLM 的固有修复能力。

**OriGen 的做法**：构造 error-correction dataset（包含多种错误类型和修复方案），显式训练 Fix LoRA 学习"读懂 stderr + 定位问题 + 修订代码"的能力。这比 prompt engineering 更系统——模型从数据中学习了错误-修复的模式映射，而不是每次靠 prompt 引导 LLM 临时推理。

### 创新点 3：双 LoRA 分离策略 -- 生成和修复用不同参数但共享基础模型

**设计动机**：在 error-correction dataset（含语法错误代码）上直接训练会削弱正常生成能力（论文实验证实）。但生成和修复需要共享底层代码理解。双 LoRA 给出优雅权衡：Gen LoRA 从干净数据学生成，Fix LoRA 从错误数据学修复，两者共享 DeepSeek-Coder 基础参数但权重互不污染。

### 创新点 4：VerilogFixEval Benchmark -- 首个专门评估 RTL 自反射修复能力的基准

221 个从性能接近 GPT-3.5 的 LLM 输出中收集的编译失败样本（避免 OriGen 自身产生的错误带来偏差），每个包含 NL 描述+错误代码+stderr，评估指标分语法正确率和功能正确率。这个设计暴露了当前所有模型的致命短板——功能修复远落后于语法修复。

## 9. 与芯片流程的关系

### 9.1 在全流程中的位置

OriGen 是"数字前端的第一步"——它接手的是**人类或系统给出的自然语言模块规格**，输出的是**通过了 Icarus 编译检查（和部分 testbench 验证）的 Verilog RTL**。它的下游是：
- **功能仿真工程**师：需要用更完整的 testbench/formal 验证 OriGen 生成的代码是否真的功能正确
- **逻辑综合工程师**：需要检查生成的 RTL 是否可综合、是否能满足时序约束
- 或者在 Agent 场景下直接接入后续的 lint/综合/formal 工具链

OriGen 解决的核心痛点是"从 0 到 1 写 RTL"的生产力瓶颈——让 LLM 完成初稿，人工只需 review 和修改。

### 9.2 "仿真通过"和"能做成芯片"之间隔着什么

OriGen 在 VerilogEval 上报告的"功能正确率"基于 HDLBits 级别的 testbench——这些 testbench 通常只覆盖基本输入-输出行为，不包含：
- **多周期时序行为**：跨时钟沿的状态机转换、流水线 stall/flush
- **复位行为**：异步复位释放时序、复位后的初始化状态
- **边界条件**：最大/最小位宽、溢出/下溢、空/满标志的精确语义
- **可综合性**：VerilogEval 的 testbench 不检查综合结果，OriGen 的代码可能包含不可综合结构（如 `initial` 块、`$display`、循环边界不固定等）
- **PPA**：没有面积/功耗/时序约束，生成的代码可能功能正确但面积膨胀或关键路径过长

也就是说，OriGen 验证的"功能正确"是在**零延迟、理想化、单模块、有限 testbench** 条件下的正确。从它的输出到可流片的 GDSII，还需要经过 ③-⑬ 的全部阶段。

## 10. 讨论与局限

### 10.1 论文自述的局限

1. **功能修复能力弱**：Fix LoRA 的语法修复率 89.1%，但功能修复率仅 33.5%。论文未提出功能级修复的解决方案。
2. **Self-reflection 仅覆盖编译错误**：推理时的修复循环只在编译失败时触发，不处理 testbench 不通过的情况。
3. **Code-to-code augmentation 依赖商业 LLM**：数据增强和 error-correction dataset 都依赖 Claude3-Haiku——这引入了外部依赖、API 成本和潜在的蒸馏一致性/版权问题。
4. **未验证综合后效果**：所有评估停留在 RTL+testbench 层面，未报告综合后的面积/时序/功耗。

### 10.2 代码/复现层面的问题

（从 [OriGen论文与代码复现详解.md](./OriGen论文与代码复现详解.md) 提炼）

1. **复现范围有限**：本地实测仅覆盖 1-bit half-adder 生成和 and2 语法修复两个最简单案例，使用 Q3_K_M 量化基础模型，未复现论文的完整 VerilogEval/RTLLM/VerilogFixEval 评测。
2. **许可证不透明**：模型卡声明 GPL-3.0，但 GitHub 根目录无标准 LICENSE 文件。权重和代码可能需要分别确认授权，商用需谨慎。
3. **权重格式转换**：作者发布的 LoRA 是 safetensors 格式，需额外转换为 llama.cpp GGUF 格式才能在 CPU 上推理。社区发布的 Q3_K_M GGUF 基础模型与作者指定的基础模型的 SHA 一致性需自行验证。
4. **训练数据未完全公开格式**：HuggingFace 上的 dataset 需要检查实际列名和格式是否符合训练脚本预期，论文中的格式描述（`### Instruction / ### Response`）与实际 HuggingFace revision 可能有出入。
5. **error-correction dataset 的构造细节缺失**：论文描述了从编译失败样本构造数据集的方法，但具体的筛选标准（如"只保留在 module body 内修改的样本"）在代码中的实现细节未完全文档化。
6. **训练成本不透明**：论文未报告 LoRA 训练的具体 GPU 数量/型号/时间/成本。在 180K 样本上做两阶段 LoRA 训练的硬件门槛对个人研究者可能不低。

### 10.3 本资料包的批判性分析

1. **"超越 GPT-4 Turbo"需要解构**：OriGen 在 Human pass@1 (54.4% vs 54.2%) 上的优势仅 0.2 pp，在统计噪声范围内。更有说服力的证据是它在 open-source 阵营的碾压式领先（超 RTLCoder 12.8 pp）和在 Machine 子集的全面领先（因训练数据天然适应 LLM 生成描述）。

2. **VerilogFixEval 的构造偏差**：benchmark 的样本来自"性能接近 GPT-3.5 的 LLM"的输出——这意味着这些样本的错误类型可能偏向于弱模型常犯的错误（如分号缺失、端口未声明），而非真实硬件设计中更复杂的错误（如状态机死锁、协议违例）。Fix LoRA 的高语法修复率可能部分来自"训练/测试错误类型分布相似"。

3. **双 LoRA 策略的部署复杂度**：两个 LoRA 需要在推理时切换（生成用 Gen，编译失败时切换 Fix），增加了工程复杂度。论文没有探索"一个 LoRA 同时做生成和修复"的可行性（只在 ablation 中提到了单一 LoRA 的生成能力下降，但未尝试联合训练策略如 multi-task learning）。

4. **Code-to-code augmentation 的污染风险**：如果用于 augmentation 的开源 RTL 与 VerilogEval benchmark 题目有来源重叠（如都来自 HDLBits），可能导致数据泄漏。论文通过 Icarus 编译过滤提供了一层保护（合成数据需重新编译通过），但不能完全排除功能等价但语法不同的代码被"记忆"。

5. **固定基础模型的局限**：OriGen 的全部设计绑定在 DeepSeek-Coder 7B v1.5 上。如果基础模型更新（如升级到 DeepSeek-Coder v2 或 33B），整个 code-to-code augmentation pipeline 可能需要重跑（因为 tokenizer、context window、代码风格偏好都可能变化）。

## 12. 一分钟复述版

1. OriGen 是一个完全开源的 RTL 代码生成框架，基座是 DeepSeek-Coder 7B v1.5（冻结），训练两个 LoRA adapter：Gen 负责生成，Fix 负责修复。
2. 核心数据来源：code-to-code augmentation——从开源 RTL 出发，用 Claude3-Haiku 反向生成自然语言描述，再用描述重新写 RTL 并通过 Icarus 编译验证，构建约 180K 高质量训练样本。
3. Gen LoRA 在 (description, RTL) 对上训练，学会从自然语言规格生成 Verilog。
4. Fix LoRA 在 (instruction, buggy RTL, stderr, fixed RTL) 四元组上训练，学会读编译器错误信息并修复代码。
5. 推理时：Gen LoRA 生成初始 RTL -> Icarus 编译 -> 若失败，Fix LoRA 接收 stderr + 错误代码 -> 修复 -> 重新编译，循环直到通过或达上限。
6. VerilogEval-Human pass@1 = 54.4%（超越 GPT-4 Turbo 的 54.2%，超越前最佳开源 RTLCoder 12.8 pp）。
7. VerilogEval-Machine pass@1 = 74.1%（全面碾压所有商业模型，因训练数据天然适应 LLM 风格描述）。
8. VerilogFixEval 语法修复率 89.1%（超 GPT-4 Turbo 19.9 pp），但功能修复率仅 33.5%——"修到能编译"远不等于"修对逻辑"。
9. 不做逻辑综合、不做时序分析、不做物理设计，只覆盖芯片流程的阶段 ①+②。
10. 核心局限：修复只能处理语法错误（非功能错误），code-to-code augmentation 依赖商业 LLM，许可证不透明，完整复现的 API 开销和算力门槛高。
