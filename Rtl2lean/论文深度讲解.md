## 1. 一句话定位

**Rtl2lean 是一个 LLM 辅助的 RTL 形式化验证框架：它把 SystemVerilog RTL 自动编译为 Lean 4（基于依赖类型理论的交互式定理证明器）的可执行状态转移模型，自底向上生成四层定理库（组合逻辑 lemma -> 时序块 lemma -> 单周期 theorem -> 可达性/不变量），在 Lean kernel 的类型检查监督下让 LLM 迭代生成中间 lemma 完成证明。6 个真实 SystemVerilog 设计上生成并验证 403 个定理（100% 通过 kernel 检查），358 个基础 lemma 中 287 个（80.2%）可跨证明自动复用，端到端翻译+定理生成仅 0.650 秒。**

这句话里的四个技术承重点，后面逐一拆解：

1. **RTL-to-Lean 4 语义编译器** -- 首个自动化工具，把 SystemVerilog 的事件驱动语义（非阻塞赋值、时钟边沿触发、组合/时序块）编译为 Lean 4 的纯函数式 `step(s, i)` 状态转移模型。PySlang 解析 + IR 规范化 + Lean 后端代码生成一条龙。
2. **四层分层定理框架** -- 不是给每个属性单独写证明模板，而是按粒度把 RTL 语义缓存为四层。L1/L2 的低层 lemma 标记 `@[simp]` 后自动参与所有高层证明，这是 80.2% 复用率的关键机制。
3. **LLM + Lean kernel 的受控证明辅助** -- LLM 只生成候选中间 lemma，每个候选必须经 Lean kernel 类型检查通过才能使用。kernel 是约几百行可信代码的"守门员"，LLM 的幻觉无法污染证明库。
4. **跨证明 lemma 复用** -- 被 kernel 接受的 lemma 加入可复用池，后续证明通过 `rw`、`apply`、`simp` 等 tactic 直接引用。证明工作量随设计规模呈亚线性增长。

> Rtl2lean 的"形式验证"与 Formality/Conformal 的"形式验证"虽然都在阶段 ⑥，但方法论有本质区别。Formality/Conformal 用 SAT/SMT 自动求解器判断"两个电路对所有输入是否等价"——这是**搜索问题**（是否存在反例？），受状态爆炸限制，且只能做等价性检查。Rtl2lean 用 Lean 4 的交互式定理证明构造"系统的某个属性是否在所有执行中成立"——这是**构造问题**（能否构造一个证明项？），可以处理任意步数的属性，通过归纳法突破有界限制，但需要人/LLM 提供证明策略。详见第 9 节对比。

## 3. 输入 / 输出

### 3.1 输入

Rtl2lean 的输入包括四部分：

**（1）SystemVerilog RTL 源码**：来自 OpenCores 的寄存器传输级设计，必须包含组合逻辑（`assign` / `always_comb`）、时序逻辑（`always_ff` @ posedge clk）、同步复位、固定位宽运算。支持的 RTL 子集：单时钟域、同步复位、阻塞/非阻塞赋值、`if-else` 条件控制、`BitVec` 位向量运算。不支持：多时钟域、异步复位、`interface`、`assertion`、`generate`、`Z`/`X` 态、`#delay`。

**具体输入示例**（带复位和使能的计数器）：

```verilog
module counter (
    input  logic        clk, rst, enable,
    output logic [7:0]  count,
    output logic        overflow
);
    logic [7:0] count_reg;
    assign count = count_reg;
    assign overflow = (count_reg == 8'hFF);

    always_ff @(posedge clk) begin
        if (rst)          count_reg <= 8'h00;
        else if (enable)  count_reg <= count_reg + 8'h01;
    end
endmodule
```

此例包含 Rtl2lean 处理的所有典型要素：连续赋值、时序过程块、同步复位、条件更新、位向量运算。

**（2）高层验证属性**：用户以自然语言给出的功能/安全性命题，框架将其构造为 Lean theorem。例如："当复位与使能均无效时，计数寄存器保持不变。"

**（3）Lean 4 证明环境**：版本 4.26.0，提供依赖类型系统与 kernel 类型检查器。

**（4）LLM 服务**：用于生成候选中间 lemma。论文未公开具体模型名称与版本。

### 3.2 中间产物

**（1）Lean 4 状态转移模型**（阶段 1 输出）：

```lean
structure CounterState where
  count_reg : BitVec 8
  overflow  : BitVec 1
structure CounterInputs where
  rst    : BitVec 1
  enable : BitVec 1
def initState : CounterState := { count_reg := 8'h00, overflow := 1'b0 }

def comb_overflow (s : CounterState) : BitVec 1 :=
  if s.count_reg = 8'hFF then 1'b1 else 1'b0

def proc_alwaysff (s : CounterState) (i : CounterInputs) : CounterState :=
  if i.rst = 1'b1 then
    { s with count_reg := 8'h00 }
  else if i.enable = 1'b1 then
    { s with count_reg := s.count_reg + 8'h01 }
  else s

def step (s : CounterState) (i : CounterInputs) : CounterState :=
  let s' := proc_alwaysff s i
  { s' with overflow := comb_overflow s' }
```

`step(s, i)` 是一个纯函数：给定当前状态 `s` 和输入 `i`，返回下一状态，无副作用。三种情形按优先级排序——复位 > 使能 > 保持，精确对应 RTL 的 `if-else` 优先级语义。

**（2）四层定理库**（阶段 2 输出，部分示例）：

```lean
-- L1: 组合逻辑 lemma（标记 @[simp] 自动复用）
@[simp] theorem overflow_compute (s : CounterState) :
  comb_overflow s = (if s.count_reg = 8'hFF then 1'b1 else 1'b0) := rfl

@[simp] theorem overflow_preserves_count_reg (s : CounterState) :
  (comb_overflow_set s).count_reg = s.count_reg := rfl

-- L2: 时序块 lemma
theorem proc_alwaysff_deterministic (s : CounterState) (i : CounterInputs) :
  proc_alwaysff s i = proc_alwaysff s i := rfl

theorem proc_alwaysff_rst (s : CounterState) (i : CounterInputs) :
  i.rst = 1'b1 -> (proc_alwaysff s i).count_reg = 8'h00 := by
  intro h; simp [proc_alwaysff, h]

-- L3: 单周期 theorem
theorem step_reset (s : CounterState) (i : CounterInputs) :
  i.rst = 1'b1 -> step s i = { count_reg := 8'h00, overflow := 1'b0 } := by
  intro h; simp [step, proc_alwaysff, h]

-- L4: 可达性与不变量
def reachable (s : CounterState) : Prop :=
  exists (inputs : List CounterInputs),
    List.foldl (fun st inp => step st inp) initState inputs = s

theorem reachable_step_closed (s : CounterState) (i : CounterInputs) :
  reachable s -> reachable (step s i) := by
  intro h; rcases h with <inputs, h_eq>
  exact <inputs ++ [i], by simp [h_eq]>
```

**（3）LLM 生成的候选中间 lemma**（阶段 3 中 LLM 根据证明上下文 + Lean 错误反馈动态生成）：只有通过 kernel 类型检查的候选才被加入 lemma 池。

### 3.3 输出

最终输出包括：

1. **403 个机器检查定理**：45 个高层属性 + 358 个基础 lemma，全部通过 Lean kernel 类型检查
2. **可复用 lemma 池**：287 个标记 `@[simp]` 的基础 lemma，`simp` tactic 自动使用
3. **高层属性证明示例**——当复位与使能均无效时计数器保持不变：

```lean
theorem count_stable_when_disabled (s : CounterState) (i : CounterInputs) :
  i.rst = 1'b0 -> i.enable = 1'b0 -> (step s i).count_reg = s.count_reg := by
  intro hrst hen
  simp [step, proc_alwaysff, hrst, hen]
```

此证明仅用 `simp` 即可完成——L1/L2 的 `@[simp]` lemma 已覆盖所需化简规则。

4. **时间开销数据**：`T_e2e` = 0.650s（端到端），`T_Lean` = 5.573s（kernel 检查 403 个定理）

## 4. 方法与架构

这节要解决的问题：**Rtl2lean 是如何把一个 SystemVerilog 模块变成 Lean 4 的机器检查定理集合的**。核心思路分三步：语义编译 -> 分层定理生成 -> LLM 辅助证明。

### 4.1 整体 Pipeline（对应论文 Figure 1）

```text
Input: SystemVerilog RTL + 高层验证属性
                   |
                   v
+--- 阶段 1: RTL-to-Lean 语义编译 ------------------------------------+
|  PySlang 解析 -> typed AST                                          |
|       -> IR 规范化（条件归约/阻塞非阻塞区别/赋值语义保留）            |
|       -> 优化（常量折叠/死代码消除/公共子表达式消除）                  |
|       -> Lean 4 后端代码生成                                         |
|  输出: State / Inputs / Outputs 类型 + step(s,i) 纯函数              |
+--------------------------------------------------+------------------+
                                                   |
                                                   v
+--- 阶段 2: 四层定理框架生成（自底向上，确定性规则引擎）---------------+
|  L1 组合逻辑 lemma: 语义 lemma + 保持 lemma（标记 @[simp]）         |
|       |                                                              |
|  L2 时序块 lemma: 确定性 lemma + 写集外保持 + 复位行为               |
|       |                                                              |
|  L3 单周期 theorem: 复位/确定性/输出反射/FSM 转移                    |
|       |                                                              |
|  L4 可达性与不变量: reachable(s) 定义 + 单步封闭 + 状态不变量       |
+--------------------------------------------------+------------------+
                                                   |
                                                   v
+--- 阶段 3: 自主证明与 Lemma 复用 ------------------------------------+
|  对每个高层属性 T：                                                  |
|    +--> 基于 L_base + L_pool 尝试证明 (simp/rw/apply)               |
|    |    |                                                            |
|    |    +--> 成功? -> 完成，L_pool += {T} + H                       |
|    |    |                                                            |
|    |    失败?                                                        |
|    |      |                                                          |
|    |      v                                                          |
|    |   LLM 生成候选 lemma(goal + context + Lean error)               |
|    |      |                                                          |
|    |      v                                                          |
|    |   Lean kernel 类型检查                                          |
|    |      |              |                                           |
|    |    通过            拒绝                                         |
|    |      |              +--> 反馈错误给 LLM，重新生成             --+
|    |      v                                                          |
|    |   加入 L_pool，继续证明                                        --+
+----------------------------------------------------------------------+
                   |
                   v
    最终输出: 403 个机器检查定理 + 287 个可复用 lemma (80.2%)
```

### 4.2 核心模块详解

#### 模块 A：RTL-to-Lean 语义编译器（阶段 1）

**存在的理由**：SystemVerilog 的事件驱动语义（`always_ff @(posedge clk)` 时钟边沿触发、非阻塞赋值 `<=` 的并行更新、阻塞赋值 `=` 的立即更新）与 Lean 4 的依赖类型理论存在根本差异。直接编码会导致每次证明都要展开完整的硬件调度语义。解决方式是用编译器规范化——把所有时钟边沿行为归约到单一纯函数。

**翻译规则**：

| RTL 概念 | Lean 4 映射 | 语义说明 |
|---|---|---|
| `reg` / `logic`（在 `always_ff` 中赋值） | `Structure` 字段 | 所有寄存器打包为 `State` 类型 |
| 输入端口 | `Inputs` 结构体字段 | 单周期输入快照 |
| 输出端口 | `Outputs` 结构体 或 组合函数返回值 | 从当前状态计算 |
| `assign` / `always_comb` | 纯函数 | 组合语义：无副作用 |
| `always_ff @(posedge clk)` | `proc_alwaysff(s, i)` 纯函数 | 时序语义：计算下一状态 |
| `if (rst) ... else if (enable) ...` | 嵌套 `if-then-else` | 条件归约，保留优先级 |
| 阻塞赋值 `=` | `let` 绑定（顺序） | 组合逻辑中保留依赖顺序 |
| 非阻塞赋值 `<=` | `{s with f1 := v1, f2 := v2}` | 并行字段更新，所有 `<=` 同时生效 |
| `[N-1:0]` | `BitVec N` | 固定位宽，保留溢出/截断语义 |

**具体实现路径**：前端用 PySlang 解析 SystemVerilog 构造带类型的 AST（Abstract Syntax Tree，抽象语法树）；中间表示（IR）层将条件更新规范化为选择表达式、区分阻塞/非阻塞赋值的更新语义；经常量折叠、死代码消除、公共子表达式消除（CSE，Common Subexpression Elimination）等标准优化后，Lean 后端生成包含 `State`、`Inputs`、`Outputs` 类型和 `step(s, i)` 纯函数的完整 Lean 4 源码。

**翻译器覆盖范围**：组合逻辑、单时钟域时序逻辑、同步复位、位向量运算。

**翻译器不覆盖**：多时钟域/异步复位（需跨时钟域语义建模，论文未涉及）、`interface`/`assertion`/`coverage`（非可综合验证组件）、`Z`/`X` 态（Lean `BitVec` 无此四值语义）、`#delay`（无物理延迟建模）、参数化模块/`generate`（论文未提及处理方式）。

#### 模块 B：四层定理框架生成器（阶段 2）

**存在的理由**：直接对高层属性做证明时，每次都要展开组合函数、时序过程、`step` 的完整定义——证明脚本极长且充满重复。分层的本质是把硬件语义按粒度缓存——低层是"硬件语义原子"，高层用它们拼成复杂属性。类似 CPU 的 L1/L2/L3 cache 分层思想。

**这是确定性规则引擎，不涉及 LLM。**

**L1 组合逻辑 lemma**：针对连续赋值和组合过程生成的每个组合函数，为每个更新字段生成语义 lemma（描述计算方式），为未修改字段生成保持 lemma（`(f s).field = s.field`），标记 `@[simp]` 属性后 `simp` tactic 自动使用。这是 80.2% 复用率的核心基础。

**L2 时序块 lemma**：针对 `always_ff` 等时序块生成的状态更新函数，推导确定性 lemma、写集合外寄存器保持 lemma、复位行为 lemma（当复位模式被识别时）。将寄存器级行为打包为可复用证明单元，避免后续证明反复展开完整时序函数。

**L3 单周期 theorem**：围绕统一 `step` 函数，刻画复位行为（`i.rst = true -> step s i = initState`）、转移确定性、输出反射（output 值与对应寄存器一致）、有限状态机（FSM，Finite State Machine）转移关系。

**L4 可达性与不变量**：定义可达状态 `reachable(s) = exists (inputs : List Inputs), foldl step initState inputs = s`。证明单步封闭性（`reachable(s) -> reachable(step s i)`），建立跨所有可达状态的不变量。L4 提供了从"单周期属性"跃升到"任意步数属性"的归纳基础——这是 ITP 路线相比 BMC（Bounded Model Checking，有界模型检查）有界性局限的关键突破口。

#### 模块 C：LLM 辅助证明循环（阶段 3）

**存在的理由**：L1-L4 的自动定理库覆盖了"和具体设计无关的通用属性"（确定性、字段保持、复位行为等）。但高层功能属性（如"计数器在特定条件下不溢出"、"FIFO 指针不越界"）需要设计相关的中间 lemma——这些无法用固定模板生成。

**LLM 的角色被严格限定**：只生成候选中间 lemma 的命题陈述（Lean 代码），不直接输出完整证明脚本。每个候选必须经 Lean kernel 类型检查通过才能使用——kernel 是最终裁判，LLM 的幻觉无法通过类型检查。

**LLM 输入**：当前证明目标 `T`、局部上下文（相关定义和已引入的变量/假设）、已有 lemma 池 `L_base union L_pool`、Lean 错误信息 `e_k`（上次尝试的 kernel 反馈）。

**LLM 输出**：候选 lemma 的 Lean 4 命题代码（如 `theorem invariant_holds (s : CounterState) : ... := by sorry`）。

**迭代循环**：证明任务先尝试基于现有定理库直接完成；若失败，LLM 根据当前证明目标和 Lean 错误反馈生成候选 lemma；Lean kernel 检查候选——通过则加入 `L_pool` 并继续证明，拒绝则返回诊断反馈给 LLM 重新生成；循环直至证明通过或无法继续。

**为什么不让 LLM 直接写整个证明**：形式证明中一个错误推理步骤就全盘无效；kernel 无法自动修正不完整的证明脚本；但 kernel 可以精确判断一个 lemma 命题是否类型正确。让 LLM 提命题、kernel 检查、再由现有 tactic 在扩充的 lemma 池下完成证明——这是"有防火墙的分工"。

### 4.3 模块职责矩阵

| 模块 | 输入 | 输出 | 用到的工具 | 是否需训练 |
|------|------|------|-----------|:---:|
| 语义编译器 | SystemVerilog RTL 源码 | Lean 4 `State`/`Inputs`/`Outputs` 类型 + `step` 函数 | PySlang, 自定义 IR, Lean 4 后端 | 否 |
| 四层定理生成器 | Lean 4 模型 | L1-L4 定理库（358 个基础 lemma） | 确定性规则引擎 | 否 |
| LLM 证明辅助 | 证明目标 + 上下文 + lemma 池 + Lean 错误 | 候选中间 lemma | LLM API + Lean 4 kernel | 否（直接用现成 LLM） |

## 5. 关键公式

### 5.1 形式证明的基本结构

Lean 4 基于依赖类型理论和"命题即类型（Propositions-as-Types）"原则。命题 `P` 是一个类型，证明 `p` 是该类型的一个项（proof term）。

$$
\Gamma \vdash P
$$

- `\Gamma`：逻辑上下文，包含变量声明、假设、已定义对象、已证明的定理
- `P`：待证命题（在依赖类型论中即"类型"）
- `\vdash`：可推导关系——`P` 可以从 `\Gamma` 通过合法推理规则推导出来

**为什么这个形式化如此重要**：在命题即类型范式下，证明 `P` 等价于构造一个类型为 `P` 的项：

$$
\Gamma \vdash p : P
$$

Lean kernel 的类型检查器验证 `p` 是否确实具有类型 `P`。

- `p`：证明项（proof term）——类型为 `P` 的 Lean 项，即命题 `P` 的形式证明
- `:`：类型归属关系——`p : P` 读作"p 是 P 的证明"或"p 属于类型 P"
- kernel 是约几百行可信代码——只要信任这几百行，就信任所有经它检查的证明。这与 SAT/SMT 求解器不同：SAT 求解器的正确性本身从未被形式化验证。

### 5.2 中间 Lemma 分解策略

不直接证明目标定理 `T`，而是先建立中间 lemma `L_1` 到 `L_n`，再用它们推导 `T`：

$$
L_1, L_2, \ldots, L_n
$$

$$
\Gamma \vdash L_1, \quad \Gamma \vdash L_2, \quad \ldots, \quad \Gamma \vdash L_n
$$

$$
\Gamma, L_1, L_2, \ldots, L_n \vdash T
$$

- `L_i`：中间 lemma，是 `T` 的辅助性质
- 中间 lemma 不改变 `T` 的语义——只暴露证明所需的辅助事实
- 这些 lemma 一旦证明，可以被其他高层属性的证明复用

**工程直觉**：这是数学证明的标准做法——不直接证复杂的结论，而是先建立一系列引理，再组合它们。Rtl2lean 的创新在于让 LLM 在 kernel 监督下自动发现这些引理。

### 5.3 单周期转移语义（step 函数的形式化）

$$
\text{step}(s, i) =
\begin{cases}
\text{init}, & i.\text{rst} = \text{true} \\
s[\text{count} \leftarrow s.\text{count} + 1], & i.\text{enable} = \text{true} \\
s, & \text{otherwise}
\end{cases}
$$

- `s`：当前硬件状态（所有寄存器的快照）
- `i`：当前周期输入向量
- `s[\text{count} \leftarrow s.\text{count} + 1]`：函数式记录更新——创建新状态，count 字段被替换为 `s.count + 1`，其余字段保持不变
- 三种情形按优先级排序：复位 > 使能 > 保持

**工程直觉**：`step` 是 Rtl2lean 的核心抽象——它把时钟边沿触发、非阻塞赋值、条件优先级这些 Verilog 的分布式语义折叠为一个纯数学函数。"纯"意味着无副作用、无隐式状态、输入相同则输出必然相同。这是后续所有定理证明的基础。

### 5.4 LLM 迭代证明循环

证明任务的形式化上下文：

$$
C(T) = (M, T, L_{\text{base}}, L_{\text{pool}})
$$

- `M`：生成的 Lean 4 状态转移模型（`State`/`Inputs`/`step` 的定义）
- `T`：待证目标定理
- `L_{\text{base}}`：四层定理框架自动生成的基础 lemma 集合
- `L_{\text{pool}}`：之前任务中已验证的可复用 lemma 池

迭代生成候选证明：

$$
p_{k+1} = \text{Generate}\;(C(T), e_k)
$$

- `p_k`：第 `k` 次迭代的候选证明/lemma
- `e_k`：Lean kernel 返回的错误信息（若第 `k` 次尝试失败）
- `\text{Generate}`：LLM 的生成函数

终止条件：

$$
\text{Check}(T, p_k) = \text{Pass}
$$

- `\text{Check}`：Lean kernel 的类型检查函数——对 `p_k` 做完整类型检查，返回 Pass 或具体的编译错误
- `\text{Pass}`：类型检查通过——`p_k` 被 kernel 接受为 `T` 的有效证明
- 该条件成立时循环终止，`T` 加入已验证定理集合

成功后 lemma 池扩充：

$$
L_{k+1} = L_k \cup \{T\} \cup H
$$

- `H`：证明过程中发现的辅助 lemma 或局部 `have` 语句
- 后续证明通过 `rw`（重写）、`apply`（应用）、`simp`（化简）等 tactic 复用这些结果

**为什么这样设计**：相比于让 LLM 直接输出完整证明脚本，这种"lemma-粒度"的辅助把 LLM 的错误限制在单个命题级别。一个错误的候选 lemma 被 kernel 拒绝后，不污染证明库，LLM 收到精确的错误反馈后重试。成功概率远高于"一步到位"的直接证明生成。

### 5.5 评估指标

证明成功率：

$$
\text{Proof Success Rate} = \frac{N_{\text{proved}}}{N_{\text{total}}} \times 100\% = 100\%
$$

- `N_{\text{proved}}`：被 Lean kernel 成功接受的定理数（403）
- `N_{\text{total}}`：生成的定理总数（403）

可复用 lemma 比例：

$$
R_{\text{reuse}} = \frac{N_{\text{reusable}}}{N_{\text{lemma}}} \times 100\% = 80.2\%
$$

- `N_{\text{reusable}}`：可在后续证明中自动复用的基础 lemma 数（287）
- `N_{\text{lemma}}`：基础 lemma 总数（358）
- 注意：该指标衡量的是"可被自动复用"的比例（标记了 `@[simp]`），而非实际被调用的比例

## 6. 训练与实验设置

### 6.1 是否需要训练

**不需要训练。** Rtl2lean 是一个纯推理时系统——不微调任何模型参数。它直接调用现成的 LLM 作为证明辅助。核心工作在于 RTL 到 Lean 4 的语义编译（确定性规则引擎）、四层分层定理生成（确定性规则引擎）、以及 LLM 与 Lean kernel 的交互式证明协议设计。论文未公开所使用的 LLM 型号与版本。

### 6.2 实验设置

**Benchmark 设计列表**（来自 OpenCores，论文 Table I）：

| Design | Main Function |
|--------|---------------|
| `debounce_edge` | Debouncing and edge detection（去抖动与边沿检测） |
| `fir_filter` | Finite impulse response filtering（有限冲激响应滤波） |
| `pwm_generator` | Pulse-width modulation（脉冲宽度调制） |
| `lfsr_crc` | LFSR and CRC computation（线性反馈移位寄存器与循环冗余校验） |
| `sync_fifo` | Synchronous FIFO buffering（同步 FIFO 缓冲） |
| `ps2_keyboard` | PS/2 keyboard control（PS/2 键盘控制） |

这 6 个设计覆盖了不同功能类型和硬件结构：组合+时序混合（debounce_edge）、数据通路（fir_filter、pwm_generator）、控制密集型（lfsr_crc、ps2_keyboard）、存储密集型（sync_fifo）。

**实验环境**：Intel Xeon Gold 6148 CPU、629 GB RAM、Lean 4.26.0。

**评估指标**（论文 Table II）：总定理数 `N_total`、高层属性数 `N_property`、基础 lemma 数 `N_lemma`、证明成功率 `R_proof`、端到端时间 `T_e2e`、Lean 检查时间 `T_Lean`、可复用 lemma 比例 `R_reuse`。

### 6.3 关键实验结果

**证明结果与 Lemma 复用**（论文 Table III）：

| Design | N_property | N_lemma | N_reusable | N_total | R_proof | R_reuse |
|--------|:---:|:---:|:---:|:---:|:---:|:---:|
| `debounce_edge` | 8 | 71 | 56 | 79 | 100% | 78.9% |
| `fir_filter` | 7 | 22 | 14 | 29 | 100% | 63.6% |
| `pwm_generator` | 7 | 74 | 62 | 81 | 100% | 83.8% |
| `lfsr_crc` | 7 | 35 | 27 | 42 | 100% | 77.1% |
| `sync_fifo` | 8 | 86 | 70 | 94 | 100% | 81.4% |
| `ps2_keyboard` | 8 | 70 | 58 | 78 | 100% | 82.9% |
| **Total** | **45** | **358** | **287** | **403** | **100%** | **80.2%** |

**这张表说明什么**：

1. 高层属性数量稳定在 7-8 个，与设计类型基本无关。基础 lemma 数量差异巨大（22 到 86），主要由状态变量数、赋值操作复杂度、状态更新依赖关系决定。`sync_fifo` 因为状态变量最多（读/写指针 + FIFO 存储阵列 + 满/空标志）和控制关系最复杂，产生了最多的基础 lemma。
2. 所有 6 个设计均达到 100% 证明成功率——403 个定理无一被 kernel 拒绝。这说明 Rtl2lean 的自动定理生成 + LLM 辅助证明的组合在中等规模设计中是可靠的。
3. 总可复用 lemma 比例为 80.2%，五个设计超过 77%。`fir_filter` 复用率最低（63.6%），可能因为其数据通路特性产生了更多设计特异性 lemma（如 FIR 系数乘法性质）。

**时间开销**（论文 Table IV）：

| Design | N_total | T_Lean (s) |
|--------|:---:|:---:|
| `debounce_edge` | 79 | 1.113 |
| `fir_filter` | 29 | 0.558 |
| `pwm_generator` | 81 | 0.918 |
| `lfsr_crc` | 42 | 0.721 |
| `sync_fifo` | 94 | 0.936 |
| `ps2_keyboard` | 78 | 1.327 |
| **Total** | **403** | **5.573** |

**这张表说明什么**：

- 端到端时间（RTL 翻译 + 定理生成 + 证明构造 + 结果收集）仅 0.650 秒——因为确定性规则引擎不需要 LLM 调用或证明搜索。
- Lean 检查总时间 5.573 秒，每个设计不到 1.4 秒。这意味着 Rtl2lean 生成的证明高度结构化，kernel 不需要大量化简步骤。
- `T_Lean` 与 `N_total` 不是严格正比——`ps2_keyboard`（78 个定理）的检查时间比 `sync_fifo`（94 个定理）更长，说明检查成本还受状态转移逻辑与位向量表达式复杂度的影响。

## 7. 创新点

### 创新点 1：首个自动化 RTL-to-Lean 4 语义编译器

在 Rtl2lean 之前，将已有 RTL 设计嵌入 ITP（Interactive Theorem Prover，交互式定理证明器）需要大量人工建模——手工定义状态类型、翻译组合/时序逻辑、构造证明。Kami[6] 和 Silver Oak[7] 要求用户在证明助手内手工编写硬件描述（而非从已有 RTL 翻译），CktFormalizer[11] 从自然语言规约生成硬件描述（处理方向不同，不是从 RTL 出发）。Rtl2lean 是首个把已有 SystemVerilog RTL **自动**翻译为 Lean 4 的工作。

与已有工作的本质区别：Kami/Silver Oak 的流程是"人写形式化硬件描述 -> Coq/Lean 中做证明"，人必须同时理解硬件设计和证明助手；Rtl2lean 的流程是"已有 Verilog -> 自动编译 -> Lean 4 模型 -> 自动生成定理 + LLM 辅助证明"，人只需提供高层验证属性。翻译过程的自动化使得"对已有 RTL 代码库做 ITP 级形式化验证"成为可能。

### 创新点 2：四层分层定理框架 + 自底向上可复用证明库

不是给每个高层属性单独写证明模板，而是把 RTL 的语义按粒度分为四层。L1（组合语义原子）、L2（时序语义原子）、L3（单周期行为接口）、L4（多周期归纳基础）。低层 lemma 标记 `@[simp]` 后自动参与所有高层证明——这使 358 个基础 lemma 中 287 个可跨证明复用。

**为什么分层**：直接对高层属性做证明，每次都要从 `step` 的完整定义开始展开——证明脚本极长且充满重复。分层的本质是"按粒度缓存硬件语义"。越下层越细粒度但越通用，越上层越具体但复用范围越窄。类似编译器的中间表示分层——你在 IR 层做优化，不用每次从源码开始。

### 创新点 3：LLM + Lean kernel 的"防火墙"式证明辅助

LLM 的角色被严格限定为生成候选中间 lemma 的命题陈述，而非直接输出完整证明。每个候选必须经 Lean kernel 类型检查通过才能使用。这形成了一道可靠性防火墙——kernel 不会接受类型错误的命题，即使 LLM 产生幻觉也不影响证明库的可靠性。

与直接让 LLM 写 tactic 脚本（如 LeanDojo[10] 的 premise selection + tactic generation）相比：Rtl2lean 把最终正确性责任从 LLM 移交给了 kernel。LLM 只需提出"可能成立的命题"——这比"正确构造证明项"对 LLM 的要求低得多。命题要么型正确（kernel 接受），要么型错误（kernel 拒绝并给出精确类型错误信息），没有模糊地带。

### 创新点 4：机器检查的跨证明 lemma 复用

被 kernel 接受的 lemma 自动进入可复用池 `L_pool`。后续证明通过 `rw`、`apply`、`simp` 等 tactic 直接引用已验证的结果，无需重复展开底层 RTL 语义。证明工作量随设计规模呈亚线性增长——已证明的属性越多，证明新属性越容易。

实验数据支撑：`pwm_generator` 达到 83.8% 复用率（74 个基础 lemma 中 62 个可复用），这验证了正向累积效应。`fir_filter` 复用率仅 63.6% 则暗示数据通路密集型设计可能需要更多设计特异性 lemma 而无法充分享受分层框架的复用红利。

## 9. 与芯片流程的关系

### 9.1 在全流程中的位置

Rtl2lean 作用于阶段 **6 形式验证**，但走的是与 Formality/Conformal（基于 SAT/SMT 自动求解）完全不同的技术路线——**交互式定理证明（ITP）**。

```text
芯片流程                         Rtl2lean 角色
============================================================
1 RTL 设计          <-- 消费此阶段的 SystemVerilog RTL 产物
2 RTL 功能仿真      <-- 无关（不跑 testbench，不产生波形）
3 逻辑综合          <-- 无关（Rtl2lean 在综合前验证 RTL 自身属性）
4~5 门级仿真/STA    <-- 无关
6 形式验证          <-- * 完整作用域：基于 ITP 的数学证明
7~17 物理设计->流片  <-- 无关
```

**Rtl2lean 解决的实际痛点**：

传统 RTL 验证的两大支柱各有硬伤：
- **仿真（阶段 2）**：无论覆盖率多高，始终是穷举有限测试向量。工业级覆盖率目标 95%+ 仍无法保证不存在未覆盖输入组合下的 bug。
- **自动形式验证（阶段 ⑥ 传统路线）**：SAT/SMT 求解器自动推理，但受状态爆炸限制（寄存器数增加 -> 搜索空间指数增长），BMC 只保证 k 步内无 bug，复杂数据通路的 SMT 编码可能不可解。

Rtl2lean 的 ITP 路线可以突破这些限制：
- **任意步数属性**：通过 L4 可达性定义 + 归纳法，可以证明"对所有执行步数都成立"的属性
- **参数化设计**：依赖类型天然支持泛型和参数化模块
- **更强可靠性**：正确性只依赖约几百行的 Lean kernel 代码，而非启发式求解器

**代价**：
- 需要人工给出高层属性规约（框架不会自动推断"该证什么"）
- LLM 生成的 lemma 不一定总能"命中"（类型可能错误）
- 目前实验仅在 6 个中等规模的 OpenCores 设计上验证

### 9.2 交互式定理证明 vs. 传统 SAT/SMT 形式验证的本质区别

| 维度 | SAT/SMT 等价性检查（Formality/Conformal） | ITP 定理证明（Rtl2lean / Lean 4） |
|------|------|------|
| **核心问题** | "两个电路对所有输入是否等价？" | "系统是否在所有可达状态下满足属性 P？" |
| **问题性质** | 搜索问题（寻找反例） | 构造问题（构造证明项） |
| **证明方式** | 自动——编码为 SAT/SMT 公式，求解器判定 | 半自动——人/LLM 写 tactic 构造证明项 |
| **覆盖范围** | 组合等价（RTL vs 网表） | 任意时序属性（功能、安全性、不变量） |
| **有界性** | BMC 有界（k 步）；完全等价检查受状态爆炸限制 | 无界——归纳法覆盖任意步数 |
| **可靠性根基** | SAT/SMT 求解器正确性（假设正确，未经形式化验证） | Lean kernel 类型检查器（约几百行，经严格审查） |
| **自动化程度** | 全自动，无需人工指导 | 半自动——框架生成骨架，LLM 补充 lemma |
| **失败模式** | 超时/内存耗尽（无法判定） | proof incomplete（证明项含 `sorry` 占位符） |
| **适用范围** | 等价性检查——两个设计是否功能一致 | 属性验证——一个设计是否满足任意时序属性 |

**关键区别的直觉理解**：

SAT/SMT 路线是"自动对拍"——你把 RTL 和综合后的网表扔进去，工具自动构造数学公式证明两者对所有输入永远输出相同。快速、自动，但只能做"A 是否等于 B"这种等价性问题。

ITP 路线是"数学证明"——你把 RTL 翻译成数学定义，然后证明"这个 FIFO 永远不会溢出"、"这个状态机永远不会死锁"等任意时序属性。比"等价性"更灵活，但需要构造证明（人/LLM 参与）。

**Rtl2lean 的独特价值**：它把 ITP 路线从"必须由人手工建模和证明"变成了"自动编译 + 自动生成定理骨架 + LLM 辅助证明"。这是让 ITP 级形式验证走向实际 RTL 设计的关键一步。

### 9.3 「证明通过」和「能做成芯片」之间隔着什么

Rtl2lean 的 "100% proof success rate" 只保证 Lean 4 模型中的定理在类型论层面成立。以下问题不在保证范围内：

1. **翻译正确性未证**：Lean kernel 检查的是"生成模型中的定理是否成立"，但未自动证明 RTL 到 Lean 4 的翻译过程保留了 RTL 的原始语义。若编译器存在语义偏差（如非阻塞赋值翻译为错误顺序的字段更新），kernel 无法发现——kernel 只检查"类型对不对"，不管"翻译对不对"。
2. **不保证可综合性**：Rtl2lean 消费的 RTL 可能已被验证为具有某些数学属性，但没有综合工具判断这些 RTL 是否能被映射为实际门电路。
3. **不保证时序收敛**：数学上正确的设计在物理实现时可能因组合逻辑路径过长而无法满足目标频率。
4. **覆盖范围有限**：只验证高层用户属性（45 个），而非"所有可能的属性"。未验证覆盖率概念。

## 10. 讨论与局限

### 10.1 论文自述的局限

1. **实验规模有限**：6 个 OpenCores 设计，最大 `sync_fifo` 仅 94 个定理——远未到工业 SoC 规模（典型 SoC 有数百个模块、数十万行 RTL）。结论的可扩展性是未验证的开放问题。
2. **工具链未发布**：translator 与 theorem library 均未开源，无法独立复现实验结果。论文的贡献停留在方法论描述层面。
3. **翻译器正确性未证**：这是整个框架最根本的可靠性裂痕。kernel 证明的是"编译后的模型满足属性 P"，而非"原始 RTL 满足属性 P"。若编译器有语义偏差，模型层面的定理成立但原始 RTL 行为不对——kernel 对此完全无感知。
4. **高层属性依赖人工**：框架不会自动推断"该证什么"，用户必须提供规约。论文未列出 45 个高层属性的完整清单，无法评估覆盖充分性。
5. **LLM 调用细节缺失**：未报告 LLM 型号、调用次数、lemma 候选成功率（通过率/拒绝率）、单次延迟。这使得"LLM 的实际参与度"无法评估。
6. **SystemVerilog 覆盖率有限**：不支持工业设计中常见的高级特性。
7. **无综合/PPA/物理验证**：形式模型层面的数学正确性不等于芯片可实现。

### 10.2 代码/复现层面的问题

论文没有公开代码，不存在代码层面的差异分析。但这也意味着所有实验结论都是不可独立验证的——研究者必须在阅读理解论文基础上自己重写 translator 和 theorem library。

### 10.3 本资料包的批判性分析

**LLM 的实际参与度存疑**：`T_e2e` = 0.650 秒这个数字暗示在 6 个实验设计中，LLM 要么几乎没有被调用，要么调用延迟未被计入 `T_e2e`。考虑到 L1-L4 自动生成框架 + `@[simp]` 机制很可能覆盖了大部分证明需求，LLM 的真实参与度可能很低。LLM 的价值或许要到更复杂的设计（如参数化模块、复杂数据通路不变量）中才能体现，但论文并未在那类设计上实验。

**100% 证明成功率的上下文需要谨慎解读**：Rtl2lean 自己生成定理，自己证明。如果生成的定理都是"容易证的"——确定性、字段保持、复位行为等——100% 是预期行为而非惊喜。关键问题是那 45 个高层属性是否覆盖了设计的核心功能与边界条件。论文没有给出具体属性清单，无法评估充分性。

**`R_reuse` 的精确含义**：论文注明该指标衡量的是"可被自动复用的 lemma 比例"（即有 `@[simp]` 标记的比例），而非实际被后续证明调用的比例。一个 marked lemma 理论上可被自动使用，但如果后续证明不需要展开那个语义，它静默存在但不被触发。真正的复用率应低于 80.2%。

**翻译器正确性问题的方法论困境**：这是所有形式化编译工作的共同困境，但 Rtl2lean 没有提供任何缓解措施。传统形式验证中，你可以用 Formality 等价性检查来缓解综合正确性问题，但 Rtl2lean 的翻译过程没有一个"裁判"来验证翻译前后的语义一致性。一个可能的缓解方案是将生成的 Lean 4 模型与传统 SystemVerilog 仿真器做交叉验证（对大量随机输入比对 `step` 的输出与仿真器的下一状态），但论文没有做。

**与 LeanDojo/CktFormalizer 的关系**：Rtl2lean 直接受益于 LeanDojo[10] 提供的 Lean 交互基础设施和检索增强证明方法，以及 CktFormalizer[11] 的硬件描述到 Lean 4 的类型安全嵌入思路。Rtl2lean 的增量在于：首次处理了"已有 RTL 到 Lean 4 的自动化翻译"这个方向（而非从规格到硬件描述），并用四层定理框架 + LLM lemma 生成来提升自动化程度。

## 12. 一分钟复述版

Rtl2lean（中科院计算所，arXiv 2026）是一个**LLM 辅助的 RTL 形式化验证框架**——不训练模型，核心三招：

1. **RTL-to-Lean 4 自动编译**：用 PySlang 解析 SystemVerilog，经 IR 规范化后将组合逻辑、时序过程、位向量运算编译为 Lean 4 的 `State`/`Inputs`/`step(s,i)` 纯函数模型。把事件驱动语义折叠为一个无副作用的数学函数。

2. **四层定理框架**：L1 组合逻辑 lemma（每个字段的语义 + 保持属性，标记 `@[simp]`）-> L2 时序块 lemma（确定性、保持、复位行为）-> L3 单周期 theorem（复位/确定性/输出反射/FSM 转移）-> L4 可达性与不变量（多周期归纳基础）。四层自底向上缓存硬件语义，低层 lemma 自动参与所有高层证明。

3. **LLM + kernel 防火墙**：高层属性无法由定理库直接证明时，LLM 根据证明目标 + 上下文 + Lean 错误反馈生成候选中间 lemma。每个候选必须经 Lean kernel 类型检查通过才能使用——kernel 是最终裁判，LLM 幻觉无法污染证明库。通过后 lemma 加入复用池，后续证明通过 `rw`/`apply`/`simp` 直接引用。

结果：6 个设计上生成 403 个定理全部通过 kernel 检查，358 个基础 lemma 中 287 个（80.2%）可跨证明自动复用，端到端仅 0.650 秒，kernel 检查 5.573 秒。

**边界**：工具链未开源，翻译器正确性未证（kernel 不验证翻译过程），仅覆盖阶段 ⑥ 中的 ITP 子路线（1/17），高层属性依赖人工规约，实验规模限于 6 个中等设计，不支持多时钟域/异步复位/interface/参数化模块，不保证可综合性/时序收敛/PPA。
