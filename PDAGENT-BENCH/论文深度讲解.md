## 1. 一句话定位

**PDAGENT-BENCH 是首个面向 VLSI 物理设计（physical design）的 LLM/VLM Agent 综合评测基准。** 353 道题覆盖五个能力维度（基础认知、报告理解、根因分析、STA、脚本生成、全流程实现），配套 Planner-Worker-Analyzer-Debugger-Optimizer 五角色闭环 Agent 框架（PDAgent），支持真实 EDA 工具（Innovus/ICC2/PrimeTime/Formality）交互与 TSMC 28nm 工艺流片级评测。11 个前沿模型的全维度评测揭示：GPT-5.5 在基础认知上达 80.4%，但在 ICC2/Innovus 脚本生成上仅 45.5%/42.2% pass@1；92% 的脚本生成失败是 syntactic near-miss（命令正确但 flag/参数错误）。Skill Pack 机制使小模型（GPT-5-mini）也能驱动完整的 RTL-to-GDSII 闭环，而 8B Vision-Language backbone 在 macro placement 上将最强基线的 TNS 从 -244.94 压至 -4.01（~60x 提升）。

这句话里的 6 个技术承重点：

1. **五维能力评测体系** — 从基础概念问答（90 题）到全流程 GDSII 实现（10 个设计），覆盖 plan/reason/perceive/tool-use 四类 Agent 核心能力，每道题配专家验证的参考解答和细粒度 scoring rubric。

2. **五角色多 Agent 闭环框架** — Planner（任务分解 DAG + Hub-and-Spoke 通信）、Worker（持久化 EDA shell 执行）、Analyzer（从 verbose 日志提取结构化指标）、Debugger（check-fix-check 多轮诊断）、Optimizer（stage-level 推进 + parameter-level tree-of-thought 搜索），天然对齐物理设计工程师团队的协作结构。

3. **Expert Skill Packs（专家技能库 grounding）** — 将资深工程师的隐性过程知识（参考 Tcl 脚本、参数调优策略、debug 决策矩阵、跨阶段影响分析）编码为可复用 Skill Pack，通过 fuzzy matching 动态加载。实验证明：纯 LLM baseline 和 RAG baseline 在 init/floorplan 阶段即失败，而 skill-enhanced PDAgent 可以完成 10 个设计的全流程。

4. **VLM macro placement 突破** — 用仅 8B 参数的视觉-语言 backbone，以 layout 图像为输入直接指导 macro 放置，在 5 个 ChiPBench 设计上匹配或超越 7 个专用方法（WireMask-EA、SA、MaskPlace、ChiPFormer、DREAMPlace、AutoDMP、OpenROAD），ariane133 上 TNS 提升 ~60x。

5. **系统化失败模式分析** — 92% 脚本生成失败为 syntactic near-miss：模型学到了 EDA 工具的**过程结构**（该用什么命令），但缺乏**工具精确语法**（具体 flag 名、参数格式、值约束）。这推翻了「LLM 不懂物理设计」的直觉，精准定位真正瓶颈。

6. **隐私保护部署方案** — 通过本地 Python coordinator 中介三方交互，模型绝不接触原始工具输出 dump、foundry 库文件或工艺 LEF/LIB，回应了 CSDW 提出的多方协作隐私互操作性挑战。

## 2. EDA 阶段映射（①-⑰）

PDAGENT-BENCH 聚焦物理设计后端（⑦~⑩），以综合后门级网表（阶段 ③ 输出）为起点，以签核通过（阶段 ⑬）为目标。下表中「核心」表示 benchmark 有专属任务集直接评测的阶段，「辅助」表示通过报告理解/根因分析/STA 推理间接覆盖的阶段。

| 阶段 | 覆盖 | 涉及的任务子集 | 说明 |
|------|:---:|------|------|
| ① RTL 设计 | ❌ | — | 物理设计 benchmark 从 netlist 开始，不涉及 RTL 编写 |
| ② RTL 功能仿真 | ❌ | — | 同上 |
| **③ 逻辑综合** | 辅助 | 全流程实现的起点 | full-flow 任务以综合后 netlist + SDC 为输入；benchmark 不评测综合本身，但根因分析任务中「综合后时序恶化」是一个诊断维度 |
| ④ 门级仿真 | ❌ | — | 不涉及 |
| ⑤ STA（静态时序分析） | ✅ 核心 | STA 推理 11 题 + 报告理解（PrimeTime 报告解读）| 路径级 setup/hold 违例推理、slack 计算、clock skew 传播、时序异常（false path、multi-cycle path）判断 |
| ⑥ 形式验证（FM） | ✅ 核心 | FM 脚本生成 22 题 | Synopsys Formality Tcl 脚本生成：RTL-vs-netlist 等价性检查的完整脚本编写 |
| **⑦ 布局规划（Floorplan）** | ✅ 核心 | 基础认知（floorplanning 12 题）+ 脚本生成（Innovus 14 题 / ICC2 8 题）+ full-flow 实现 + **macro placement 专项评测** | macro placement 由 VLM 以 layout 图像为视觉输入直接完成；涉及 die/core area 定义、IO pin 放置、power grid topology 规划；benchmark 在 5 个 ChiPBench 设计上对 7 个基线做专项对比 |
| **⑧ 标准单元摆放（Placement）** | ✅ 核心 | 基础认知（placement 10 题）+ 脚本生成（Innovus 12 题 / ICC2 18 题）+ full-flow 实现 | 全局与详细 placement；优化 HPWL（Half-Perimeter Wirelength，半周长线长）、density、congestion、timing；full-flow 中逐阶段追踪 WNS 与 density |
| **⑨ 时钟树综合（CTS）** | ✅ 核心 | 基础认知（CTS 8 题）+ 脚本生成（Innovus 17 题 / ICC2 17 题）+ full-flow 实现 | CTS/CTSopt 全流程；控制 clock skew、insertion delay；full-flow 中追踪 CTS 阶段 WNS/density 变化 |
| **⑩ 布线（Routing）** | ✅ 核心 | 基础认知（routing 7 题）+ 脚本生成（Innovus 19 题 / ICC2 21 题）+ full-flow 实现 | 全局+详细布线；DRC 违规诊断属于报告理解与根因分析范畴；full-flow 中以 DRC=0 为收敛目标 |
| ⑪ 后仿真 | ❌ | — | 不涉及 |
| **⑫ 物理验证（DRC + LVS）** | 部分 | DRC 违规检测（报告理解 + 根因分析 + full-flow）+ DRC 修复 (Debugger Agent) | DRC 覆盖完整（检测+诊断+修复）；**LVS（Layout Versus Schematic）明确未覆盖**——论文自述为 signoff 完整性的重要缺口 |
| **⑬ 签核（Signoff）** | ✅ 核心 | ECO 脚本生成 10 题 + STA 推理 11 题 + FM 脚本 22 题 + full-flow 最终 DRC 清零验证 | ECO（Engineering Change Order，工程变更命令）脚本服务于 post-route 局部修复；paper 明确指出 LVS 验证当前排除在外 |
| ⑭-⑰ | ❌ | — | 不涉及流片/制造/封装/测试 |

**覆盖率：7/17（⑤、⑥、⑦、⑧、⑨、⑩、⑬）。LVS 缺失使签核完整性不完整，DRC fixing 中部分 GUI 依赖场景无法自动化。**

**与 FluxBench 和 CLOSER-Bench 的覆盖对比：**

| 维度 | FluxBench | CLOSER-Bench | PDAGENT-BENCH |
|------|-----------|-------------|---------------|
| 流程覆盖 | ③~⑫（RTL-to-GDS 全流程）| ③~⑬（design closure，延伸至 signoff）| ⑦~⑩ + ⑤⑥⑫⑬（物理设计 + STA + FM + ECO）|
| 核心评测对象 | 传统算法 flow 的参数调优 | LLM Agent 的跨阶段决策策略 | LLM/VLM Agent 在物理设计子任务上的五维能力 |
| 评测粒度 | Coarse（flow-level）| Medium（trajectory-level，有 anytime progress）| Fine-grained（per-subtask capacity）|
| 预算约束 | 无 | 有（仿真/综合/PnR/wall-clock 三级预算）| 有（micro/meso/macro 三级重试预算）|
| 任务数 | 若干 flow 配置 | 10 pilot 任务 | 353 任务（含 10 个 full-flow 设计）|
| 数据集开放性 | 工具链开源 | 未发布 | HuggingFace 已发布（MIT）|
| 签核覆盖 | DRC | DRC+LVS+STA（多角）| DRC（LVS 未覆盖）|

PDAGENT-BENCH 与 FluxBench 的差异：FluxBench 评测「给定一个 RTL，自动化 flow 能不能生成 GDS」，侧重流程集成和兼容性。PDAGENT-BENCH 评测「LLM/VLM agent 在物理设计各子任务上分别强在哪弱在哪」，侧重 agent 能力的细粒度诊断。FluxBench 回答「这个 flow 能跑通吗」，PDAGENT-BENCH 回答「这个 LLM 能做 placement 脚本生成吗？能读懂 timing report 吗？能独立跑通一个从 netlist 到 GDS 的全流程吗？」。

PDAGENT-BENCH 与 CLOSER-Bench 的差异：CLOSER-Bench 覆盖更大范围（③~⑬），但评测维度聚焦在「跨阶段回退决策」——Agent 在综合后 WNS 为负时退回去改 RTL 还是调约束？PDAGENT-BENCH 覆盖范围较窄（⑦~⑩），但评测粒度显著更细——Agent 对 floorplan 知识掌握多少（90 题，难度 E/M/H 分层）、placement Tcl 脚本写得对不对（与标准答案逐 flag 比对）、VLM 能不能从 layout 图像做 macro placement（专项对比 7 个 baseline）。两者互补：CLOSER-Bench 解决「跨阶段协调」问题，PDAGENT-BENCH 解决「单阶段能力」问题。

> 最容易误读的边界：PDAGENT-BENCH 的 353 题不是「越多越好」的数据集——它的核心价值在于五维度的**诊断性设计**：每个维度评测 Agent 的不同能力（知识/感知/推理/工具使用），失败模式被精确分解为 syntactic near-miss vs conceptual error vs multi-step reasoning failure。这种诊断粒度是推动物理设计 AI agent 发展的关键基础设施。

## 3. 输入 / 输出

### 3.1 输入

PDAGENT-BENCH 的输入按三类任务分层设计，所有数据项统一编码为 JSON schema。

**（1）理解类任务输入（Physical Design Understanding, 133 题）**

自然语言问题 + 多模态辅助材料 + 专家验证的 reference answer + 细粒度 scoring rubric。

**基础认知（Foundational Knowledge, 90 题）** — 评测 physical-design 和 EDA 基础概念。难度分布：Easy 31%（28 题）、Medium 39%（35 题）、Hard 30%（27 题）。覆盖 10 个主题：

```
Physical Design 原理: 14 题    STA: 16 题
Floorplanning: 12 题           Placement: 10 题
CTS: 8 题                      Routing: 7 题
Power: 6 题                    Device/Tech: 6 题
Signal Integrity: 6 题         DFT: 5 题
```

典型题目与 rubric 示例：

```
Question: "In VLSI backend physical design flow, describe the essential
input files required by a physical design tool and the key output files
it generates. For each file, briefly explain its purpose and common
format extensions."

Reference Answer (摘要):
Input:
  1. Technology file (.tf / .techlef): process rules, parasitics
  2. Physical libraries (.lef / .gds / .CEL / .FRAM): layout abstraction
  3. Timing/power libraries (.lib / .db): timing/power characterization
  4. TDF file (.tdf / .io): pad/pin arrangement
  5. Constraints (.sdc): area, power, timing constraints
  6. DEF/PDEF (optional): pre-existing placement data

Output:
  1. Standard Delay Format (.sdf): post-layout timing
  2. Parasitics (.spef / .dspf): extracted R/C
  3. Post-routed netlist (.v)
  4. Physical layout (.gds)
  5. Design Exchange Format (.def)

Scoring Rubric (10 points):
  Input-Tech & Lib (3pt): .tf/.techlef + .lef/.gds + .lib/.db
  Input-Constraints & Optional (2pt): SDC + IO/TDF/DEF/PDEF
  Output-Timing & Parasitics (2pt): SDF + SPEF/DSPF
  Output-Netlist/Layout/DEF (2pt): .v netlist + GDS + DEF
  Clarity & Completeness (1pt): well-organized, no major omissions
```

**报告理解（Report Comprehension, 11 题）** — 多模态任务（文本 + EDA 工具截图/报告）。来源涵盖 PrimeTime STA 报告、Innovus routing/placement 报告、工具错误日志。难度：Easy 27%、Medium 45%、Hard 27%。

**根因分析（Root Cause Analysis, 21 题）** — 诊断 PPA/收敛问题的根因。覆盖 placement/routing/CTS/tape-out-ECO/floorplanning/power-IR/synthesis/STA 八个子领域。难度：Easy 38%、Medium 43%、Hard 19%。

**STA 推理（11 题）** — 路径级 setup/hold 违例推理、slack 计算、clock skew 传播、时序异常判断。

**（2）脚本生成类任务输入（Script Generation, 210 题）**

自然语言指令 + 指定目标 EDA 工具，每题配多组可接受答案（覆盖工具版本差异）：

```
"Generate the Innovus Tcl command to perform global placement with
timing-driven optimization and high congestion effort."

参考答案: place_opt_design -timing_driven -congestion_effort high
可接受替代: setPlaceMode -cong_effort high; place_opt_design -timing
```

另有 ECO 10 题 + FM（Synopsys Formality 形式验证）22 题。共 210 题。所有脚本解答均经过实际执行验证，确认功能正确性与工具兼容性（验证覆盖 Innovus/ICC2 2018~2022 版本）。

### 3.2 输出

**（1）理解/脚本类任务输出**

pass@1 / pass@5 的通过率统计 + LLM-as-Judge 0~10 分 rubric 评分 + 可执行性判定。

- **pass@1**：temperature=0 确定性解码，单次生成，按 rubric 判定通过/失败
- **pass@5**：temperature=0.8, top-p=0.95 随机采样 5 次，取最优 rubric 分
- **LLM-as-Judge**：Claude Sonnet 4.6 作为评判 model，按预定义 rubric 逐项打分（0~10）
- **人类评估校准**：3 名资深物理设计工程师独立打分，与 LLM-Judge 偏差 2~6 分
- **脚本类额外判定**：命令级精确匹配——命令名、flag 名、参数值、参数格式四项必须在可接受答案集中

**（2）全流程任务输出**

逐阶段设计指标矩阵 + Token 消耗统计 + LLM 调用次数。以 TinyRISCV（GPT-5-mini backbone）为例：

```
Floorplan    —           0          0.650 (Util)
Powerplan    —           0          —

CTS          -0.127ns    0          0.717
CTSopt       +0.001ns    0          0.713
```

## 4. Benchmark 构建方法

PDAGENT-BENCH 的构建围绕两个核心问题：**评测什么**（数据集设计——覆盖物理设计 Agent 所需的全部能力维度）和**怎么评测**（Agent 框架设计——让 LLM/VLM 在真实 EDA 工具闭环中执行物理设计）。

### 4.1 数据集构建五项原则

| 原则 | 含义 | PDAGENT-BENCH 的具体体现 |
|------|------|-------------------------|
| **C1 Coverage & diversity** | 覆盖物理设计全流程多阶段 | 从基础概念（90 题）到全流程 GDSII 实现（10 个设计），涵盖 floorplan→ECO |
| **C2 Ground-truth fidelity** | 每题配有可验证参考答案 | 三位领域专家独立审核；所有 210 道脚本题解答经实际 EDA 工具执行验证 |
| **C3 Multi-modality** | 文本 + 脚本 + 图像 | floorplan 图、DRC heatmap、时序报告截图统一编码为 JSON schema |
| **C4 Leakage resistance** | 防数据泄露/记忆 | 题目源自 ISSCC/VLSI/A-SSCC/CICC 等顶会发表的生产项目，非公开题库 |
| **C5 Realistic difficulty** | 真实工业难度 | 远超简单 QA——需解读真实 EDA 报告、诊断根因、生成可执行 Tcl |

### 4.2 三维度任务体系

**Physical Design Understanding（133 题）** — 评测 reasoning + planning + perception

核心能力维度：Foundation Knowledge 评测纯概念理解（GPT-5.5 达 80.4%），Report Comprehension 评测多模态感知+信息提取（Claude Opus 4.7 达 90.9%），Root Cause Analysis 评测多步诊断推理（GPT-5.5 达 73.3%），STA 评测路径级时序推理（Claude Opus 4.7 / GPT-5.5 达 72.7%）。

**Script Generation（210 题）** — 评测 **tool use**

这是所有模型差距最大的维度。Innovus 90 题 + ICC2 88 题按 9 个物理设计阶段均匀分布（init→floorplan→powerplan→placement→CTS→CTSopt→route→routeopt→chip finishing），确保覆盖真实流程中的每个关键操作点。ECO 10 题 + FM 22 题覆盖 post-route 修复和 formal equivalence checking。

**Full-Flow Implementation（10 个设计）** — 评测全部四类能力的综合

设计选择标准：跨多个复杂度数量级（176~1.48M cells）、覆盖控制逻辑（Elevator FSM、UART）和数据通路密集型（Systolic array、NVDLA）、包含真实工业 IP（Open910 应用级处理器、NVDLA 深度学习加速器）。

### 4.3 PDAgent 五角色多 Agent 框架

PDAgent 是配套的评测执行框架，其设计直接映射物理设计工程师团队的协作结构：

| Agent | 角色 | 关键机制 |
|-------|------|---------|
| **Planner** | 中央协调器：将用户意图分解为 subtask DAG（有向无环图），路由所有 Agent 间消息，维护全局 DesignContext（macro 位置、die/core area、时钟拓扑） | Hub-and-Spoke 通信拓扑（Agent 间消息全经 Planner，工具交互绕开 hub 以降低延迟）；DesignContext 通过查询 EDA 工具初始化后共享给所有 Agent |
| **Worker** | 与 EDA 工具的**唯一交互入口**：通过持久化交互式 Tcl shell（如 `innovus -shell`）执行 EDA 命令；floorplan 阶段 macro placement 由 **VLM 以 layout 图像为视觉输入**直接完成 | 三种执行模式：skill-guided generation（LLM 从 skill 内容合成脚本）、script execution（直接 source 参考脚本）、optimization application（应用 Optimizer 的调优指令） |
| **Analyzer** | 从冗长的 EDA 工具日志中提取结构化指标，**仅在分析密集型阶段激活**（placement/CTS/routing） | 输出 StageMetrics 向量：WNS/TNS/DRC violations/utilization/density/congestion/power |
| **Debugger** | 检测 DRC 违规和其他错误，执行多轮 **check->fix->check** 诊断循环 | 加载 stage-specific debug skill；三级预算：micro（语法错误 2 次）、meso（参数调整 4 次）、macro（跨阶段回滚 2 次）；预算耗尽后升级至 Optimizer |
| **Optimizer** | 两层优化：stage-level 推进物理设计流程；parameter-level 在当前阶段内探索参数空间 | 普通模式：多轮指标检查→参数调整→验证；树搜索模式：生成 K 个候选配置，并行/顺序评估，按 stage-aware 加权得分选优；MetricsDB 记录完整参数-指标映射轨迹 |

### 4.4 Skill Packs（专家技能库）

这是 PDAgent 区别于纯 LLM Agent 和 RAG 方法的核心机制。Skill 是由资深物理设计工程师编码的**过程性知识**，组织为 `skills_{tech}_{tool}/` 目录（如 `skills_tsmc28nm_innovus/`）。每个 skill pack 包含四层知识：

1. **参考 Tcl 脚本**：可直接 source 的完整阶段脚本
2. **参数调优策略**：如「WNS < -50ps → priority raise placement effort → `setPlaceMode -cong_effort high -timing_effort high`」
3. **Debug 决策矩阵**：如「macro overlap → 先 read core area via `dbGet top.fPlan.coreBox` → 重新放置越界 macro」
4. **跨阶段影响分析**：如「高 utilization floorplan → placement congestion 风险增大 → 预留更多 routing resource」

Skill 通过 **fuzzy matching** 在初始化时自动发现和加载，支持无缝扩展到新技术节点和 EDA 工具。

**Skill 关键性证明（消融实验）**：

- **无 skill 纯 LLM baseline**：在 init/floorplan 阶段即失败（setup 失败、pin placement 失败、power ring 缺失）
- **RAG-enhanced baseline**（从 EDA 命令参考手册和物理设计指南中检索）：同样无法通过前三个 stage——pin placement 失败、power ring/stripes 缺失或不连接——通用文档检索过于粗粒度，无法提供 EDA 工具所需的精确语法和过程知识
- **PDAgent（含 skill）**：使用 GPT-5-mini 作为 backbone，完成 10 个设计的全流程闭环

## 5. 关键公式

### 5.1 pass@k 无偏估计

PDAGENT-BENCH 采用与 RTLLM、VerilogEval 一致的 pass@k 评测范式，用于物理设计理解与脚本生成任务的自动评分：

$$
\text{pass@k} = \mathbb{E}_{\text{Problems}}\left[1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}\right]
$$

- $\text{pass@k}$：从每道题的 $n$ 次生成中任取 $k$ 次，至少有一次通过的无偏概率估计
- $n$：每道题的总生成次数（论文中 $n = 5$）
- $c$：$n$ 次生成中通过 rubric 判定的次数（$c \leq n$）
- $k$：选取的尝试次数（$k = 1$ 或 $k = 5$）
- $\binom{n-c}{k}$：从 $n-c$ 次失败中选 $k$ 次的组合数
- $\binom{n}{k}$：从 $n$ 次中任选 $k$ 次的组合数

**工程直觉**：这个公式估计的不是「pass 率 = c/n」——那样会低估模型能力（因为如果模型在某题上 5 次生成中只有 1 次通过，c/n = 20%，但 pass@1 = 20%、pass@5 = 100%）。无偏估计给出的是「如果你允许模型试 k 次，至少有一次成功的概率」，更真实地反映模型在给定计算预算下的实用价值。

**论文实现细节**：pass@1 使用 temperature=0 确定性解码（greedy decoding，单次生成）。pass@5 使用 temperature=0.8、top-p=0.95 随机采样 5 次，取最优 rubric 得分。对不支持 temperature 参数的商业 API，使用默认配置采样 5 次。

### 5.2 Stage-Aware 加权得分

用于 Optimizer Agent 在 tree-of-thought 搜索中对候选参数配置进行排序：

$$
\text{score}(c) = \sum_{m \in \mathcal{M}_s} w_m^{(s)} \cdot \hat{v}_m(c)
$$

- $\text{score}(c)$：候选参数配置 $c$ 的综合质量评分
- $\mathcal{M}_s$：阶段 $s$ 的指标集（如 placement 阶段含 WNS、density、congestion；routing 阶段含 DRC count、wirelength、via count）
- $w_m^{(s)}$：阶段特异性权重，由 skill 编码的领域经验决定（如 routing 阶段 DRC weight 最高，placement 阶段 WNS + congestion weight 最高）
- $\hat{v}_m(c)$：候选配置 $c$ 下指标 $m$ 的归一化值（$\in [0,1]$）

最优候选 $c^* = \arg\max_c \text{score}(c)$ 成为下一轮搜索的起点。搜索终止条件：阶段指标满足（如 routing DRC = 0）、得分提升低于阈值 $\delta$、或 batch budget $B$ 耗尽。

**工程直觉**：这是多目标优化的加权融合——不同阶段关心的指标不同，weights 反映了实际工程优先级。例如 routing 阶段 DRC=0 是硬约束（weight 远高于 wirelength），placement 阶段 WNS 和 congestion 是主要矛盾（weight 高于 density）。

### 5.3 收敛判定条件

全流程闭环终止标准：

$$
\text{WNS}_{\text{final}} > 0 \;\land\; \text{DRC}_{\text{final}} = 0 \;\lor\; \text{budget exhausted}
$$

- $\text{WNS}_{\text{final}} > 0$：所有时序路径 slack 为正（时序闭合）
- $\text{DRC}_{\text{final}} = 0$：零设计规则违例（物理制造可行）
- $\text{budget exhausted}$：三级预算（micro 2 次 / meso 4 次 / macro 2 次）耗尽

## 6. 评测协议与打分

### 6.1 三层次评测协议

PDAGENT-BENCH 的评测粒度分三层，形成从微观到宏观的完整评测体系：

**层次一：独立任务层（per-subtask evaluation）**

- 理解类任务（133 题）：LLM-as-Judge（Claude Sonnet 4.6）按预定义 rubric（0~10 分）逐项打分
- 脚本类任务（210 题）：命令级精确匹配——命令名、flag 名、参数值、参数格式四项必须在多组可接受答案集中。GPT-5.5 在 Innovus 上 52 次失败的细分类：

| 失败类别 | 数量 | 占比 | 说明 |
|---------|:---:|:---:|------|
| Multi-line near-miss | 33 | 63.5% | 正确意图和命令序列，但 flag 名错误或缺少步骤 |
| Same command, wrong attribute | 12 | 23.1% | 单行命令正确，flag 写错（如 `-follow core` vs `-around core -center 1`）|
| Same command, value formatting | 3 | 5.8% | 命令和 flag 正确，参数格式/值偏差 |
| Wrong command | 4 | 7.7% | 完全选错命令（含 1 例自由文本回答）|

86.6% 的失败是「命令选对但参数不全对」——模型学到了 EDA 流程的**过程结构**，但缺乏**工具精确语法 grounding**。

**层次二：阶段任务层（per-stage evaluation）**

全流程实现中每个物理设计阶段（floorplan/placement/CTS/routing）有独立的指标追踪和收敛判定。Analyzer Agent 在 placement/CTS/routing 阶段激活，提取 StageMetrics 向量供 Debugger 和 Optimizer 做闭环 refine。

**层次三：全流程串联层（end-to-end full-flow evaluation）**

10 个设计从 netlist 到 GDSII 的完整闭环，评测 Agent 的跨阶段协调和长程规划能力。以 WNS > 0 且 DRC = 0 为最终收敛标准，同时记录 token 消耗和 LLM 调用次数。

### 6.2 打分指标汇总

| 指标类型 | 具体指标 | 适用任务 | 评测方式 |
|---------|---------|---------|---------|
| 正确性 | pass@1 / pass@5 | 理解类 (133) + 脚本类 (210) | rubric 判定 + 多候选匹配 |
| 质量 | LLM-Judge 0~10 分 | 理解类 (133) | Claude Sonnet 4.6 自动评分 |
| 质量 | 人类工程师 0~10 分 | 理解类子集 (校准用) | 3 名资深工程师独立打分 |
| 时序 | WNS / TNS | full-flow (10) + macro placement | STA 签核工具（PrimeTime）|
| 物理验证 | DRC violations | full-flow (10) | EDA 工具 DRC 检查 |
| 布局密度 | Density / Utilization | full-flow (10) | 逐阶段追踪 |
| 功耗 | Power | full-flow + macro placement | EDA 工具功耗分析 |

系统 prompt：「Please act as an impartial physical-design engineer and judge the quality of the response...」Claude Sonnet 4.6 按 pre-defined rubric 打分 0~10。3 名人类工程师独立打分与 LLM-Judge 偏差为 2~6 分，验证了 LLM-as-Judge 在物理设计任务上作为可靠代理评分方案的可行性。

### 7.5 四项核心发现（Finding 1-4）

**Finding 1: 失败以语法为主（~92% syntactic near-miss）。** 模型掌握了 EDA 流程的过程结构（该调用什么命令），但缺乏对工具特定语法（准确 flag 名、参数格式、值约束）的精确掌握。改进方向：不是训练更强的通用 LLM，而是做 explicit syntax grounding 或 retrieval over tool documentation。

**Finding 2: 基础认知表现强劲（80%+）。** 前沿模型可以可靠回答概念级和入门级物理设计问题，作为知识理解的良好 baseline。这表明「LLM 不懂物理设计」的直觉错误——它们懂概念，但不会操作工具。

**Finding 3: 感知强于决策（perception >> decision-making）。** 报告理解接近完美（~90%+），但当需要基于理解做出的诊断和优化动作时（根因分析），表现显著下降（~70%）。这一 gap 说明「看懂了」和「知道怎么做」之间存在鸿沟——需要机制把感知转化为可执行的设计决策。

**Finding 4: Skill augmentation 使端到端执行从不可能变为可能。** 纯 LLM 和 RAG baseline 在早期阶段即失败，而 skill-enhanced PDAgent 可以驱动完整的物理设计闭环。这一发现直接指明了物理设计 Agent 的关键路径：不是更强的通用推理能力，而是**领域过程知识的有效 grounding**。

## 8. 创新点

**创新点 1：首个物理设计 Agent 综合评测基准。** 在 PDAGENT-BENCH 之前，物理设计评测碎片化在孤立子问题上：ChiPBench（20 设计，macro placement 算法）、ChatEDA-Bench/iScript-Bench（50 题，仅脚本生成）、CircuitNet 3.0（8659 题，仅预测）。PDAGENT-BENCH 首次将五维能力（知识/感知/推理/工具使用/全流程）统一在一个评测框架内，支持多模态输入和闭环 EDA 工具交互。与 FluxBench（RTL-to-GDS 全流程，侧重传统算法 flow 参数调优）和 CLOSER-Bench（跨阶段 closure，侧重跨抽象层回退决策）不同，PDAGENT-BENCH 的核心定位是**物理设计 Agent 能力的细粒度诊断**——回答的不只是「这个 flow 能跑通吗」，而是「agent 在哪类子任务上强、哪类弱、为什么弱」。

**创新点 2：五角色多 Agent 闭环框架**。Planner-Worker-Analyzer-Debugger-Optimizer 的分工直接映射物理设计工程师团队的组织结构，使 Agent 工作流自然与人类设计流程对齐。Hub-and-Spoke 通信拓扑提供了全局状态可观测性，execute_tool 同步接口绕开 hub 以降低工具查询延迟。这不是 ReAct 范式——PDAgent 是预定义的多角色协作工作流，每个 Agent 有明确职责边界，但 Debugger 和 Optimizer 内部执行迭代闭环。

**创新点 3：Skill Packs 证明过程知识 grounding 是 Agent 实用化的关键。** 将资深工程师的隐性过程知识（参考脚本、参数调优策略、debug 决策矩阵、跨阶段影响分析）显式化为可复用模块。纯 LLM 和 RAG baseline 的全流程失败 vs PDAgent（含 skill）的成功证明了：物理设计 Agent 的核心瓶颈不是通用推理能力，而是领域过程知识的编码和检索机制。

**创新点 4：VLM 在 macro placement 上超越专用算法。** 用仅 8B 参数的 VLM backbone，以 layout 图像为视觉输入直接指导 macro placement，在 5 个设计上匹配或超越 7 个专用方法（analytical + RL + SA），ariane133 上 TNS 从 -244.94 压至 -4.01（~60x）。这证明视觉理解可以捕获纯数值优化无法编码的空间布局直觉。

**创新点 5：系统化失败模式分析。** GPT-5.5 在 Innovus 脚本生成上的 52 次错误被精确分类为四个类别，86.6% 是「命令正确但参数不全对」——推翻了「LLM 不懂物理设计」的直觉，精确定位真正瓶颈为工具语法 grounding 缺失。

**创新点 6：隐私保护部署方案。** 通过本地 Python coordinator 中介 LLM/VLM-EDA 工具-商业 PDK 三方交互，确保模型绝不接触原始工具输出 dump、foundry 库或工艺文件。回应了 CSDW（Cognitive Silicon Design Workshop）提出的多方协作隐私互操作性问题。

## 10. 讨论与局限

### 10.1 论文自述局限

1. **LVS（Layout Versus Schematic）验证未覆盖。** 物理验证包括 DRC 和 LVS 两个维度，当前 benchmark 仅覆盖 DRC。LVS 是 signoff 的必要步骤——验证实际版图布线是否与原始网表逻辑一致——其缺失是签核完整性的重要缺口。

2. **部分 DRC 修复依赖 GUI 交互。** 某些复杂 DRC 违例（多层金属间距冲突、天线效应修复）需要人工通过 GUI 目视检查和交互式操作，难以在纯脚本驱动的 Agent 工作流中自动完成。这解释了大规模设计（Open910 残余 DRC=125、NVDLA-large 残余 DRC=85）上残余 DRC 的部分来源。

3. **数据集规模与多样性有限。** 353 题已覆盖核心物理设计概念，但未涉及多电压域（multi-voltage domain）、3D-IC（三维集成）、先进封装（advanced packaging）、混合信号设计等前沿课题。

4. **大设计未完全收敛。** NVDLA-large（1.48M cells, 残余 DRC=85）、Open910（755K cells, 残余 DRC=125）在 RouteOpt 后仍有残余 DRC。论文归因于当前框架缺乏更复杂的 ECO 和 DRC-fixing 能力。

5. **商业工具与 PDK 依赖。** 完整复现依赖 Cadence/Synopsys 商业工具及 TSMC 28nm 专有 PDK。开源替代路径（OpenROAD + Nangate45）虽已声明支持，但命令语法和 flow 结构与商业工具非 1:1 等价。

### 10.2 评测公平性与可信度分析

**（1）LLM-as-Judge 的「裁判参赛」问题。** Claude Sonnet 4.6 既作为被评测模型之一，又作为所有理解类任务的评判模型。语言模型倾向于偏好自己生成的回答——这引入了 inherent bias 风险。论文通过 3 名人类工程师独立打分（偏差 2~6 分）部分缓解但未完全消除。更严谨的做法是引入正交评判模型（如用 GPT 评价 Claude 的输出，用 Claude 评价 GPT 的输出）或纯规则化评分。

**（2）pass@k 的工业可用性鸿沟。** pass@5=50% 的统计含义是「给模型 5 次机会，有一半的概率得到一个可用脚本」。但在工业流程中，工程师不可能为每个 Tcl 命令等待 5 次生成再手动挑选。工业级可用性要求 pass@1 > 95%（一次性生成质量可靠）。GPT-5.5 在 ICC2 脚本生成上 pass@1=45.5% 意味着超过一半的命令需要人工修正——远未达到「辅助人类」门槛。

**（3）数据 contamination 风险评估。** 论文声称 dataset 源自 ISSCC/VLSI/A-SSCC/CICC 等顶会的生产项目，以减少 memorization-based performance。但 353 题的绝对规模较小，且其中 90 道基础认知题的话题分布（STA 16 题、PD fundamentals 14 题等）是 standard textbook coverage——前沿 LLM 的训练语料几乎确定包含类似内容。论文未做 memorization probe（如 canary string test 或 temporal data split）。

**（4）Skill Pack 的跨节点/跨工具可迁移性。** Skill 按 `skills_{tech}_{tool}/` 目录组织，直接绑定具体工艺节点和 EDA 工具。从 TSMC 28nm+Innovus 移植到 TSMC 7nm+Innovus 或 GF 12nm+ICC2，需要重写大部分 skill 文件。fuzzy matching 自动发现机制便于加载但**不会自动适配**——论文未评估跨节点/跨工具的 skill 复用率。工业部署中，维护覆盖多节点多工具的 skill 库可能成为显著工程负担。

**（5）LLM 调用开销未与人工流对比。** 全流程平均 53 次 EDA 工具交互 + 最多 192 次 LLM 调用。LLM API 延迟（每次 2~5 秒）累计达 6~16 分钟，加上 EDA 工具自身运行时间，端到端 wall-clock 可能达数小时。论文未做与传统人工 flow 的 wall-clock time 对比——这个对比对工业评估 Agent 方案的实际经济可行性至关重要。

**（6）VLM macro placement 的 scaling 问题。** 8B VLM 在 5 个 ChiPBench 设计上表现优异，但这些设计通常只有几十到上百个 macro。在包含数百到上千个 macro 的现代 SoC 上，仅凭 layout 图像级别的视觉推理能否有效？论文未讨论 macro 数量 scaling 的能力边界。

### 10.3 本资料包的批判性分析

**（1）Skill 的「过程知识 v.s. 声明性知识」边界。** Skill Pack 包含四层知识（参考脚本/调优策略/debug 矩阵/跨阶段分析），但其中哪些是真正需要专家编码的隐性知识（tacit knowledge），哪些是可以通过改进 LLM 训练数据（如增加 EDA 手册和命令参考覆盖）来弥补的显性知识（explicit knowledge）？如果 86.6% 的失败是 flag 名写错（如把 `-around core -center 1` 写成 `-follow core`），那么提供 tool documentation retrieval 机制（而非完整的 expert skill pack）是否足够解决大部分问题？论文未做这个消融实验。

**（2）PDAgent 框架的设计空间探索有限。** Hub-and-Spoke 拓扑、五角色分工、三级预算体系——这些设计选择合理但并非唯一可能。其他可能的拓扑（如 fully connected multi-agent debate、hierarchical planner-subplanner）是否更优？论文未做框架层面的消融。Benchmark 数据集的价值独立于 Agent 框架——即使使用不同的 Agent 架构，PDAGENT-BENCH 的 353 道题仍然用于评测。

**（3）与 FluxBench 和 CLOSER-Bench 的互补性。** 三个 benchmark 分别评测 EDA Agent 的不同维度：FluxBench 评测流程的一次性通过能力（③~⑫，one-pass pipeline），CLOSER-Bench 评测跨阶段回退决策质量（③~⑬，iterative convergence），PDAGENT-BENCH 评测物理设计段的细粒度能力（⑦~⑩，fine-grained capability）。完整的 EDA Agent 评测应涵盖这三个维度，但目前缺乏一个整合框架把三者的评测结果放在同一坐标系中。

## 12. 一分钟复述版

1. PDAGENT-BENCH 是首个 VLSI 物理设计 Agent 综合评测基准：353 题 x 5 维度（基础知识 + 报告理解 + 根因分析 + STA + 脚本生成 + 全流程实现）+ Planner-Worker-Analyzer-Debugger-Optimizer 五角色闭环框架。
2. 11 个模型评测揭示四层能力梯度：基础知识 80%+ (textbook level OK)，报告理解 ~74-91% (perception OK)，根因分析 ~73-76% (reasoning decay)，脚本生成 < 50% (tool use bottleneck)。
3. 92% 脚本生成失败是 syntactic near-miss——模型知道该用什么命令，但 flag 名/参数写错。瓶颈不是领域知识，而是工具语法 grounding。
4. Skill Pack 机制将专家过程知识编码为可复用模块，使 GPT-5-mini 也能驱动全流程闭环——纯 LLM 和 RAG 基线在 init/floorplan 阶段即失败。
5. 8B VLM 在 macro placement 上超越 7 个专用算法（WNS/TNS 大幅领先，ariane133 上 TNS 提升 ~60x）。
6. 全流程 10 个设计：小/中规模（<50K cells）全部成功收敛（WNS>0, DRC=0）；大规模（>250K cells）时序可达但残余 DRC。
7. pass@k 使用标准无偏估计公式，pass@1 用 greedy temp=0，pass@5 用 temp=0.8 top-p=0.95。
8. LLM-as-Judge (Claude Sonnet 4.6) + 人类工程师独立打分校准（偏差 2~6 分）。
9. 局限：LVS 未覆盖、大设计 DRC 残留、商业工具依赖、pass@1 工业可用性不足（45.5% << 95% 门槛）。
10. 与 FluxBench（one-pass pipeline, ③~⑫）和 CLOSER-Bench（iterative convergence, ③~⑬）形成 EDA Agent 评测的三维互补——PDAGENT-BENCH 贡献的是物理设计段 agents 的 fine-grained capability diagnosis。
