## 1. 一句话定位

**VPR-Evolve 不调参，而是让多个 LLM Agent（Planner / Coder / Reviewer / Inspiration Collector）直接修改 FPGA 布局布线工具 VPR 的 C++ 源码——Planner 提修改计划、Coder 在隔离 worktree 中实施并完整 build+run 验证、Reviewer 根据真实 CPD/WL/RT 组合分数判定保留或回退，在 5 个 VTR-9 基准电路上以仅 25 次代码修改（约 AutoTuner 的 1/106 次完整 VPR run）达到相对 stock VPR 最高 2.7% 的组合分数改善，单项 CPD 最高降低 9.8%、布线线长最高降低 18.1%、运行时间最高降低 79.3%。**

这句话里的四个技术承重点，后面逐一拆解：

1. **直接演化 EDA 工具源码而非调参** -- 已有 AI4EDA 工作或是基于学习的预测模型（ML 预测 congestion/timing），或是 LLM 生成 RTL（如 RTLLM/ChipNeMo），或是传统超参数调优（如 AutoTuner 用贝叶斯优化调 VPR 参数）。VPR-Evolve 将搜索空间从"固定算法的参数组合"扩展到"可变算法 + 可变参数"的联合空间——这类似于 AutoML 中从 hyperparameter search 到 neural architecture search 的跃迁。每个候选不是靠启发式打分，必须实际编译 VPR 并通过完整的 pack-place-route 流程，直接测量 CPD/WL/RT。

2. **多 Agent 分阶段协作 + 共享记忆去重** -- 不是单个 LLM 端到端生成代码，而是 Planner（策略决策）-> Coder（代码实施）-> Reviewer（质量判定）-> Inspiration Collector（停滞时引入外部知识）的分工流水线。共享记忆 M 记录历史尝试的 idea tag，Planner 生成新计划时主动去重——直接解决 LLM "重复提出相似建议"的固有问题。

3. **五阶段演化循环（Pack -> Place -> Route -> CrossStage -> Tune）** -- 前三个阶段分别演化 pack/place/route 子系统源码，CrossStage 做跨阶段联合修改或移植已发表算法，Tune 对演化后的实现做超参数精调。S1-S4 源码演化贡献约 62% 的 CPD 改善，S5 超参数调优贡献约 38%，说明算法结构变化和参数优化是互补的。

4. **可审计、可迁移的演化产物** -- 输出不是一堆数字，而是带注释的 git 历史 + 源码 patch。人类工程师可以阅读每次修改及其 QoR 影响。跨设计迁移实验表明：19 个非对角迁移中 17 个在目标电路上保持改善，演化产物具有一定泛化性。

## 2. EDA 阶段映射（①-⑰）

VPR-Evolve 作用于 **FPGA 后端物理设计流程**。理解其阶段映射之前，必须先讲清楚 FPGA 流程与 ASIC 流程的一个根本区别。

### 2.1 FPGA 与 ASIC 物理设计的关键差异

数字 ASIC 的 17 阶段流程（参照 [芯片流程.md](../芯片流程.md)）描述的是"从零制造一颗新芯片"的完整链条。FPGA（Field-Programmable Gate Array，现场可编程门阵列）则完全不同：**芯片已经制造好了**，用户要做的是将自己的电路映射到芯片上已有的可编程资源上。

这带来几个根本差异：

| 维度 | ASIC 流程 | FPGA 流程 |
|------|-----------|----------|
| 目标硬件 | 从零制造 | 已制造好的可编程芯片 |
| 基本逻辑单元 | 标准单元库（AND2X1, XOR2X1, FDRE 等 1000+ 种） | LUT（查找表）+ FF（触发器）组成的 CLB（可配置逻辑块） |
| 存储单元 | SRAM 宏单元（定制尺寸） | BRAM（块 RAM，固定大小的硬核存储块） |
| 算术单元 | 用标准单元搭乘法器/加法器 | DSP（数字信号处理器，硬核乘法器/累加器） |
| 时钟网络 | 需要 CTS（时钟树综合），插缓冲器树，手工平衡 skew | 专用低 skew 全局时钟网络 + PLL/DCM 已预置，**无独立 CTS** |
| 布线资源 | 用多个金属层自由走线，via 换层 | 预置的布线通道 + 可编程开关盒（SB）和连接盒（CB） |
| 布局规划 | 自由摆放宏单元、IO、电源网络 | FPGA 芯片的网格结构已固定，只能在已有网格内放置 CLB/DSP/BRAM |
| 物理验证 | DRC + LVS，确保能制造 | **不需要**——FPGA 芯片本身已通过物理验证 |
| 签核 | 生成 GDSII 送代工厂 | 生成 bitstream（配置文件）下载到 FPGA |
| 流片/制造/封测 | 3-6 个月光刻-刻蚀-掺杂... | **不存在**——芯片已在货架上 |

**Packing 是 FPGA 特有的步骤**：ASIC 综合直接将 RTL 映射到标准单元库中的具体门型号；FPGA 则需要将综合后的 LUT/FF/DSP 打包（pack）进 CLB——一个 CLB 可能包含多个 LUT + 多个 FF + 进位链 + 多路选择器，资源粒度完全不同。

### 2.2 VPR-Evolve 的阶段映射表

参照 [芯片流程.md](../芯片流程.md) 的 17 阶段标准编号，结合上述 FPGA 特点：

| 阶段 | 覆盖 | 说明 |
|------|:---:|------|
| ① RTL 设计 | ❌ | VPR-Evolve 不涉及 RTL 编写。输入是已综合好的 BLIF 网表 |
| ② RTL 功能仿真 | ❌ | 不涉及 testbench 仿真。VPR-Evolve 的"验证"是 VPR 工具的运行结果（CPD/WL/RT），不是 RTL 功能验证 |
| **③ 逻辑综合（工艺映射子步骤）** | ✅ **辅助** | VPR Packing（S1）将综合后的 LUT/FF/DSP 打包进 CLB，这是 FPGA 特有的"工艺映射"步骤。ASIC 综合直接将 RTL 映射到标准单元库，FPGA 则需要额外一次 pack 来适配 CLB 的资源粒度 |
| ④ 门级仿真 | ❌ | 无 SDF 反标，不涉及门级仿真 |
| ⑤ STA | ❌ | VPR 报告的 CPD（关键路径延迟）是 VPR 内部时序分析引擎（基于 Elmore 延迟模型）的结果，不是 PrimeTime/Tempus 级别的签核级 STA |
| ⑥ 形式验证 | ❌ | 不证明等价性 |
| ⑦ 布局规划（Floorplan） | ⚠️ **部分对应** | FPGA 上没有 ASIC 意义上的自由 floorplan（芯片网格结构已固定），但确定 FPGA 架构文件中的布局尺寸、通道宽度、I/O 引脚位置等是 VPR 的初始配置步骤。VPR-Evolve 使用固定布局（1.2x 最小尺寸），不演化此阶段 |
| **⑧ 标准单元摆放（Placement）** | ✅ **核心** | VPR Placement（S2）将 CLB/DSP/BRAM 放置到 FPGA 芯片网格的固定坐标。VPR 默认使用模拟退火（SA）或解析布局（AP），VPR-Evolve 直接修改 placement 源码 |
| ⑨ 时钟树综合（CTS） | ❌ **FPGA 无此步骤** | FPGA 芯片制造时已预置专用低 skew 全局时钟网络（global clock buffer + PLL/DCM），不存在 ASIC 中插缓冲器树平衡 clock skew 的需求。VPR 只需将时钟信号分配到这些预置资源 |
| **⑩ 布线（Routing）** | ✅ **核心** | VPR Routing（S3）通过可编程开关盒（SB）和连接盒（CB）连通所有信号。VPR 默认使用 PathFinder 协商拥塞算法，VPR-Evolve 直接修改 routing 源码 |
| ⑪ 后仿真 | ❌ | FPGA 工具流中无 SPEF 寄生提取 + SDF 反标的严格后仿真。VPR 的时序分析是内置的，不涉及独立的 RC 提取 |
| ⑫ 物理验证（DRC + LVS） | ❌ | FPGA 芯片本身已通过 DRC/LVS，用户不需要再做物理验证 |
| ⑬ 签核（Signoff） | ❌ | FPGA 的"签核"是生成 bitstream（配置文件），不是 GDSII。VPR-Evolve 不涉及 bitstream 生成 |
| ⑭-⑰ 流片 → 制造 → 封装测试 → 芯片 | ❌ | FPGA 已制造完成，下载 bitstream 即可使用 |

**覆盖率：3/17。** VPR-Evolve 核心覆盖了 FPGA 后端物理设计的三个关键步骤（pack + place + route），外加跨阶段联合修改和超参数调优。它在 FPGA 流程中的定位相当于 ASIC 流程中 Innovus/ICC2 的 placement + routing 引擎——但不涉及 floorplan（在 FPGA 中不是独立阶段）、不涉及 CTS（FPGA 不需要）、不涉及物理验证和签核（FPGA 不需要）。

> ⚠️ **VPR-Evolve 的"成功"是指在一个固定 FPGA 架构和固定布局/通道宽度下，演化后的 VPR 源码能在 CPD/WL/RT 上优于 stock VPR。这和在真实项目中将一个设计部署到 FPGA 上、通过时序收敛、生成 bitstream 并跑通硬件测试，还隔着相当远的距离。VPR 使用的时序模型（Elmore 延迟）是理想化的，真实 FPGA 芯片上的走线延迟、温度/电压波动、信号完整性等因素都不在 VPR 的评估范围内。**

### 2.3 五阶段演化循环与 EDA 阶段的对应

VPR-Evolve 的五个演化阶段 S1-S5 与上述映射：

- **S1 (Pack)**：演化 VPR packing 源码 → 对应 ③ 中的 FPGA 工艺映射算法实现
- **S2 (Place)**：演化 VPR placement 源码 → 对应 ⑧ FPGA 摆放的算法实现
- **S3 (Route)**：演化 VPR routing 源码 → 对应 ⑩ FPGA 布线的算法实现
- **S4 (CrossStage)**：跨 pack/place/route 的联合修改，或从灵感库移植已发表的 FPGA CAD 算法
- **S5 (Tune)**：对演化后 VPR 实现暴露的超参数进行调优

   float dist = get_manhattan_distance_to_tile(target_loc,

-  float gain_mult = 1.0f;

## 4. 方法与架构

### 4.1 整体 Pipeline

这节展示 VPR-Evolve 从初始化到输出最终实现的完整演化循环（对应论文 Figure 1 和 Algorithm 1）。

```text
┌──────────────────────────────────────────────────────────────────────┐
│                      VPR-Evolve 演化循环                              │
│                                                                       │
│  [初始化]                                                              │
│  ├─ ComparePlacementFlows({SA, AP}, C=100) → 选择更优 flow f_low     │
│  ├─ 记录 stock VPR 基线 S_b → 设置 x = x* = stock VPR                │
│  └─ 初始化共享记忆 M（文献摘要 + idea menu + 灵感库 + 历史）           │
│                          │                                            │
│                          ▼                                            │
│  ┌─────────────────────────────────────────────────────┐             │
│  │   外层循环 (itr < I_max=5 且未超时/超token)          │             │
│  │                                                      │             │
│  │   按阶段遍历 S = {S1 Pack → S2 Place → S3 Route →    │             │
│  │                   S4 CrossStage → S5 Tune}            │             │
│  │     │                                                │             │
│  │     ├─▶ Planner (Claude Opus 4.7):                   │             │
│  │     │   输入：当前 x + 共享记忆 M + 灵感库             │             │
│  │     │   输出：最多 N=5 个结构化修改计划                │             │
│  │     │   每个计划含：机制描述 + QoR 预期 + 源码区域     │             │
│  │     │             + 可行性/风险 + idea 去重检查        │             │
│  │     │                                                │             │
│  │     ├─▶ Coder (Claude Sonnet 4.6):                   │             │
│  │     │   在隔离 git worktree 中实现单个计划             │             │
│  │     │   rebuild VPR + B=5 seeds 完整 pack→place→route │             │
│  │     │   placement 阶段使用 f_low (SA 或 AP)            │             │
│  │     │   输出：git diff + build 状态 + CPD/WL/RT 报告   │             │
│  │     │                                                │             │
│  │     └─▶ Reviewer (Claude Sonnet 4.6):                │             │
│  │          ├─ build/P&R 失败 → BUILD_FAILED             │             │
│  │          ├─ 有效 & Score < Score(x) → KEPT, x ← 新值  │             │
│  │          │   Score < Score(x*) → 更新 x*               │             │
│  │          └─ 有效 & Score >= Score(x) → REVERTED, 记r* │             │
│  │                                                      │             │
│  │   [停滞恢复 Plateau Escape]                           │             │
│  │    若连续 P_escape 轮无改进 & r* 存在                  │             │
│  │    → 以 r* 为受控非单调移动起点 (x ← r*)               │             │
│  │    → Inspiration Collector 搜文献/代码 → 补充灵感库    │             │
│  │    → 重置停滞计数, escapes++                          │             │
│  └──────────────────────────────────────────────────────┘             │
│                          │                                            │
│                          ▼                                            │
│  终止条件：itr = I_max ∪ escapes = E_max ∪ Elapsed() > T_max          │
│           ∪ TokenWeeklyExhausted()                                    │
│    → 返回 x* + 带注释的 git 演化历史                                   │
└──────────────────────────────────────────────────────────────────────┘
```

**阶段顺序是固定的**：Pack -> Place -> Route -> CrossStage -> Tune。这个顺序反映 FPGA 物理设计流程的自然依赖——packing 的结果约束 placement，placement 的结果约束 routing。CrossStage 在三个单阶段之后进行，可以跨边界做联合优化。Tune 在最后，在已演化的算法结构上精调参数。

### 4.2 核心模块逐个详解

**4.2.1 Planner（规划 Agent）—— 演化的"大脑"**

- **做什么**：为当前阶段生成最多 N=5 个具体的代码级修改计划。每个计划包含：(a) 修改机制（改什么算法、怎么改）；(b) 预期对 CPD/WL/RT 的影响方向和量级；(c) 涉及的具体源文件和函数；(d) 实施可行性与风险评估；(e) 去重标记（是否与历史尝试相似）。
- **为什么这样设计**：将"想"和"做"分离。Planner 只负责策略层面的搜索方向决策，不需要写代码，可以集中精力分析文献、记忆和当前状态，提出有理论依据的修改方向。使用更强的 Claude Opus 4.7（1M context window），因为 Plan generation 是每阶段唯一需要大量上下文和推理判断的调用。
- **输入**：当前阶段的 VPR 源码、当前 x 的 QoR、共享记忆 M（含文献摘要 + idea menu + 历史计划）、灵感库中的算法描述。
- **输出**：结构化的修改计划列表，每个计划作为 Coder 的输入。
- **LLM 角色**：Planner 是 LLM 扮演的核心决策者——需要理解 FPGA CAD 算法的学术文献、读懂 VPR 的 C++ 源码结构、识别可能的改进方向、生成可执行的计划。

**4.2.2 Coder（编码 Agent）—— 演化的"手"**

- **做什么**：在隔离的 VPR git worktree 中实现单个修改计划——直接编辑 C++ 源文件。然后 rebuild VPR 并用 B=5 个随机种子执行完整的 pack -> place -> route 流程。Placement 阶段使用 ComparePlacementFlows 选定的 f_low（SA 或 AP）。
- **为什么这样设计**：每个候选在独立 worktree 中编译运行，互不干扰。B=5 个种子用于评估修改的稳定性——单个种子下的随机噪声（SA 的随机性、routing 的随机性）可能导致误判。使用 Claude Sonnet 4.6（而非 Opus），因为代码实施相比策略规划对推理深度的要求较低。
- **输入**：单个修改计划 + VPR 源码 + 目标电路网表 + FPGA 架构文件。
- **输出**：包含 diff 的 git commit + build 状态 + B=5 个种子的 CPD/WL/RT 测量值 + 组合分数。

**4.2.3 Reviewer（审查 Agent）—— 演化的"过滤器"**

- **做什么**：判定候选的保留/回退/失败。判定依据：(a) 编译是否成功；(b) P&R 是否全部跑完；(c) 组合分数是否低于当前 x。
- **为什么这样设计**：自动化实验评估的核心——每个候选必须经过真实 VPR build + run 的完整检验，而非启发式近似。这保证选择压力严格对应于实际的 FPGA 实现质量，避免了代理模型偏差（proxy model bias）。
- **输入**：Coder 的 git diff + build log + 5-seed QoR 报告 + 组合分数。
- **输出**：判定标签（KEPT / REVERTED / BUILD_FAILED）+ 更新的搜索状态（x / x* / r*）。

**4.2.4 Inspiration Collector（灵感搜集 Agent）—— 演化的"外援"**

- **做什么**：仅在搜索停滞（p_escape 连续无改进）时激活。从最新 FPGA CAD 文献和开源参考实现中搜集新机制，补充到灵感库和阶段 idea menu。它不能修改源码或做接受/拒绝决策。
- **为什么这样设计**：防止 Planner 陷入"想法枯竭"——当所有本地修改尝试都不再产生改善时，需要引入外部知识开辟新的搜索方向。这实现了受控的探索-利用平衡（exploration-exploitation）：正常搜索阶段是 exploitation（在已有想法中找最优），停滞恢复阶段是 exploration（引入全新想法）。
- **输入**：学术文献数据库、开源 FPGA CAD 代码仓库。
- **输出**：新的 idea 条目（含文献引用、算法描述、预期影响），追加到共享记忆 M 的灵感和 idea menu 中。

**4.2.5 共享记忆 M（Shared Memory）**

- **长期记忆**：灵感库、FPGA CAD 文献摘要、各阶段 idea menu、历史计划数据库（含结果）。
- **短期记忆**：当前搜索状态 x、最近计划的尝试结果、当前迭代已尝试的 idea tag（用于去重）。
- **为什么这样设计**：避免重复探索相同或相似的想法。Planner 生成新计划时，可以查询"这个 idea tag 之前试过吗？结果如何？"——这直接针对 LLM 倾向于"重复提出相似建议"的固有问题。成功的 idea 成为未来计划的正向引导信号（"这个方向有效，尝试类似变体"），失败的 idea 成为负向规避信号（"这条路走不通"）。

### 4.3 模块职责矩阵

| 模块 | 输入 | 输出 | 用到的模型/工具 | 是否需训练 |
|------|------|------|-----------------|-----------|
| **Planner** | 当前阶段源码 + x 的 QoR + 共享记忆 M + 灵感 | 结构化修改计划 (<=5 个) | Claude Opus 4.7 | 否 |
| **Coder** | 单个计划 + VPR 源码 + 网表 + 架构文件 | git commit + CPD/WL/RT 报告 | Claude Sonnet 4.6 + VPR build/run | 否 |
| **Reviewer** | git diff + build log + QoR 报告 | 判定标签 + 更新 x/x*/r* | Claude Sonnet 4.6 | 否 |
| **Inspiration Collector** | FPGA CAD 文献 + 开源代码仓库 | 新 idea 条目 | Claude Sonnet 4.6 | 否 |

| **Git 版本控制** | Coder 的 commit/revert | 可审计的演化轨迹 | Git | 否 |

## 5. 关键公式

### 5.1 组合分数（Composite Score）

这是 VPR-Evolve 的适应度函数，每一个候选实现都通过它来判定"是好是坏"。

论文定义的组合分数：

$$
\text{Score} = S_{\text{ref}} - (\alpha \cdot \text{imp}_{\text{CPD}} + \beta \cdot \text{imp}_{\text{WL}} + \gamma \cdot \text{imp}_{\text{RT}})
$$

其中每一项的改善百分比定义为：

$$
\text{imp}(S_b, S_m) = 100 \cdot \frac{S_b - S_m}{S_b}
$$

- $S_{\text{ref}} = 1000$：参考分数（stock VPR 基线，分数越低越好）
- $S_b$：基线实现（stock VPR）在对应指标上的值，搜索开始时测量一次并固定
- $S_m$：候选实现在对应指标上的值
- $\alpha = 0.5$：CPD（Critical-Path Delay，关键路径延迟，ns）权重 -- 主优化目标，决定了最高工作频率
- $\beta = 0.2$：WL（Routed Wirelength，布线线长）权重 -- 次要目标，影响功耗和拥塞
- $\gamma = 0.3$：RT（Runtime，运行时间，s）权重 -- 效率目标，防止以不可接受的运行时间换取 CPD/WL 改善
- $\alpha + \beta + \gamma = 1.0$：权重归一化

**工程直觉**：stock VPR 固定得 1000 分。如果某个代码修改使 CPD 降低 5%（改善 +5%），WL 降低 2%，RT 降低 3%，则总改善 = 0.5 x 5 + 0.2 x 2 + 0.3 x 3 = 3.8，分数变为 996.2。**分数越低越好，1000 以下即为优于 stock VPR。**

**为什么把 RT 放进目标函数**：如果不惩罚运行时间，Planner 可能提出"用更复杂的启发式大幅改善 CPD 但运行时间翻倍"的修改。将 RT 以 gamma=0.3 的权重纳入组合分数，确保 CPD 和 WL 的改善不以不可接受的运行时间增长为代价。

### 5.2 决策规则

论文未给编号公式，以下是对其算法行为的形式化：

$$
\text{Decision}(c) = \begin{cases}
\text{KEPT} & \text{if } \text{Valid}(c) \text{ and } \text{Score}(c) < \text{Score}(x) \\
\text{REVERTED} & \text{if } \text{Valid}(c) \text{ and } \text{Score}(c) \geq \text{Score}(x) \\
\text{BUILD\_FAILED} & \text{if } \neg \text{Valid}(c)
\end{cases}
$$

- $\text{Valid}(c)$：候选 c 编译成功且完整 P&R 运行完成
- $\text{Score}(c)$：候选 c 在 B=5 个 in-loop 种子上的平均组合分数
- $\text{Score}(x)$：当前搜索状态 x 的组合分数
- KEPT 时 $x \leftarrow c$，若 $\text{Score}(c) < \text{Score}(x^*)$ 则 $x^* \leftarrow c$
- REVERTED 时记录 $r^* \leftarrow \text{BetterOf}(r^*, c)$（保存停滞期间最佳被拒候选）

**工程直觉**：这是一个贪心接受策略——只接受严格改善的候选。贪心策略在非凸搜索空间中容易卡局部最优，这正是 Plateau Escape 机制存在的理由：当连续无改善时，接受一个之前被拒绝的候选 r* 作为新的搜索起点（受控的非单调移动），从不同初始点继续搜索。

### 5.3 停滞恢复条件

论文未给编号公式，以下是对其算法行为的形式化：

$$
\text{PlateauEscape} \iff p_{\text{plateau}} \geq P_{\text{escape}} \text{ and } r^* \neq \emptyset
$$

- $p_{\text{plateau}}$：连续无候选被保留的迭代轮数
- $P_{\text{escape}} = 1$：停滞阈值（论文设定非常激进——仅 1 轮无改进就触发恢复）
- $r^*$：停滞期间记录的最佳被拒候选

停滞恢复时执行：
1. $x \leftarrow r^*$（受控非单调移动）
2. InspirationCollector(M)（补充新想法）
3. $p_{\text{plateau}} \leftarrow 0$（重置停滞计数）
4. $\text{escapes} \leftarrow \text{escapes} + 1$（递增逃离计数）
5. $r^* \leftarrow \emptyset$（清空，开始新停滞周期）

**终止条件**：

$$
\text{Terminate} \iff itr = I_{\text{max}} \text{ or } \text{escapes} = E_{\text{max}} \text{ or } \text{Elapsed}() > T_{\text{max}} \text{ or } \text{TokenWeeklyExhausted}()
$$

## 6. 训练与实验设置

### 6.1 是否需要训练

**不需要训练。** VPR-Evolve 是一个纯推理时（inference-time）的多 Agent 系统，直接调用现成的 Claude API（通过 Claude Code agent harness），不对任何模型参数进行微调。所有"智能"来自 LLM 的预训练知识 + 精心设计的 Agent 分工 + 共享记忆机制。

核心开销在于：
- **LLM 调用成本**：每电路 338.8M-728.3M tokens（含缓存读取，其中缓存读取由服务商以较低成本提供，不计入 token 预算）
- **计算成本**：每候选需完整 build VPR + B=5 seeds 完整 P&R 运行
- **时间成本**：每电路 wall-clock 预算 120 小时，实际搜索受 I_max、E_max、T_max 限制而非 token 周预算

### 6.2 实验设置

**Benchmark**：5 个 VTR-9 benchmark 电路，规模从 36,833 到 167,249 个 primitives。论文选择较大规模电路，因为在小型设计上改善空间有限、超参数调优也能达到类似效果；VPR-Evolve 在大电路上更能展示源码演化相对于参数搜索的优势。

**FPGA 架构与约束**：固定使用 `k6_frac_N10_frac_chain_mem32K_40nm` 架构。布局尺寸 = 1.2 x d_min（最小自动布局尺寸），通道宽度 = 1.2 x W_min 向上取偶数。每电路有固定布局、固定通道宽度，所有实验在同一固定设置下运行，确保改善不来自器件尺寸变化。

**硬件**：64 核 CPU + 256 GB RAM 的数据中心服务器。

**Baseline 方法**：

| Baseline | 说明 | 评估方式 |
|----------|------|----------|
| Stock VTR-9（commit `bd5434a94`） | VTR-9 的固定（pinned）版本，所有演化算法和调优配置都在同一代码基线测量 | 100 种子几何均值 |
| AutoTuner | 基于 Ray Tune + Optuna TPE（Tree-structured Parzen Estimator，贝叶斯族序贯模型优化器）的超参数调优框架 | 最多 3000 次迭代，100 种子最终评估 |

AutoTuner 获得慷慨的迭代预算（3000 次/电路），其调优 wall-clock 在每电路上都超过 VPR-Evolve——论文有意给 AutoTuner 更多调优时间，以展示源码演化的搜索效率优势而非计算预算优势。

**评估指标**：

- **组合分数（Composite Score）**：见第 5.1 节公式。100 个评估种子上的 per-seed 分数的均值。论文 Figure 2 展示分布（箱线图：25-75 百分位 + 中位数 + 5-95 百分位须线）。
- **单项指标**：CPD（ns）、WL、RT（s），报告 100 个评估种子上的几何均值（论文 Table 3）。
- **变异系数（CoV）**：标准差 / 均值，衡量 100 个种子下组合分数的稳定性。
- **跨设计迁移分数**：将源电路演化出的实现直接应用于目标电路后的组合分数（论文 Table 4）。

**评估协议**：
- B=5 个 in-loop 种子用于搜索过程中的候选评估
- 搜索结束后，100 个独立评估种子用于最终 QoR 测量
- 基线值 S_b 在搜索开始时测量一次并固定，后续所有分数均以此基线计算

**稳定性**：VPR-Evolve 组合分数的变异系数 CoV 在 LU8、bgm、sv2、mcml、LU32 上分别为 0.06%、0.14%、0.20%、0.05%、0.12%，极低——演化产物在不同随机种子下表现高度一致，说明改善不是"幸运种子"的偶然结果。

**跨设计迁移**（论文 Table 4）：19 个完成的非对角迁移（将源电路演化出的实现直接应用于不同目标电路）中 17 个优于默认 VTR-9（分数低于 1000）。LU8、sv2、mcml 演化出的实现对**所有**完成的目标电路均带来改善——说明演化产物不是"过拟合"到源电路的。

## 7. 创新点

### 创新点 1：首次将 LLM 驱动的算法演化引入 FPGA 物理设计 CAD

已有 AI4EDA 工作的搜索空间边界：

| 范式 | 代表性工作 | 搜索空间 | 局限 |
|------|-----------|---------|------|
| 基于学习的预测模型 | ML 预测 congestion/timing | 固定算法的参数 | 不改变算法本身 |
| LLM 生成 RTL | RTLLM, ChipNeMo, VerilogCoder | RTL 代码 | 不改 EDA 工具内部算法 |
| 超参数调优 | AutoTuner（贝叶斯优化）, DATuner（multi-armed bandit） | 固定算法暴露的参数 | 只能选择已有行为，不能引入新机制 |
| LLM 演化 EDA 工具（ASIC） | GR-Evolve（全局布线）, ABC/Yosys Evolve（逻辑综合）, AuDoPEDA（OpenROAD） | EDA 工具源码 | ASIC 流程，未涉及 FPGA 特有的 pack 阶段和多阶段交互 |

VPR-Evolve 的独特之处：(a) **首次将 LLM 驱动的源码演化引入 FPGA CAD**，而非 ASIC CAD；(b) FPGA 流程有 pack/place/route 三个交互阶段，每个阶段的修改会影响下游，VPR-Evolve 通过分阶段演化 + CrossStage 联合优化来处理这种交互；(c) 将搜索空间从"固定算法的参数组合"扩展到"可变算法 + 可变参数"的联合空间。

### 创新点 2：多 Agent 分阶段协作 + 共享记忆去重机制

不是单个 LLM 端到端生成代码（如 AlphaEvolve），而是 Planner -> Coder -> Reviewer 的分工流水线，各 Agent 职责单一、权限分离（Coder 不能评判自己的修改，Reviewer 不能修改代码）。

共享记忆 M 的去重机制是工程上最务实的创新：(a) Planner 在生成新计划时主动查询"这个 idea tag 是否已尝试过"；(b) 历史尝试的原因（KEPT/REVERTED/BUILD_FAILED）和 QoR 影响保留在记忆中；(c) 直接解决了 LLM "重复提出相似建议"的固有问题——这在开放式代码演化中是一个被低估的关键挑战。

### 创新点 3：完整 VPR build + run 作为真实评估（no proxy）

每个候选不是靠启发式打分或代理模型评估——必须实际编译 VPR 并通过完整的 pack -> place -> route，直接测量 CPD/WL/RT。这保证选择压力严格对应于真实 FPGA 实现质量，避免了代理模型偏差。

代价是评估成本高昂：每候选至少 5 个种子的全流程 VPR run。但正因为评估是真实而非近似的，搜索结果在实验上可靠——不需要担心"代理模型最优 != 真实最优"的偏差。

### 创新点 4：源码演化 + 超参数调优的联合搜索

论文发现 S1-S4 源码演化贡献约 62% 的 CPD 改善，S5 超参数调优贡献约 38%。这说明两类搜索是互补的——先演化算法结构扩大搜索空间，再在更好的结构上精细调参。这种"先改算法、后调参数"的顺序是有意识的设计选择（而不只是"两个都做"），因为调参的效果上限受算法结构制约——先在结构层面打破瓶颈，再通过参数层面榨取剩余收益。

### 创新点 5：可审计、可迁移的演化产物

与纯参数搜索（输出一堆数字）不同，VPR-Evolve 的输出是带注释的 git 历史 + 源码 patch——人类工程师可以阅读、理解、审计每一次代码修改及其 QoR 影响。这不仅是实验结果可复现性的保障，也使得演化产物可以作为 FPGA CAD 研究社区的知识资产（"这个高斯衰减对 mcml 类电路有效"），而非不可解释的黑箱参数组合。

### 9.2 VPR-Evolve 解决的痛点

传统 FPGA 工具流中，pack/place/route 算法由 VPR 开发者手工设计并固定发布，所有电路——无论规模、连接模式、时序特征多么不同——都用同一套"一刀切"算法。AutoTuner 等超参数调优方法可以在这个固定算法的参数空间中寻找更好的配置，但不能引入新机制。

VPR-Evolve 展示了一条新路径：LLM 可以为**每个具体 FPGA 设计自动定制 EDA 工具内部的算法实现**。这不是"调参"，而是"改算法"——把 distance attenuation 从分段二次/平方根 knee 改成平滑高斯衰减（mcml 的 packing 阶段）、调整 placement 的 move 选择策略、修改 routing 的拥塞代价函数等。这种"设计-工具协同优化"的思路对 ASIC EDA 工具链（如 Innovus/ICC2 的 placement/routing 引擎）同样具有启发意义。

### 9.3 「VPR 评估通过」和「真实 FPGA 部署成功」之间隔着什么

VPR-Evolve 的"成功"是指在固定 FPGA 架构和固定布局/通道宽度下，VPR 内部时序引擎报告的 CPD/WL/RT 改善。但在真实 FPGA 项目中，以下差距客观存在：

1. **时序模型精度**：VPR 使用 Elmore 延迟模型——这是 RC 树的近似，精度远低于 SPICE。真实 FPGA 芯片上的走线延迟受温度/电压/工艺角/串扰等因素影响，VPR 的 CPD 报告只是一个理想化估计。工业 FPGA 工具（Vivado/Quartus）的时序分析引擎精度远超 VPR。

2. **没有真实硬件验证**：VPR-Evolve 不生成 bitstream，不在真实 FPGA 芯片上运行。bitstream 生成（VPR 可以配合 VTR 做，但不是本文评估范围）、硬件时序收敛、信号完整性验证都不在本文范围。

3. **单架构评估**：仅在 `k6_frac_N10_frac_chain_mem32K_40nm`（6-LUT + 进位链 + 32Kb BRAM，40nm）一种架构上评估。实际 FPGA 产品跨越多种架构（Xilinx UltraScale、Intel Agilex 等），每种架构有不同的 LUT 结构、布线拓扑和硬核资源，VPR-Evolve 的演化策略是否跨架构有效未知。

4. **固定布局约束**：使用固定布局（1.2x 最小尺寸）和固定通道宽度（1.2x W_min 向上取偶），排除了 floorplan 阶段的自由。真实项目中，布局/通道宽度是可以调节的自由度——有时增大芯片面积换取更好的时序是合理的 trade-off，但 VPR-Evolve 的实验设计防止了"靠增大布局取胜"的策略。

## 10. 讨论与局限

### 10.1 论文自述的局限

1. **评估范围局限于单架构 + 5 电路**：仅在一种 FPGA 架构和固定布局/通道宽度下评估。跨架构泛化（如从 40nm 架构迁移到 28nm 架构的 VPR 配置）未测试。
2. **LLM 模型与成本漂移**：使用特定版本 Claude 模型和 token 预算，模型更新或定价变化会影响可复现性和经济性。
3. **源码正确性风险**：LLM 修改生产级 C++ EDA 工具源码可能引入难以察觉的回归 bug 或边界条件错误——虽然每个候选经过完整 VPR build + run 测试，但 5 个种子的覆盖范围不足以发现所有潜在问题。
4. **组合分数权重固定**：alpha=0.5, beta=0.2, gamma=0.3 由作者设定，不同设计场景可能需要不同的 CPD/WL/RT 优先级。

### 10.2 代码/复现层面的问题

5. **代码已声明开源但本地未核验**：论文声明代码在 https://github.com/ASU-VDA-Lab/VPR-Evolve 开源，但本地未实际 clone/build/运行。复现需要：(a) VTR-9 工具链编译环境；(b) 5 个 benchmark 电路数据；(c) Claude API 访问权限 + Claude Code agent harness 配置；(d) 64 核 256GB 规模的计算资源。

6. **LLM 调用成本构成复现门槛**：每电路 token 消耗 338.8M-728.3M（包含缓存读取），即使缓存读取以较低成本提供，input/output/cache-creation tokens 的实际API费用也是显著开支。使用不同模型版本或不同 LLM 提供商可能导致 Planner 提出的修改计划质量不同，影响最终结果。

### 10.3 本资料包的批判性分析

7. **源码演化 vs 超参数调优的价值边界未充分比较**：论文给 AutoTuner 3000 次迭代的预算，VPR-Evolve 的搜索受 I_max=5、E_max=2、T_max=120h 限制。最关键但未做的对照实验：如果给 AutoTuner **相同的 120 小时 wall-time 预算**（而非固定的 3000 次迭代），它是否能通过更密集的参数搜索达到接近或超过 VPR-Evolve 的结果？AutoTuner 每次迭代只跑一次 VPR（不需要编译，不需要 B=5 种子评估），在 wall-time 预算内可能完成远超 2645 次的评估次数。当前实验设计保证了 VPR-Evolve 在"搜索效率"指标上胜出（106x 更少 VPR run），但没有保证在"等 wall-time"指标上同样胜出。

8. **演化产物的可维护性问题**：每个电路产生独立 fork 的 VPR 源码（LU8 +640 行，mcml +27 行）。这些补丁是针对特定电路调优的——当 VPR 官方升级时，补丁能否合并？是否会与新版本的默认行为冲突？"每电路一个定制 VPR"的模型在工程上不具可扩展性——如果用户有 50 个设计，就需要维护 50 个 VPR 分支。

9. **搜索效率与评估成本的矛盾**：mcml 上仅 25 次代码修改听上去高效（vs AutoTuner 2645 次配置评估），但每次修改需要完整 build + 5-seed P&R。论文图 3 显示总 wall-clock 仍以数十小时计。如果目标电路更大（如工业级 FPGA 设计，百万级 LUT），单次 VPR run 可能就要数小时，25 次修改的 wall-clock 将不可承受。**搜索效率的声称需要放在"单次评估成本"的语境下理解**——VPR-Evolve 虽然评估次数少，但每次评估的代价远高于 AutoTuner 的单次参数评估。

10. **跨设计迁移的真正含义被高估**：Table 4 显示 19 个非对角迁移中 17 个"优于 stock VPR"，但这只是一个很低的标准。关键问题是：迁移产物与**直接在目标电路上单独演化**相比差多少？如果迁移后的组合分数（如 sv2 演化产物在 LU32 上得 993）远差于直接在 LU32 上演化（992.5），迁移的价值就大打折扣。论文未提供"迁移 vs 直接演化"的差距分析。

11. **LLM 作为"搜索引擎"的黑箱问题**：Planner 提出修改计划的过程完全不透明。我们不知道 LLM 是**真正推理**了 VPR 的算法结构和电路特性之间的匹配关系，还是从训练数据中"回忆"了 FPGA CAD 论文中的改进 idea（如高斯衰减替代分段衰减这种在文献中出现过的方案）。如果是后者，VPR-Evolve 的价值更多在于**自动化实现已有论文 idea**（这仍然有价值，但性质不同），而非**发现全新算法**。

12. **Plateau Escape 的有效性取决于 r\* 的偶然性**：当停滞触发时，VPR-Evolve 以 r*（停滞期间最佳被拒候选）作为新的搜索起点。但 r* 的质量取决于停滞期间 Coder 碰巧尝试了哪些修改——如果所有被拒候选都在同一个局部最优盆地内，从 r* 重新开始也不会走出盆地。P_escape=1 的激进设置（仅 1 轮无改进就触发恢复）意味着系统频繁重置搜索起点，可能打断正在收敛的搜索方向。

13. **适应性景观的隐式假设**：VPR-Evolve 假设 CPD/WL/RT 的组合分数构成一个"可逐步攀登的适应性景观"——存在一系列单步改进使 Planner 逐渐接近全局最优。但如果 VPR 的适应性景观高度非凸（微小代码改动导致 QoR 剧烈跳变，或不相关的代码区域存在强交互效应），贪心接受策略（KEPT only if strictly better）会频繁卡在局部最优。Paper 仅设计了 Plateau Escape 来应对，没有探索更复杂的全局搜索策略（如 MCTS、beam search、population-based）。

14. **等预算对比缺失影响结论强度**：论文声称"VPR-Evolve 扩展了搜索空间"，但未证明这个更大搜索空间**在等计算预算下**能带来更好的结果。如果给超参数调优相同的 LLM token 预算（让 LLM 更智能地选择要评估的参数组合），结果如何？如果给超参数调优相同的 wall-time 预算（让贝叶斯优化跑更多迭代），结果如何？这些缺失使得"源代码演化 > 超参数调优"的结论建立在不完全公平的比较之上。

## 12. 一分钟复述版

VPR-Evolve（Arizona State University, ASP-DAC 2027 投稿）是一个**不训练任何模型、直接修改 FPGA 布局布线工具 VPR 的 C++ 源码的多 LLM-Agent 演化框架**。核心四招：

1. **多 Agent 分工协作**：Planner（Claude Opus 4.7）提出源码修改计划，Coder（Claude Sonnet 4.6）在隔离 worktree 中实施并 build+run 完整 VPR 流程，Reviewer（Claude Sonnet 4.6）根据真实 CPD/WL/RT 组合分数判定 KEPT/REVERTED/BUILD_FAILED，Inspiration Collector 在搜索停滞时引入外部知识。四个 Agent 通过共享记忆 M 协作，记忆中的 idea tag 去重机制解决了 LLM "重复提建议"的固有问题。

2. **五阶段演化循环**：Pack -> Place -> Route -> CrossStage -> Tune，按 FPGA 物理设计流程的自然依赖顺序执行。S1-S4 源码演化贡献约 62% 的 CPD 改善，S5 超参数调优贡献约 38%——算法结构变化和参数优化是互补的。

3. **完整 VPR build + run 作为真实评估**：每个候选必须实际编译并通过完整 P&R，直接测量 CPD/WL/RT。不依赖代理模型或启发式打分，保证选择压力严格对应真实 FPGA 实现质量。代价是评估成本高昂——但这正是"结果可靠"的代价。

4. **可审计、可迁移的演化产物**：输出是带注释的 git 历史 + 源码 patch，人类工程师可以阅读和理解每次修改。跨设计迁移实验：19 个非对角迁移中 17 个在目标电路上保持改善。

**结果**：5 个 VTR-9 benchmark 电路上，相对 stock VPR 组合分数最高改善 2.7%，CPD 最高降低 9.8%，WL 最高降低 18.1%，RT 最高降低 79.3%。搜索代价约 AutoTuner 的 1/106（25 vs 2645 次代码/配置修改，125 vs 13,225 次完整 VPR run）。

**边界**：(a) 覆盖 FPGA 物理设计 3/17 阶段，不涉及 RTL、综合、门级仿真、STA、物理验证、流片；(b) 仅评估单 FPGA 架构 + 5 电路，跨架构泛化未知；(c) VPR 的 Elmore 延迟模型精度低于工业工具，CPD 结果是理想化估计；(d) "每电路一个 VPR"的模型不可工程扩展；(e) 等 wall-time/等 token 预算的对比实验缺失——无法区分"源码演化 > 超参数调优"和"LLM 辅助的搜索 > 贝叶斯优化"；(f) Planner 的修改计划来源不透明——可能更多是"回忆已知论文 idea"而非"发现新算法"；(g) 代码声明开源但本地未核验，复现需要 Claude API + 64 核 256GB 服务器。
