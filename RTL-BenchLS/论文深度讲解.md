## 1. 一句话定位

RTL-BenchLS 是首个同时在"数据规模"和"任务范式"两个维度上突破现有 RTL 评测基准的 LLM 评测套件——它把 **10,028 条经过 LEC/SEC 形式化等价校验的 Verilog 设计**（平均 94 行、最长 495 行，比 VerilogEval/RTLLM 大两到三个数量级）与 **三个全新任务**（自监督的 Round-Trip Reasoning 与 Masked-Content Reasoning、贴近真实工程环境的 Repository-Issue Reasoning）组合在一起，全部用 **Cadence Conformal / JasperGold 形式等价性检查**自动打分，无需任何手写 testbench。八个前沿 LLM 在新基准上的最佳成绩仅 ~23% / ~28% / ~12%，与 VerilogEval 上近 88% 的"饱和"水平形成强烈反差，揭示了 LLM 在硬件推理与生成方向上仍存在巨大的提升空间。

## 2. EDA 阶段映射

本工作位于前端数字设计自动化（front-end digital design automation）的两个阶段：

| EDA 阶段 | 本工作覆盖？ | 说明 |

| ① 系统需求与市场定义 | ✗ | — |

| ⑫ 时钟树综合 (CTS) | ✗ | — |

| ⑭ 物理验证 (DRC/LVS) | ✗ | — |
| ⑮ 寄生参数提取 (PEX) | ✗ | — |
| ⑯ 时序收敛 (timing closure) | ✗ | — |

**覆盖率: 2 / 17**

具体而言：

- **RTL 功能仿真阶段**：传统做法是编写 testbench 跑仿真对比波形；本文创新性地用形式等价性检查（LEC 对组合、SEC 对时序）来判定功能正确性，把"仿真"这一阶段从基于向量的随机验证升级为基于数学等价的形式验证。

## 3. 输入 / 输出

### 3.1 输入

| 任务 | 输入 | 数据规模 |
|---|---|---|
| **Task 1：Round-Trip Reasoning** | 一段完整的 Verilog 设计 `D`（slice 1 上 420 条） | 单模块，平均 94 LoC，最长 495 LoC |
| **Task 2：Masked-Content Reasoning** | 一段 Verilog 设计 `D\B`（含 `[MASKED]` 占位符）+ 该被掩码块的自然语言描述 `A_B`（由 LLM 在 Step 1 自生成） | 同 Task 1 的 420 条，每条 1 个掩码 |
| **Task 3：Repository-Issue Reasoning** | 完整的仓库代码 `R` + issue 评论（含标题与正文）`I` + 简化的"buggy 设计" `Dbuggy` | 108 条从 25 个 GitHub 仓库挖掘的真实 issue-PR 对 |

附加可选输入（用于 Task 1 抽象格式）：
- 中间抽象类型选择：自然语言 `A_NL`（带压缩比 r∈{0.5, 1.0}）/ 图表式自然语言 `A_NL-Diag` / 可执行代码 `A_Code`（Python 或 C）/ 自由格式 `A_Free`。
- 风格化 prompt：鼓励模型使用状态转换表、真值表、模块级描述等"硬件工程师惯用表达"。

### 3.2 输出（具体例子）

#### 任务 1 输出示例（Round-Trip Reasoning，自然语言抽象）

- 输入 D（一段 `crc16_lfsr`，49 行）
- Step 1 失败样例（GPT-4o）：`A_NL` = "The LFSR updates its state ... certain bits are updated using XOR operations involving the input data and the most significant bit of the LFSR." → 未指定具体 bit 位置 → Step 2 重建出的 RTL 不能通过 SEC。
- Step 1 成功样例（DeepSeek-v3.2、Claude Haiku-4.5）：`A_NL` 显式写出 "bit 0 is computed as the XOR of `data_in` and bit 15; bit 5 incorporates additional XOR feedback; bit 12 similarly ..." → Step 2 重建 RTL 通过 SEC。

#### 任务 2 输出示例（Masked-Content Reasoning，8-bit 加法器溢出标志）

- 输入 `D\B`：ALU 模块中含 `[MASKED]` 占位符；上下文提供 `intermediate_carry[6]` 和 `carry` 信号。
- 成功样例（DeepSeek-v3.2、Mistral-Large）：Step 1 描述为 "Detects overflow using XOR logic"；Step 2 重建 `overflow = intermediate_carry[6] ^ carry;`（处理加/减两种路径）→ 通过 SEC。
- 失败样例（GPT-4o、Sonnet-4.5）：Step 1 描述为 "Detects signed overflow condition"；Step 2 给出符号位教科书公式 `(a[7]&b[7]&~sum[7]) | (~a[7]&~b[7]&sum[7])` → 在减法路径上失效。

#### 任务 3 输出示例（Repository-Issue Reasoning，lowRISC/ibex #1178）

- 输入 issue：PMP NAPOT 地址掩码逻辑在 granule 跨整时使用 `PMPGranularity+2` 是错误的，正确应为 `PMPGranularity+1`。
- Golden fix（一行）：
  ```
  - ~&csr_pmp_addr_i[r][b-1:PMPGranularity+2];
  + ~&csr_pmp_addr_i[r][b-1:PMPGranularity+1];
  ```
- 成功样例（Sonnet-4.5、DeepSeek-v3.2）：恰好改动同一行；LLaMA-3.3-70B 改写成等价形式亦通过。
- 失败样例（GPT-4o）：把所有 `+2` 替换为 `+1`，破坏无关数组宽度。
- 失败样例（Haiku-4.5）：正确定位但过度工程化，新增 `if (PMPGranularity==0) begin ... end` 分支，结构差异过大未通过 SEC。

## 4. 方法与架构

RTL-BenchLS 框架分为 **数据生产流水线**（Figure 4）和 **任务调用框架**（Figure 1）两大部分。

### 4.1 数据流水线

```
  Source                Module Extraction       Filtering Pipeline
  ------                -----------------       ------------------
  S1: 25+ GitHub repos -+
  S2: OriGen corpus    -+
  S3: AutoVCoder       -+-- Recursive parser --> LoC + NoM + TF-IDF -->  Formal Env
  S4: RTLPP            -+    (per-module)        (similarity > 0.2)       (Conformal LEC/SEC)
  S5: MG-Verilog       -+                                              |
                                                                          v
                                                                     10,028 designs
                                                                     (avg 63 LoC, max 479)
                                                                          |
                                                                          v
                                                                  10 patches (slice-1..10)
                                                                  + 5 source partitions (S1..S5)
```

关键设计点：
1. **模块级抽取（Recursive Parser）**：对每个 GitHub 仓库或 LLM 生成语料，逐文件递归遍历模块声明，保留独立可综合的 Verilog module 单元。
2. **相似度去重**：用字符 4-gram + TF-IDF 向量化两两设计，余弦相似度 > 0.2 的对按贪心策略剪枝；Figure 3 显示数据分布远低于 0.1，过滤掉了 ~5.5M / 10k×10k 对中相似度过高的 ~1.8M。
3. **形式等价自校验**：组合逻辑用 Cadence Conformal LEC、时序逻辑用 Cadence JasperGold SEC，对每个模块做"自指"等价检查（module 与自身 elaborated 版本），确保编译 + 形式等价通过。
4. **双切片策略**：
   - *Patch-based*：10 个大小近似的子集，每个子集按比例保留 S1-S5 来源分布，用于"可控消融 + 代表性评估"。
   - *Source-based*：按 S1-S5 来源切分，用于"分析 LLM 在真实仓库 vs LLM 生成语料上的差异"。

### 4.2 任务架构

#### Task 1：Round-Trip Reasoning（自监督）

```
            Step 1. Reasoning             Judger            Step 2. Generation          Verification
            -----------------             ------            -------------------          ------------
   D   -->  LLM  -->  Abstract A   -->   LLM-judger   -->   LLM  -->  D'   -->   LEC / SEC   -->   pass?
                          (length check, leakage check)              (D'  =  D  ?)
```

四种中间抽象格式：
- `A_NL`：纯自然语言，受 spec ratio `r = L(A) / L(D)` 约束（r=0.5 强制压缩）。
- `A_NL-Diag`：图表风格自然语言（状态机表、真值表、模块框图描述）。
- `A_Code`：可执行 Python 或 C 代码，强制把 RTL 转写为软件函数。
- `A_Free`：模型自选任意格式混合。

#### Task 2：Masked-Content Reasoning（自监督）

```
   Step 1. Concise Description            Step 2. Mask Recover
   --------------------------             --------------------
   RTL D + block B  -->  LLM  -->  A_B   D\B (with [MASKED]) + A_B  -->  LLM  -->  B'   -->   LEC/SEC
                                                   (D\B + B'  =  D ?)
```

两种掩码粒度：
- **Block mask**：随机选取 always / assign / case 等语句块。
- **Module mask**：随机选取子模块实例化。

#### Task 3：Repository-Issue Reasoning（半监督 / 真实 bug）

```
  RTL Repo R  +  Issue comment I  +  (optional D_buggy)  -->  LLM  -->  D_fix  -->  LEC/SEC
                                                                                  (D_fix = D_fix*  ?)
```

该任务采自真实 GitHub PR，要求 LLM 在大上下文里定位 bug、写出修复。

## 5. 关键公式

### 5.1 Round-Trip Reasoning 的形式定义

$$
A = f_\theta(D)
$$

$$
D' = f_\theta(A)
$$

$$
\text{s.t.} \quad D' \equiv D
$$

- `f_theta`：参数为 theta 的大语言模型。
- `D`：原始 RTL 设计。
- `A`：Step 1 生成的中间抽象（可能是自然语言、可执行代码或自由格式）。
- `D'`：Step 2 重建的 RTL。
- `equiv`：Cadence Conformal LEC / JasperGold SEC 判定的功能等价关系。
- 公式含义：模型必须先压缩、再重建，且两次调用都必须正确才能算 pass。

### 5.2 Spec Ratio 约束

$$
r = \frac{L(A)}{L(D)}
$$

$$
L(A) \leq r \times L(D), \quad r \in \{0.5, 1.0\}
$$

- `L(.)`：非注释字符数（non-comment characters）。
- `r`：spec ratio，控制中间抽象相对原 RTL 的长度比例。
- `r=0.5` 强制模型压缩到原设计一半以下，必须保留最核心语义；`r=1.0` 允许等长甚至略长。
- 注意：`A_NL-Diag` 和 `A_Code` 不在 prompt 中强制 `r`，而是测量后报告平均比值（Python ~0.9、C ~1.1）。

### 5.3 Masked-Content Reasoning 的形式定义

$$
A_B = f_\theta(D \setminus B)
$$

$$
B' = f_\theta(A_B,\ D \setminus B)
$$

$$
\text{s.t.} \quad D \setminus B \;+\; B' \;\equiv\; D
$$

- `B`：随机选中的被掩码代码块或子模块实例化。
- `D \setminus B`：把 `B` 替换为 `[MASKED]` 后的不完整 RTL。
- `A_B`：Step 1 生成的对 `B` 功能的简短自然语言描述。
- `B'`：Step 2 重建的被掩码代码。
- `+`：把 `B'` 拼回 `D \setminus B` 的对应位置。
- `equiv`：对完整结果 `(D \setminus B + B')` 与原始 `D` 做 LEC/SEC。

### 5.4 Repository-Issue Reasoning 的形式定义

$$
D_{\text{fix}} = f_\theta(R,\ I)
$$

$$
\text{s.t.} \quad D_{\text{fix}} \equiv D_{\text{fix}}^{\star}
$$

- `R`：完整仓库代码上下文。
- `I`：issue 评论（标题 + 正文）。
- `D_fix`：模型产出的修复版本。
- `D_fix_star`：开发者提交的 golden patch 修复版本。
- `equiv`：SEC 判定的功能等价。
- 简化变体：实验中还向模型额外提供 buggy 模块位置 `D_buggy`，让模型专注于 root-cause 而非 bug 定位。

### 5.5 任务 1 的可执行代码抽象 pass 率分解

$$
\text{pass}_{\text{code}} = \mathbb{I}[\text{ACode 编译通过} \wedge \text{与 D 周期匹配}]
$$

$$
\text{pass}_{\text{RTL}} = \mathbb{I}[D' \equiv D]
$$

- `I[.]`：指示函数（条件成立为 1，否则为 0）。
- `ACode`：中间 Python 或 C 代码抽象。
- `pass_code` 和 `pass_RTL` 是 Figure 10 中报告的两种独立指标，前者用 Synopsys VCS 仿真做 cycle-accurate I/O 匹配，后者用 Conformal LEC/SEC 判定。

### 5.6 TF-IDF 余弦相似度（用于过滤）

$$
\text{sim}(D_i,\ D_j) = \frac{\mathbf{v}_i \cdot \mathbf{v}_j}{\|\mathbf{v}_i\|_2 \, \|\mathbf{v}_j\|_2}
$$

- `v_i`：第 `i` 个设计用字符 4-gram TF-IDF 向量化后的向量。
- `||.||_2`：L2 范数。
- `sim(D_i, D_j) > 0.2` 的设计对被贪心剪枝。

## 7. 创新点

1. **规模突破（数据集层面）**：首次将经过形式等价校验的 RTL 评测数据推到 10,028 条，比 VerilogEval（156）、RTLLM（50）、CVDP（783）等大两个数量级以上；平均 94 LoC、最长 495 LoC，远超现有"单模块 <100 行"的简单模块。
2. **任务范式突破（评测协议层面）**：提出三个互补任务——Round-Trip Reasoning（自监督压缩-重建）、Masked-Content Reasoning（自监督掩码补全）、Repository-Issue Reasoning（真实仓库 bug 修复）——前者两个不依赖任何对齐标签，彻底打破"评测基准必须有 spec+RTL+testbench 三件套"的传统约束。
3. **形式等价验证基础设施**：用 Cadence Conformal LEC（组合）+ JasperGold SEC（时序）作为统一打分器，配合"代码自指验证"思路（设计与自身 elaborated 版本），实现了真正"无 testbench"的功能正确性评估。
4. **可解释的失败模式分类**：把错误划分为 Datapath / Control / Interface / Timing / Syntax 五类，并展示它们随任务类型和 LoC 桶的变化规律，为后续研究提供针对性优化方向。
5. **双切片设计**：patch-based slicing（10 个比例匹配的子集）和 source-based slicing（S1-S5），既支持"小成本可控实验"也支持"来源敏感分析"。
6. **揭示 NL 抽象的相对薄弱**：首次用实验数据说明：在 Round-Trip 上，可执行代码（Python/C）作为中间表示比纯自然语言更易恢复（52.1% vs 23.1%），挑战了"自然语言 spec 是 LLM 最自然形式"的常识。

## 9. 与芯片流程的关系

### 9.1 在前端 RTL 设计自动化版图中的位置

RTL-BenchLS 填补的是 **LLM 评测基础设施** 这一空白，位于"前端 RTL 设计"和"RTL 验证"两个阶段的交叉处：

```
[Spec 撰写] --> [RTL 设计] <-- LLM 评测基础设施 --> [RTL 验证]
                                       |
                                       v
                                  RTL-BenchLS
                                  (10k+ designs, 3 tasks)
```

- **上游**：它消费前序 LLM-for-RTL 工作（如 ChipGPT, RTLCoder, OriGen, AutoVCoder, RTLPP, MG-Verilog）提供的训练语料与方法，但剥离了"训练"环节，专注于"评测"。
- **下游**：评估结果直接指导 RTL 生成 agents（AutoChip, VerilogCoder, MAGE, ChipNeMo 等）的下一代优化方向。

### 9.2 与资料包其他论文的关系

- 相对 [RTLLM 论文深度讲解](../RTLLM/论文深度讲解_RTLLM.md) ：RTLLM 提供 50 条高质量 spec+RTL+testbench"三件套"，是 Round-Trip 实验在 Scenario 1/S2 上对比的标杆；RTL-BenchLS 用相同设计测同一模型，证明其 pass 率从 60-80% 跌至 10-50%。
- 相对 [VerilogEval 论文深度讲解](../VerilogEval/论文深度讲解_VerilogEval-v2.md) ：VerilogEval Human v2 是业界事实标准（156 designs，88% 已饱和）；RTL-BenchLS 提供的是"正交挑战"——更大设计 + 更难任务。
- 相对 [CVDP 论文深度讲解](../cvdp_benchmark/论文深度讲解.md) ：CVDP 把任务扩到 13 类（含 assertion / coverage / debug 等），但每类设计 < 200；RTL-BenchLS 选择"三任务 × 大数据"路线，对每任务给到数千到上万设计。
- 相对 [OriGen 论文深度讲解](../OriGen/论文深度讲解.md) 与 [AutoVCoder 论文深度讲解](../AutoVCoder/论文深度讲解.md) ：两篇论文都贡献了 LLM 生成的训练语料（S2、S3 数据来源），但其目标是"训练数据增广"；RTL-BenchLS 把这些语料"反向"用作测试集，加入形式等价过滤。
- 相对 [ChipGPT-V](../chipgptv/) 等多模态生成工作：RTL-BenchLS 纯文本（Verilog + 自然语言），不覆盖"图表→RTL"的多模态路径。
- 相对 [CodeV-R1](../CodeV-R1/) 等"round-trip 合成作为数据质量过滤"思路：CodeV-R1 用 round-trip 在 *训练* 阶段筛数据，RTL-BenchLS 把 round-trip 作为 *评测* 范式。

### 9.3 任务 3 在 EDA 流程中的工程意义

Task 3 直接对应硬件工程师日常工作中"读 issue → 跑 simulation → 定位 → 写 patch"的调试闭环。当前 12% 最佳成绩意味着 LLM 距"独立调试员"还差至少一个数量级。

## 10. 讨论与局限

### 10.1 讨论

1. **从 spec-to-RTL 到 reasoning+generation 的范式跃迁**：本文用"Round-Trip"实验证明，仅仅把"生成"换成"压缩+生成"的复合任务，就让所有 LLM 在 VerilogEval 上掉了 7-40 个百分点。这暗示 spec-to-RTL 的高分并不等同于"理解"——很多高分其实是"模式匹配"。
2. **抽象格式选择影响巨大**：`A_Code` > `A_NL-Diag` > `A_Free` > `A_NL` 的稳定性排序（前沿模型）揭示了"结构化中间表示"对 LLM 的友好性。可执行代码在 cycle-accurate 层面保留更多比特级语义，比纯自然语言更可重建。
3. **`A_Code` 与 `D'` 的 gap（Figure 10）**：即便中间 Python 编译失败或 I/O 不匹配，最终 RTL 重建仍可能通过 SEC——说明代码抽象对 LLM 而言更像是"结构脚手架"而非"严格功能规约"。这一观察可启发新的"多模态中间表示"研究。
4. **LoC 与 pass 率的非线性**：Task 1 中设计规模从 <30 LoC 到 200+ LoC 时 pass 率断崖式下跌，但 Task 3 全 LoC 区间都很低，提示两类瓶颈不同——前者是"信息密度+长上下文"，后者是"语义推理 + bug 定位"。
5. **形式等价 ≠ 真实等价**：LEC/SEC 验证的是综合后的网表等价，但 LLM 生成的 RTL 可能在仿真行为、综合面积、时序收敛上仍有差异；这是论文未覆盖的维度。

### 10.2 局限

1. **抽象格式偏少**：Task 1 仅考察 4 种中间表示，未覆盖波形（waveform）、FSM 图、SystemVerilog assertion 等硬件工程师常用表达。
2. **切片 1 即 420 条**：评估只在 patch 1 上做完整表格，patch 2-10 仅开源但不报告，可能引入 source-distribution 偏差。
3. **任务 3 数据规模小**：仅 108 条真实 issue-PR 对，统计显著性较弱，且 bug 类型偏重 PMP/CSR 类寄存器逻辑，缺少跨时钟域、复位策略等更难模式。
4. **缺少对超大规模 LLM 的分析**：用户给定的 8 个模型虽然前沿，但 GPT-5、Claude-4.6-Opus、Gemini-3-Pro 的具体版本/参数并未在原论文公开，是否使用 tool-use / agent 框架尚不清楚。
5. **未评估 EDA 工具协同**：任务 1 的 `A_Code` Python 抽象可通过"运行代码"获得功能正确的伪参考，但论文并未把这种"工具调用"纳入正式评分。
6. **没有覆盖 SystemVerilog 高级特性**：UVM、interface、class、package 等在 S1 真实仓库中占比极小（多数为 .v 而非 .sv），限制了 Task 3 的代表性。
7. **形式验证工具成本**：Cadence Conformal 与 JasperGold 是商业闭源工具，复现成本高；论文未提供开源等价物（如 SymbiYosys、Verilator + SBY）的替代方案。

## 12. 一分钟复述版

> "现有 RTL 评测基准（VerilogEval、RTLLM、CVDP…）规模太小、任务太单一，LLM 在 spec-to-RTL 上已经接近饱和（88%）。RTL-BenchLS 把这件事推到 10,028 条经过 LEC/SEC 形式等价校验的 Verilog 设计（平均 94 行、最长 495 行），并设计三个全新任务：① **Round-Trip Reasoning**——让 LLM 先压缩成中间抽象（A_NL 自然语言 / A_Code Python 或 C / A_NL-Diag 图表式 / A_Free 自由格式），再从抽象重建 RTL，功能等价即 pass——自监督、无需标签；② **Masked-Content Reasoning**——把设计中的一个 always/assign 块或子模块实例化掩码掉，让 LLM 先写自然语言描述、再补全代码；③ **Repository-Issue Reasoning**——给 LLM 真实 GitHub issue + 仓库上下文，让它修 bug（108 个 PR 对已筛选）。所有任务都用 Cadence Conformal LEC / JasperGold SEC 形式等价检查自动打分，不写 testbench。八个前沿 LLM（GPT-5/Claude-4.6-Opus/Gemini-3-Pro/DeepSeek-V3.2/Qwen3.5-397B/LLaMA-4-Maverick 等）的最佳成绩只有 ~23%（Round-Trip A_NL）/ ~28%（Masked-Content）/ ~12%（Repo-Issue），对比 VerilogEval 的 88% 形成巨大反差。结论：LLM 在硬件推理-生成一体化方向仍有巨大提升空间，RTL-BenchLS 为社区提供了可持续扩展的评测基座。开源仓库：https://github.com/hkust-zhiyao/RTL-BenchLS。"

## 附录 F：术语对照（中文-英文）

- 设计（design）：一段完整的 Verilog/SystemVerilog 模块。
- 抽象（abstract）：介于原 RTL 和重建 RTL 之间的中间表示（自然语言 / 代码 / 图表 / 自由格式）。
- 压缩比（spec ratio `r`）：抽象长度 / 原 RTL 长度。
- 形式等价（formal equivalence）：用 LEC/SEC 判定两份 RTL 在综合后网表层面等价。
- 自我验证（self-verification）：原设计与自身 elaborated 版本的等价检查。
- 自监督任务（self-supervised task）：无需外部标注、以原设计自身为 oracle 的任务。

## 附录 G：每个任务最常被引用的具体案例详解

### G.1 Case 1 详解：CRC-16 LFSR 设计上的 Round-Trip

原始 49 行 Verilog（节选关键 3 行）：

```verilog
lfsr[0]  <= data_in ^ lfsr[15];   // bit 0  XOR feedback
lfsr[5]  <= lfsr[4] ^ data_in ^ lfsr[15];   // bit 5  XOR feedback
lfsr[12] <= lfsr[11] ^ data_in ^ lfsr[15];  // bit 12 XOR feedback
```

**GPT-4o 失败抽象**（vague）：
> "When the enable signal is active and init is not, the LFSR updates its state based on the input data and its current state. Specifically, certain bits of the LFSR are updated using XOR operations involving the input data and the most significant bit of the LFSR."

缺点：未指定哪些 bit 用 XOR → Step 2 模型只能猜 → 无法通过 SEC。

**DeepSeek-v3.2 / Haiku-4.5 成功抽象**：
> "Specific bits (5 and 12) also incorporate additional XOR feedback ... bit 0 is computed as the XOR of data_in and bit 15 ..."

明确写出 bit 索引 → 重建 RTL 通过 SEC。

### G.2 Case 2 详解：8-bit 加法器溢出标志

被掩码的黄金一行：

```verilog
assign overflow = intermediate_carry[6] ^ carry;
```

此公式处理 ADD 和 SUB 两种路径：ADD 时 `carry` 为进位，SUB 时 `carry` 为借位的反。

**DeepSeek-v3.2 成功**：
- 描述：`Detects overflow using XOR logic intermediate_carry[6] ^ carry;`
- 重建：`assign overflow = intermediate_carry[6] ^ carry;` → SEC PASS

**GPT-4o 失败**：
- 描述：`Detects signed overflow condition`
- 重建：`(a[7] & b[7] & ~sum[7]) | (~a[7] & ~b[7] & sum[7])`（教科书符号位公式） → 在 SUB 路径失效 → SEC FAIL

教训：教科书"有符号溢出"公式并不能处理所有路径的 ALU overflow flag。

### G.3 Case 3 详解：lowRISC/ibex #1178 修复

Buggy 代码（4 行片段）：

```verilog
assign region_addr_mask[r][b] =
  (csr_pmp_cfg_i[r].mode != PMP_MODE_NAPOT) |
  ~&csr_pmp_addr_i[r][b-1:PMPGranularity+2];
```

Golden fix（一行）：

```verilog
- ~&csr_pmp_addr_i[r][b-1:PMPGranularity+2];
+ ~&csr_pmp_addr_i[r][b-1:PMPGranularity+1];
```

**Sonnet-4.5 / DeepSeek-v3.2**：恰好改同一行 → PASS
**LLaMA-3.3-70B**：改写为等价形式（同时改两个 +2 索引，但所有引用都同步调整） → PASS
**GPT-4o 失败**：把所有 +2 替换为 +1（5 处），破坏无关数组宽度 → FAIL
**Haiku-4.5 失败**：正确定位但加了 `if (PMPGranularity==0) begin ... end` 分支，结构差异过大 → FAIL

教训：在长上下文 + 多处同名数字字面量的场景下，"恰好只改一处"的精确性是当前 LLM 的核心短板。

## 附录 I：方法论选择的深层理由

1. **为什么用 LEC/SEC 而非 VCS 仿真**：仿真仅能验证"已采样输入"下的行为，等价性检查是数学证明。形式等价是功能正确性的"充分条件"，但工业界仍把 LEC/SEC 作为 sign-off 前的"必要条件"。
2. **为什么需要四种抽象格式**：自然语言是工程规范的主流；可执行代码保留 cycle-accurate 语义；图表风格贴近 RTL 设计文档；自由格式测试模型自我表达能力。多样性排除"过拟合到特定 prompt 风格"。
3. **为什么双切片**：patch-based 提供"小样本代表性"，source-based 提供"来源敏感性"，二者互补。
4. **为什么引入 `A_Free`**：避免 prompt 风格化导致的"训练分布偏差"，让模型自选最自然表达。
5. **为什么用低温度 0.2**：追求评估的"稳定性/可复现性"，避免随机性主导结果排序。
6. **为什么 Task 3 简化设置**：LLM 当前在"定位 + 推理 + 修复"上同时出错，无法区分错误来源；提供 `D_buggy` 后错误来源被隔离为"推理 + 修复"。
