## 1. 一句话定位

**CircuitWeave 不是把原理图图片和文本直接拼接喂给多模态 LLM 让它吐 RTL，而是先分别从原理图中抽取拓扑合同（topology contract，记录器件/连线/寄存器边界）、从文本中抽取行为合同（behavior contract，记录接口/位宽/时钟语义），显式融合为电路合同（circuit contract）并标注对应关系、缺失证据与冲突，最后仅以这个显式中间表示为条件生成可执行的 Verilog RTL。** 在 VerilogEval-Human 上 adapted Qwen3.5-4B 达到 pass@1 = 46.60%（相较同 checkpoint 纯文本提升 +8.46 个百分点），RTLLM 上达到 40.00%（+2pp）。核心主张：把"图里的拓扑"和"字里的行为"分开抽取再融合，比直接多模态解码更不容易让模型在互联正确时违反位宽、或在位宽正确时插错寄存器边界。

这句话里的五个技术承重点，后面逐一拆解：

1. **合同介导而非直接多模态解码** -- 在图文和 RTL 之间插入显式的结构化合同层。RTL 生成调用不接触原始图文，强制合同成为唯一的代码条件。
2. **源受限调用实现证据角色分离** -- topology 抽取只看图、behavior 抽取只看文字、fusion 只看两个合同、RTL 生成只看 fused contract。不是统计独立性假设，而是调用级信息隔离。
3. **显式冲突与缺失标注** -- fused contract 不只"合并"，还显式标注 supported / missing / conflict / unknown，让下游生成时明确知道不确定性在哪里。
4. **反向重建正则化** -- 从 reference RTL 反向预测合同字段，提供 self-supervised 辅助信号，不暴露 testbench 也不引入 EDA 奖励。
5. **受控 2x2 实验设计** -- 交叉 base/adapted checkpoint x text/text+image 四个条件，分别量化 adaptation 效果、加图效果、以及两者交互。

## 2. EDA 阶段映射 -- 跨域论文的特殊处理

CircuitWeave 的核心任务是从 **schematic（电路原理图）+ 自然语言规格** 生成 **Verilog RTL**。这与标准数字流程中以纯文本规格为起点的论文（如 VerilogCoder、MAGE）有本质区别：它的输入 schematic 源于模拟/混合信号设计传统，属于数字流程的"前站"资产。

### 2.1 为什么不能强制塞进 17 阶段

标准 17 阶段数字流程（参照 [芯片流程.md](../芯片流程.md)）的起点是 **① RTL 设计**——用 Verilog/VHDL 描述电路行为。但 CircuitWeave 的输入 schematic 本身比 RTL 更"靠前"：在传统设计实践中，schematic 是模拟工程师表达电路结构的主要方式，通常**在 RTL 编码之前**就存在。把 schematic 转成 RTL，本质上是将一种"前数字流程"的表示翻译为数字流程的入口格式。

因此，下面这张映射表区分了"CircuitWeave 直接覆盖的数字阶段"和"schematic 作为输入所跨越的域"。

### 2.2 阶段覆盖对照表

| 阶段 | 覆盖 | 说明 |
|------|:---:|------|
| **schematic 存在（前-①）** | ✅ **输入来源** | schematic 是模拟/混合信号设计的标准表示，在数字流程开始前就已存在。CircuitWeave 把它作为拓扑证据输入 |
| **① RTL 设计** | ✅ **核心输出** | CircuitWeave 的输出就是完整的 Verilog module，直接充当数字流程的起点 |
| **② RTL 功能仿真** | ✅ **验证手段** | 使用 Icarus Verilog（`iverilog` 编译 + `vvp` 仿真）+ 隐藏 testbench 判定候选 RTL 是否"可执行通过" |
| ③ 逻辑综合 | ❌ | 论文明确排除。生成的 RTL "能仿真通过"不等于"可综合且 PPA 合理" |
| ④ 门级仿真 | ❌ | 无 SDF 反标，看不到毛刺、建立/保持违例、X 传播 |
| ⑤ STA | ❌ | 不计算任何路径延迟 |
| ⑥ 形式验证 | ❌ | 不做 SAT/SMT 等价性证明 |
| ⑦ 布局规划 Floorplan | ❌ | — |
| ⑧ 标准单元摆放 Placement | ❌ | — |
| ⑨ CTS | ❌ | — |
| ⑩ 布线 Routing | ❌ | — |
| ⑪ 后仿真 | ❌ | 无 SPEF |
| ⑫ 物理验证 DRC + LVS | ❌ | — |
| ⑬ 签核 Signoff | ❌ | — |
| ⑭-⑰ 流片→制造→封装测试→芯片 | ❌ | — |

**覆盖率：2/17（① + ②）。** CircuitWeave 是一个跨域（模拟表示→数字入口）的 RTL 生成框架，在阶段 ①② 之间通过合同介导完成 schematic→RTL 的翻译。

### 2.3 跨域映射表：什么能映射、什么不能

由于 CircuitWeave 跨越了模拟 schematic 域和数字 RTL 域，很多概念不能一一对应。下表梳理了这种跨域关系：

| 概念维度 | 模拟 schematic 域 | CircuitWeave 的处理 | 数字 RTL 域 | 是否直接映射 |
|------|------|------|------|:---:|
| 结构表示 | 图形符号（晶体管/运放/电阻）+ 连线 | topology contract $z_v$ 提取器件、端口、连线、寄存器边界 | `module` + `wire` + `assign` + `always` | ✅ 间接（经合同序列化） |
| 行为描述 | 散落在文档/邮件/规格书中 | behavior contract $z_t$ 提取接口、位宽、时钟/复位语义 | 时钟沿行为、复位逻辑、组合逻辑功能 | ✅ 间接（经合同融合） |
| 层级结构 | 图纸上的 block symbol + 内部电路 | 通过合同字段"hierarchy"标注，但不展开子模块 | module 例化 + `generate` | ⚠️ 部分（论文限于单模块） |
| 数据通路 | 图纸上的加法器/乘法器符号 + 数据线 | datapath operators + dependencies 字段 | `+` `*` `<<` 等运算符 | ✅ |
| 状态机 | 图纸上的状态 bubble + 转移箭头 | state transitions 字段（$z_v$ 中的 sequential 组） | `case(state)` + `next_state` | ✅ |
| 时序约束 | 无（schematic 不表达时钟周期） | 来自 $z_t$ 的 clock/reset/latency 字段 | `@(posedge clk)` + 非阻塞赋值 | ✅（但只有语义级，无物理时序） |
| 电气特性 | 晶体管尺寸、偏置电压、负载电容 | 完全不涉及 | 无对应概念 | ❌ |
| 工艺信息 | 隐含在元件模型里（如 BSIM 模型参数） | 完全不涉及 | 标准单元库选择 | ❌ |
| 物理约束 | 版图面积估计、匹配要求 | 完全不涉及 | 面积/功耗约束 | ❌ |

> **关键洞察**：CircuitWeave 做的是从"结构可视但行为隐式"的 schematic 到"结构和行为都显式编码"的 RTL 的翻译。它不处理模拟域的电气/物理信息——这是合理的，因为翻译的目标是数字流程入口，而非模拟仿真或版图。但它确实丢失了 schematic 中可能隐含的物理设计意图（如匹配对、电流镜比例等），这些信息在 schematic 上可见但无法进入 RTL。

### 2.4 与同资料包 Weave、SINA 的域间定位

这三篇论文都在做 schematic / netlist / RTL 之间的转换，构成了一个"电路表示互转光谱"：

```
         schematic (图像/图形化表示)
              ▲                    │
              │ Weave              │ SINA
              │ (netlist→schematic) │ (schematic→netlist)
              │ 确定性算法          │ YOLO+GPT-4o pipeline
              │ 模拟域              │ 模拟域
              │                    ▼
         SPICE netlist          SPICE netlist
         (文本化连接关系)        (文本化连接关系)

                             CircuitWeave
                             (schematic+text→RTL)
                             LoRA-fine-tuned LLM
                             跨越模拟→数字域
                                   │
                                   ▼
                             Verilog RTL
                             (可综合的数字设计入口)
```

| 维度 | Weave | SINA | CircuitWeave |
|------|-------|------|--------------|
| 输入 | SPICE netlist（文本） | schematic 图像 | schematic 图像 + 文本规格 |
| 输出 | LTspice .asc 原理图 | SPICE netlist | Verilog RTL |
| 转换方向 | 文本→图像 | 图像→文本 | 多模态→可综合代码 |
| 电路域 | 模拟 | 模拟 | **跨越模拟表示→数字 RTL** |
| 方法范式 | 确定性算法（elkjs 图布局） | 检测+OCR+VLM pipeline | LoRA 微调多模态 LLM |
| 是否需要训练 | 否 | 部分（YOLO 微调） | 是（LoRA） |
| 正确性保证 | round-trip 连通性验证 | 图同构 + Ngspice 仿真 | Icarus 仿真 pass/fail |

CircuitWeave 的独特位置：它是三者中唯一跨越"模拟表示→数字流程"的工作，打通了"传统原理图设计资产→数字芯片流程入口"的自动化路径。代价是必须处理多模态对齐的困难（schematic 的拓扑信息 + 文本的行为约束），而 Weave 和 SINA 只需处理单一模态或单一域的转换。

## 3. 输入 / 输出

### 3.1 输入

CircuitWeave 的端到端输入包含两类模态和一种隐藏验证资产：

**(a) 自然语言规格（behavior evidence）$x_t$**

以 VerilogEval-Human 中典型的 FSM 任务为例：

```text
Module: fsm_example
Input: clk (1-bit), rst (1-bit), in (1-bit)
Output: out (1-bit)
Behavior: Implement a Mealy FSM with states S0, S1, S2.
  - From S0: if in=1 go to S1, else stay in S0
  - From S1: go to S2 unconditionally
  - From S2: if in=0 go to S0, else stay in S2
  - out = 1 only in state S2
```

**(b) 原理图图像（topology evidence）$x_v$**

由 Nano Banana 2（Gemini 3.1 Flash 图像版）根据上述文本描述**生成**的电路原理图。图像包含：状态寄存器、次态逻辑的组合云、输出逻辑、时钟和复位连接。关键：在论文实验设定中，schematic 是文本的"结构化视觉重述"而非独立来源——这是一个重要的实验局限（见第 10 节）。

**(c) 隐藏自检测试平台（testbench）$T$**

仅用于可执行资格判定，**不作为模型输入**。训练时用于筛选 executable-qualified packages，推理时用于判定候选 RTL 是否通过。格式：

```verilog
module tb();
    reg clk, rst, in;
    wire out_dut, out_ref;

    fsm_example dut(clk, rst, in, out_dut);
    RefModule  ref(clk, rst, in, out_ref);  // 参考模型，LLM 不可见

    always #5 clk = ~clk;  // 10ns 时钟周期

    initial begin
        // 随机激励序列
        rst = 1; #10; rst = 0;
        repeat(100) @(posedge clk) in = $random;
        // ...
    end

    // 逐拍比对
    always @(negedge clk)
        if (out_dut !== out_ref) errors <= errors + 1;

    final begin
        $display("Mismatches: %0d in %0d samples", errors, total_checks);
    end
endmodule
```

**(d) 数据包结构（训练时）**

每个训练 package 含 5 类 artifact：

| Artifact | 构造来源 | 角色 |
|------|------|------|
| Text 规格 | Web 收集的公开 Verilog 模块描述 | behavior contract $z_t$ 的数据源 |
| Schematic 图像 | Nano Banana 2 从 text 生成 | topology contract $z_v$ 的数据源 |
| Contract 记录 | Gemini 3 Flash 在源受限条件下构造 | $z_v$, $z_t$, fused $z$ 的训练 target |
| Reference RTL | Web 收集的原始 Verilog 模块 | $y$ 的训练 target；编译+仿真验证 |
| Testbench | GPT-5.5 生成的自检测试平台 | 隐藏 qualifier；与 RTL 一起经 Icarus 执行 |

共构造 5,000 个 executable-qualified packages，经 Icarus 编译+仿真门控保留（reference RTL + testbench 必须 elaborate、terminate、satisfy expected checks），训练/验证按 4,750/250 切分。

### 3.2 中间产物

**(a) Topology contract $z_v$（从 schematic 提取）**

固定 heading 的结构化文本记录，最小示例：

```text
<topology>
Components and Ports:
  - clk: input, 1-bit, clock signal
  - rst: input, 1-bit, reset signal
  - in: input, 1-bit, FSM input
  - out: output, 1-bit, FSM output, Z = Q
  - state_reg: 2-bit register, holds current state

Connectivity:
  - in -> next_state_logic
  - state_reg -> next_state_logic
  - next_state_logic -> state_reg
  - state_reg -> out (combinational)

Datapath Operators:
  - next_state_logic: combinational, depends on state_reg and in
  - out: combinational = state_reg

Register Boundaries:
  - state_reg: 2 D flip-flops, clocked by posedge clk, reset by rst

State Transitions:
  - S0(2'b00) -> S1(2'b01) when in=1
  - S1(2'b01) -> S2(2'b10) unconditional
  - S2(2'b10) -> S0(2'b00) when in=0

Unknown Evidence: none
</topology>
```

**(b) Behavior contract $z_t$（从文本提取）**

```text
<behavior>
Interface:
  - clk: input, 1-bit
  - rst: input, 1-bit
  - in: input, 1-bit
  - out: output, 1-bit

Clock/Reset:
  - clock: posedge clk
  - reset: posedge rst, asynchronous or synchronous: unknown

Function:
  - Mealy FSM with 3 states
  - S0 -> S1 when in=1, else S0
  - S1 -> S2 unconditionally
  - S2 -> S0 when in=0, else S2
  - out = 1 only in state S2

Latency: 1 cycle (Mealy output)

Corner Cases: reset behavior, all state transitions covered
</behavior>
```

**(c) Fused circuit contract $z$（融合产物）**

```text
<fused>
Correspondence:
  - Ports: clk (both), rst (both), in (both), out (both)
    -- Source: both; Status: supported
  - State encoding: 2-bit from topology, Mealy from behavior
    -- Source: both; Status: supported
  - Output logic: topology says Z=Q (combinational), behavior says out=1 in S2
    -- Source: both; Status: supported (consistent)
  - Reset polarity: topology says posedge, behavior says posedge
    -- Source: both; Status: supported

Missing Evidence:
  - Asynchronous vs synchronous reset: behavior says unknown
    -- Source: behavior; Status: missing in topology

Conflicts: none

RTL Constraints:
  - Use 2-bit state register with posedge clk and posedge rst
  - out must be combinational (assign) not registered
  - next_state_logic: combinational, cover all 3 states
</fused>
```

### 3.3 输出

**(a) 生成的 Verilog 模块 $y$**

以 `<answer> ... </answer>` 块包围。以 FSM 任务为例（text+image 条件）：

```verilog
module fsm_example (
    input  wire clk, rst,
    input  wire in,
    output reg  out
);
    reg [1:0] state, next_state;

    // 状态寄存器
    always @(posedge clk or posedge rst)
        if (rst) state <= 2'b00;
        else     state <= next_state;

    // 次态逻辑
    always @(*) begin
        next_state = state;
        case (state)
            2'b00: if (in) next_state = 2'b01;
            2'b01: next_state = 2'b10;
            2'b10: if (!in) next_state = 2'b00;
        endcase
    end

    // 输出逻辑 -- 关键：组合逻辑，Z=Q
    assign out = (state == 2'b10);
endmodule
```

**关键差异**：在 text-only 条件下，同一模型把 `out` 放在 `always @(posedge clk)` 块内用非阻塞赋值更新，导致输出使用 pre-edge 状态，产生一周期延迟。schematic 明确标注 $Z=Q$（输出等于当前状态），image-conditioned 候选用组合 `assign` 避免了该时序错误。见论文 Figure 2。

**(b) 可执行接受判定**

$$
A(y, T) = \mathbf{1}\left[E(y) \neq \bot \;\wedge\; \text{compile}(E(y), T) \;\wedge\; \text{simulate}(E(y), T)\right]
$$

$E(y)$ 从 `<answer>` 块提取完整 `module...endmodule`。提取失败、接口不匹配、编译错误、超时、仿真 mismatch 全部判 0。

### 4.2 核心模块逐个详解

#### 4.2.1 Backbone 与适配策略

- **基座模型**：Qwen3.5-4B 多模态 LLM（vision encoder + multimodal aligner + LLM decoder）
- **参数高效适配**：LoRA（Low-Rank Adaptation，低秩适配），rank=32，scaling factor=64，目标为 all-linear 层
- **冻结部分**：base weights、vision encoder、multimodal aligner 全部冻结
- **共享 decoder**：同一个 decoder 承担全部 5 个条件任务（topology contract 抽取、behavior contract 抽取、contract fusion、contract-conditioned RTL 生成、反向合同重建）

设计理由：冻结 vision encoder 和 aligner 意味着模型不重新学习"怎么看图"，而是重新学习"看图后怎么组织信息、怎么把组织好的信息翻译成 RTL"。这在数据量有限（4,750 个 packages）的前提下是合理的——视觉理解能力由预训练提供，适配只调整结构化输出能力。

#### 4.2.2 视觉编码器的角色

论文没有在视觉编码器侧做特殊设计。视觉编码器（Qwen3.5-4B 自带）将 schematic 图像编码为视觉 token，经 multimodal aligner 投影到 LLM token 空间。关键不在视觉编码器架构，而在 pipeline 设计：视觉特征仅用于生成 $z_v$（拓扑合同），不直接进入 RTL 解码。这是架构级的"证据隔离"，而非编码器级的专门优化。

这种设计巧妙地绕开了 schematic 图像理解的固有难点——拓扑等价性：同一电路的不同画法（拉伸、旋转、重新布线）在像素空间看起来完全不同，但在电气上等价。CNN/ViT 对空间布局敏感，而电路理解需要的是对"连接关系"敏感。CircuitWeave 通过将视觉理解转化为"生成结构化拓扑合同"的任务，把空间视觉问题约化为结构化文本生成问题。

#### 4.2.3 图结构信息如何注入模型

schematic 的拓扑信息通过结构化文本序列化注入模型，而非图神经网络：

1. schematic 图像 → vision encoder → 视觉 token
2. 视觉 token 经 decoder 在源受限条件下生成结构化拓扑合同 $z_v$（文本形式），固定 heading 包括：components and ports, connectivity, datapath operators, register boundaries, state transitions, internal dependencies, unknown evidence
3. $z_v$ 与 $z_t$ 融合为 $z$，共享实体对齐、独有约束保留、冲突显式标注
4. RTL decoder 只读 $z$ 的序列化文本——此时 schematic 的拓扑信息已经以结构化自然语言形式存在于 $z$ 中

为什么要这样做：直接让 LLM 同时看图和文本生成 RTL，模型可能"跟着图的连线走但忘了文本里的位宽"，或者"匹配了文本接口但在错误位置插入寄存器"。显式分离 + 融合阶段强制模型在生成代码前先厘清"哪些信息来自图、哪些来自文字、哪里矛盾"。

#### 4.2.4 合同融合策略

合同融合是 CircuitWeave 区别于简单多模态拼接的核心机制：

| 合同组 | 拓扑 $z_v$ 覆盖 | 行为 $z_t$ 覆盖 | 融合/反向重建处理 |
|--------|----------------|-----------------|-------------------|
| Interface | 可见引脚和连接 | 名称、方向、位宽 | $z$: 融合端口；$z_{\text{cov}}$: 端口声明 |
| Sequential | 寄存器、状态边沿 | 时钟、复位、延迟 | $z$: 融合状态/时序；$z_{\text{cov}}$: 事件控制 |
| Datapath | 算子、依赖关系 | 功能、corner cases | $z$: 融合操作；$z_{\text{cov}}$: 选定依赖 |
| Status | 可见或 unknown | 已陈述或 unknown | $z$: 保留来源/状态标记；$z_{\text{cov}}$: 省略 unknown/conflict |

融合的关键规则：
- 每个字段保留来源标注（来自 $z_v$ / 来自 $z_t$）
- unsupported 字段标 `unknown`
- 两边都有显式值但不一致时标 `conflict`（除非有明确优先级规则）
- 任何未解决的冲突在 $z$ 中保持显式

这种显式标注让模型在生成 RTL 时知道"哪些信息是确定的、哪些是缺失的、哪里需要谨慎"——而不是把不确定性隐藏在自由格式推理中。

#### 4.2.5 源受限调用的推理实现

推理阶段通过四次独立的 decoder 调用完成（见 Listing 1）：

```text
Contract phase:
  A. schematic only -> <topology> components; edges; operators; state </topology>
  B. text only -> <behavior> ports/widths; clock/reset; timing; function </behavior>
  C. z_v and z_t only -> <fused> correspondence; missing/conflict; RTL constraints </fused>

RTL phase:
  D. fused z only -> <answer> complete Verilog module </answer>
```

当图像缺失时（text-only 条件），$z_v$ 中以显式 `unknown` 字段替代视觉证据。这种设计确保模型不会在没有 schematic 时"脑补"拓扑信息——它明确知道拓扑信息缺失。

#### 4.2.6 源受限调用 vs 统计独立性

一个常见的误解：论文的源受限调用（source-restricted calls）声称"text 和 image 是独立的"。实际上，这是**调用级的信息隔离**（每个子任务只看到指定输入），而非统计独立性的声明——因为在论文设定中，schematic 本身就是从同一文本生成的。

论文原文明确指出："Source restriction denotes this call-level input constraint, not statistical independence between the modalities."（3.1 节末尾）

#### 4.2.7 训练策略与五项损失

在 4,750 个 packages 上使用 teacher forcing 训练，五项损失共享 decoder 参数：

1. $\mathcal{L}_{\text{topo}}$：从 schematic $x_v$ 预测 topology contract $z_v$
2. $\mathcal{L}_{\text{behavior}}$：从 text $x_t$ 预测 behavior contract $z_t$
3. $\mathcal{L}_{\text{align}}$：从 $z_v$, $z_t$ 预测 fused contract $z$（含 correspondence/status 字段）
4. $\mathcal{L}_{\text{RTL}}$：从 fused $z$ 预测 reference RTL $y$
5. $\mathcal{L}_{\text{cons}}$：从 reference RTL $y$ 反向重建 $z_{\text{cov}}$（$z$ 的确定性投影）

$z_{\text{cov}}$ 的定义：$z_{\text{cov}} = P_{\text{cov}}(z)$ 是 $z$ 的确定性投影。它保留端口声明、寄存器/状态元素、时钟/复位事件控制、显式数据通路算子与依赖，省略 unknown/conflict 值以及超出反向任务范围的行为需求（延迟、corner-case 行为、完整功能等价性）。

**Teacher-forcing / inference gap**：训练时 RTL 生成任务接收的是 reference fused contract $z$（ground truth），推理时接收的是模型自己预测的 $z$。这是一个需要注意的 gap——如果合同阶段的预测质量差，RTL 阶段的生成也会受影响。

### 4.3 模块职责矩阵

| 模块 | 输入 | 输出 | 所用模型 | 是否需训练 |
|------|------|------|------|:---:|
| Topology 抽取 | schematic $x_v$ | $z_v$ 文本 | shared decoder (Qwen3.5-4B + LoRA) | ✅ |
| Behavior 抽取 | text $x_t$ | $z_t$ 文本 | shared decoder | ✅ |
| Contract 融合 | $z_v$, $z_t$ | fused $z$ 文本 | shared decoder | ✅ |
| RTL 生成 | fused $z$ | Verilog module $y$ | shared decoder | ✅ |
| 反向重建 | reference $y$ | $z_{\text{cov}}$ 文本 | shared decoder | ✅（仅训练） |
| 候选提取 $E(y)$ | decoder 输出 | `module...endmodule` | 确定性正则匹配 | ❌ |
| 可执行判定 | $E(y)$, testbench $T$ | pass/fail | Icarus Verilog | ❌ |

## 5. 关键公式

### 5.1 推理图分解（Eq. 1）

$$
p_\theta(z_v, z_t, z, y \mid x_v, x_t) = p_\theta(z_v \mid x_v) \; p_\theta(z_t \mid x_t) \; p_\theta(z \mid z_v, z_t) \; p_\theta(y \mid z)
$$

- $x_v$：schematic 图像（topology evidence）
- $x_t$：文本规格（behavior evidence）
- $z_v$：topology contract——从图中提取的结构化记录（器件、连线、寄存器边界、状态转移）
- $z_t$：behavior contract——从文本中提取的结构化记录（接口、位宽、时钟语义、功能）
- $z$：fused circuit contract——融合 $z_v$ 与 $z_t$、标注对应关系与冲突的中间表示
- $y$：生成的 Verilog RTL 模块
- $p_\theta$：以 $\theta$ 为参数的条件概率（共享 decoder）

**工程直觉**：这个因式分解不是数学恒等式，而是**推理阶段的调用约束设计**。它声明了：topology 知识只能从 schematic 来、behavior 知识只能从 text 来、融合只能操作两个合同、RTL 只能从 fused contract 来。任何试图"偷看"原始输入的行为都被这个结构阻止。

**为什么这么设计**：在直接多模态解码中，模型可能在任何时候混合图文特征。如果模型"跟着图的连线走但忘了文本里的位宽"，不仅错误发生了，而且无法追溯错误来源。源受限因式分解使得：如果 RTL 位宽错了，你可以追溯是 (a) behavior contract 写错位宽、(b) fusion 覆盖了正确位宽、(c) RTL decoder 忽略了合同位宽——三者之一，而非一个黑箱。

### 5.2 边际化形式（Eq. 2）

$$
p_\theta(y \mid x_t, x_v) = \sum_{z_v, z_t, z} p_\theta(y \mid z) \; p_\theta(z \mid z_v, z_t) \; p_\theta(z_v \mid x_v) \; p_\theta(z_t \mid x_t)
$$

- 推理时不枚举所有中间合同，而是按四次独立 decoder 调用沿因式分解路径执行
- 这个公式定义了理论上的边际分布，实际推理用 argmax 近似

### 5.3 完整训练目标（Eq. 3）

$$
\mathcal{L} = \mathcal{L}_{\text{topo}} + \mathcal{L}_{\text{behavior}} + \mathcal{L}_{\text{RTL}} + \lambda \mathcal{L}_{\text{align}} + \mu \mathcal{L}_{\text{cons}}
$$

- $\mathcal{L}_{\text{topo}}$：从 schematic 预测 topology contract 的 token 级交叉熵损失（按监督 token 数归一化）
- $\mathcal{L}_{\text{behavior}}$：从 text 预测 behavior contract 的 token 级交叉熵损失（归一化同前）
- $\mathcal{L}_{\text{RTL}}$：从 fused contract 生成 reference RTL 的 token 级交叉熵损失（归一化同前）
- $\mathcal{L}_{\text{align}}$：监督融合记录（含 correspondence 和 status 字段）的交叉熵，乘以系数 $\lambda$
- $\mathcal{L}_{\text{cons}}$：从 reference RTL 反向重建 $z_{\text{cov}}$ 的交叉熵，乘以系数 $\mu$
- $\lambda, \mu$：论文未公开具体数值的权重系数

**工程直觉**：$\mathcal{L}_{\text{cons}}$ 的作用往往被误解。它不是 EDA 奖励信号，也不形式化验证 candidate 与 contract 的一致性。它通过共享参数间接正则化 decoder——让 decoder 学会"RTL 和合同是互译的"。这在理论上帮助模型在推理时从自己预测的 $z$ 生成更一致的 RTL，因为参数已经被训练为保持 contract-RTL 之间的双向映射。

**为什么这么设计**：五项损失共享 decoder 参数是关键。如果每项损失有独立参数，$\mathcal{L}_{\text{cons}}$ 的正则化效应就无法传递到 RTL 生成任务。共享参数迫使 decoder 的内部表示同时编码"看图写拓扑""看字写行为""融合两份合同""合同转 RTL""RTL 转回合同"五种映射——这种多任务压力在理论上促进了解纠缠的表示学习。

### 5.4 可执行接受判定（Eq. 4）

$$
A(y, T) = \mathbf{1}\left[E(y) \neq \bot \;\wedge\; \text{compile}(E(y), T) \;\wedge\; \text{simulate}(E(y), T)\right]
$$

- $E(y)$：从 decoder 输出中提取完整 `module...endmodule` 的确定性函数，提取失败返回 $\bot$
- $\text{compile}(E(y), T)$：通过 Icarus Verilog（`iverilog`）编译 $E(y)$ 与 testbench $T$ 的布尔结果
- $\text{simulate}(E(y), T)$：通过 `vvp` 仿真已编译的二进制，检查是否通过 testbench 所有断言的布尔结果
- $\mathbf{1}[\cdot]$：指示函数，所有条件同时满足才为 1

**工程直觉**：这个判定是一个"全有或全无"的二值门控。它不区分"接近通过"和"完全错误"——一个信号有一处位宽错误和整个模块不工作，在 $A(y,T)$ 下都是 0。这种严格的判定方式适用于 benchmark 评测（明确的对错边界），但不提供改进方向（不知道错在哪、差多远）。

## 7. 创新点

### 创新点 1：合同介导而非直接多模态解码

**已有方法**：将图文拼接送入 decoder 直接生成 RTL（如 VeriGround 等）。模型在内部混合处理图文特征，无法区分哪些约束来自文本、哪些来自图像。

**CircuitWeave 的做法**：在图文和 RTL 之间插入显式的结构化合同层。RTL 生成调用不接触原始图文——这意味着模型无法在生成代码时"偷看"原始输入来弥补合同阶段的遗漏。合同成为唯一的代码条件，实现了调用级的证据分离。

**工程价值**：可审计。如果 RTL 错了，你可以沿着合同链追溯根因是哪个阶段出了问题，而不是面对一个端到端黑箱。

### 创新点 2：源受限调用实现证据角色分离

topology 抽取只看图、behavior 抽取只看文字、fusion 只看两个合同、RTL 生成只看 fused contract。这不是统计独立性假设，而是调用级的信息隔离——防止模型在融合前就混合两模态的原始特征，从而确保 $z$ 中的 "missing/conflict" 标注是诚实的而非事后补救。

### 创新点 3：显式冲突与缺失标注

fused contract 不只是"合并后的规格"，它显式序列化：哪些信息两边都有且一致（supported）、哪些只有单边（标注来源 + 另一边 missing）、哪些两边都有但矛盾（conflict）。这比"让 LLM 自己看着办"更可审计——下游 RTL 生成可以明确知道不确定性在哪里。

与自由格式推理的关键区别：自由格式的 "both text and schematic indicate X" 看起来像确认，但模型可能没有真正比对过两者。显式标注强制模型做出判断。

### 创新点 4：反向重建正则化

$\mathcal{L}_{\text{cons}}$ 从 reference RTL 反向预测合同字段。这是一种 self-supervised 辅助信号：如果合同字段可以从 RTL 可靠地恢复，说明合同确实编码了 RTL 中的关键结构化信息。这不同于 VeriReason/VeriRL 的仿真反馈 RL——不暴露 testbench，不引入 EDA 奖励，纯训练时正则化。

### 创新点 5：5,000 个 executable-qualified 多模态 packages

数据集不仅包含图文-RTL 三元组，还包含结构化合同记录和可执行 testbench。与 RTLCoder-27K（纯文本 SFT）、CraftRTL（非图像结构化任务）、CodeV（多层次摘要）等资源的区别：每个 package 同时包含 generated schematic、modality-specific + fused contracts、reference RTL、executable testbench。

数据构造 pipeline：Nano Banana 2 生成 schematic、Gemini 3 Flash 承担 contract agent（源受限条件下分别构造 $z_v$、$z_t$、fused $z$）、GPT-5.5 生成 self-checking testbench、Icarus Verilog 执行可执行资格检查。

### 创新点 6：受控 2x2 实验设计

交叉 base/adapted checkpoint x text/text+image 共 4 个受控条件，共享采样预算、解码温度、提取过程和 EDA harness。使得 "adaptation 的效果" 和 "加图的效果" 以及两者的交互可以分别量化，而非笼统地报一个 text+image 分数。这在 RTL generation 文献中是比较严谨的实验设计。

## 9. 与芯片流程的关系

### 9.1 在全流程中的位置

CircuitWeave 的输出是可综合的 Verilog module，直接定位到阶段 ① RTL 设计。验证手段使用阶段 ② RTL 功能仿真（Icarus Verilog + testbench）。论文明确排除 ③ 逻辑综合及之后的所有阶段。

```text
  schematic（模拟域资产） + 文本规格
             │
             ▼
    CircuitWeave（合同介导翻译）
             │
             ▼
    ① RTL 设计  ← 输出 Verilog module
             │
             ▼
    ② RTL 功能仿真  ← 验证手段（Icarus + testbench）
             │
             ▼  ⚠️ CircuitWeave 到此为止
    ③ 逻辑综合 → ④ 门级仿真 → ⑤ STA → ... → ⑰ 芯片
```

### 9.2 解决什么痛点

**核心痛点**：大量 legacy 电路 IP 以 schematic（原理图）形式存在，没有对应的 RTL 源代码。在模拟/混合信号设计传统中，工程师习惯用原理图表达电路结构。当这些设计需要集成到数字 SoC 流程中时，必须人工把原理图"翻译"成 Verilog RTL。

翻译过程费时且易错：
- 人工看图写 RTL 需要同时理解拓扑（谁连谁、寄存器边界在哪）和行为（时钟频率、复位极性、接口协议）
- 原理图只管拓扑，行为约束散落在文档/邮件/规格书里
- 拓扑等价性挑战：原理图拉伸、重排、不同画法不改变电路含义，但对图像理解模型来说可能完全不同

CircuitWeave 试图让模型自动完成"图 + 文字 → RTL"的翻译，用合同机制显式分离拓扑证据和行为证据。

### 9.3 "仿真通过"和"能做成芯片"之间隔着什么

CircuitWeave 的 "executable acceptance" 只保证：给定 testbench 的全部激励下，候选 RTL 的输出与 reference RTL 一致。以下每一类问题都会在 ② 通过后被后续阶段拦截：

1. **可综合性**（阶段 ③ 逻辑综合）：`initial` 块赋初值、组合逻辑环、意外 latch、不完整敏感列表——仿真器全都能跑，综合器直接拒绝。
2. **时序正确性**（阶段 ④ 门级仿真 + ⑤ STA）：阻塞/非阻塞赋值混用、组合逻辑路径过深导致 setup violation——零延迟 RTL 仿真完全看不出。
3. **PPA 优化**（阶段 ③-⑩）：CircuitWeave 完全不优化面积、频率、功耗。一段面积翻 3 倍但功能正确的 RTL，在 CircuitWeave 眼里是满分。
4. **覆盖率**（阶段 ② 的补全）：Icarus 通过只保证 reference RTL 与 testbench 在已执行行为上一致，不保证 testbench 覆盖了所有 corner cases。弱 testbench 可能接受功能错误的 RTL。
5. **物理实现**（阶段 ⑦-⑬）：完全不涉及布局布线、时钟树、功耗分析、IR drop 等物理设计问题。

## 10. 讨论与局限

### 10.1 论文自述的局限

1. **Schematic 是"生成的"而非"独立的"**：实验中的 schematic 是从同一文本描述生成的"结构化视觉重述"，不构成独立的多源证据。在真实场景中，原理图可能是另一个工程师独立绘制的，图文之间可能存在真实的矛盾和互补——当前实验无法验证这种场景下的合同融合效果。

2. **未做视觉 grounding 控制实验**：没有 blank-image、mismatched-image、identifier-anonymization 或 topology-perturbed 控制条件。正面的 image delta（adapted 条件下 +8.46 pp）只能说明"加图有帮助"，不能证明模型真正"看懂了图"——可能只是在利用图像为 token 分布提供某种正则化。论文本身在 Section 6 中将此列为 validity threat。

3. **单模型单规模**：仅验证 Qwen3.5-4B 一个 4B checkpoint。结论向更大模型（7B/14B/72B）或其他架构的外推性未知。

4. **仿真级评估边界**：Icarus 通过只保证 reference RTL 与 testbench 在已执行行为上一致，不保证覆盖率、跨模态保真度或语义正确性。弱 testbench 可能接受错误 RTL。

5. **受控设计无法分离各组件贡献**：$\mathcal{L}_{\text{align}}$、$\mathcal{L}_{\text{cons}}$、topology/behavior 分支、LoRA 的独立作用未被消融实验剥离。46.60% 这个数字里有多大比例来自"合同机制"、多大比例来自"就是多了一个训练信号"，论文无法回答。

6. **统计稳健性有限**：结果是单次训练/采样的 aggregate 点估计，无跨 seed 重复、无任务级置信区间。对于 RTLLM 上 +2pp 这种小 delta，统计显著性尤其不确定。

7. **数据 provenance 风险**：基于网络收集的公开 Verilog 模块，存在许可、benchmark 重叠（数据泄露到 VerilogEval/RTLLM 评估集的可能性）等威胁。论文将 benchmark 重叠列为 validity threat（Section 3.2 末尾）。

8. **不覆盖后端**：无综合、STA、面积/功耗/时序、物理设计、形式验证。

### 10.2 额外分析

9. **合同质量的代理风险**：合同是由 Gemini 3 Flash 在源受限条件下生成的，其质量没有被人工审计或形式化验证。如果合同本身有错——比如 topology contract 把两个串联寄存器错误标注为一个寄存器边界——那么 fusion 和 RTL 生成都会在错误的基础上工作。$\mathcal{L}_{\text{cons}}$（反向重建）能部分缓解这个问题（因为 reference RTL 是 ground truth），但不能完全消除。

10. **多模态难点的本质**：schematic 图像理解比一般图像理解难，核心原因是拓扑等价性——电路的电气含义由连接关系决定，与空间布局无关。CNN/ViT 对空间布局敏感，而电路理解需要的是对"连接关系"敏感。CircuitWeave 通过将视觉理解转化为"生成结构化拓扑合同"的任务，把空间视觉问题约化为结构化文本生成问题——这绕开了直接让 vision encoder 学习拓扑不变性的困难，但也引入了 contract agent 的代理风险。

11. **image delta 的方向不一致**（Table 5）：在 VerilogEval-Human pass@10 上 adapted image delta 仅 +2.57 pp 且交互项为负（−0.63 pp），在 RTLLM pass@5/10 上交互项也为负。这说明"加图"的效果在更多采样预算下未必持续放大——当模型可以多试几次（pass@10）时，text-only 条件通过"多采样碰运气"已经能覆盖大部分可解任务，image 的边际贡献自然缩小。

12. **因式分解的设计选择未消融**：Eq. 1 中的因式分解顺序（先 topology + behavior 并行出合同，再 fusion，再 RTL）是一种特定的设计选择。论文没有比较其他可能的分解顺序——例如先 fuse 图文特征再出合同、或者让 RTL decoder 同时看到合同和原始输入的"软约束"版本。

## 12. 一分钟复述版

CircuitWeave（北航，arXiv 2026）是一个合同介导的多模态 RTL 生成框架。核心思路三招：

1. **合同分离**：不从图文直接解码 RTL，而是先从 schematic 抽取 topology contract（器件/连线/寄存器边界）、从 text 抽取 behavior contract（接口/位宽/时钟语义），由 Gemini 3 Flash 在源受限条件下构造——"看图的不看字，看字的不看图"。

2. **显式融合**：把两份合同融合为 circuit contract，标注 supported / missing / conflict / unknown——不隐式掩盖证据缺口。RTL decoder 只看这份 fused contract，不接触原始图文。训练时加一项反向重建损失（从 RTL 恢复合同字段）做正则化。

3. **受控 2x2 验证**：交叉 base/adapted checkpoint x text/text+image 四个条件，分离 adaptation 和 image 的各自贡献。Adapted Qwen3.5-4B（LoRA, rank=32, 4,750 packages）在 VerilogEval-Human 上 pass@1 = 46.60%（vs text-only 38.14%，+8.46 pp），RTLLM 上 40.00%（+2 pp）。Base checkpoint 加图反而下降 −3.01 pp——说明不经适配的多模态模型无法利用 schematic。

边界：schematic 是生成的而非独立来源，未做视觉 grounding 控制实验，仅 4B 单模型单规模，仿真级评估不覆盖综合/时序/PPA，合同质量未经人工审计，image delta 在高 cutoff 上方向不一致，单次训练/采样的点估计缺乏统计显著性。
