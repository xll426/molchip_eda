## 1. 一句话定位

**FVEval 是首个面向数字硬件形式化验证（FV）的 LLM 综合评测基准，包含 3 个子任务、约 475 个测试用例（NL2SVA-Human 79 + NL2SVA-Machine 300 + Design2SVA 192），通过 Cadence Jasper 的工业级形式等价性判定，首次给出「功能正确 vs 仅语法正确」的可量化差距——在 NL2SVA-Human 上 GPT-4o 仅 0.456 功能 pass@1，0.911 语法 pass@1；并证明仅靠 BLEU 相似度与功能正确性几乎不相关（相关系数 0.056）。**

这句话里的 6 个承重点，后面逐一拆解：

1. **三任务分级评测体系** — NL2SVA-Human（79 道题，工业专家 testbench + NL→SVA）、NL2SVA-Machine（300 道题，合成 NL↔SVA 配对、覆盖各种时序算子）、Design2SVA（192 道题，96 pipeline + 96 FSM 的纯 RTL→SVA）。三个任务从「有规格辅助」逐步升级到「无规格、仅凭 RTL 推断关键属性」，完整映射工业 FV 工程师的认知链条。
2. **形式等价性度量** — 不沿用软件代码生成的 BLEU/CodeBLEU 字符串相似度，而是借助 Cadence 在 Jasper 中定制实现的 assert-to-assert equivalence checking，给出「完全等价 / 蕴含-部分等价 / 失败」三态判据，把 BLEU 与功能等价性的相关性量化到 0.056（GPT-4o）/0.093（Llama-3.1-70B）。
3. **pass@k 而非 pass@1** — 引入 best-of-5（NL2SVA-Human）或 best-of-5 + nucleus 采样（Design2SVA）以逼近 LLM-agent 工作流。结果显示 gpt-4o 在 Design2SVA 的 FSM 子集上 functional pass@5 从 pass@1 的 0.373 跃升到 0.900，pass@k 拉开 0.5 以上差距。
4. **语法正确 ≠ 功能正确** — 在所有模型上，syntax pass@1 与 functional pass@1 普遍存在 0.2~0.5 的差距，最差的 Llama-3-8B 仅 0.063 functional vs 0.747 syntax。这意味着即使生成可编译 SVA，半数以上语义与专家答案不匹配。
5. **算子幻觉** — Llama-3.1-70B 凭空捏造 `eventually(...)` 算子；多数模型会出现 `s_eventually`、`strong`、`$onehot0` 等算子的语义错配——根源是 SVA 词表与 LLM 训练语料的错位。
6. **开放工程化基线** — 公开 benchmark + 评测脚本 + prompt 模板 + Jasper 等价检查接入指南。GPT-4o、Gemini-1.5-pro/flash、Llama-3/3.1（8B/70B）、Mixtral-8x22B 在三任务上结果均给出，构成可复现的横向基线。

## 2. EDA 阶段映射（①-⑰）

参照 [芯片流程.md](../芯片流程.md) 的 17 阶段标准编号。FVEval 定位于硬件形式化验证环节。

| 阶段 | 覆盖 | 说明 |
|------|:---:|------|
| **① RTL 设计** | ✅ **核心** | Design2SVA 直接从 RTL 推导待验证属性；NL2SVA-Human/Machine 隐含 RTL 在 testbench 中作为信号上下文 |
| **② RTL 功能仿真** | ❌ | 不涉及基于激励的 testbench 仿真，但等价性检查依赖 Jasper 的形式化遍历 |
| ③ 逻辑综合 | ❌ | 不涉及门级网表 |
| ④ 门级仿真 | ❌ | 不涉及 |
| ⑤ STA（静态时序分析） | ❌ | 不涉及时序收敛 |
| **⑥ 形式验证** | ✅ **核心** | FVEval 的本职——SVA 形式属性生成 + Jasper 等价性证明。属于「属性生成」而非「等价性检查」本身 |
| ⑦ 布局规划 | ❌ | 不涉及 |
| ⑧ 标准单元摆放 | ❌ | 不涉及 |
| ⑨ 时钟树综合 | ❌ | 不涉及 |
| ⑩ 布线 | ❌ | 不涉及 |
| ⑪ 后仿真 | ❌ | 不涉及 |
| ⑫ 物理验证 | ❌ | 不涉及 |
| ⑬ 签核 | ❌ | 不涉及 |
| ⑭ 流片 | ❌ | 不涉及 |
| ⑮ 制造 | ❌ | 不涉及 |
| ⑯ 封装 + 测试 | ❌ | 不涉及 |
| ⑰ 芯片到手 | ❌ | 不涉及 |

**覆盖率：2/17。** FVEval 集中在 ① RTL 设计 与 ⑥ 形式验证 两个阶段——前者是 Design2SVA 的输入来源，后者是 NL2SVA-* 的输出目标与评测手段。它不涉及综合、时序、布局布线等物理实现链，也不做仿真驱动的覆盖率闭合，是「形式属性自动化撰写」的专用基准。

> ⚠️ **最容易被误读的边界**：FVEval 评测的「正确」= Jasper 形式证明模型输出的 SVA 与专家写的 SVA 等价（或蕴含）。这并不等于「属性对 RTL 真的成立」——若专家答案本身有 bug，benchmark 也跟着错。此外，pass@5 提升 0.5 不代表工程部署可用——best-of-N 仍需外部 verifier 做 N 次等价检查，时钟周期与算力成本对工业场景并不友好。

## 3. 输入 / 输出

### 3.1 输入

#### 3.1.1 NL2SVA-Human（工业专家 testbench + 自然语言规格）

输入 = 一段 SystemVerilog 测试台（去除原 assertions 的版本） + 一段自然语言断言描述。

```verilog
// arbiter_rr_tb.sv（节选）
module arbiter_rr_tb (
  input clk,
  input tb_reset,
  input [3:0] tb_req,
  input [3:0] tb_gnt,
  input busy
);
  // ... 内部信号建模、状态机 ...
endmodule
```

```text
Question: Create a SVA assertion that checks:
whether starvation occurs, i.e. check that each request
from client is eventually granted.
```

#### 3.1.2 NL2SVA-Machine（合成 NL↔SVA 配对）

输入 = 一段纯文字化的时序逻辑描述，**不含任何 RTL**。

```text
Question: Create a SVA assertion that checks:
If sig_G and sig_J are both true, then two clock cycles later,
sig_G must have an odd number of 1's and all bits of sig_B must be 1.
```

Reference SVA：
```systemverilog
assert property(@(posedge clk)
  (sig_G && sig_J)
    |-> ##2 ((^sig_G === 1'b1) && &sig_B)
);
```

#### 3.1.3 Design2SVA（参数化合成的 pipeline + FSM RTL）

输入 = 一段 RTL（pipeline 或 FSM）+ 测试台头（含端口定义和 reset 信号） + 提问。

```text
Question: generate a single SVA assertion for the given design RTL
that is most important to verify. If necessary, produce any extra
code, including wires, registers, and their assignments.
```

### 3.2 中间产物

**LLM 响应**（按 prompt 要求包裹在 `systemverilog` 围栏中）：

```systemverilog
// NL2SVA-Human — GPT-4o on arbiter starvation
assert property (@(posedge clk) disable iff (tb_reset)
  (tb_req && !busy) |-> tb_gnt
);
```

对于 Design2SVA，LLM 还需自行生成辅助 wires/registers：

```systemverilog
// Design2SVA — GPT-4o on FSM test instance
wire [FSM_WIDTH-1:0] next_state_tb;
assign next_state_tb = (fsm_out == S0) ? S2 :
 (fsm_out == S1) ? S3 :
 (fsm_out == S2) ? ((in_D || in_C) == 'd0) ? S0 : (in_C <= 'd1) != in_A) ? S1 : S3 :
 (fsm_out == S3) ? S1 : '0;
assert property (@(posedge clk) disable iff (reset_)
  (fsm_out == next_state_tb)
);
```

**评估中间态**：Jasper 的 `prove`/`assume` 输出、`assert_equivalent` 内置函数的 PASS/FAIL 标记、SBY（SymbiYosys）风格的反例路径。

### 3.3 输出

输出 = **四项指标**（NL2SVA-* 三个表头：Syntax / Func. / Partial Func. / BLEU；Design2SVA：Syntax@1/5、Func.@1/5）。

| Benchmark | 总题数 | 来源 | 覆盖算子 / 模块类型 |
|-----------|:------:|------|----------------------|
| NL2SVA-Human | **79** | 工业 testbench 抽取 | 1R1W FIFO（20）、Multi-Port FIFO（6）、Arbiter（37）、FSM（4）、Counter（5）、RAM（7），共 13 个 testbench 变体 |
| NL2SVA-Machine | **300** | 自动合成 + LLM 反向写 NL + LLM 评判 + 人工终审 | 各种 SVA 时序算子的随机采样 |
| Design2SVA-Pipeline | **96** | 参数化生成 | 算术流水线 |
| Design2SVA-FSM | **96** | 参数化生成 | 有限状态机 |
| **合计** | **571** | — | — |

<!-- 修正：原文 Section A.1 Table 6 显示 NL2SVA-Human 共 79 个 assertions / 13 个 testbench 变体；Section 3.4 给出 Design2SVA 每类 96 个，pipeline+FSM 共 192；Section 3.3 给出 NL2SVA-Machine 共 300 个。合计 79+300+192=571，不是 475。 -->

末态产物对使用者而言是「LLM 在该任务上的功能/语法 pass@1 数字」+「Jasper 形式证明日志」，可作为新 prompt 工程或微调方案的对照基线。

### 4.1 整体 Pipeline

### 4.2 核心模块逐个详解

#### A. NL2SVA-Human 题目集（Section 3.2）

- **来源**：从 13 个工业 testbench 变体（1R1W FIFO、Multi-Port FIFO、Arbiter、FSM、Counter、RAM）抽取自然语言→SVA 配对。
- **关键设计**：
  - 题目分布非均匀：Arbiter 占 37 题、FIFO 共 26 题。反映了工业中「Arbiter 是出错最多的子模块」的经验。
  - 每道题提供「去除原 assertion 但保留内部信号建模」的 testbench——保证 LLM 只能访问已建模的 wires/state，不能凭空假设 `fifo_empty` 这种内部信号存在。
- **最小可运行例子（1R1W FIFO no-underflow）**：
  ```text
  Question: Create a SVA assertion that checks:
  that the FIFO does not underflow, assuming no bypass.
  Use the signals 'rd_pop' and 'fifo_empty'.
  ```
  ```systemverilog
  asrt: assert property (@(posedge clk) disable iff (tb_reset)
    (fifo_empty && rd_pop) !== 1'b1
  );
  ```

#### B. NL2SVA-Machine 合成管线（Section 3.3）

四步生成：

1. **随机 SVA 生成**：在 SVA 算子集合中随机采样（`&&`、`||`、`|->`、`##N`、`|=>`、`$countones`、`^`、`s_eventually`...）。
2. **NL 反写**：GPT-4o（temperature=1.0）根据 SVA 写出 NL 描述。
3. **Critic 评判**：GPT-4-turbo（temperature=0.0）评估 NL 是否准确反映 SVA 语义；若失败，重试步骤 2。
4. **人工终审**：作者手工抽检后定稿 300 道题。

> 这种「SVA → NL → LLM 校验 → 人工」的设计保证了「答案（SVA）+ 问题（NL）」双向一致——避免因 NL 描述模糊导致 LLM 看似错、实则对的争议。

#### C. Design2SVA 参数化 RTL 生成器（Section 3.4）

两类 RTL：

| 类别 | 控制参数 | 工业对应场景 |
|------|---------|---------------|
| **算术流水线** | #execution units / pipeline depth / bit width / 组合逻辑复杂度 | 数据完整性、forward propagation |
| **FSM** | #states / #transitions / pipeline depth / bit width / 状态转移逻辑复杂度 | cache controller、memory interface 等控制逻辑 |

每个 RTL 都附一份「自动生成的 testbench harness」（只含端口 + reset 信号），LLM 在此 harness 上写 SVA。

#### D. 形式等价性检查（Jasper 内置）

论文核心方法学贡献。Cadence 在 Jasper 中定制实现：

```
assert_equivalent(LLM_generated_SVA, expert_SVA) →
    PASS         (双向蕴含成立)
    IMPLY_FORWARD / IMPLY_BACKWARD  (单向蕴含 = partial pass)
    FAIL
```

这比单纯字符串匹配的优势：

- `(a && b) !== 1'b1` 与 `!(a && b)` 是字符串不同的 SVA，但形式等价；
- `wr_push |-> ##[1:$] rd_pop` 与 `wr_push |-> strong(##[0:$] rd_pop)` 不等价（Jasper 给出 FAIL），但 BLEU 分数可能接近。

#### E. BLEU 对照实验（Figure 6）

- 用标准 n-gram BLEU 度量 LLM 输出 vs 专家答案。
- 散点图 + 相关系数：GPT-4o 0.0563、Llama-3.1-70B 0.0926——几乎不相关。
- 结论：BLEU 不能替代形式等价性评测。

#### F. 评测协议（Section 4.1）

- **NL2SVA-Human**：zero-shot greedy decoding 为主，pass@1 报告（Table 1）+ 部分 best-of-5（Table 2）。
- **NL2SVA-Machine**：zero-shot + 3-shot（固定 3 个 ICL example，Figure 15）对比，Table 3 + Table 4。
- **Design2SVA**：nucleus sampling (top p=0.95, t=0.8)，pass@k 用 Chen et al. (2021) [6] 的 unbiased estimator，k ∈ {1,3,5}。

## 5. 关键公式

论文本身没有大量形式化公式（基准工作重心在数据集 + 评测）。下面给出口径定义（Section 3.2、3.3、3.4 中的指标）：

### 5.1 语法通过率

$$
\text{SyntaxPassRate} = \frac{n_{\text{syntax\_pass}}}{n_{\text{total}}}
$$

- $n_{\text{syntax\_pass}}$：通过 Jasper syntax check 的 LLM 响应数
- $n_{\text{total}}$：测试集大小

### 5.2 功能等价通过率（完全等价）

$$
\text{FuncPassRate} = \frac{n_{\text{equiv}}}{n_{\text{total}}}
$$

- $n_{\text{equiv}}$：`assert_equivalent` 返回 FULL EQUIV 的响应数
- 这是论文最严格的功能正确性指标

### 5.3 部分功能等价通过率

$$
\text{PartialFuncPassRate} = \frac{n_{\text{equiv}} + n_{\text{imply}}}{n_{\text{total}}}
$$

- $n_{\text{imply}}$：IMPLY_FORWARD ∪ IMPLY_BACKWARD 的响应数（单向蕴含）
- 体现「答案非完全等价但语义有重叠」的宽容判据

### 5.4 Pass@k（Design2SVA 的 unbiased estimator）

$$
\text{pass@k} = 1 - \frac{\binom{n - c}{k}}{\binom{n}{k}}
$$

- $n$：每个问题采样的响应数（论文 n=5）
- $c$：通过 functional 判据的响应数
- $k$：top-k 中的 k 值
- 该无偏估计器来自 Chen et al. 2021 [6]，已在 HumanEval / MBPP 等代码基准广泛使用

**工程直觉**：当 $c=0$ 时 pass@k=0；当 $c=n$（全部正确）时 pass@k=1；公式避免了对每道题「枚举 k 阶子集再求并」的计算爆炸。

### 5.5 BLEU 相似度

$$
\text{BLEU} = \text{BP} \cdot \exp\left(\sum_{n=1}^{N} w_n \log p_n\right)
$$

- $\text{BP}$：brevity penalty（短输出惩罚）
- $p_n$：n-gram 精度
- $w_n$：权重，常取 $1/N$（均匀加权）
- 论文用此度量与功能等价做相关性散点图（图 6），证明其不足以替代形式证明

## 6. 训练与实验设置

### 6.1 是否需要训练

**不需要训练任何模型。** FVEval 是纯评测框架，LLM 用现成的指令微调版本：

| 模型 | 提供方 | 版本 / 时间 |
|------|--------|------------|
| GPT-4o | OpenAI | gpt-4o-0513（2024-05 端点） |
| GPT-4-turbo | OpenAI | gpt-4-0125-preview（仅 generation / critic） |
| Gemini-1.5-pro | Google | -001（2024-05 端点） |
| Gemini-1.5-flash | Google | -001 |
| Llama-3-8B / 70B | Meta | instruction-tuned（vLLM 推理） |
| Llama-3.1-8B / 70B | Meta | instruction-tuned |
| Mixtral-8x22B-Instruct-v0.1 | Mistral | sparse MoE，约 39B active params |

评测平台：vLLM（PagedAttention 高吞吐推理框架）；温度 / 采样策略：见各子节。

### 6.2 实验设置

- **Greedy decoding**：T=0，主要表格（Table 1/3）。
- **3-shot ICL**：固定 3 个 hand-crafted examples（NL2SVA-Machine，Figure 15），所有测试题用同一组 example。
- **Sampling for pass@k**：nucleus sampling, top p=0.95, T=0.8（Design2SVA）；T=1.0 (NL2SVA-Machine 的 multi-response 实验，文中未明示温度，但 follow Table 4 的推断)。
- **判定工具**：Cadence Jasper（商用）+ Cadence 定制的 `assert_equivalent` 内置函数。

### 6.3 关键实验结果

#### 6.3.1 NL2SVA-Human (Table 1, zero-shot greedy)

## 7. 创新点

### 创新点 1：首个面向 LLM 的硬件形式化验证综合基准

**区别**：此前工作 [34, 11, 27, 41] 评测 LLM 在 FV 任务上的能力时，只用 ≤20 个 hand-pick 实例，且不区分任务类型。FVEval 一次性提供 79 + 300 + 192 = 571 道题，分三个子任务（NL→SVA-专家驱动 / NL→SVA-算子压力测试 / RTL→SVA-无规格），覆盖工业 FV 工作流的核心环节。

**为什么这样设计**：FV 工程师的认知链条是「读规格 → 写属性 → 验证」，FVEval 三任务与此一一对应——NL2SVA-Human 测「理解 NL 规格」，NL2SVA-Machine 测「掌握 SVA 算子」，Design2SVA 测「从 RTL 推断关键属性」。这种「任务分级」让基准能精细诊断 LLM 短板（是语言理解差，还是 SVA 语法差，还是 RTL 语义推断差）。

### 创新点 2：Jasper-based 形式等价性判据 + Partial Equivalence 三态分类

**区别**：此前工作要么用 BLEU/CodeBLEU（字符串相似度），要么用仿真器跑 testbench（基于激励的功能正确性）。FVEval 借助 Cadence Jasper 的形式化引擎 + 定制的 `assert_equivalent`，给出「FULL EQUIV / IMPLY / FAIL」三态，且论文首次量化 BLEU 与形式等价性的相关系数仅 0.056（GPT-4o）/ 0.093（Llama-3.1-70B）。

**为什么这么设计**：SVA 是线性时序逻辑（LTL）的子集，两个 SVA 字符串不同但形式等价是常态（`(a && b) !== 1'b1` 与 `!(a && b)`）。BLEU 把这种「语义等价字符串差异」误判为失败。形式等价 + 三态分类则保留了「LLM 输出虽与专家不同但更宽/更严」的语义信息（Partial Pass）——这对工业场景更宽容、更可用。

### 创新点 3：参数化 RTL 生成器实现可扩展的 Design2SVA

**区别**：OpenTitan 等开源 RTL 「设计正确但不适合 LLM 评测」（单模块属于 SoC 子模块，上下文依赖太大）。FVEval 用参数化生成器（pipeline 控制参数 + FSM 控制参数）批量产出测试实例，自动生成 testbench harness，并保证每个 RTL 都「存在可证 true 的形式属性」。

**为什么这么设计**：形式验证要求 RTL 是「可被证明的」——不能有死锁、未初始化状态。参数化生成器可以保证每条 RTL 都遵循「good FSM / 数据对齐流水线」等可证明范式，同时通过调节控制参数实现难度梯度（简单 FSM 几十行 → 复杂 pipeline 上万行）。

### 创新点 4：首次量化「语法正确 vs 功能正确」的系统性差距

**区别**：软件代码生成（HumanEval/MBPP）通常 syntax pass@1 ≈ functional pass@1，因为代码执行能反馈错误。SVA 不会执行——LLM 写错 `s_eventually` 还是 `eventually`，Jasper 都会给出 syntax pass。FVEval 第一次用工业数据（8 个模型 × 571 道题）实证：在 SVA 任务上 syntax - functional 差距普遍 ≥0.2，最严重达 0.684（Llama-3-8B: 0.747 - 0.063）。

**为什么这么重要**：揭示了 LLM 在「形式语言」任务上的特有失败模式——不是不会写语法，而是「语法幻觉」（hallucinate valid-looking but non-existent operators）。这与软件代码生成的失败模式根本不同。

## 9. 与芯片流程的关系

### 9.1 在全流程中的位置

FVEval 横跨 ① RTL 设计与 ⑥ 形式验证两个阶段，但定位侧重于「属性自动撰写」而非「等价性检查」本身。

```text
① RTL 设计 ─────┐
                 │  Design2SVA:
                 │  从 RTL 推断关键属性
                 │
⑥ 形式验证 ◀────┘
                 │
                 │  NL2SVA-Human:
                 │  从 NL spec + 工业 TB 写 SVA
                 │
                 │  NL2SVA-Machine:
                 │  从 NL spec（无 RTL）写 SVA
                 │
                 ▼
            评测 Jasper 等价性
```

### 9.2 「评测通过」到「工程可用」的鸿沟

FVEval 评测 GPT-4o NL2SVA-Human Func. pass@1 = 0.456，已经是该任务最高水平。但这到「工业 FV 工程师能放心用」还差：

1. **专家答案的覆盖率偏差**：基准测试集中的 79 道 NL2SVA-Human 题来自「NL 描述清晰、专家答案明确」的子集——工业规格往往含糊、答案多样（同一 NL 可以写出多个语义不等但都「合理」的 SVA）。换言之，FVEval 测的是「LLM 是否匹配专家答案」，不是「LLM 是否写出工业可接受的 SVA」。
2. **最佳答案是「部分等价」而非「完全等价」**：GPT-4o 在 0.582 Partial Func. vs 0.456 Func.——这意味着 12.6% 的「pass」是因 LLM 答案比专家更宽（如 `wr_push |-> ##[1:$] rd_pop` 比 `wr_push |-> strong(##[0:$] rd_pop)` 弱，但两者都「合理」）。工业部署时这种「更宽」可能掩盖 bug。
3. **缺乏 corner-case 与 boundary-condition**：基准不测 reset 行为、跨时钟域、未初始化寄存器等真实工程痛点；这些恰是 FV 工程师日常关注的。
4. **pass@5 提升不直接转化为可用性**：best-of-5 需要 5 次 Jasper 证明，每次工业级 RTL 的证明耗时从分钟到小时不等——5×开销不可忽视。
5. **RTL→SVA 的 Design2SVA 仅限 pipeline+FSM**：不测缓存一致性协议、总线仲裁握手、AXI/CHI 等工业接口——这些才是真实设计的主要 FV 场景。

## 10. 讨论与局限

### 10.1 论文自述的局限

1. **设计风格覆盖不足**：Design2SVA 仅 pipeline + FSM 两类，未覆盖缓存协议、总线、AXI/CHI、跨时钟域等真实工业设计。
2. **未探索 prompt 工程与结构化推理**：未系统测试 CoT、ToT、ReAct 等 prompt 策略对 SVA 生成的影响；也未接入外部 symbolic solver 做 neurosymbolic 增强。
3. **单轮评测，无 agentic 闭环**：评测是单次 LLM 调用 + Jasper 验证，不涉及「失败重试 + 反馈」的 agent 框架。
4. **专家答案可能不唯一**：论文承认部分 NL 描述存在 ambiguity，对应的 SVA 可能有多个「都合理」的写法——Partial Pass 在这里成为必要的容忍机制。

### 10.2 代码/复现层面的问题

1. **Jasper 是商用工具**：评测依赖 Cadence Jasper 的许可证，学术用户难以直接复现「形式等价」指标。这是评测基准工程化的最大门槛。
2. **NL2SVA-Machine 的 LLM-as-critic 依赖**：合成阶段的「critic」是 GPT-4-turbo——若该版本停止服务或 API 变更，整个生成管线需重跑。
3. **vLLM 版本依赖**：开源模型推理依赖 vLLM，但具体版本（论文写 [24] Kwon et al. 2023）未明示 commit，复现时 PagedAttention 配置可能影响采样一致性。
4. **nucleus sampling 参数隐含**：Design2SVA 的 Table 5 用 top-p=0.95 + T=0.8，但 NL2SVA-Machine 的 Table 4 multi-response 实验温度未明确写出——需查代码确认。

### 10.3 本资料包的批判性分析

1. **测试集「自顶向下」的偏差**：NL2SVA-Human 的 13 个 testbench 来自 NVIDIA 内部工程经验，并非随机抽样；Arbiter 占 37 题、FIFO 占 26 题——这种「Arbiter 偏多」恰好匹配 NVIDIA GPU 设计的痛点，但放到 CPU/网络芯片领域就不一定合适。
2. **pass@5 的工程化误解**：论文展示 pass@5 比 pass@1 提升 0.5（FSM Func.@1→@5: 0.373→0.900），但 pass@5 意味着 5 次 Jasper 证明——单次工业 RTL 证明 10 分钟级，5×成本 50 分钟。论文未讨论「在算力预算内 LLM agent 是否仍有优势」。
3. **Functional Pass 的语义陷阱**：Partial Pass 包含「IMPLY_FORWARD / IMPLY_BACKWARD」两种——前者是 LLM 答案蕴含专家答案（更宽），后者是专家答案蕴含 LLM 答案（更严）。这两种「部分正确」在工程上意义不同：更宽的 LLM 答案可能放过 bug，更严的可能误报。但论文把它们合并为 Partial Func.，未分开统计。
4. **评测协议对开源模型不友好**：开源模型（Llama-3-8B）的 context window 8K，对 Design2SVA 复杂 RTL（>16K token）直接被排除——这让「开源 vs 闭源」对比天然偏向前者。但论文的结论是「GPT-4o 在简单题上领先，开源在复杂题上有时被截断」——这种截断本身是工业部署的隐性障碍。
5. **缺乏 RTL-only 的 NL2SVA-Machine 变体**：NL2SVA-Machine 故意去掉了 RTL（仅 NL spec），是为了纯测 LLM 的「SVA 算子掌握度」。但这意味着 LLM 无法利用 RTL 中的信号名做交叉验证——工业场景中 NL spec 往往配合 RTL 看，剥离开来不够真实。

## 12. 一分钟复述版

1. **问题**：硬件形式验证（FV）需要工程师手动写 SVA 断言，成本高。LLM 有望自动化，但缺乏「覆盖工业全场景、能用形式等价性度量」的评测基准——既有工作仅用 ≤20 题，且依赖 BLEU 这类「字符串相似度」判据，与功能正确性几乎不相关（相关系数 0.056）。

2. **方法**：FVEval = 3 子任务 × 571 题 × Jasper 形式等价性评测。NL2SVA-Human（79 题，工业 TB + NL spec）、NL2SVA-Machine（300 题，参数化合成 NL↔SVA 配对）、Design2SVA（192 题，参数化生成 pipeline+FSM RTL）。评测 8 个 LLM（GPT-4o、Gemini-1.5-pro/flash、Llama-3/3.1-8B/70B、Mixtral-8x22B），报告 Syntax / Func. / Partial Func. / BLEU 四指标及 pass@k。

3. **结果**：GPT-4o 在 NL2SVA-Human 取得 0.911 Syntax / 0.456 Func. / 0.582 Partial Func.，是所有模型最高。BLEU 与功能等价性几乎不相关（GPT-4o 0.056）。Design2SVA 的 FSM 子集 pass@5 提升显著（GPT-4o: 0.373→0.900）——best-of-N 是 FSM 任务的有效策略，但 pipeline 提升有限。所有模型「syntax - functional」差距 ≥ 0.2，暴露 SVA 算子幻觉（`eventually`、`s_eventually`、`strong` 等）。

4. **意义**：首个「工业规模 + 形式等价性」评测框架，为后续 LLM-for-FV 工作（prompt 工程、领域微调、agent 框架）提供统一基线。

5. **局限**：(1) 评测依赖 Jasper 商用 license，学术门槛高；(2) Design2SVA 仅覆盖 pipeline+FSM，未覆盖工业协议/总线/缓存；(3) pass@5 提升在算力预算下未必工程化；(4) 测试集分布偏 NVIDIA GPU 设计场景，跨领域适用性待验证；(5) 未探索 prompt 工程与 neurosymbolic 增强。
