## 1. 一句话定位

**SpecLoop 是第一个把「形式等价检查（Formal Equivalence Checking, FEC）」当成 reward 信号塞进 RTL→自然语言规格文档（spec）生成闭环的智能体（agentic）框架**——它在每轮让同一个 LLM 既当「spec 作者」又当「spec 的 RTL 读者」，再让 Yosys EQY 用 SAT 后端在深度 10 内对两份 RTL 做穷尽等价证明；不通过就把「哪个信号、哪个时刻值不一样」连同 reconstructor 的根因分析（spec inaccuracy / spec ambiguity / reconstruction limitation）回喂给 spec 生成器，最多 2 轮 retry。在 VerilogEval 与 RTLLM 上，把 6 个 LLM 的 RR-Score 平均拉高约 +0.06，**DeepSeek-V3.1 在 VerilogEval 上从 0.865 推到 0.940，GLM-4.6 在 RTLLM 上从 0.813 推到 0.880**——这是该论文给出的核心数字。

这句话里有 4 个承重点，后面各章节逐一拆解：

1. **方向反转（RTL→Spec）** — 大多数 AI4EDA 论文解决「spec→RTL」或「RTL→RTL」；SpecLoop 切到「RTL→Spec」，瞄准的是文档维护/理解这一长期被忽略的痛点。
2. **重建式反馈循环（reconstruction-and-check）** — 把 Huang et al. (arXiv:2512.00045) 的「重建可逆性」当 RL 的 reward 用，但这里换成形式等价检查（不是仿真），所以是 exhaustive semantics-level 的反馈。
3. **形式等价检查（FEC）+ LLM 自我诊断的串联** — 4 类错误（E.1~E.4）× 2 类反馈通道（编译错→reconstructor、对抗样本→spec generator）× 「信息隐藏」原则（不回传 FEC log 给 reconstructor 防止作弊）。
4. **同模型双角色 + 模型无关** — 同一个 LLM 既写 spec 又重建 RTL（避免给 reconstructor 加外挂能力），并且不需要 fine-tune——直接用 OpenRouter 调用 6 个开源/闭源 LLM。

## 2. EDA 阶段映射（①-⑰）

参照 [芯片流程](../芯片流程.md) 的 17 阶段标准编号。SpecLoop 跨越了流程上完全相反的两个节点——**① RTL 设计（核心入口）** 和 **⑥ 形式验证（核心闭环）**——它在 EDA 时间轴上的位置是「RTL 设计已完成，但下游综合/布局都还没开始」这一档口。

| 阶段 | 覆盖 | 说明 |
|------|:---:|------|
| ① RTL 设计 | ✅ **核心** | 接收已有 RTL（自然来或 LLM 生成）作为输入，输出自然语言功能规格文档，是整篇论文的「对象」与「产物」所在阶段 |
| ② RTL 功能仿真 | ✅ | 用于 RR-Score 评估——reconstructor 输出的 RTL 在 testbench 上跑通才算 RR=1，论文把这当作 ground-truth proxy |
| ③ 逻辑综合 | ❌ | 不涉及——spec 描述的是行为意图，不指定门级实现 |
| ④ 门级仿真 | ❌ | 不涉及 |
| ⑤ STA | ❌ | 不涉及——spec 是功能层面，不关心时序 |
| **⑥ 形式验证** | ✅ **核心** | Yosys EQY（SAT 后端、深度 10）做 original vs reconstructed RTL 的穷尽等价证明，是反馈循环的 oracle |
| ⑦ 布局规划 | ❌ | 不涉及 |
| ⑧ 标准单元摆放 | ❌ | 不涉及 |
| ⑨ 时钟树综合 | ❌ | 不涉及 |
| ⑩ 布线 | ❌ | 不涉及 |
| ⑪ 后仿真 | ❌ | 不涉及 |
| ⑫ 物理验证（DRC+LVS） | ❌ | 不涉及 |
| ⑬ 签核 | ❌ | 不涉及 |
| ⑭-⑰ 流片→制造→封装测试→芯片到手 | ❌ | 不涉及 |

**覆盖率：2/17。** SpecLoop 切入点是 RTL 已写完、文档还没写的「中间地带」，与传统 spec→RTL 路线方向相反。

> ⚠️ 最容易被误读的边界：SpecLoop 的「验证」是**形式等价证明**（mathematical proof over all inputs），不是仿真通过（testbench sampling）；并且它只比对两份 RTL 的等价性，不验证 spec 自身的「物理可实现性」「功耗」「时序」「工艺约束」。换句话说——**SpecLoop 不替你回答「这个 spec 写得好不好」**，它只回答「这份 spec 详细到是否能让一个独立 LLM 重构出与原 RTL 等价的代码」。

## 3. 输入 / 输出

### 3.1 输入

**(1) 原始 RTL 代码**（任何合法可综合的 Verilog module）：

```verilog
// 论文 Figure 4 给的「同步复位 0~999 计数器」
module TopModule (input clk,
                  input reset,
                  output reg [9:0] q);
    always @(posedge clk)
        if (reset || q == 999) q <= 0;
        else                   q <= q + 1;
endmodule
```

**(2) 任务 prompt**（spec generator 第一轮）：固定模板，3 段式（详见 §4.2）。

**(3) 原始 RTL 经过同一个 LLM 重构后得到的 RTL**，第三轮起还会收到 **[REPORT_START]...[REPORT_END]** 形式的 verifier 反馈块。

> SpecLoop 不吃 testbench，只吃 RTL。这与它的「反向文档化」定位一致。

### 3.2 中间产物

**(a) 第一轮的候选 spec**（结构化文本，含 `[SPEC_START]...[SPEC_END]` 标记）：

```text
[SPEC_START]
Summary:
  This module implements a 10-bit up-counter that counts from 0 to 999
  and then wraps around. It supports a synchronous reset that clears
  the counter on the next clock edge when asserted.
Module Name: TopModule
Inputs:
  clk (1-bit): Clock signal, positive edge triggered.
  reset (1-bit): Synchronous reset; takes effect on next rising edge.
Outputs:
  q (10-bit): Counter output.
Detailed Functional Description:
  On every rising edge of clk: if reset is high or q == 999 then q <= 0;
  else q <= q + 1.
Clocking and Reset Behavior:
  Clock: posedge clk. Reset: Synchronous.
Notes:
  Counter wraps at 999.
[SPEC_END]
```

**(b) 重构的 RTL**（第二个 LLM 调用产物）：

```verilog
module TopModule (
    input  wire       clk,
    input  wire       reset,
    output reg [9:0]  q
);
    always @(posedge clk) begin
        if (reset || (q == 10'd999)) q <= 10'd0;
        else                          q <= q + 1'b1;
    end
endmodule
```

**(c) Verifier 报告**（结构化文本块，下一轮直接喂给 spec generator）：

```text
Spec Verification [pass/fail].
# Reconstruction RTL:
...(the reconstructed module above)...
# Logs of equivalent-checking tool:
Mismatched Signal: t=11 sig=q
rtl_reconstruct: 0000000000
rtl_original:    0000001010
```

### 3.3 输出

**最终 spec 文档**——与 §3.2 (a) 同构，但保证通过 FEC 闭环验证或达到 retry 上限。该 spec 在外部评测（RR-Score）里被 GPT-5 Codex 重新读回去，构造 RTL，跑 testbench——**通过率就是 RR-Score**。

**端到端 walkthrough 一句话**：第 0 轮，原始 Verilog → LLM 写出「异步复位」假 spec → reconstructor 编出带 `posedge clk or posedge reset` 的 RTL → EQY 在 t=11 抓到 q 值不匹配 → 回喂 → 第 1 轮 LLM 把 reset 改成同步 → 通过。RR-Score 提升可观察。

## 4. 方法与架构

### 4.1 整体 Pipeline（对应论文 Figure 1）

```text
┌─────────────────────────────────────── SpecLoop ───────────────────────────────────────┐
│                                                                                        │
│   ┌─────────────┐                                                                        │
│   │  Original   │                                                                        │
│   │     RTL     │                                                                        │
│   └──────┬──────┘                                                                        │
│          │                                                                              │
│          ▼                                                                              │
│   ┌─────────────────────┐                                                                │
│   │  Spec Generator     │   同一 LLM（model-agnostic，OpenRouter 调用）                  │
│   │  (multi-step 3 段)  │   ① 分析 RTL → ② 写结构化 spec → ③ 自检                      │
│   └──────┬──────────────┘                                                                │
│          │  candidate spec                                                              │
│          ▼                                                                              │
│   ┌─────────────────────┐         ┌─────────────────────┐                                │
│   │  RTL Reconstructor  │ ──────► │  Compiler (iverilog)│──► [E.2] feed back here        │
│   │   (same LLM)        │ ◄────── │  if compile fails   │                                │
│   └──────┬──────────────┘         └─────────────────────┘                                │
│          │  reconstructed RTL (compilable)                                               │

│          │  pass/fail + 可能的 counterexample                                            │
│          ▼                                                                              │
│   ┌─────────────────────┐         retry ≤ 2，总共 3 次 spec 生成                       │

│   │   (in next-round    │    E.4 → 回喂「inconclusive」让 spec 改                       │
│   │    prompt)          │    E.1 → 直接停（原始 RTL 不合法）                          │
│   └─────────────────────┘                                                                │

└────────────────────────────────────────────────────────────────────────────────────────┘
```

**Figure 对应关系**：外圈 = 论文 Figure 1(a)「SpecLoop 主循环」；内圈右半 = Figure 1(b)「spec verifier 子循环」。

### 4.2 Spec Generator（核心创新点之一）

论文改编自 Huang et al. (2025) 的多步推理 prompt，强制 3 段式：

| 阶段 | 内容 | 目的 |
|------|------|------|
| Stage 1 | Internal Analysis | 分析 signal 定义、数据依赖、seq vs comb、FSM/计数器、时钟/复位 |
| Stage 2 | Structured Spec Output | 强制结构：Summary / Module Name / Inputs / Outputs / Detailed Functional Description / Clocking & Reset / Notes，外加 `[SPEC_START]...[SPEC_END]` 包裹 |
| Stage 3 | Self-Reflection | 自我一致性检查：每个 I/O 是否在 RTL 里、每个 output 是否在描述里、reset/clock 是否识别正确 |

**第二轮起换成 refinement prompt**（论文 Figure 2 右半）：3 步——(1) 总结 verifier 报告 (2) 对每个 mismatch 归因（spec inaccuracy / spec ambiguity / reconstruction limitation） (3) 决策（哪种错就改哪种字段；如果全错在 reconstructor，原样不动 spec 并停）。

### 4.3 RTL Reconstructor（验证回路的「逆向引擎」）

- 严格「**用同一个 LLM**」做 spec→RTL 的重建——论文明确声明这是为了剥离「再加一个更强的模型」对实验的混淆（§IV.A）。
- 重建失败分两层：
  - 编译失败 → 直接喂编译错给 reconstructor（**唯一例外**：此处允许回传「工具信号」给 reconstructor，因为编译错不泄漏原 RTL 语义——见 §III.C 的「信息隐藏」原则）。
  - FEC 失败 → **不允许**把 FEC log 回传给 reconstructor，否则 reconstructor 会从 log 里「偷看」原始 RTL（log 里的 mismatched signal 名、波形值就是 RTL 的 sub-piece），等于绕过 spec。
- reconstructor retry budget = 2（与 spec generator 同），**总计最多 3 轮 + 3 次重构**。

### 4.4 Formal Equivalence Checker（oracle）

- 工具：**Yosys EQY**（YosysHQ 出品，论文引用 [23]）。
- 配置：**SAT 后端 + depth bound = 10**——depth bound 是 EQY 的关键旋钮，限制它展开多少 cycle 的 unrolling，超出即返回 INCONCLUSIVE。
- 错误分类表（论文 Table II 完整版）：

| 错误类型 | 含义 | 给 Reconstructor | 给 Spec Generator |
|---------|------|------------------|------------------|
| **E.1** | 原始 RTL 不能被 EQY 解析/综合 | — | **停**（这种 case 无法被反馈循环改进） |
| **E.2** | 重构的 RTL 编译不过 | 用编译错再重建 | 用尽 retry budget 后，把编译错送给 spec |
| **E.3** | 两者**功能不等价**（有 counterexample） | 再重构一次（同 budget） | 用尽 budget 后，把 counterexample 送给 spec |
| **E.4** | EQY 返回 inconclusive（timeout / 工具问题） | 再重构一次 | 用尽 budget 后，把 error message 送给 spec |

### 4.5 模块职责矩阵

| 模块 | 输入 | 输出 | 用到的模型/工具 | 是否需训练 |
|------|------|------|----------------|----------|
| Spec Generator (round 1) | 原始 RTL | 候选 spec（结构化文本） | 任意 LLM（OpenRouter API） | 否 |
| Spec Generator (refinement) | 上一轮 spec + verifier 报告 | 修订后的 spec | 同上 LLM | 否 |
| RTL Reconstructor | 候选 spec | 重构 RTL（Verilog 代码） | 同上 LLM | 否 |
| Compiler（轻量级） | 重构 RTL | 编译 ok / error log | iverilog / 兼容 Verilog 编译器 | 否 |
| Formal Equivalence Checker | 原始 RTL + 重构 RTL | pass/fail + diagnostics | **Yosys EQY**, SAT backend, depth=10 | 否 |
| Log/VCD Parser | EQY 输出 | 归类为 E.1~E.4 + counterexample | 论文自研的轻量级 parser | 否 |
| LLM API Gateway | 所有 LLM 调用 | 统一接口 | **OpenRouter** | 否 |

整套系统**完全无训练**：6 个现成 LLM 即插即用。

### 4.6 信息隐藏（Information Hiding）原则

这是论文最容易被忽视但非常关键的设计点：

- **不**把 FEC log 喂给 reconstructor —— 否则 reconstructor 会从 log 里学到原 RTL 的细节，绕过 spec 这条信息通道。
- **唯一例外**：编译错误（E.2）可以喂给 reconstructor —— 因为编译错误说的是「这个 RTL 代码长这样编不过」，没有泄漏原 RTL 的功能语义。
- 这个原则保证了 spec 是 reconstructor **唯一**能从原 RTL 抽取功能语义的通道——也就是让 spec 真正被验证，而不是 spec 和 FEC log 双通道同时给 reconstructor（那样 spec 的作用就被稀释了）。

### 4.7 与 Huang et al. (2025) 的关系

Huang et al. (arXiv:2512.00045) 只做了**单轮**的 RTL→spec 评测（也就是 SpecLoop 的「baseline」）。SpecLoop 是其直接 follow-up：把单次生成升级成迭代生成，并且**首次引入 FEC 作为 oracle**。所以论文标题里的「agentic framework with formal verification feedback loop」其实是把 Huang 的「评测协议」改造成「生成算法」。

## 5. 关键公式

论文没有给出很多解析公式（它本质上是 agentic loop 工程而非数学理论）。下面给出的形式化都是基于论文文字描述的「合理化表达」，并非论文原编号公式。

### 5.1 SpecLoop 总反馈循环（论文 Algorithm 隐含形式化）

论文没有给伪代码编号，下面用自然语言里的循环写成伪公式：

$$
S_{i+1} = \Phi_{\text{LLM}}\left(S_i,\, \mathrm{VerEQ}\left(R,\;\Psi_{\text{LLM}}(S_i)\right)\right),\quad i = 0, 1, \ldots, N-1
$$

$$
S^{*} = S_{i^{\star}},\; i^{\star} = \arg\min_{i}\;\mathrm{T}_{\mathrm{NOT\_EQ}}\left(R,\;\Psi_{\text{LLM}}(S_i)\right)
$$

- $S_i$：第 $i$ 轮生成的候选 spec
- $\Phi_{\text{LLM}}$：spec 生成器（同一个 LLM 加上 multi-step prompt）
- $\Psi_{\text{LLM}}$：RTL 重建器（与 $\Phi_{\text{LLM}}$ 用同一个 LLM）
- $R$：原始 RTL
- $\mathrm{VerEQ}(\cdot, \cdot)$：Yosys EQY 形式等价检查
- $N$：最大迭代次数（论文 $= 3$，即初始轮 + 2 次 retry）
- $i^{\star}$：使 $R$ 与 $\Psi_{\text{LLM}}(S_i)$ 等价的最早轮；若不存在则取最后 $S_{N-1}$

**工程直觉**：这是把「spec 写得对不对」转化成「从 spec 重构 RTL 能否复现原 RTL 的功能」，再用 EQY 给出一个 exhaustive 的 0/1 判决——把生成问题降维成可验证的搜索问题。

**为什么这么设计**：与 Huang 等人只做「评测指标」不同，这里把评测指标当 RL 里的 reward 用，让 LLM 在每轮看到具名信号、具名 cycle 的差异，自动比 self-reflection 更精准。

### 5.2 RR-Score 评估指标（沿用 Huang et al.）

$$
\text{RR-Score} = \mathbb{E}_{\text{problems}}\left[\frac{1}{K}\sum_{k=1}^{K}\mathbf{1}\left\{\mathrm{Testbench}_{\text{pass}}\!\left(\Psi_{\text{frontier}}(S^*)\right)\right\}\right]
$$

- $K$：每个问题采样次数（论文取 1 即可视化）
- $\Psi_{\text{frontier}}$：**外部**另请 GPT-5 Codex 来做 spec→RTL 的「独立重建」（**不是 SpecLoop 内部的 reconstructor**——这是为了公平）
- $\mathbf{1}\{\cdot\}$：通过 testbench 则 1，否则 0

**为什么这么设计**：RR 把 spec 的功能保真度操作为「二次重建能否在外部测试平台通过」，独立于 SpecLoop 的 reconstructor（避免自己当裁判）。

### 5.3 错误归因的三分类（论文 §III.B 描述的根因分析形式化）

$$
\text{Cause}(m) \in \{ \text{Inaccuracy},\;\text{Ambiguity},\;\text{ReconLimit}\}
$$

$$
\mathbb{1}\{\text{Inaccuracy}\} = \left[\exists\,\text{signal}\;x : S_i \text{ 描述的 } x \text{ 与 } R \text{ 中的 } x \text{ 不一致}\right]
$$

$$
\mathbb{1}\{\text{Ambiguity}\} = \left[S_i \text{ 与 } R \text{ 一致, 但} \Psi_{\text{LLM}}(S_i) \neq_{F} R\right]
$$

$$
\mathbb{1}\{\text{ReconLimit}\} = \left[S_i \text{ 明确无歧义, 但} \Psi_{\text{LLM}}(S_i) \neq_{F} R \text{ 是因模型能力}\right]
$$

- $\neq_{F}$：FEC 不等价
- Inaccuracy → 改 spec 的错误字段
- Ambiguity → 改 spec 让措辞更精确，含义不变
- ReconLimit → 原样输出不修改（spec 已经够好）

**工程直觉**：这是 LLM 的「元推理」——不是判断 spec 哪里错，而是判断「错的性质是什么、谁来负责」，据此决定下一步动作。能区分这三类是论文设计的精妙之处。

### 5.4 验证 vs RR-Score 的差距（论文实验的「internal metric vs external metric」对照）

$$
\underbrace{\mathrm{VerEQ}\!\left(R,\;\Psi_{\text{LLM}}^{\text{internal}}(S^*)\right)}_{\text{SpecLoop 内部 oracle (FEC)}} \quad\text{vs.}\quad \underbrace{\mathrm{Testbench}\!\left(\Psi_{\text{GPT-5}}(S^*)\right)}_{\text{RR-Score (外部 frontier reconstructor)}}
$$

- 两者**测的不是同一个东西**：内部 FEC 用较弱 same-LLM reconstructor，外部 RR 用 GPT-5 Codex。
- 一个 spec 可能内部 FEC 通过但 RR 失败（因为内部 reconstructor 弱，能等价证明，但 frontier reconstructor 给出的代码过不了 testbench）。
- 反之亦可能：内部 FEC 失败的 spec 由 frontier reconstructor 重建时反而过了 testbench。
- 论文 Figure 3 的「Verified vs Unverified」就是分析这两者的 correlation——verified 子集明显 RR=1 比例更高（强模型如 Qwen3-Coder-480B 达 91%）。

## 6. 训练与实验设置

### 6.1 是否需要训练

**不训练**。SpecLoop 是纯推理时（inference-time）的 agentic 框架，调用 LLM API（通过 OpenRouter）即可。所有 LLM（Llama4-Scout, Llama4-Maverick, Qwen3-Coder-30B, Qwen3-Coder-480B, DeepSeek-v3.1, GLM-4.6）都用原始权重。

### 6.2 Benchmark 与 Baseline

**Benchmark**：
- **VerilogEval** [20]（Liu et al., ICCAD 2023）——「toy-level」模块集合
- **RTLLM** [21]（Lu et al., ASP-DAC 2024）——更大规模设计

**Metric**：
- **RR-Score（RTL Reconstruction Score）** [11]——外部 frontier reconstructor（GPT-5 Codex）独立重建 spec，跑原 benchmark 的 testbench，通过率即分数。比 GPT-Score 更敏感（捕捉细节错误而非仅整体语义相似）。

**Baselines**（两个）：

| Baseline | 描述 |
|---------|------|
| **Single Round** | 直接复现 Huang et al. (2025) 的单轮 LLM 生成，不做 verifier-guided（与 SpecLoop 共享同一 prompt 模板，仅去掉迭代部分） |
| **Pass/Fail-Only** | Full Diagnosis 的简化版——verifier 只给 pass/fail 二值反馈，对失败不附带任何诊断信息 |

### 6.3 消融设计（implicit in Table III）

论文通过把 Full Diagnosis vs Pass/Fail-Only vs Single Round 三个 setting 在同一模型同一 benchmark 上对比，自然给出消融：

```
Single Round       (没有 verifier 反馈)
Pass/Fail-Only     (有 verifier 反馈，但只有 pass/fail 二值)
Full Diagnosis     (有 verifier 反馈，包含编译错 / counterexample)
```

如果 Full > Pass/Fail > Single，则说明：
- 反馈本身有用（vs Single）
- 诊断信息比二值有用（vs Pass/Fail）

### 6.4 实现细节

- **FEC 工具**：Yosys EQY，**SAT 后端，深度界 10**
- **Log/VCD Parser**：作者自研的轻量级 parser——把 EQY 的输出归类到 E.1~E.4，从 VCD 抽 counterexample
- **Retry budget**：spec generator ≤ 2 次 retry（共 3 轮含初始），reconstructor ≤ 2 次 retry
- **LLM 调用**：通过 OpenRouter API，温度 **T = 0.4**（平衡随机性与正确性）
- **统计**：每个实验跑 3 次取均值 ± 标准差

## 7. 创新点

### 创新点 1：形式等价检查（FEC）作为 RTL→Spec 生成的 oracle

**以前**：Huang et al. (2025) 用「reconstruction 协议」来**评估**生成的 spec 质量，但生成端仍然是单次 prompting。
**本文**：把 Huang 的「评估协议」升级为「生成算法」——同一 LLM 在多轮内既写 spec 又重读 spec；FEC 是 oracle，决定是否回喂反馈。
**为什么**：FEC 是 exhaustive（覆盖所有输入组合），而仿真只覆盖 testbench 决定的子集。在文档化场景里，「spec 是否准确」的最佳近似就是「能否被独立重建为功能等价的 RTL」。FEC 把这个近似从概率性变成确定性。

### 创新点 2：编译错 vs 功能错的分类反馈（E.1~E.4）

**以前**：仿真器/SAT 给出的反馈是单一的「pass/fail + 波形」。
**本文**：把 verifier 输出分成 4 类（E.1~E.4），并对应不同的反馈通道：编译错回 reconstructor（因为没泄漏 RTL 语义），counterexample 回 spec generator（因为这是对 spec 准确性的语义级质疑），inconclusive 单独处理。
**为什么**：盲目回传 FEC log 让 LLM 看到所有信号、所有 cycle，会导致 reconstructor 直接「抄」原始 RTL，绕过 spec——这就是论文里的「信息隐藏」原则。

### 创新点 3：根因三分类（Spec Inaccuracy / Ambiguity / Reconstruction Limitation）

**以前**：LLM 在 refinement 阶段直接修改 spec，没有判断「失败归谁负责」。
**本文**：refinement prompt 强制 LLM 先归因（inaccuracy / ambiguity / recon limit），再决策（inaccuracy → 改错；ambiguity → 加精确措辞；recon limit → 原样输出不动）。
**为什么**：这避免「明明是 reconstructor 没能力重建正确的 spec、却去改写 spec」这种 credit assignment error——spec 可能写得很对，错的是重建端的 LLM。

### 创新点 4：同模型双角色的实验约束

**以前**：用 frontier LLM 当 reconstructor、用弱 LLM 当 spec generator，会让结果被 reconstructor 的能力主导。
**本文**：spec generator = reconstructor = 同一个 LLM。**任何 RR-Score 的提升都来自 verifier-guided loop，而非外挂更强模型**。
**为什么**：这种「模型容量隔离」让实验能干净地归因到 verification feedback loop 本身。

### 创新点 5：模型无关（model-agnostic）+ 无需微调

**以前**：很多 AI4EDA 工作需要 SFT/RT/RLHF 在专用数据集上微调 LLM。
**本文**：直接通过 OpenRouter 调 6 个不同 LLM（开源到闭源），参数原封不动，验证了 FEC 反馈循环对各种 backbone 都有效。
**为什么**：表明反馈机制而非模型能力是 spec 质量提升的主要驱动力——这对工业部署特别友好（不需要 GPU 训练集群）。

## 9. 与芯片流程的关系

### 9.1 在全流程中的位置

SpecLoop 是数字芯片设计流程的「文档化中间件」——填在 **① RTL 设计** 写完后、**③ 逻辑综合** 开始前，专门解决「RTL 有但 spec 缺或过时」的痛点。

```text
┌───────────────┐
│ ① RTL 设计    │ ← SpecLoop 的入口（吃 RTL，吐 spec）
│  (Verilog)    │
└───────┬───────┘
        ▼
┌───────────────┐
│ ② RTL 功能仿真│ ← RR-Score 评测时复用 testbench（不走主流程）
└───────┬───────┘
        ▼
┌───────────────┐
│ ③ 逻辑综合    │ ← 需要 spec？但 spec 是给人看的，综合不看 spec
└───────────────┘
        ...
```

**SpecLoop 在主流程里没有「下一步交棒」**——它生成的是给人/给设计文档/给 AI 同事看的自然语言规格文档，**不**直接喂给综合或下游物理实现。这意味着它的 ROI 不在于「让综合更快」，而在于：

- **降低维护成本**：spec 与 RTL 一致 → 改 RTL 后能自动重写 spec
- **帮助新工程师理解设计**：进入新项目时一份好 spec 比直接啃 RTL 友好
- **审计 / 复用**：把老 RTL 变成可读的 spec 后，便于 cross-project 复用
- **下游 AI 同事**：让未来的生成式 AI（[MAGE](../MAGE/论文深度讲解.md)、[VerilogCoder](../VerilogCoder/论文深度讲解.md)、[RTLFixer](../RTLFixer/论文深度讲解.md) 等）能基于历史 spec 做事

### 9.2 与资料包内其他论文的关系

| 论文 | 关系 | 说明 |

### 9.3 从 EDA 工程视角：SpecLoop 能不能进生产？

短期：**可以**用于文档自动化（内部 wiki / 设计 review 文档）。

长期：**还差**：
- **多模块层次化**：Figure 4 例子是单 module；真实设计动辄几十个 module、跨文件 `include`、`parameter` 传递
- **FPGA/PPA 视角**：spec 是功能层，不含 timing/area/power 等物理约束
- **版本控制**：spec 与 RTL 的双向 diff——SpecLoop 只解 RTL→spec，反方向 spec→RTL diff 由 [MAGE](../MAGE/论文深度讲解.md) 等解决
- **跨厂商 IP**：当前 EQY 只验证自写的 RTL，工业里的 IP 核（ARM/Synopsys IP）大多加密无法 EQY

## 10. 讨论与局限

### 10.1 论文自述的局限（§VI）

**基础性局限**（与范式相关）：

1. **End-to-end 强依赖 RTL reconstructor**——若 reconstructor 自己能力不足（弱 LLM 或 spec 描述超出其训练分布），FEC 把问题归到 recon limit，原 spec 不被改进。这是正确归因但等于没用。
2. **资源有界检查（depth bound 10）**——EQY 只能展开 10 cycle 内的差异；deep pipeline 或复杂 FSM 的差异可能在 cycle > 10 才出现，此时 FEC 返回 INCONCLUSIVE（E.4），归到 recon limit。
3. **RR 评测也依赖 frontier reconstructor**——评测本身不是 ground truth，是另一个 LLM 的重建能力。

**工程性局限**（可改进）：

4. **反馈解析的启发式**——把 EQY 输出归类到 E.1~E.4 的 parser 是论文自研的，未必鲁棒。
5. **不能扩展到大工业 RTL**——单 module 设计之外，跨文件、parameter、IP wrapper 都需要 multi-agent（planning, tool selection, IP dependency handling）才能处理。

### 10.2 代码/复现层面的问题

**代码可获得性**：
- 论文中**未给仓库地址**——代码状态 ⏳ 待跟（截止发稿未在 arXiv 找到公开 link）
- 6 个 LLM 都通过 OpenRouter 商业 API 调用，复现需 OpenRouter key + 余额
- Yosys EQY 是开源工具（YosysHQ 出品），自行安装即可

**复现门槛**（估算）：
- API 成本：6 模型 × 2 benchmark × 几十题 × 3 retry × 2 reconstructor = 数万次 LLM 调用，每次 ~1-3k tokens，估算 $200-500 美元（取决于模型）
- 工具链：Yosys + EQY + iverilog + OpenRouter，全开源/低门槛
- VRAM：API 模式无需本地 GPU

**已知关键坑**（推断）：
- 论文把 reconstructor 与 spec generator 强制同模型，是个**实验约束**——产品化可解耦
- 信息隐藏原则要求严格控制 verifier→reconstructor 通道的输出——parser 错把 FEC log 塞给 reconstructor，结果会立即崩溃
- OpenRouter 的不同 LLM 后端有 rate limit，需 retry 队列

### 10.3 本资料包的批判性分析

**SpecLoop 的方法学是「评测协议当算法」**——这是它优雅的地方，也是它脆弱的地方：

1. **优雅**：FEC 给了 spec 生成一个 deterministic oracle，比 self-reflection、LLM-as-judge 都强。
2. **脆弱**：(a) FEC 本身是 NP-hard 问题，depth bound 10 是工程取舍，对深层 FSM 不够；(b) FEC 比较的是「两份 RTL 是否等价」，不是「spec 是否符合硬件工程师的预期」——可能通过 FEC 但 spec 漏写了某种 corner case（恰好不影响 RTL 的 surface behavior）。
3. **评测公平性**：Full Diagnosis 内部用同 LLM 做 reconstructor，外部用 GPT-5 Codex 做 RR 评测——两个模型本身就是不同的，两个 oracle 测的不是同一件事，Figure 3 的「verified → RR=1 高」是相关而非因果。
4. **可扩展性天花板**：现在的 retry budget = 2，对 toy VerilogEval 足够，对 RTLLM 的更复杂设计就乏力（看 Table III RTLLM 提升普遍不如 VerilogEval）——作者也在论文里承认了「未来 multi-agent」。

**隐藏的评估问题**：
- SpecLoop 的「Pass/Fail-Only」仍能打过 Single Round——这说明即使没有诊断，反复试错就能涨点。「诊断信息多大价值」其实需要 Single Round vs Pass/Fail-Only vs Full Diagnosis 三组配对读，但 Llama4-Scout 在 VerilogEval 上 Pass/Fail-Only (0.722) > Full Diagnosis (0.705) 是反例——表明该模型上 Full Diagnosis 反而有害，可能是诊断信息使其陷入 over-correcting。
- 论文 Figure 3 的标准差（图中未显示）应该在 0.01~0.04 之间，5 个百分点的差异有时在 2σ 之内。

## 12. 一分钟复述版

1. **问题**：RTL 文档（自然语言 spec）常常缺失或过时，工程师维护成本高；以前 LLM 生成 spec 没有「对不对」的客观信号。

2. **方法**：SpecLoop = agentic 反馈循环。LLM 写 spec → 同一 LLM 再把 spec 重构成 RTL → Yosys EQY（SAT backend, depth=10）对两份 RTL 做穷尽等价证明 → 失败就把 counterexample 喂回去，最多重试 2 轮。4 类错误（E.1 invalid original / E.2 compile fail / E.3 functional mismatch / E.4 inconclusive）对应不同反馈通道；并执行「信息隐藏」——FEC log 不回传 reconstructor 防作弊。

3. **关键技术点**：
   - **多步 prompt 设计**——Spec generator 用 3-stage（分析 / 写 spec / 自检），refinement 用 3-stage（总结 verifier / 归因 / 决策）。
   - **归因三分类**——LLM 在每轮先判断错是 inaccuracy / ambiguity / recon limit，再决定改不改 spec。
   - **同模型双角色**——spec generator = reconstructor = 同一个 LLM，避免外挂更强模型混淆实验。
   - **模型无关 + 无训练**——6 个现成 LLM 都通过 OpenRouter 直调，参数冻结。

4. **结果**：
   - VerilogEval 上 **DeepSeek-V3.1：0.865 → 0.940**，**Qwen3-Coder-30B：0.722 → 0.795**
   - RTLLM 上 **GLM-4.6：0.813 → 0.880**，**DeepSeek-V3.1：0.767 → 0.800**
   - Full Diagnosis > Pass/Fail-Only > Single Round（12 setting 中 Full Diagnosis 9 次排第一）
   - Verified 子集的 RR=1 比例（85-91%）远高于 Unverified（34-45%）

5. **局限**：强依赖 reconstructor 自身能力、depth bound 10 对复杂 FSM 不够、单 module 设计之外需 multi-agent、代码未公开。

6. **意义**：把「评测协议」（Huang et al. RR）改造成「生成算法」，首次把形式等价检查作为 RTL→spec 生成的 oracle 引入资料包，补齐了 LLM 介入 spec↔RTL↔断言三元组的反向赛道。
