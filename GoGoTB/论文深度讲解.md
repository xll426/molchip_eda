## 1. 一句话定位

**GoGoTB 是首个零人工干预的 Agentic RTL 功能验证闭环框架——给定 RTL 源码、自然语言规格和可选参考模型，全自动生成完整 cocotb 验证环境（Driver / Monitor / Scoreboard / Coverage Model），将每个功能覆盖率 bin 锚定到命名规格行为，通过 7 类根因诊断定向修复实现覆盖率闭合；在 8 个设计、7 种 backbone LLM 上达到 100% 环境生成成功率，平均 98.4% Line / 97.2% Branch / 97.0% Toggle / 83.2% Functional Coverage。**

这句话里的 4 个承重点，后面逐一拆解：

1. **100% 环境生成成功率** — 8 个设计 x 7 种 LLM backbone（Kimi-K2.5 / GLM-5.1 / Minimax-M2.7 / Claude Opus 4.6 / Claude Sonnet 4.6 / GPT-5.4 / DeepSeek-V3.2）全部成功，而同一基准上 UVM2 的 SRG 为 0%。成功不依赖特定模型，而来自三层执行控制架构。
2. **Specification-Grounded Coverage** — 每个 functional coverage bin 绑定一条命名规格行为（如 "baud_115200_tx_0x55"），而非传统做法的 RTL 信号范围分区（如 `bins range[] = {[0:255]}`）。这使得覆盖率模型从"测了多少种值"升维到"验了多少种行为"，gap 可诊断、可定向修复。
3. **7 类根因诊断 + 定向修复闭环** — 残留覆盖缺口按 Stimulus Gap / Sequence Gap / Cross Hole / State Unreached / Timing Dependent / Transition Gap / Seed Insufficient 七类分类，每类有定向修复策略。Stall-aware 检测防止无限循环。
4. **Python/cocotb 验证栈的工程决策** — LLM 对 Python 的首次正确率远高于 SystemVerilog，Verilator 输出结构化可解析诊断，这两点共同支撑了 100% SRG 的可达成性。

## 2. EDA 阶段映射（①-⑰）

参照 [芯片流程.md](../芯片流程.md) 的 17 阶段标准编号。GoGoTB 是纯粹的 RTL 功能仿真工具——以阶段 ② 为核心，严格不涉及 ④ 门级仿真和 ⑥ 形式验证。

| 阶段 | 覆盖 | 说明 |
|------|:---:|------|
| **① RTL 设计** | 辅助（输入侧） | 接收待验证的 Verilog RTL 源码作为输入，GoGoTB 本身不参与 RTL 设计过程，不生成 RTL、不修改 RTL（Boundary Enforcement 保证 RTL 对所有后续 stage 只读） |
| **② RTL 功能仿真** | ✅ **核心** | GoGoTB 的全部工作都在此阶段：解析规格 → 分解 testpoint → 构建 coverage model → 生成 cocotb testbench → 运行 Verilator 仿真 → 测量代码覆盖率 + 功能覆盖率 → 诊断残留缺口 → 定向修复 → 循环闭合。使用的仿真栈为 Verilator 5.024 + cocotb 2.0.1（Python-based），零延迟假设，信号值只有 0/1 |
| ③ 逻辑综合 | ❌ | GoGoTB 是前端验证工具，完全不涉及 RTL→门级网表翻译、技术映射、SDC 约束、SDF 延时提取等综合流程 |
| **④ 门级仿真** | ❌ | GoGoTB 使用 Verilator（RTL 级周期精确仿真器），不读取 SDF 延时文件、不处理 X/Z 传播、不检测毛刺（glitch）、不检查建立/保持时间违例——这些都是门级仿真的专属能力。GoGoTB 的仿真世界中没有延迟概念 |
| ⑤ STA（静态时序分析） | ❌ | 不扫描寄存器到寄存器路径、不计算 WNS/TNS、不涉及工艺角——STA 属于后端时序签核，与功能验证正交 |
| **⑥ 形式验证** | ❌ | GoGoTB 使用仿真（有穷测试），而非 SAT/SMT 数学证明。论文明确将形式验证列为 future work："integrating formal methods to cover structurally hard-to-reach states"。仿真验证的完备性上限由 testpoint 集合决定，形式验证的完备性是数学上的（对所有可能输入证明等价性） |
| ⑦ 布局规划 (Floorplan) | ❌ | 不涉及物理设计任何阶段 |
| ⑧ 标准单元摆放 (Placement) | ❌ | — |
| ⑨ 时钟树综合 (CTS) | ❌ | — |
| ⑩ 布线 (Routing) | ❌ | — |
| ⑪ 后仿真 | ❌ | 不涉及 SDF + SPEF 联合反标的版图后仿真 |
| ⑫ 物理验证 (DRC+LVS) | ❌ | — |
| ⑬ 签核 (Signoff) | ❌ | — |
| ⑭ 流片 | ❌ | — |
| ⑮ 制造 | ❌ | — |
| ⑯ 封装 + 测试 | ❌ | — |
| ⑰ 芯片到手 | ❌ | — |

**覆盖率：1/17。** GoGoTB 是纯粹的数字前端功能验证工具，从阶段 ③ 开始的所有后端流程均不涉及。

> **最容易误读的边界**：GoGoTB 的"验证通过"指的是 RTL 在零延迟理想仿真环境下、在随机激励覆盖到的场景中表现符合规格——这不等于芯片能正常工作。真实芯片还要跨过门级仿真（毛刺/X 传播）、STA（时序违例）、形式验证（综合等价性）、后仿真（走线延迟+串扰）、物理验证（DRC+LVS）五道关卡。GoGoTB 的"100% SRG"只是验证环境可跑，"83.2% Func Cov"是规格行为覆盖率，都不是 signoff 级别的流片就绪信号。

## 3. 输入 / 输出

### 3.1 输入

GoGoTB 接收三类输入，全程零人工干预：

| 输入项 | 必需 | 格式 | 说明 |
|--------|:---:|------|------|
| RTL 源码 | 是 | Verilog (.v) | 待验证的数字电路设计，可为组合逻辑、时序逻辑、FSM、协议控制器等 |
| 自然语言规格 | 是 | 英文文本 | 描述设计行为的完整文档，是 testpoint 分解和 bin 锚定的唯一依据 |
| 参考模型 | 否 | Python | golden 行为模型，从规格推导且对 RTL 实现隔离（不可见 RTL 内部信号），防止 oracle 腐败 |

**Benchmark 设计实例（8 个，5 类，291~1424 行，1~9 模块）**：

> **注**：原标准化总结的 benchmark 表中 ALU/UART 行数模块数有行偏移错误，以下以论文 Table 2 为准。

| 设计 | 类型 | 模块数 | 行数 | 来源 |
|------|------|--------|------|------|
| AES | 组合密码 | 8 | 684 | UVM2 [7] |
| ALU | 组合+时序 (IEEE 754 FP) | 7 | 409 | UVM2 [7] |
| UART | 串行协议 | 4 | 387 | [24] |
| SPI | 串行协议 | 3 | 291 | This work |
| I2C | 串行协议 (slave) | 3 | 470 | [25] |
| SHA256 | 序列密码 | 4 | 1,142 | [26] |
| SM4 | 序列密码 | 9 | 1,424 | [27] |
| SDRAM | 存储控制器 | 1 | 433 | [28] |

AES 和 ALU 来自 UVM2 公开 benchmark，其余 6 个选自高质量开源 RTL 仓库以覆盖 UVM2 未涉及的设计类别。

**具体输入示例（UART）**：

```verilog
// UART RTL 片段（论文用例, 387行, 4模块）
module uart (
    input  wire        clk,
    input  wire        rst_n,
    input  wire        rx,
    output wire        tx,
    input  wire [15:0] baud_div,
    input  wire [7:0]  tx_data,
    input  wire        tx_start,
    output wire [7:0]  rx_data,
    output wire        rx_valid,
    output wire        tx_busy,
    output wire        frame_err,
    output wire        parity_err,
    output wire        fifo_full,
    output wire        fifo_empty
);
    // 内部: baud generator, TX FSM, RX FSM, FIFO (depth 16)
endmodule
```

自然语言规格描述：
- 波特率：9600 / 115200 可配置
- 数据位宽：8 位
- 停止位：1 位
- 校验位：NONE / ODD / EVEN
- FIFO 深度：16，满标志 / 空标志
- 帧错误检测（stop bit != 1）
- 溢出检测（FIFO 满时写入）
- 复位行为（异步复位，所有寄存器清零）

参考模型为独立 Python 模块：
```python

class UARTRefTX:
    def send_byte(self, data: int) -> list[int]:

        pass

class UARTRefRX:
    def receive_frame(self, bits: list[int]) -> int:
        """解析 UART 帧，返回 data byte"""
        pass
```

### 3.2 中间产物

GoGoTB 流程中的关键中间表示：

**Design Profile（S1 输出）**：从 RTL 和规格解析出的结构化设计概要，包含端口列表、模块层次、参数范围、设计类别（组合密码/串行协议/存储控制器等）。这是知识系统中 Reference Library 相似度匹配的输入。

**Testpoint Inventory（S2 输出）**：四元组集合 \langle s, r, c, d \rangle，覆盖 7 个行为维度（D1~D7）：
- D1 Data Boundaries（数据边界）：输入/输出取极值 0x00 / 0xFF / 全 0 / 全 1
- D2 Control Flow（控制流）：条件分支、模式切换
- D3 Timing Constraints（时序约束）：背靠背帧间隔、周期精确条件
- D4 FSM State Transitions（状态机跳转）：所有合法状态转移 + 非法转移拒绝
- D5 Protocol Compliance（协议合规）：起始/停止/校验位格式
- D6 Error Injection（错误注入）：帧错误、校验错误、溢出
- D7 Microarchitectural Interaction（微架构交互）：FIFO 满时写入、同时收发

**Coverage Model（S3 输出）**：每个 testpoint 映射为一个 coverpoint bin，携带命名行为声明。与 UVM2 的本质区别：

```python
# UVM2 做法: bin 基于信号取值范围（两个同端口设计产出相同模型）
covergroup uvm_cg;
    data_cp: coverpoint data_in {
        bins range[] = {[0:255]};  // 只看数值范围
    }
endgroup

# GoGoTB 做法: 每个 bin 锚定命名规格行为
covergroup gogotb_cg;
    baud_cp: coverpoint baud_config {
        bins baud_115200 = {DIV_115200};  // spec §3.2 行为
        bins baud_9600   = {DIV_9600};    // spec §3.1 行为
    }
    fifo_cp: coverpoint fifo_status {
        bins overflow = {FULL && WR_EN};  // spec §4.3 行为
        bins underrun = {EMPTY && RD_EN}; // spec §4.3 行为
    }
endgroup
```

### 3.3 输出

**完整验证环境（cocotb/Python）**：
- Driver：驱动 DUT 输入端口，按 testpoint 生成激励
- Monitor：观测 DUT 输出端口，按协议进行采样同步
- Scoreboard：逐周期比较 DUT 输出与参考模型期望输出
- Coverage Model：每个 bin 锚定命名规格行为（见 3.2）
- Reference Model：独立的 golden Python 行为模型

传统需数周手写 SystemVerilog/UVM，GoGoTB 在 5.5~48 分钟内自动生成（取决于设计复杂度和 LLM）。

**四维覆盖率报告**（8 设计平均）：

| 指标 | GoGoTB | UVM2 |
|------|--------|------|
| Line Coverage | 98.4% | —（SRG=0%） |
| Branch Coverage | 97.2% | — |
| Toggle Coverage | 97.0% | — |
| Functional Coverage | 83.2% | —（SRG=0%） |

GoGoTB 平均每个设计产出 10.8 个 coverpoint + 3.0 个 cross；UVM2 在 AES 上仅产出 3 coverpoints + 1 cross，对 AES/ALU 之外的 6 个设计无任何 coverage model。

**Sign-off Report（S8 输出）**：每个残留 gap 标注根因分类 + 定向修复尝试 + 最终状态，无 gap 被无声丢弃，输出完全可审计。

## 4. 方法与架构

### 4.1 整体 Pipeline

GoGoTB 由三大子系统构成，驱动一个 8 阶段 Agentic 流水线。以下框图对应论文 Figure 2。

```text
                      输入: RTL 源码 + 自然语言规格 + 可选参考模型
                                       │
    ┌──────────────────────────────────┼──────────────────────────────────┐
    │  子系统① Agentic Execution Control — 包裹全部 8 个 stage              │
    │  L1: Tool-Call Interception (Guard → Structuring → Validation)       │
    │  L2: Quality Gates (Hard Gate / Soft Gate / Advisory Gate)           │
    │  L3: Failure Recovery (L1 补丁 → L2 跨文件 → L3 重构 → L4 回退)      │
    │  Boundary Enforcement: RTL 只读 / Ref Model 不可见 RTL 实现           │
    │  ┌──────────────────────────────────────────────────────────────┐   │
    │  │  Phase 1: Spec Analysis     │  Phase 2: Env Construction     │   │
    │  │   S1  解析 RTL+规格          │   S3  构建 Coverage Model      │   │
    │  │       输出 Design Profile   │       (bin 锚定规格行为)       │   │
    │  │   S2  7 维 Testpoint 分解    │   S4  构建 Reference Model     │   │
    │  │       输出 Testpoint 清单    │   S5  构建 Testbench           │   │
    │  │                             │       (Driver/Monitor/Scb)     │   │
    │  ├─────────────────────────────┼───────────────────────────────┤   │
    │  │  Phase 3: Stochastic Sim    │  Phase 4: Coverage Closure     │   │
    │  │   S6  自适应种子策略随机仿真  │   S8  7 类根因诊断 →           │   │
    │  │   S7  累积 Code + Func Cov  │       定向修复 → 返回 S6       │   │
    │  └─────────────────────────────┴───────────────────────────────┘   │
    │         ▲ 子系统② — 在每个 stage 入口注入知识                       │
    │         ▲ 子系统③ — 跨 S1~S3 + S6~S8 运行覆盖率闭合                 │
    └────────────────────────────────────────────────────────────────────┘
                                       │
                                       ▼
               输出: 验证环境 + 四维覆盖率报告 + 缺口诊断 Sign-off Report
```

**四阶段解读**：
- Phase 1（S1~S2）规格分析：从自然语言规格中提取所有可验证行为，testpoint 完备性决定验证质量上限
- Phase 2（S3~S5）环境构建：全自动生成 coverage model、参考模型、testbench
- Phase 3（S6~S7）随机仿真：自适应种子策略，连续 batch 无增益时标记随机仿真能力边界
- Phase 4（S8）覆盖率闭合：诊断、修复、循环，直到达目标或触发 stall-aware 终止

### 4.2 核心模块逐个详解

#### 子系统① — Agentic Execution Control（三层执行控制）

**为什么需要这个子系统**：LLM Agent 循环容易出现三类失败——调错工具、破损产出跨 stage 传播、重复失败修复不收敛。传统 Agent 框架（ReAct / Reflexion）提供推理-行动-观察循环，但不提供确定性强制层。GoGoTB 在工具调用边界、stage 边界、失败恢复边界各设一层独立于 LLM 的强制机制。

**Layer 1 — Tool-Call Interception**：每个 LLM 工具调用经过三步拦截（全部在 LLM 决策之外运行）：
- **Guard**：检查工具是否匹配当前 stage，阻止错误调用（如 S5 中调用综合工具）
- **Structuring**：将 Verilator 原始编译/仿真输出转为结构化诊断（{错误类型, 文件, 行号, 根因建议}），消除噪音误导
- **Validation**：session 边界验证产出完整可编译，不通过不关闭 session。同一命令失败 3 次且输出无变化 → 注入 redirect prompt 打破死循环

**Layer 2 — Quality Gates**：在 stage 边界运行，阻止破损产出传播到下游：
- **Auto-Repair**：确定性修复常见结构错误（无需 LLM 参与，如缺失 import、重复定义）
- **Hard Gate**：编译成功 + 必要产出存在，不通过强制阻塞
- **Soft Gate**：testpoint 完整性 + 信号名一致性，早期阻塞，后期（attempt 数上升后）降级为警告
- **Advisory Gate**：语义审查，永不阻塞，只提供反馈

**Layer 3 — Failure Recovery**：按失败次数自动扩大修复范围：
- **L1**：单文件最小补丁
- **L2**：读取完整跨文件上下文后编辑
- **L3**：重构整个有问题组件
- **L4**：回退到最小正确实现（fallback）

每次 attempts 数跨阈值自动升级修复级别，确保循环收敛而非原地踏步。

**Boundary Enforcement**（跨层约束）：RTL 源码对后续 stage 只读；参考模型从规格推导且对 RTL 实现不可见 → 任何仿真 mismatch 必定指向真实 DUT 缺陷，不可能源自 oracle 腐败。

#### 子系统② — Evolvable Knowledge System（可演化知识系统）

**为什么需要这个子系统**：LLM 对验证方法学和设计特定知识的掌握有限且不可靠。全量注入涨满上下文窗口稀释有用信息，注入不相关知识则主动误导 LLM。需要"按需分发、不确定不分发"的机制。

**Skill Library（技能库）**：10 个技能模块（testbench 构建、测试规划、覆盖率闭合、RTL 分析、仿真器后端、密码设计模式、串行协议模式等）。按 stage 级确定性映射调度——S1 自动加载"RTL 分析"模块，S5 自动加载"testbench 构建"模块。入口只发 TOC（目录），按需加载完整内容。新增设计类别只需在知识目录中新增一个文件。

**Reference Library（参考库）**：存储真实验证过的完整设计（RTL + spec + testbench + testpoint），按结构相似度三级门控：
- **高度相似** → 作为直接模板分发
- **部分相似** → 作为风格指南分发
- **不相似** → **抑制分发**，LLM 收不到任何参考

抑制是核心设计决策。低相似度参考比不提供更危险——LLM 会高置信度套用错误模板。CS1 实证了这一设计：知识系统关闭时，UART 功能覆盖率为 0%（三个寂静失败链：无协议帧格式化、观测不同步、参考模型未分离 TX/RX）；开启后三个 domain contract 逐一修复，功能覆盖率恢复至 75.3%。

#### 子系统③ — Specification-Grounded Coverage Closure（规格锚定覆盖率闭合）

**为什么需要这个子系统**：覆盖率模型的质量在构建时决定，而非测量时。基于 RTL 信号范围的模型可能 100% 命中但漏掉关键规格行为；两个同端口设计产生相同模型。必须将每个 bin 锚定到命名规格行为才能让 gap 可诊断。

**S1~S2 Testpoint 分解**：S1 将 RTL + 规格解析为 Design Profile（端口、层次、参数、设计类别）。S2 从规格推导 7 维 testpoint 全集。Testpoint 完备性 = 验证质量的上限。

**S3 Coverage Model 构建**：每个 testpoint 转为 coverage bin，携带命名行为声明且可追溯到规格原文。覆盖率模型从信号值分区变为行为断言集合。

**S6~S7 随机仿真**：按 testpoint 组生成测试用例，自适应种子策略运行仿真。连续 batch 无覆盖率增益 → 停止，标记随机仿真能力边界。这决定了 S8 接手时的"基线"。

**S8 根因诊断与闭合**：因每个 bin 已锚定规格，残留 gap 可映射到 7 类根因中的一类，各有定向修复：

| 根因类别 | 典型场景 | 定向修复 |
|----------|---------|---------|
| Stimulus Gap | 缺少特定输入组合激发行为 | 生成定向测试 |
| Sequence Gap | 缺少多步事务序列 | 生成 multi-transaction 定向测试 |
| Cross Hole | 交叉覆盖率约束不匹配 | 精炼约束条件 |
| State Unreached | FSM 特定状态未访问 | 生成状态路由序列 |
| Timing Dependent | 需周期精确时序条件 | 生成 cycle-precise 激励 |
| Transition Gap | 未覆盖边沿条件 | 生成边沿条件测试 |
| Seed Insufficient | 随机种子采样不足 | 扩展种子空间 |

**三种停止条件**：(1) 所有 bin 覆盖 → 达标终止；(2) 连续两轮无增益 → stall-aware 终止（已达 LLM 定向测试上限）；(3) 仅剩结构不可达 bin → 从分母移除后达标终止。

## 5. 关键公式

### 5.1 LLM 自回归生成

GoGoTB 将 LLM 从一个无状态映射扩展为有状态 Agent。论文首先给出 LLM 基础行为的数学描述，以解释为什么纯单轮 LLM 调用不足以构建验证环境。

$$
P(y_{1:m} \mid x_{1:n}) = \prod_{t=1}^{m} P(y_t \mid x_{1:n}, y_{1:t-1})
$$

- $x_{1:n}$：输入 prompt 序列（固定上下文窗口）
- $y_{1:m}$：输出 token 序列
- $y_t$：第 $t$ 个生成的 token，条件概率由原始 prompt 和已生成 token 共同决定
- $m$：输出长度

**工程直觉**：LLM 的每次推理是纯函数——相同 prompt 产生相同输出分布，没有跨轮次的记忆，无法根据仿真反馈修正错误。这对应传统 SystemVerilog 的功能仿真中的"零延迟假设"——LLM 无法感知执行反馈，就像 RTL 仿真无法感知布线延迟。所有先前 LLM 验证工作 [5-7] 都在此范式中：各组件独立单轮生成、无共享上下文、无迭代修复。

**为什么这么设计**：Agent 将这一无状态映射扩展为推理-行动-观察循环——动作（生成代码 / 运行仿真）的结果作为观察反馈给 LLM 的下一轮上下文，形成闭合。这对应数字电路中组合逻辑向时序逻辑的升级——加了"反馈" = 加了"记忆"。三层执行控制则是在反馈路径上加了"组合逻辑保证"（确定性强制，不依赖 LLM）。

### 5.2 环境生成成功率 SRG

SRG 是衡量验证环境可用性的核心指标——它不是"单个组件能编译"这种弱指标，而是要求完整环境编译零错误、仿真无死锁、覆盖率非零三者同时满足。

$$
\text{SRG}(M) = \frac{1}{N}\sum_{i=1}^{N} \mathbf{1}[\,\text{compile} \land \text{simulate} \land \text{cov} > 0\,]
$$

- $M$：backbone LLM 型号（7 种，从 Kimi-K2.5 到 DeepSeek-V3.2）
- $N$：独立运行次数
- $\mathbf{1}[\cdot]$：指示函数，三个条件同时满足为 1，否则为 0
- $\text{compile}$：零错误编译（Verilator + cocotb 联合编译通过）
- $\text{simulate}$：仿真无死锁完成
- $\text{cov} > 0$：至少产生非零覆盖率（排除"编译通过但 testbench 什么都没测"的假阳性）

**工程直觉**：SRG 的三个条件对应验证流程的三道硬门槛——能编译、能跑通、能测到东西。GoGoTB 的 100% SRG 意味着三层执行控制在这三道门槛上全部成功。UVM2 的 0% SRG 意味着各组件独立单轮生成、无共享上下文、无迭代修复——编译失败和仿真死锁累积且无任何恢复机制。

**为什么这么设计**：高单组件生成率（per-component generation rate）不等于完整环境可用——组件在隔离下各自通过语法检查，但接口假设不一致导致组装后失败。SRG 的"三条件同时满足"设计确保了"环境整体可运行"才计数，避免了这类假阳性。

## 6. 训练与实验设置

### 6.1 是否需要训练

**不需要训练。** GoGoTB 直接调用现成 LLM API，不做任何微调（SFT）、RLHF、或从头训练。论文测试了 7 种 backbone LLM（Kimi-K2.5、GLM-5.1、Minimax-M2.7、Claude Opus 4.6、Claude Sonnet 4.6、GPT-5.4、DeepSeek-V3.2），覆盖不同家族、参数规模和训练语料。100% SRG 在所有 7 种模型上一致达成，说明能力来自 Agent 架构设计而非特定模型的强度。

### 6.2 实验设置

**平台**：Intel Xeon Gold 6248R（48 核），512 GB DDR4，Ubuntu 22.04 LTS。仿真栈：Verilator 5.024 + cocotb 2.0.1。Agent SDK：CodeBuddy Agent SDK [23]。

**Benchmark**：8 个设计（详见表 2），覆盖组合数据通路（ALU）、流水线密码核（AES / SM4）、串行协议（UART / SPI / I2C）、状态存储控制器（SDRAM）、纯组合密码（SHA256）。

**Baseline**：UVM2 [7]——唯一尝试功能覆盖率的先前 LLM 验证系统。UVM2 使用 SystemVerilog/UVM/VCS 栈，各组件独立单轮 LLM 调用生成。在 8 个设计上均达 0% SRG——编译失败和仿真死锁无恢复机制。

**评估指标**：
- **SRG**：环境生成成功率（公式见 5.2）
- **Line Coverage**：RTL 代码行执行覆盖
- **Branch Coverage**：条件分支覆盖（if/case 的每个分支）
- **Toggle Coverage**：信号 0→1 和 1→0 翻转覆盖
- **Functional Coverage**：规格衍生 bin 的命中比例
- **Coverage Model Richness**：coverpoint 和 cross-coverage 数量

**消融设计**：
- RQ1：跨 8 设计 x 7 LLM 验证执行控制可靠性
- RQ2：与 UVM2 对比覆盖率模型质量和功能覆盖率
- CS1：UART 上开关知识系统（"是否因知识缺口而非模型能力缺口"）
- CS2：I2C 上追踪覆盖率闭合全流程（"7 类根因是否都能诊断并驱动收敛"）

1. **全覆盖不等于全验证**：代码覆盖率超过 97% 而功能覆盖率平均 83.2%，中间约 15pp 的差距正是"代码执行过"和"行为验证过"的区别。行覆盖高只说明代码被执行，不代表正确行为被确认。若功能覆盖率模型不锚定规格（如 UVM2 的信号范围分区），这段差距会被 100% 的信号范围覆盖率掩盖。

- GoGoTB：8/8 设计，7/7 backbone LLM，全部成功（SRG = 100%）

## 7. 创新点

### 创新点 1：三层执行控制架构——首次在 EDA Agent 中系统分离 LLM 推理与确定性强制

**以前的做法**：LLM 验证工作 [5-7] 中，LLM 输出直接喂给工具执行，工具输出直接喂回 LLM。这意味着执行可靠性完全依赖 LLM 推理质量——LLM 调错工具、输出破损产物、重复无效修复时，系统没有任何独立于 LLM 的防御层。

**GoGoTB 的做法**：在三个边界各设一层确定性强制——工具调用边界（Guard → Structuring → Validation 三步），stage 边界（Hard/Soft/Advisory Gate + Auto-Repair），失败恢复边界（L1→L4 递进修复）。LLM 只负责推理，执行/验证/修复由架构保证。

**为什么有效**：传统做法把"推理"和"执行"混在一个不可靠的 LLM 调用里——就像把 combinational 和 sequential 逻辑混为一体。GoGoTB 把它拆成"LLM 推理"（灵活但不保证正确）+"确定性强制层"（正确但不灵活）——这在数字电路中等价于把设计拆成数据通路和控制通路。7 种 backbone LLM 全达 100% SRG 证明了这个架构决策的正确性。

### 创新点 2：两级可演化知识系统——解决领域知识的按需注入与误注入抑制

**以前的做法**：LLM 验证没有结构化领域知识库，依赖 LLM 训练数据中的隐含知识——这对复杂协议（UART 帧格式、I2C 时钟拉伸）和稀缺设计模式（密码轮函数、DRAM 时序约束）完全不可靠。

**GoGoTB 的做法**：Skill Library（方法学知识，按 stage 确定性分发）+ Reference Library（设计特定知识，按结构相似度门控分发/抑制）。抑制是关键——低相似度参考比不提供更危险。

**为什么有效**：这是"确定性知识路由"的思想——什么东西该在什么时候给、该不该给都不依赖 LLM 判断。CS1 给出了实验证据：同样的 LLM，加上 UART domain contract 使功能覆盖率从 0% 跳至 75.3%。知识系统的 O(N) 扩展性也更好——新增设计类别只需在 Skill Library 中加一个文件。

### 创新点 3：规格锚定覆盖率闭合——从"测了多少种值"到"验了多少种行为"

**以前的做法**：Functional coverage model 基于 RTL 信号范围分区——bins 定义是 `{[0:255]}`、`{[0:7]}` 这类数值区间。两个同端口设计（比如两个不同的 ALU）产生**完全相同的 coverage model**。覆盖率 100% 只说明每个数值区间被跑到了，不说明任何规格行为被验证。

**GoGoTB 的做法**：覆盖率模型构建在仿真之前——S1~S2 先将规格分解为 testpoint 全集，S3 将每个 testpoint 转为携带命名行为声明的 bin。每个 bin 可追溯到规格原文。gap 不再是"某个数值区间没跑到"，而是"某个规格行为没被验证"→ 有根因 → 可定向修复 → 收敛有原则。

**为什么有效**：这是 L2（UVM2 的信号范围功能覆盖率）到 L3~L4（规格锚定 + 根因诊断）的跃迁。数据支撑：GoGoTB 的平均功能覆盖率 83.2% 虽然离 100% 有距离，但剩下的每个 gap 都是**可诊断**的——不像 UVM2 的覆盖率模型，100% 也不代表任何规格行为被覆盖到。

### 创新点 4：Python/cocotb 验证栈——语言-工具协同设计的工程决策

**为什么不用 SystemVerilog/UVM**：LLM 对 Python 的首次正确率远高于 SystemVerilog——Python 训练数据量、语法一致性、社区代码质量均优于 SV。Verilator 输出结构化可解析诊断（错误类型/文件/行号），支持确定性错误分类而无需 LLM 参与。cocotb 的 GPI 接口天然支持后续扩展到 VCS/Xcelium 等商业仿真器。

**为什么这是个创新点**：这不是简单的"换了个语言"，而是整个系统设计的基石。100% SRG 要求编译成功率极高——如果每轮都因 SV 语法错误浪费迭代次数，三层执行控制也救不回来。选择 Python/cocotb 是"语言模型能力"与"工具链确定性"的联合优化。

| UART | Universal Asynchronous Receiver/Transmitter | 通用异步收发器，异步串行通信协议 |

## 9. 与芯片流程的关系

### 9.1 在全流程中的位置

GoGoTB 工作在 [芯片流程](../芯片流程.md) 7 阶段验证层次的最底层——阶段 ② RTL 功能仿真。

```text
RTL 功能仿真（逻辑对不对，有穷）
  → 门级仿真（时序对不对，有穷但有延迟信息）
    → 形式验证（综合没改错？无穷——数学证明）
```

GoGoTB 端到端承接 RTL 源码和自然语言规格，全自动完成验证环境构建和执行。由于 Boundary Enforcement 保证参考模型与 RTL 实现隔离，GoGoTB 天然具备"独立验证"的属性——参考模型从规格推导，不是从 RTL 改写，因此可以发现 RTL 实现与规格之间的 deviation。

**解决的核心痛点**：

1. **验证环境编写耗时**：传统完整 UVM 环境需资深工程师数周手写 [3,4]，GoGoTB 在 5.5~48 分钟内零人工完成。时间瓶颈从"编写 testbench"转移到"规格是否完整准确"和"LLM 定向测试能力"。

2. **覆盖率模型与规格脱节**：传统 covergroup 基于信号范围 + 工程师直觉，覆盖率 100% 但重要场景漏测是工业界的常见事故。GoGoTB 将这个问题从"依赖人的细心"升维到"由系统架构保证"——每个 bin 必须锚定规格行为，不锚定就进不了覆盖率模型。

### 9.2 "仿真通过"和"能做成芯片"之间隔着什么

GoGoTB 的"成功率"和"覆盖率"都是**前端功能验证**范畴内的指标，距离物理流片至少有五道关键关卡需要跨越：

| 关卡 | 差距 | GoGoTB 当前状态 |
|------|------|:---:|
| 门级仿真（④） | 零延迟世界 → 真实门延迟世界。X 传播、毛刺、建立/保持违例全部在 GoGoTB 的盲区 | 完全不涉及 |
| 形式验证（⑥） | 有穷测试（仿真）→ 完备证明（SAT/SMT）。仿真测不到的场景永不被发现 | 论文列为 future work |
| STA（⑤） | 不管时序。功能正确但路径延迟超过时钟周期 → 芯片 = 废品 | 完全不涉及 |
| 物理验证 + 后仿真（⑪⑫） | SDF+SPEF 联合反标、DRC/LVS、串扰、IR Drop 等制造关卡 | 完全不涉及 |
| 工艺偏差 | 制造偏差（工艺角 SS/FF/TT × 温度 × 电压）导致的功能失效 | 完全不涉及 |

**具体差距举例（UART）**：GoGoTB 报告 UART 功能覆盖率 75.3%。即便提升至 100%，以下问题也超出其验证范围：
- 异步复位恢复时间不足 → 寄存器亚稳态 → 不可预测行为
- 时钟树偏斜 → 不同寄存器在略有不同的时间看到时钟沿 → 跨时钟域数据采样错误
- 走线串扰 → 相邻信号线的耦合电容在 TX 信号翻转时在 RX 线上感应毛刺
- 工艺角 SS（最慢）下门延迟翻倍 → baud generator 计数值不准 → 帧时序错位

这些都属于阶段 ④~⑬ 的范畴，GoGoTB 的"通过"不覆盖任何一项。这是数字芯片设计中"前端验证完成"和"流片就绪"之间的本质性鸿沟——GoGoTB 没有做错什么，只是它的工作范围天然不包括这些。

## 10. 讨论与局限

### 10.1 论文自述的局限

1. **LLM 定向测试生成是当前瓶颈**：Stimulus Gap + Sequence Gap 占 I2C 上 24 个残留 gap 的 16 个（67%）。系统正确识别"该测什么"但 LLM 无法生成命中复杂多步协议场景的精确定向测试。论文将此列为最高优先级改进方向。

2. **Benchmark 规模有限**：8 个设计，最大 1,424 行 / 9 模块，工业 SoC 数十万行 RTL 的可扩展性未验证。更复杂的层次化设计、多时钟域、跨模块交互对 Agent 循环的收敛性构成未知挑战。

3. **依赖规格质量**：testpoint 分解上限由规格完整性和清晰度决定。规格遗漏的场景永不被验证——这不是工具缺陷而是方法论限制。

### 10.2 代码/复现层面的问题

4. **代码未开源**：论文声明后续开源（"will be open-sourced at a later date"），截至核验时仓库不存在。SRG 100%、功能覆盖率 83.2% 等核心数字无法独立复现。三层执行控制中各层的具体实现（Guard 规则集、Gate 阈值、L1→L4 触发条件）无法审计。

5. **Benchmark 不可完全复现**：SPI 标注为 "This work"（即作者自己提供的设计），UART/I2C/SHA256/SM4/SDRAM 虽然是开源设计，但论文未提供配套的规格文档和参考模型——这些是 GoGoTB 的核心输入。无这些输入就无法跑通完整流水线。

6. **与 UVM2 的比较公平性**：UVM2 使用 SystemVerilog/UVM/VCS 栈（LLM 不擅长），GoGoTB 使用 Python/cocotb/Verilator 栈（LLM 擅长）。100% vs 0% 的 SRG 差距中，语言-工具选择贡献了部分优势，不完全来自三层执行控制的功劳。如果用相同 LLM 给 UVM2 换成 cocotb 后端，SRG 可能不是 0%。论文没有做这个对照实验。

### 10.3 本资料包的批判性分析

7. **Agent 框架的可迁移性未验证**：GoGoTB 基于 CodeBuddy Agent SDK [23]（腾讯云产品），三层执行控制的具体实现是否依赖 SDK 特定能力未知。在 LangChain/AutoGen 等其他 Agent 框架上复现的难度和保真度未知。

8. **覆盖率 ≠ 无 bug**：Scoreboard 逻辑错误（比如用错了参考模型输出端口）、参考模型本身的偏差（比如对 spec 边缘情况理解不同）、跨模块微妙死锁都可能在覆盖率很高时逃逸。独立 assertion、负向测试、property checking 仍是必要补充。GoGoTB 的 scoreboard 其实就是"比较 DUT 输出和参考模型输出"——如果参考模型错了，100% 覆盖率也是 100% 的假阴性。

9. **知识系统的冷启动问题**：Reference Library 的相似度门控需要已有的验证过的设计作为种子。论文未说明初始 Reference Library 包含多少设计、覆盖多少设计类别。对于全新设计类别（如新型协议），Reference Library 触发的是"抑制分发"（因为无相似设计），此时 Skill Library 的方法学知识能否单独支撑合格的验证环境是未验证的。

10. **Stall-Aware 检测的保守性**：连续两轮无增益 → 终止的策略在理论上是合理的（收敛性保证），但在实践中可能过早终止——第三轮恰好需要的定向测试在第一、第二轮之后才被正确生成的边界情况无法排除。

## 12. 一分钟复述版

1. **做什么**：给定 RTL + 自然语言规格，零人工全自动生成 cocotb 验证环境，测量覆盖率，诊断 gap，定向修复，循环闭合。
2. **为什么需要**：功能验证占前端工作量 50%+，一个逃逸 bug 到芯片 → 天价重流片。传统 UVM 环境需数周手写。LLM 可以加速，但纯 LLM 生成不可靠——UVM2 在 8 个设计上 0% 成功率。
3. **怎么做到的（架构三板斧）**：
   - 三层执行控制：工具调用边界拦截 + stage 边界质检 + 失败递进修复，7 种 LLM 全达 100% SRG。
   - 两级知识系统：Skill Library 按 stage 分发 + Reference Library 按相似度门控/抑制（不相似 = 不给 = 宁缺毋滥）。
   - 规格锚定覆盖率：每个 bin 绑定命名规格行为，gap 可诊断（7 类根因）→ 可定向修复 → 收敛有原则。
4. **效果**：8 设计，平均 98.4% Line / 97.2% Branch / 97.0% Toggle / 83.2% Functional，UVM2 全部为 0/8。
5. **不做什么**：只管 RTL 功能仿真（阶段 ②），不管门级仿真/STA/形式验证/物理设计——"验证通过"不等同于"能流片"。
6. **当前天花板**：LLM 定向测试生成——知道该测什么但生成不出命中复杂多步协议场景的精确定向测试（Stimulus Gap + Sequence Gap 占 I2C 残留 gap 的 67%）。
7. **核心局限**：代码未开源，benchmark 的规格文档和参考模型未发布，依赖 CodeBuddy Agent SDK。Func Cov 83.2% 还有 17pp 的提升空间。
8. **一句话**：GoGoTB 证明了 Agentic 架构可以把 LLM 验证从"不可靠的一次性生成"升级为"可靠的有收敛保证的闭环"，但规格锚定覆盖率的上限由规格完整性和 LLM 定向测试能力共同决定。
