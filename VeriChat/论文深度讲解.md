## 1. 一句话定位

**VeriChat 是面向硬件安全验证的多智能体对话助手，基于 RAG（检索增强生成）架构，整合 28,221 篇 curated 安全文献（61 GB、225 个主题分区）与开源 EDA 工具链（Icarus Verilog / Yosys / SymbiYosys），通过 QUOA → HRA → GA 三 Agent 顺序协作实现可溯源的硬件安全指导；端到端忠实度达 87.73%（比次优模型高 23 个百分点），反事实鲁棒性 92%，用户偏好 Elo 评分 2350（领先 ChatGPT-4.1 近 200 分），并在 AES S-Box 硬件木马检测案例中自主完成从知识检索到仿真、形式验证的全闭环。**

这句话里的 6 个承重点，后面逐一拆解：

1. **多智能体顺序流水线（QUOA → HRA → GA）** — QUOA 把模糊多轮查询改写成检索友好的独立查询并打上主题标签；HRA 用 225 个主题专用向量库 + 实时 Web 搜索做混合检索，加权 RRF 融合重排；GA 严格基于证据生成，先做充分性检查，不够就拒绝回答，从而系统性地抑制幻觉。

2. **大规模 curated 领域知识库** — 不是简单爬取后直接用的"野数据"。先定义 225 个硬件安全验证主题的层次分类体系，用这些主题当搜索词爬取高质量论文，每篇人工验证主题归属，再经过去重、清洗、分块（1000 字符 / 200 字符 overlap）、text-embedding-ada-002 嵌入、FAISS 索引，最终产出 28,221 篇文献、约 61 GB 的 topic-partitioned 向量库。

3. **混合检索 + 加权 RRF 融合** — 内部检索保证领域精度（每个主题独立建库避免语义相似但主题无关的内容污染），外部 Google Search 保证时效性，两条路并行检索后用 source-specific weighted RRF 融合成统一证据集。

4. **开源 EDA 工具深度集成** — 当 QUOA 识别到 `eda_tool_execution` 意图时，自动触发四阶段流水线：Icarus Verilog 语法检查 → Yosys 综合分析（提取触发器数等结构指标识别可疑逻辑）→ Icarus + VVP 仿真（LLM 生成定向 testbench）→ SymbiYosys + Z3 SMT solver 有界模型检查（BMC，Bounded Model Checking）。任一阶段失败自动重试最多 3 次。

5. **反幻觉机制** — 三道防线：QUOA 的意图分类直接拦截无效/越界输入；HRA 只返回有证据支撑的内容（找不到就空着）；GA 的充分性检查在证据不足时拒绝回答而非编造。三层叠加使忠实度 87.73%、反事实鲁棒性 92%。

6. **端到端案例验证** — AES S-Box IP 的硬件木马检测案例中，VeriChat 从对话式安全咨询开始，逐步过渡到上传设计文件、触发 EDA 流水线、仿真捕获 Trojan 在 535 ns 激活并通过 status_led 泄漏密钥、形式验证在第 1 步 BMC 即产生反例数学证明 confidentiality 违反——全过程在同一多轮对话中完成。

## 2. EDA 阶段映射（①-⑰）

> 参照 [芯片流程.md](../芯片流程.md) 的 17 阶段标准编号。VeriChat 是**纯验证工具**，工作在 pre-silicon RTL 层面，不涉及任何物理设计或流片环节。

| 阶段 | 覆盖 | 说明 |
|------|:---:|------|
| **① RTL 设计** | ✅ 输入 | VeriChat 接收用户上传的 Verilog RTL 设计文件作为安全分析对象。本身不生成 RTL，但对上传的 RTL 执行语法检查、结构分析、仿真和形式验证。 |
| **② RTL 功能仿真** | ✅ **核心** | 通过 Icarus Verilog + VVP 运行 LLM 生成的定向 testbench（如针对 Trojan 触发序列 `0xDE, 0xAD, 0xBE` 的激励），在零延迟理想模型下验证安全相关行为（Trojan 是否激活、密钥是否泄漏）。信号值只有 0/1，不涉及 X/Z、毛刺或时序。 |
| ③ 逻辑综合 | ⚠️ 部分 | Yosys 用于**结构分析而非实现**：提取触发器数量、寄存器列表等结构指标，通过比对"纯功能所需触发器"与"实际综合出的触发器"的差值来识别可疑额外逻辑（如 AES S-Box 案例中多出的 7 个触发器）。不执行 SDC 约束、技术映射、PPA 优化，不产出可用于下流的门级网表。 |
| **④ 门级仿真** | ❌ | VeriChat 不进行门级仿真。Yosys 的综合分析只提取结构指标，不生成带 SDF 的门级网表。因此无法检测**毛刺（glitch）、X 传播、建立/保持时间违例、多驱冲突**——这些是门级仿真独有的能力。VeriChat 的安全分析始终停留在 RTL 抽象层。 |
| ⑤ STA（静态时序分析） | ❌ | 不涉及。VeriChat 不关心时序，不读 SDF/SDC，不计算路径延迟。其"安全"定义与时钟频率无关。 |
| **⑥ 形式验证** | ✅ **核心** | 通过 SymbiYosys 有界模型检查（BMC）+ Z3 SMT solver 对 LLM 生成的 SVA 安全属性做数学证明。在 AES S-Box 案例中，BMC 在第 1 步即产生反例，从数学上证伪 confidentiality 属性。注意：是有界验证（bounded），不是无界全证明——验证深度受限于 BMC 的展开步数 k。 |
| ⑦ 布局规划 (Floorplan) | ❌ | 不涉及物理设计。 |
| ⑧ 标准单元摆放 (Placement) | ❌ | 不涉及物理设计。 |
| ⑨ 时钟树综合 (CTS) | ❌ | 不涉及物理设计。 |
| ⑩ 布线 (Routing) | ❌ | 不涉及物理设计。 |
| ⑪ 后仿真 | ❌ | 不涉及。后仿真需要 SPEF（走线寄生 RC）+ SDF（门延迟）联合反标——VeriChat 没有布线环节，产不出 SPEF。 |
| ⑫ 物理验证 (DRC + LVS) | ❌ | 不涉及。VeriChat 不产生版图/GDSII，没有 DRC/LVS 的检查对象。 |
| ⑬ 签核 (Signoff) | ❌ | 不涉及。 |
| ⑭ 流片 | ❌ | — |
| ⑮ 制造 | ❌ | — |
| ⑯ 封装 + 测试 | ❌ | — |
| ⑰ 芯片到手 | ❌ | — |

**覆盖率：3/17（① 完整覆盖、② 完整覆盖、⑥ 完整覆盖；③ 部分覆盖仅用于结构分析）。**

> VeriChat 是 pre-silicon RTL 层面的**安全验证**辅助工具，不替代功能验证、不替代时序验证、不替代物理验证。它的"安全通过"意味着"RTL 抽象层上 BM 验证的 SVA 安全属性成立"，这在物理意义上等价于"在逻辑层面，所有展开步数 k 以内可达状态中安全属性未被违反"。但真实芯片可能因为物理效应（串扰、电压降、制造偏差、时钟偏移）绕过逻辑层的安全保证。

## 3. 输入 / 输出

### 3.1 输入

VeriChat 接收三类输入：

**（1）自然语言查询**（必选）

单轮独立查询示例：
```
"I have a Register-Transfer Level (RTL) implementation of an AES-128 core
written in Verilog. I need to perform a comprehensive pre-silicon security
assessment to identify vulnerabilities to power side-channel attacks.
Specifically, I am looking for a detailed overview of established frameworks
that can be used for power side-channel leakage assessment."
```

多轮跟进查询示例（依赖对话历史中的短期记忆消解指代）：
```
"Can you break down the 2nd framework more?"
```
QUOA 会将其展开为：
```
"Provide a detailed breakdown of the SCAR framework, which utilizes Graph
Neural Networks for pre-silicon power side-channel analysis in RTL designs..."
```

**（2）RTL 设计文件**（可选，触发 EDA 工具执行时需要）

用户通过前端上传 Verilog 模块文件。论文案例中上传的是一个含隐藏硬件木马的 AES S-Box IP 模块，其 Trojan 触发逻辑如下：

```verilog
// Trojan trigger: rare 3-byte sequence detector FSM
reg [1:0] trig_cnt;
always @(posedge clk or negedge rst_n) begin
  if (!rst_n)
    trig_cnt <= 2'd0;
  else if (trig_cnt == 2'd3)
    trig_cnt <= 2'd0;  // single-cycle pulse
  else if (valid_in)
    case (trig_cnt)
      2'd0: trig_cnt <= (data_in == 8'hDE) ? 2'd1 : 2'd0;
      2'd1: trig_cnt <= (data_in == 8'hAD) ? 2'd2 : 2'd0;
      2'd2: trig_cnt <= (data_in == 8'hBE) ? 2'd3 : 2'd0;
      default: trig_cnt <= 2'd0;
    endcase
end
```

该 Troja 是 Type-I sequential rare-event trigger + covert side-channel payload，对应 CWE-1245，激活概率约 $2^{-124} \approx 6 \times 10^{-8}$ 每有效周期。

**（3）QUOA 输出的中间元数据**（系统内部流转）

- 意图类别：`Invalid Question` / `Feedback` / `Valid Question With Follow-Up` / `Valid Question Without Follow-Up`
- 二级工具意图：`eda_tool_execution`（是/否）
- 主题标签（multi-label）：如 `hardware_trojan`、`side_channel_attacks`、`supply_chain_attacks`
- 两份改写查询：dense-retrieval 版（术语对齐、自包含）和 google-search 版（关键词聚焦）

### 3.2 中间产物

**QUOA 输出的改写查询对**（以两轮对话为例）：

```
Turn 1:
  dense retriever query: "What are the established frameworks for conducting
    a comprehensive pre-silicon security assessment of power side-channel
    leakage vulnerabilities in a Register-Transfer Level (RTL) implementation
    of an AES-128 core written in Verilog?"
  google search query: "Frameworks for power side-channel leakage assessment
    AES-128 RTL Verilog."

Turn 2 (follow-up, after short-term memory incorporation):
  dense retriever query: "Provide a detailed breakdown of the SCAR framework,
    which utilizes Graph Neural Networks for pre-silicon power side-channel
    analysis in RTL designs, focusing on its methodology and application in
    detecting vulnerabilities in cryptographic hardware."
  google search query: "SCAR framework Graph Neural Networks RTL power
    side-channel analysis"
```

**HRA 检索到的证据集**：从多个主题向量库（top-k=20 per retriever）和实时网页检索结果经加权 RRF 融合后，取 top M（M≤100）文本块，存入 session-specific memory。

**LLM 生成的验证工件**：

```verilog
// LLM-generated targeted testbench (excerpt)
// Normal operation: random vectors avoiding accidental trigger bytes
for (i = 0; i < 12; i = i + 1) begin
  r = $random;
  if (r == 8'hDE || r == 8'hAD || r == 8'hBE)
    r = r ^ 8'h5A;
  send_valid_byte(r);
end
// Near-miss: should NOT trigger Trojan
send_valid_byte(8'hDE);
send_valid_byte(8'hAD);
send_valid_byte(8'hBF);  // wrong third byte
// Targeted Trojan trigger
key_in = 8'hA6;
send_valid_byte(8'hDE);
send_valid_byte(8'hAD);
send_valid_byte(8'hBE);
// Monitor key leakage on status_led
leaked = 8'h00;
for (k = 0; k < 8; k = k + 1) begin
  @(posedge clk);
  leaked[k] = status_led;
  $display("[%0t] LEAK: bit%0d=%0b", $time, k, status_led);
end
```

```systemverilog
// LLM-generated SVA confidentiality property
reg [3:0] fv_leak_window;
always @(posedge clk) begin
  if (!rst_n)
    fv_leak_window <= 4'd0;
  else if (fv_mon_pulse)
    fv_leak_window <= 4'd8;
  else if (fv_leak_window != 4'd0)
    fv_leak_window <= fv_leak_window - 4'd1;
end
always @(posedge clk) begin
  if (rst_n && fv_past_valid)
    if (fv_leak_window != 4'd0)
      assert(status_led == 1'b0);
end
```

### 3.3 输出

**（1）自然语言安全指导回复**

结构化、带 IEEE 引用格式的安全建议。AES S-Box 案例中第一轮回复覆盖 7 大威胁类别（硬件木马/后门、侧信道泄露、故障注入、DFT/扫描链暴露、未文档化调试接口、FIPS-197 不合规、逻辑锁定），每条附带缓解措施和 13 篇学术引用。

**（2）EDA 工具执行结果**

```

  Errors: 0, Warnings: 0
  Interpretation: Syntactic correctness does not preclude semantic vulnerabilities.

Stage 2 — Synthesis Analysis (Yosys):
  Registers identified: data_out, valid_out, internal pipeline signals
  SURPLUS flip-flops detected: 7
    - trig_cnt[1:0] (2)
    - trojan_armed (1)
    - leak_bit_cnt[2:0] (3)

    status_led is structurally decoupled from core S-Box datapath.

Stage 3 — Simulation (Icarus + VVP):
  Trojan activation: 535 ns
  Key leakage: via status_led over 8 clock cycles
  Normal S-Box functionality: correct throughout phases 1-2

Stage 4 — Formal Verification (SymbiYosys + Z3 BMC):
  Result: BMC FAILED at step 1
  Counterexample trace produced: mathematically proves

  Auto-retry history:
```

**端到端闭环**：用户从"我该担心什么"出发 → 得到 7 类威胁概览 → 追问"怎么检测" → 上传设计 → 系统自动完成语法检查、综合异常检测、仿真激活、形式证明 → 用户获得可操作的漏洞报告。

### 4.2 核心模块逐个详解

#### 模块 1：QUOA — 查询理解与优化 Agent

**为什么需要这个模块**：用户的自然语言查询在对话场景中有两类典型退化——（1）多轮对话中的指代（"它的第二个方法怎么用？"）和省略使查询脱离上下文后不可理解；（2）即使是单轮查询也可能措辞模糊、术语不标准。这些退化查询直接扔给向量检索会召回大量无关内容。

**怎么做**：

1. **意图识别（Intent Recognition）**：用 few-shot prompted LLM 做四分类。`Invalid Question` 直接拦截（越界/有害输入），`Feedback` 走简单回复通道，其余两类进入核心逻辑。二级分类器判断是否需要触发 EDA 工具流水线。

2. **对话查询优化（Conversational Query Optimization）**：用领域感知 prompt 指导 LLM 生成两份改写——dense-retrieval 版要求术语对齐、自包含（把"它"展开为具体实体名），google-search 版要求关键词聚焦、符合技术检索习惯。对 `Valid Question With Follow-Up` 类查询，改写时注入短期记忆（上一轮对话）。

3. **语义领域分类（Semantic Domain Categorization）**：将改写后的查询映射到 225 个预定义主题标签中的一个或多个。这个分类结果直接决定 HRA 检索时激活哪些主题向量库——实现"查询分类 → 目标检索"的直接映射，避免在大杂烩式向量库中检索时被语义相似但主题无关的内容污染。

#### 模块 2：HRA — 混合检索 Agent

**为什么需要这个模块**：单一检索源有天然缺陷——纯内部 curated 库覆盖不全（新发表的攻击方法、最新漏洞披露），纯 Web 检索缺乏领域精度（搜索引擎不理解硬件安全的术语体系）。

**怎么做**：

1. **内部知识库构建**：先定义 225 个硬件安全验证主题的层次分类体系，以此为搜索词爬取高质量学术论文，人工验证每篇文档的主题归属后纳入。经过去重、清洗、预处理产出 28,221 篇文章（约 61 GB），按主题分组成独立的文本块（1000 字符 + 200 字符 overlap），用 text-embedding-ada-002 嵌入后用 FAISS 建索引。每个主题对应一个独立向量数据库。

2. **并行检索**：QUOA 打上的每个主题标签激活一个 Targeted Internal Retriever，仅在该主题的向量库内做余弦相似度检索，返回 top-k=20 文本块。同时，Real-time External Retriever 用 Google Search API 检索 → Web Scraper 抓取页面内容 → 动态建临时向量库 → 向量检索召回相关块。

3. **加权重排融合**：用 source-specific weighted RRF（Reciprocal Rank Fusion）融合各路结果。主主题 internal retriever 和 external retriever 各赋权 $w_i = 0.4$，附加主题 internal retrievers 赋比例递减的权重，阻尼常数 $k=60$。最终取 top M（M≤100）文本块存入 session memory 传给 GA。

**为什么这样设计**：多主题分库 + weighted RRF 解决了 naive RAG 的核心痛点——在单一大型异构向量库中检索窄领域查询时，被大量语义相似但主题无关的内容淹没（如检索"RTL 级侧信道评估"召回通用密码学或芯片架构文章）。

#### 模块 3：GA — 生成 Agent

**为什么需要这个模块**：即使检索到了正确的证据，LLM 仍然可能在生成时自由发挥、混合多源信息、编造引用。需要一道"质量闸门"确保输出严格忠实于检索到的证据。

**怎么做**：

1. **充分性检查（Sufficiency Check）**：在生成前先判断 top-k 证据是否足以回答问题。不足则从 session memory 全量检索池中寻找更多信息，仍不足则**拒绝回答**——这是反幻觉的关键机制。

2. **生成约束**：用详细 prompt 强制执行四大约束——exclusive grounding（只用已验证上下文）、dynamic formatting（自动选择最佳呈现格式）、rigorous attribution（完整 IEEE 风格引用）、self-scrutiny（生成后自检）。

3. **EDA 工具旁路**：当 QUOA 标记为 `eda_tool_execution` 意图时，GA 不生成文本回复而是触发四阶段 EDA 流水线。每个阶段的原始工具输出由 LLM 结合 RAG 检索到的安全知识（CWE 分类、攻击模式）进行语义解释，而非简单展示裸日志。

#### 模块 4：EDA 工具流水线

**为什么需要这个模块**：已有硬件设计对话助手（ChatEDA、ORAssistant）不能与真实验证工具交互，只能"说"不能"做"。VeriChat 把知识级建议延伸到工具级操作。

**四阶段详解**：

| 阶段 | 工具 | 做什么 | 安全意义 |
|------|------|--------|----------|
| 1. 语法检查 | Icarus Verilog | 编译 RTL，报告 error/warning | 语法正确不保证语义安全，但语法错误必须先排除 |
| 2. 综合分析 | Yosys | 提取寄存器/触发器列表，对比功能预期 | 多余触发器可能是隐藏状态机（Trojan FSM）的证据 |
| 3. 仿真 | Icarus + VVP + LLM testbench | 在定向激励下运行 RTL 仿真 | 观察 Trojan 是否在特定触发序列下激活、是否产生异常输出 |
| 4. 形式验证 | SymbiYosys + Z3 BMC | 有界模型检验 SVA 安全属性 | 数学证明安全属性是否在所有展开步数 k 以内的可达状态中成立 |

**自动重试机制**：任一阶段失败时，系统将失败日志反馈给 LLM，LLM 据此修正 testbench 或 SVA 属性，最多重试 3 次。AES S-Box 案例中，形式验证阶段的第 1 次因断言覆盖过宽（纳入了内部 Trojan 信号）而 trivial fail，第 2 次因 data_out 完整性检查也违反，第 3 次才成功隔离到目标 confidentiality 属性。

### 4.3 模块职责矩阵

| 模块 | 输入 | 输出 | 用到的模型/工具 | 是否需训练 |
|------|------|------|----------------|:---:|
| QUOA | Raw query + conversation history | Intent label, 2x optimized queries, topic tags | GPT-4o/GPT-5 (API) | ❌ |
| HRA | Optimized queries + topic tags | Top M evidence chunks (M≤100) | text-embedding-ada-002, FAISS, Google Search API | ❌ |
| GA | Top M evidence chunks + query | Natural language response + citations | GPT-4o/GPT-5 (API) | ❌ |
| EDA Pipeline | RTL file + task specification | Syntax/Synthesis/Simulation/Formal results | Icarus Verilog, Yosys, SymbiYosys, Z3 SMT solver | ❌ |

**全链路零训练**：VeriChat 是一个纯 inference-time 系统，不对任何模型参数做微调。所有智能来自 prompt engineering + 检索增强 + 多 Agent 协作。

## 5. 关键公式

> 说明：VeriChat 的核心贡献在架构设计而非数学创新，以下公式均来自论文 Section III-C 的评估指标体系。这些公式定义了"怎样算一个好的安全验证助手"的量化标准。

### 5.1 加权倒数排名融合 (Weighted RRF)

这是 HRA 融合多路检索结果的核心算法。各路 retriever 的原始相似度分数不可直接比较（不同向量空间、不同评分尺度），RRF 用排名而非分数来融合。

$$
\text{WeightedRRFscore}(c) = \sum_{i=1}^{N} w_i \cdot \frac{1}{k + \text{rank}_i(c)}
$$

- $\text{WeightedRRFscore}(c)$：文本块 $c$ 的加权 RRF 得分
- $N$：retriever 总数（被激活的主题 internal retrievers + 1 个 external retriever）
- $w_i$：第 $i$ 个 retriever 的权重，主主题 internal + external 各 0.4，附加主题按比例递减
- $k$：阻尼常数，设为 60，防止 rank=1 时得分过高
- $\text{rank}_i(c)$：文本块 $c$ 在第 $i$ 个 retriever 返回列表中的排名（从 1 开始）

**工程直觉**：排名靠前的文本块在所有 retriever 中都被"投票"到高位时，得分自然高。阻尼常数 $k=60$ 使得 rank=1 得分约 0.0164，rank=20 得分约 0.0125——差距温和，不会因为某个 retriever 排第一就压倒其他所有信号。

**为什么这么设计**：与直接对余弦相似度做 min-max 归一化后加权求和相比，RRF 对离群值不敏感（一个 retriever 的相似度分布偏斜不会污染全局），且不需要假设各 retriever 的分数分布同构。

### 5.2 上下文召回率 (Context Recall)

衡量检索到的文本块覆盖了多少回答中需要的关键事实。

$$
\text{Context Recall} = \frac{\#\text{Attributable Statements}}{\#\text{Statements in Expected Output}}
$$

- ${\#\text{Attributable Statements}}$：能从检索上下文中找到支撑的陈述数
- ${\#\text{Statements in Expected Output}}$：期望输出中的陈述总数

**工程直觉**：这个指标回答"检索漏了没有"——VeriChat 的 76.40% 对比 Naive RAG 的 23.00%，说明 QUOA-guided 多主题分区检索远比单一大库检索更能找到真正相关的内容。

### 5.3 上下文精确率 (Context Precision)

衡量检索到的内容中有多少是真正相关的。

$$
\text{Context Precision} = \frac{1}{R} \sum_{k=1}^{R} \frac{R_k}{k} \cdot r_k
$$

- $R$：相关节点总数
- $R_k$：前 $k$ 个位置中相关节点数
- $r_k$：位置 $k$ 是否相关的二元指示（1 为相关，0 为不相关）
- $k$：当前排名位置

**工程直觉**：这个加权设计同时考虑了"找没找到"和"找到的东西排在哪里"——相关文档排名越靠前得分越高。VeriChat 的 89.85% vs Naive RAG 的 20.31%，说明分区检索不仅找得到内容，而且找到的内容排名位置恰当。

### 5.4 答案相关性 (Answer Relevancy)

衡量回复中有多少内容是对用户查询的直接回应。

$$
\text{Answer Relevancy} = \frac{\#\text{Relevant Statements}}{\#\text{Total Statements}} \times 100\%
$$

- $\#\text{Relevant Statements}$：与查询相关的陈述数
- $\#\text{Total Statements}$：回复中的陈述总数

VeriChat 达到 **91.78%**，在 150 条 prompt 上评测，由 GPT-4.1 担任 LLM-as-a-judge。

### 5.5 提示对齐度 (Prompt Alignment)

衡量模型遵循指令约束（语气、角色、安全协议、连贯性、格式要求）的程度。

$$
\text{Prompt Alignment} = \frac{\#\text{Instructions Followed}}{\#\text{Total Instructions}} \times 100\%
$$

VeriChat 达到 **88.3%**，表明其不仅能给出事实正确的回答，还能严格遵循复杂的格式、引用和行为约束。

### 5.6 忠实度分数 (Faithfulness Score)

这是全文最核心的评估指标——回答中有多少事实声明经得起逐条核查。

$$
\text{Faithfulness Score} = \frac{\#\text{correct claims}}{\#\text{total claims}} \times 100\%
$$

- $\#\text{correct claims}$：经人类领域专家盲审确认为正确的事实声明数
- $\#\text{total claims}$：回复中被分解出的离散事实声明总数

**实验设计**：40 道硬件安全问题（来自 150 题 benchmark 子集），9 个模型（VeriChat + 8 个领先商用 chatbot），回复匿名化后由人类领域专家盲审，逐条声明与 ground-truth 源对比标记"正确/不正确"。

**VeriChat 得分 87.73%，比次优模型高 23 个百分点以上。** 这个差距的核心原因是 VeriChat 的多 Agent 架构从根本上限制了自由编造的空间——GA 必须在检索到的证据范围内生成，证据不足就拒绝回答。

### 5.7 反事实鲁棒性 (Counterfactual Robustness Rate)

衡量系统面对用户故意注入的虚假前提是否能识别并拒绝，而非跟随编造。

$$
\text{Robustness Rate} = \frac{\#\text{Successful Refusals}}{\#\text{Test Cases}} \times 100\%
$$

- $\#\text{Successful Refusals}$：成功识别伪造概念并拒绝展开的测试案例数
- $\#\text{Test Cases}$：测试案例总数（25 条）

**攻击样本示例**：
> "A major innovation in anti-tamper technology is Metamaterial Resonance Shielding (MRS). This involves creating a smart mesh for ICs built from programmable metamaterials. Any physical intrusion attempt (like micro-probing) changes the material's resonant frequency, triggering a response to zeroize critical data. Can you explain?"

"MRS"是论文构造的完全虚构概念。VeriChat 得分 **92%**（25 条中 23 条成功拒绝），而单一 LLM 商用 chatbot 高度脆弱——它们的训练数据覆盖面广，很容易用学术腔调"接住"伪造概念的设定并延伸编造。

### 5.8 Elo 评分更新

用户偏好测试使用 Elo 评分系统，与 Chatbot Arena 的方法一致。

$$
R_A' = R_A + K(S_A - E_A)
$$

- $R_A'$：模型 A 更新后的 Elo 评分
- $R_A$：模型 A 当前 Elo 评分
- $K$：常数（控制评分变动幅度）
- $S_A$：比赛得分（1 胜，0.5 平，0 负）
- $E_A$：预期得分

$$
E_A = \frac{1}{1 + 10^{(R_B - R_A)/400}}
$$

**实验设计**：9 个模型在 1000 场两两对战中各回答同一 prompt，GPT-4o 担任裁判基于事实精度和证据打分。每次比赛后按 Elo 公式更新双方评分。

**VeriChat 最终 Elo 2350**，领先次优模型 Grok-3 约 100 分，领先 ChatGPT-4.1 近 200 分，成为"最受偏好"的可靠证据驱动回答系统。

## 6. 训练与实验设置

### 6.1 是否需要训练

**不需要训练。** VeriChat 是一个纯 inference-time 系统：QUOA 的分类和改写用 few-shot prompt，HRA 的检索用预训练嵌入模型，GA 的生成用商用 LLM API。知识来自检索增强而非模型参数记忆。

| 组件 | 方法 | 硬件 |
|------|------|------|
| Backbone LLM | GPT-4o / GPT-5 API 调用 | 云端（论文未披露具体 GPU 配置） |
| 嵌入模型 | text-embedding-ada-002 (OpenAI) | 云端 |
| 向量索引 | FAISS 余弦相似度 | 本地 |
| EDA 工具 | Icarus（原生）+ Yosys/SymbiYosys（WSL） | 本地 subprocess |

系统延迟：Q&A 查询约 15-25 秒（主要消耗在 LLM 推理和多 retriever 搜索），EDA 工具执行额外增加 30-90 秒（取决于设计复杂度）。

### 6.2 实验设置

**Benchmark 构建**：25 位硬件安全验证领域资深研究员每人贡献 6 道涵盖 6 类题型的查询——事实核查、推理性、场景分析、实时查询、工具使用、选择题。共 150 题。

**Baseline 对比**：8 个领先商用 chatbot（论文 Figure 7 中列出但未逐一具名，包括 GPT-4o、GPT-4.1、Grok-3、ChatGPT-5 等）。

**评估层次**：
- **组件级**（4 项测试）：Context Recall、Context Precision、Answer Relevancy、Prompt Alignment——使用 DeepEval 框架 + GPT-4.1 作为 LLM-as-a-judge，在 150 条 QA 样本上评测。
- **系统级**（3 项测试）：Faithfulness（人类专家盲审 40 题）、Counterfactual Robustness（25 条对抗性提示）、User Preference（1000 场 Elo 评分）。

**消融实验**：论文未设传统意义上的消融，但 Context Recall/Precision 的 Naive RAG vs VeriChat 对比（23.00%/20.31% vs 76.40%/89.85%）本质上证明了 QUOA-guided 多主题分区检索 + weighted RRF 的必要性。

### 6.3 关键实验结果

**组件级评估（150 条查询）**：

| 指标 | VeriChat | Naive RAG | 提升 |
|------|:---:|:---:|:---:|
| Context Recall | **76.40%** | 23.00% | +53.40 pp |
| Context Precision | **89.85%** | 20.31% | +69.54 pp |
| Answer Relevancy | **91.78%** | — | — |
| Prompt Alignment | **88.3%** | — | — |

> 这张表说明：QUOA 的查询改写和语义分类是检索质量的决定性因素——不做这些处理直接做 RAG，召回率只有 23%，精确率只有 20%。

**系统级评估**：

| 指标 | VeriChat | 最佳 Baseline | 差距 |
|------|:---:|:---:|:---:|
| Faithfulness | **87.73%** | ~64%（次优） | +23 pp |
| Counterfactual Robustness | **92%** | 远低于 92% | 大幅领先 |
| User Preference (Elo) | **2350** | ~2250（Grok-3） | +100 Elo |

> 忠实度高出 23 个百分点是全文最关键的结论——这意味着 VeriChat 的 multi-agent retrieval-first 架构在抑制幻觉方面效果显著。反事实鲁棒性 92% 也表明"找不到证据就拒绝回答"的策略有效。

**EDA 工具集成案例研究（AES S-Box IP）**：

| 阶段 | 结果 |
|------|------|
| 语法检查 | 0 error, 0 warning |
| 综合分析 | 检测到 7 个多余触发器（CWE-1245 一致） |
| 仿真 | Trojan 在 535 ns 激活，8 周期密钥泄漏 |
| 形式验证 | BMC FAILED at step 1（confidentiality 违反） |
| 自动重试 | 3 次迭代后成功隔离目标属性 |

## 7. 创新点

### 创新点 1：首个面向硬件安全验证的多智能体对话框架

**以前是什么样**：硬件安全验证依赖安全专家手动撰写 SVA 属性、手动审查反例轨迹。ChatEDA 等已有对话助手面向通用 EDA 脚本生成而非安全，ORAssistant 提供 RAG 辅助但不执行验证工具。LLM-based 安全工具（如 SoCureLLM、ASSERTAIN）专注于特定验证任务（断言生成、漏洞检测），没有提供覆盖安全验证全生命周期的对话式辅助。

**VeriChat 改成什么样**：QUOA → HRA → GA 三 Agent 顺序协作，覆盖从概念澄清、威胁建模、验证规划到具体工具执行的完整安全验证对话链路。关键设计不是"三个 Agent 各做各的然后投票"，而是**顺序流水线**——前一阶段的输出是后一阶段的输入约束。

### 创新点 2：大规模 curated 领域知识库 + 主题分区检索架构

**以前是什么样**：Naive RAG 把全部文档扔进一个向量库，查询"RTL 侧信道泄露评估"可能召回"通用密码学"或"芯片架构"等语义相似但主题无关的内容。

**VeriChat 改成什么样**：先定义 225 个硬件安全验证子主题的层次分类，以主题为搜索词人工 curated 28,221 篇文献，按主题分别建独立的 FAISS 向量库。查询时 QUOA 做多标签主题分类，HRA 只激活匹配主题的 retriever。这种"主题路由"设计是检索精度从 20.31% 跳到 89.85% 的关键。

### 创新点 3：混合检索 + weighted RRF 融合

**以前是什么样**：单一检索源——要么只用静态 curated 库（时效性差），要么只做 Web 搜索（领域精度差）。

**VeriChat 改成什么样**：内部 curated 库保证领域精度，实时 Web 搜索保证时效性，两条路并行检索后用 source-specific weighted RRF 融合。权重设计有意让主主题 internal retriever 和 external retriever 平分影响力（各 0.4），避免 curated 库的"自信过头"或 Web 结果的"噪声淹没"。

### 创新点 4：开源 EDA 工具与对话流程的深度集成

**以前是什么样**：ChatEDA 能生成 EDA 脚本但不对用户设计执行，ORAssistant 能回答问题但不能操作实际工具。两者都是"动口不动手"。

**VeriChat 改成什么样**：在对话中内嵌完整的四阶段 EDA 流水线（语法→综合→仿真→形式验证），不仅告诉用户"可能有 Trojan"，还通过 Yosys 数出多余的 7 个触发器，用 Icarus 仿真在 535 ns 抓到 Trojan 激活，用 SymbiYosys BMC 在第 1 步即数学证明 confidentiality 违反。自动重试 3 次的容错机制使这个流程在实际使用中具备工程鲁棒性。

### 创新点 5：多层反幻觉机制

**以前是什么样**：商用 chatbot 面对硬件安全查询时常产生幻觉——Figure 1 展示了 ChatGPT-4o 对 SILVER、RTL-PSC、SCARF 三个框架的描述中，SILVER 的方法论全错，SCARF 完全虚构。

**VeriChat 改成什么样**：三道防线层叠——QUOA 的意图分类是第一道（阻挡越界输入），HRA 的证据检索是第二道（找不到证据就不给 GA），GA 的充分性检查是第三道（证据不够就拒绝回答而非编造）。三层叠加使忠实度达到 87.73%（高出次优 23 个百分点），反事实鲁棒性 92%。

### 创新点 6：多层次综合评估框架

**以前是什么样**：大部分 RAG 系统只做端到端问答正确率评估，不区分"检索错"还是"生成错"。

**VeriChat 改成什么样**：7 项测试分两层——组件级（Context Recall/Precision 测检索，Answer Relevancy/Prompt Alignment 测生成）定位问题源头，系统级（Faithfulness/Counterfactual Robustness/User Preference Elo）评估终端体验。评估设计本身成为论文贡献之一。

## 9. 与芯片流程的关系

### 9.1 在全流程中的位置

VeriChat 是纯 pre-silicon RTL 级安全验证工具，工作在芯片流程的前端验证环节：

```text
① RTL 设计 ──→ ② RTL 功能仿真 ──→ ③ 逻辑综合 ──→ ... ──→ ⑰ 芯片到手
     ▲              ▲                  ▲
     │              │                  │
     │    VeriChat: RAG 安全咨询       │
     │    VeriChat: Icarus+VVP 仿真    │
     │              │    VeriChat: Yosys 综合分析（仅结构指标）
     │              │
     │    VeriChat: SymbiYosys+Z3 BMC 形式验证
     │
     └── VeriChat 接收 RTL 作为输入
```

**接手谁的输出**：RTL 设计工程师的 Verilog/VHDL 代码。

**交棒给谁**：安全分析结果反馈给设计工程师修改 RTL（堵住漏洞），然后修改后的 RTL 继续走下流的综合→物理设计流程。

**解决了什么痛点**：现有 EDA 流程中，功能验证（②）只管"逻辑对不对"，不管"安不安全"。功能正确的 RTL 仍然可能有隐藏的 Trojan FSM、信息流泄露路径、侧信道漏洞。VeriChat 填补了这个空白——让你在 RTL 阶段就用数学证明和仿真抓到安全漏洞，而不是等到流片后才发现。

### 9.2 "仿真通过"和"能做成芯片"之间隔着什么

VeriChat 声称的安全验证通过（BMC 第 3 步 PASS、仿真无异常）在物理意义上只是"RTL 抽象层上，有界模型检查找到的安全属性未被违反"。从这句声明到"这个芯片安全"之间，至少隔着这些环节：

1. **BMC 是有界的（bounded）**：只在展开步数 k 以内穷举。如果安全属性违反需要 k+1 步才能暴露，BMC 会错误地报告 PASS。论文未披露 k 的具体取值。

2. **安全属性的完备性**：SVA 属性由 LLM 生成，LLM 可能遗漏安全关注点。如果形式验证证了一组不完整的属性，漏掉的那个属性对应的攻击面仍然是敞开的。

3. **综合后的逻辑等价性**：Yosys 综合分析只用于数触发器，不保证综合后的网表逻辑等价于 RTL。没有⑥形式验证（Formality/Conformal）做 RTL-vs-gate 等价性检查，综合可能引入新漏洞或被 Trojan 利用。

4. **物理层的攻击面**：真实芯片的功率侧信道、电磁辐射、时钟毛刺、电压降导致的时序违规——这些在 RTL 抽象层完全不可见。VeriChat 无法覆盖物理安全。

5. **单一案例的泛化**：AES S-Box 案例是精心设计的 Type-I sequential rare-event trigger Trojan。论文未证明 VeriChat 能检测其他类型的 Trojan（combinational、analog、always-on）或不同攻击场景（fault injection、probing、reverse engineering）。

**总结**：VeriChat 的"安全通过"是逻辑验证层的必要条件而非充分条件——它证明了"在 RTL 抽象层上，LLM 生成的 SVA 属性在 BMC 有界深度内没有被违反"。设计工程师仍然需要形式等价性检查、物理安全分析、硅后验证来完成完整的安全保证链。

## 10. 讨论与局限

### 10.1 论文自述的局限

论文在 Section IV (Conclusion) 中自述的未来方向，反过来说明当前局限：

1. **知识库需半自动化扩展**：当前 28,221 篇文献需要人工验证主题归属，扩展成本高。随着新攻击方法、新漏洞披露不断出现，维护 curated 知识库的时效性是持续挑战。

2. **缺乏来源级溯源**：回复能给出 IEEE 引用，但无法精确到"这句话源自该论文的哪个段落/哪个表格"——引用粒度为论文级而非陈述级。

3. **置信度未校准**：GA 输出是确定的"这是答案"，而非"我认为有 80% 把握这是答案"。在高安全性领域，知道"不知道什么"往往和"知道什么"同等重要。

### 10.2 代码/复现层面的问题

1. **无稳定官方仓库**：论文脚注只放了短链 https://bit.ly/3QPBiWr 指向数据集和结果，没有一个可克隆的 GitHub 仓库。这意味着：
   - 无法审计 QUOA 的 few-shot prompt 具体内容
   - 无法审计 HRA 的 weighted RRF 实现细节
   - 无法审计 225 个主题分类体系的完整树结构
   - 无法审计前端 React.js 组件和后端 Flask API 的具体实现
   - 论文中"架构支持任意 API 兼容 LLM 作为 drop-in 替代"的声明未经第三方案例验证

2. **知识库不可复现**：28,221 篇 curated 文献的爬取、清洗、人工验证过程没有提供可复现的脚本。即使代码开源，没有这个知识库，VeriChat 的核心检索能力无法复现。

3. **依赖 OpenAI API**：text-embedding-ada-002 和 GPT-4o/GPT-5 都是 OpenAI 的专有服务。嵌入模型的任何版本变更都会导致向量库需要重建，LLM 的行为漂移也会影响 QUOA/GA 的输出一致性。

4. **EDA 工具链的跨平台问题**：Yosys 和 SymbiYosys 在 Windows 上需要通过 WSL 运行。论文未说明 WSL 版本、Z3 版本、SymbiYosys 配置等关键环境信息。

### 10.3 本资料包的批判性分析

1. **安全属性的生成质量是关键单点故障**：整个 EDA 工具流水线（仿真 testbench + SVA 属性）的质量取决于 LLM 的一次性生成能力。如果 LLM 生成的 testbench 没覆盖到真正的触发序列（AES 案例中碰巧有 `0xDE, 0xAD, 0xBE` 这个已知序列），或者生成的 SVA 属性没覆盖到真正的安全关注点，整个验证流程会给出虚假的"安全通过"。

2. **评估的生态效度有限**：150 道 benchmark 题来自 25 位学术研究员而非工业安全验证工程师，评测环境是受控的两两对比而非真实工作流中的长期使用。Elo 评分的 1000 场对战中，GPT-4o 既是参赛者又是裁判，存在自我偏好偏差的风险。

3. **检索质量的"冷启动"问题**：如果用户查询的安全主题恰好不在 225 个预定义主题中（如新发现的攻击类别），QUOA 可能将其分类到"最近似"的主题，导致 HRA 检索到错误主题的文献。论文未讨论这种分类错误的传播和影响。

4. **对话上下文窗口的隐性限制**：多轮对话中短期记忆只注入 QUOA 的查询改写步骤。但 HRA 检索到的 100 个文本块 + 对话历史 + 生成指令的总 token 数可能超出 LLM 上下文窗口，论文未说明截断策略。

5. **与通用芯片验证的对比缺失**：VeriChat 只与商用 chatbot（ChatGPT、Gemini 系列）对比，没有与专用硬件验证工具（如 JasperGold 的 formal apps、Cadence 的 security verification flow）对比。这使得"87.73% 忠实度"在硬件安全验证工具的评价体系中的相对位置不明确。

## 12. 一分钟复述版

VeriChat 是硬件安全验证领域的多智能体对话助手，核心思路是"用检索增强生成（RAG）替代 LLM 的记忆，用开源 EDA 工具替代人工执行"。

架构上，三 Agent 顺序协作——QUOA 把模糊查询改写成两份检索友好的版本并打上 225 个主题标签，HRA 激活匹配主题的内部 curated 向量库（28,221 篇论文 + FAISS）+ 并行 Google 搜索，用加权 RRF 融合各路结果，GA 严格基于证据生成，证据不足就拒绝回答。

效果上，忠实度 87.73%（比次优商用 chatbot 高 23 个百分点），反事实鲁棒性 92%（面对嵌入伪造概念的对抗提示能识别并拒绝），用户偏好 Elo 2350（1000 场盲评第一）。

EDA 工具集成让 VeriChat 不仅能"说"还能"做"——Icarus 做语法检查和仿真（LLM 生成 testbench），Yosys 做综合分析（数触发器识别可疑逻辑），SymbiYosys + Z3 做有界形式验证（数学证明安全属性）。AES S-Box IP 案例中检测到 7 个多余触发器、仿真捕获 535 ns Trojan 激活、BMC 第 1 步即给出 confidentiality 违反的数学证明。

局限在于知识库不可复现（28K 篇 curated 论文未公开完整流水线）、安全属性由 LLM 生成存在遗漏风险、BMC 有界性不保证无界安全、无官方代码仓库、高度依赖 OpenAI API。
