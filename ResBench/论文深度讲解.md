## 1. 一句话定位

**ResBench 是首个面向 LLM 生成 HDL 的 FPGA 资源感知 benchmark，它不训练任何模型，而是构建了 56 道覆盖 12 个 FPGA 应用领域的 Verilog 设计题目，在 Vivado 2023.1 + AMD Zynq-7000 真实器件上对 9 个主流 LLM 进行功能仿真和逻辑综合闭环评测，发现 GPT-o1-mini 以 75.1% 的功能通过率和 19 次 LUT 最优次数双领先，并揭示了功能等价的 RTL 实现间可存在百倍级 LUT 差异——例如 `(a+b)^2-(a-b)^2` 未经化简的实现消耗 213 LUT，而 GPT-4 化简为 `4ab` 后仅需 0 LUT + 1 DSP。**

这句话里的四个承重点，后面逐一拆解：

1. **FPGA 资源感知评测维度** — 首次将 LUT/FF/DSP/BRAM/IO 等真实硬件资源效率纳入 LLM 代码生成 benchmark，而不只是语法和功能正确性。传统的 VerilogEval、HDLEval、RTLLM 等只问"代码能不能通过 testbench"，ResBench 追问"通过 testbench 的多个实现中，哪个在目标 FPGA 上更省资源"。
2. **56 题 12 类 FPGA 应用领域** — 题目涵盖从基础组合逻辑、FSM、流水线、多项式求值到机器学习、金融计算、加密、物理建模、气候计算等真实 FPGA 工作负载。题目设计遵循"资源使用差异化"和"FPGA 应用多样性"两条指导原则，使得不同 LLM 的资源优化能力在 benchmark 上产生显著分歧。
3. **Vivado 真实综合闭环** — 不是做文本检查或 lint，而是在 AMD Zynq-7000 XC7Z020CLG400-1 SoC 上运行 Vivado 2023.1 行为仿真和逻辑综合，每道题每个 LLM 生成 15 个候选，功能通过者进入综合提取 LUT/FF/DSP/BRAM/IO 数值，功能失败记为 LUT=∞。
4. **功能正确不等于资源最优** — 论文通过 `(a+b)^2-(a-b)^2` 化简为 `4ab` 等典型案例，证明 LLM 生成的 Verilog 可以在 testbench 全过的前提下，LUT 消耗相差数百倍。这是 ResBench 区别于所有前人 benchmark 的核心洞察。

## 2. EDA 阶段映射（①-⑰）

参照 [芯片流程.md](../芯片流程.md) 的 17 阶段标准编号：

| 阶段 | 覆盖 | 说明 |
|------|:---:|------|
| **① RTL 设计** | ✅ **核心** | LLM 根据自然语言规格 + 固定 module header 生成 Verilog RTL，含 15 个候选/题，temperature=1.5 |
| **② RTL 功能仿真** | ✅ **核心** | Vivado 2023.1 behavioral simulation + 手写 testbench，判定标准为 stdout 含 `All tests passed` |
| **③ 逻辑综合** | ✅ **辅助** | Vivado `synth_design` 将功能正确的 RTL 映射到 AMD Zynq-7000 XC7Z020CLG400-1，提取 LUT/FF/DSP/BRAM/IO 资源数值 |
| ④ 门级仿真 | ❌ | 不做 SDF 反标门级仿真，不检查毛刺、建立/保持违例、X 传播。论文综合后仅读 utilization report，不跑 gate-level simulation |
| **⑤ STA（静态时序分析）** | △ **部分** | Vivado summary 报告了 hold/setup TNS/WNS 作为时序质量参考，但论文主实验不以时序指标为排名依据，也未施加 clock constraint |
| ⑥ 形式验证 | ❌ | 不做 SAT/SMT 等价性证明，功能正确仅由 testbench 有限测试向量定义 |
| ⑦ 布局规划 Floorplan | ❌ | ResBench 只做到综合（synthesis），不进入 implementation 流程 |
| ⑧ 标准单元摆放 Placement | ❌ | — |
| ⑨ CTS（时钟树综合） | ❌ | — |
| ⑩ 布线 Routing | ❌ | — |
| ⑪ 后仿真 | ❌ | 无 SPEF 寄生参数提取，无走线延迟反标 |
| ⑫ 物理验证 DRC+LVS | ❌ | — |
| ⑬ 签核 Signoff | △ **部分** | 综合资源报告 + 时序报告构成 FPGA 实现质量的初步评估，但未到 placement/routing 及完整物理签核 |
| ⑭ 流片 | ❌ | — |
| ⑮ 制造 | ❌ | — |
| ⑯ 封装 + 测试 | ❌ | — |
| ⑰ 芯片 | ❌ | — |

**覆盖率：2.5/17。** ResBench 是一个**前端 RTL 生成 → 功能仿真 → 综合资源评估**的 benchmark 框架。它在阶段 ① 输入 LLM 生成的 RTL，经过阶段 ② 功能仿真过滤，在阶段 ③ 逻辑综合层面提取资源指标。与 VerilogCoder（只到 ②）、MAGE（只到 ②）相比，ResBench 多推进了一步综合，但它不进入物理实现（placement/routing），因此报告的 LUT/FF/DSP/BRAM 数值是**综合后估计**而非布局布线后的最终资源占用。

> **ResBench 的"资源评估"与真实 FPGA implementation 之间的边界**：综合后的 LUT 数不等于 place & route 后的实际资源占用。Vivado 综合阶段的资源估计相对准确，但 placement 拥塞、routing 资源不足、时序闭合等因素可能导致最终实现与综合估计有偏差。论文明确将自身定位为"综合后资源估计 benchmark"，而非完整 FPGA implementation PPA benchmark。

## 3. 输入 / 输出

### 3.1 输入

ResBench 的输入是一套结构化的 benchmark 数据，每道题包含三个组件。

**（a）自然语言问题描述（`Problem` 字段）**

```text
Implement parity of an 8-bit vector. The module has an 8-bit input 'in'
and a 1-bit output 'out'. Output 1 if the number of 1s in 'in' is odd.
```

**（b）固定模块头（`Module header` 字段）**

```verilog
module parity_8bit(input [7:0] in, output out);
```

LLM 不可修改端口名称和位宽，仅需填充模块内部逻辑。

**（c）手写 testbench（嵌入 `problems.json`）**

每道题的 testbench 包含 reference module 实现（LLM 不可见），用于 Vivado behavioral simulation 的输入激励和输出比对。判定条件为仿真输出包含 `All tests passed`。

**（d）LLM 采样配置**

| 参数 | 值 |
|------|-----|
| 每题候选数 | 15 |
| Temperature | 1.5 |
| top_p | 0.75（仓库配置） |
| max_tokens | 3000 |
| 输出格式 | JSON `{"solution": "<verilog>"}` |
| SystemVerilog | prompt 明确禁用 |

**（e）目标器件**

```text
器件：AMD Zynq-7000
Part：xc7z020clg400-1
工具：Vivado 2023.1
时钟：默认频率（论文未施加显式 clock constraint）
```

### 3.2 中间产物

**（a）候选 Verilog 代码集（`solutions.json`）**

每模型 56 题 × 15 候选 = 840 份 Verilog 候选，仓库已发布 9 个模型共 7,560 份历史候选。

```json
{
  "gpt-4o": {
    "Combinational Logic": [
      {
        "parity_8bit": {
          "solution": "module parity_8bit(input [7:0] in, output out);\n  assign out = ^in;\nendmodule",
          "pass": "true",
          "resource": {
            "optimized": {"LUT": 1, "FF": 0, "DSP": 0, "BRAM": 0, "IO": 9},
            "primitives": {"LUT": 1, "FF": 0, "DSP": 0, "BRAM": 0, "IO": 9}
          }
        }
      }
    ]
  }
}
```

**（b）Vivado 仿真日志与综合报告**

功能仿真输出包含 `All tests passed` 标记；综合输出为 `resource_usage.rpt`，解析字段包括 `optimized.LUT`、`optimized.FF`、`optimized.DSP`、`optimized.BRAM`、`optimized.IO`。

### 3.3 输出

ResBench 的最终输出是一套**双重评测报告**：

**（a）功能正确性三分类表（论文 Table 4）**

每单元格格式：`pass / synthesis OK but incorrect design / synthesis error`，三者之和 = 类别题数 × 15。

**（b）资源使用 LUTmin 表（论文 Table 5）**

每道题各模型的最小 LUT 值，功能失败/综合失败的候选记 LUT=∞，从而自然排除。

**（c）可视化产物**

ordered first-k 热图、overall pass@k 曲线（仓库已提供预生成图片）。

## 4. Benchmark 构建方法

ResBench 不是一个生成模型，而是一个**端到端评测 harness**。本节详细说明其题目来源与设计原则、数量与难度分层、参考实现与质量把关流程，以及自动化评测流水线。

### 4.1 题目来源与设计原则

ResBench 的 56 道题并非从现有题库（如 HDLBits）直接搬运，而是作者针对 FPGA 资源感知评测需求**全新设计**。题目设计遵循两条核心原则：

**原则一：资源使用差异化（Principle of Resource Usage Differentiation）**

题目必须允许多种资源优化策略，使得不同 LLM 的实现即使功能等价，也能在 LUT/DSP 等资源指标上产生可量化的差异。典型手段包括：

- 代数化简：`(a+b)^2-(a-b)^2` 可化简为 `4ab`，LUT 消耗从 213 降至 0（转用 1 个 DSP）
- 多项式重排：`x^3+3x^2+3x+1` 即 `(x+1)^3`，展开式 vs 因式分解的 LUT 差异显著
- DSP inference：乘法是否由综合器推断映射到 DSP 硬核 vs 用 LUT 搭乘法器

**原则二：FPGA 应用多样性（Principle of FPGA Application Diversity）**

题目覆盖 12 个真实 FPGA 应用领域，既有基础数字逻辑练习题，也有高层算法实现题，确保 benchmark 不只是测"LLM 会不会写 AND 门"。

### 4.2 题目数量与难度分层

12 类 56 题的具体分布（对应论文 Table 2）：

| 类别 | 题数 | 代表题目 | 难度特征 |
|------|:---:|------|------|
| Combinational Logic | 8 | `parity_8bit`, `mux4to1`, `bin_to_gray` | 基础：纯组合逻辑，无状态，LUT 差异小 |
| Finite State Machines | 4 | `fsm_3state`, `traffic_light`, `elevator_controller` | 中等：需正确建模状态寄存器 + 转移逻辑 |
| Mathematical Functions | 5 | `int_sqrt`, `fibonacci`, `mod_exp` | 高：需理解迭代/递归算法的硬件映射 |
| Basic Arithmetic Operations | 5 | `add_8bit`, `mult_4bit`, `abs_diff` | 基础：算术运算，但位宽和溢出需正确处理 |
| Bitwise and Logical Operations | 4 | `bitwise_ops`, `left_shift`, `rotate_left` | 基础：位操作，移位语义需精确 |
| Pipelining | 5 | `pipelined_adder`, `pipelined_multiplier`, `pipelined_fir` | 高：需理解流水线时序和延迟语义 |
| Polynomial Evaluation | 5 | `(x+2)^2+(x+2)^2+(x+2)^2`, `(a+b)^2-(a-b)^2` | 中等：代数化简能力决定 LUT 消耗 |
| Machine Learning | 5 | `matrix_vector_mult`, `relu`, `mse_loss` | 高：涉及矩阵运算、激活函数等实际加速器场景 |
| Financial Computing | 4 | `compound_interest`, `present_value`, `currency_converter` | 高：需处理定点/整数近似的金融公式 |
| Encryption | 3 | `caesar_cipher`, `modular_add_cipher`, `feistel_cipher` | 高：密码学算法涉及移位、替换、模运算 |
| Physics | 4 | `free_fall_distance`, `kinetic_energy`, `wavelength` | 中等：物理公式的硬件实现 |
| Climate | 4 | `carbon_footprint`, `heat_index`, `air_quality_index` | 中等：环境模型公式的多项式展开 |
| **合计** | **56** | — | — |

**难度分层逻辑**：基础题（组合逻辑、算术、位操作）的 LUT 差异小（各模型训练数据中已有标准解），但功能正确率高；高层应用题（流水线、金融、加密、ML）的功能正确率和资源效率差异大，是区分 LLM 能力的关键区域。

### 4.3 参考实现与质量把关流程

每道题的手写 testbench 中嵌入了 **reference module**（`good1` 实例），该模块是作者人工编写的功能正确实现，用于：

1. 作为行为仿真的 golden reference 输出
2. LLM 生成的 DUT（`top_module1` 实例）输出与之逐周期比对
3. 但 reference 的 RTL 实现细节对 LLM 完全不可见（LLM 只拿到自然语言规格和模块头）

**质量把关流程**（从 benchmark 设计的规范性推断）：

- 每题 testbench 均包含 `All tests passed` marker，确保判定逻辑一致
- 55/56 题 testbench 显式包含 `$finish`，防止仿真挂死
- 题目经过 Vivado 2023.1 行为仿真验证，确保 reference 实现本身功能正确
- 所有模型在同一器件、同一 Vivado 版本、同一策略下评测，消除工具链差异干扰

## 5. 关键公式

ResBench 论文给出了明确的 LUT 资源评分公式，以下按原文编号呈现。

### 5.1 单候选 LUT 评分（论文公式 1）

$$
\text{LUT}(d_i) =
\begin{cases}
\text{LUT count}, & \text{if } d_i \text{ is synthesizable and correct} \\[4pt]
\infty, & \text{otherwise}
\end{cases}
$$

- $d_i$：第 $i$ 个 LLM 生成的候选设计
- $\text{LUT count}$：Vivado 综合后 `optimized.LUT` 数值
- $\infty$：表示该候选不可综合或功能不正确，从后续资源比较中被自然排除

**工程直觉**：用 $\infty$ 而非 0 来表示失败候选，堵住了一条关键投机路径——"什么逻辑都没实现，LUT=0，所以胜出"。这个设计使得功能失败的设计不可能在资源维度上获得优势。

**为什么这么设计**：如果失败候选的 LUT 记为 0，针对简单题目（如 `assign out = 0;`），一个"全错但 LUT 极小"的设计会污染排名。$\infty$ 天然地将"功能正确"设为资源比较的前提条件，避免了指标博弈。

### 5.2 每题最小 LUT（论文公式 2）

$$
\text{LUT}_{\min} = \min(\text{LUT}(d_0), \text{LUT}(d_1), \ldots, \text{LUT}(d_{n-1}))
$$

- $n$：每题 LLM 生成的候选总数，论文固定 $n = 15$
- $\text{LUT}_{\min}$：该题所有功能正确且可综合候选中的最小 LUT 值

**工程直觉**：这是"LLM 在某题上能生成的最佳资源效率"的保守估计。取 min 而非 mean 反映了一种实用主义——在实际工程中，工程师只要从 LLM 的 15 个候选中挑出最好的那个就够了。

**为什么是 min 不是 mean**：取平均会惩罚生成多样性（如果一个 LLM 有时生成极优方案、有时生成平庸方案，mean 可能反而低于一个"始终生成中等方案"的 LLM）。min 更适合回答"这个 LLM 在最好情况下能生成多省资源的 RTL"。

### 5.3 LUT win 数定义（论文未编号，从 Table 5 和正文提取）

对每道题 $p$，定义该题所有模型中的全局最小 LUT：

$$
\text{LUT}_{\text{global\_min}}(p) = \min_{m \in \mathcal{M}} \text{LUT}_{\min}(p, m)
$$

模型 $m$ 的 win 数定义为它在多少道题上取得了 $\text{LUT}_{\text{global\_min}}(p)$（允许并列）：

$$
\text{wins}(m) = \left|\left\{ p \mid \text{LUT}_{\min}(p, m) = \text{LUT}_{\text{global\_min}}(p) \right\}\right|
$$

- $\mathcal{M}$：所有评测模型的集合（论文含 9 个模型）
- $p$：题目标识符，$p \in \{1, 2, \ldots, 56\}$
- $\text{LUT}_{\min}(p, m)$：模型 $m$ 在题目 $p$ 上的最小 LUT
- $\text{wins}(m)$：模型 $m$ 的 LUT win 数

**工程直觉**：win 数是"这个 LLM 在多少道题上给出了最省资源的实现"。并列 win 设计意味着如果多个模型在同一题上取得相同的最小 LUT，它们都计入 win——这避免了因随机波动（如综合器在不同候选上产生相同 LUT）导致的不公平。

## 6. 评测协议与打分

这一节回答 benchmark 论文必须回应的四个核心问题。

### 6.1 评测什么能力？

ResBench 评测 LLM 的**两项核心能力**：

1. **功能正确性**：LLM 能否从自然语言规格 + 固定接口头生成在 Vivado 行为仿真中通过 hand-crafted testbench 的 Verilog RTL。评测的底层能力是 LLM 对硬件描述语义的理解（组合逻辑、时序逻辑、状态机、流水线、算术运算的精确编码）。

2. **FPGA 资源优化意识**：在功能正确的前提下，LLM 生成的设计能否以较少的 FPGA 资源（LUT/FF/DSP/BRAM/IO）实现。评测的底层能力包括代数化简能力（如识别 `(a+b)^2-(a-b)^2 = 4ab`）、硬件结构选择能力（乘法用 LUT 搭还是 map 到 DSP）、以及对 FPGA 器件特性的隐式理解。

### 6.2 怎么打分？

**功能维度**：每题 15 个候选，直接计数通过行为仿真的候选数。论文不使用标准 Pass@k 无偏估计，而是直接统计三分类（pass / synthesis OK but incorrect / synthesis error）。

**资源维度**：取每题功能正确候选中的最小 LUT 作为该模型在该题的资源得分（见第 5 节公式）。在所有 9 个模型中比较，计数每模型取得全局最小 LUT 的题目数（win 数）。

**为什么不使用 Pass@k**：论文明确指出，"we intend to distinguish designs that fail hardware synthesis from those that successfully synthesize but do not meet functional correctness requirements"。三分类提供了比 Pass@k 更细粒度的诊断信息——它能区分"LLM 写不出合法 Verilog（synthesis error）"和"LLM 写出了合法 Verilog 但逻辑不对（synthesis OK but incorrect）"。

**附加指标**：仓库同时记录 FF、DSP、BRAM、IO 以及 Vivado summary 中的 hold/setup TNS/WNS，但论文主表仅以 LUT 为资源排名指标。

### 6.6 局限性在哪？

1. **单一 LUT 指标可能诱导资源转移**：最小化 LUT 可能将成本转移到 DSP/BRAM（如 `(a+b)^2-(a-b)^2` 0 LUT + 1 DSP），完整评价需多目标 Pareto front。
2. **公开 testbench 污染风险**：`problems.json` 包含完整 testbench，后续模型可能针对性过拟合。
3. **问题集偏向组合/算术逻辑**：虽然覆盖 12 类，但组合逻辑与算术运算占比高，需扩展更多时序、流水线设计。
4. **不是完整 FPGA implementation**：只做到综合，未进入 place & route，报告的 LUT 是综合后估计。
5. **Vivado 工具链绑定**：结果依赖 Vivado 2023.1 和 AMD Zynq-7000，不能直接与 Yosys/nextpnr 开源流程的结果混比。

## 7. 创新点

### 创新点 1：首次将 FPGA 资源效率纳入 LLM 代码生成基准评测

**已有 benchmark 的做法**：VerilogEval（2023）、HDLEval（2024）、RTLLM（2024）、VHDL-Eval（2024）、GenBen（2024）均以功能正确性（Pass@k、testbench pass、形式验证）为主要甚至唯一评测维度。两个功能等价但 LUT 消耗相差百倍的实现，在这些 benchmark 上得分完全一样。

**ResBench 的做法**：在功能正确的基础上增加一层硬件代价维度。所有通过功能仿真的候选都要经过 Vivado 综合，提取真实 LUT/FF/DSP/BRAM/IO 数值，并在同题候选中取最小 LUT 作为模型在该题的资源得分。这实现了从"能不能跑通 testbench"到"跑通的方案哪个在真实 FPGA 上更省面积"的评测跃迁。

**证据**：`(a+b)^2-(a-b)^2` 一题，Qwen-2.5 的直接展开（213 LUT）和 GPT-4 的代数化简（0 LUT + 1 DSP）在功能仿真中都输出 `All tests passed`，但硬件资源消耗天差地别。只有 ResBench 的评测框架能揭示这种差异。

### 创新点 2：两条指导原则设计了 56 题 12 类的差异化题库

**资源使用差异化原则**：题目设计中刻意引入需要代数化简、数学变换、硬件结构选择等"超越语法层面"的优化空间。不是每道题都有优化余地——简单的 `parity_8bit` 各模型实现几乎无差异——但在多项式求值、流水线、数学函数等类别上，不同 LLM 的实现产生了数百倍的 LUT 差异。

**FPGA 应用多样性原则**：12 个类别中有 6 个是高层应用领域（ML、金融、加密、物理、气候），而非仅覆盖基础数字逻辑。这在 LLM 评测中引入了领域知识的维度——例如 `compound_interest`（复利计算）、`heat_index`（热指数）需要 LLM 理解金融/气象公式并正确映射到硬件实现。

### 创新点 3：揭示"功能正确不等于资源最优"的核心洞察

这不是 ResBench 的工程创新，而是它的核心科学贡献。论文通过大规模实验（9 模型 × 56 题 × 15 候选 = 7,560 份 RTL）系统性地证明了：**在功能正确的候选集合内部，资源消耗的差异可以跨越两个数量级**。这个洞察为后续研究（如 ChipSeek 的 RL 资源优化）提供了直接动机。

### 创新点 4：开源完整的 benchmark + 历史 artifact

ResBench 不仅发布了题目和评测代码，还发布了 9 个模型完整的 7,560 份历史候选及其功能标记和资源数值。这为后续研究者提供了无需重新调用昂贵 LLM API 和运行 Vivado 即可进行静态分析的 artifact。同时也建立了 LLM 生成 RTL 资源效率的基线，后续模型可以直接与已发布数据进行对比。

## 9. 与芯片流程的关系

### 9.1 在全流程中的位置

```text
  人类设计规格 + 固定模块头 + 手写 testbench
              │
              ▼
  ┌──────────────────────────────────────────────────┐
  │  ① RTL 设计  ←──────────────────────────┐       │
  │      │                                   │       │
  │      ▼                                   │       │
  │  ② RTL 功能仿真（Vivado behavioral sim）  │       │
  │      │                                   │       │
  │      ▼                                   │       │
  │  ③ 逻辑综合（Vivado synth_design）───────┘       │
  │      提取 LUT/FF/DSP/BRAM/IO                      │
  └───────────────────┬──────────────────────────────┘
                      │  ⚠️ ResBench 在此交棒
                      │     综合后资源报告 = 最终输出
                      ▼
        ④ 门级仿真  ⑤ STA  ⑥ 形式验证
                      ▼
        ⑦ Floorplan → ⑧ Placement → ⑨ CTS → ⑩ Routing
                      ▼
        ⑪ 后仿真 → ⑫ DRC/LVS → ⑬ Signoff → ⑭ 流片 → ⑮ 制造 → ⑯ 封测 → ⑰ 芯片
```

ResBench 接手的是 LLM 生成的 RTL 文本，经过功能仿真和综合后，产出资源评估报告。它在流程上的进步（相对于只到 ② 的 VerilogCoder/MAGE）是推进到了综合层面，提取了真实器件上的资源数值。但它不替代后续物理实现验证——综合后 LUT 估计与 placement/routing 后的实际资源占用可能存在偏差。

### 9.2 「功能正确 + 低 LUT」和「能做成芯片」之间隔着什么

ResBench 的 "pass + low LUT" 只保证**给定 testbench 全通过 + 综合后 LUT 估计低**。以下环节未被覆盖：

**综合到实现的鸿沟**：综合后的 LUT 数不等于布局布线后的实际资源。Placement 拥塞可能导致工具使用更多 LUT 来满足时序；Routing 资源不足可能导致设计无法布线。一个"综合后 LUT 极低"的设计可能因为布线拥塞而无法实现。

**时序闭合风险**：论文未施加 clock constraint，综合工具以最小面积为目标而非满足特定时序。如果施加 200MHz 时钟约束，许多"低 LUT"实现可能因组合逻辑路径过长而无法满足时序。

**DSP vs LUT 的隐藏权衡**：0 LUT + 1 DSP 的实现在 DSP 资源紧张的设计中未必优于 213 LUT 的实现。真实的 FPGA 设计需要在多维度资源（LUT/FF/DSP/BRAM）之间做 Pareto 最优选择，而不仅是单一 LUT 最小化。

**testbench 覆盖不足**：功能正确仅相对于 testbench 有限测试向量。流水线设计的延迟级数、valid/ready 握手行为、复位语义等可能未被充分覆盖。形式验证（⑥）才能证明对所有输入的等价性。

## 10. 讨论与局限

### 10.1 论文自述的局限

1. **单一 LUT 指标可能诱导资源转移**：追求最小 LUT 可能增加 DSP/BRAM 使用（如 `(a+b)^2-(a-b)^2` 案例），需引入 LUT/FF/DSP/BRAM 多目标 Pareto 评估。
2. **功能正确性前提过强**：约 25-60% 候选功能错误，被排除在资源比较之外，应同时报告功能覆盖率与资源效率的联合指标。
3. **问题集偏向组合/算术逻辑**：虽然覆盖 12 个领域，但组合逻辑与算术运算占比较高，未来需扩展更多时序、流水线、状态驱动电路。
4. **工具与器件绑定**：结果依赖 Vivado 2023.1 与 AMD Zynq-7000。使用 Yosys/nextpnr 等不同综合器可能改变绝对 LUT 数，但相对效率预计稳定。
5. **仅支持 Verilog**：未来需扩展至 VHDL 和 HLS。
6. **未包含完整的 timing/power 评估**：论文主要关注资源使用，未施加 clock constraint，未评估动态功耗。

### 10.2 代码/复现层面的问题

以下问题整理自本地代码审计 [ResBench论文与代码复现详解](./ResBench论文与代码复现详解.md)：

1. **入口导入错误**（阻断级）：`setup.py` 从 `functional_correctness` 导入 `run_resource_usage`，但该函数实际定义在 `resource_usage.py`。README 的标准命令在 import 阶段即失败。
2. **`top_module` 作用域错误**（阻断级）：`write_tcl()` 直接引用 `top_module`，但该变量是调用函数的局部变量而非全局变量，运行时触发 `NameError`。
3. **两题字段大小写不一致**：`ddm` 和 `feistel_cipher` 使用 `Module Header`（H 大写），而生成器读取 `Module header`（h 小写），导致这两题发送给 LLM 的模块头为空字符串。
4. **错误过滤恒真**：`if "error" or "fail" in line.lower()` 逻辑恒为 True（非空字符串 `"error"` 永远为真），导致所有仿真日志行都被标记为错误。
5. **可视化 bug**：`plot_pass.py` 将 pass@15 的值重复填入 k=1 到 k=15 的所有位置，生成的 heatmap 文件名不同但内容相同。
6. **论文 Table 5 与发布 CSV 存在数值差异**：`power` 题 GPT-4o 的 LUT，论文报告 93，发布 CSV 为 74。缺少原始 Vivado log 无法判定哪个是正确的。
7. **无 timeout 和独立工作区**：Vivado 子进程无 timeout 限制，多题共用固定文件和 project 名，并行执行会互相覆盖。
8. **多模型完整 runner 缺失**：当前仅实现 OpenAI API adapter，论文报告的 Llama3.1、Qwen 系列、Codestral 的生成脚本未开源。
9. **78 个功能通过候选无 LUT 数值**：发布 artifact 中 4,621 个 pass 候选中有 78 个没有 numeric `optimized.LUT`（综合成功但报告解析失败或综合失败），状态表达不够精细。
10. **无根 LICENSE**：仓库根目录无许可证文件。

### 10.3 评测公平性与可信度分析

**指标设计的公平性**

LUT 作为主指标的局限性已在前文讨论（DSP/BRAM 转移）。更根本的问题是：**LUT 最小化是否真的对应"更好的 FPGA 设计"？**

- 在资源充裕的场景下（设计只占 FPGA 的 10%），LUT 多 50 个无关紧要
- 在资源紧张的场景下（设计需榨干 FPGA 的 90%），每个 LUT 都很关键
- 在时序敏感的场景下，更多的 LUT 可能意味着更短的组合逻辑路径（逻辑复制、面积换速度）

ResBench 的 LUT 排名是一个**方向性**指标（低 LUT 通常更好），但不是**决定性**指标（不能仅凭 LUT win 数断言一个 LLM 比另一个更适合 FPGA 设计）。

**评测的一致性风险**

- **Vivado 综合的随机性**：Vivado synthesis 的结果在相同 RTL 输入下可能随 seed/strategy 变化。论文使用默认策略且未记录 seed，不能排除 LUT 数值受综合器内部随机因素影响。
- **模型版本的不可冻结性**：`gpt-4`、`gpt-4o` 等闭源模型的服务端版本随时间变化，今天的 API 调用结果可能与论文实验当时不同。
- **testbench 污染风险**：`problems.json` 已公开包含完整 testbench，后续模型可能针对性过拟合。论文建议引入隐藏测试或形式属性验证。
- **论文数值与 CSV 数据的一致性**：`power/GPT-4o` 的 LUT 在论文（93）和 CSV（74）之间存在差异，缺少原始 Vivado 综合日志无法确定哪个是最终权威值。这降低了将论文 Table 5 数值直接用于下游研究的可信度。

**与同类 benchmark 的可比性**

ResBench 不能直接替代 VerilogEval/RTLLM，而应作为它们的**互补评测层**。建议的评测链：

```text
VerilogEval / RTLLM：功能正确性基线
        ↓
ResBench：FPGA 资源效率差异化
        ↓
（未来）完整 FPGA PPA benchmark：placement/routing + timing/power
```

**跨工具链的可迁移性**

论文结果依赖 Vivado 2023.1 的特定综合策略和器件库。使用 Yosys/nextpnr 开源流程重跑无法直接与论文 Table 5 数值比较——因为 LUT 架构（XC7 vs generic）、tech mapping 规则、DSP inference 策略均不同。正确的对照方式是比**排名稳定性**（同一候选在 Vivado 和 Yosys 下的 LUT 排名是否一致），而非**绝对数值**。

## 12. 一分钟复述版

ResBench（Imperial College London，HEART 2025）是**首个面向 LLM 生成 HDL 的 FPGA 资源感知 benchmark**，不训练任何模型，而是构建了一套完整的自动化评测框架。

核心四要素：

1. **题库设计**：56 题 12 类，从基础组合逻辑到机器学习、金融计算、加密等真实 FPGA 应用领域。题目刻意设计为允许多种资源优化策略（如代数化简 `(a+b)^2-(a-b)^2 = 4ab`），遵循"资源使用差异化"和"FPGA 应用多样性"两条原则。

2. **评测流水线**：LLM 生成 15 个候选/题 → Vivado 2023.1 行为仿真（testbench 通过 = 功能正确）→ Vivado 综合（提取 Zynq-7000 XC7Z020 的 LUT/FF/DSP/BRAM/IO）→ 同题候选取 min LUT → 跨模型比较 win 数。功能失败记为 LUT=∞，堵住"不实现逻辑=零资源"的投机。

3. **核心发现**：GPT-o1-mini 功能正确率 **75.1%**（631/840）和 LUT win 数 **19** 次双领先，推理模型在资源优化上系统性优于代码专用模型（Qwen2.5-Coder 仅 7 次 win、Codestral 仅 8 次）。代码专用模型的训练语料以软件代码为主，缺乏 FPGA 硬件约束的理解。功能等价实现间 LUT 差异可达百倍。

4. **评测贡献**：从"过不过 testbench"推进到"通过的实现哪个更省硬件"。基准数据 + 7,560 份历史候选已开源，为后续资源感知 RTL 生成研究（如 ChipSeek 的 RL reward）提供了量化基线。

**边界**：覆盖流程 ①-③（2.5/17），只到综合后资源估计而非完整 FPGA implementation；单一 LUT 指标可能诱导 DSP/BRAM 转移；公开 testbench 存在污染风险；代码有 2 个阻断级 bug 和 1 处论文/CSV 数值差异；78 个功能通过候选无 LUT 数值；依赖 Vivado 2023.1 商业工具而非开源流程。
