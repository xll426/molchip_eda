## 1. 一句话定位

**CLOSER-Bench 是首个将硬件 Agent 评测从「独立任务完成」升级为「预算约束下的跨阶段设计闭合（design closure）」的评测基准。** 它通过 stage-paired 任务设计（spec->RTL、RTL->GDS、spec->GDS）把单阶段编码能力与跨阶段协调决策能力分离开，用 anytime progress 轨迹指标（AUC_B、stagnation、rollback 精确率）替代传统 pass/fail。10-task pilot 的核心发现：三个 Agent 在 AXI 修复任务上全部满分，但在验证闭合任务上 Codex 满分、Big-Pickle 仅 0.0588、DeepSeek-V4 直接误报——completion 不等于 closure。

这句话里的 5 个技术承重点：

1. **Stage-Paired 任务设计** — 从同一个设计规格和隐藏条件出发，派生 spec->RTL（Task A）、RTL->GDS（Task B）、spec->GDS（Task C）三个 track，共享功能子集和签核 oracle。通过对比 A+B vs C 的聚合预算表现，分离「单阶段编码能力」与「跨阶段协调能力」。

2. **预算约束下的序列决策** — 不只看最终答案对不对，而是记录每次仿真、综合/STA（Static Timing Analysis，静态时序分析）、完整 PnR（Place and Route，布局布线）调用，计算在有限预算内 Agent 能否有效率地达到 design closure。预算分 Low/Medium/High 三级。

3. **Anytime Progress 轨迹指标** — 引入 AUC_B（归一化曲线下面积）、首次可行时间、stagnation episode（停滞窗口）、cross-stage rollback 精确率等轨迹级指标，捕捉「Agent 怎么成功的」而不仅是「最终答案好不好」。

4. **开放可执行 Harness** — 基于 Harbor 封装 Verilator + Yosys + OpenROAD + KLayout + Sky130HD PDK，提供从仿真到签核的完整开源工具链。Pristine evaluator 从原始脚本重建并在隐藏条件下运行，防止 Agent 缓存或作弊。

5. **Completion-Closure Gap 的实证暴露** — 10-task pilot 证明：同一模型同一套工具，修复任务满分不等于验证闭合任务能及格。这个差距来自长反馈链路上的因果推理需求 >> 短反馈链路的局部模式匹配能力。

## 2. EDA 阶段映射（①-⑰）

CLOSER-Bench 的核心特征是「跨阶段迭代」——不是一次跑通各阶段，而是在 ③~⑬ 区间内反复回退、修正、再推进，直到所有约束同时满足。下面按 17 阶段标准编号映射。

| 阶段 | 覆盖 | 涉及的任务 / 阶段 | 说明 |
|------|:---:|------|------|
| **① RTL 设计** | ✅ 核心 | Task A（spec->RTL）、Task C（spec->GDS）| Agent 从自然语言规格编写/修改可综合 Verilog；pilot 中的 PicoRV32 debug、AXI DWC repair、Vortex multifault 均检测 RTL 编写与修复能力 |
| **② RTL 功能仿真** | ✅ 核心 | 有效性门控第一关 G_func；pilot 中的 PicoRV32 coverage（Verilator line coverage）、axi-dwc-verify（mutation-kill）| Verilator 验证功能正确性；axi-dwc-verify 任务中 Agent 仅可编辑 testbench，按 kill 的 17 个隐藏转换器故障比例计分 |
| **③ 逻辑综合** | ✅ 核心 | Task B（RTL->GDS）、Task C（spec->GDS）；PicoRV32 fmax 任务 | Yosys 0.64 综合，Agent 需选综合策略和约束；fmax 任务中 Codex 达到 181.7 MHz（满分目标 120 MHz），Oracle 99.0 MHz，Big-Pickle 110.1 MHz |
| **④ 门级仿真** | ✅ 核心 | 有效性门控 G_gls 因子 | Verilator 对综合后门级网表跑 testbench，防止仿真-综合分歧 |
| **⑤ STA（静态时序分析）** | ✅ 核心 | 全流程迭代的核心反馈信号 | OpenSTA（OpenROAD 内嵌）多角 STA；WNS 为负触发回退决策——Agent 必须判断回退到哪一抽象层（RTL / SDC / floorplan） |
| **⑥ 形式验证（LEC）** | ✅ 核心 | 有效性门控 G_lec 因子 | Yosys LEC 检测逻辑变化型优化是否改变了设计功能 |
| **⑦ 布局规划（Floorplan）** | ✅ 核心 | Task B、Task C 可编辑 floorplan 约束 | OpenROAD floorplan；pilot 中 PicoRV32 PnR 运行时 global placement + detailed routing 占 90% |
| **⑧ 标准单元摆放（Placement）** | ✅ 核心 | OpenROAD global placement | 与 detailed routing 合计占 PicoRV32 约 90% 运行时间（论文 Table 3）；Agent 可调 placement density 和 effort |
| **⑨ 时钟树综合（CTS）** | ✅ 核心 | OpenROAD CTS | Agent 可调整时钟约束和 CTS 参数 |
| **⑩ 布线（Routing）** | ✅ 核心 | OpenROAD detailed routing；有效性门控 G_route 因子 | 与 placement 合计占 PicoRV32 约 90% 运行时间；Phase-0 三设计均生成 GDS 且零 route DRC violation |
| **⑪ 后仿真** | ❌ | — | 不在当前 pilot 中作为独立门控 |
| **⑫ 物理验证（DRC + LVS）** | ✅ 核心 | 有效性门控 G_drc + G_lvs 双因子 | KLayout 0.30.7 执行 DRC + LVS；零 DRC violation 是 GDS 有效性的硬门槛 |
| **⑬ 签核（Signoff）** | ✅ 目标 | 最终 oracle 判定 | 判定设计是否满足全部约束（WNS>0, DRC=0, LVS 通过）；论文发表时 firdma macro-based flow 的 final signoff 仍为 pending |
| **⑭-⑰** | ❌ | — | 不涉及流片/制造/封装/测试 |

**覆盖率：12/17（①-⑩、⑫-⑬）。**

CLOSER-Bench 的独特定位：在 ③→⑬ 区间内，它评测的不是「能不能按顺序跑通各阶段」，而是「跑不通时 Agent 能不能在预算限制下找到正确的回退路径」。典型的 design closure 迭代包括：综合后 WNS 为负 → 改 RTL/约束重新综合 → 布局后时序恶化 → 调整 floorplan → 布线后 hold violation → 回到 CTS 层插缓冲器 → DRC fail → 重新布局。

**与 FluxBench 和 PDAGENT-BENCH 的覆盖对比：**

| 维度 | FluxBench | CLOSER-Bench | PDAGENT-BENCH |
|------|-----------|-------------|---------------|
| 流程覆盖 | ③~⑫（RTL-to-GDS 全流程）| ③~⑬（design closure，延伸至 signoff）| ⑦~⑩（物理设计）|
| 核心问题 | 流程能不能一次跑通（one-pass pipeline）| 跑不通时能不能正确回退（iterative convergence）| Agent 在物理设计各子任务上的细粒度能力 |
| 评测对象 | 传统算法 flow 参数调优 | LLM Agent 的跨阶段决策策略 | LLM/VLM Agent 的五维能力（知识/感知/推理/工具/全流程）|
| 预算约束 | 无 | 有（仿真/综合/PnR/wall-clock 三级预算）| 有（micro/meso/macro 三级重试预算）|
| 签核覆盖 | DRC | DRC + LVS + STA（多角）| DRC（LVS 未覆盖）|

CLOSER-Bench 与 FluxBench 的关系：FluxBench 评测「给定 RTL，流水线能不能一次跑通所有阶段」，CLOSER-Bench 评测「跑不通时，Agent 能不能在有限预算下找到正确回退路径」。两者评测的是 EDA Agent 能力谱的两个正交维度（一次性通过 vs 迭代收敛），理想的完整评测应同时覆盖。

CLOSER-Bench 与 PDAGENT-BENCH 的关系：PDAGENT-BENCH 聚焦物理设计段（⑦⑧⑨⑩），评测 Agent 在 floorplan/placement/CTS/routing 各子任务上的细粒度能力（知识理解、报告解读、根因分析、脚本生成、全流程实现五个维度）。CLOSER-Bench 则跨越更大范围（③~⑬），但评测维度集中在「跨阶段决策策略」而非「单阶段技能掌握」。PDAGENT-BENCH 回答「Agent 会不会做 floorplan」，CLOSER-Bench 回答「floorplan 做坏了 Agent 知道该退回去改 RTL 还是改 floorplan 参数」。

> 最容易误读的边界：CLOSER-Bench 的 spec->GDS 不是「一键生成芯片」，而是在共享设计意图和隐藏条件下评测 Agent 在 RTL/SDC/floorplan/flow 等多抽象层之间的决策能力。10-task pilot 不等于成熟排行榜，不等试验次数，属「诊断性验证」。

## 3. 输入 / 输出

### 3.1 输入

CLOSER-Bench 的输入是一个**受控跨阶段任务上下文包**，包含六个层次：

**（1）共同设计规格 s**

所有 stage-paired 任务共享的自然语言/结构化设计意图。纵向切片 firdma 是一个流式 FIR（Finite Impulse Response，有限脉冲响应）加速器，包含以下功能模块：

- AXI-Lite 控制平面：寄存器读写接口
- DMA（Direct Memory Access，直接存储器访问）风格读写引擎：可配置突发长度和反压
- FIR 计算核心：乘法累加（MAC）流水线
- FIFO（First In First Out，先进先出队列）缓冲：输入/输出数据缓冲
- 中断/状态/错误处理：完成中断、溢出/下溢错误报告
- SRAM（Static Random-Access Memory，静态随机存储器）macro：替换原 flop-FIFO 实现

```
spec 示例（firdma 功能意图）：
- AXI-Lite slave 接口，地址空间 0x00-0xFF
- 控制寄存器：FIR_START(0x00)、FIR_LENGTH(0x04)、FIR_STATUS(0x08)
- DMA 读引擎从 AXI 总线读取 LENGTH 个 16-bit 样本
- FIR 系数为 [c0, c1, c2, c3, c4, c5, c6, c7]，存储在寄存器 0x10-0x2C
- DMA 写引擎将 LENGTH 个 16-bit 滤波结果写回内存
- 支持 AXI 反压（backpressure）和 abort（中止）语义
- 目标：200 MHz 下完成，面积 < 0.1 mm²（Sky130）
```

初始 flop-FIFO 版本经 Yosys/slang 综合产出 23,789 cells。512-entry Sky130 SRAM macro 替换版本是纵向切片的当前工作版本。

**（2）隐藏条件集 Omega**

每个任务实例化时，从以下类别的私有参数中随机采样——Agent 仅见公开子集，最终评测在隐藏条件下进行（论文仅给出类别，以下具体值为基于 AXI/DMA 上下文的合理推测示例）：

- AXI 数据宽度：e.g. 64-bit / 128-bit / 256-bit（合法值示例）
- 突发长度：e.g. 1 / 4 / 8 / 16（合法值示例）
- 反压配置：随机 stall 概率（论文未指定具体百分比）
- PVT（Process, Voltage, Temperature）corner：论文未公开具体 corner 组合
- Floorplan seed：不同的初始 macro 放置方案
- 目标工作负载：随机合法 AXI transaction 序列

公开条件与私有条件互不相交——例如 Agent 可能被告知「AXI 宽度为 64-bit」，但实际评测使用 128-bit 加随机反压。

**（3）可编辑表面（Edit Surface）**

| Track | 可编辑 Artifacts | 不可编辑 |
|-------|-----------------|---------|
| Task A（spec->RTL） | RTL 源码（SystemVerilog）、基础时序约束 | SDC、floorplan、flow 脚本 |
| Task B（RTL->GDS） | RTL 微调、SDC 约束、floorplan 定义、ORFS flow 配置参数 | Spec 定义 |
| Task C（spec->GDS） | 以上所有 + 跨层 artifacts 的任意组合 | 工具链二进制、参考模型、prebuilt testbench |

**（4）预算约束（AXI/DMA 配对任务暂定）**

| 资源 | Low | Medium | High |
|------|-----|--------|------|
| 仿真调用次数 | 40 | 100 | 不限制（仍计数）|
| 综合/STA 调用次数 | 10 | 25 | 60 |
| 完整 PnR 调用次数 | 3 | 8 | 20 |
| Wall-clock 上限 | 4 h | 10 h | 24 h |

预算分层的依据来自 Phase-0 物理可行性测量：PicoRV32（27.6k 实例）完整 PnR 18.3 分钟，Chameleon（492.7k 实例，6 个 macro）22.3 分钟。

**（5）Agent 动作空间**

在规定的编辑表面上修改源文件/脚本/约束，通过 Harbor 封装的四个工具类接口调用工具链：仿真（Verilator）、综合/STA（Yosys + OpenSTA）、完整 PnR（OpenROAD）、最终验证器（pristine evaluator）。

**（6）Harbor 运行环境**

隔离的 agent/workspace/verifier 三区布局、网络禁用、任务容器化。固定 Phase-0 Docker 镜像：`openroad/orfs:26Q3-52-gc90beac09`（内含 Yosys 0.64 + KLayout 0.30.7）。

### 3.2 输出

CLOSER-Bench 输出一套**多维轨迹级评测结果**，而非单一分数：

**（1）有效性门控 G(x, omega)** — 七因子二进制乘积，判定候选设计是否物理有效：

$$
G(x, \omega) = G_{\text{func}} \cdot G_{\text{lec}} \cdot G_{\text{gls}} \cdot G_{\text{sta}} \cdot G_{\text{route}} \cdot G_{\text{drc}} \cdot G_{\text{lvs}}
$$

- $G_{\text{func}}$：RTL 功能仿真通过（Verilator + 隐藏 testbench seed）
- $G_{\text{lec}}$：逻辑等价性检查通过（Yosys LEC）
- $G_{\text{gls}}$：门级仿真通过（综合后网表 vs RTL 行为一致）
- $G_{\text{sta}}$：多角 STA 通过（全部 WNS >= 0）
- $G_{\text{route}}$：布线完成且连通
- $G_{\text{drc}}$：零 DRC violation
- $G_{\text{lvs}}$：Layout vs Schematic 通过

阶段不适用的因子取 1；任意一项为 0 → 整个候选得 0。

**（2）质量评分 R(x, omega)** — 在有效候选上按预注册目标计算的连续评分：

$$
\ell_j(x, \omega) = \max\left\{0,\ \log\frac{m_j(x, \omega)}{m_j^*}\right\}
$$

- $\ell_j(x, \omega)$：指标 j 的超额损失（当实测值超过目标值的对数惩罚）
- $m_j(x, \omega)$：候选设计在隐藏条件 omega 下实测的第 j 项指标（area、delay、power、cycles）
- $m_j^*$：预注册目标值

$$
R(x, \omega) = G(x, \omega) \cdot \exp\left(-\sum_j w_j \cdot \ell_j(x, \omega)\right)
$$

- $R(x, \omega)$：最终质量评分，取值 [0, 1]
- $w_j$：预注册权重
- 全部达成 → R = 1；无效 → R = 0；进展中 → R in (0,1)
- 对数缩放确保「超额 2 倍」和「超额 10 倍」的惩罚可比

**（3）Anytime Progress 轨迹与 AUC_B**

$$
\text{AUC}_B = \frac{1}{B} \int_0^B r^*(c) \, dc
$$

- $B$：总预算额度
- $c$：累计成本（wall-clock 时间或 EDA 工具调用次数）
- $r^*(c)$：成本 c 之前观察到的 best-so-far reward
- AUC_B = 1：从零时刻满分并维持；接近 0：几乎全程零分
- 两个 Agent 可能最终 reward 相同，但 AUC_B 差异巨大——AUC 捕捉「多早开始收敛」

**（4）辅助轨迹指标**

| 指标 | 定义 | 衡量什么 |
|------|------|---------|
| 首次可行时间 | $\min\{c : G(x(c), \omega) = 1\}$ | Agent 多快找到第一个物理有效候选 |
| 到达阈值时间 | $\min\{c : r^*(c) \geq \theta\}$ | Agent 多快达到预注册质量目标 |
| 昂贵调用占比 | $N_{\text{PnR}} / N_{\text{total}}$ | Agent 对昂贵工具的依赖程度 |
| Public-private gap | $R_{\text{public}}(\omega) - R_{\text{hidden}}(\omega)$ | Agent 是否过拟合到可见配置 |
| Rollback 精确率 | $P(\text{rollback 后 final } R > \text{rollback 前 } r^*)$ | 跨阶段回退后能否真正恢复并改进 |
| Stagnation 检测 | 预注册窗口内 r* 无变化 | Agent 是否在做无用功 |
| Run-to-run variance | 重复试验的 R 标准差 | 策略稳定性 |
| Provenance | 区分 4 种终止原因 | Agent 失败 / Agent 超时留有效 patch / 验证器失败 / 基础设施失败 |

**（5）输出示例**

```
axi-dwc-verify, Codex/GPT-5.6, Medium budget:
  G(x,omega) = 1 (all 7 gates passed)
  R(x,omega) = 1.000 (17/17 hidden faults killed, golden alarm = 0)
  AUC_B = 0.84
  first-feasible = 1.2h wall-clock
  PnR ratio = 0.75 (75% of budget consumed by PnR calls)
  public-private gap = 0.12
  rollback count = 2 (RTL -> SDC -> floorplan, both improved reward)
```

## 4. Benchmark 构建方法

CLOSER-Bench 的构建基于四个设计原则和一个受控实验协议，其核心思想是：**评测的不是 Agent 在一个已知问题上的表现，而是在不确定、高成本、多回退的迭代中做决策的质量。**

### 4.1 四项设计原则

**原则 1：First feasible is not finished。** 每个任务在有效性门控之后还有分级质量目标（area、delay、power、cycles）。Agent 需要持续 trade PPA 各维度——一个 WNS 为正但面积超标的设计不算闭合。这迫使 Agent 在「接受当前方案」和「继续优化」之间做真实的工程决策。

**原则 2：Delay must carry information。** 昂贵工具揭示的事实与快速代理不同。一次完整 PnR 可能需要数十分钟，但能暴露布局拥塞和真实走线延迟——仅靠综合/STA（分钟级）无法获取这些信息。预算约束强制 Agent 权衡：什么时候值得花一次 PnR 来获取更精确的反馈，什么时候基于不精确信息推进就够了。

**原则 3：Public feedback is not the final oracle。** 隐藏的工作负载、AXI 配置、PVT corner、floorplan seed 与公开条件互不相交。Agent 在公开条件下表现好 ≠ 策略真正泛化。RTL 和门级仿真防止仿真-综合分歧，LEC 防止逻辑变化型优化，unconstrained-path audit 防止时序逃避，DRC/LVS 防止物理无效。

**原则 4：Every result has provenance。** 四种终止状态严格区分：Agent 主动报告「无法完成」、Agent 超时但留下了一个 scoreable patch（通过有效性门控但未收敛）、验证器无法完成评测（工具崩溃）、基础设施失败（网络/认证/Docker 问题）。这避免了传统 benchmark 中「Agent 跑了但结果无效」被错误归因为 Agent 失败的常见问题。

### 4.2 Stage-Paired 任务协议

这是 CLOSER-Bench 最核心的构建创新。设共同设计规格为 s，隐藏条件集为 Omega：

- **Task A（spec->RTL）**：从 s 出发，终止于经综合投影验证的 RTL checkpoint。编辑面：RTL 源码、基础约束。Oracle：最终签核 oracle 经综合投影（即只跑 RTL 仿真 + 综合 + LEC + 门级仿真）。
- **Task B（RTL->GDS）**：从功能正确但物理弱化的 canonical 实现 x_B 出发。编辑面：RTL 微调、SDC 约束、floorplan 定义、flow 脚本。Oracle：完整签核 oracle。
- **Task C（spec->GDS）**：从 s 出发，编辑面为 A 和 B 的并集——全部跨阶段 artifact。Oracle：完整签核 oracle。

三个核心比较维度：

1. **A vs C 在 verified-RTL checkpoint**：独立做 spec->RTL vs 在 spec->GDS 中嵌入做 spec->RTL，Agent 是否因为知道还要走物理设计而改变 RTL 策略？
2. **B vs C 在首次 feasible layout 之后**：从功能正确但物理弱化的 RTL 出发 vs 从零开始——Agent 在编辑自由度更大时是更优还是更差？
3. **A+B（独立求解后拼接）vs C（同等聚合预算下一次性求解）**：分离「分阶段决策」与「跨阶段一次性决策」的优劣——这是 RQ1 的核心实验。

功能子集 Omega 对所有 track 共享；B 与 C 由同一签核 oracle 评估。共享的工作负载、约束和签核检查使性能差异归因于阶段边界的存在/缺失，而非不相关的任务内容。

### 4.3 Trajectory Wrapper 与隐藏评测

Trajectory wrapper（而非 Agent）负责计数四类工具调用（仿真、综合/STA、完整 PnR、最终验证器）和 wall-clock 时间，记录每个时间戳的修改文件、推断出的编辑层（RTL/constraint/floorplan/flow）、工具结果和 best-so-far reward。

Pristine evaluator 从 Agent 修改后的源码出发，使用原始脚本重新构建，在**隐藏条件**下运行完整流程：RTL 仿真 → 综合/LEC → 门级仿真 → 多角 STA → 布线 → DRC/LVS → 签核检查。Agent 无法缓存、预计算或依赖公开条件作弊。

### 4.4 Pilot Suite 构建（10 任务）

10 个可执行任务跨 4 个仓库、7 种能力类型，用于验证 harness 和揭示奖励设计失败模式：

| 任务 | 能力维度 | Oracle 类型 | 角色 |
|------|----------|------------|------|
| PicoRV32 fmax | RTL 时序优化 | hidden RTL+GLS, pristine STA | continuous pilot（目标 120 MHz，Codex 达 181.7 MHz → 目标已饱和）|
| PicoRV32 coverage | 验证闭合 | Verilator line coverage | iterative pilot（Codex 88.7%，cap 85% → cap 饱和）|
| PicoRV32 debug | RTL 修复 | 6 hidden tests | smoke task（已被 frontier agent 饱和）|
| Vortex SimX DSE | 约束 DSE | kernel speedup under area cap | continuous pilot（cap 已饱和）|
| Vortex SIMT debug | 模型调试 | 6 scored kernels | smoke task（多个模型可解）|
| Vortex dual-model | RTL/reference differential | 3 hidden kernels | 验证 cross-model oracle（局部可解）|
| Vortex multifault | 分级 RTL 修复 | 3 independent faults | 一次有效 Haiku run 修复 2/3 |
| AXI DWC repair | 协议/数据通路修复 | hidden byte scoreboard | matched completion control（已饱和）|
| AXI DWC verify | mutation-kill 闭合 | 17 hidden faults + golden alarm gate | matched closure control（有区分度）|
| Ibex secure abort | 安全/非干扰 | hidden RVFI traces | 真实上游缺陷（Agent 运行 pending）|

Pilot 的设计意图：不是做排行榜，而是暴露 completion-closure gap。axi-dwc-repair 和 axi-dwc-verify 使用同一 PULP AXI data-width converter 设计——前者 Agent 修复两个 byte-lane 缺陷（固定位置、定向修复），后者 Agent 仅可编辑 Verilator testbench、kill 17 个 hidden converter fault 且 golden RTL 不得误报。两种任务对因果推理的需求完全不同。

## 5. 关键公式

CLOSER-Bench 定义了四个层次的形式化判定标准。

### 5.1 有效性门控 G(x, omega)

$$
G(x, \omega) = G_{\text{func}} \cdot G_{\text{lec}} \cdot G_{\text{gls}} \cdot G_{\text{sta}} \cdot G_{\text{route}} \cdot G_{\text{drc}} \cdot G_{\text{lvs}}
$$

- $G_{\text{func}}$：RTL 功能仿真通过
- $G_{\text{lec}}$：逻辑等价性检查通过
- $G_{\text{gls}}$：门级仿真通过
- $G_{\text{sta}}$：多角 STA 全部通过
- $G_{\text{route}}$：布线完成
- $G_{\text{drc}}$：零 DRC violation
- $G_{\text{lvs}}$：LVS 通过

每个因子为二值（0 或 1）；阶段不适用的因子取 1。

**工程直觉**：这不是「打分」，是「关卡」。仿真是第一关（功能对不对），LEC 第二关（综合改错了没），门级仿真第三关（综合后时序上对不对），STA 第四关（所有路径时序满足吗），布线第五关（物理能连上吗），DRC 第六关（制造规则满足吗），LVS 第七关（版图和网表是同一个电路吗）。只有全通才能进入质量评分——这比传统的「仿真通过 = 成功」严格得多。

### 5.2 单目标超额损失 l_j(x, omega)

$$
\ell_j(x, \omega) = \max\left\{0,\ \log\frac{m_j(x, \omega)}{m_j^*}\right\}
$$

- $\ell_j(x, \omega)$：指标 j 的超额损失
- $m_j(x, \omega)$：实测值
- $m_j^*$：预注册目标值

**为什么取对数**：线性惩罚会让「超额 2 倍」和「超额 10 倍」的差距被放大 5 倍，但工程上两者都是「不达标」——对数缩放使得「超额 2 倍」（ln(2) ≈ 0.69）和「超额 10 倍」（ln(10) ≈ 2.30）的惩罚在合理范围内，同时超额越多惩罚越重。max{0, ...} 表示低于目标时不奖励（但也不惩罚——因为你已经达成了目标），这是一种「软上界」设计。

### 5.3 最终质量评分 R(x, omega)

$$
R(x, \omega) = G(x, \omega) \cdot \exp\left(-\sum_j w_j \cdot \ell_j(x, \omega)\right)
$$

- $R(x, \omega)$：最终质量评分，取值 [0, 1]
- $w_j$：预注册权重（反映各 dimension 的相对重要性）
- $G(x, \omega) = 0$ → $R = 0$（物理无效候选零分）
- $\sum_j w_j \cdot \ell_j = 0$（全部目标达成）→ $R = 1$（满分）
- 部分达成 → $R \in (0, 1)$（连续评分，反映距离目标的远近）

**工程直觉**：exp(-sum(...)) 是一个「相乘型」评分——每个未达标的 dimension 都会独立地压低总分，压低程度由 log-ratio 决定。这模仿了实际设计中「一个 dimension 不达标（如功耗超标 50%）会否决整个设计，即使其他 dimension 表现完美」的现实。

### 5.4 归一化 Progress AUC

$$
\text{AUC}_B = \frac{1}{B} \int_0^B r^*(c) \, dc
$$

- $B$：总预算
- $c$：累计成本
- $r^*(c)$：成本 c 之前的最佳 so-far reward

**工程直觉**：这是「投资回报率」的连续版本。两个 Agent 最终 reward 都是 0.9，但一个在第 1 小时就达到 0.9 并维持（AUC ≈ 0.9），另一个在第 9 小时才从 0 跳变到 0.9（AUC ≈ 0.1）。AUC_B 捕捉到这个差异——它惩罚「在无效尝试中浪费预算」的策略。

**为什么引入 AUC**：传统 pass/fail 只看终点，但 design closure 是过程——什么时候第一次 feasible、是否在 stagnation（原地踏步）、回退后能否恢复——这些轨迹特征比终点分数更能揭示 Agent 的决策质量。

### 5.5 跨阶段回退判定

论文未给编号公式，以下是对其算法行为的形式化：

设 Agent 在成本 c 时的编辑层为 $L(c) \in \{\text{RTL}, \text{SDC}, \text{floorplan}, \text{flow}\}$，则跨阶段回退定义为：

$$
\exists\ c_1 < c_2: L(c_2) \text{ 在抽象层次上早于 } L(c_1) \text{ 且 } r^*(c_2 + \Delta) > r^*(c_1)
$$

- $c_1, c_2$：两个时刻的累计成本，$c_1 < c_2$ 表示 $c_1$ 在前
- $L(c)$：成本 $c$ 时刻 Agent 正在修改的抽象层次（RTL / SDC / floorplan / flow）
- $r^*(c)$：成本 $c$ 之前的最佳 so-far reward
- $\Delta$：回退后给它继续优化的观察窗口

即 Agent 在收到后期阶段反馈后，回到更早的抽象层修改，并且修改后 reward 确实提升了。如果回退后 reward 未提升，则计为「无效回退」或 stagnation。

## 6. 评测协议与打分

CLOSER-Bench 的评测协议与传统 benchmark 有两个根本区别：它不是 pass@k，而是 reward trajectory；它不只看最终结果，而是全程记录 Agent 的每一步决策。

### 6.1 评测协议

**（1）Trajectory 记录协议**

Trajectory wrapper 在每次 Agent 调用 EDA 工具时记录以下维度：

- 时间戳（wall-clock）
- 修改的文件列表
- 推断出的编辑层：RTL / SDC / floorplan / flow
- 工具输入（传给 Verilator/Yosys/OpenROAD 的完整命令）
- 工具输出摘要（通过/失败/错误信息）
- 累计成本 c（按工具类别的加权和或 wall-clock）
- 当前 best-so-far reward r*(c)

**（2）评测触发条件**

Trajectory wrapper 在以下时机触发 pristine evaluator：

- Agent 显式调用最终验证器
- Wall-clock 或调用预算耗尽
- Agent 进程超时（如果留下了 scoreable patch）

Pristine evaluator 使用隐藏条件 Omega 从原始脚本重新构建并运行完整流程，返回 G(x, omega) 和 R(x, omega)。

**（3）Provenance 分类**

| 终止状态 | 记录方式 | 是否计分 |
|---------|---------|---------|
| Agent 成功 | 最终 G(x,omega) 和 R(x,omega) | 是 |
| Agent 失败（主动报告无法完成）| 无 scoreable patch，记录为 agent-reported failure | 否（不计分，保留 provenance）|
| Agent 超时，留 scoreable patch | 对 patch 运行 pristine evaluator | 是 |
| Agent 超时，无 scoreable patch | 不计分，记录为 invalid run | 否 |
| 验证器失败（tool crash）| 不计分，记录为 infrastructure error | 否 |
| 基础设施失败（网络/认证/Docker）| 不计分，记录为 infrastructure error | 否 |

### 6.2 打分指标汇总

| 指标 | 类型 | 说明 |
|------|------|------|
| G(x, omega) | 二值关卡 | 七因子乘积，0 或 1 |
| R(x, omega) | 连续 [0,1] | 质量评分 |
| AUC_B | 连续 [0,1] | 归一化 progress 曲线下面积 |
| 最终 reward | 连续 [0,1] | B 时刻的 r*(B) |
| 首次可行时间 | wall-clock / 调用计数 | min c where G=1 |
| 到达阈值时间 | wall-clock / 调用计数 | min c where r* >= theta |
| 昂贵调用占比 | [0,1] | N_PnR / N_total |
| Public-private gap | 实数 | R_public - R_hidden |
| Rollback 精确率 | [0,1] | 有效回退 / 总回退 |
| Stagnation count | 整数 | 预注册窗口内无改善的次数 |
| Run-to-run variance | 实数 | 重复试验 R 的标准差 |

### 6.3 与传统 pass@k 的区别

CLOSER-Bench 不使用 pass@k。原因：design closure 不是「从 n 次尝试中选 k 次看是否至少一次通过」的独立采样问题，而是一个**序列决策过程**——每一次尝试消耗真实预算（时间+计算资源），前面失败的信息会影响后续决策。AUC_B 正是为了捕捉「在什么成本下取得什么进展」的序列信息而设计的。

## 7. 实验与发现

### 7.1 实验设置

**Agent/模型配置（pilot 阶段）**：
- Codex / GPT-5.6
- OpenCode / Big-Pickle
- OpenCode / DeepSeek-V4

**工具链**：Harbor harness + Verilator + Yosys 0.64 + OpenROAD + KLayout 0.30.7 + Sky130HD PDK

**硬件**：96-core 主机（Phase-0 物理流可行性测试）、网络禁用任务容器（pilot 试验）

**试验设计**：不等试验次数（diagnostic 而非 ranking）。axi-dwc-repair 每个配置 2 次、axi-dwc-verify 每个配置 1 次。

### 7.2 物理流程可行性（Table 3）

| Design | Instances | Macros | Time | Final status |
|--------|-----------|--------|------|-------------|
| GCD | 751 | 0 | 2.9 min | WNS -1.46 ns |
| PicoRV32 | 27,590 | 0 | 18.3 min | WNS +5.44 ns |
| Chameleon | 492,693 | 6 | 22.3 min | WNS -0.04 ns |

三个设计均生成 GDS 且零 route DRC violation。PicoRV32 在 12 ns 时钟下 WNS +5.44 ns，验证工具链可行性。Global placement + detailed routing 占 PicoRV32 90% 运行时间，支持将廉价综合和昂贵 PnR 分别预算。这些测量验证了 4/10/24 小时预算分层合理，但 **尚未确立最终 firdma 的难度等级**。

### 7.3 AXI 完成-闭合对照（Table 4，核心实验）

| Agent/model | Repair | Verify |
|-------------|--------|--------|
| Codex/GPT-5.6 | **1.000** (2/2) | **1.000** (17/17) |
| OpenCode/Big-Pickle | **1.000** (2/2) | 0.0588 (1/17) |
| OpenCode/DeepSeek-V4 | **1.000** (2/2) | 0.000 (golden alarm) |

这张表是论文最核心的实验发现：

- **axi-dwc-repair**：Agent 修复固定 64-to-128-bit upsizer 中的两个 byte-lane 缺陷——这是一个局部推理任务（已知位置、短反馈回路）。三个 Agent 全部满分。
- **axi-dwc-verify**：Agent 仅可编辑 Verilator testbench，目标是 kill 17 个 hidden converter fault——这是一个系统级因果推理任务（未知 fault 位置、需覆盖 17 种错误模式、golden alarm 零容忍）。只有 Codex 满分。
- **DeepSeek-V4 在 verify 上得 0.000** 的原因是触发了 golden alarm（对 golden RTL 误报 fault）——不是没找到 fault，而是产生了 false positive，导致整个 run 无效。
- **Big-Pickle 仅 kill 1/17**，在 28.7 分钟内无法生成足够的 fault 覆盖——agent 缺乏在开放搜索空间中系统地覆盖 fault 空间的策略。

这说明：能修 bug（completion）不等于能验证设计（closure）。Verification 需要 Agent 在 17 个 fault 空间中系统搜索且绝对不能误报黄金行为——这比修复已知位置的缺陷需要更长反馈链路的因果推理。**这一发现直接指向 LLM Agent 的根本局限：长反馈链路上的因果推理能力 << 短反馈链路的局部模式匹配能力。**

### 7.4 其他 Pilot 结果

**PicoRV32 fmax**：Codex 达到 181.7 MHz（满分目标 120 MHz），Oracle 99.0 MHz，Big-Pickle 110.1 MHz。奖励 cap 设计饱和——原始 MHz 指标必须伴随归一化 reward。

**PicoRV32 coverage**：Codex 达 88.7% line coverage（cap 85%）。Line coverage alone 不表示 checker 强度——需要 mutation coverage 或 formal property coverage 升级。

**Vortex multifault**：一次有效 Haiku run 修复 3 个独立 fault 中的 2 个，得分为 2/3。

### 7.5 尚未完成的核心实验

论文明确指出以下实验不在当前 pilot 范围内，是未来的 benchmark release 内容：

- Tasks A-C 的全部 3x3（3 个 model/ scaffold x 3 个 budget tier）重复试验矩阵
- A+B vs C 在同等聚合预算下的对比（RQ1）
- 跨阶段恢复混淆矩阵（RQ2：Agent 在 RTL/SDC/floorplan/flow 四层之间回退的精确率和召回率）
- Low/Medium/High 预算 progression curves + bootstrap confidence intervals（RQ3）

## 8. 创新点

**创新点 1：将 Design Closure 建模为预算约束下的序列决策问题。** 已有 benchmark（RTLLM、VerilogEval）评单点 RTL 生成，FluxBench 评 RTL-to-GDS 一次跑通。CLOSER-Bench 是第一个把「什么时候调用昂贵 PnR」「什么时候退回去改 RTL」「什么时候接受够好但不完美的方案」变成形式化评测对象的 benchmark。预算约束不是锦上添花，而是评测的核心维度——一个不知道节制 PnR 调用的 Agent 会在 Low budget 下耗尽预算而未收敛，而一个善于用廉价仿真替代昂贵 PnR 做预筛选的 Agent 会在同一预算下取得更高 AUC。

**创新点 2：Stage-Paired 分离「单阶段能力」与「跨阶段协调能力」。** A/B/C 三 track + A+B vs C 聚合对比，首次在 EDA Agent 评测中系统分离了这两个维度。Pilot 中同一模型 A 满分但 C 失败的潜在模式（尚未大规模验证，但 protocol 已就绪）精确捕捉了「不会在物理反馈下调整 RTL」这种能力缺口。

**创新点 3：Anytime Progress 指标族。** 传统 benchmark 只看 final pass/fail 或 best-of-N accuracy。CLOSER-Bench 引入 AUC_B、首次可行时间、stagnation、rollback 精确率等轨迹级指标——把「Agent 怎么成功的」变成可量化维度。这张「progress curve」在工业界的实际意义是：一个 AUC=0.9 的 Agent 可以在预算进行到 10% 时就锁定可行方案并持续优化，而一个 AUC=0.2 的 Agent 直到预算耗尽前一分钟才碰巧找到方案——前者才是能嵌入实际设计迭代流程的工具。

**创新点 4：Public-Private 条件分离。** 公开条件用于 Agent 决策，隐藏条件用于最终评测。这暴露了一个关键问题：Agent 是否过拟合到可见配置？例如一个 Agent 可能针对可见的 AXI 64-bit 宽度做了专项优化，但换成隐藏的 128-bit 立即失败。Public-private gap 量化了这个泛化差距。

**创新点 5：Completion-Closure Gap 的实证发现。** 10-task pilot 的核心贡献不是具体分数，而是通过精心设计的 matched pair（axi-dwc-repair vs axi-dwc-verify）首次给出了「completion != closure」的定量证据。

| AXI | Advanced eXtensible Interface | ARM 定义的高性能片上总线协议 |
| DMA | Direct Memory Access | 直接存储器访问——不经过 CPU 的数据搬移 |
| FIFO | First In First Out | 先进先出队列 |
| SRAM | Static Random-Access Memory | 静态随机存储器（比寄存器阵列密度高）|
| RVFI | RISC-V Formal Interface | RISC-V 形式验证接口——trace 格式用于验证 |
| SIMT | Single Instruction Multiple Threads | GPU 的线程执行模型（Vortex 用到的架构）|
| ORFS | OpenROAD Flow Scripts | OpenROAD 的标准自动化流程脚本集 |

## 10. 讨论与局限

### 10.1 论文自述局限

1. **Pilot 仅 10 任务**：不足以形成稳定排行榜，不等试验次数，属「诊断性验证」而非成熟 benchmark。
2. **垂直切片单一**：当前纵向设计仅 firdma 一个 FIR 加速器 + Sky130 一个 PDK，未覆盖多设计/多工艺的泛化评测。
3. **签核与任务打包待完成**：论文发表时 macro-based firdma flow 的 final signoff oracle 和 task checksums/containers 仍为 pending。
4. **人为注入故障**：AXI 任务中的缺陷手工注入，不能替代真实历史 bug 集群的统计分布。
5. **Token/wall-clock 不可比**：不同 Agent scaffold 的 token 计数不可直接比较，wall-clock 受主机资源竞争影响。
6. **部分 pilot 已饱和**：PicoRV32 fmax（120 MHz 目标 vs Codex 181.7 MHz）、PicoRV32 coverage（85% cap vs Codex 88.7%）等任务的 reward cap 设计被模型性能超越，无法区分后续更强模型。

### 10.2 评测公平性与可信度分析

**（1）Budget tier 的校准基础**。Low/Medium/High 三级预算是基于 Phase-0 物理流测量（PicoRV32 18.3 min、Chameleon 22.3 min PnR）推导的，但当前尚未针对最终 firdma 设计做实际测量校准。firdma 的 PnR 时间可能显著不同于 Phase-0 设计（需要 macro placement + SRAM 集成），因此预算分层的绝对数值可能需要调整。

**（2）Hidden condition 的覆盖完整性**。Omega 包含 AXI 宽度/突发/反压、PVT corner、floorplan seed 的随机采样。但这种随机化是否覆盖了所有「Agent 可能过拟合」的维度？例如不同的 SRAM macro 尺寸、不同的 FIR 系数精度、不同的总线拓扑——这些维度是否被 Omega 覆盖，论文未详细说明。

**（3）Oracle 跑分 vs Agent 跑分的公平性**。论文把 Oracle（人工设计的参考实现）的跑分与 Agent 对比作为分数天花板。但 Oracle 的 PicoRV32 fmax 仅 99.0 MHz，而 Codex 达 181.7 MHz——这暗示 Oracle 本身可能不是最优实现，或者 reward cap 设计（120 MHz）本身就低于最佳可能。reward cap 设定直接影响 R(x, omega) 的「有效区间」——如果 cap 太低，评分饱和后无法区分好和更好的 Agent。

**（4）Single-design 的泛化性局限**。Stage-paired 协议基于一个 firdma 设计——不同类型的 IP（CPU core、GPU shader、crypto engine、NoC router）对跨阶段 closure 的难度差异巨大。一个 CPU core 的 floorplan 决策对 CTS 和 routing 的影响远比一个流式加速器复杂。当前评测结论是否能泛化到其他设计类型，是待回答的关键问题。

**（5）工具链版本锁定 vs 真实设计迭代**。固定 Phase-0 Docker 镜像 `openroad/orfs:26Q3-52-gc90beac09` 保证了可复现性，但真实项目中工具版本会频繁更新、bug fix 和特性增加——Agent 在一个固定工具版本上的策略可能无法迁移到新版本。

### 10.3 本资料包的批判性分析

**（1）命题合理但证据不足**。「Completion != Closure」是核心命题，axi-dwc-repair vs verify 一对 controlled contrast 确实给出了有力证据。但 1 对 controlled contrast + 1 次 verify trial per model 不足以支撑整个命题的普适性。需要更多 matched pair（不同 IP、不同 failure mode、不同 tool stage）的重复验证。

**（2）AUC_B 的实用性未经验证**。AUC 是一个优美的理论指标，但它是否和人类工程师对「Agent 好不好用」的直觉判断一致？一个 AUC=0.6 的 Agent 和一个 AUC=0.8 的 Agent 在实际设计迭代中体验差异多大？论文没有做用户研究或人类基线对比。

**（3）隐藏条件的反 gaming 效力**。Omega 的随机化确实防止了最简单的过拟合（如 Agent 记忆固定 testbench seed），但更高级的 gaming 策略（如 Agent 在公开条件下探测 Omega 的分布特征、调整策略以覆盖最可能的隐藏条件）是否仍然有效，论文未讨论。

**（4）与 FluxBench 和 PDAGENT-BENCH 的互补定位**。三个 benchmark 共同构成了 EDA Agent 评测的完整图景：FluxBench 覆盖「流程能不能一次跑通」（③~⑫，one-pass pipeline），CLOSER-Bench 覆盖「跑不通时能不能正确回退」（③~⑬，iterative convergence），PDAGENT-BENCH 覆盖「在物理设计段的各子任务上到底强在哪弱在哪」（⑦~⑩，fine-grained capability diagnosis）。需要一个整合框架把三者的评测结果放在同一坐标系里——目前还没有这样的框架。

## 12. 一分钟复述版

1. CLOSER-Bench 把硬件 Agent 评测从「任务完成」升级为「预算约束下的跨阶段设计闭合」——核心命题：completion != closure。
2. Stage-paired 设计：从同一规格和隐藏条件派生出 spec->RTL（A）、RTL->GDS（B）、spec->GDS（C）三个 track，分离单阶段能力与跨阶段协调能力。
3. 不只看最终 pass/fail——记录每次仿真/综合/STA/PnR 调用，用 AUC_B、stagnation、rollback 精确率等 anytime progress 指标评估决策质量。
4. 有效性门控 G 需要同时通过 RTL 仿真 + LEC + 门级仿真 + 多角 STA + 布线 + DRC + LVS 七关，任一 fail 则 R=0。
5. 质量评分 R 是 exp(-weighted log-ratio penalty) 的连续评分——全部目标达标 = 1，任意维度超标按对数惩罚扣分。
6. 10-task pilot 覆盖 4 仓库 7 能力类型，核心发现来自 axi-dwc-repair vs verify matched pair。
7. 三个 Agent 在 repair（修复 2 个 byte-lane 缺陷）上全满分；在 verify（杀 17 个 hidden fault + 不准误报 golden）上 Codex 满分、Big-Pickle 0.0588、DeepSeek-V4 0.000（触发 golden alarm）。
8. 长反馈链路上的因果推理 << 短反馈链路的局部模式匹配——这是当前 LLM Agent 在物理/跨阶段设计中最致命的短板。
9. 开放工具链（Verilator + Yosys + OpenROAD + KLayout + Sky130）保证可复现性，但中心实验矩阵（A/B/C 全预算全模型 3 次重复试验）尚未完成。
10. 与 FluxBench（one-pass pipeline, ③~⑫）和 PDAGENT-BENCH（fine-grained physical design capability, ⑦~⑩）形成 EDA Agent 评测的三维互补。
